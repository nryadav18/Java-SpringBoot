66. Docker for Spring Boot

Package your Spring Boot app into a small, secure Docker image that runs the same way on your laptop, your colleague's laptop and any server in the cloud.

1. Why this matters

You know the famous sentence: “But it works on my machine!” Your app runs on your laptop with Java 17.0.19, but the test server has Java 11, a different time zone and a missing font. The production server has another OS version. Bugs appear that nobody can reproduce.

Docker solves this by packaging your app together with everything it needs — the Java runtime, OS libraries, configuration defaults — into one image. That image runs identically everywhere Docker runs: your Windows laptop, a Linux server, AWS, Azure, Google Cloud, Kubernetes.

  • Same environment everywhere — dev, test and production use the very same image.
  • Fast start — a container starts in seconds, not minutes like a virtual machine.
  • Easy extra tools — need MySQL, Kafka, Redis, Zipkin? docker run instead of installing them (you did this in topics 43, 51, 57, 58, 65).
  • Foundation for the rest of the course — Docker Compose (67), CI/CD (68) and Kubernetes (69) all work with images.
ℹ️ Where you will see this at work Practically every company that runs Spring Boot microservices ships them as container images. A typical CI pipeline: commit → tests → docker build → push to a registry → deploy the image to Kubernetes or a cloud container service. “Write a Dockerfile for this service” is a normal task for a Java developer.

2. Real-life analogy

🚢 The shipping container

Before the 1950s, ships were loaded piece by piece: sacks of rice, barrels, boxes of every shape. Every port needed different handling, loading took weeks and things broke or got lost.

Then came the standard shipping container: one size, one shape. Whatever is inside — bananas or laptops — every ship, crane, train and truck in the world can handle it the same way.

  • The packing list / instructions for filling a container = the Dockerfile.
  • A sealed, ready-to-ship container design = the image (read-only, can be copied many times).
  • A container actually on a ship, in use = a running container (you can run many from one image).
  • The port warehouse where containers are stored and picked up = the registry (Docker Hub).
  • The ship and cranes = the Docker engine — it does not care what is inside.

A virtual machine, in comparison, is like shipping a whole house (with its own foundation, plumbing and roof) just to move a sofa.

3.3 Your first Dockerfile (the simple one)

Dockerfile.simpleFROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY target/docker-demo.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Line by line:

  1. FROM eclipse-temurin:17-jre-alpine — start from an existing image that already contains a Java 17 runtime (Eclipse Temurin is the same OpenJDK build you installed; JRE = only what is needed to run, no compiler; alpine = a very small Linux).
  2. WORKDIR /app — “cd /app” (creates it if needed). Following commands run there.
  3. COPY target/docker-demo.jar app.jar — copy the jar from your computer (the build context) into the image.
  4. EXPOSE 8080 — documentation: “this app listens on 8080”. It does not open the port to your PC by itself.
  5. ENTRYPOINT [...] — the command that runs when a container starts.

Build and run it (the jar must exist first):

mvn clean package -DskipTests
docker build -f Dockerfile.simple -t docker-demo:simple .
docker run --rm -p 8080:8080 docker-demo:simple

The dot . at the end of docker build is the build context: the folder whose files Docker may COPY. Easy to forget!

3.4 Dockerfile instructions you will use

InstructionWhat it doesExample
FROMBase image. AS name names a stage (multi-stage builds).FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIRSet the working directory.WORKDIR /app
COPYCopy files from the build context (or from another stage with --from).COPY --from=build /workspace/target/x.jar app.jar

ENVEnvironment variable available at build and run time.ENV SPRING_PROFILES_ACTIVE=docker
ARGVariable only during the build (docker build --build-arg).ARG JAR_FILE=target/*.jar
EXPOSEDocument the port.EXPOSE 8080
USERRun following steps and the container as this user.USER spring
HEALTHCHECKCommand Docker runs regularly to check the app is healthy.HEALTHCHECK CMD wget -qO- http://localhost:8080/actuator/health

💡 ENTRYPOINT vs CMD, and why the JSON array form ENTRYPOINT = what runs; CMD = default extra arguments that the user can replace: docker run docker-demo:1.0 --debug replaces CMD. Always use the exec form (JSON array). With the shell form (ENTRYPOINT java -jar app.jar) Java runs as a child of /bin/sh, does not receive the stop signal from docker stop and is killed hard after 10 s — no graceful shutdown.

3.5 Layers and the build cache

Every FROM, COPY and RUN creates a layer. An image is a stack of layers. When you rebuild, Docker reuses (caches) every layer whose inputs did not change — until the first changed layer; everything after it is rebuilt.

That is why our Dockerfile copies pom.xml and downloads dependencies before copying src: editing a Java file does not invalidate the slow “download dependencies” layer.

3.6 .dockerignore

Before building, Docker sends the whole build context folder to the engine. .dockerignore (same idea as .gitignore) excludes files: faster builds, smaller context, and no secrets (like .env) sneaking into the image.

.dockerignore (part)target/*
!target/docker-demo.jar     # "!" = but DO include this one (needed by Dockerfile.simple)
.vscode/
.git/
*.md
.env

3.7 Multi-stage builds

The simple Dockerfile needs Java and Maven on the machine that builds it, and you must remember to run mvn package first. A multi-stage Dockerfile does the build inside Docker:

Stage 1 “build”
maven + JDK (~500 MB)
compiles the jar→ jar → Stage 2 “extract”
splits jar into layers→ layers → Stage 3 runtime
JRE only (~200 MB)
this is the final image

Only the last stage becomes the image. Maven, the JDK and your source code stay behind in the throw-away stages — a smaller image and a smaller attack surface.

3.8 Spring Boot layered jars

A Spring Boot “fat jar” contains your classes and ~20 MB of dependencies. If you COPY the whole jar, every code change creates a new 20 MB layer. Since Boot 2.3 the jar contains a layers.idx file, and Boot 3.3+ offers the tools jar mode to extract it into folders:

java -Djarmode=tools -jar target/docker-demo.jar extract --layers --destination extracted

extracted/
  application/            app.jar (your classes; its manifest points to ../lib)
  dependencies/           lib/*.jar
  snapshot-dependencies/
  spring-boot-loader/

(I ran exactly this command on the project in this folder: the four folders appear, and java -jar app.jar started from the merged folders works.) In the Dockerfile each folder becomes its own COPY → its own layer. You can list the layers with java -Djarmode=tools -jar target/docker-demo.jar list-layers.

3.10 Port mapping

A container has its own network. The app listens on port 8080 inside it. To reach it from your browser you publish a host port: -p HOST:CONTAINER.

Browser
localhost:9090→ -p 9090:8080 → container port 8080→ Spring Boot (Tomcat :8080) 
docker run -d --name demo1 -p 8080:8080 docker-demo:1.0
docker run -d --name demo2 -p 9090:8080 docker-demo:1.0   # second copy: same image, other host port
⚠️ localhost inside a container means the container itself If your app in a container uses jdbc:mysql://localhost:3306, it looks for MySQL inside its own container — and fails. Use host.docker.internal to reach your PC from Docker Desktop, or (better) Docker Compose service names (topic 67).

3.11 Environment variables → Spring configuration

One image must run in dev, test and prod with different settings. You never rebuild for that — you pass environment variables, which Spring Boot reads with higher priority than application.yml (topic 29). Names are converted by “relaxed binding”: UPPER CASE, dots → underscores, dashes removed.

PropertyEnvironment variable
server.portSERVER_PORT
spring.profiles.activeSPRING_PROFILES_ACTIVE
spring.datasource.urlSPRING_DATASOURCE_URL
app.greetingAPP_GREETING
app.environment-nameAPP_ENVIRONMENTNAME
docker run -d --name demo -p 8080:8080 ^
  -e APP_GREETING="Hello from Docker" ^
  -e SPRING_PROFILES_ACTIVE=docker ^
  docker-demo:1.0

# or put them in a file (one VAR=value per line) - keep it out of Git!
docker run -d --name demo -p 8080:8080 --env-file .env docker-demo:1.0

(^ continues a line in cmd; in PowerShell use a backtick `, in Git Bash \ — or simply write everything on one line.)

🚨 Never bake secrets into the image ENV DB_PASSWORD=secret in a Dockerfile is visible to anyone who can pull the image (docker history, docker inspect). Pass secrets at run time (env vars, Docker/Kubernetes secrets, a vault).

3.12 Java in a container: memory

Modern JVMs (Java 10+) understand container limits. By default the heap may use only 25 % of the container memory — often too little. Set a percentage instead of a fixed -Xmx:

docker run -d -m 512m -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0" -p 8080:8080 docker-demo:1.0
curl.exe http://localhost:8080/api/info      # "maxHeapMb": about 375

JAVA_TOOL_OPTIONS is read automatically by every JVM (you will see “Picked up JAVA_TOOL_OPTIONS…” in the log). Our Dockerfile sets it by default.

3.13 Buildpacks — an image without a Dockerfile

Cloud Native Buildpacks look at your project and build a good, layered, non-root image automatically. Spring Boot's Maven plugin supports them:

mvn spring-boot:build-image
# image name configured in pom.xml: docker-demo-buildpacks:1.0.0
docker run --rm -p 8080:8080 docker-demo-buildpacks:1.0.0
pom.xml (plugin configuration)<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
        <image>
            <name>docker-demo-buildpacks:${project.version}</name>
            <env>
                <BP_JVM_VERSION>17</BP_JVM_VERSION>
            </env>
        </image>
    </configuration>
</plugin>

3.14 Pushing to Docker Hub

A registry lets other machines (servers, colleagues, CI) pull your image. Docker Hub is free for public images.

docker login                                          # your Docker Hub username + password/token
docker tag docker-demo:1.0 yourname/docker-demo:1.0    # name must start with your username
docker push yourname/docker-demo:1.0
# on any other machine:
docker pull yourname/docker-demo:1.0

In companies you usually push to a private registry (GitHub Container Registry ghcr.io, AWS ECR, Azure ACR, Harbor, Nexus) from the CI pipeline (topic 68).

4.1 The production Dockerfile

Dockerfile# ---------- Stage 1: BUILD the jar with Maven + JDK 17 ----------
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /workspace
COPY pom.xml .
RUN mvn -B -q dependency:go-offline          # cached until pom.xml changes
COPY src ./src
RUN mvn -B -q package -DskipTests

# ---------- Stage 2: SPLIT the fat jar into layers ----------
FROM eclipse-temurin:17-jre-alpine AS extract
WORKDIR /extract
COPY --from=build /workspace/target/docker-demo.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --destination extracted

# ---------- Stage 3: the small RUNTIME image ----------
FROM eclipse-temurin:17-jre-alpine
RUN addgroup -S spring && adduser -S spring -G spring
WORKDIR /app
COPY --from=extract /extract/extracted/dependencies/ ./
COPY --from=extract /extract/extracted/spring-boot-loader/ ./
COPY --from=extract /extract/extracted/snapshot-dependencies/ ./
COPY --from=extract /extract/extracted/application/ ./
USER spring
EXPOSE 8080
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0" \
    SPRING_PROFILES_ACTIVE=docker
HEALTHCHECK --interval=30s --timeout=3s --start-period=40s --retries=3 \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "app.jar"]
  • Stage 1 uses the official Maven image, so the build machine needs nothing but Docker. -B = batch mode (no colours/progress bars), -q = quiet.
  • Stage 2 extracts the layers (section 3.8).
  • Stage 3: addgroup/adduser -S create a system user without password; USER spring means the JVM does not run as root. If an attacker breaks into the app, they are a powerless user.
  • Four COPYs = four layers, ordered from rarely to often changed. They all land in /app; app.jar's manifest finds the jars in /app/lib.
  • HEALTHCHECK uses BusyBox wget (included in Alpine) against Actuator. docker ps then shows (healthy). --start-period gives Spring time to boot.

4.3 The controller proves where it runs

HelloController.java (part)@GetMapping("/info")
public Map<String, Object> info() {
    Runtime rt = Runtime.getRuntime();
    Map<String, Object> info = new LinkedHashMap<>();
    info.put("host", hostName());                                 // container id inside Docker
    info.put("javaVersion", System.getProperty("java.version"));
    info.put("runningAsUser", System.getProperty("user.name"));   // "spring", not "root"
    info.put("maxHeapMb", rt.maxMemory() / (1024 * 1024));
    info.put("activeProfiles", Arrays.asList(environment.getActiveProfiles()));
    info.put("greeting", props.greeting());
    return info;
}

6. Common mistakes

⚠️ “failed to connect to the docker API … dockerDesktopLinuxEngine … The system cannot find the file specified” Docker Desktop is not running.
Fix: start Docker Desktop, wait for “Engine running”, try again.
⚠️ “Bind for 0.0.0.0:8080 failed: port is already allocated” Another container or your mvn spring-boot:run already uses 8080.
Fix: stop it, or map another host port: -p 9090:8080.
⚠️ The app runs but the browser cannot reach it You forgot -p 8080:8080 (EXPOSE alone does not publish).
⚠️ “COPY failed: file not found … target/docker-demo.jar” With Dockerfile.simple: you did not run mvn package first, or .dockerignore excludes the jar. Also check you passed the build context ..
⚠️ Container exits immediately docker ps shows nothing. Fix: docker ps -a to see it, then docker logs <name> — usually a Spring startup error (wrong profile, missing DB).
⚠️ Database at localhost from inside a container Fails because localhost is the container. Fix: host.docker.internal or Compose service names (topic 67).
⚠️ “no matching manifest for linux/arm64” on Apple Silicon Some -alpine JRE tags are x86-64 only. Fix: use eclipse-temurin:17-jre (Ubuntu based) — then create the user with groupadd/useradd and install curl for the health check (see exercise 5).
🚨 Running as root, using :latest, secrets in ENV All three are classic security-review findings. Add USER, pin versions, pass secrets at runtime.
⚠️ Shell-form ENTRYPOINT ENTRYPOINT java -jar app.jar → Java does not receive SIGTERM, docker stop waits 10 s and kills it. Use the JSON array form.

7. Best practices

  • Multi-stage builds: build tools stay out of the runtime image.
  • JRE, not JDK, in the runtime stage; small base images; consider distroless for high security.
  • Layered jars + order instructions from rarely to often changed → fast builds, small pushes.
  • Non-root user (USER spring).
  • Pin versions of base images (eclipse-temurin:17.0.x_y-jre-alpine or even a digest) for reproducible builds; update them regularly for security patches.
  • One process per container; log to stdout/stderr.
  • Health checks via Actuator; graceful shutdown (server.shutdown=graceful) and exec-form ENTRYPOINT.
  • Configuration via env vars, secrets from a secret store — never in the image.
  • Container-aware JVM flags: -XX:MaxRAMPercentage instead of fixed -Xmx; always set a memory limit in production.
  • .dockerignore to keep the context small and secret-free.
  • Scan images for known vulnerabilities (docker scout cves docker-demo:1.0, Trivy, Snyk) in CI.
  • Meaningful tags: version and/or Git commit SHA (1.4.2, 1.4.2-3f2a9c1), not just latest.
  • Optional extras: CDS / AOT cache to speed up startup, labels (LABEL org.opencontainers.image.source=...).

8. Key takeaways

  • A container packages the app with its runtime; it shares the host kernel → small and fast compared to a VM.
  • Dockerfile → docker build → image → docker run → container; registries store images.
  • Each instruction = a layer; Docker caches layers until the first change.
  • Multi-stage + Spring Boot layered jar (-Djarmode=tools extract --layers) = small image, fast rebuilds.
  • -p HOST:CONTAINER publishes ports; -e VAR=value overrides Spring properties (relaxed binding).
  • Run as non-root, use exec-form ENTRYPOINT, health checks, graceful shutdown, MaxRAMPercentage.
  • Buildpacks (mvn spring-boot:build-image) build a good image without a Dockerfile.
  • docker login / tag / push to share images through Docker Hub or a private registry.

9. Practice exercises

Easy

Two copies. Run the image twice on host ports 8081 and 8082 with different greetings. Call both /api/hello endpoints — what is different?

Hint / solution
docker run -d --name a -p 8081:8080 -e APP_GREETING="I am A" docker-demo:1.0
docker run -d --name b -p 8082:8080 -e APP_GREETING="I am B" docker-demo:1.0
curl.exe localhost:8081/api/hello      # message "I am A", host = container id of a
curl.exe localhost:8082/api/hello      # message "I am B", other host id
docker rm -f a b

Same image, two isolated containers with their own configuration and host names.

Easy

Change the port inside. Make the app listen on 9000 inside the container without rebuilding, and reach it from your browser on 7000.

Hint / solution
docker run -d --name p -e SERVER_PORT=9000 -p 7000:9000 docker-demo:1.0
curl.exe localhost:7000/api/hello
docker rm -f p

Note: the HEALTHCHECK still checks 8080, so the status becomes unhealthy — a good reason to make the health URL configurable (e.g. use ${SERVER_PORT:-8080} in a shell-form HEALTHCHECK).

Medium

Memory limit. Run with -m 300m and compare maxHeapMb with and without JAVA_TOOL_OPTIONS (override it with -e JAVA_TOOL_OPTIONS=).

Hint / solution

With 75 %: ≈ 225 MB. With the variable emptied the JVM default (25 % of the limit) applies: ≈ 75 MB. Low heap → more garbage collection or OutOfMemoryError under load, which is why the percentage flag is common practice.

Medium

Measure the cache. Build once, then change only a log message and rebuild. Then add a dependency (e.g. spring-boot-starter-validation) and rebuild. Which steps were CACHED each time and why?

Hint / solution

Code change: COPY pom.xml and dependency:go-offline are cached; COPY src and everything after re-run. In the runtime stage only the application/ layer is new. Dependency change: pom.xml changed → the download step and everything after re-run, and the dependencies/ layer changes too.

Challenge

Ubuntu-based runtime. Rewrite stage 3 using eclipse-temurin:17-jre (Ubuntu). Keep non-root and the health check.

Hint / solution
FROM eclipse-temurin:17-jre
RUN groupadd --system spring && useradd --system --gid spring spring \
    && apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

10. Interview questions

Q1. What is the difference between an image and a container?

An image is a read-only template (layers of filesystem changes + metadata like the start command). A container is a runnable instance of an image with its own writable layer, process space and network. Many containers can run from one image — like objects from a class.

Q2. How do containers differ from virtual machines?

VMs virtualize hardware and each runs a full guest OS on a hypervisor. Containers virtualize at the OS level: they share the host kernel and are isolated with namespaces and cgroups. Containers are much smaller and start faster; VMs offer stronger isolation.

Q3. What is a multi-stage build and why use it?

A Dockerfile with several FROM stages where later stages copy artifacts from earlier ones (COPY --from). You build with a JDK/Maven image and ship only a JRE image with the jar, giving smaller, more secure images and builds that need only Docker.

Q4. What are Spring Boot layered jars?

The fat jar includes a layers.idx describing layers (dependencies, spring-boot-loader, snapshot-dependencies, application). With java -Djarmode=tools -jar app.jar extract --layers (Boot 3.3+; earlier -Djarmode=layertools) you extract them and COPY each into its own image layer, so code changes only rebuild and push the small application layer.

Q5. ENTRYPOINT vs CMD? Exec form vs shell form?

ENTRYPOINT defines the executable; CMD gives default arguments (or a default command) that can be overridden at docker run. Exec form (JSON array) runs the process directly as PID 1 so it receives signals (graceful shutdown); shell form wraps it in /bin/sh -c, which doesn't forward SIGTERM.

Q6. How do you pass configuration to a Spring Boot app in a container?

Environment variables (relaxed binding: SPRING_DATASOURCE_URL ↔ spring.datasource.url), SPRING_PROFILES_ACTIVE, command-line args after the image name, mounted config files (spring.config.additional-location), or Kubernetes ConfigMaps/Secrets. Secrets are never baked into the image.

Q7. How do you handle JVM memory in containers?

Set a container memory limit and use container-aware percentage flags like -XX:MaxRAMPercentage=75 (Java 10+ detects cgroup limits), leaving headroom for metaspace, threads and native memory. Avoid hard-coded -Xmx that ignores the limit.

Q8. List Dockerfile best practices for Java apps.

Multi-stage builds, JRE/small base image, pinned versions, layered jars and cache-friendly ordering, .dockerignore, non-root USER, exec-form ENTRYPOINT, HEALTHCHECK, graceful shutdown, no secrets, image scanning, meaningful tags.

Q9. What are Cloud Native Buildpacks?

A way to turn source/jars into OCI images without a Dockerfile. Builders detect the app type and assemble layers (JRE, dependencies, app) with best practices. Spring Boot supports them via mvn spring-boot:build-image / Gradle bootBuildImage.

Q10. What does EXPOSE do? How do you reach a container port from the host?

EXPOSE only documents which port the app listens on (and is used by some tools). To reach it from the host you publish it with -p hostPort:containerPort (or -P to publish all exposed ports to random host ports).
