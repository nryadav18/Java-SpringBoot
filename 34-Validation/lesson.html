34. Validation

Stop bad data at the front door: add a few annotations to your DTOs and Spring rejects invalid requests with a clear 400 Bad Request before your code even runs.

🎯 What you will learn

1. Why this matters

Your API is a door to the outside world. Anyone can knock: your own web page, a mobile app, a partner company, a curious student with curl, or an attacker. Some of them will send nonsense:

  • An empty name, an email like "abc", an age of -5.
  • A booking for a date in 1990, or for 5,000 seats.
  • A 10 MB string in the "first name" field.

If bad data gets inside, it spreads: wrong reports, crashes deep in the code (NullPointerException), corrupted database rows, or security holes. The cheapest place to stop it is right at the entrance — the API boundary — before any business logic runs.

⚠️ "But the front-end already validates!" Front-end checks are for user comfort (instant feedback). They are not security. Anyone can skip your web page and call the API directly with curl or Postman. The server must always validate.

Writing if (name == null || name.isBlank()) ... for every field in every endpoint is long, repetitive and easy to forget. Bean Validation lets you write the rule once, as an annotation, right next to the field.

2. Real-life analogy

🛂 Think of the security check at an airport Before you reach the plane (your business logic), staff at the entrance check your documents: Is there a name on the ticket? Is the passport valid (not expired — a date in the future)? Is your bag under 7 kg (a maximum)?
  • The rules are printed on a board (the annotations on your DTO).
  • The officer who checks them is always the same, no matter which flight (Hibernate Validator).
  • If something is wrong you are stopped immediately, told exactly what is wrong ("bag too heavy"), and you never reach the plane (HTTP 400 — your controller method is never called).
  • Some airports have special rules — e.g. "liquids in a clear bag" (custom validators).

3. Concepts step by step

3.1 Jakarta Bean Validation, Hibernate Validator, and the starter

NameWhat it is
Jakarta Bean Validation (package jakarta.validation)A specification — a standard list of annotations (@NotBlank, @Email…) and interfaces. It used to be called javax.validation before Spring Boot 3.
Hibernate ValidatorThe implementation — the engine that actually checks the annotations. (Same company as Hibernate ORM, but a separate library; you don't need a database.)
spring-boot-starter-validationThe Spring Boot starter that brings both, and plugs them into Spring MVC automatically.
pom.xml<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
🛑 Very common trap spring-boot-starter-web does not include validation any more (since Spring Boot 2.3). Without the validation starter, your code still compiles if the annotations are on the classpath, but every @NotBlank is silently ignored. If validation "does nothing", check this dependency first.

3.2 The flow: where validation happens

JSON request→ Jackson creates the DTO→ @Valid? → Validator checks every rule→ ✅ all OK → controller method runs
Validator finds problems→ MethodArgumentNotValidException→ HTTP 400 Bad Request
controller never called

The great news: if your controller method is running, the input is guaranteed to be valid. No if checks needed.

@NotNull vs @NotEmpty vs @NotBlank — the classic interview question

Important rule: most constraints accept null

@Size, @Email, @Min, @Pattern, @Past, … all treat null as valid. That sounds strange, but it is smart: each annotation checks one thing. "Is it present?" is the job of @NotNull/@NotBlank. So:

@Email String email;               // null is OK, "abc" is not  -> an OPTIONAL email
@NotBlank @Email String email;     // must exist AND look valid  -> a REQUIRED email

Custom messages and placeholders

Every annotation has a message attribute. Inside it you can use the annotation's own attributes as {placeholders}:

@Size(min = 2, max = 50, message = "Name must be between {min} and {max} characters")
@Min(value = 18, message = "You must be at least {value} years old")

Without a message, you get a default English text such as "must not be blank" or "size must be between 2 and 50".

ℹ️ Messages from a file Real apps often keep messages in src/main/resources/ValidationMessages.properties (e.g. user.name.size=Name must be between {min} and {max} characters) and write message = "{user.name.size}". This allows translations such as ValidationMessages_hi.properties.

3.4 Annotations on records

Our DTOs are records (topic 33). Put the annotations directly on the record components:

public record RegisterUserRequest(
        @NotBlank(message = "Name is required")
        @Size(min = 2, max = 50)
        String name,

        @NotNull @Min(18) @Max(120)
        Integer age                     // Integer, not int!
) { }
💡 Use wrapper types (Integer, Long, Boolean) in request DTOs If the client forgets "age", an int silently becomes 0 and you cannot tell "missing" from "zero". An Integer becomes null, and @NotNull catches it.

3.5 Triggering validation: @Valid on @RequestBody

Annotations on the DTO are only rules. Something must say "check them now!". That is @Valid on the controller parameter:

@PostMapping
public ResponseEntity<UserResponse> register(@Valid @RequestBody RegisterUserRequest request) {
    // reaching this line means: request is valid
}

Forget @Valid and nothing is checked. On failure Spring throws MethodArgumentNotValidException, which Spring turns into 400 Bad Request. All errors are collected (not only the first), so the client can fix everything in one go.

@Validated (Spring's own annotation, from org.springframework.validation.annotation) works here too, and it can also choose validation groups — see 3.9.

3.6 Validating @PathVariable and @RequestParam

Simple parameters are not objects, so there is nothing to put @Valid on. Instead you put the constraint directly on the parameter:

@GetMapping("/{id}")
public ResponseEntity<UserResponse> getById(@PathVariable @Min(1) Long id) { ... }

@GetMapping("/search")
public List<UserResponse> search(@RequestParam @NotBlank @Size(min = 2, max = 30) String name) { ... }

This is called method validation (validating a method's parameters). There are two ways it can be switched on — you will meet both in real projects:

Modern way (Spring 6.1+ / Boot 3.2+) — used in this projectClassic way — @Validated on the class
HowJust put the constraint on the parameter. Spring MVC sees it and validates built-in.Add @Validated on the controller class. Spring wraps the controller in an AOP proxy (topic 27) that validates.
ExceptionHandlerMethodValidationExceptionConstraintViolationException
Default status400 Bad Request ✅500 Internal Server Error ❌ (until you handle it — topic 35)
⚠️ Don't mix them If the class has @Validated, Spring MVC skips its built-in method validation and lets the AOP proxy do it — so you suddenly get 500 instead of 400. In Spring Boot 3.2+ projects, leave @Validated off the controller class unless you really need the classic behaviour. (In older Spring Boot versions, @Validated on the class was required for parameter validation — that's why old tutorials show it everywhere.)

Method validation is not only for controllers. You can validate the parameters of any Spring bean, e.g. a service, by putting @Validated on that class:

@Service
@Validated                                        // AOP proxy validates parameters
public class ReportService {
    public Report monthly(@Min(1) @Max(12) int month) { ... }   // ConstraintViolationException if invalid
}

3.7 Nested validation

A user has an address, and the address has its own rules. By default the validator does not look inside nested objects. You must say "go inside" with @Valid on the field:

public record RegisterUserRequest(
        ...
        @NotNull(message = "Address is required")   // the address must exist
        @Valid                                       // ...and its own fields must be valid
        AddressRequest address
) { }

public record AddressRequest(
        @NotBlank String street,
        @NotBlank String city,
        @NotBlank @Pattern(regexp = "\\d{6}") String pinCode
) { }

Error field names show the path: address.street, address.pinCode. The same works for lists of DTOs: List<@Valid OrderItemRequest> items.

Validating list elements

Constraints can go inside the generic type, so every element is checked:

@Size(max = 5)                              // the list: at most 5 items
List<@NotBlank String> interests             // every item: not blank

An empty item gives an error on field interests[0].

3.8 Custom constraints: @StrongPassword

Built-in annotations can't express everything. "A password needs 8+ characters, an uppercase letter, a lowercase letter, a digit and a special character" — we write our own annotation. It needs two pieces:

@StrongPassword
the annotation (the rule's name)→ @Constraint(validatedBy = …) → StrongPasswordValidator
the class with the check 
validation/StrongPassword.java@Documented
@Constraint(validatedBy = StrongPasswordValidator.class)         // who checks it
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.RECORD_COMPONENT,
        ElementType.METHOD, ElementType.TYPE_USE})              // where it may be placed
@Retention(RetentionPolicy.RUNTIME)                              // visible at runtime (topic 18)
public @interface StrongPassword {

    String message() default "Password must be at least {minLength} characters and contain "
            + "an uppercase letter, a lowercase letter, a digit and a special character";

    int minLength() default 8;                                   // our own attribute

    Class<?>[] groups() default {};                              // REQUIRED by the spec
    Class<? extends Payload>[] payload() default {};             // REQUIRED by the spec
}
validation/StrongPasswordValidator.javapublic class StrongPasswordValidator implements ConstraintValidator<StrongPassword, String> {

    private int minLength;

    @Override
    public void initialize(StrongPassword annotation) {
        this.minLength = annotation.minLength();     // read the annotation's settings once
    }

    @Override
    public boolean isValid(String password, ConstraintValidatorContext context) {
        if (password == null) {
            return true;                              // presence is @NotBlank's job
        }
        boolean longEnough = password.length() >= minLength;
        boolean hasUpper   = password.chars().anyMatch(Character::isUpperCase);
        boolean hasLower   = password.chars().anyMatch(Character::isLowerCase);
        boolean hasDigit   = password.chars().anyMatch(Character::isDigit);
        boolean hasSpecial = password.chars().anyMatch(ch -> !Character.isLetterOrDigit(ch));
        return longEnough && hasUpper && hasLower && hasDigit && hasSpecial;
    }
}

Use it like any built-in one: @NotBlank @StrongPassword String password.

  • ConstraintValidator<StrongPassword, String> — "I validate @StrongPassword on String values".
  • The three attributes message, groups, payload are mandatory; forget one and you get a ConstraintDefinitionException at runtime.
  • Validator classes are created by Spring, so you may even inject beans into them (e.g. a repository to check "username not taken") — but keep database checks in the service when possible.

The project also contains @ValidPhoneNumber (Indian mobile numbers: 10 digits starting 6–9, optional +91), built the same way with a precompiled regex.

ℹ️ Cross-field rules "checkOut must be after checkIn" or "password and confirmPassword must match" involve two fields. Put a custom annotation on the class (@Target(ElementType.TYPE)) and let the validator receive the whole object. See exercise 5.

3.9 Validation groups (brief)

Sometimes one DTO needs different rules in different situations. Example: when creating a product the client must not send an id; when updating, the id is required.

public final class ValidationGroups {
    public interface OnCreate extends Default { }    // empty "label" interfaces
    public interface OnUpdate extends Default { }
}

public record ProductRequest(
        @Null(groups = OnCreate.class)  @NotNull(groups = OnUpdate.class) Long id,
        @NotBlank String name,                        // no groups -> Default group
        @NotNull @Positive BigDecimal price
) { }

@PostMapping  public ... create(@Validated(OnCreate.class) @RequestBody ProductRequest r)
@PutMapping   public ... update(@Validated(OnUpdate.class) @RequestBody ProductRequest r)
  • @Valid can't pick a group; Spring's @Validated(Group.class) can.
  • Why extends Default? Constraints without groups belong to the Default group. If OnCreate did not extend Default, @Validated(OnCreate.class) would skip @NotBlank name!
  • Honest advice: two small DTOs (CreateProductRequest, UpdateProductRequest) are often clearer than groups. Use groups when a team already does.

3.10 The default error response

When validation fails, what does the client receive? Out of the box, Spring Boot sends only:

{
  "timestamp": "2026-10-09T04:36:56.754+00:00",
  "status": 400,
  "error": "Bad Request",
  "path": "/api/users"
}

Correct status — but the client has no idea which field was wrong. Spring Boot hides details by default (it is safer). For learning, we switched two properties on in application.properties:

application.propertiesserver.error.include-message=always
server.error.include-binding-errors=always

Now the error contains a message and an errors array. It works, but each error looks like this — long and technical:

{"objectName":"registerUserRequest","field":"age","rejectedValue":15,
 "codes":["Min.registerUserRequest.age","Min.age","Min.java.lang.Integer","Min"],
 "arguments":[...],"defaultMessage":"You must be at least 18 years old",
 "bindingFailure":false,"code":"Min"}

A front-end developer wants something like {"field":"age","message":"You must be at least 18 years old"}. In topic 35 we catch MethodArgumentNotValidException ourselves and return exactly that.

Also keep database constraints (NOT NULL, UNIQUE, column lengths) as the last safety net. Validation in three places sounds like a lot, but each has a different job.

3.12 Programmatic validation (good to know)

Sometimes data doesn't come through a controller — e.g. rows from a CSV file. You can inject the Validator and call it yourself:

@Service
public class CsvImportService {
    private final jakarta.validation.Validator validator;   // auto-configured by Spring Boot
    public CsvImportService(jakarta.validation.Validator validator) { this.validator = validator; }

    public void importRow(RegisterUserRequest row) {
        Set<ConstraintViolation<RegisterUserRequest>> violations = validator.validate(row);
        if (!violations.isEmpty()) {
            throw new ConstraintViolationException(violations);
        }
        // ...save
    }
}

Our unit test RegisterUserRequestValidationTest does exactly this, without Spring.

6. Common mistakes

🛑 Mistake: missing spring-boot-starter-validation Annotations compile but nothing is validated — invalid data goes straight through.
Fix: Add the starter. Quick test: send {} to your endpoint; you must get 400.
⚠️ Mistake: forgetting @Valid on the @RequestBody The DTO has rules but nobody checks them.
Fix: @Valid @RequestBody MyRequest request — every time.
⚠️ Mistake: forgetting @Valid on a nested object @NotNull AddressRequest address only checks that an address exists — an address with a blank city passes.
Fix: @NotNull @Valid AddressRequest address.
⚠️ Mistake: @NotNull on a String "" and " " pass.
Fix: Use @NotBlank for strings, @NotEmpty for collections, @NotNull for everything else.
⚠️ Mistake: @Size or @Min on a primitive / thinking they block null @Min(18) int age — a missing age becomes 0 and the message says "at least 18", confusing the user. And @Size(min=2) String name accepts null.
Fix: Use wrapper types and combine with @NotNull/@NotBlank.
⚠️ Mistake: @Validated on the controller class in Boot 3.2+ Parameter validation then throws ConstraintViolationException → 500 instead of 400.
Fix: Remove the class-level @Validated (built-in method validation gives 400), or handle ConstraintViolationException in a global handler (topic 35).
⚠️ Mistake: custom annotation missing groups() / payload() or RUNTIME retention Startup/validation fails with ConstraintDefinitionException, or the annotation is never seen.
Fix: Copy the full template: message, groups, payload, @Retention(RUNTIME), @Constraint(validatedBy=…).
⚠️ Mistake: validation groups without extends Default @Validated(OnCreate.class) silently skips all your normal constraints.
Fix: interface OnCreate extends Default {}.
⚠️ Mistake: importing javax.validation Old tutorials use javax.validation.constraints.NotBlank. In Spring Boot 3 these are ignored or don't compile.
Fix: Always jakarta.validation....
⚠️ Mistake: a too-strict email regex Writing your own email regex rejects valid addresses like first.last+tag@sub.example.co.in.
Fix: Use @Email. The only real proof an email exists is sending a confirmation mail.

7. Best practices

  • Validate at the boundary (request DTOs), every time, even if the front-end validates too.
  • Put constraints on DTOs, not on entities (entities may still have database constraints). Different APIs may need different rules for the same entity.
  • Write human-friendly messages — the end user may see them. Say what is expected: "PIN code must be exactly 6 digits", not "invalid".
  • Always set a maximum length on strings (@Size(max = ...)) and sizes on lists — it protects memory, the database column, and against abuse.
  • Wrapper types (Integer, Boolean) in request DTOs so "missing" is detectable.
  • One rule per annotation, and custom validators return true for null.
  • Keep business rules in the service (uniqueness, stock, balance), not in annotations that secretly hit the database.
  • Test your custom validators with plain unit tests and @ParameterizedTest.
  • Return a clean, consistent error format — handled centrally (next topic). Don't expose the raw default details in production.
  • For many messages or multiple languages, keep them in ValidationMessages.properties.

8. Key takeaways

  • Never trust input: the server must validate even if the client does.
  • Add spring-boot-starter-validation (Jakarta Bean Validation + Hibernate Validator).
  • Put constraint annotations on DTO fields; trigger them with @Valid on @RequestBody.
  • Invalid body → MethodArgumentNotValidException → 400, controller never runs, all errors reported.
  • Put constraints directly on @PathVariable/@RequestParam; Boot 3.2+ validates them built-in (400). Class-level @Validated is the older AOP way (500 unless handled).
  • @NotBlank for strings; most other constraints accept null.
  • Nested objects need @Valid; list elements can be constrained with List<@NotBlank String>.
  • Custom constraint = annotation (@Constraint) + ConstraintValidator class.
  • Validation groups choose rule sets with @Validated(Group.class); groups should extend Default.
  • Default error JSON hides details; topic 35 builds a clean error response.

Hint / solution 
@Documented
@Constraint(validatedBy = ValidStayDatesValidator.class)
@Target(ElementType.TYPE)                         // on the CLASS / record
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidStayDates {
    String message() default "Check-out must be after check-in";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class ValidStayDatesValidator implements ConstraintValidator<ValidStayDates, HotelBookingRequest> {
    @Override
    public boolean isValid(HotelBookingRequest r, ConstraintValidatorContext ctx) {
        if (r == null || r.checkIn() == null || r.checkOut() == null) return true;
        if (r.checkOut().isAfter(r.checkIn())) return true;
        // attach the error to the checkOut field instead of the whole object
        ctx.disableDefaultConstraintViolation();
        ctx.buildConstraintViolationWithTemplate(ctx.getDefaultConstraintMessageTemplate())
           .addPropertyNode("checkOut").addConstraintViolation();
        return false;
    }
}

10. Interview questions

Q1. What is the difference between @NotNull, @NotEmpty and @NotBlank?

@NotNull only rejects null. @NotEmpty rejects null and empty (length/size 0) — for strings, collections, maps, arrays. @NotBlank (strings only) rejects null, empty and whitespace-only strings. For text input @NotBlank is usually right.

Q2. What is the difference between @Valid and @Validated?

@Valid is the standard Jakarta annotation: it triggers validation of a parameter and cascades into nested objects (on fields). @Validated is Spring's annotation: on a parameter it also triggers validation but can specify validation groups; on a class it enables AOP-based method validation of that bean's parameters and return values. @Validated cannot be used for cascading on fields — use @Valid there.

Q3. What happens when @Valid fails on a @RequestBody?

Spring throws MethodArgumentNotValidException (a BindException) containing all field errors in a BindingResult. The controller method is not executed. By default Spring Boot returns 400 Bad Request; you usually handle the exception in a @RestControllerAdvice to return a friendly list of field errors.

Q4. How do you validate path variables and request params?

Put constraint annotations directly on the parameters, e.g. @PathVariable @Min(1) Long id. Since Spring Framework 6.1 Spring MVC applies method validation built-in and throws HandlerMethodValidationException (400). In older versions, or when the controller class is annotated @Validated, the AOP-based MethodValidationPostProcessor validates and throws ConstraintViolationException, which you must map to 400 yourself.

Q5. How do you create a custom validation annotation?

Create an annotation with @Constraint(validatedBy = MyValidator.class), @Retention(RUNTIME), a suitable @Target, and the mandatory attributes message(), groups() and payload(). Then implement ConstraintValidator<MyAnnotation, TargetType> with the logic in isValid (optionally reading attributes in initialize). By convention return true for null values.

Q6. How do you validate nested objects and collections?

Mark the nested field with @Valid so validation cascades into it. For collections either annotate the field @Valid List<Item> or use a type-argument constraint List<@Valid Item>; simple elements can be constrained like List<@NotBlank String>. Error paths look like items[2].quantity.

Q7. What are validation groups and when would you use them?

Groups are marker interfaces that let you apply different subsets of constraints in different situations — e.g. id must be null on create but not null on update. You assign constraints with groups = OnCreate.class and activate with @Validated(OnCreate.class). Make the groups extend Default so ungrouped constraints still run. Many teams prefer separate DTOs for clarity.

Q8. Where should validation happen — controller, service or database?

All three, with different jobs: format/input validation on DTOs at the controller boundary (Bean Validation); business rules that need state (uniqueness, stock, balance) in the service; and database constraints (NOT NULL, UNIQUE, FK, lengths) as the final safety net for data integrity and race conditions.

Q9. Why is client-side validation not enough?

Clients can be bypassed — anyone can call the API directly with curl/Postman or a modified app. Client-side validation improves user experience; server-side validation protects data integrity and security.

Q10. Why does @Min(18) on an int field not detect a missing value?

A missing JSON property leaves a primitive int at its default 0, so the validator sees 0 (and reports "must be ≥ 18", which is misleading). Use Integer with @NotNull so a missing value becomes null and is reported correctly.
