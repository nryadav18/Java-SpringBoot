1. Why this matters

Until now, every program you wrote lived in one file. Real software is different. A normal company project has hundreds or thousands of classes written by many people. Without rules, it becomes a mess:

  • Two people create a class called Product — which one is which?
  • Someone sets account.balance = -50000 directly, skipping all checks.
  • Every object keeps its own copy of a value that should be shared (like a tax rate).
  • Someone overrides an important method in a child class and breaks the security rule inside it.

This topic gives you the tools to prevent all of that:

ToolProblem it solvesWhere you'll see it at work
PackagesOrganise classes, avoid name clashesEvery Spring Boot project: com.company.shop.controller, ...service, ...repository
Access modifiersHide internal details, protect dataPrivate fields in every entity/DTO, public service methods
staticShare one value/method across the whole programConstants, utility classes, loggers (private static final Logger log)
finalStop accidental changesConstructor injection in Spring: private final OrderService orderService;
Nested classesKeep a helper class close to the class that uses itBuilders, Map.Entry, test classes
SingletonExactly one shared objectSpring beans are singletons by default!
ℹ️ Spring connectionWhen you reach Spring Boot, you will write code like @SpringBootApplication in package com.course.shop. Spring only scans packages under that one. Put a class in the wrong package and Spring simply won't find it. So packages are not "just folders" — they really matter.

2. Real-life analogy

🏢 Think of a big office building
  • Packages are the departments / floors: Accounts on floor 1, HR on floor 2, IT on floor 3. Two people can both be called "Priya" — "Priya from Accounts" and "Priya from IT" are different people. That's com.shop.model.Product vs com.warehouse.Product.
  • Access modifiers are the door badges:
    • public = the reception lobby — anyone can walk in.
    • protected = family room — your department, plus your children who work in other departments.
    • default (no word) = department-only room — only people from the same floor.
    • private = your personal locker — only you.
  • static is the notice board in the corridor: there is ONE board, everybody reads the same board. Each employee's desk (instance field) is their own.
  • final is a sign written in permanent marker — once written, it cannot be changed.
  • Singleton is the CEO: the company has exactly one, and everyone goes to the same person.

3. Concepts step by step

3.1 What is a package?

A package is a named group of related classes. On disk, a package is simply a folder. The name uses dots, and each dot means "go into a sub-folder":

Package nameFolder on disk (under src)
com.shopsrc\com\shop\
com.shop.modelsrc\com\shop\model\
com.shop.utilsrc\com\shop\util\

You put a class in a package with a package line. It must be the very first statement of the file (only comments may come before it):

src/com/shop/util/PriceUtils.javapackage com.shop.util;      // 1st statement: "this class lives in com.shop.util"

public final class PriceUtils {
    ...
}

The class's full name (its "fully qualified name") is now com.shop.util.PriceUtils. The short name PriceUtils is just a nickname.

Why packages?

  1. Organisation — like folders for your photos: "Holidays", "Family", "Work".
  2. No name clashes — java.util.Date and java.sql.Date both exist happily.
  3. Access control — "package-private" things are visible only inside the same package (see 3.4).

Naming rules (convention)

  • All lowercase: com.shop.model, not com.Shop.Model.
  • Start with your company's domain reversed: the company owns course.com → packages start with com.course. This makes names unique worldwide. In this course every Spring project uses com.course.<shortname>.
  • Then the project and the area: com.course.shop.order, com.course.shop.payment.

The packages you already used

The JDK itself is organised into packages: java.lang (String, Math, System), java.util (Scanner, Arrays), java.time (LocalDate), java.io (files). The package java.lang is imported automatically — that's why you never wrote import java.lang.String;.

3.2 import — using classes from other packages

A class in package com.shop wants to use Product from com.shop.model. You have two choices:

// Choice 1: write the full name every time (works, but long)
com.shop.model.Product pen = new com.shop.model.Product("Pen", 20.0, "Stationery");

// Choice 2: import once at the top, then use the short name
import com.shop.model.Product;
...
Product pen = new Product("Pen", 20.0, "Stationery");

The different kinds of import:

FormExampleMeaning
Single-type importimport java.util.Scanner;Import one class. Recommended — you can see exactly what is used.
Wildcard (on-demand) importimport java.util.*;Import all classes of that package (not sub-packages!). Fine for quick tests.
Static importimport static java.lang.Math.PI;Use a static member without the class name: PI instead of Math.PI.
Static wildcardimport static java.lang.Math.*;All static members of Math: sqrt(16), max(a, b).
ℹ️ Imports are just shortcutsAn import does not copy code and does not make your program bigger or slower. It only tells the compiler: "when I write Product, I mean com.shop.model.Product".
💡 Wildcards do not include sub-packagesimport com.shop.*; does NOT import com.shop.model.Product. Sub-packages are completely separate packages; the dots only look like a family tree.

Order of lines in a Java file is always: package → imports → class.

3.4 The 4 access modifiers

An access modifier is a word placed before a class, field, method or constructor that says who can use it. There are 4 levels, from most open to most closed:

ModifierSame classSame packageChild class in another packageEveryone else
public✅✅✅✅
protected✅✅✅ (through inheritance)❌
default (no keyword) — "package-private"✅✅❌❌
private✅❌❌❌

Memory trick: public > protected > default > private — each one is "the one above minus something".

See all four in our Product class:

src/com/shop/model/Product.java (key parts)package com.shop.model;

public class Product {                 // public class: usable from any package
    private double price;              // private: ONLY Product itself
    protected String category;         // protected: com.shop.model + child classes anywhere
    String internalCode;               // default: ONLY classes in com.shop.model

    public double getPrice() { return price; }   // public: everyone
}

And this is what the compiler says when App (package com.shop) breaks the rules — these are the real messages:

error: price has private access in Product
error: internalCode is not public in Product; cannot be accessed from outside package
error: category has protected access in Product
error: PriceUtils() has private access in PriceUtils
error: StockChecker is not public in com.shop.model; cannot be accessed from outside package

Access modifiers on classes

  • A top-level class (one not inside another class) can only be public or default.
  • A file can contain only one public top-level class, and the file must be named after it: public class Product → Product.java.
  • A class without public (like class StockChecker) is visible only in its own package. Great for hidden helpers.
  • Nested classes (3.8) may use all four modifiers.

"protected" — the tricky one

FlashSaleProduct lives in com.shop.sale but extends Product. It may use category because it inherited it:

src/com/shop/sale/FlashSaleProduct.javapublic String getBanner() {
    return "FLASH SALE on " + category + ": " + discountPercent + "% off!";   // OK: protected + child class
}

But App is not a child of Product and not in com.shop.model, so pen.category fails.

Which one should I use? (simple rules)

  1. Fields: almost always private (encapsulation from Topic 7). Give access through methods.
  2. Methods other classes need: public.
  3. Helper methods used only inside the class: private.
  4. protected: only when you design a class to be extended and a child really needs it.
  5. default: for "internal" classes of a package (also used a lot in tests and in Spring for @Bean methods).
💡 Golden ruleStart with the most private option. Open it up only when needed. It is easy to make something more public later, but very hard to make it private again once other code depends on it.

3.5 static — belongs to the class, not to an object

Normally each object has its own copy of each field. Two students, two names. That's an instance field. A static field is different: there is only one copy, stored with the class, shared by all objects.

class Student {
    static String collegeName;          // ONE copy for all students
    private static int totalStudents;   // ONE shared counter

    private final String name;          // each student has their own
    private final int rollNumber;

    Student(String name) {
        this.name = name;
        totalStudents++;                  // update the shared counter
        this.rollNumber = totalStudents;
    }

    static int getTotalStudents() { return totalStudents; }
}

Static methods

A static method is called on the class: Student.getTotalStudents(), Math.max(7, 12), Integer.parseInt("42"). You don't need an object. And main itself is static — the JVM calls it before any object exists!

⚠️ A static method has no thisInside a static method you cannot use instance fields or instance methods directly. Why? A static method belongs to the class, not to a particular student — so "name" would be meaningless (whose name?). The compiler says: non-static variable name cannot be referenced from a static context.
The reverse is fine: an instance method can use static fields.
Instance (non-static)static
Belongs toEach objectThe class
CopiesOne per objectExactly one
Called likeasha.printInfo()Student.getTotalStudents()
Can use this?YesNo
Can use instance fields?YesNo (only through an object reference)
Typical useData & behaviour of one thingCounters, constants, helper/utility methods, factory methods, main

Static blocks

A static block (static { ... }) runs once, when the JVM first loads the class. Use it for one-time setup of static fields that needs more than one line.

static {
    collegeName = "City College";
    System.out.println("[static block] Student class loaded.");
}

There is also an instance initializer block (just { ... } without static) which runs before the constructor body for every new object. You'll rarely need it — constructors are clearer.

Utility classes — a very common static pattern

src/com/shop/util/PriceUtils.javapublic final class PriceUtils {
    public static final double GST_RATE = 0.18;     // constant

    private PriceUtils() { }                        // no objects allowed

    public static double withGst(double amount) {
        return amount + amount * GST_RATE;
    }
}

The JDK has many: Math, Arrays, Collections, Objects. Usage: PriceUtils.withGst(100) → 118.0.

⚠️ Don't overuse staticBeginners often make everything static "because the error goes away". That turns your program back into old-style procedural code: hard to test and hard to change. In Spring, almost all your classes will be normal (non-static) beans that Spring creates and connects for you. Use static for constants and small pure helpers.

3.6 final — "this cannot change"

final can be used in 3 places, with 3 meanings:

On a...MeansExample
variable (local, parameter, field)Can be assigned only oncefinal double rate = 0.04;
methodChild classes cannot override itfinal String withdrawalRule()
classNo class can extend itfinal class Receipt, String

Final variables and constants

final double interestRate = 0.04;
interestRate = 0.05;   // ❌ error: cannot assign a value to final variable interestRate

static final String BANK_NAME = "Java Bank";   // a CONSTANT: static + final, UPPER_SNAKE_CASE

"Blank final" fields

A final field doesn't need a value on the same line. It can be set once in the constructor — and the compiler forces every constructor to set it. This is how you make fields that never change after the object is built:

class BankAccount {
    private final String accountNumber;     // blank final

    BankAccount(String accountNumber) {
        this.accountNumber = accountNumber; // set exactly once
    }
}
ℹ️ You will write this a lot in Spring 
@Service
public class OrderService {
    private final PaymentService paymentService;   // final + set in constructor

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
This is "constructor injection" (Topic 24). final guarantees the dependency is always set and never swapped by accident.

The "final reference" trap

final on a variable that holds an object means the variable can't point to a different object. It does not freeze the object itself:

final StringBuilder notes = new StringBuilder("[Opened online]");
notes.append(" [KYC done]");      // ✅ allowed: we change the OBJECT
notes = new StringBuilder();      // ❌ error: we try to change the VARIABLE
🏠 AnalogyA final reference is like a permanent address label on your house. You can't move the label to another house, but you can still paint the walls and change the furniture inside.

Final methods and classes

class BankAccount {
    final String withdrawalRule() { ... }   // child classes can't change this rule
}

final class Receipt { ... }                // nobody can "extends Receipt"

Why? Safety. String is final so nobody can create a "fake String" that behaves differently (for example, one that changes its text after a password check). Use final classes for things that must be immutable (never change after creation).

💡 final vs finally vs finalizeThree different things! final = keyword from this topic. finally = block in exception handling (next topic). finalize() = an old, deprecated method — never use it. A classic interview question.

3.7 static + final together = constants

public static final int MAX_CART_ITEMS = 20;
public static final String SUPPORT_EMAIL = "help@shop.com";
  • static → one copy (no need to store 20 in every object).
  • final → it never changes.
  • Name in UPPER_SNAKE_CASE so readers immediately know it's a constant.
  • Replaces "magic numbers": if (items > MAX_CART_ITEMS) is clearer than if (items > 20).

3.8 Classes inside classes: nested, inner, local, anonymous

Java lets you declare a class inside another class (or even inside a method). Why? To keep a small helper class right next to the only place that uses it. There are 4 kinds:

KindDeclaredNeeds an outer object?Typical use
Static nested classInside a class, with staticNoHelper types that belong together: Map.Entry, Builders, Order.Address
Inner class (non-static)Inside a class, no staticYes — tied to one outer objectParts that need the outer object's data: an order's items
Local classInside a method—Rare; a helper used by one method only
Anonymous classInline, in an expression, no name—One-off implementation of an interface (before lambdas)

Static nested class

class FoodOrder {
    static class Address { ... }
}

FoodOrder.Address home = new FoodOrder.Address("12 MG Road", "Bengaluru", "560001");

It's basically a normal class whose name is "grouped" under FoodOrder. No FoodOrder object is needed.

Inner class

class FoodOrder {
    private final int orderId;

    class Item {
        void print() {
            System.out.println("Order #" + orderId + " ...");   // reads the OUTER object's field
        }
    }
}

Every Item object secretly holds a reference to the FoodOrder that created it, so it can read orderId. From outside you'd create one with the unusual syntax order.new Item(...) — but usually the outer class creates them itself.

💡 Prefer static nestedIf the nested class does NOT need the outer object's fields, make it static. It's simpler, uses less memory and avoids accidentally keeping the outer object alive.

Anonymous class

Sometimes you need an object of an interface just once. Writing a whole named class for it is overkill. An anonymous class creates the class and the object in one go:

interface Discount {
    double apply(double amount);
}

Discount festivalOffer = new Discount() {     // "a new unnamed class that implements Discount"
    @Override
    public double apply(double amount) {
        return amount - amount * 0.10;
    }
};                                            // ← note the semicolon: this whole thing is one statement

festivalOffer.apply(220.0);   // 198.0
ℹ️ Coming soon: lambdasIn Topic 13 you'll learn that the same thing can be written as Discount festivalOffer = amount -> amount - amount * 0.10;. Lambdas replaced most anonymous classes — but you still need to recognise them in older code.

3.9 The Singleton pattern

A design pattern is a well-known, named solution to a common problem. Singleton answers: "How do I make sure only one object of a class ever exists?" Examples: app configuration, an ID generator, a connection pool.

It combines everything from this topic:

Example04_Singleton.java (eager version)final class AppConfig {
    private static final AppConfig INSTANCE = new AppConfig();   // 2. the one object

    private AppConfig() { }                                      // 1. nobody else can call new

    public static AppConfig getInstance() {                      // 3. global access point
        return INSTANCE;
    }
}
Class loads→ INSTANCE created once→ getInstance() always returns it
StyleWhen is the object created?Thread-safe?Notes
EagerWhen the class loadsYes (JVM guarantees it)Simplest. Use this by default.
Lazy + synchronizedOn first getInstance()YesUseful if creation is expensive and may never be needed.
Lazy without synchronizedOn first call❌ NoTwo threads might create two objects. Avoid.
Enum (enum X { INSTANCE; })When the enum loadsYesShortest and safest; recommended by the book "Effective Java".
ℹ️ Singleton in SpringSpring creates one object per bean by default ("singleton scope") and hands the same object to everyone who needs it. The difference: Spring manages it, so your class stays a normal class (public constructor, no getInstance()), and it's easy to test. That's why hand-written singletons are rare in Spring apps. More in Topic 25.

4.1 The shop project (src/)

App.java — the top of the file shows the order: package, then imports, then the class:

src/com/shop/App.javapackage com.shop;

import com.shop.model.Product;           // single-type import (recommended)
import com.shop.sale.FlashSaleProduct;
import com.shop.util.PriceUtils;
import static com.shop.util.PriceUtils.GST_RATE;   // static import of one constant

public class App {
    public static void main(String[] args) {
        Product pen = new Product("Pen", 20.0, "Stationery");
        System.out.println(pen);
        System.out.println("Pen with GST: " + PriceUtils.formatRupees(PriceUtils.withGst(pen.getPrice())));
        System.out.println("GST rate used: " + GST_RATE);   // no "PriceUtils." needed
        ...
        // A fully qualified name works WITHOUT any import line:
        java.time.LocalDate openingDay = java.time.LocalDate.of(2025, 1, 15);
    }
}
  • PriceUtils.withGst(...) — a static method, called on the class name.
  • GST_RATE — usable without the class name thanks to import static.
  • java.time.LocalDate — used with its full name, so no import is needed.
  • At the bottom of main you'll find 5 commented-out lines that break access rules. Un-comment one, compile, read the error, comment it back.

Product.java — internalCode is set using the package-private helper StockChecker. This is allowed because both classes are in com.shop.model:

src/com/shop/model/Product.javapublic Product(String name, double price, String category) {
    this.name = name;
    setPrice(price);                 // reuse validation from the setter
    this.category = category;
    this.internalCode = StockChecker.makeCode(name);   // same package -> OK
}

public boolean isInStock() {
    return StockChecker.hasStock(internalCode);         // a public method that uses a hidden helper
}

Outside code can ask isInStock() (public) but can never see how stock is checked. If we later replace StockChecker with a real warehouse system, no code outside the package needs to change. That's the power of hiding details.

FlashSaleProduct.java — in a different package, but a child of Product:

src/com/shop/sale/FlashSaleProduct.javapackage com.shop.sale;

import com.shop.model.Product;

public class FlashSaleProduct extends Product {
    private final int discountPercent;          // final: set once

    public double getSalePrice() {
        return getPrice() - (getPrice() * discountPercent / 100.0);   // must use public getter: price is private
    }

    public String getBanner() {
        return "FLASH SALE on " + category + ...;  // protected field: OK in a child class
    }
}

ℹ️ Number formattingString.format uses your computer's language settings. On some systems you may see 1.499,50 instead of 1,499.50. That's normal.

5.3 Try breaking the rules

Open App.java, remove the // before pen.price = 0;, and compile again. You'll see error: price has private access in Product. Put the // back. Do the same for each of the 5 lines — reading compiler errors is a skill, and this is a safe place to practise.

6. Common mistakes

❌ Mistake: "Could not find or load main class" You ran java -cp out App or java -cp out com/shop/App.java, or you are in the wrong folder.
Fix: run from the topic folder and use the fully qualified name with dots: java -cp out com.shop.App.
⚠️ Mistake: package line doesn't match the folder The file is in src\com\shop\model but says package com.shop.models;. With -sourcepath javac then can't find it (error: cannot find symbol or file does not contain class ...).
Fix: package name and folder path must match exactly (lowercase).
⚠️ Mistake: public class name ≠ file name public class Product saved in product.java or Products.java → error: class Product is public, should be declared in a file named Product.java.
Fix: exact same name, same capital letters.
⚠️ Mistake: using an instance field from main non-static variable count cannot be referenced from a static context. Beginners "fix" it by adding static everywhere.
Fix: create an object (Counter c = new Counter(); c.count++;), or think about whether the field truly should be shared.
⚠️ Mistake: thinking final makes an object unchangeable final StringBuilder sb or final int[] marks — the contents can still change.
Fix: to make an object truly unchangeable, make its class immutable (private final fields, no setters).
⚠️ Mistake: forgetting to assign a blank final error: variable accountNumber not initialized in the default constructor.
Fix: every constructor must assign every final field exactly once.
⚠️ Mistake: making fields public "to make it work" It compiles, but anyone can now put invalid data in (negative price).
Fix: keep fields private and add a method that validates.
⚠️ Mistake: forgetting the semicolon after an anonymous class Discount d = new Discount() { ... } ← needs a ; at the end, because it's one assignment statement.

7. Best practices

  • Package by feature in real apps: com.course.shop.order, com.course.shop.product, each containing its controller, service, repository. (Topic 33 compares this with package-by-layer.)
  • Use lowercase, reversed-domain package names. Never use the default (no-package) package in real projects.
  • Prefer single-type imports; let VS Code organise them (Shift + Alt + O = Organize Imports).
  • Fields private, always. Expose behaviour through methods. Start with the most restrictive modifier.
  • Use final generously: for fields that never change, for dependencies, for constants. Immutable objects are thread-safe and easy to reason about.
  • Constants: private static final (or public if shared), UPPER_SNAKE_CASE, no magic numbers.
  • Utility classes: final + private constructor + static methods. Keep them small and "pure" (no hidden state).
  • Avoid mutable static state (static fields that change) — it's shared by everyone and causes bugs, especially with threads in web servers.
  • Prefer static nested over inner classes unless you really need the outer object.
  • In Spring apps, let Spring manage singletons — don't write getInstance() for your services.

8. Key takeaways

  • A package = a folder of related classes; the package line comes first and must match the folder path.
  • import is just a shortcut for long names; java.lang is imported automatically; import static imports static members.
  • Compile with javac -d out -sourcepath src ..., run with java -cp out com.shop.App (fully qualified name).
  • Access levels: public > protected > default (package) > private. Fields should be private.
  • static = belongs to the class, one shared copy. Static methods have no this.
  • final variable = assign once; final method = no override; final class = no extends. A final reference can still point to a changing object.
  • static final = constant (UPPER_SNAKE_CASE).
  • Nested classes: static nested (independent), inner (tied to an outer object), local (inside a method), anonymous (no name, one-off).
  • Singleton = private constructor + private static instance + public static getInstance(). Spring beans are singletons by default.

final class AppLogger {
    private static AppLogger instance;
    private int lineNo = 0;

    private AppLogger() { }

    public static synchronized AppLogger getInstance() {
        if (instance == null) {
            instance = new AppLogger();

        return instance;

        lineNo++;

10. Interview questions

Q1. What is a package in Java and why do we use it?

A package is a namespace that groups related classes and interfaces, and maps to a folder structure. We use packages to organise code, avoid name conflicts (java.util.Date vs java.sql.Date) and control access (package-private members are visible only within the package).

Q2. Explain the four access modifiers.

public: accessible everywhere. protected: same package plus subclasses in other packages. Default (no modifier): same package only. private: same class only. Top-level classes can only be public or default.

Q3. What is the difference between a static and an instance variable?

An instance variable belongs to each object — every object has its own copy. A static variable belongs to the class — one copy shared by all objects, created when the class is loaded. Static variables are accessed with the class name.

Q4. Why can't a static method access instance variables directly? Can we override static methods?

A static method is not called on an object, so there is no this — the JVM wouldn't know which object's variable to use. Static methods cannot be overridden: if a child declares the same static method, it hides the parent's one (method hiding); the call is decided at compile time by the reference type, not by the object.

Q5. Why is the main method static?

So the JVM can call it without creating an object of the class first. At startup there are no objects yet — main is the entry point.

Q6. What does final mean for a variable, method and class?

Variable: can be assigned only once (a final reference can't point elsewhere, but the object may still change). Method: cannot be overridden. Class: cannot be extended (e.g. String, Integer). Also: final, finally and finalize are unrelated.

Q7. What is a static block and when does it run?

A static { } block runs once when the class is loaded/initialised by the JVM, before any object is created and before static methods are used. It's used to initialise static fields that need more than a single expression.

Q8. Difference between a static nested class and an inner class?

A static nested class doesn't need an outer instance and cannot access outer instance fields directly. An inner (non-static) class is tied to an instance of the outer class (created with outer.new Inner()) and can access its fields, including private ones. Prefer static nested unless you need that link.

Q9. What is an anonymous class?

A class without a name, declared and instantiated in a single expression, usually to implement an interface or extend a class once: new Runnable() { public void run() { ... } }. For interfaces with one abstract method, lambdas are now usually preferred.

Q10. How do you implement a Singleton? Is it thread-safe? How does Spring relate?

Private constructor, private static final instance, public static getInstance(). The eager version and the enum version are thread-safe; a lazy version needs synchronized (or double-checked locking with volatile). Spring beans are singletons by default per container, but Spring manages them, so classes stay normal and testable — you don't hand-write getInstance().
