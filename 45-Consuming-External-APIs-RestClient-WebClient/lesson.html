45. Consuming External APIs: RestClient & WebClient

Make your Spring Boot app talk to other APIs — with RestTemplate, RestClient, WebClient and declarative HTTP interfaces — safely, with timeouts and proper error handling.

🎯 What you will learn
  • Why backend services call other APIs, and what changes when you are the client.
  • RestTemplate — the classic client you will meet in existing code.
  • RestClient — the modern, recommended client for normal (blocking) code.
  • WebClient — the reactive client (a preview; topic 55 goes deeper).
  • Declarative HTTP interfaces — @HttpExchange + HttpServiceProxyFactory.
  • Base URL in properties, timeouts, and turning remote errors into good answers (404 / 502 / 503).
  • How to work offline with a mock, and how to test client code with MockRestServiceServer.

1. Why this matters

So far our apps have only received HTTP requests. In real projects, your backend very often sends requests to other systems too:

  • An online shop calls a payment provider (Stripe, Razorpay, PayPal) to charge a card.
  • A food delivery app calls a maps API to compute distance, and an SMS API to send the OTP.
  • A travel site calls airline APIs to get flight prices.
  • In microservices (Part F), the order-service calls the product-service all day long.

When your app is the client, new problems appear: the other API can be slow, down, change its answers, or return errors. A good developer handles all of that so their users still get a clear answer. This lesson teaches the tools and the safety habits.

2. Real-life analogy

📞 You are a travel agent on the phone

A customer (your user) asks you for a flight price. You don't know it — you must phone the airline (the external API).

  • RestTemplate is the old desk phone: works fine, everybody knows it, but it's not getting new features.
  • RestClient is a modern smartphone: same idea (you call and wait on the line), but nicer to use.
  • WebClient is sending WhatsApp messages to three airlines at once and doing other work while you wait for the replies.
  • HTTP interface is a speed-dial button labelled "Airline – get price". You press it; the phone does the dialling.
  • Timeout: if the airline keeps you on hold for 10 minutes, you hang up and tell the customer "please try again later" — you don't freeze your whole office.
  • Error translation: the airline shouts technical jargon at you; you tell the customer a calm, clear sentence.

3. Concepts step by step

3.1 The big picture

Browser / curl→ Our DemoController→ Our service→ HTTP client (RestClient…)→ External API (JSONPlaceholder)

Our app is a server for the browser and a client for JSONPlaceholder at the same time. The HTTP client does 4 jobs for us:

  1. Build the request (method, URL, headers, JSON body from a Java object).
  2. Send it over the network and wait for the answer.
  3. Check the status code (2xx? 4xx? 5xx?).
  4. Convert the JSON answer into a Java object (with Jackson — same as in our controllers, just the other direction).
ℹ️ What is JSONPlaceholder? https://jsonplaceholder.typicode.com is a free, fake REST API for practice. It has /posts, /users, /comments... It even accepts POST requests (but doesn't really save them). Open https://jsonplaceholder.typicode.com/posts/1 in your browser to see the JSON.

💡 Simple rule New Spring MVC app? Use RestClient (or an HTTP interface on top of it). Reactive WebFlux app? Use WebClient. Existing code with RestTemplate? Keep it working; migrate when convenient.

3.3 Mapping JSON to Java (records)

The remote API returns JSON like {"userId":1,"id":1,"title":"...","body":"..."}. We create a record with the same field names:

model/Post.javapublic record Post(Long userId, Long id, String title, String body) { }

Jackson matches JSON names to record components. Extra JSON fields we don't declare (like address in User) are ignored, because Spring Boot configures Jackson with FAIL_ON_UNKNOWN_PROPERTIES = false. That's good: when the other team adds a field, our code doesn't break.

ℹ️ Different names? If the remote JSON uses user_id, write @JsonProperty("user_id") Long userId on the record component.

3.4 RestTemplate (legacy, but everywhere)

// GET → object
Post post = restTemplate.getForObject("/posts/{id}", Post.class, 1);

// GET → status + headers + body
ResponseEntity<Post> entity = restTemplate.getForEntity("/posts/{id}", Post.class, 1);

// POST
Post created = restTemplate.postForObject("/posts", newPost, Post.class);

// Generic types (List<Post>) need exchange + ParameterizedTypeReference
ResponseEntity<List<Post>> response = restTemplate.exchange(
        "/posts?userId={userId}", HttpMethod.GET, null,
        new ParameterizedTypeReference<List<Post>>() { }, 2);

Errors arrive as exceptions: HttpClientErrorException (4xx, with subclasses like HttpClientErrorException.NotFound), HttpServerErrorException (5xx), ResourceAccessException (no answer: timeout, connection refused).

ℹ️ Why ParameterizedTypeReference? Because of type erasure (topic 12), List<Post>.class does not exist. The anonymous subclass new ParameterizedTypeReference<List<Post>>() { } "remembers" the full generic type so Jackson knows to create Post objects inside the list.

3.5 RestClient (modern, recommended)

A fluent API: each step returns an object that offers the next step, so the code reads like a sentence.

Post post = restClient.get()                 // 1. HTTP method
        .uri("/posts/{id}", 1)               // 2. URL (relative to the base URL), {id} is filled in
        .retrieve()                          // 3. send it; get ready to read the response
        .body(Post.class);                   // 4. JSON body → Post

List<Post> posts = restClient.get()
        .uri(b -> b.path("/posts").queryParam("userId", 2).build())   // safe query parameters
        .retrieve()
        .body(new ParameterizedTypeReference<List<Post>>() { });

ResponseEntity<Post> created = restClient.post()
        .uri("/posts")
        .contentType(MediaType.APPLICATION_JSON)
        .body(newPost)                       // Java object → JSON request body
        .retrieve()
        .toEntity(Post.class);               // status + headers + body
After retrieve()Gives you
.body(Post.class)Just the body as an object
.toEntity(Post.class)ResponseEntity<Post>: status, headers, body
.toBodilessEntity()Status + headers, no body (e.g. for DELETE)
.onStatus(predicate, handler)Custom error handling for this call

By default, RestClient throws HttpClientErrorException / HttpServerErrorException for 4xx/5xx — the same exceptions as RestTemplate. We'll replace them with our own exceptions (3.9).

3.6 WebClient (reactive preview)

WebClient looks almost the same, but returns a Mono (0 or 1 value, later) or a Flux (0..N values, later) from Project Reactor.

Mono<Post> postMono = webClient.get()
        .uri("/posts/{id}", 1)
        .retrieve()
        .bodyToMono(Post.class);      // nothing is sent yet! A Mono is a "recipe".

Flux<Post> postsFlux = webClient.get().uri("/posts").retrieve().bodyToFlux(Post.class);

Important beginner facts:

  • Lazy: the request is only sent when someone subscribes. In a controller, just return the Mono — Spring subscribes for you.
  • Non-blocking: no thread sits waiting for the answer. That's why one server can handle many thousands of concurrent calls.
  • Parallel calls are easy: Mono.zip(userMono, postsMono) starts both requests at the same time and combines the results when both are back.
  • .block() turns a Mono into a normal value by waiting. OK in a main method or test; avoid it inside reactive code. In a Spring MVC app, prefer RestClient over "WebClient + block()".
GET /users/1∥ GET /posts?userId=1→ Mono.zip waits for both→ UserSummary

3.7 Declarative HTTP interfaces (@HttpExchange)

The nicest style of all: you only write an interface. Spring generates the implementation at runtime (a proxy, like the ones from topic 27).

@HttpExchange
public interface PostHttpClient {

    @GetExchange("/posts/{id}")
    Post getPost(@PathVariable Long id);

    @GetExchange("/posts")
    List<Post> getPosts(@RequestParam(required = false) Long userId);

    @PostExchange("/posts")
    Post createPost(@RequestBody NewPost newPost);
}

Then create the proxy once, as a bean:

HttpServiceProxyFactory factory = HttpServiceProxyFactory
        .builderFor(RestClientAdapter.create(restClient))   // use RestClient underneath
        .build();
PostHttpClient client = factory.createClient(PostHttpClient.class);

Post p = client.getPost(1L);   // → GET {baseUrl}/posts/1
AnnotationHTTP
@HttpExchangeGeneric (on the interface: shared URL prefix, headers)
@GetExchange, @PostExchange, @PutExchange, @PatchExchange, @DeleteExchangeThe matching HTTP method
@PathVariable, @RequestParam, @RequestBody, @RequestHeaderSame annotations you know from controllers, used "in reverse"
ℹ️ Feign Spring Cloud OpenFeign (topic 63) is an older library with the same idea. HTTP interfaces are Spring's built-in alternative, with no extra dependency.

3.8 Configuration: base URL and timeouts

Never hard-code URLs in Java. The URL is different in dev, test and production. Put it in properties and bind it to a record (topic 29):

application.propertiesexternal.jsonplaceholder.base-url=https://jsonplaceholder.typicode.com
external.jsonplaceholder.connect-timeout=3s
external.jsonplaceholder.read-timeout=5s
config/ExternalApiProperties.java@Validated
@ConfigurationProperties(prefix = "external.jsonplaceholder")
public record ExternalApiProperties(@NotBlank String baseUrl,
                                    @NotNull Duration connectTimeout,
                                    @NotNull Duration readTimeout) { }

Two timeouts:

  • Connect timeout — the maximum time to open the connection (is anyone answering the phone?).
  • Read timeout — the maximum time to wait for the answer once connected (how long on hold?).
🛑 Why timeouts are not optional Each request in Spring MVC uses one Tomcat thread (topic 17). Tomcat has ~200. If the remote API hangs and you have no timeout, each of your requests waits forever. After 200 requests, your whole app is frozen — even pages that don't use the remote API. One slow partner took you down. This is called a cascading failure (topic 64 shows circuit breakers for it).

3.9 Error handling strategy

Three kinds of problems can happen when calling an API:

What happenedSpring throws (by default)Our exceptionWe answer our client
Remote says 404HttpClientErrorException.NotFoundExternalResourceNotFoundException404 Not Found
Remote says other 4xx/5xxHttpClientErrorException / HttpServerErrorExceptionExternalServiceException502 Bad Gateway
No answer (timeout, connection refused, no internet)ResourceAccessException (WebClient: WebClientRequestException, TimeoutException)ExternalServiceUnavailableException503 Service Unavailable

Why translate? Our callers should not care which library or partner we use. "502" means "the server behind me failed"; "503" means "try again later". And we never forward the remote error body — it may contain internal details.

With RestClient you can set a default handler for every call, and override it per call:

RestClient client = builder
        .baseUrl(props.baseUrl())
        .defaultStatusHandler(HttpStatusCode::isError, (request, response) -> {
            if (response.getStatusCode().isSameCodeAs(HttpStatus.NOT_FOUND)) {
                throw new ExternalResourceNotFoundException("Remote resource not found: " + request.getURI());
            }
            throw new ExternalServiceException("Remote API returned " + response.getStatusCode().value(),
                    response.getStatusCode().value());
        })
        .build();

// per call (wins over the default):
restClient.post().uri("/posts").body(newPost).retrieve()
        .onStatus(HttpStatusCode::is4xxClientError, (req, res) -> { throw new ExternalServiceException(...); })
        .toEntity(Post.class);

3.10 Working offline: a local mock

Depending on a real internet API while learning (or in tests) is fragile: no Wi-Fi, a company firewall, or the API is down. So this project contains a small fake JSONPlaceholder inside the app (MockJsonPlaceholderController, under /mock-api). The offline profile simply points the base URL at it:

application-offline.propertiesexternal.jsonplaceholder.base-url=http://localhost:${server.port:8080}/mock-api

Not a single line of Java changes — that's the reward for putting the URL in configuration.

ℹ️ In real projects Mocks live in tests, not in production code: MockRestServiceServer (for RestTemplate/RestClient — used in our PostServiceTest), WireMock (a fake HTTP server for any client) or MockWebServer (OkHttp). We put the mock in src/main only so you can play with it in the browser.

4.2 HttpClientsConfig — one place for all clients

Spring Boot auto-configures builders (RestTemplateBuilder, RestClient.Builder, WebClient.Builder) already wired with Jackson and other defaults. We use them and add our settings:

config/HttpClientsConfig.java@Bean
public ClientHttpRequestFactory externalApiRequestFactory(ExternalApiProperties props) {
    HttpClient jdkHttpClient = HttpClient.newBuilder()           // java.net.http.HttpClient (Java 11+)
            .connectTimeout(props.connectTimeout())
            .build();
    JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory(jdkHttpClient);
    factory.setReadTimeout(props.readTimeout());
    return factory;
}

@Bean
public RestTemplate jsonPlaceholderRestTemplate(RestTemplateBuilder builder, ExternalApiProperties props) {
    return builder.rootUri(props.baseUrl())
            .connectTimeout(props.connectTimeout())
            .readTimeout(props.readTimeout())
            .build();
}

@Bean
public RestClient jsonPlaceholderRestClient(RestClient.Builder builder, ExternalApiProperties props,
                                            ClientHttpRequestFactory externalApiRequestFactory) {
    return builder
            .baseUrl(props.baseUrl())
            .requestFactory(externalApiRequestFactory)                 // ← the timeouts
            .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
            .defaultHeader(HttpHeaders.USER_AGENT, "course-api-client/1.0")
            .defaultStatusHandler(HttpStatusCode::isError, (request, response) -> { ... })   // see 3.9
            .build();
}

@Bean
public WebClient jsonPlaceholderWebClient(WebClient.Builder builder, ExternalApiProperties props) {
    return builder.baseUrl(props.baseUrl())
            .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
            .build();
}

@Bean
public PostHttpClient postHttpClient(RestClient jsonPlaceholderRestClient) {
    return HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(jsonPlaceholderRestClient))   // re-use URL, timeouts, errors
            .build()
            .createClient(PostHttpClient.class);
}
💡 Why build the clients once, as beans? Clients are thread-safe and somewhat expensive to create (connection pools). Create them once, inject them everywhere. Don't call RestClient.create() inside every method.

4.3 PostService (RestClient)

service/PostService.javapublic Post getPost(Long id) {
    try {
        return restClient.get()
                .uri("/posts/{id}", id)
                .retrieve()
                .body(Post.class);              // 404 → ExternalResourceNotFoundException (default handler)
    } catch (ResourceAccessException e) {       // timeout / no connection
        throw new ExternalServiceUnavailableException("JSONPlaceholder is not reachable: " + e.getMessage(), e);
    }
}

public UserSummary getUserSummary(Long userId) {
    User user = restClient.get().uri("/users/{id}", userId).retrieve().body(User.class);   // call 1
    List<Post> posts = getPostsByUser(userId);                                           // call 2 (after call 1)
    return UserSummary.of(user, posts);
}

4.4 ReactivePostService (WebClient)

service/ReactivePostService.javapublic Mono<Post> getPost(Long id) {
    return webClient.get()
            .uri("/posts/{id}", id)
            .retrieve()
            .onStatus(status -> status.isSameCodeAs(HttpStatus.NOT_FOUND),
                    response -> Mono.error(new ExternalResourceNotFoundException("Post " + id + " not found (WebClient)")))
            .onStatus(HttpStatusCode::isError,
                    response -> Mono.error(new ExternalServiceException("Remote error", response.statusCode().value())))
            .bodyToMono(Post.class)
            .timeout(timeout)                                   // give up after 5 s
            .onErrorMap(this::isConnectionProblem,              // low-level error → our exception
                    e -> new ExternalServiceUnavailableException("JSONPlaceholder is not reachable", e));
}

public Mono<UserSummary> getUserSummary(Long userId) {
    Mono<User> userMono = webClient.get().uri("/users/{id}", userId).retrieve().bodyToMono(User.class);
    Mono<List<Post>> postsMono = webClient.get()
            .uri(b -> b.path("/posts").queryParam("userId", userId).build())
            .retrieve().bodyToFlux(Post.class).collectList();

    return Mono.zip(userMono, postsMono)                         // both calls run AT THE SAME TIME
            .map(tuple -> UserSummary.of(tuple.getT1(), tuple.getT2()));
}

Notice the difference: in WebClient, errors are values in the stream (Mono.error(...)), not thrown immediately.

4.6 ApiExceptionHandler

web/ApiExceptionHandler.java@ExceptionHandler(ExternalResourceNotFoundException.class)
public ProblemDetail notFound(ExternalResourceNotFoundException ex) {
    return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
}

@ExceptionHandler(ExternalServiceException.class)
public ProblemDetail remoteError(ExternalServiceException ex) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_GATEWAY, "The external service returned an error");
    problem.setProperty("remoteStatus", ex.getRemoteStatus());
    return problem;
}

@ExceptionHandler({ExternalServiceUnavailableException.class, ResourceAccessException.class})
public ProblemDetail unavailable(RuntimeException ex) {
    return ProblemDetail.forStatusAndDetail(HttpStatus.SERVICE_UNAVAILABLE,
            "The external service is not reachable right now. Please try again later.");
}

6. Common mistakes

🛑 Mistake: no timeouts One slow partner freezes all Tomcat threads and your whole app.
Fix: always configure connect and read timeouts (and later: circuit breakers, topic 64).
⚠️ Mistake: new RestTemplate() / RestClient.create() inside methods No shared config, no timeouts, new objects for each call.
Fix: configure the client once as a bean using the Boot builders; inject it.
⚠️ Mistake: hard-coded URLs "https://api.partner.com/v1/orders" in Java code.
Fix: base URL in application.properties, per-profile overrides, relative paths in code.
⚠️ Mistake: building query strings by hand "/search?q=" + text breaks with spaces or &, and can be a security problem.
Fix: uri("/search?q={q}", text) or uriBuilder.queryParam("q", text) — they encode for you.
⚠️ Mistake: body(List.class) You get a List of LinkedHashMaps, not Posts — ClassCastException later.
Fix: new ParameterizedTypeReference<List<Post>>() { }.
⚠️ Mistake: WebClient that "does nothing" You called webClient.post()...bodyToMono(...) but never returned or subscribed to the Mono, so no request was sent.
Fix: return the Mono to Spring, or chain it into another reactive flow.
⚠️ Mistake: letting remote errors leak Your API returns 500 with HttpClientErrorException: 404 Not Found: [{...partner body...}].
Fix: translate to your own exceptions and a clean ProblemDetail (404 / 502 / 503).
⚠️ Mistake: secrets in code API keys like "sk_live_..." in Java or Git.
Fix: external.payment.api-key=${PAYMENT_API_KEY} and send it via defaultHeader("Authorization", "Bearer " + key).

7. Best practices

  • One configured client bean per external API, with base URL, timeouts, default headers and default error handling.
  • Wrap each external API in your own class (a service or an @HttpExchange interface). The rest of your code never sees URLs or HTTP details — easy to mock, easy to replace.
  • Use your own DTOs for remote data and declare only the fields you need.
  • Translate errors: 404 → 404 (if it makes sense), other remote errors → 502, no answer → 503/504.
  • Retry only idempotent calls (GET/PUT/DELETE), with a limit and back-off; for POST use an Idempotency-Key (topic 44). Resilience4j (topic 64) adds retries and circuit breakers declaratively.
  • Log the remote URL, status and duration (never the full body if it contains personal data or secrets).
  • Cache data that rarely changes (topic 51) to reduce calls and latency.
  • Test without the network: MockRestServiceServer, WireMock, or @RestClientTest.
  • Pick the right client: RestClient for MVC apps; WebClient for WebFlux apps or massive parallel I/O; HTTP interfaces for clean typed clients on top of either.

8. Key takeaways

  • Backends constantly call other APIs: payments, maps, SMS, other microservices.
  • RestTemplate is the classic client (maintenance mode) — read it, don't start new code with it.
  • RestClient (Spring 6.1) is the recommended blocking client: get().uri().retrieve().body().
  • WebClient is reactive: returns Mono/Flux, is lazy, and makes parallel calls easy (Mono.zip).
  • @HttpExchange interfaces + HttpServiceProxyFactory = typed clients with no implementation code.
  • Base URL and timeouts belong in properties; always set connect and read timeouts.
  • Translate remote problems: 404 → 404, remote error → 502, no answer → 503.
  • Use mocks (a local mock profile, MockRestServiceServer, WireMock) to work and test offline.

10. Interview questions

Q1. What are the options to call a REST API from Spring, and which would you choose today?

RestTemplate (classic, blocking, maintenance mode), RestClient (Spring 6.1, fluent, blocking — recommended for Spring MVC apps), WebClient (reactive, non-blocking — for WebFlux or high-concurrency I/O), declarative HTTP interfaces with @HttpExchange (on top of RestClient or WebClient), and Spring Cloud OpenFeign. For a new MVC app: RestClient, often behind an HTTP interface.

Q2. Is RestTemplate deprecated?

Not formally deprecated in Spring 6, but it's in maintenance mode: only minor fixes, no new features. Spring recommends RestClient for new synchronous code. (The Spring team has announced plans to deprecate it in a future major version.)

Q3. What is the difference between blocking and non-blocking HTTP clients?

A blocking client keeps the calling thread waiting until the response arrives. A non-blocking client registers a callback and frees the thread; the result is delivered later (as a Mono/Flux). Non-blocking scales better for many concurrent slow calls, but the programming model is more complex.

Q4. What do retrieve() and exchange() do in RestClient/WebClient?

retrieve() is the simple path: it sends the request and gives you convenient methods to read the body/entity, applying status handlers (errors throw by default). exchange() (RestClient) / exchangeToMono() (WebClient) gives full access to the raw response so you decide how to handle every status yourself.

Q5. How do you configure timeouts?

Connect timeout and read/response timeout on the underlying request factory or HTTP library — e.g. JdkClientHttpRequestFactory with HttpClient.connectTimeout + setReadTimeout for RestClient, RestTemplateBuilder.connectTimeout/readTimeout, Reactor Netty's responseTimeout or the .timeout() operator for WebClient. Spring Boot also offers spring.http.client.* properties / ClientHttpRequestFactorySettings.

Q6. How does a declarative HTTP interface work internally?

HttpServiceProxyFactory creates a JDK dynamic proxy for the interface. Each method call is intercepted; the annotations (@GetExchange, @PathVariable, @RequestBody...) are read to build an HTTP request, which is executed through an adapter (RestClientAdapter or WebClientAdapter), and the response is converted to the method's return type.

Q7. How do you handle errors from an external API?

Register status handlers (defaultStatusHandler / onStatus) or catch HttpClientErrorException/HttpServerErrorException/ResourceAccessException; translate them into domain exceptions; map those in a @RestControllerAdvice to suitable responses (404, 502, 503/504); log details internally; add retries/circuit breakers for transient failures.

Q8. How do you read a JSON array into List<Post>?

Pass a ParameterizedTypeReference<List<Post>> (because generic type information is erased at runtime), or in WebClient use bodyToFlux(Post.class).collectList(). With HTTP interfaces, simply declare the return type List<Post>.

Q9. How do you test code that calls an external API?

Unit/slice tests with MockRestServiceServer (RestTemplate/RestClient, also via @RestClientTest), mocking the client interface with Mockito, or a fake HTTP server like WireMock/MockWebServer for realistic integration tests (also works for WebClient). Avoid calling real third-party APIs in automated tests.

Q10. Can you use WebClient in a Spring MVC application?

Yes — add spring-boot-starter-webflux alongside -web; the app keeps running on Tomcat/MVC. Controllers may even return Mono/Flux. However, if you end up calling .block() everywhere, RestClient is the simpler and better choice.
