1. Why this matters

Imagine you change one line in BookService on a Friday evening. Did you break the discount rule? The duplicate-ISBN check? The 404 answer? Without tests, the only way to know is to click through everything by hand — or wait for an angry customer on Monday.

With a good test suite you type mvn test, wait 30 seconds, and get a clear green (everything still works) or red (this exact thing broke). That is why:

  • Every serious company requires tests in pull requests. CI pipelines (topic 68) run them on every push and block merging if they fail.
  • Tests let you refactor without fear.
  • Tests are living documentation: rejectsDuplicateIsbnAndNeverCallsSave() tells a new colleague exactly what the rule is.
  • Interviews for Spring developers almost always include "how do you test a controller / a repository?".

In topic 21 you learned JUnit 5 and Mockito on plain Java. Now we add the Spring part: how to test controllers, JSON, validation, repositories and the whole running app.

2. Real-life analogy

🚗 Testing a car before it leaves the factory
  • Unit tests = testing each part alone on a workbench: "Does this brake pad grip with 500 N?" The engine is not even attached. Fast and cheap — the factory does thousands per day. (BookService with a fake repository)
  • Slice tests = testing one system on a test rig: the whole braking system, with a fake wheel that just measures. (@WebMvcTest = only the web layer; @DataJpaTest = only the database layer)
  • Integration tests = a test driver takes the complete car around the track. Slow and expensive, so only a few — but it catches problems that appear only when everything is connected. (@SpringBootTest with a real server)
  • Mocks = crash-test dummies and fake wheels: stand-ins that behave the way you script them, and record what happened to them.
  • Code coverage = a checklist showing which parts of the car were touched by any test at all.

💡 The AAA pattern (from topic 21) Every test has three parts: Arrange (prepare data and mocks), Act (call the thing you test, once), Assert (check the result). Some teams write it as Given / When / Then. Keep the three parts visible with blank lines or comments.

3.3 Unit tests with Mockito — no Spring at all

A service has dependencies (a repository). In a unit test we replace them with mocks: fake objects whose answers we script, and which remember how they were called.

Mockito toolMeaning
@ExtendWith(MockitoExtension.class)Lets Mockito process the annotations below (JUnit 5 extension)
@Mock BookRepository repositoryCreate a fake repository. By default every method returns empty/null/0/false
@InjectMocks BookService serviceCreate a real service and inject the mocks (via constructor)
when(repo.findById(1L)).thenReturn(Optional.of(b))"When asked this, answer that" (stubbing)
thenThrow(...) / thenAnswer(inv -> ...)Throw an exception / compute the answer
verify(repo).save(any())Check that a method was called
verify(repo, never()).save(any())Check that it was not called; also times(2)
ArgumentCaptor<Book>Catch the argument passed to a mock to inspect it
ℹ️ Why constructor injection makes testing easy Because BookService receives its repository in the constructor (topic 24), a test can simply write new BookService(mockRepository). With field injection (@Autowired private BookRepository repo;) you would need reflection or Spring to set it.

3.4 @WebMvcTest + MockMvc — testing the web layer

@WebMvcTest(BookController.class) starts a small Spring context with only what the web layer needs:

The controller needs a BookService, which isn't loaded — so we provide a mock as a Spring bean with @MockitoBean.

MockMvc sends "pretend" HTTP requests straight into Spring MVC's DispatcherServlet (topic 31). No port, no network — but the full MVC machinery runs: URL mapping, @Valid, JSON conversion, exception handlers.

3.5 @MockitoBean vs the old @MockBean

For years, Spring Boot had @MockBean (package org.springframework.boot.test.mock.mockito). In Spring Framework 6.2 / Spring Boot 3.4, the Spring team moved this feature into the core framework under a new name:

Old (deprecated since Boot 3.4)New (use this)
@MockBean@MockitoBean — org.springframework.test.context.bean.override.mockito.MockitoBean
@SpyBean@MockitoSpyBean

They do the same job: create a Mockito mock and put it into the Spring context, replacing (or adding) the bean of that type. You'll still see @MockBean in older projects and tutorials — just read it as @MockitoBean. (It is removed in Spring Boot 4.)

⚠️ @Mock vs @MockitoBean @Mock = plain Mockito, for unit tests without Spring. @MockitoBean = a mock that lives inside the Spring context, for slice/integration tests. Using @Mock in a @WebMvcTest does nothing for the controller — Spring doesn't know about it.

3.6 @DataJpaTest — testing repositories

@DataJpaTest starts only the persistence slice: entities, Spring Data repositories, Hibernate, a DataSource. By default it:

  • Replaces your configured database with an embedded in-memory database (H2) — we have H2 on the classpath.
  • Runs every test in a transaction that is rolled back afterwards → tests don't leak data into each other.
  • Shows the SQL in the log, and provides TestEntityManager to insert test data directly.

What to test here? Your queries: derived methods, @Query JPQL/native, constraints. Don't test save()/findById() — the Spring team already did.

ℹ️ Flush! JPA writes to the database lazily. Constraints (unique, not null) are only checked when SQL is actually sent. Use saveAndFlush(...) or entityManager.flush() in tests that expect a database error.

3.7 @SpringBootTest — the full application

@SpringBootTest starts the whole application context — exactly like main() does. The webEnvironment attribute decides about the web server:

webEnvironmentServerUse with
MOCK (default)No real server; a mock servlet environment@AutoConfigureMockMvc + MockMvc
RANDOM_PORTReal embedded Tomcat on a free random portTestRestTemplate or WebTestClient
DEFINED_PORTReal server on server.port (8080)Rarely — clashes if 8080 is busy
NONENo web at allTesting non-web beans with the full context

TestRestTemplate is a test-friendly RestTemplate (topic 45) that is pre-configured with the random port, so you write "/api/books". And it doesn't throw on 4xx/5xx — you just check response.getStatusCode(). @LocalServerPort injects the actual port if you need it.

⚠️ No automatic rollback here With a real server, requests run on server threads, not in the test's transaction. Clean up yourself (repository.deleteAll() in @AfterEach) or each test must create unique data.
💡 Context caching Spring caches application contexts between test classes with the same configuration. Every different @MockitoBean set, properties or profile creates a new context (slow). Keep test configuration consistent to keep the suite fast.

3.9 Testcontainers (introduction)

H2 is "almost" MySQL/PostgreSQL — but not exactly. SQL functions, data types and constraint behaviour differ. Testcontainers starts a real database in Docker for your tests and removes it afterwards (we mentioned it in topic 43):

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)   // don't swap in H2
@Testcontainers
class BookRepositoryMySqlTest {

    @Container
    @ServiceConnection                         // Boot reads URL/user/password from the container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.4");

    // ... same tests, now against real MySQL
}

It needs Docker running and the test dependencies org.springframework.boot:spring-boot-testcontainers, org.testcontainers:junit-jupiter and org.testcontainers:mysql. It also works for Kafka, RabbitMQ, Redis... Our project stays with H2 so mvn test works without Docker.

3.10 Code coverage with JaCoCo

Code coverage = the percentage of your code that ran during the tests. JaCoCo ("Java Code Coverage") is the standard tool. It attaches an agent to the test JVM, records which lines and branches ran, and writes an HTML report.

pom.xml<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.13</version>
    <executions>
        <execution><id>prepare-agent</id><goals><goal>prepare-agent</goal></goals></execution>   <!-- before tests -->
        <execution><id>report</id><phase>test</phase><goals><goal>report</goal></goals></execution>   <!-- after tests -->
        <execution>
            <id>check</id><goals><goal>check</goal></goals>                <!-- on mvn verify -->
            <configuration>
                <rules><rule>
                    <element>BUNDLE</element>
                    <limits><limit>
                        <counter>LINE</counter><value>COVEREDRATIO</value><minimum>0.70</minimum>
                    </limit></limits>
                </rule></rules>
            </configuration>
        </execution>
    </executions>
</plugin>

After mvn test, open target/site/jacoco/index.html. Green lines ran, red lines never ran, yellow means only some branches of an if ran.

⚠️ Coverage is a flashlight, not a grade 100 % coverage does not mean "no bugs" — a test can run a line without checking anything. Use the report to find untested important logic. Many teams aim for ~70–80 % and focus on services and edge cases.

4.1 The service under test

book/BookService.java@Transactional
public BookResponse create(BookRequest request) {
    if (repository.existsByIsbn(request.isbn())) {
        throw new DuplicateIsbnException(request.isbn());          // rule 1
    }
    Book book = new Book(request.title().trim(), request.author().trim(), request.isbn(),
            request.price().setScale(2, RoundingMode.HALF_UP));    // rule 3
    return BookResponse.from(repository.save(book));
}

@Transactional
public BookResponse applyDiscount(Long id, int percent) {
    if (percent < 1 || percent > MAX_DISCOUNT_PERCENT) {
        throw new IllegalArgumentException("Discount must be between 1 and " + MAX_DISCOUNT_PERCENT + " percent");   // rule 2
    }
    Book book = getOrThrow(id);
    BigDecimal factor = BigDecimal.valueOf(100 - percent).divide(BigDecimal.valueOf(100));
    book.setPrice(book.getPrice().multiply(factor).setScale(2, RoundingMode.HALF_UP));
    return BookResponse.from(repository.save(book));
}

4.2 BookServiceTest — unit tests

src/test/java/com/course/testingdemo/book/BookServiceTest.java@ExtendWith(MockitoExtension.class)
class BookServiceTest {

    @Mock
    private BookRepository repository;     // fake

    @InjectMocks
    private BookService service;           // real, with the fake inside

    @Test
    @DisplayName("rejects a duplicate ISBN and never calls save()")
    void rejectsDuplicateIsbn() {
        // Arrange
        BookRequest request = new BookRequest("Clean Code", "Robert C. Martin", "978-0132350884", new BigDecimal("450.00"));
        when(repository.existsByIsbn("978-0132350884")).thenReturn(true);

        // Act + Assert
        assertThatThrownBy(() -> service.create(request))
                .isInstanceOf(DuplicateIsbnException.class);

        verify(repository, never()).save(any());      // the important part: nothing was saved!
    }

Capturing what was saved:

when(repository.existsByIsbn("978-0134757599")).thenReturn(false);
when(repository.save(any(Book.class))).thenAnswer(invocation -> invocation.getArgument(0));   // echo it back

service.create(new BookRequest("  Refactoring ", " Martin Fowler ", "978-0134757599", new BigDecimal("499.999")));

ArgumentCaptor<Book> captor = ArgumentCaptor.forClass(Book.class);
verify(repository).save(captor.capture());          // catch the Book passed to save()
Book saved = captor.getValue();
assertThat(saved.getTitle()).isEqualTo("Refactoring");             // trimmed
assertThat(saved.getPrice()).isEqualByComparingTo("500.00");       // rounded

@Nested inner classes group the tests per method (findById, create, applyDiscount), so the test report reads like a specification. isEqualByComparingTo compares BigDecimal values ignoring scale (90.0 equals 90.00) — isEqualTo would fail there!

4.3 BookControllerTest — web slice

src/test/java/com/course/testingdemo/book/BookControllerTest.java@WebMvcTest(BookController.class)
class BookControllerTest {

    @Autowired private MockMvc mockMvc;
    @Autowired private ObjectMapper objectMapper;

    @MockitoBean
    private BookService bookService;          // mock placed into the Spring context

    @Test
    void postCreatesBookAndReturns201WithLocation() throws Exception {
        BookRequest request = new BookRequest("Refactoring", "Martin Fowler", "978-0134757599", new BigDecimal("499.00"));
        when(bookService.create(any(BookRequest.class)))
                .thenReturn(new BookResponse(7L, "Refactoring", "Martin Fowler", "978-0134757599", new BigDecimal("499.00")));

        mockMvc.perform(post("/api/books")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(objectMapper.writeValueAsString(request)))   // Java → JSON
                .andExpect(status().isCreated())
                .andExpect(header().string("Location", containsString("/api/books/7")))
                .andExpect(jsonPath("$.id").value(7));
    }

    @Test
    void postWithInvalidBodyReturns400AndNeverCallsService() throws Exception {
        String invalidJson = """
                { "title": "", "author": "Someone", "isbn": "123", "price": -1 }
                """;
        mockMvc.perform(post("/api/books").contentType(MediaType.APPLICATION_JSON).content(invalidJson))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.errors.title").exists())
                .andExpect(jsonPath("$.errors.price").exists());

        verify(bookService, never()).create(any());     // validation stopped it before the service
    }

This test proves things a unit test cannot: the URL and HTTP method are mapped, @Valid is active, JSON field names are right, the Location header is built, and the @RestControllerAdvice turns exceptions into the right status codes. .andDo(print()) prints the full request and response in the console — great for debugging.

4.4 BookRepositoryTest — JPA slice

src/test/java/com/course/testingdemo/book/BookRepositoryTest.java@DataJpaTest
class BookRepositoryTest {

    @Autowired private TestEntityManager entityManager;
    @Autowired private BookRepository repository;

    @BeforeEach
    void insertBooks() {
        entityManager.persist(new Book("Clean Code", "Robert C. Martin", "978-0132350884", new BigDecimal("450.00")));
        entityManager.persist(new Book("Clean Architecture", "Robert C. Martin", "978-0134494166", new BigDecimal("480.00")));
        entityManager.persist(new Book("Effective Java", "Joshua Bloch", "978-0134685991", new BigDecimal("599.00")));
        entityManager.flush();
    }

    @Test
    void findByAuthorIsCaseInsensitiveAndSortedByTitle() {
        List<Book> books = repository.findByAuthorContainingIgnoreCaseOrderByTitleAsc("MARTIN");
        assertThat(books).extracting(Book::getTitle).containsExactly("Clean Architecture", "Clean Code");
    }

    @Test
    void uniqueIsbnIsEnforcedByTheDatabase() {
        Book duplicate = new Book("Copy", "Someone", "978-0132350884", new BigDecimal("1.00"));
        assertThatThrownBy(() -> repository.saveAndFlush(duplicate))
                .isInstanceOf(DataIntegrityViolationException.class);
    }
}

Each test starts with the same 3 books, because the previous test's changes were rolled back. You'll see an ERROR ... Unique index or primary key violation line in the log during uniqueIsbnIsEnforcedByTheDatabase — that's Hibernate logging the error we expected; the test still passes.

4.5 BookApiIntegrationTest — the whole app

src/test/java/com/course/testingdemo/BookApiIntegrationTest.java@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT,
        properties = "app.seed-data=false")              // no sample data: tests own their data
class BookApiIntegrationTest {

    @LocalServerPort private int port;
    @Autowired private TestRestTemplate restTemplate;
    @Autowired private BookRepository repository;

    @AfterEach
    void cleanDatabase() { repository.deleteAll(); }

    @Test
    void fullBookLifecycle() {
        BookRequest request = new BookRequest("Clean Code", "Robert C. Martin", "978-0132350884", new BigDecimal("450.00"));
        ResponseEntity<BookResponse> created = restTemplate.postForEntity("/api/books", request, BookResponse.class);
        assertThat(created.getStatusCode()).isEqualTo(HttpStatus.CREATED);
        URI location = created.getHeaders().getLocation();
        Long id = created.getBody().id();

        ResponseEntity<BookResponse> fetched = restTemplate.getForEntity(location, BookResponse.class);
        assertThat(fetched.getBody().title()).isEqualTo("Clean Code");

        ResponseEntity<BookResponse> discounted = restTemplate.exchange(
                "/api/books/{id}/discount?percent=10", HttpMethod.PATCH, null, BookResponse.class, id);
        assertThat(discounted.getBody().price()).isEqualByComparingTo("405.00");

        ResponseEntity<Void> deleted = restTemplate.exchange("/api/books/{id}", HttpMethod.DELETE, null, Void.class, id);
        assertThat(deleted.getStatusCode()).isEqualTo(HttpStatus.NO_CONTENT);
    }

    @Test
    void unknownBookReturns404() {
        ResponseEntity<ProblemDetail> response = restTemplate.getForEntity("/api/books/12345", ProblemDetail.class);
        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.NOT_FOUND);
    }
}

Real HTTP, real JSON, real Tomcat, real H2, real transactions. If any wiring is wrong (a missing bean, a wrong property, a broken query), this test shows it.

6. Common mistakes

⚠️ Mistake: @SpringBootTest for everything Every test starts the whole app; the suite takes minutes.
Fix: unit tests for logic, slices for layers, a few @SpringBootTests for key flows.
⚠️ Mistake: NoSuchBeanDefinitionException: BookService in a @WebMvcTest Services aren't loaded in the web slice.
Fix: add @MockitoBean private BookService bookService;.
⚠️ Mistake: using @Mock instead of @MockitoBean in a Spring test (or the other way round).
Fix: @Mock + @ExtendWith(MockitoExtension.class) for plain unit tests; @MockitoBean for tests with a Spring context.
⚠️ Mistake: comparing BigDecimal with isEqualTo new BigDecimal("90.0") is not equal to new BigDecimal("90.00") (different scale).
Fix: isEqualByComparingTo("90.00").
⚠️ Mistake: tests that depend on each other or on order Test B only passes if test A ran first and left data behind.
Fix: each test arranges its own data; clean up in @AfterEach; rely on rollback in @DataJpaTest.
⚠️ Mistake: expecting a constraint error without flushing repository.save(duplicate) passes; the error appears later or never.
Fix: saveAndFlush(...) or entityManager.flush().
⚠️ Mistake: "UnnecessaryStubbingException" Mockito's strict mode complains that you stubbed something the code never used.
Fix: remove the unused when(...) — it usually means the test doesn't test what you think.
⚠️ Mistake: hard-coding port 8080 in tests Fails when the app (or another test run) is already using 8080.
Fix: RANDOM_PORT + TestRestTemplate (relative URLs) or @LocalServerPort.
🛑 Mistake: tests without assertions A test that calls code but checks nothing always passes and gives false confidence (and fake coverage).
Fix: every test must assertThat or verify something meaningful.

7. Best practices

  • Follow the pyramid: many fast unit tests, some slice tests, a few integration tests.
  • One behaviour per test, with a descriptive name: rejectsDuplicateIsbnAndNeverCallsSave or @DisplayName.
  • AAA / Given-When-Then structure, visible in every test.
  • Test behaviour, not implementation: assert results and important interactions, not every internal call.
  • Test the edges: empty lists, 0, negative numbers, max values, nulls, duplicates, not found.
  • Mock only what you own and what is slow/external (repositories, HTTP clients). Don't mock simple value objects or DTOs.
  • Keep tests independent and repeatable: no shared mutable state, no dependence on time/order/network (inject a Clock for time-based logic).
  • Prefer Testcontainers for repository/integration tests against your real database engine in CI.
  • Run tests on every push (CI, topic 68) and never merge red builds.
  • Use coverage to find gaps, not as a target to game; review the red lines in services first.
  • Keep the context cache warm: reuse the same test configuration across classes; avoid unnecessary @DirtiesContext.

8. Key takeaways

  • spring-boot-starter-test bundles JUnit 5, Mockito, AssertJ, Hamcrest, MockMvc, JSONPath and more.
  • Unit tests use @ExtendWith(MockitoExtension.class), @Mock, @InjectMocks, when/verify — no Spring, milliseconds.
  • @WebMvcTest loads only the web layer; use MockMvc + jsonPath, and @MockitoBean for services.
  • @MockitoBean/@MockitoSpyBean replace the deprecated @MockBean/@SpyBean (Boot 3.4+).
  • @DataJpaTest loads JPA + embedded H2 and rolls back each test; test your own queries and constraints.
  • @SpringBootTest(webEnvironment = RANDOM_PORT) + TestRestTemplate tests the real running app end to end.
  • Testcontainers runs real databases/brokers in Docker for realistic tests.
  • JaCoCo measures coverage (target/site/jacoco/index.html) and can fail the build below a threshold.

Hint / solution
@SpringBootTest(properties = "app.seed-data=false")
@AutoConfigureMockMvc
@Transactional
class BookFlowMockMvcTest {

    @Autowired MockMvc mockMvc;

    @Test
    void createThenRead() throws Exception {
        String location = mockMvc.perform(post("/api/books")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                {"title":"DDD","author":"Eric Evans","isbn":"978-0321125217","price":700}
                                """))
                .andExpect(status().isCreated())
                .andReturn().getResponse().getHeader("Location");

        mockMvc.perform(get(location))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.title").value("DDD"));
    }
}

With the MOCK environment, MockMvc calls the controller on the test's own thread, so it joins the test transaction, which Spring rolls back at the end. With RANDOM_PORT, requests are handled by Tomcat threads with their own transactions that commit — the test's transaction can't undo them.

10. Interview questions

Q1. What is the difference between a unit test and an integration test in Spring Boot?

A unit test checks one class in isolation, with dependencies mocked and no Spring context — very fast. An integration test runs several real components together (often the full context with @SpringBootTest, a real database and HTTP) to verify they work together. Slice tests sit in between: a partial context for one layer.

Q2. What does @WebMvcTest load, and how do you deal with the service dependency?

It loads only MVC infrastructure: the specified controllers, @ControllerAdvice, Jackson, validation, converters, filters and MockMvc — not services, repositories or data sources. Missing dependencies like services are provided as mocks with @MockitoBean (formerly @MockBean).

Q3. @Mock vs @MockitoBean (or @MockBean)?

@Mock creates a plain Mockito mock, used with MockitoExtension in tests without Spring. @MockitoBean creates a mock and registers it in the Spring ApplicationContext, replacing any bean of that type, so other beans (e.g. the controller) get it injected. @MockitoBean (Spring Framework 6.2) replaces Spring Boot's @MockBean, deprecated in Boot 3.4.

Q4. What does @DataJpaTest do by default?

Configures only JPA components (entities, repositories, EntityManager), replaces the DataSource with an embedded in-memory database if available, enables SQL logging, provides TestEntityManager, and wraps each test in a transaction rolled back at the end. Use @AutoConfigureTestDatabase(replace = NONE) to use a real database (e.g. with Testcontainers).

Q5. What is MockMvc and how is it different from TestRestTemplate?

MockMvc performs requests directly against the DispatcherServlet in a mock servlet environment — no real server or network, same thread as the test. TestRestTemplate sends real HTTP requests to a running embedded server (RANDOM_PORT). MockMvc is faster and allows transactional rollback; TestRestTemplate is more realistic (real serialization over the wire, filters, server behaviour).

Q6. Explain the webEnvironment options of @SpringBootTest.

MOCK (default): mock servlet environment, used with MockMvc; RANDOM_PORT: real server on a random free port; DEFINED_PORT: real server on the configured port; NONE: no web environment.

Q7. Why might Spring tests be slow, and how do you speed them up?

Starting application contexts is expensive. Speed up by preferring unit and slice tests, keeping test configuration consistent so Spring's context cache can reuse contexts (each distinct set of @MockitoBeans/properties/profiles creates a new context), avoiding @DirtiesContext, and running tests in parallel where safe.

Q8. What is Testcontainers and when would you use it?

A library that starts throwaway Docker containers (databases, Kafka, Redis...) from tests. Use it for integration/repository tests that must behave exactly like production infrastructure, instead of H2 or fakes. Spring Boot's @ServiceConnection wires connection details automatically.

Q9. What is code coverage, and is 100 % a good goal?

The share of code (lines, branches, instructions) executed by tests, measured by tools like JaCoCo. It's useful to find untested code, but 100 % is rarely worth it and doesn't guarantee correctness — assertions matter more. Teams commonly set a reasonable threshold (e.g. 70–80 %) and focus on critical business logic.

Q10. How do you test that a method was NOT called, or inspect the argument passed to a mock?

verify(mock, never()).method(any()) checks it was not called (also times(n), atLeastOnce()). ArgumentCaptor<T> with verify(mock).method(captor.capture()) captures the actual argument so you can assert on its fields.
