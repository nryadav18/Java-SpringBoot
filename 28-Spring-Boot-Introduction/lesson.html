1. Why this matters

In topics 22–27 you used the plain Spring Framework. It worked well, but think about how much setup you did: you picked the right version of spring-context, wrote @Configuration classes, created the AnnotationConfigApplicationContext yourself, and added the exec plugin just to run main.

Now imagine a real web application. Before Spring Boot (before 2014), a developer also had to:

  • install a separate web server (Apache Tomcat) and copy a .war file into it,
  • write a web.xml file to register Spring's DispatcherServlet,
  • configure a JSON library, a database connection pool, a transaction manager, logging…
  • and make sure all 30+ library versions worked together (they often did not!).

That could take a whole day before writing one line of business code. Spring Boot removes almost all of it. You add one dependency, write one class with main, and you have a running web server in seconds.

ℹ️ Where you will see it at work Today almost every new Spring project in companies is a Spring Boot project: banking back-ends, e-commerce APIs, microservices, batch jobs, internal tools. When a job advert says "Spring", it practically always means "Spring Boot". Everything from here to the end of the course is built on Spring Boot.

2. Real-life analogy

🏠 A furnished apartment vs an empty plot of land

The Spring Framework is like buying a plot of land plus a truck full of excellent building materials. You can build any house you want — but you must design it, lay the pipes, fit the wiring and buy matching parts yourself.

Spring Boot is like moving into a fully furnished apartment. Electricity, water, a kitchen, a bed — all ready. The builder made sensible choices for you ("opinionated defaults"). You just bring your clothes (your business code) and start living. And if you don't like the sofa? You can still replace it (override any default).

  • Starters = furniture packages ("kitchen package" = stove + fridge + pots that fit together).
  • Auto-configuration = the caretaker who notices "you brought a coffee machine, let me connect it to power and water".
  • Embedded Tomcat = the apartment comes with its own front door; you don't need to rent a separate building to receive guests.
  • Actuator = the smart meter on the wall that tells you if everything is healthy.

3. Concepts step by step

3.1 What exactly is Spring Boot?

Spring Boot is not a new framework that replaces Spring. It is a layer on top of the Spring Framework that configures Spring for you. Inside every Spring Boot app there is the same ApplicationContext, the same beans, the same dependency injection you learned in topics 22–27. Spring Boot just builds and wires it automatically.

Your code
controllers, serviceson top of Spring Boot
auto-config, starters, embedded serveron top of Spring Framework
IoC, DI, MVC, AOP…on top of Java 17 / JVM

Spring Boot gives you six big things:

FeatureWhat it means in simple words
Auto-configurationSpring Boot looks at the libraries on your classpath and creates the beans you probably need. Web library present? It starts a web server. H2 database present? It creates a DataSource.
StartersOne dependency that pulls in a whole, tested set of libraries. spring-boot-starter-web = Spring MVC + Jackson + Tomcat + validation helpers + logging.
Embedded serverTomcat runs inside your application. Your app is a normal main method and a normal jar. No server to install.
Opinionated defaultsSensible choices are made for you: port 8080, Logback for logging, Jackson for JSON, HikariCP for DB connections. You override only what you want to change.
ActuatorProduction-ready endpoints like /actuator/health and metrics, by adding one starter (topic 53 goes deeper).
No XMLConfiguration is Java annotations plus one simple application.properties (or .yml) file.

3.3 Starters — dependency "packages"

A starter is a Maven dependency that contains almost no code. Its job is to pull in a group of other dependencies that belong together, in versions that are tested together. Starters are named spring-boot-starter-*.

pom.xml (part)<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <!-- no <version>! The parent POM decides it -->
</dependency>

That single block brings in Spring MVC, Jackson (JSON), embedded Tomcat, logging (SLF4J + Logback), YAML support and more — about 20 jars.

3.4 The parent POM — one version to rule them all

pom.xml (part)<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.6</version>
</parent>

Remember parent POMs and BOMs from topic 20? The Spring Boot parent contains a huge list of "approved" versions for hundreds of libraries (Spring, Jackson, Tomcat, Hibernate, JUnit…). That is why we never write <version> for those dependencies. When you upgrade Spring Boot, you change one number and all libraries move together. The parent also sets the Java version (from <java.version>), UTF-8 encoding and good plugin settings.

3.5 The embedded server

Old way: the server was the main program and your app was a guest inside it. Spring Boot way: your app is the main program and it starts Tomcat inside itself, like starting a thread.

Old: Tomcat installed on server→deploy app.war into it
Boot: java -jar app.jar→main() starts→embedded Tomcat starts on port 8080

Benefits: the same jar runs on your laptop, a test server, a Docker container or the cloud (topics 66–69). Tomcat is the default; you can swap to Jetty or Undertow by changing dependencies.

3.11 CommandLineRunner — "do this once at startup"

Sometimes you need to run code once, right after the app has started: insert sample data, print a summary, check a connection. Any bean that implements CommandLineRunner is called automatically at step 9.

@Component
public class StartupRunner implements CommandLineRunner {
    @Override
    public void run(String... args) {
        System.out.println("App started with args: " + Arrays.toString(args));
    }
}

You can also write it as a @Bean returning a lambda (we use this style in topic 29):

@Bean
CommandLineRunner sayHi() {
    return args -> System.out.println("Hi from a lambda runner!");
}
ℹ️ ApplicationRunner is the twin of CommandLineRunner. It receives an ApplicationArguments object that already splits options like --name=Asha for you. If you have several runners, order them with @Order(1), @Order(2).

3.12 Your first REST endpoint

@RestController
public class HelloController {
    @GetMapping("/hello")
    public String hello(@RequestParam(defaultValue = "World") String name) {
        return "Hello, " + name + "!";
    }
}
  • @RestController — "this class answers HTTP requests and writes return values directly into the response".
  • @GetMapping("/hello") — "call this method for GET http://localhost:8080/hello".
  • @RequestParam — reads ?name=Asha from the URL; if missing, uses World.
  • Return a String → plain text. Return an object, list or Map → JSON, automatically, thanks to Jackson.

Topics 31 and 32 explain all of this in depth. For now, enjoy that this is the entire code needed for a web endpoint.

3.13 Running: mvn spring-boot:run vs java -jar

CommandWhat it doesWhen to use
mvn spring-boot:runCompiles and runs the app directly from your source folder.During development.
mvn clean packageCompiles, runs tests and builds target/boot-intro-0.0.1-SNAPSHOT.jar.Before shipping.

The jar is a "fat jar" (also called "uber jar"): the spring-boot-maven-plugin puts your classes and all dependency jars inside it, plus a small launcher that knows how to load jars-inside-a-jar. That is why it is ~20 MB, and why it "just runs".

3.14 DevTools — automatic restart

With spring-boot-devtools on the classpath, the app restarts automatically whenever compiled classes change. In VS Code, Java files are compiled when you save, so: edit → Ctrl + S → the app restarts in ~1 second.

  • The restart is fast because DevTools uses two class loaders: one for libraries (never reloaded) and one for your code (reloaded).
  • DevTools is disabled automatically when you run a packaged jar with java -jar — it is a development-only tool.
  • It also turns off template caching (useful for Thymeleaf in topic 36).
💡 Tip If you run the app with mvn spring-boot:run in a terminal, run mvn compile in a second terminal to trigger the restart (or simply rely on VS Code's auto-build).

3.15 The banner

The big ASCII "Spring" logo at startup is the banner. Put a file called banner.txt in src/main/resources and Spring Boot prints it instead. Placeholders like ${spring-boot.version} are replaced. Turn it off with spring.main.banner-mode=off. Fun, but it also helps you see at a glance which app is starting in a busy terminal.

3.16 How auto-configuration works (the "magic" explained)

In topic 26 you wrote a @Conditional bean: a bean that is created only if a condition is true. Auto-configuration is simply hundreds of ready-made @Configuration classes with conditions, shipped inside the spring-boot-autoconfigure jar.

  1. @EnableAutoConfiguration reads a list of auto-configuration classes from the file META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports inside the jar.
  2. For each class, Spring checks its conditions.
  3. If all conditions match, its beans are created. If not, the class is skipped.

A simplified version of a real one looks like this:

@AutoConfiguration
@ConditionalOnClass(ObjectMapper.class)          // only if Jackson is on the classpath
public class JacksonAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                    // only if YOU did not define your own ObjectMapper
    public ObjectMapper jacksonObjectMapper() {
        return new ObjectMapper();
    }
}
ConditionMeaning
@ConditionalOnClassA certain class is on the classpath (a library was added).
@ConditionalOnMissingClassA class is NOT on the classpath.
@ConditionalOnBean / @ConditionalOnMissingBeanA bean of some type exists / does not exist yet.
@ConditionalOnPropertyA property has a certain value (e.g. a feature switch).
@ConditionalOnWebApplicationThe app is a web application.
💡 The key idea: "back off" Thanks to @ConditionalOnMissingBean, if you define your own bean, Spring Boot's default steps aside. That is how you customise anything: just declare your own bean.

Seeing the decisions: start the app with --debug (or set debug=true in application.properties). Spring Boot prints a CONDITIONS EVALUATION REPORT:

============================
CONDITIONS EVALUATION REPORT
============================

Positive matches:
-----------------
   DispatcherServletAutoConfiguration matched:
      - @ConditionalOnClass found required class 'org.springframework.web.servlet.DispatcherServlet'

Negative matches:
-----------------
   DataSourceAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class 'org.springframework.jdbc.datasource.embedded.EmbeddedDatabaseType'

Read it like this: "a web server was configured because Spring MVC is present; no database was configured because no JDBC library is present". When something is (or is not) auto-configured and you don't know why, this report is your first stop. To switch off one auto-configuration on purpose: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class).

3.17 Actuator in one minute

Adding spring-boot-starter-actuator gives ready-made management endpoints. By default only /actuator/health is exposed over HTTP. We also exposed info:

management.endpoints.web.exposure.include=health,info

GET /actuator/health returns {"status":"UP"}. Load balancers, Docker and Kubernetes call this to check your app is alive. Topic 53 covers Actuator fully.

4.2 HelloController and GreetingService

src/main/java/com/course/bootintro/HelloController.java@RestController
public class HelloController {

    private final GreetingService greetingService;

    public HelloController(GreetingService greetingService) {   // constructor injection
        this.greetingService = greetingService;
    }

    @GetMapping("/hello")
    public String hello(@RequestParam(defaultValue = "World") String name) {
        return greetingService.greet(name);
    }

    @GetMapping("/info")
    public Map<String, Object> info() {
        return Map.of(
                "app", "boot-intro",
                "framework", "Spring Boot 3.5.6",
                "javaVersion", System.getProperty("java.version"),
                "serverTime", LocalDateTime.now().toString());
    }
}

Notice that the controller uses constructor injection exactly like topic 24 — no @Autowired needed with a single constructor. The /info method returns a Map<String, Object>, and Spring Boot's auto-configured Jackson turns it into JSON. We did not configure Jackson anywhere — auto-configuration did.

4.3 StartupRunner

src/main/java/com/course/bootintro/StartupRunner.java@Component
public class StartupRunner implements CommandLineRunner {

    private final ApplicationContext context;
    private final GreetingService greetingService;

    public StartupRunner(ApplicationContext context, GreetingService greetingService) {
        this.context = context;
        this.greetingService = greetingService;
    }

    @Override
    public void run(String... args) {
        System.out.println(" Command-line args : " + Arrays.toString(args));
        System.out.println(" Beans in container: " + context.getBeanDefinitionCount());
        System.out.println(" Quick self-test   : " + greetingService.greet("Startup"));
    }
}

The bean count is an eye-opener: our project has only 4 classes, but the container holds about 280 beans. Almost all of them were created by auto-configuration (Tomcat, DispatcherServlet, Jackson, Actuator…). We can even inject the ApplicationContext itself.

6. Common mistakes

❌ Mistake: "Web server failed to start. Port 8080 was already in use." Another program (often your own app started earlier and still running) is using port 8080.
Fix: stop the old app (Ctrl + C, or the ■ button). Or start on another port: --server.port=8081. To find who uses the port in PowerShell: netstat -ano | findstr :8080, then Stop-Process -Id <PID>.
⚠️ Mistake: controller in the wrong package → 404 Not Found You put HelloController in com.course.controllers but the main class is in com.course.bootintro. Component scan does not find it, so /hello returns a 404 "Whitelabel Error Page".
Fix: move classes into the main class's package or its sub-packages.
⚠️ Mistake: the app starts and immediately stops You forgot spring-boot-starter-web (or added only spring-boot-starter). Without a web library there is no server, so after the runners finish, the app exits.
Fix: add the web starter if you want an HTTP server.
⚠️ Mistake: writing versions for Spring Boot-managed dependencies Adding <version>6.1.0</version> to a Spring dependency can mix incompatible versions and cause strange NoSuchMethodErrors.
Fix: remove the version and let the parent manage it.
⚠️ Mistake: "no main manifest attribute" when running java -jar The spring-boot-maven-plugin is missing from <build>, so a normal (non-executable) jar was built.
Fix: add the plugin and run mvn clean package again.
⚠️ Mistake: "Whitelabel Error Page" at http://localhost:8080/ This is not a crash! There is simply no endpoint mapped to /. Use /hello.
⚠️ Mistake: thinking auto-configuration is "magic you can't control" Every decision is visible in the --debug report and can be overridden by defining your own bean or setting a property.

7. Best practices

  • Always start from Spring Initializr (website or VS Code). It gives a correct, current structure.
  • Keep the main class in the root package and organise code in sub-packages.
  • Prefer starters over picking individual libraries; let the parent POM manage versions.
  • Keep the main class tiny. Business code belongs in services, not in main or runners.
  • Override, don't fight. To customise auto-configuration, set a property first; only if that is not enough, define your own bean.
  • Use constructor injection everywhere (as in topic 24).
  • Upgrade Spring Boot regularly (patch versions like 3.5.5 → 3.5.6 contain security fixes) — one line in the pom.
  • DevTools only in development — keep it optional with runtime scope.
  • Expose Actuator endpoints carefully. health is safe; things like env or beans must not be public in production.
  • Ship one jar and configure it from outside (next topic) instead of building different jars for each environment.

8. Key takeaways

  • Spring Boot = Spring Framework + auto-configuration + starters + embedded server + sensible defaults.
  • Starters are dependency bundles; the parent POM manages all versions.
  • @SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan.
  • SpringApplication.run prepares the environment, creates the container, auto-configures, creates beans, starts Tomcat and calls runners.
  • Auto-configuration = conditional @Configuration classes; they back off when you define your own beans. See them with --debug.
  • CommandLineRunner runs code once after startup.
  • Run with mvn spring-boot:run; ship with mvn package + java -jar (fat jar).
  • DevTools restarts the app on code changes during development.

10. Interview questions

Q1. What is Spring Boot and how is it different from the Spring Framework?

Spring Boot is a project built on top of the Spring Framework that makes it quick to create production-ready apps. It adds auto-configuration, starter dependencies, an embedded server, externalised configuration and Actuator. The Spring Framework provides the core features (IoC/DI, MVC, AOP…); Spring Boot configures them for you with sensible defaults.

Q2. What does @SpringBootApplication do?

It combines @SpringBootConfiguration (a @Configuration), @EnableAutoConfiguration and @ComponentScan (scanning the package of the annotated class and its sub-packages).

Q3. How does auto-configuration work internally?

@EnableAutoConfiguration loads auto-configuration classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Each is a @Configuration guarded by conditions such as @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty. Only matching ones contribute beans. Run with --debug to see the conditions evaluation report.

Q4. What is a starter? Give examples.

A starter is a dependency descriptor that brings a consistent set of libraries for a feature: spring-boot-starter-web, -data-jpa, -security, -test, -actuator. Versions come from the Spring Boot BOM/parent.

Q5. How do you disable a specific auto-configuration?

@SpringBootApplication(exclude = DataSourceAutoConfiguration.class) or the property spring.autoconfigure.exclude=.... Often you don't need to exclude: just define your own bean and the default backs off.

Q6. Which embedded servers does Spring Boot support, and how do you change the port?

Tomcat (default), Jetty and Undertow for servlet apps; Netty for reactive apps. Change the port with server.port=9090 (properties, env var SERVER_PORT or --server.port=9090). server.port=0 picks a random free port.

Q7. What is CommandLineRunner? How is it different from ApplicationRunner?

Both are callbacks that run once after the context has started. CommandLineRunner.run(String... args) gets raw arguments; ApplicationRunner.run(ApplicationArguments) gets parsed option/non-option arguments. Order multiple runners with @Order.

Q8. What is a fat jar? How does java -jar run a Spring Boot app?

The Spring Boot Maven plugin repackages the jar to include all dependency jars (in BOOT-INF/lib) and your classes (in BOOT-INF/classes). The manifest's Main-Class is Spring Boot's JarLauncher, which sets up a class loader for nested jars and then calls your main class (Start-Class).

Q9. What is spring-boot-devtools used for? Is it active in production?

It speeds up development with automatic restarts, LiveReload and dev-friendly defaults (e.g., no template caching). It is automatically disabled when running a fully packaged application with java -jar, and it is usually marked optional/runtime so it is not shipped.

Q10. What happens when you call SpringApplication.run()?

It determines the application type, prepares the Environment (properties, profiles, args), prints the banner, creates the ApplicationContext, performs component scanning and auto-configuration, instantiates singleton beans, starts the embedded web server, publishes startup events and calls CommandLineRunner/ApplicationRunner beans.
