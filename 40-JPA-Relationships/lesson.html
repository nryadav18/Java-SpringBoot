Connect your entities — customers with addresses, customers with orders, orders with products — and avoid the famous traps: LazyInitializationException, the N+1 problem and infinite JSON.

1. Why this matters

Real data is connected. A customer has an address. A customer places many orders. An order contains many products, and a product appears in many orders. In the database these links are stored as foreign keys. In Java we want to simply write customer.getOrders() or order.getCustomer().getName().

JPA relationships give you exactly that. But they are also the place where most performance bugs and confusing errors in Spring Boot applications come from. Companies regularly find pages that run 500 SQL queries instead of 1 because of the "N+1 problem". After this lesson you will know how to spot and fix it — an extremely valuable skill and a top interview topic.

2. Real-life analogy

🏠 A family, a house, and a shop One-to-one: one person has one passport. The passport number is written in the person's file.
One-to-many: one mother, many children. Each child's birth certificate says who the mother is. The mother's file doesn't have a list of birth-certificate numbers — the information is stored on the children's side. That's why, in JPA, the "many" side (the child) is the owner of the relationship.
Many-to-many: students and courses. A student takes many courses, a course has many students. You can't write it on either card — you need a separate enrolment list (a join table) with lines like "Asha – Java", "Asha – Spring", "Ben – Java".
Lazy loading is like a library catalogue card that says "see shelf 7": you only walk to shelf 7 if you actually need the book. The N+1 problem is walking to the shelf separately for each of 100 books instead of bringing a trolley once.

3. Concepts step by step

3.1 Foreign keys in 1 minute

A foreign key (FK) is a column that stores the id of a row in another table. orders.customer_id = 1 means "this order belongs to customer 1". The database guarantees that customer 1 really exists.

3.2 The relationship kinds

KindExampleAnnotationsWhere is the FK?
One-to-oneCustomer ↔ Address@OneToOneIn one of the two tables (we chose customers.address_id)
One-to-many / Many-to-oneCustomer → Orders@OneToMany on the "one" side, @ManyToOne on the "many" sideAlways in the "many" table (orders.customer_id)
Many-to-manyOrder ↔ Product@ManyToMany + @JoinTableIn a separate join table (order_products)

3.3 Unidirectional vs bidirectional

  • Unidirectional: only one class has a field pointing to the other. customer.getAddress() works, but Address has no getCustomer().
  • Bidirectional: both classes point to each other. customer.getOrders() and order.getCustomer().

In the database there is no "direction" — a foreign key can be followed both ways with a JOIN. Direction is only about which Java fields you want. Rule: make it bidirectional only if you really need to navigate both ways.

3.4 The owning side and mappedBy — the simple explanation

In a bidirectional relationship there are two Java fields but only one foreign key column. Hibernate must know which field to look at when it writes that column. That field is the owning side. The other field is the inverse side, marked with mappedBy.

💡 Three rules to remember 1. The owning side is the entity whose table contains the foreign key.
2. In one-to-many, the many side (@ManyToOne) is always the owner.
3. mappedBy = "customer" means: "I'm just a mirror. The real information is in the field called customer on the other class." Hibernate ignores changes made only on the mappedBy side.
// OWNING side - its table has the FK column
@Entity class PurchaseOrder {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")   // the FK column
    private Customer customer;
}

// INVERSE side - just a mirror
@Entity class Customer {
    @OneToMany(mappedBy = "customer")   // "see PurchaseOrder.customer"
    private Set<PurchaseOrder> orders = new LinkedHashSet<>();
}

So this code saves nothing to orders.customer_id:

customer.getOrders().add(order);   // only the mirror changed - Hibernate ignores it!

The fix: helper methods that always update both sides:

public void addOrder(PurchaseOrder order) {
    orders.add(order);          // mirror (keeps the Java objects consistent)
    order.setCustomer(this);    // owner  (this is what gets written to the database)
}

3.5 @JoinColumn and @JoinTable

@JoinColumn(name = "customer_id", nullable = false)   // name + rules of the FK column

@JoinTable(name = "order_products",
           joinColumns = @JoinColumn(name = "order_id"),           // FK to the owner (this entity)
           inverseJoinColumns = @JoinColumn(name = "product_id"))  // FK to the other entity

Both are optional — without them Hibernate invents names like customer_id and orders_products. Being explicit makes the schema predictable (important later with Flyway, topic 43).

3.6 Cascade types

Cascade = "when I do something to the parent, do the same to the children". Without cascade, you must save/delete each entity yourself.

CascadeTypeWhen the parent is......the children are also
PERSISTpersisted (saved as new)persisted
MERGEmerged (detached → managed)merged
REMOVEremovedremoved
REFRESHreloaded from DBreloaded
DETACHdetacheddetached
ALLany of the abovesame

Where to use it: from a parent to children that belong only to that parent and live and die with it — Customer → Address, Customer → Orders, Order → OrderLines. Thanks to cascade, our seeder saves the whole graph with one saveAll call.

🛑 Never cascade REMOVE on @ManyToMany or towards shared data If Order.products had cascade = ALL, deleting an order would delete the Laptop product — from every other order and the whole catalogue! Products are shared, so no cascade there. Also don't cascade from a child to its parent (@ManyToOne(cascade = REMOVE)).

3.7 orphanRemoval

An orphan is a child that was removed from its parent's collection. With orphanRemoval = true Hibernate deletes it from the database:

@OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
private Set<PurchaseOrder> orders;

customer.removeOrder(order);   // -> DELETE FROM orders WHERE id = ?
cascade = REMOVEorphanRemoval = true
Parent deletedchildren deletedchildren deleted
Child removed from the collectionnothing happens (child stays, maybe with a null FK)child deleted

3.8 Fetch types: LAZY vs EAGER

When Hibernate loads a customer, should it also load the address and all orders immediately?

  • EAGER: yes, always load it right away (extra JOIN or extra SELECT).
  • LAZY: no, put a placeholder (a proxy or an uninitialised collection). The real SELECT runs the first time you touch it (e.g. getOrders().size()).
AnnotationDefault fetchRecommendation
@OneToManyLAZYkeep LAZY
@ManyToManyLAZYkeep LAZY
@ManyToOneEAGER ⚠️change to fetch = FetchType.LAZY
@OneToOneEAGER ⚠️change to fetch = FetchType.LAZY (on the owning side)
💡 The golden rule Make everything LAZY, then for each use case load exactly what you need with JOIN FETCH or @EntityGraph. EAGER can't be switched off per query and quietly loads half the database.

3.9 LazyInitializationException

A lazy relationship can only be loaded while the persistence context (Hibernate session) is open — normally, during a transaction. If you touch it after the transaction ended (the entity is detached, topic 38), Hibernate can't run the SELECT anymore:

org.hibernate.LazyInitializationException: failed to lazily initialize a collection of role:
com.course.jparelationships.entity.Customer.orders: could not initialize proxy - no Session

Typical situations: you return an entity from a service, and the controller (or Jackson while writing JSON) touches a lazy field.

Fixes, from best to worst:

  1. Load what you need with JOIN FETCH / @EntityGraph in the service, and convert to a DTO inside the transaction. ✅
  2. Touch the lazy field inside a @Transactional service method (works, but may cause N+1).
  3. ❌ FetchType.EAGER everywhere — hides the problem and makes everything slow.
  4. ❌ spring.jpa.open-in-view=true (Spring Boot's default!) — keeps the session open during the whole web request, so the error disappears, but queries now run in the view/JSON layer, unnoticed. That's why we set it to false.

3.10 The N+1 problem

You want a list of customers with their order count. You write the obvious code:

List<Customer> customers = customerRepository.findAll();   // 1 query
for (Customer c : customers) {
    c.getOrders().size();                                  // +1 query PER customer
}

1 query for the list + N queries for the orders = N+1. With 3 customers that's 4 queries, with 1,000 customers that's 1,001 queries — each a network round trip. In our project the summary also shows the city, so the lazy address adds another N: 1 + 3 + 3 = 7 statements. The /demo/n-plus-one endpoint counts them for you:

{"approach":"findAll() + lazy loading (N+1 problem)","customers":3,"sqlStatements":7, ...}
SELECT customers→ SELECT address #1→ SELECT orders #1→ SELECT address #2→ ...

Fix 1: JOIN FETCH in JPQL

@Query("SELECT DISTINCT c FROM Customer c LEFT JOIN FETCH c.address LEFT JOIN FETCH c.orders ORDER BY c.id")
List<Customer> findAllWithOrders();

FETCH means "load the related entities in the same SELECT and fill the fields". LEFT keeps customers without orders (Chen). Result: 1 statement.

Fix 2: @EntityGraph

@EntityGraph(attributePaths = {"address", "orders"})
@Query("SELECT c FROM Customer c ORDER BY c.id")
List<Customer> findAllWithAddressAndOrders();

@EntityGraph(attributePaths = {"address", "orders", "orders.products"})   // nested paths work too
Optional<Customer> findWithDetailsById(Long id);

Same effect, no JPQL join syntax, and it works on derived queries. Result: 1 statement.

ℹ️ Other tools against N+1 @BatchSize(size = 50) or spring.jpa.properties.hibernate.default_batch_fetch_size=50 loads lazy collections for many parents at once with WHERE customer_id IN (...) — turning N+1 into 1 + N/50. DTO projections (topic 39) also avoid it because they select only flat columns.
⚠️ Fetching collections: List vs Set When you JOIN FETCH a collection and a nested collection (orders and orders.products), the SQL result has one row per product. If orders is a List, the same order appears several times in the list! And fetching two Lists at once throws MultipleBagFetchException. That's why Customer.orders is a Set (with @OrderBy("id") for a stable order). We hit this exact bug while building this lesson's project — a test caught it.
⚠️ Don't JOIN FETCH collections together with paging JOIN FETCH on a collection + Pageable makes Hibernate load all rows and page in memory (warning HHH90003004). For paged lists, page the parents first, then fetch children with a second query or @BatchSize. (Paging is the next topic.)

3.11 JSON infinite recursion

If a controller returns a Customer entity, Jackson writes its fields: orders → each order → its customer → its orders → ... forever, until StackOverflowError (or Jackson's "Infinite recursion" / "Document nesting depth exceeds" error). Plus every lazy field touched by Jackson either triggers queries or a LazyInitializationException.

FixHowVerdict
DTOsReturn records that contain only what the client needs and never point back to the parent.✅ Best. Used by all normal endpoints in this project.
@JsonManagedReference / @JsonBackReferencePut Managed on the parent's collection (serialized) and Back on the child's parent field (skipped).OK for quick prototypes. Couples the entity to JSON.
@JsonIgnoreSkip a field entirely.Simple, but the field is gone for every endpoint.
@JsonIdentityInfoWrites an object fully once, then only its id.Odd JSON for clients.

The /api/customers/1/raw endpoint returns the entity using the annotation approach so you can compare; notice that the orders in the JSON have no customer field and products have no orders field.

3.12 Equals/hashCode for entities in Sets (good to know)

Our entities don't override equals/hashCode, so Java uses object identity. Inside one persistence context Hibernate guarantees one object per row, so Sets work fine. If you override them, don't use all fields or the generated id naively (the id is null before saving, so the hash changes after save). Use a natural business key (e.g. orderNumber) or a constant hashCode. This is an advanced topic; identity equality is fine for this course.

4.1 Customer — two relationships

entity/Customer.java@Entity
@Table(name = "customers")
public class Customer {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    // name, email ...

    @OneToOne(cascade = CascadeType.ALL, orphanRemoval = true, fetch = FetchType.LAZY)
    @JoinColumn(name = "address_id", unique = true)          // FK in customers table -> OWNING side
    private Address address;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    @OrderBy("id")
    @JsonManagedReference
    private Set<PurchaseOrder> orders = new LinkedHashSet<>(); // INVERSE side

    public void addOrder(PurchaseOrder order) {
        orders.add(order);
        order.setCustomer(this);
    }
    public void removeOrder(PurchaseOrder order) {
        orders.remove(order);
        order.setCustomer(null);    // orphanRemoval -> DELETE
    }
}

unique = true on address_id is what makes it truly one-to-one in the database: two customers can't share an address row. Collections are initialised (new LinkedHashSet<>()) so addOrder never hits a NullPointerException on a new customer.

4.2 PurchaseOrder — owner of two relationships

entity/PurchaseOrder.java@Entity
@Table(name = "orders")                         // "order" is a reserved SQL word!
public class PurchaseOrder {

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    @JsonBackReference
    private Customer customer;

    @ManyToMany                                 // no cascade: products are shared!
    @JoinTable(name = "order_products",
               joinColumns = @JoinColumn(name = "order_id"),
               inverseJoinColumns = @JoinColumn(name = "product_id"))
    private Set<Product> products = new LinkedHashSet<>();

    public void addProduct(Product product) {
        products.add(product);
        product.getOrders().add(this);
    }
    void setCustomer(Customer customer) { ... }  // package-private: use Customer.addOrder()
}

4.5 The service — working inside transactions

service/CustomerService.java@Transactional
public OrderResponse placeOrder(Long customerId, CreateOrderRequest request) {
    Customer customer = customerRepository.findById(customerId).orElseThrow(...);
    List<Product> products = productRepository.findAllById(new HashSet<>(request.productIds()));
    // ... check all ids exist ...
    PurchaseOrder order = new PurchaseOrder("ORD-" + UUID.randomUUID().toString().substring(0, 8).toUpperCase());
    products.forEach(order::addProduct);
    customer.addOrder(order);       // cascade from the MANAGED customer inserts the order at commit
    customerRepository.flush();     // run the INSERTs now so the order has its id
    return OrderResponse.from(order);
}

@Transactional
public void removeOrder(Long customerId, Long orderId) {
    Customer customer = ...;
    PurchaseOrder order = customer.getOrders().stream()
            .filter(o -> o.getId().equals(orderId)).findFirst().orElseThrow(...);
    customer.removeOrder(order);    // orphanRemoval -> DELETE FROM orders + join rows
}

6. Common mistakes

⚠️ Updating only the mappedBy side customer.getOrders().add(order) — the order is saved with customer_id = NULL (or not at all).
Fix: set the owning side (order.setCustomer(customer)) — best via a helper method like addOrder.
⚠️ mappedBy with the wrong name @OneToMany(mappedBy = "customers") → startup error "mappedBy reference an unknown target entity property".
Fix: mappedBy is the field name on the other class (customer), not the table or class name.
⚠️ Both sides as owners Forgetting mappedBy on one side of a bidirectional relationship creates two independent relationships — e.g. an extra join table customers_orders you never wanted.
Fix: exactly one side has @JoinColumn/@JoinTable, the other has mappedBy.
⚠️ LazyInitializationException in the controller Returning entities from the service and touching lazy fields later.
Fix: fetch what you need in the service (JOIN FETCH/@EntityGraph) and return DTOs.
🛑 FetchType.EAGER "to fix" lazy errors It makes every load of the entity pull the relationship — often with N+1 extra selects — and can't be undone per query.
Fix: keep LAZY, fetch per use case.
🛑 cascade = CascadeType.ALL on @ManyToMany Deleting one order deletes shared products.
Fix: no cascade (or only PERSIST/MERGE if you really must) towards shared entities.
⚠️ Returning entities as JSON Infinite recursion, StackOverflowError, or "No serializer found for class ...ByteBuddyInterceptor" (Jackson meets a Hibernate proxy).
Fix: DTOs.
⚠️ MultipleBagFetchException / duplicated children JOIN FETCH of two List collections, or a List plus a nested collection.
Fix: use Set, or fetch the second collection in a separate query.
⚠️ Entity named Order / table order SQL syntax error at startup.
Fix: @Table(name = "orders") (and maybe rename the class to avoid confusion).

7. Best practices

  • All associations LAZY; change the EAGER defaults of @ManyToOne/@OneToOne.
  • Fetch per use case with JOIN FETCH or @EntityGraph; consider default_batch_fetch_size as a safety net.
  • Prefer unidirectional unless you really navigate both ways. A @ManyToOne alone is often enough — query the "many" side with a repository method (findByCustomerId).
  • Bidirectional? Add helper methods that keep both sides in sync, and make the owning setter non-public.
  • Initialise collections (= new LinkedHashSet<>()); prefer Set for collections you fetch-join.
  • Cascade only parent → owned children; never towards shared/reference data; use orphanRemoval for true composition.
  • Many-to-many with extra data → an explicit join entity (OrderItem).
  • spring.jpa.open-in-view=false and return DTOs from services.
  • Watch the SQL count in development (show-sql, Hibernate statistics) and write tests that assert the number of queries for important screens.
  • Name join columns and tables explicitly — it keeps the schema predictable for migrations.

8. Key takeaways

  • @OneToOne, @OneToMany/@ManyToOne, @ManyToMany map foreign keys and join tables to Java references and collections.
  • The owning side has the FK (@JoinColumn/@JoinTable); the inverse side uses mappedBy and is ignored for writes. In one-to-many, the many side owns.
  • Keep both sides in sync with helper methods.
  • Cascade = propagate operations to children; orphanRemoval = delete children removed from the collection. Never cascade to shared entities.
  • Everything LAZY; @ManyToOne/@OneToOne are EAGER by default — change that.
  • LazyInitializationException = touching a lazy field after the session closed → fetch in the service, return DTOs.
  • N+1 = 1 query for parents + 1 per parent for children → fix with JOIN FETCH, @EntityGraph or batch fetching.
  • JSON recursion → DTOs (best), or @JsonManagedReference/@JsonBackReference/@JsonIgnore.

10. Interview questions

Q1. What is the owning side of a relationship and why does it matter?

The owning side is the entity whose table holds the foreign key (declared with @JoinColumn or @JoinTable). Hibernate uses only the owning side to decide what to write to the database; the inverse side (mappedBy) is ignored for persistence. In one-to-many/many-to-one, the many side is always the owner. You must set the owning side for changes to be saved.

Q2. What does mappedBy do?

It marks the inverse side of a bidirectional relationship and names the field on the owning entity that maps it. It tells JPA not to create another FK column or join table for this side.

Q3. What are the default fetch types?

@OneToMany and @ManyToMany: LAZY. @ManyToOne and @OneToOne: EAGER. Best practice is to make all of them LAZY and fetch explicitly per use case.

Q4. What is the N+1 select problem and how do you fix it?

Loading N parents with one query and then lazily loading a relationship for each parent, producing N additional queries. Fixes: JOIN FETCH in JPQL, @EntityGraph, batch fetching (@BatchSize / hibernate.default_batch_fetch_size), or DTO projections that select only needed columns. Detect it with SQL logging or Hibernate statistics.

Q5. What causes LazyInitializationException and how do you solve it properly?

Accessing an uninitialised lazy proxy/collection after its persistence context (session) has closed, i.e. on a detached entity. Proper solutions: fetch required associations in the transactional service (fetch join / entity graph) and map to DTOs before returning. Avoid "fixes" like EAGER fetching or relying on Open Session In View.

Q6. Difference between CascadeType.REMOVE and orphanRemoval = true?

Both delete children when the parent is deleted. orphanRemoval additionally deletes a child when it is removed from the parent's collection (or the reference is set to null), treating it as an orphan. Use orphanRemoval for compositions where children can't exist without the parent.

Q7. Why shouldn't you cascade on @ManyToMany?

The related entities are shared. Cascading REMOVE would delete entities still referenced by other parents (or fail with constraint violations). Many-to-many targets usually have their own lifecycle and are managed separately.

Q8. How do you handle a many-to-many that needs extra columns?

Replace it with an explicit join entity (e.g. OrderItem or Enrollment) that has two @ManyToOne associations plus the extra columns, turning it into two one-to-many relationships.

Q9. How do you prevent infinite recursion when serializing bidirectional entities to JSON?

Best: return DTOs. Alternatives: @JsonManagedReference on the forward side and @JsonBackReference on the back side, @JsonIgnore on one side, or @JsonIdentityInfo. Annotations couple persistence entities to the API format and can still trigger lazy loading.

Q10. What is MultipleBagFetchException?

Hibernate throws it when you try to fetch-join two or more List (bag) collections in one query, because the cartesian product can't be mapped back unambiguously. Fixes: use Set, fetch one collection per query, or use batch fetching. Fetching one List with a nested collection also yields duplicates.
