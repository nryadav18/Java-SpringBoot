62. Centralized Configuration with Config Server

Keep the settings of all your services in one place, per service and per environment – and change them at runtime without rebuilding or restarting.

1. Why this matters

In Topic 29 you learned to put settings in application.yml and use profiles. That works great for one app. Now imagine 20 microservices, each running in dev, test and prod:

  • 20 services × 3 environments = 60 config files, inside 20 different jars.
  • The company changes its support e-mail → you edit 20 projects, rebuild 20 jars, redeploy 20 services.
  • Marketing wants a 10% discount now → a full release just to change one number.
  • Nobody knows which value is active where. Secrets (DB passwords, API keys) are copied around in plain text.

This is the "config scattered everywhere" problem. Factor 3 of the 12-factor app (Topic 59) says: store config outside the code. Spring Cloud Config takes that further: one Config Server serves the configuration of all services from one place (usually a Git repository), and services fetch it at startup – and can reload it later without a restart.

At work you'll see the same idea with other tools too: Kubernetes ConfigMaps/Secrets (Topic 69), HashiCorp Consul and Vault, AWS Parameter Store, Azure App Configuration. Learn the idea once, recognise it everywhere.

2. Real-life analogy

🍔 The restaurant chain's central menu office

A burger chain has 200 branches. If every branch printed its own menu, prices would be different everywhere and a price change would take weeks.

Instead, there is a head office (= Config Server) with one master folder of menus (= config repository):

  • a common page used by every branch: company name, hygiene rules (= application.yml),
  • a page per type of branch: drive-through, mall kiosk (= product-service.yml),
  • special pages per situation: festival season, test kitchen (= profiles: product-service-dev.yml).

Each morning a branch opens and downloads its menu from head office (= the service fetches config at startup). If head office changes a price at noon, it sends a message "please re-print your menu" (= POST /actuator/refresh) – the branch doesn't close and re-open. The master folder is kept in a filing cabinet with a history of every change (= Git): who changed what, when, and how to go back. The safe-box code is written in secret ink that only head office can read (= encrypted {cipher} values).

3. Concepts step by step

3.1 The architecture

  1. The config repository holds plain YAML/properties files (a folder in dev, a Git repo in real life).
  2. The Config Server reads them and offers an HTTP API: GET /{application}/{profile}[/{label}].
  3. Each client service, at startup, asks: "I am product-service, profile dev – give me my config." The answer is merged into its Environment like any other property source (Topic 26).

3.2 The Config Server

  • Dependency: org.springframework.cloud:spring-cloud-config-server (with the Spring Cloud 2025.0.0 BOM).
  • Annotation: @EnableConfigServer on the main class.
  • Port: 8888 by convention (clients assume it by default).

Its REST API (try them in the browser!):

URLReturns
/product-service/defaultJSON: list of property sources for the default profile
/product-service/devJSON for the dev profile (dev file first = highest priority)
/product-service/dev/mainsame, from Git branch/tag main (the "label")
/product-service-dev.yml or .propertiesThe merged result as a file
POST /encrypt, POST /decryptEncrypt / decrypt a value (when a key is configured)

3.3 Backends: native (folder) and Git

📁 Native (file system)

Activated with the native profile. Reads files from spring.cloud.config.server.native.search-locations (e.g. file:../config-repo/).

✅ zero setup – perfect for learning and local dev
❌ no history, no review, the folder must exist on the server machine

🌿 Git (the default and the industry standard)

Set spring.cloud.config.server.git.uri to a repo. The server clones it and serves the files from a branch/tag (label).

✅ full history, pull-request reviews, easy rollback, audit trail ("who changed the DB URL?")
❌ needs a Git server and credentials

Other backends exist too: Vault (secrets), JDBC, Redis, AWS S3… and you can combine them (composite).

3.4 File naming and priority

The server picks files based on the client's application name (spring.application.name) and active profiles:

File in config-repoUsed byPriority
product-service-dev.ymlproduct-service with profile dev🥇 highest
application-dev.ymlALL services with profile dev🥈
product-service.ymlproduct-service, every profile🥉
application.ymlALL services, every profilelowest (shared defaults)

Rule of thumb: more specific wins – profile-specific beats general, service-specific beats shared. And everything from the Config Server beats the client's own local application.yml. (Command-line arguments and environment variables still beat everything – Topic 29.)

ℹ️ Example from our reposhop.welcome-message is defined in three files. With profile dev, product-service gets the one from product-service-dev.yml; with no profile, the one from product-service.yml; the shared one from application.yml would only be used by a service without its own value.

3.5 The client side: spring.config.import

A service becomes a config client with the dependency spring-cloud-starter-config and one line:

spring:
  application:
    name: product-service                               # which files to fetch
  config:
    import: optional:configserver:http://localhost:8888 # where the server is
  • configserver: – "import config from a Config Server at this URL". This happens very early, before beans are created, so even server.port or spring.datasource.url can come from the server.
  • optional: – if the server is unreachable, start anyway with local values. Without optional: the app fails to start (often preferred in production – better to crash than to run with wrong settings). You can add spring.cloud.config.fail-fast=true and retries for that.
⚠️ Old way: bootstrap.ymlBefore Spring Cloud 2020, clients used a separate bootstrap.yml with spring.cloud.config.uri. That is legacy (it needs the extra spring-cloud-starter-bootstrap). Use spring.config.import in new projects.

3.6 Refreshing config at runtime

Config is read at startup. To pick up changes without a restart:

  1. Change the file in config-repo (or push to Git).
  2. Call POST /actuator/refresh on the client (needs actuator and the refresh endpoint exposed).
  3. The client re-fetches its config, compares it and returns the list of changed keys, e.g. ["shop.welcome-message","shop.discount-percent"].

Which beans see the new values?

How the value is usedAfter refresh
@ConfigurationProperties bean (JavaBean with setters)✅ re-bound automatically
@Value in a bean annotated @RefreshScope✅ the bean is re-created on next use with new values
@Value in a normal singleton❌ keeps the old value until restart
Environment.getProperty(...) each time✅ always current
Things built once at startup (DataSource pool, server port)❌ need a restart (or careful refresh-scope design)

How does @RefreshScope work? Spring injects a proxy instead of the real object. On refresh, the real object behind the proxy is thrown away. The next method call creates a brand-new object – which gets the new @Values. (Remember proxies from Topic 27.)

edit config-repo→ POST /actuator/refresh→ client re-fetches from :8888→ @ConfigurationProperties re-bound
@RefreshScope beans recreated
ℹ️ 50 instances? Spring Cloud BusCalling /actuator/refresh on every instance by hand doesn't scale. Spring Cloud Bus connects all instances through RabbitMQ/Kafka (Topics 57, 58): one call to /actuator/busrefresh broadcasts the refresh to all. A Git webhook can even trigger it automatically on every push.

3.7 Secrets: encryption with {cipher}

Config repos are read by many people, so plain-text passwords don't belong there. The Config Server can store values encrypted:

  1. Give the server a key: encrypt.key (symmetric) – in real life via the ENCRYPT_KEY environment variable, never in Git. (Asymmetric RSA keystores are also supported.)
  2. Encrypt a value: POST http://localhost:8888/encrypt with the secret as body → a long hex string.
  3. Put it in the repo with a prefix and quotes: payment-api-key: '{cipher}1501635eab...'
  4. When a client asks, the server decrypts and sends the plain value (over HTTPS in production!). The repo only ever contains cipher text.
⚠️ Encryption is the minimumAnyone who can call the Config Server gets decrypted secrets – so secure the server (Spring Security, private network, HTTPS). Many companies go further and keep secrets in a dedicated vault (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, Kubernetes Secrets) and keep only non-secret config in Git.

4.4 ShopProperties – re-bound on refresh

product-service/src/main/java/com/course/configdemo/product/ShopProperties.java@ConfigurationProperties(prefix = "shop")
public class ShopProperties {

    private String companyName;
    private String supportEmail;
    private String welcomeMessage;
    private int discountPercent;
    private String paymentApiKey;
    private final Feature feature = new Feature();   // shop.feature.*

    public static class Feature {
        private boolean newArrivals;                 // shop.feature.new-arrivals
        public boolean isNewArrivals() { return newArrivals; }
        public void setNewArrivals(boolean newArrivals) { this.newArrivals = newArrivals; }
    }

    public int getDiscountPercent() { return discountPercent; }
    public void setDiscountPercent(int discountPercent) { this.discountPercent = discountPercent; }
    // ... other getters and setters
}

It is registered with @EnableConfigurationProperties(ShopProperties.class) on the main class. In Topic 29 we used a record for type-safe properties. Here we deliberately use a class with setters: on refresh Spring Cloud re-binds @ConfigurationProperties beans by calling the setters again. A record is immutable, so it could not be updated in place.

4.5 MessageController – @RefreshScope + @Value

product-service/src/main/java/com/course/configdemo/product/MessageController.java@RestController
@RefreshScope
public class MessageController {

    private final String welcomeMessage;
    private final String companyName;
    private final Environment environment;
    private final LocalTime beanCreatedAt = LocalTime.now().withNano(0);

    public MessageController(@Value("${shop.welcome-message}") String welcomeMessage,
                             @Value("${shop.company-name}") String companyName,
                             Environment environment) {
        this.welcomeMessage = welcomeMessage;
        this.companyName = companyName;
        this.environment = environment;
    }

    @GetMapping("/api/message")
    public Map<String, Object> message() {
        Map<String, Object> result = new LinkedHashMap<>();
        result.put("welcomeMessage", welcomeMessage);
        result.put("companyName", companyName);
        result.put("activeProfiles", Arrays.toString(environment.getActiveProfiles()));
        result.put("beanCreatedAt", beanCreatedAt.toString());
        return result;
    }
}

beanCreatedAt is a little trick: after a refresh the time changes, proving that a new bean object was created. Remove @RefreshScope and the message will never change until restart – try it!

4.6 ProductController – behaviour driven by config

product-service/src/main/java/com/course/configdemo/product/ProductController.java@GetMapping
public List<ProductView> findAll() {
    int discount = shop.getDiscountPercent();          // read on EVERY request -> always current
    log.debug("Building product list with discount {}%", discount);
    return List.of(view(1L, "Laptop", 55000.0, discount), ...);
}

@GetMapping("/new-arrivals")
public List<ProductView> newArrivals() {
    if (!shop.getFeature().isNewArrivals()) {          // feature flag
        throw new ResponseStatusException(HttpStatus.NOT_FOUND, "New arrivals are not available yet");
    }
    return List.of(view(10L, "Smart Watch", 12999.0, shop.getDiscountPercent()));
}

@GetMapping("/secret-check")
public Map<String, Object> secretCheck() {
    String key = shop.getPaymentApiKey();
    boolean decrypted = key != null && !key.startsWith("{cipher}") && !key.isBlank();
    String masked = decrypted ? key.substring(0, Math.min(4, key.length())) + "****" : String.valueOf(key);
    return Map.of("paymentApiKeyReceived", decrypted, "maskedValue", masked);   // never return real secrets!
}

A feature flag is a config switch that turns a feature on or off without a release – a very common enterprise technique (dark launches, A/B tests, "kill switches").

6. Common mistakes

⚠️ Mistake: the client always shows the local fallback valuesThe server isn't running, runs on another port, or the client started first.
Fix: start config-server first; check http://localhost:8888/product-service/default; look for "Fetching config from server" in the client log.
⚠️ Mistake: the server returns empty propertySourcesThe server can't find the folder (started from the wrong directory) or the file name doesn't match spring.application.name (product_service.yml, productservice.yml…).
Fix: start from the config-server folder or set CONFIG_REPO_PATH; name files exactly <application-name>[-<profile>].yml.
⚠️ Mistake: "No spring.config.import property has been defined"You added spring-cloud-starter-config but no spring.config.import line – the app refuses to start.
Fix: add spring.config.import=optional:configserver:http://localhost:8888 (or set spring.cloud.config.enabled=false to switch the client off, e.g. in tests).
⚠️ Mistake: refresh returns [] or the value doesn't change(a) You forgot to save the file, (b) you edited the wrong profile file, (c) the value is used via @Value in a bean without @RefreshScope, (d) the properties class is a record.
Fix: use @ConfigurationProperties JavaBeans or @RefreshScope; check with /actuator/env.
⚠️ Mistake: 404 on POST /actuator/refreshThe endpoint is not exposed or actuator is missing.
Fix: add spring-boot-starter-actuator and management.endpoints.web.exposure.include: refresh. It must be a POST.
🛑 Mistake: committing secrets or the encrypt key to GitPlain-text passwords in config-repo, or encrypt.key in the server's committed application.yml in production.
Fix: {cipher} values or a vault for secrets; pass the key via the ENCRYPT_KEY environment variable; secure the Config Server endpoints.
⚠️ Mistake: an unexpected ${...} inside a config valueValues containing ${...} are resolved by Spring on the client side. That's a feature (url: jdbc:mysql://${DB_HOST}/shop), but a surprise if you didn't mean it.
Fix: escape or avoid ${ in literal text.

7. Best practices

  • Use a Git backend in real projects: changes go through pull requests, history and rollback come for free.
  • Use labels (branches/tags) to tie config versions to releases, e.g. spring.cloud.config.label=v1.4.0.
  • Keep only bootstrap facts locally (spring.application.name, spring.config.import); everything else centrally.
  • Put company-wide values in application.yml, service values in <service>.yml, environment differences in -<profile>.yml.
  • In production, prefer fail-fast (no optional:) with retries, so a service never runs with incomplete config.
  • Run 2+ Config Server instances (or register it in Eureka and use discovery) – startup of every service depends on it.
  • Secure the Config Server (HTTPS, Spring Security basic auth / OAuth2, private network).
  • Never store secrets in plain text; use {cipher} or better a vault; never expose /actuator/env values in production.
  • Make refreshable things refreshable on purpose (@ConfigurationProperties); restart for infrastructure changes (DB pools, ports).
  • Use Spring Cloud Bus (or a rolling restart) to refresh many instances consistently.

8. Key takeaways

  • A Config Server (@EnableConfigServer, port 8888) serves configuration for all services from one repository.
  • Backends: native folder (learning) and Git (industry standard, with history and reviews).
  • Files are chosen by application name and profile: application.yml < product-service.yml < application-dev.yml < product-service-dev.yml.
  • Clients use spring-cloud-starter-config + spring.config.import=optional:configserver:http://localhost:8888; optional: allows starting without the server.
  • Server values override the client's local application.yml; local values act as fallback.
  • POST /actuator/refresh reloads config: @ConfigurationProperties beans are re-bound, @RefreshScope beans are re-created.
  • Secrets: {cipher} values decrypted by the server with encrypt.key; better: a vault. Never commit keys.

        initial-interval: 1000
        multiplier: 1.5

Start the client first: it retries (watch the log), and if you start the server within those attempts, it continues normally; otherwise it stops with an error.

10. Interview questions

Q1. What problem does Spring Cloud Config solve?

Externalized, centralized configuration for distributed systems: one place (usually Git) holds the config for all services and environments, with versioning, auditing and the ability to change config without rebuilding artifacts and – with refresh – without restarting services.

Q2. How does a client get its configuration?

Via spring-cloud-starter-config and spring.config.import=configserver:<url>. Early in startup it calls GET /{spring.application.name}/{active profiles}/{label} on the server and adds the returned property sources to its Environment with higher precedence than its local application files.

Q3. What is the order of precedence between the files?

Profile-specific beats non-profile, application-specific beats shared: {app}-{profile}.yml > application-{profile}.yml > {app}.yml > application.yml. Remote config beats the client's packaged config; command-line args and env vars can still override (depending on settings).

Q4. How do you refresh configuration without restarting?

Expose the actuator refresh endpoint and POST /actuator/refresh. The client re-fetches config, publishes an EnvironmentChangeEvent, re-binds @ConfigurationProperties beans and clears @RefreshScope beans so they are recreated lazily. For many instances, Spring Cloud Bus broadcasts the refresh via /actuator/busrefresh.

Q5. What does @RefreshScope do internally?

It's a custom scope: the bean is injected as a proxy, and the target is cached in the scope. On refresh, the cache is cleared; the next call through the proxy creates a new instance with freshly injected values. Costs: proxies, re-creation, and beans that hold resources need care.

Q6. Native vs Git backend?

Native reads from the local file system/classpath – simple, good for dev and tests, but no versioning and tied to one machine. Git gives history, code review, branches/tags as labels, rollback and audit; the server clones the repo and can refresh on each request. Vault, JDBC, S3 and composite backends also exist.

Q7. How are secrets handled?

Values can be stored encrypted as {cipher}...; the server decrypts them with a symmetric key (encrypt.key) or an RSA keystore before serving (or clients can decrypt themselves). Endpoints /encrypt and /decrypt help. The key must come from a secure source (env var), the server must be secured and use HTTPS. Many organisations prefer Vault/cloud secret managers for secrets.

Q8. What happens if the Config Server is down when a service starts?

With optional:configserver: the service starts with local config only (maybe wrong for production). Without optional: (or with fail-fast=true) startup fails, optionally after retries (spring-retry). Mitigations: run multiple Config Server instances behind discovery or a load balancer; clients keep the config they already loaded if the server dies later.

Q9. bootstrap.yml vs spring.config.import?

bootstrap.yml was the old mechanism (a parent "bootstrap context" loaded first). Since Spring Boot 2.4 / Spring Cloud 2020, the Config Data API with spring.config.import is the standard; bootstrap needs the legacy spring-cloud-starter-bootstrap dependency.

Q10. Config Server vs Kubernetes ConfigMaps?

ConfigMaps/Secrets are the Kubernetes-native way: config is mounted as files or env vars; changes may require pod restarts (or Spring Cloud Kubernetes to reload). Config Server is platform-independent, Git-backed, supports profiles, labels, encryption and runtime refresh. On Kubernetes, teams often use ConfigMaps + an external secrets operator, or combine both.
