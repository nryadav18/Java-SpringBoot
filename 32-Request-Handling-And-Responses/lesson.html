1. Why this matters

In topic 31 you built a simple API. Real clients expect more precision:

  • The mobile team wants to filter products: ?category=electronics&maxPrice=1000.
  • After creating a product they need to know where it lives (the Location header) and get 201, not 200.
  • They want to change only the price (PATCH) without sending the whole product.
  • The web team's React app on localhost:5173 gets blocked by the browser until you configure CORS.
  • The JSON field must be called stock, the internal supplier code must never appear, dates must look like 09-10-2026 14:30:00.

These are everyday tasks in a backend job. A well-behaved API is predictable: the right status code, the right headers, consistent JSON. Front-end developers love working with such APIs — and interviewers love asking about them.

2. Real-life analogy

📦 Ordering at a courier counter
  • The address on the parcel (/products/42) identifies exactly which thing → @PathVariable.
  • Tick-boxes on the form ("express? fragile? max price?") are optional choices → @RequestParam.
  • The parcel itself — the actual content you hand over → @RequestBody.
  • The sticker "sent by: mobile-app" — information about the delivery → @RequestHeader.
  • The receipt you get back: a status ("Accepted"), a tracking number telling you where your parcel now lives (Location header), and a copy of the details (body) → ResponseEntity.
  • Pressing the lift button five times still calls the lift once → idempotent. Paying at the counter five times charges you five times → not idempotent (POST).

3.2 @PathVariable

@GetMapping("/{id}")
public ResponseEntity<Product> getOne(@PathVariable Long id) { ... }

// several variables, and a different Java name:
@GetMapping("/categories/{categoryName}/products/{productId}")
public Product get(@PathVariable("categoryName") String category,
                   @PathVariable Long productId) { ... }
  • The name in {...} must match the parameter name, or be given explicitly: @PathVariable("categoryName").
  • Spring converts the text "3" to Long. If it can't (/products/abc) → 400 Bad Request automatically.
  • Path variables are required — without them the URL simply doesn't match.
ℹ️ Parameter names @PathVariable Long id works without ("id") because the Spring Boot parent compiles with the -parameters flag, which keeps parameter names in the bytecode. If you ever see "Name for argument of type [java.lang.Long] not specified", add the name explicitly.

3.3 @RequestParam — required, defaultValue

@GetMapping
public ResponseEntity<List<Product>> getAll(
        @RequestParam(required = false) String category,               // may be missing -> null
        @RequestParam(required = false) BigDecimal maxPrice,           // "1000" -> BigDecimal
        @RequestParam(name = "sort", defaultValue = "id") String sortBy) { ... }
RequestcategorymaxPricesortBy

/api/products?maxPrice=cheap→ 400 Bad Request (can't convert "cheap")
  • By default @RequestParam is required. Missing → 400 "Required parameter 'x' is not present".
  • defaultValue automatically makes it optional.
  • Optional<String> also works as an optional parameter type.
  • Lists: ?tag=a&tag=b or ?tag=a,b → @RequestParam List<String> tag.

3.4 @RequestBody

@PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
public ResponseEntity<Product> create(@RequestBody ProductRequest request) { ... }

Jackson reads the JSON body and builds a ProductRequest. Important details:

  • Only one @RequestBody per method (there is only one body).
  • The client must send Content-Type: application/json, otherwise → 415.
  • Broken JSON → 400. Missing fields → null (or 0 for int). Unknown fields are ignored by default — we set spring.jackson.deserialization.fail-on-unknown-properties=true so a typo like "prise" gives 400 instead of being silently lost.
  • Use a separate request class (ProductRequest) rather than the full Product, so clients can't set the id, timestamps or internal fields. (Topic 33 calls these DTOs.)
  • Validation (@Valid, @NotBlank…) comes in topic 34.

3.5 @RequestHeader

@RequestHeader(name = "X-Client-Id", required = false) String clientId          // optional custom header
@RequestHeader(name = HttpHeaders.USER_AGENT, defaultValue = "unknown") String ua // standard header with default
@RequestHeader HttpHeaders allHeaders                                             // all headers at once
@RequestHeader Map<String, String> headerMap                                     // also possible

Header names are case-insensitive (x-client-id = X-Client-Id). Like @RequestParam, they're required unless you say otherwise. Custom headers often start with X- by tradition.

3.6 ResponseEntity — full control of the response

Returning a plain object always gives 200 (or the code from @ResponseStatus). ResponseEntity<T> lets you choose the status, headers and body per call:

A neat pattern with Optional (from topic 14):

return productService.findById(id)
        .map(ResponseEntity::ok)                       // found     -> 200 + product
        .orElse(ResponseEntity.notFound().build());    // not found -> 404

3.7 201 Created and the Location header

The HTTP standard says: after creating a resource, answer 201 Created with a Location header containing the new resource's URL, so the client can fetch it later. Building that URL by hand ("http://localhost:8080/...") breaks behind proxies or with a different port. Use ServletUriComponentsBuilder, which starts from the current request URL:

URI location = ServletUriComponentsBuilder.fromCurrentRequest()   // http://localhost:8080/api/products
        .path("/{id}")                                                // + /{id}
        .buildAndExpand(created.getId())                             // {id} -> 5
        .toUri();                                                    // http://localhost:8080/api/products/5
return ResponseEntity.created(location).body(created);
HTTP/1.1 201
Location: http://localhost:8080/api/products/5

PUT vs PATCH in practice — existing product: {"name":"Mug","category":"kitchen","price":299,"stock":100}

RequestResult
PUT {"name":"Big Mug","category":"kitchen","price":349,"stock":80}Everything replaced.

For PATCH we use a request record whose fields are all wrapper types (Integer, not int), so "not sent" (null) is different from "set to 0".

3.9 Idempotency

An operation is idempotent if doing it once or ten times leaves the server in the same state.

Request sent 3 timesResultIdempotent?
GET /api/products/1Nothing changes✅ (and safe)
PUT /api/products/1 with the same bodyProduct 1 has that data — same as after the first call✅
DELETE /api/products/11st: 204, then 404 — but the state is the same: product 1 is gone✅
POST /api/productsThree new products (ids 5, 6, 7)!❌
PATCH {"price": 349}Same result each time✅ in this case
PATCH {"stockIncrease": 10}Stock +30 instead of +10❌ — PATCH is not guaranteed idempotent

Why it matters: networks fail. A mobile app sends a request, the connection drops, and it doesn't know if the server received it. Idempotent requests can be retried safely. For POST (e.g. payments), APIs often accept an Idempotency-Key header so the server can detect and ignore duplicates (more in topic 44).

ℹ️ Dates Without @JsonFormat, Spring Boot writes LocalDateTime as ISO-8601: "2026-10-09T14:30:00". ISO is actually the best choice for APIs (every language parses it). We use a custom pattern here only to show how it works.

3.11 Content negotiation (brief)

One resource can have several representations (JSON, XML, CSV). The client says what it wants in the Accept header; the server picks a matching HttpMessageConverter. That's content negotiation.

  • produces = MediaType.APPLICATION_JSON_VALUE — "this endpoint only produces JSON". Accept: application/xml → 406 Not Acceptable.
  • consumes = MediaType.APPLICATION_JSON_VALUE — "this endpoint only accepts JSON bodies". Other Content-Type → 415 Unsupported Media Type.
  • Add the dependency jackson-dataformat-xml (commented out in our pom.xml) and remove produces — the same endpoint then returns XML for Accept: application/xml. No code changes!

3.12 CORS basics

Browsers follow the Same-Origin Policy: JavaScript from one origin (scheme + host + port) may not read responses from another origin unless that server allows it. http://localhost:5173 (React dev server) and http://localhost:8080 (our API) are different origins (different ports).

Browser JS at :5173→ OPTIONS (preflight) → API at :8080→ "Access-Control-Allow-Origin: http://localhost:5173" → Browser sends the real request

For "non-simple" requests (e.g. POST with JSON, PUT, DELETE, custom headers) the browser first sends a preflight OPTIONS request asking permission. If the server's answer doesn't allow the origin, the browser blocks the call and shows a red CORS error in the console.

Two ways to allow origins in Spring:

// 1) Local: on a controller class or a single method
@CrossOrigin(origins = "http://localhost:5173")
@GetMapping("/headers-demo") ...

// 2) Global: one place for all /api/** URLs (preferred)
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://localhost:5173", "http://localhost:3000")
                .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE")
                .exposedHeaders("Location", "X-Total-Count");
    }
}
⚠️ CORS is a browser rule, not security for your API curl, Postman and other servers ignore CORS completely. It protects users' browsers, not your data — you still need authentication (topics 47–49). With Spring Security, CORS must also be enabled in the security config (topic 47).

        @JsonProperty("stock") Integer quantityInStock) { }   // Integer: null = "not sent"

BigDecimal for money: double can't store 0.1 exactly (0.1 + 0.2 = 0.30000000000000004), which is unacceptable for prices.

4.2 ProductService — PUT vs PATCH logic

src/main/java/com/course/requesthandling/ProductService.java (part)public Optional<Product> replace(long id, ProductRequest request) {
    Product existing = products.get(id);
    if (existing == null) return Optional.empty();
    existing.setName(request.name());                     // EVERY field overwritten
    existing.setCategory(request.category());
    existing.setPrice(request.price());
    existing.setQuantityInStock(request.quantityInStock());
    existing.setUpdatedAt(LocalDateTime.now());
    return Optional.of(existing);
}

public Optional<Product> patch(long id, ProductPatchRequest patch) {
    Product existing = products.get(id);
    if (existing == null) return Optional.empty();
    if (patch.name() != null) existing.setName(patch.name());           // ONLY sent fields
    if (patch.category() != null) existing.setCategory(patch.category());
    if (patch.price() != null) existing.setPrice(patch.price());
    if (patch.quantityInStock() != null) existing.setQuantityInStock(patch.quantityInStock());
    existing.setUpdatedAt(LocalDateTime.now());
    return Optional.of(existing);
}

The service returns Optional/boolean and knows nothing about HTTP. The controller decides 200 vs 404. This separation pays off in topic 33.

4.3 ProductController — the heart of the topic

src/main/java/com/course/requesthandling/ProductController.java (key parts)@RestController
@RequestMapping(value = "/api/products", produces = MediaType.APPLICATION_JSON_VALUE)
public class ProductController {

    @GetMapping
    public ResponseEntity<List<Product>> getAll(
            @RequestParam(required = false) String category,
            @RequestParam(required = false) BigDecimal maxPrice,
            @RequestParam(name = "sort", defaultValue = "id") String sortBy) {
        List<Product> result = productService.findAll(category, maxPrice, sortBy);
        return ResponseEntity.ok()
                .header("X-Total-Count", String.valueOf(result.size()))
                .body(result);
    }

    @GetMapping("/{id}")
    public ResponseEntity<Product> getOne(@PathVariable Long id) {
        return productService.findById(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<Product> create(
            @RequestBody ProductRequest request,
            @RequestHeader(name = "X-Client-Id", required = false) String clientId) {
        Product created = productService.create(request);
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                .path("/{id}")
                .buildAndExpand(created.getId())
                .toUri();
        return ResponseEntity.created(location)
                .header("X-Created-By", clientId == null ? "anonymous" : clientId)
                .body(created);
    }

    @PutMapping(value = "/{id}", consumes = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<Product> replace(@PathVariable Long id, @RequestBody ProductRequest request) {
        return productService.replace(id, request).map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @PatchMapping(value = "/{id}", consumes = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<Product> patch(@PathVariable Long id, @RequestBody ProductPatchRequest patch) {
        return productService.patch(id, patch).map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        if (productService.delete(id)) {
            return ResponseEntity.noContent().build();
        }
        return ResponseEntity.notFound().build();
    }

    @CrossOrigin(origins = "*")
    @GetMapping("/headers-demo")
    public ResponseEntity<Map<String, Object>> headersDemo(
            @RequestHeader(name = HttpHeaders.USER_AGENT, defaultValue = "unknown") String userAgent,
            @RequestHeader(name = "Accept-Language", required = false) String language,
            @RequestHeader HttpHeaders allHeaders) { ... }
}

Points to notice:

  • ResponseEntity<Void> for DELETE — there's never a body.
  • produces on the class applies to every method; consumes only on methods that take a body.
  • X-Total-Count is a common convention for "how many items match"; useful for paging UIs.
  • Why doesn't /headers-demo clash with /{id}? A literal segment is more specific than a variable, so Spring prefers it.

6. Common mistakes

⚠️ Mistake: required @RequestParam missing → 400 @RequestParam String category is required by default. Calling /api/products fails.
Fix: required = false or a defaultValue.
⚠️ Mistake: primitive optional parameter @RequestParam(required = false) int page → error when missing, because null can't go into an int.
Fix: Integer page or defaultValue = "0".
⚠️ Mistake: path variable name mismatch @GetMapping("/{productId}") with @PathVariable Long id → error "Missing URI template variable 'id'".
Fix: same names, or @PathVariable("productId") Long id.
⚠️ Mistake: 200 with an empty body instead of 404 Returning null from a controller gives 200 with nothing. Clients think it worked.
Fix: ResponseEntity.notFound().build() (or an exception, topic 35).
⚠️ Mistake: POST returning 200 without Location Works, but breaks REST conventions. Use ResponseEntity.created(uri).
⚠️ Mistake: hard-coding the Location URL URI.create("http://localhost:8080/api/products/" + id) is wrong on any other host/port. Use ServletUriComponentsBuilder.fromCurrentRequest().
⚠️ Mistake: using PUT for partial updates Clients send only {"price":..} and lose all other data. Use PATCH for partial changes.
⚠️ Mistake: int fields in a PATCH body You can't tell "not sent" from 0. Use wrapper types.
❌ Mistake: @CrossOrigin(origins = "*") everywhere Any website can then call your API from its users' browsers. Never combine * with credentials (cookies). List real front-end origins instead, preferably in a global config driven by properties per profile.
⚠️ Mistake: "CORS error" while testing with Postman? Impossible — Postman ignores CORS. If only the browser fails, it's CORS; if Postman fails too, it's your endpoint.

7. Best practices

  • Path variables identify, query params filter. /products/5 vs /products?category=books.
  • Use ResponseEntity when the status or headers vary; plain return types + @ResponseStatus when they don't.
  • 201 + Location for creation, 204 for delete, 404 for missing, 400 for bad input.
  • Separate request types (records) from your internal model; never let clients set ids or internal fields.
  • Prefer ISO-8601 dates in APIs; use @JsonFormat only when a client really needs a specific format.
  • Hide internal fields with @JsonIgnore — or better, with separate response DTOs (topic 33).
  • Use BigDecimal for money.
  • Configure CORS globally, list explicit origins, and make them configurable per profile.
  • Design for retries: keep GET/PUT/DELETE idempotent; consider idempotency keys for important POSTs.
  • Be strict with input (fail-on-unknown-properties) during development to catch client typos early; teams decide whether to keep it in production for backward compatibility.

8. Key takeaways

  • @PathVariable = path segment, @RequestParam = query string (required by default; required=false/defaultValue), @RequestBody = JSON body, @RequestHeader = headers.
  • ResponseEntity controls status + headers + body: ok, created, noContent, notFound, status(...).
  • Create → 201 + Location built with ServletUriComponentsBuilder.fromCurrentRequest().
  • CRUD: GET list/one, POST create, PUT replace, PATCH partial, DELETE remove.
  • GET/PUT/DELETE are idempotent; POST is not; PATCH isn't guaranteed.
  • @JsonProperty renames, @JsonIgnore hides, @JsonFormat formats.
  • Accept/produces and Content-Type/consumes drive content negotiation (406/415).
  • CORS is a browser rule; allow front-end origins with @CrossOrigin or a global WebMvcConfigurer.

@PostMapping("/{id}/restock")
public ResponseEntity<Product> restock(@PathVariable Long id, @RequestParam int amount) {
    if (amount <= 0) {
        return ResponseEntity.badRequest().build();
    }
    return productService.findById(id)
            .map(p -> {

5. Simple paging. Add page (default 0) and size (default 2, max 50) query params to the list endpoint. Return only that slice and set headers X-Total-Count (all matches) and X-Total-Pages.

Hint / solution
@GetMapping
public ResponseEntity<List<Product>> getAll(
        @RequestParam(required = false) String category,
        @RequestParam(required = false) BigDecimal maxPrice,
        @RequestParam(name = "sort", defaultValue = "id") String sortBy,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "2") int size) {
    int safeSize = Math.min(Math.max(size, 1), 50);
    List<Product> all = productService.findAll(category, maxPrice, sortBy);
    List<Product> slice = all.stream().skip((long) page * safeSize).limit(safeSize).toList();
    int totalPages = (int) Math.ceil(all.size() / (double) safeSize);
    return ResponseEntity.ok()
            .header("X-Total-Count", String.valueOf(all.size()))
            .header("X-Total-Pages", String.valueOf(totalPages))
            .body(slice);
}

6. XML too. Uncomment jackson-dataformat-xml in pom.xml, remove produces = ...JSON from the class, restart, and request GET /api/products/1 with Accept: application/xml. What do you get? What happens with no Accept header now — and in the browser?

Hint / solution

You get <Product><id>1</id><name>Wireless Mouse</name>...<stock>50</stock></Product> — the Jackson annotations apply to XML too. With no Accept header (curl) you still get JSON (first suitable converter). Browsers send Accept: text/html,application/xhtml+xml,application/xml;..., so the browser now shows XML — a classic surprise! That's why many APIs keep produces = JSON. 10. Interview questions

Q1. Difference between @PathVariable and @RequestParam?

@PathVariable binds a URI template segment (/products/{id}) — used to identify a resource. @RequestParam binds query string (or form) parameters (?category=x) — used for filtering, sorting, paging. Both are required by default; @RequestParam supports required=false and defaultValue.

Q2. What is ResponseEntity and when do you use it?

A wrapper representing the whole HTTP response: status, headers and body. Use it when the status or headers depend on logic (201 with Location, 404 vs 200, 204, custom headers). For fixed statuses a plain return value with @ResponseStatus is fine.

Q3. How do you return 201 Created with the URL of the new resource?

Build the URI with ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(id).toUri() and return ResponseEntity.created(uri).body(created), which sets the Location header.

Q4. What does idempotent mean? Which HTTP methods are idempotent?

Repeating the request has the same effect on server state as sending it once. GET, HEAD, OPTIONS, PUT and DELETE are idempotent; POST is not; PATCH is not guaranteed. It matters for safe retries after network failures.

Q5. PUT vs PATCH — how would you implement PATCH?

PUT replaces the full representation; PATCH applies partial changes. A simple implementation uses a request DTO with nullable wrapper fields and updates only non-null ones. Alternatives: JSON Merge Patch (RFC 7386) or JSON Patch (RFC 6902) documents.

Q6. Explain @JsonIgnore, @JsonProperty and @JsonFormat.

@JsonIgnore excludes a property from (de)serialization; @JsonProperty("name") sets the JSON name (or marks a property for inclusion); @JsonFormat controls the shape/format, e.g. date patterns and time zones.

Q7. What is content negotiation in Spring MVC?

Choosing the response representation based on the request's Accept header (and the available HttpMessageConverters and the produces condition). If nothing matches, 406 Not Acceptable. For request bodies, Content-Type and consumes are matched; mismatch → 415.

Q8. What is CORS and how do you configure it in Spring Boot?

Cross-Origin Resource Sharing: a browser mechanism allowing a page from one origin to call another origin if the server responds with Access-Control-Allow-* headers (with a preflight OPTIONS for non-simple requests). Configure with @CrossOrigin on controllers/methods or globally via WebMvcConfigurer.addCorsMappings; with Spring Security, also enable http.cors().

Q9. What happens if the client sends a JSON field that doesn't exist in your class?

By default Spring Boot's ObjectMapper ignores unknown properties. With spring.jackson.deserialization.fail-on-unknown-properties=true (or @JsonIgnoreProperties(ignoreUnknown=false)) deserialization fails and Spring returns 400.

Q10. How do you read all request headers in a controller?

Declare a parameter @RequestHeader HttpHeaders headers or @RequestHeader Map<String, String> headers (or MultiValueMap); for a single one, @RequestHeader("X-Client-Id") String id.
