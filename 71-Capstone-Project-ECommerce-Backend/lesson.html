1. Why this matters

Congratulations — you made it to the last topic! 🎉 Up to now you learned every skill on its own: validation in one project, JWT in another, caching in a third. Real jobs are different. On your first day at a company you will open a codebase where all of these things live together, and the hard part is understanding how they fit.

That is exactly what this capstone gives you. ShopEasy is an online shop backend — think of a tiny Amazon or Flipkart without the website. A mobile app or a React front-end would talk to it over HTTP + JSON.

2. Real-life analogy

🏬 ShopEasy is a real department store
  • The security guard at the door checks your membership card (the JWT). No card? You can still look at the shop window (public product list), but you cannot take a basket. Staff badge (ADMIN)? You may enter the stock room.
  • The shelves are the product catalog, sorted into aisles (categories). You can search: "books under ₹1000, in stock".
  • Your shopping basket is the cart. Putting something in the basket does not reserve it — another customer can still take the last one from the shelf.
  • The cashier is the OrderService. At the till everything happens together or not at all: check each item is still available, take it off the stock list, print the receipt, empty your basket. If the last item is gone, the whole sale is cancelled — the cashier does not sell you "half an order". That is a transaction.
  • The receipt is the order. It shows the price you paid that day, even if the price tag changes tomorrow (a snapshot).
  • The "bestsellers" board by the door is the cache: quick to read, but someone must update it when stock changes.
  • The building's renovation log is Flyway: every change to the store layout is written down, numbered, and done exactly once.
  • The store directory at the entrance is Swagger UI, and the CCTV + fire-alarm panel is Actuator.

3. The project: requirements, architecture, data model, API

3.1 Requirements — what must ShopEasy do?

Every real project starts with requirements. Functional requirements say what the system does; non-functional ones say how well it does it.

WhoCan do
Anonymous visitorRegister, log in, list categories, search / filter / sort / page through products, view one product.
CUSTOMEREverything a visitor can + see "my profile", manage my cart (add, change quantity, remove, clear), place an order from the cart, list my orders, view one of my orders, cancel my order while it is PENDING or PAID.
ADMINCreate / update / delete categories and products, list all orders (filter by status), move an order through its life cycle (PAID → SHIPPED → DELIVERED or CANCELLED), see Actuator metrics and caches.

Business rules (the interesting part):

  1. Stock can never go below zero — even if two customers check out at the same millisecond.
  2. An order stores a snapshot of product name and price. Later price changes do not change old orders.
  3. The client never sends prices or totals. The server calculates them.
  4. Cancelling an order returns the items to stock. A SHIPPED order cannot be cancelled.
  5. Deleting a product is a soft delete (it disappears from the shop, but old orders still point to it).
  6. A category that still has products cannot be deleted.
  7. Registration always creates a CUSTOMER. Nobody can make themselves ADMIN.
  8. A customer can never see or change another customer's cart or orders.

3.4 The data model (ER diagram)

Seven tables. PK = primary key, FK = foreign key, UK = unique. Read the lines as "one user has one cart", "one order has many order items", and so on (relationships: topic 40).

💡 Two design decisions worth remembering
  • Cart items have no price; order items do. The cart always shows today's price. The order is a historical record, so it copies (snapshots) name and price at the moment of purchase.
  • Money is DECIMAL(12,2) in SQL and BigDecimal in Java — never double (topic 2: 0.1 + 0.2 != 0.3 in floating point).

3.6 Life of one request: "place my order"

POST /api/v1/orders→ RequestIdFilter
id = d1be0d43→ JwtAuthenticationFilter
token ✔ → UserPrincipal→ hasRole('CUSTOMER') ✔→ OrderController
@Valid body→ OrderService
@Transactional→ DB: lock, update stock, insert order
  1. RequestIdFilter gives the request an id and puts it in the logging MDC — every log line of this request will show [d1be0d43].
  2. JwtAuthenticationFilter reads Authorization: Bearer eyJ…, verifies the signature and expiry, loads the user and stores a UserPrincipal in the SecurityContext.
  3. The authorization rules in SecurityConfig check: is this user a CUSTOMER? If not → 403.
  4. Jackson turns the JSON body into a PlaceOrderRequest record; @Valid checks @NotBlank shippingAddress. If invalid → 400.
  5. OrderController gets the user id from @AuthenticationPrincipal (never from the request body!) and calls OrderService.placeOrder.
  6. The @Transactional proxy starts a transaction (topic 27: it is AOP!). The service locks the products, reduces stock, creates the order, empties the cart.
  7. Method returns → COMMIT. Then the cache entries for those products are evicted.
  8. The controller returns 201 Created with a Location header and the OrderResponse JSON.
  9. If anything threw an exception in step 6, the transaction is rolled back and GlobalExceptionHandler writes a ProblemDetail (e.g. 409 "Insufficient stock").

ℹ️ Defence in depth for stock The rule "stock ≥ 0" is enforced three times: in the request validation, in the entity method Product.decreaseStock(), and by the database CHECK constraint. If a future developer forgets one, the others still protect the data.

Why are the demo users not inserted by Flyway? Their passwords must be BCrypt hashes. config/DataSeeder.java (an ApplicationRunner) creates admin@shopeasy.com and customer@shopeasy.com at startup with the real PasswordEncoder — and only if they do not exist yet (idempotent).

Step 4 · Entities — a rich domain model

Topic 38 and 40. All entities extend AuditableEntity, a @MappedSuperclass with @CreationTimestamp / @UpdateTimestamp. We use no Lombok and no public setters. Instead, entities have small methods that protect their rules:

product/Product.java (excerpt)@Entity
@Table(name = "products")
public class Product extends AuditableEntity {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, precision = 12, scale = 2)
    private BigDecimal price;                       // money = BigDecimal

    @Column(name = "stock_quantity", nullable = false)
    private int stockQuantity;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)   // LAZY: no hidden joins
    @JoinColumn(name = "category_id", nullable = false)
    private Category category;

    @Version
    private Long version;                           // optimistic locking (topic 42)

    /** Takes items out of the warehouse. Refuses to go below zero. */
    public void decreaseStock(int quantity) {
        if (quantity <= 0) throw new IllegalArgumentException("quantity must be positive");
        if (quantity > stockQuantity) {
            throw new InsufficientStockException(id, name, quantity, stockQuantity);
        }
        this.stockQuantity -= quantity;
    }
}

The cart and the order are aggregates: the parent owns its children with cascade = ALL, orphanRemoval = true. Removing an item from the list is enough — Hibernate deletes the row. That is why there is no CartItemRepository.

cart/Cart.java (excerpt)@OneToMany(mappedBy = "cart", cascade = CascadeType.ALL, orphanRemoval = true)
@OrderBy("id")
private List<CartItem> items = new ArrayList<>();

/** Adds a product, or increases the quantity if it is already in the cart (no duplicate lines). */
public CartItem addProduct(Product product, int quantity) {
    Optional<CartItem> existing = findItem(product.getId());
    if (existing.isPresent()) {
        CartItem item = existing.get();
        item.changeQuantity(item.getQuantity() + quantity);
        return item;
    }
    CartItem item = new CartItem(this, product, quantity);
    items.add(item);
    return item;
}

public List<CartItem> getItems() { return Collections.unmodifiableList(items); }   // read-only view

OrderStatus is an enum with behaviour — a tiny state machine (topic 15: switch expressions):

order/OrderStatus.javapublic enum OrderStatus {
    PENDING, PAID, SHIPPED, DELIVERED, CANCELLED;

    public boolean canMoveTo(OrderStatus next) { return allowedNext().contains(next); }

    private Set<OrderStatus> allowedNext() {
        return switch (this) {
            case PENDING -> Set.of(PAID, CANCELLED);
            case PAID -> Set.of(SHIPPED, CANCELLED);
            case SHIPPED -> Set.of(DELIVERED);
            case DELIVERED, CANCELLED -> Set.of();   // final states
        };
    }
}

Step 7 · Errors as ProblemDetail

Topic 35. Services throw meaningful exceptions; one @RestControllerAdvice turns each into the right status. It extends ResponseEntityExceptionHandler, so Spring's own errors (bad JSON, wrong method…) also become ProblemDetails.

common/exception/GlobalExceptionHandler.java (excerpt)@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(InsufficientStockException.class)
    ProblemDetail handleInsufficientStock(InsufficientStockException ex) {
        ProblemDetail pd = problem(HttpStatus.CONFLICT, "Insufficient stock", "insufficient-stock", ex.getMessage());
        pd.setProperty("productId", ex.getProductId());   // extra fields for the front-end
        pd.setProperty("available", ex.getAvailable());
        return pd;
    }

    /** @PreAuthorize failures arrive HERE - without this the catch-all would turn them into 500. */
    @ExceptionHandler(AccessDeniedException.class)
    ProblemDetail handleAccessDenied(AccessDeniedException ex) { ... 403 ... }

    @ExceptionHandler(Exception.class)                    // safety net
    ProblemDetail handleUnexpected(Exception ex) {
        log.error("Unexpected error", ex);                // full details for US
        return problem(HttpStatus.INTERNAL_SERVER_ERROR, "Internal server error", "internal",
                "Something went wrong on our side. Please try again later.");   // nothing for attackers
    }
}

⚠️ Order of rules matters Spring checks requestMatchers from top to bottom and uses the first match. That is why "GET products is public" comes before "everything else under products needs ADMIN".

Creating a token. The payload contains only non-secret data (it is Base64, not encrypted):

    Instant now = Instant.now();
    return Jwts.builder()
            .issuer(properties.issuer())
            .subject(user.email())
            .claim("uid", user.id())
            .claim("role", user.role().name())
            .issuedAt(Date.from(now))
            .expiration(Date.from(now.plus(properties.expiration())))
            .signWith(signingKey)
            .compact();
}

The specification builds the WHERE clause only from the filters that were sent:

product/ProductSpecifications.java (excerpt)public static Specification<Product> from(ProductSearchCriteria criteria) {
    List<Specification<Product>> specs = new ArrayList<>();
    specs.add(isActive());                                   // soft-deleted products never appear
    if (criteria.q() != null && !criteria.q().isBlank()) specs.add(textContains(criteria.q().trim()));
    if (criteria.categoryId() != null) specs.add(inCategory(criteria.categoryId()));
    if (criteria.minPrice() != null)   specs.add(priceAtLeast(criteria.minPrice()));
    if (criteria.maxPrice() != null)   specs.add(priceAtMost(criteria.maxPrice()));
    if (Boolean.TRUE.equals(criteria.inStock())) specs.add(inStock());
    return Specification.allOf(specs);
}

We return our own PageResponse record instead of Spring's Page — a small, stable JSON contract:

{ "content": [ {...}, {...}, {...} ], "page": 0, "size": 3, "totalElements": 4, "totalPages": 2, "first": true, "last": false }

An unknown sort field (?sort=foo,asc) would normally cause a 500. We catch PropertyReferenceException and answer 400 "Cannot sort by 'foo'".

Topic 51. Reads of single products and of the category list are cached; writes evict.

@Transactional
@CacheEvict(cacheNames = CacheNames.PRODUCTS, key = "#id")
public ProductResponse update(Long id, ProductRequest request) { ... }
config/CacheConfig.java@Bean
CacheManager cacheManager() {
    ConcurrentMapCacheManager cacheManager = new ConcurrentMapCacheManager(CacheNames.PRODUCTS, CacheNames.CATEGORIES);
    cacheManager.setAllowNullValues(false);
    // Evictions inside a transaction are delayed until COMMIT (nothing evicted on rollback).
    return new TransactionAwareCacheManagerProxy(cacheManager);
}
ℹ️ Why TransactionAwareCacheManagerProxy? Placing an order changes stock inside a transaction. If we evicted the cache before the commit, another request could read the old stock from the database in that tiny gap and put it back into the cache — stale forever. Evicting after commit closes that gap. With several app instances you would switch to Redis (topic 51) so all instances share one cache.

Step 12 · Placing an order — the transactional heart

Topic 42. This is the method interviewers love to ask about. Read the comments slowly:

order/OrderService.java (placeOrder)@Transactional
public OrderResponse placeOrder(Long userId, PlaceOrderRequest request) {
    // 1. Which products are in the cart?
    List<Long> productIds = cartRepository.findProductIdsInCart(userId);
    if (productIds.isEmpty()) {
        throw new BusinessRuleException("Your cart is empty - add products before placing an order");
    }

    // 2. Lock them BEFORE reading the stock. Rows stay locked until this transaction ends.
    productRepository.findAllByIdForUpdate(productIds);

    // 3. Load the cart; its products are the freshly locked instances (same persistence context).
    Cart cart = cartRepository.findByUserId(userId)
            .orElseThrow(() -> new BusinessRuleException("Your cart is empty"));

    Order order = new Order(cart.getUser(), request.shippingAddress().trim());
    for (CartItem line : cart.getItems()) {
        Product product = line.getProduct();
        if (!product.isActive()) {
            throw new BusinessRuleException("'" + product.getName() + "' is no longer available.");
        }
        product.decreaseStock(line.getQuantity());   // throws InsufficientStockException → ROLLBACK
        order.addLine(product, line.getQuantity());  // snapshot of name + price
    }

    // 4. Persist the order (cascade saves the lines) and empty the cart.
    Order saved = orderRepository.save(order);
    cart.clear();
    evictProductsFromCache(productIds);              // happens after COMMIT

    log.info("Order {} placed by user {}: {} line(s), total {}", saved.getId(), userId,
            saved.getItems().size(), saved.getTotalAmount());
    return OrderMapper.toResponse(saved);
}

Why each detail matters:

  • One transaction: if line 3 of the cart is out of stock, the stock already reduced for lines 1 and 2 is rolled back. No half orders.
  • Pessimistic lock (SELECT … FOR UPDATE): Alice and Bob both want the last 3 mugs. Bob's transaction waits at step 2 until Alice's commits; then Bob reads stock = 0 and gets a clean 409. Without the lock, both could read "3 in stock" and both succeed → stock −3.
  • Lock before reading: we load only the ids first, lock, and only then load the products. If we read the products first, Hibernate would keep the old (unlocked) values in memory.
  • Lock in id order (order by p.id): two transactions always lock rows in the same order, which prevents deadlocks.
  • @Version as a safety net: any other code path that updates a product concurrently fails with ObjectOptimisticLockingFailureException → 409 "Concurrent update".
  • Dirty checking: we never call productRepository.save(product). Products are managed entities; Hibernate writes the new stock at commit (topic 38).

Cancelling works the same way in reverse: order.changeStatus(CANCELLED) (the enum refuses illegal moves), lock the products, increaseStock, evict the cache. Customers who ask for someone else's order get 404, not 403 — we do not even confirm that the order exists.

6. Common mistakes

⚠️ Mistake: forgetting "Bearer " in the Authorization header Authorization: eyJhbGci... → 401. The filter only reads headers that start with Bearer (with a space).
Fix: Authorization: Bearer eyJhbGci.... In Swagger UI paste the token without the word Bearer — Swagger adds it.
⚠️ Mistake: confusing 401 and 403 401 = "I don't know who you are" (no/expired/invalid token). 403 = "I know who you are, but you are not allowed" (a CUSTOMER calling an ADMIN endpoint).
Fix: on 401 log in again; on 403 log in as a user with the right role.
🛑 Mistake: editing a Flyway migration that already ran You change V1__create_schema.sql and restart against MySQL → Validate failed: Migration checksum mismatch for migration version 1.
Fix: never edit an applied migration. Add V3__add_product_rating.sql instead. (With H2 in-memory the database is new on every start, so you only notice this on MySQL — or in production!)
⚠️ Mistake: LazyInitializationException after adding a field to a DTO We set spring.jpa.open-in-view=false. If a controller touches a lazy association (e.g. order.getItems()) outside the service transaction, Hibernate has no session any more.
Fix: do all mapping to DTOs inside the @Transactional service method, and load what you need with @EntityGraph/JOIN FETCH.
⚠️ Mistake: "Port 8080 was already in use" Another app (or an old ShopEasy) is still running.
Fix: stop it, or start on another port: mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081.
⚠️ Mistake: a JWT secret that is too short or not Base64 WeakKeyException: The specified key byte array is 64 bits which is not secure enough at startup.
Fix: HS256 needs at least 32 random bytes, Base64-encoded: openssl rand -base64 32 (Git Bash). Put it in the JWT_SECRET environment variable.
⚠️ Mistake: caching entities instead of DTOs, or forgetting to evict A cached JPA entity is detached and may explode with lazy loading later; a forgotten @CacheEvict shows customers old prices or stock.
Fix: cache immutable DTO records; every write path evicts (we evict on update, delete, order placed and order cancelled).
⚠️ Mistake: trusting the client Accepting price, total, role or userId from the request body lets attackers buy a laptop for ₹1 or become ADMIN.
Fix: the server calculates prices and totals, registration always sets CUSTOMER, and the user id always comes from the token.
⚠️ Mistake: using curl in PowerShell like in Bash curl -X POST ... -d '{...}' in Windows PowerShell 5.1 calls Invoke-WebRequest and fails with strange parameter errors.
Fix: use Git Bash, call curl.exe explicitly, or use Invoke-RestMethod (section 5.4).

7. Best practices & extension ideas

7.1 What makes this codebase "enterprise-quality"

  • Package-by-feature with one-way dependencies between features.
  • Thin controllers, rich services, rich entities. Rules live where the data lives (Product.decreaseStock, OrderStatus.canMoveTo).
  • DTO records for every request and response — the API is a contract, independent of the database.
  • One error format (ProblemDetail) for every error — including 401/403 from the security filters.
  • Secure by default: deny unless allowed, stateless JWT, BCrypt, user id only from the token, no secrets in Git (env variables), 404 instead of 403 for other people's resources.
  • The database is managed by migrations, not by ddl-auto=update. Constraints and indexes are in SQL.
  • Correct under concurrency: pessimistic lock at checkout, @Version elsewhere, cache evicted after commit.
  • Performance basics: pagination with a max size, @EntityGraph and batch fetching against N+1, indexes on searched columns, caching hot reads (topic 70).
  • Observability: request id in every log line, no passwords in logs, health probes, metrics.
  • Automated tests at three levels and a CI pipeline that runs them on every change.

8. Key takeaways

  • A real backend is many simple ideas combined carefully: layers, DTOs, validation, errors, security, transactions, caching, docs, tests, deployment.
  • Package-by-feature keeps related code together and makes a later microservice split possible.
  • Entities protect their own rules (decreaseStock, canMoveTo); controllers stay thin; services own transactions.
  • The checkout is one @Transactional unit: lock → check → change → save → commit, or roll back everything.
  • Use a pessimistic lock where overselling must be impossible, @Version as a general safety net.
  • Orders store a snapshot of price and name; the client never sends prices, totals, roles or user ids.
  • Stateless JWT + roles + method security; 401 vs 403; every error is a ProblemDetail.
  • Flyway owns the schema; Hibernate only validates it. Same SQL runs on H2 and MySQL.
  • Cache DTOs, evict on every write, preferably after commit.
  • Prove it with unit, slice and end-to-end tests; ship it with Docker and CI.

10. Interview questions

Q1. Walk me through the architecture of your e-commerce project.

It is a Spring Boot 3 modular monolith organised by feature: auth, user, category, product, cart and order, plus shared security, config and common packages. Each feature has a thin REST controller, a transactional service and a Spring Data JPA repository; requests and responses are Java records, mapped from entities by small mapper classes. Security is stateless JWT with two roles. Errors are returned as RFC 9457 ProblemDetail by a global handler. Flyway owns the schema (H2 for dev, MySQL in production), the catalog is cached, there are unit, web-slice and end-to-end tests, and it ships as a Docker image built by GitHub Actions.

Q2. How do you prevent overselling when two customers buy the last item at the same time?

Checkout runs in one @Transactional method. Before reading stock it locks the product rows with SELECT … FOR UPDATE (@Lock(PESSIMISTIC_WRITE)), ordered by id to avoid deadlocks. The second transaction waits until the first commits, then sees the reduced stock and fails with InsufficientStockException → 409, and its changes roll back. The entity method refuses negative stock and the database has a CHECK (stock_quantity >= 0) constraint as the last line of defence. @Version optimistic locking protects other update paths. Alternative designs: an atomic UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ? and checking the affected row count, or stock reservations with a timeout.

Q3. Why do order items store the product name and price instead of just a product id?

An order is a legal/historical record of what was sold at what price. If we only stored the product id, a later price change or rename would silently change old orders and invoices. So we snapshot name and unit price into the order line and keep the product id for reference (restocking, "buy again"). The cart, on the other hand, stores no price because it should always show the current price.

Q4. Why JWT, and what are its downsides? How would you log a user out?

JWT keeps the server stateless: any instance can verify a token with the secret key, no session store needed, which suits horizontal scaling and mobile clients. Downsides: a token cannot be revoked before it expires, the payload is only Base64 (never put secrets in it), and the secret must be protected. Mitigations: short expiry (1 hour here, often 15 minutes) plus refresh tokens stored server-side; logout deletes the refresh token, and for urgent cases a deny-list of token ids. ShopEasy also reloads the user on every request, so a disabled account stops working immediately.

Q5. What is the difference between 401 and 403, and how does your app produce them?

401 Unauthorized means "not authenticated" — no token, invalid or expired token, or wrong password. 403 Forbidden means "authenticated but not allowed" — e.g. a CUSTOMER calling an ADMIN endpoint. Because these errors happen in the security filter chain before any controller, @RestControllerAdvice cannot see them; a custom AuthenticationEntryPoint (401) and AccessDeniedHandler (403) write them as ProblemDetail JSON. @PreAuthorize failures are thrown inside the controller call, so the global handler maps AccessDeniedException to 403 as well.

Q6. Why use DTOs instead of returning entities directly?

Security (never leak password hashes or internal flags, prevent mass assignment like setting role), stability (the API contract does not change when the table changes), performance and correctness (no lazy-loading exceptions or infinite JSON recursion from bidirectional relationships), and the ability to shape data for the client (flattened categoryName, computed inStock). Records make DTOs short and immutable.

Q7. How does caching work in the project, and how do you avoid stale data?

Single products and the category list are cached with @Cacheable, storing immutable DTOs. Every write evicts: update and delete evict that product id, renaming a category clears the products cache, and placing or cancelling an order evicts the affected products because stock changed. The cache manager is wrapped in TransactionAwareCacheManagerProxy, so evictions happen after commit — otherwise a concurrent read could re-cache the old value between eviction and commit. Search pages are not cached because there are too many combinations and stock changes often. With multiple instances we would use Redis so all instances share the cache.

Q8. Why Flyway and ddl-auto=validate instead of ddl-auto=update?

update guesses schema changes from entities, never drops or renames safely, cannot migrate data, and behaves differently per environment — dangerous in production. Flyway applies versioned, reviewed SQL scripts exactly once, in order, records them in flyway_schema_history, and gives the same schema everywhere. validate then makes Hibernate fail fast at startup if entities and tables do not match.

Q9. How did you test the application?

Following the test pyramid: fast pure unit tests for domain rules and the JWT service; Mockito unit tests for OrderService (happy path, rollback on insufficient stock, empty cart, cancellation, ownership); a @WebMvcTest slice for the product controller with the real security configuration (@MockitoBean for the service, @WithMockUser for roles) to check status codes, validation errors and ProblemDetail bodies; and a @SpringBootTest(RANDOM_PORT) end-to-end test that registers, browses, adds to cart, orders, checks stock and cache eviction, races two customers for the last items and checks the security rules over real HTTP. CI runs all of them on every push.

Q10. What does spring.jpa.open-in-view=false do and why did you set it?

Open Session In View keeps the Hibernate session open until the HTTP response is written, so controllers and Jackson can lazily load data. It hides N+1 problems, holds a database connection for the whole request and makes the transaction boundary unclear. Turning it off forces all data loading and DTO mapping to happen inside the service's @Transactional method, with explicit fetch plans (@EntityGraph, batch fetching). Spring Boot even logs a warning when it is left on by default.
