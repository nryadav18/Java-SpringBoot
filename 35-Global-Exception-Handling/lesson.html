35. Global Exception Handling

Turn every error in your API — not found, invalid input, broken JSON, business rule, unexpected bug — into one clean, consistent, safe JSON response, written in one place.

🎯 What you will learn
  • What Spring Boot does with an exception by default (the /error page and its JSON).
  • How to design custom exceptions like ResourceNotFoundException.
  • @ResponseStatus — the quick way to attach an HTTP status to an exception.
  • @ExceptionHandler — handle an exception in one controller.
  • @RestControllerAdvice — handle exceptions for all controllers in one class.
  • A standard ErrorResponse DTO (timestamp, status, error, message, path, fieldErrors).
  • Handling MethodArgumentNotValidException and other common Spring MVC exceptions.
  • ProblemDetail (RFC 7807 / RFC 9457), built into Spring 6, and spring.mvc.problemdetails.enabled.
  • Best practices — above all: never leak stack traces.

1. Why this matters

Things go wrong all the time in a real API: a book id doesn't exist, a form is half empty, someone sends broken JSON, a business rule says "no", or — sadly — there is a bug. How your API reports these problems matters a lot:

  • Front-end and mobile developers need one predictable error format so they can show a nice message: "This book is not available" instead of "Error".
  • Security: an error that prints a Java stack trace, a SQL statement or a class name tells attackers how your system is built.
  • Clean code: without a central handler, every controller method fills up with try/catch blocks that build error responses by hand — copied, slightly different each time.

In topic 33 we used @ResponseStatus and in topic 34 we saw Spring's long, technical validation errors. Now we do it properly — the way almost every production Spring Boot API does it: throw meaningful exceptions anywhere, catch them in ONE place.

2. Real-life analogy

🏥 Think of a hospital's front desk Doctors, nurses and labs (your controllers and services) do their work. When a problem happens — "the patient's file is missing", "this test is not possible today" — they don't each run out to the waiting room and explain it in their own words and jargon. They send the problem to the front desk (the @RestControllerAdvice).
  • The front desk explains every problem to the visitor in the same polite format: what happened, when, and what to do (the ErrorResponse).
  • It translates medical jargon into simple words — and never hands out internal notes (no stack traces).
  • For a truly unexpected emergency it says "Something went wrong, we are on it" to the visitor, while the full details go into the internal report (the server log).

3. Concepts step by step

3.1 What Spring Boot does by default

When an exception escapes your controller and nobody handles it, Spring Boot forwards the request to a special URL, /error, served by BasicErrorController. For a REST client it returns JSON like this:

{
  "timestamp": "2026-10-09T04:46:48.986+00:00",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/api/books/99"
}

(In a browser you'd see the famous "Whitelabel Error Page" instead.) Notice the problems:

  • A missing book gives 500 — "server bug" — but really it is the client asking for something that doesn't exist (should be 404).
  • No message — by default Spring Boot hides it, because messages might contain sensitive details.
  • Validation errors don't say which field was wrong.
PropertyDefaultMeaning
server.error.include-messageneverAdd the exception message
server.error.include-binding-errorsneverAdd raw validation errors
server.error.include-stacktraceneverAdd the Java stack trace — keep it never
server.error.include-exceptionfalseAdd the exception class name
server.error.whitelabel.enabledtrueThe HTML Whitelabel page for browsers

Turning on include-message=always looks helpful, but look what our "plain" profile returns for a simulated bug:

{"status":500,"error":"Internal Server Error",
 "message":"Cannot invoke \"String.toUpperCase()\" because \"notLoaded\" is null", ...}

That's internal code leaking out. We need control: our messages for expected problems, a generic message for bugs.

3.2 Step 1 — meaningful custom exceptions

Instead of throw new RuntimeException("not found"), create exceptions whose name says what went wrong:

exception/ResourceNotFoundException.javapublic class ResourceNotFoundException extends RuntimeException {

    private final String resourceName;   // "Book"
    private final String fieldName;      // "id"
    private final Object fieldValue;     // 99

    public ResourceNotFoundException(String resourceName, String fieldName, Object fieldValue) {
        super(resourceName + " not found with " + fieldName + ": " + fieldValue);
        this.resourceName = resourceName;
        this.fieldName = fieldName;
        this.fieldValue = fieldValue;
    }
    // getters...
}

// usage in ANY service:
throw new ResourceNotFoundException("Book", "id", 99);       // "Book not found with id: 99"
throw new ResourceNotFoundException("Member", "email", email);
  • Extend RuntimeException (unchecked, topic 10) — no throws clauses everywhere; Spring handles them centrally anyway.
  • Make it reusable: one ResourceNotFoundException works for books, members, orders…
  • Typical family: ResourceNotFoundException (404), DuplicateResourceException (409), BusinessRuleException/BookNotAvailableException (422 or 409), AccessDeniedException (403, from Spring Security later).

3.3 Step 2 (quick option) — @ResponseStatus

@ResponseStatus(HttpStatus.NOT_FOUND)
public class ResourceNotFoundException extends RuntimeException { ... }

Now when this exception escapes a controller, the status is 404 instead of 500. Simple! But limited:

  • The body is still Spring Boot's default JSON (you can't add fields).
  • You can't use it on exceptions from libraries (you can't edit their classes).
  • It is ignored as soon as an @ExceptionHandler handles the exception — handlers win.

Our exceptions keep @ResponseStatus as a sensible fallback (you'll see it working in the plain profile), but the real work is done by the advice.

ℹ️ ResponseStatusException For a quick one-off you can also throw Spring's ready-made throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Book not found") without creating a class. Fine for prototypes; custom exception classes are clearer in bigger apps.

3.4 Step 3 — @ExceptionHandler in one controller

A method annotated with @ExceptionHandler is called when a controller method throws that exception type. Its return value becomes the response:

@RestController
public class BookController {
    // ... endpoints ...

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<String> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(404).body(ex.getMessage());
    }
}

Problem: it only works for exceptions thrown by this controller. With 20 controllers you would copy it 20 times. Enter the advice…

3.5 Step 4 — @RestControllerAdvice: one handler for all controllers

@ControllerAdvice marks a class whose @ExceptionHandler methods apply to all controllers. @RestControllerAdvice = @ControllerAdvice + @ResponseBody, so return values are written as JSON.

Request→ Controller→ Service throws
ResourceNotFoundException↗ bubbles up ↗ DispatcherServlet
asks exception resolvers→ @RestControllerAdvice
@ExceptionHandler(ResourceNotFound…)→ 404 + ErrorResponse JSON

How does Spring pick a method? It chooses the handler whose exception type is the closest match (the most specific class in the exception's hierarchy). So @ExceptionHandler(ResourceNotFoundException.class) beats @ExceptionHandler(RuntimeException.class), which beats @ExceptionHandler(Exception.class). Order of methods in the file does not matter.

Order Spring triesMechanism
1@ExceptionHandler in the controller itself
2@ExceptionHandler in a @ControllerAdvice/@RestControllerAdvice
3@ResponseStatus on the exception class / ResponseStatusException
4Spring's built-in handling of its own exceptions (e.g. 405, 415, 400)
5Nobody: forward to /error → default JSON with 500

Handler methods can receive useful parameters: the exception itself, HttpServletRequest (for the path), WebRequest, Locale… and can return ResponseEntity<T>, any object (with @ResponseStatus on the method), or a ProblemDetail.

💡 Scope an advice @RestControllerAdvice(basePackages = "com.course.exceptions.controller") or (assignableTypes = BookController.class) limits it to some controllers — useful when an app has both a public API and an admin API with different error formats.

3.6 Step 5 — a standard ErrorResponse DTO

Every error should look the same. We use a record:

dto/ErrorResponse.java@JsonInclude(JsonInclude.Include.NON_NULL)          // hide fieldErrors when null
public record ErrorResponse(
        Instant timestamp,      // when
        int status,             // 404
        String error,           // "Not Found"
        String message,         // "Book not found with id: 99"  (safe, human-readable)
        String path,            // "/api/books/99"
        List<FieldErrorDetail> fieldErrors   // only for validation errors
) {
    public record FieldErrorDetail(String field, String message) { }

    public static ErrorResponse of(int status, String error, String message, String path) {
        return new ErrorResponse(Instant.now(), status, error, message, path, null);
    }
}
FieldWhy it's useful
timestampMatching the error with server logs ("what happened at 10:15:30?")
statusSame as the HTTP status — handy when the body is logged or forwarded
errorShort standard reason phrase
messageHuman-readable explanation — the UI can show it
pathWhich URL failed
fieldErrorsWhich input fields are wrong — the UI can highlight them in the form
⚠️ Name clash Spring 6 also has an interface named org.springframework.web.ErrorResponse. When VS Code offers imports, pick your com.course.exceptions.dto.ErrorResponse. (Some teams name theirs ApiError to avoid confusion.)

3.7 Handling validation errors: MethodArgumentNotValidException

From topic 34: a failed @Valid @RequestBody throws MethodArgumentNotValidException. Its BindingResult holds every FieldError. We turn them into a short list:

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleBodyValidation(MethodArgumentNotValidException ex,
                                                          HttpServletRequest request) {
    List<FieldErrorDetail> fieldErrors = ex.getBindingResult().getFieldErrors().stream()
            .map(fe -> new FieldErrorDetail(fe.getField(), fe.getDefaultMessage()))
            .sorted((a, b) -> a.field().compareTo(b.field()))
            .toList();
    ErrorResponse body = new ErrorResponse(Instant.now(), 400, "Bad Request",
            "Validation failed for " + fieldErrors.size() + " field(s)",
            request.getRequestURI(), fieldErrors);
    return ResponseEntity.badRequest().body(body);
}

Result — compare it with the 1,000-character monster from topic 34:

{
  "timestamp": "2026-10-09T04:45:45.242Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed for 3 field(s)",
  "path": "/api/books",
  "fieldErrors": [
    { "field": "copies", "message": "Copies cannot be negative" },
    { "field": "isbn",   "message": "ISBN must be exactly 13 digits" },
    { "field": "title",  "message": "Title is required" }
  ]
}

We deliberately do not echo the rejected value — it might be a password.

🛑 The catch-all trap Once you add @ExceptionHandler(Exception.class), it also catches Spring's own exceptions that you didn't handle explicitly. A typo in a URL (NoResourceFoundException) or a wrong HTTP method would suddenly become 500! Always handle the common Spring MVC exceptions explicitly (as in the table) — or extend ResponseEntityExceptionHandler, which handles all of them for you (section 3.10).

3.9 The catch-all: log everything, reveal nothing

@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleUnexpected(Exception ex, HttpServletRequest request) {
    log.error("Unexpected error on {} {}", request.getMethod(), request.getRequestURI(), ex); // full stack trace in LOG
    return build(HttpStatus.INTERNAL_SERVER_ERROR,
            "Something went wrong on our side. Please try again later.", request);              // nothing technical to CLIENT
}

Passing ex as the last argument to the logger prints the full stack trace (topic 30). Developers see everything in the logs; clients see a polite generic sentence.

3.10 ProblemDetail — the official standard (RFC 7807 → RFC 9457)

Many companies invented their own error JSON — every API looked different. The IETF published a standard: "Problem Details for HTTP APIs", first RFC 7807 (2016), updated by RFC 9457 (2023). Spring Framework 6 supports it out of the box with the ProblemDetail class. The response has Content-Type application/problem+json:

{
  "type": "https://api.library.example/problems/resource-not-found",
  "title": "Resource not found",
  "status": 404,
  "detail": "Book not found with id: 99",
  "instance": "/api/books/99",
  "resource": "Book",
  "timestamp": "2026-10-09T04:46:09.824Z"
}
FieldMeaningOur ErrorResponse equivalent
typeURI identifying the kind of problem (can link to docs). Default about:blank—
titleShort summary of the problem typeerror
statusHTTP status codestatus
detailExplanation of this occurrencemessage
instanceURI of this occurrence (Spring fills in the request path)path
extra propertiesAnything you add with setProperty(...)timestamp, fieldErrors
exception/ProblemDetailExceptionHandler.java (part)@RestControllerAdvice
@Profile("problem")
public class ProblemDetailExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setType(URI.create("https://api.library.example/problems/resource-not-found"));
        problem.setTitle("Resource not found");
        problem.setProperty("resource", ex.getResourceName());   // custom extra field
        problem.setProperty("timestamp", Instant.now());
        return problem;                                         // status taken from the ProblemDetail
    }
}

Why extend ResponseEntityExceptionHandler? It is a Spring base class that already handles ~20 Spring MVC exceptions (bad JSON, 405, 415, type mismatch, missing parameter, unknown URL, parameter validation…) and returns them as ProblemDetail. You only add your own exceptions and override what you want to customise — e.g. handleMethodArgumentNotValid to add a fieldErrors list.

spring.mvc.problemdetails.enabled

application-problem.propertiesspring.mvc.problemdetails.enabled=true

With zero code, this property makes Spring Boot register its own ResponseEntityExceptionHandler, so all of Spring MVC's built-in exceptions are answered as ProblemDetail. If you write your own subclass (like we did), Boot's one steps back and yours is used. Your custom exceptions with @ResponseStatus still get the right status either way.

Also handy: Spring's exception classes such as ErrorResponseException already carry a ProblemDetail. You can extend it for your own exceptions: class BookNotFound extends ErrorResponseException { super(HttpStatus.NOT_FOUND, ProblemDetail.forStatusAndDetail(...), null); }.

💡 Which format should I choose? For a new API, ProblemDetail is a great default — it's a standard, tools understand it, and Spring supports it natively.Your own ErrorResponse is fine too, and very common in existing projects. The important thing is: one format, used everywhere. This project shows both so you can recognise them.

4.1 The service: just throw

service/BookService.java (part)public BookResponse borrow(Long id) {
    Book book = getBook(id);                                   // 404 if missing
    if (book.getCopiesAvailable() == 0) {
        throw new BookNotAvailableException(book.getTitle());  // 422 business rule
    }
    book.setCopiesAvailable(book.getCopiesAvailable() - 1);
    return toResponse(repository.save(book));
}

private Book getBook(Long id) {
    return repository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Book", "id", id));
}

No status codes, no ResponseEntity, no try/catch. The service says what went wrong; the advice decides how to tell the client.

4.3 The global handler

exception/GlobalExceptionHandler.java (structure)@RestControllerAdvice
@Profile("!problem & !plain")
public class GlobalExceptionHandler {

    // 1. our business exceptions
    @ExceptionHandler(ResourceNotFoundException.class)     -> 404
    @ExceptionHandler(DuplicateResourceException.class)    -> 409
    @ExceptionHandler(BookNotAvailableException.class)     -> 422

    // 2. validation (topic 34)
    @ExceptionHandler(MethodArgumentNotValidException.class)   -> 400 + fieldErrors
    @ExceptionHandler(HandlerMethodValidationException.class)  -> 400 + fieldErrors

    // 3. client mistakes detected by Spring MVC
    @ExceptionHandler(HttpMessageNotReadableException.class)        -> 400
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)    -> 400
    @ExceptionHandler(HttpRequestMethodNotSupportedException.class) -> 405
    @ExceptionHandler(NoResourceFoundException.class)               -> 404

    // 4. safety net
    @ExceptionHandler(Exception.class)                     -> 500, generic message, full log
}

Each handler is short thanks to a private helper:

@ExceptionHandler(ResourceNotFoundException.class)
public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex,
                                                    HttpServletRequest request) {
    return build(HttpStatus.NOT_FOUND, ex.getMessage(), request);
}

private ResponseEntity<ErrorResponse> build(HttpStatus status, String message, HttpServletRequest request) {
    ErrorResponse body = ErrorResponse.of(status.value(), status.getReasonPhrase(), message,
            request.getRequestURI());
    return ResponseEntity.status(status).body(body);
}

Parameter validation errors (HandlerMethodValidationException) are a bit different from body errors — they are grouped per method parameter:

List<FieldErrorDetail> fieldErrors = ex.getParameterValidationResults().stream()
        .flatMap(result -> result.getResolvableErrors().stream()
                .map(error -> new FieldErrorDetail(
                        result.getMethodParameter().getParameterName(),   // "minCopies"
                        error.getDefaultMessage())))                       // "minCopies must be at least 1"
        .toList();

4.4 The ProblemDetail handler: customising validation

exception/ProblemDetailExceptionHandler.java (part)@Override
protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
        HttpHeaders headers, HttpStatusCode status, WebRequest request) {
    ProblemDetail problem = ex.getBody();          // Spring already prepared a ProblemDetail
    problem.setTitle("Validation failed");
    problem.setDetail("One or more fields are invalid");
    problem.setProperty("fieldErrors", ex.getBindingResult().getFieldErrors().stream()
            .map(fe -> Map.of("field", fe.getField(), "message", String.valueOf(fe.getDefaultMessage())))
            .toList());
    return handleExceptionInternal(ex, problem, headers, status, request);
}

6. Common mistakes

🛑 Mistake: sending stack traces or exception messages of unexpected errors to clients return ex.toString() or server.error.include-stacktrace=always in production reveals class names, SQL, file paths.
Fix: Catch-all handler returns a generic message and logs the full exception server-side.
⚠️ Mistake: catch-all Exception handler turns 404/405 into 500 Unknown URLs and wrong methods suddenly look like server bugs.
Fix: Handle NoResourceFoundException, HttpRequestMethodNotSupportedException etc. explicitly, or extend ResponseEntityExceptionHandler.
⚠️ Mistake: swallowing exceptions catch (Exception e) { return null; } in a service. The client gets 200 with an empty body and nobody knows why.
Fix: Let exceptions travel up to the advice; only catch what you can actually handle.
⚠️ Mistake: try/catch in every controller method Hundreds of lines building error responses by hand, each slightly different.
Fix: One @RestControllerAdvice.
⚠️ Mistake: wrong status codes Returning 500 for "not found", 200 with {"error": "..."}, or 400 for a missing resource.
Fix: Client mistakes = 4xx (400 invalid, 404 missing, 409 conflict, 422 business rule); server bugs = 5xx.
⚠️ Mistake: the advice class is not picked up Placed outside the main package, or missing @RestControllerAdvice.
Fix: Put it in a sub-package of the @SpringBootApplication class.
⚠️ Mistake: two handlers for the same exception Two advices both handling ResourceNotFoundException — which one wins is unclear.
Fix: One global advice, or control priority with @Order and scoping (basePackages).
⚠️ Mistake: using @ControllerAdvice and returning an object Without @ResponseBody Spring tries to find a view with that name.
Fix: Use @RestControllerAdvice for REST APIs (or return ResponseEntity).

7. Best practices

  • One error format for the whole API — your own ErrorResponse or the standard ProblemDetail. Document it (topic 44).
  • Throw specific, meaningful exceptions from services; keep them unchecked and reusable (ResourceNotFoundException("Book", "id", id)).
  • Map exceptions to HTTP in one place (@RestControllerAdvice), not in services.
  • Never leak internals: no stack traces, exception class names, SQL, or file paths in responses. Keep server.error.include-stacktrace=never.
  • Log properly: unexpected errors at ERROR with stack trace; expected client errors (404, 400) at most at DEBUG/INFO/WARN — they are not bugs and shouldn't flood your logs.
  • Return field-level validation errors so UIs can highlight fields.
  • Don't echo sensitive input (passwords, card numbers) in error messages.
  • Use correct status codes: 400, 401, 403, 404, 405, 409, 415, 422, 500, 503.
  • Add a correlation/trace id to error responses in bigger systems so support can find the matching log line (topic 65).
  • Test your error responses like any other feature (MockMvc, see the tests).

8. Key takeaways

  • Without handling, exceptions become Spring Boot's default /error JSON — often a 500 with no useful message.
  • Create meaningful unchecked exceptions (ResourceNotFoundException, DuplicateResourceException…).
  • @ResponseStatus on an exception sets its status quickly but can't change the body.
  • @ExceptionHandler handles exceptions; inside @RestControllerAdvice it applies to all controllers.
  • The most specific @ExceptionHandler wins; handlers beat @ResponseStatus.
  • Use a standard ErrorResponse DTO: timestamp, status, error, message, path, fieldErrors.
  • Handle MethodArgumentNotValidException to return clean field errors.
  • ProblemDetail (RFC 9457) is the standard format, built into Spring 6; spring.mvc.problemdetails.enabled=true enables it for Spring's exceptions.
  • A catch-all returns a generic 500 and logs everything — never leak stack traces.

Easy

Medium

Handle ConstraintViolationException. Put @Validated on BookService and @Min(1) on the id parameter of findById(@Min(1) Long id). Call /api/books/0. Then add a handler that returns 400 with fieldErrors.

Hint / solution 
@ExceptionHandler(ConstraintViolationException.class)
public ResponseEntity<ErrorResponse> handleConstraint(ConstraintViolationException ex,
                                                      HttpServletRequest request) {
    List<FieldErrorDetail> errors = ex.getConstraintViolations().stream()
            .map(v -> new FieldErrorDetail(v.getPropertyPath().toString(), v.getMessage()))
            .toList();
    return ResponseEntity.badRequest().body(new ErrorResponse(Instant.now(), 400, "Bad Request",
            "Invalid input", request.getRequestURI(), errors));
}

The field will be named like findById.id (method name + parameter).

Medium

Error code for clients. Add a machine-readable code field to ErrorResponse (e.g. "BOOK_NOT_AVAILABLE", "RESOURCE_NOT_FOUND", "VALIDATION_FAILED"). Why is this better for front-ends than comparing message texts?

Hint / solution

Add String code to the record and pass it from each handler. Messages may change wording or be translated; codes are stable, so the UI can do if (error.code === 'BOOK_NOT_AVAILABLE') showWaitlistButton(). In ProblemDetail the type URI plays this role.

Challenge

Unify the two formats. Make GlobalExceptionHandler extend ResponseEntityExceptionHandler and override handleExceptionInternal(...) so that all Spring MVC exceptions (415, missing params, etc.) are returned as your ErrorResponse — then remove your hand-written handlers for HttpMessageNotReadableException, HttpRequestMethodNotSupportedException and NoResourceFoundException.

Hint / solution 
@Override
protected ResponseEntity<Object> handleExceptionInternal(Exception ex, Object body, HttpHeaders headers,
                                                         HttpStatusCode statusCode, WebRequest request) {
    HttpStatus status = HttpStatus.valueOf(statusCode.value());
    String path = ((ServletWebRequest) request).getRequest().getRequestURI();
    String message = (body instanceof ProblemDetail pd && pd.getDetail() != null)
            ? pd.getDetail() : status.getReasonPhrase();
    ErrorResponse error = ErrorResponse.of(status.value(), status.getReasonPhrase(), message, path);
    return new ResponseEntity<>(error, headers, status);
}

Careful: once you extend it, you must not also declare @ExceptionHandler(MethodArgumentNotValidException.class) — the base class already handles it (you'd get an "Ambiguous @ExceptionHandler" startup error). Override handleMethodArgumentNotValid instead.

10. Interview questions

Q1. How do you handle exceptions globally in Spring Boot?

Create a class annotated with @RestControllerAdvice containing @ExceptionHandler methods for each exception type. Each method builds a consistent response (custom DTO or ProblemDetail) with the right status. Services throw meaningful exceptions, controllers stay free of try/catch.

Q2. What is the difference between @ControllerAdvice and @RestControllerAdvice?

@RestControllerAdvice is @ControllerAdvice + @ResponseBody: handler return values are serialized into the response body (JSON). With plain @ControllerAdvice a returned String is treated as a view name unless you use @ResponseBody or ResponseEntity.

Q3. @ResponseStatus vs @ExceptionHandler — when to use which?

@ResponseStatus on an exception class is a quick way to set the HTTP status, but you can't customise the body, can't use it on third-party exceptions, and it is ignored if a handler exists. @ExceptionHandler gives full control over status, headers and body. In real APIs, a @RestControllerAdvice with handlers is the standard approach.

Q4. If several @ExceptionHandler methods match, which one is chosen?

The one declared for the closest (most specific) exception type in the thrown exception's class hierarchy. Handlers in the controller itself take precedence over those in an advice; between multiple advices, @Order/Ordered decides.

Q5. What is ProblemDetail?

A Spring 6 class implementing RFC 9457 (formerly RFC 7807) "Problem Details for HTTP APIs": a standard JSON error format with type, title, status, detail, instance plus custom properties, served as application/problem+json. You can return it from @ExceptionHandler methods; ResponseEntityExceptionHandler and ErrorResponseException use it natively; spring.mvc.problemdetails.enabled=true makes Spring Boot use it for built-in MVC exceptions.

Q6. How do you return field-level validation errors?

Handle MethodArgumentNotValidException, iterate ex.getBindingResult().getFieldErrors() and map each to {field, message}. For parameter validation handle HandlerMethodValidationException (Spring 6.1+) or ConstraintViolationException (class-level @Validated).

Q7. What is ResponseEntityExceptionHandler?

A convenient base class for a @ControllerAdvice that already handles the standard Spring MVC exceptions (HttpRequestMethodNotSupported, HttpMediaTypeNotSupported, MissingServletRequestParameter, MethodArgumentNotValid, NoResourceFound, etc.) and returns ProblemDetail bodies. You extend it and override specific handleXxx methods or handleExceptionInternal to customise.

Q8. Why should you not expose stack traces in API responses?

They reveal implementation details — framework versions, class and package names, SQL, file paths — which help attackers find vulnerabilities, and they are useless/confusing for API consumers. Log them on the server, return a generic message (optionally with a correlation id) to the client.

Q9. Checked or unchecked exceptions for business errors in Spring?

Usually unchecked (RuntimeException subclasses): they don't pollute method signatures, they propagate naturally to the global handler, and by default Spring's @Transactional rolls back on unchecked exceptions (topic 42) — checked exceptions don't trigger rollback unless configured with rollbackFor.

Q10. Which status code for a business rule violation like "book not available"?

The request is syntactically valid and the resource exists, so 400 and 404 don't fit. Common choices are 409 Conflict (conflicts with the current state of the resource) or 422 Unprocessable Content (understood but can't be processed due to semantic/business rules). Choose one convention and use it consistently.
