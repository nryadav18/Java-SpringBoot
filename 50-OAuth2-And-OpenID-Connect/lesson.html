1. Why this matters

In topics 47–49 our application stored usernames and password hashes and created its own tokens. That works – but it also means we are responsible for password resets, two-factor login, account lockout, leaked databases… Big companies prefer to give this job to a specialist:

  • "Login with Google / GitHub / Microsoft" buttons – users do not need yet another password, and you never see theirs.
  • Single Sign-On (SSO) in companies: employees log in once (Keycloak, Okta, Azure AD / Entra ID, Auth0) and can use dozens of internal apps.
  • Microservices (Part F): one central authorization server issues tokens; every service only checks them.
  • Third-party access: "Allow this photo-printing app to read your Google Photos" – without giving it your Google password.

All of these are built on two standards: OAuth 2.0 (delegated authorization) and OpenID Connect (authentication on top of OAuth2). They appear in almost every enterprise job description that mentions security. Spring Security supports both with very little code.

2. Real-life analogy

🚗 The valet key

You arrive at a fancy restaurant. A valet will park your car. You do not hand over your house keys and your normal car key (your password). Many cars come with a special valet key: it starts the engine and drives a short distance, but it cannot open the boot or the glove box.

  • You = the resource owner (the car is yours).
  • The valet = the client application that wants to do something for you.
  • The valet key = the access token: limited power (scope: "drive, but not open the boot"), temporary, and you can take it back.
  • The car = the resource server that accepts the valet key.
  • The restaurant's key desk that checks your identity and hands out valet keys = the authorization server.

The valet never learns your master key. If they misbehave, you cancel that one key – your house is still safe. That is exactly what OAuth2 gives you online.

OpenID Connect adds a name badge to the deal: along with the valet key, the desk gives the valet a signed card saying "This car belongs to Alice Learner, alice@example.com". Now the valet knows who you are, not just what they may do.

3. Concepts step by step

3.1 The problem: the "password anti-pattern"

Years ago, apps that wanted your Gmail contacts simply asked: "Enter your Gmail password". The app could then read all your mail, change your password, and keep access forever. If that app was hacked, millions of Gmail passwords leaked. OAuth2 (2012) replaced this with tokens: limited, temporary, revocable permissions – and the password is typed only at Google.

3.3 Vocabulary you will meet

TermSimple meaning
Client IDPublic name of your app at the authorization server (like a username for the app).
Client secretPassword of your app. Only for confidential clients running on a server. Never in browser JavaScript or mobile apps.
Redirect URI (callback)Where the authorization server sends the browser back after login. Must be registered exactly.
ScopeWhat the app asks permission for: read:user, email, openid profile…
ConsentThe "Allow Course App to read your profile?" screen.
Authorization codeA short-lived, one-time code sent via the browser; the client swaps it for tokens.
Access tokenThe valet key. Sent as Authorization: Bearer ... to resource servers. Often a JWT (topic 49).
Refresh tokenUsed by the client to get new access tokens without bothering the user.
ID token (OIDC)A JWT that says who logged in. Meant for the client, not for APIs.

PKCE ("pixy")Proof Key for Code Exchange: a one-time secret proving the code is redeemed by the same client that asked for it. Mandatory for public clients, recommended for all.
IssuerThe authorization server's identity URL, e.g. http://localhost:8180/realms/course. Appears as iss in tokens.

3.4 Grant types ("flows")

OAuth2 defines several ways to get a token, for different situations:

3.5 The Authorization Code flow, step by step

When we ran our oauth2-login-client and asked for /oauth2/authorization/github, step ② produced exactly this redirect (client id is our placeholder):

HTTP/1.1 302
Location: https://github.com/login/oauth/authorize?response_type=code
          &client_id=replace-with-your-github-client-id
          &scope=read:user%20user:email
          &state=7EE-fj9DK32Ut04Fd6lFr1UvYBXrqA-i78_QuKyEyzM%3D
          &redirect_uri=http://localhost:8080/login/oauth2/code/github

Why the extra code step instead of sending the token directly in ⑤? Everything in a redirect URL can end up in browser history, logs, or extensions. The code is useless on its own – exchanging it needs the client secret (or the PKCE verifier), which never leaves our server.

3.6 OAuth2 vs OpenID Connect

OAuth2 was designed for authorization ("may this app read my photos?"). It says nothing about who the user is. People used it for login anyway, each provider in its own way. OpenID Connect (OIDC) is a thin, standard identity layer on top:

OAuth 2.0OpenID Connect
AnswersWhat may the client do?Who is the user? (+ everything OAuth2 does)
Main tokenAccess token (for APIs)+ ID token (JWT for the client)
TriggerAny scopesScope openid
User infoProvider-specific API (GitHub: /user)Standard claims (sub, name, email…) + /userinfo endpoint
DiscoveryNo standard/.well-known/openid-configuration lists all URLs and keys
ExamplesGitHubGoogle, Microsoft, Keycloak, Auth0, Okta
Spring principalOAuth2UserOidcUser (extends OAuth2User)

A decoded ID token from Keycloak looks like this (shortened):

{
  "iss": "http://localhost:8180/realms/course",
  "sub": "8c1f0e7a-3b2d-4c55-9a8e-6f1d2b7c9e10",
  "aud": "course-client",
  "exp": 1791521810,
  "iat": 1791521510,
  "preferred_username": "alice",
  "email": "alice@example.com",
  "name": "Alice Learner"
}
⚠️ ID token ≠ access token The ID token is for the client ("who logged in?"). APIs must be called with the access token. Never send an ID token to a resource server as a Bearer token.

3.10 The Resource Server – validating tokens from an issuer

In topic 49 our API created and checked tokens with one shared secret (HS256). In the OAuth2 world, the authorization server signs tokens with its private key (RS256), and every API verifies them with the matching public key. The API never needs a secret at all. Configuration:

resource-server/src/main/resources/application.ymlspring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: ${ISSUER_URI:http://localhost:8180/realms/course}

That single line makes Spring:

  1. Fetch {issuer-uri}/.well-known/openid-configuration (OIDC discovery) on the first request with a token.
  2. Read jwks_uri from it and download the issuer's public keys (cached, refreshed when a new kid appears).
  3. For each request, BearerTokenAuthenticationFilter takes the token from Authorization: Bearer ... and checks signature, exp/nbf and iss.
  4. Turn the token into a JwtAuthenticationToken with authorities and put it into the SecurityContext.

Scopes → authorities. By default Spring turns the scope claim into authorities with a SCOPE_ prefix: "scope": "openid profile email" → SCOPE_openid, SCOPE_profile, SCOPE_email. So rules look like hasAuthority("SCOPE_profile").

Roles from Keycloak. Keycloak puts the user's roles in a nested claim that Spring does not know: "realm_access": {"roles": ["user","admin"]}. A small converter adds them as ROLE_USER, ROLE_ADMIN:

resource-server/.../KeycloakRealmRoleConverter.javapublic class KeycloakRealmRoleConverter implements Converter<Jwt, Collection<GrantedAuthority>> {

    private final JwtGrantedAuthoritiesConverter scopesConverter = new JwtGrantedAuthoritiesConverter();

    @Override
    public Collection<GrantedAuthority> convert(Jwt jwt) {
        List<GrantedAuthority> authorities = new ArrayList<>(scopesConverter.convert(jwt)); // SCOPE_...
        Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");
        if (realmAccess != null && realmAccess.get("roles") instanceof Collection<?> roles) {
            for (Object role : roles) {
                authorities.add(new SimpleGrantedAuthority("ROLE_" + role.toString().toUpperCase()));
            }
        }
        return authorities;
    }
}
resource-server/.../SecurityConfig.javahttp
    .csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/public/**", "/error").permitAll()
        .requestMatchers("/api/profile").hasAuthority("SCOPE_profile")
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .anyRequest().authenticated())
    .oauth2ResourceServer(oauth2 -> oauth2
        .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthenticationConverter())));

@Bean
public JwtAuthenticationConverter jwtAuthenticationConverter() {
    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(new KeycloakRealmRoleConverter());
    converter.setPrincipalClaimName("preferred_username");   // getName() = "alice" instead of a UUID
    return converter;
}

💡 Topic 49 vs topic 50 In topic 49 we wrote JwtService + JwtAuthenticationFilter + login endpoints ourselves. A resource server needs none of that: no users table, no passwords, no login endpoint – just issuer-uri and authorization rules. That is why companies love central authorization servers.

3.12 Security notes for OAuth2/OIDC

  • Redirect URIs must be exact – no wildcards in production. Otherwise an attacker can steal codes by redirecting to their site.
  • state and PKCE – Spring adds and checks state automatically, and uses PKCE for public clients (and can for confidential ones).
  • Client secrets only on servers. SPAs and mobile apps are public clients: use Authorization Code + PKCE without a secret, or a Backend-for-Frontend.
  • Validate the audience (aud) in resource servers when possible: a token for API A should not be accepted by API B (spring.security.oauth2.resourceserver.jwt.audiences).
  • Request the smallest scopes you need. Users trust apps that ask for less.
  • HTTPS for everything except your laptop.

6. Common mistakes

⚠️ Mistake: "redirect_uri_mismatch" / "The redirect_uri is not associated with this application" The callback URL registered at GitHub/Google/Keycloak differs from what Spring sends (port, http vs https, trailing slash, registration id).
Fix: register exactly http://localhost:8080/login/oauth2/code/{registrationId}.
⚠️ Mistake: app with the keycloak profile fails at startup A client registration with issuer-uri performs discovery at startup – Keycloak must already be running.
Fix: docker compose up -d and wait until Keycloak is ready, then start the app.
⚠️ Mistake: 401 with "The iss claim is not valid" The token was issued for http://127.0.0.1:8180/... or http://keycloak:8080/... but the API expects http://localhost:8180/.... Issuer strings must match exactly.
Fix: request tokens using the same host name that is configured in issuer-uri.
⚠️ Mistake: admin user still gets 403 on hasRole("ADMIN") Spring's default converter only reads scope; Keycloak roles in realm_access are ignored.
Fix: a custom converter like KeycloakRealmRoleConverter. Check the token's claims and /api/me's authorities.
⚠️ Mistake: sending the ID token to the API The ID token's audience is the client; APIs expect access tokens.
Fix: use access_token from the token response (or OAuth2AuthorizedClient.getAccessToken()).
⚠️ Mistake: GitHub user has email: null GitHub hides private emails from /user, and GitHub is not OIDC.
Fix: request scope user:email and call https://api.github.com/user/emails with the access token, or use a stable id (id) to identify users.
🔥 Mistake: client secret committed to Git or shipped in a SPA Anyone can impersonate your app.
Fix: environment variables / secret manager; public clients use PKCE and no secret. Rotate a leaked secret immediately.
⚠️ Mistake: using the password grant in a real app It teaches users to type their password into your app – the very thing OAuth2 exists to avoid – and it is removed in OAuth 2.1.
Fix: Authorization Code + PKCE for users, Client Credentials for machines.

7. Best practices

  • Don't build your own identity provider for serious systems – use Keycloak, Auth0, Okta, Entra ID or Spring Authorization Server.
  • Authorization Code + PKCE for every user-facing client; Client Credentials for service-to-service calls.
  • Resource servers: configure issuer-uri, validate aud, map roles/scopes explicitly, stay stateless.
  • Keep access tokens short-lived; let the client starter refresh them automatically.
  • Use stable identifiers (sub) to link external accounts to your own user records – emails and usernames can change.
  • Ask for the minimum scopes; check scopes in APIs (SCOPE_orders.read) for fine-grained access.
  • Secrets only in environment variables or a vault; separate client registrations per environment (dev/test/prod).
  • Test with oauth2Login(), oidcLogin() and jwt() – no real provider needed in CI. Use Testcontainers + Keycloak for full integration tests.

8. Key takeaways

  • OAuth2 = delegated authorization with tokens (the valet key); OIDC = OAuth2 + identity (ID token, openid scope, discovery).
  • Four roles: resource owner, client, authorization server, resource server.
  • Authorization Code flow: redirect to the server → user logs in there → code comes back → client swaps code for tokens on the back channel.
  • spring-boot-starter-oauth2-client + oauth2Login() + a registration in YAML = "Login with GitHub/Google/Keycloak".
  • spring-boot-starter-oauth2-resource-server + issuer-uri = an API that validates JWTs with the issuer's public keys (JWKS).
  • Scopes become SCOPE_x authorities; provider-specific roles need a custom JwtAuthenticationConverter.
  • Real client id/secret (or a local Keycloak) are needed to actually log in; tests use oauth2Login(), oidcLogin(), jwt().

@GetMapping("/courses-from-api")
public String callApi(@RegisteredOAuth2AuthorizedClient("keycloak") OAuth2AuthorizedClient client) {
    return RestClient.create("http://localhost:8081")
            .get().uri("/api/me")

            .retrieve()
            .body(String.class);

10. Interview questions

Q1. What is OAuth2? Explain its roles.

An authorization framework that lets a client app access resources on behalf of a user using tokens instead of passwords. Roles: resource owner (user), client (app), authorization server (issues tokens after authenticating the user and getting consent), resource server (API that accepts access tokens).

Q2. Difference between OAuth2 and OpenID Connect?

OAuth2 handles authorization (access tokens, scopes) but defines no standard way to identify the user. OIDC is a layer on OAuth2 that adds authentication: the openid scope, an ID token (JWT with sub, email…), a userinfo endpoint and discovery metadata.

Q3. Walk through the Authorization Code flow.

Client redirects the browser to the authorization endpoint with client_id, scope, redirect_uri, state (and PKCE challenge). User authenticates and consents. Server redirects back with a one-time code. Client verifies state and exchanges the code (plus secret or PKCE verifier) at the token endpoint over a back channel, receiving access/refresh (and ID) tokens.

Q4. What is PKCE and why is it needed?

Proof Key for Code Exchange: the client creates a random code_verifier, sends its hash (code_challenge) with the authorization request, and the original verifier with the token request. An attacker who intercepts the code cannot redeem it. Essential for public clients (SPAs, mobile) that cannot keep a secret; recommended for all in OAuth 2.1.

Q5. Which grant type for which scenario?

User logging in to web/SPA/mobile: Authorization Code + PKCE. Backend service calling another service: Client Credentials. Devices without a browser: Device Code. Renewing tokens: Refresh Token. Implicit and Password grants are deprecated.

Q6. How does a Spring resource server validate a JWT?

From issuer-uri it discovers the JWKS URI, downloads and caches the issuer's public keys, then for each request verifies the signature (matching kid), expiry/not-before, issuer (and audience if configured), and converts claims into a JwtAuthenticationToken with authorities (scopes as SCOPE_* by default).

Q7. Access token vs ID token vs refresh token?

Access token: presented to resource servers to access APIs (audience = API). ID token: tells the client who the user is (audience = client), never sent to APIs. Refresh token: long-lived, sent only to the authorization server to obtain new access tokens.

Q8. How do you map Keycloak roles to Spring Security authorities?

Provide a JwtAuthenticationConverter with a custom Converter<Jwt, Collection<GrantedAuthority>> that reads realm_access.roles (or resource_access.{client}.roles) and creates ROLE_* authorities, optionally keeping the default scope authorities.

Q9. What is the state parameter for?

A random value bound to the user's session, sent in the authorization request and checked on the callback. It prevents CSRF/login-injection attacks where an attacker makes the victim complete a login with the attacker's code. Spring generates and validates it automatically.

Q10. When would you still implement your own JWT (topic 49) instead of OAuth2?

For a single small application with its own user base, no third-party clients and no SSO need, a self-issued JWT can be simpler. As soon as you have multiple apps/services, external identity providers, SSO, MFA or compliance requirements, a dedicated authorization server with OAuth2/OIDC is the better, safer choice.
