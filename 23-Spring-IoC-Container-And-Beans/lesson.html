1. Why this matters

In Topic 22 we wrote every bean by hand with a @Bean method. That's fine for 2 beans. A real Spring Boot application has hundreds of beans — controllers, services, repositories, configuration objects. Nobody writes 300 @Bean methods.

Instead, you put one small annotation such as @Service on your class, and Spring finds it automatically, creates it and wires it. That is how 95% of beans are created in real projects. When you open any Spring Boot project at work, the first things you'll see are classes marked @RestController, @Service and @Repository.

Understanding the container also helps you read errors. Messages like "No qualifying bean of type 'BookService' available" or "No bean named 'x' available" are the most common Spring errors beginners hit. After this topic, you'll know exactly what they mean and how to fix them.

2. Real-life analogy

🏢 A company's HR department on the first day

Think of the Spring container as the HR department of a new office.

  • On opening day, HR walks through the building (component scanning) and looks for people wearing a badge: "Developer", "Accountant", "Receptionist". These badges are the stereotype annotations @Service, @Repository, @Controller, @Component. People without a badge are ignored.
  • Some workers are contractors from outside agencies (JDK or library classes like Clock). They don't wear our badge, so HR hires them through a written contract — a @Bean method.
  • HR writes each person in the staff register under a unique name (the bean name).
  • Before the office opens, HR makes sure everyone has what they need: the accountant gets a calculator, the developer gets a laptop (dependency injection).
  • When you need someone, you ask HR: "Send me the accountant" (getBean("accountant")) or "Send me whoever does accounting" (getBean(Accountant.class)).

A BeanFactory is a lazy HR clerk who only hires someone the moment you ask. An ApplicationContext is a proper HR department that hires and prepares everyone before the office opens — so problems are found on day one, not in the middle of a customer meeting.

3. Concepts step by step

3.1 Quick recap: container, bean, bean definition

WordMeaning
IoC containerThe Spring object that creates, wires and manages your objects.
BeanAn object created and managed by the container.
Bean definitionThe recipe for a bean: which class, which name, which scope, which dependencies. Spring first collects all recipes, then cooks (creates) the beans.
Configuration metadataYour instructions to Spring, given as annotations (modern), Java @Bean methods (modern) or XML (old).
💡 Recipe vs cake A bean definition is the recipe card. The bean is the cake. Spring reads all recipe cards first, then bakes the cakes in the right order (you can't put icing on a cake that's not baked yet — you can't inject a dependency that doesn't exist yet).

3.2 BeanFactory vs ApplicationContext

Spring has two main container interfaces:

  • BeanFactory — the basic container. It can create beans and inject dependencies. That's it. It creates a bean lazily: only when somebody first asks for it.
  • ApplicationContext — extends BeanFactory (it is-a BeanFactory) and adds lots of enterprise features. It creates all singleton beans eagerly, during startup.
FeatureBeanFactoryApplicationContext
Create & inject beans✅✅
When singletons are createdLazily (first getBean)Eagerly (at startup) → errors found immediately
Annotation processing (@Autowired, @PostConstruct…) set up automatically❌ (manual)✅
Events (publish / listen)❌✅
Reading property files, profiles (Environment)❌✅
Messages / internationalisation (i18n)❌✅
AOP proxies set up automatically❌ (manual)✅
Used in real applications?Rarely directly (it's the engine inside)Always — Spring Boot creates one for you

Our App.java proves the lazy vs eager difference:

App.java — demo 1DefaultListableBeanFactory factory = new DefaultListableBeanFactory();
factory.registerBeanDefinition("reportGenerator", new RootBeanDefinition(ReportGenerator.class));
System.out.println("BeanFactory: recipe registered. Object created yet? No (lazy).");
ReportGenerator r1 = factory.getBean(ReportGenerator.class);      // constructor runs HERE

try (AnnotationConfigApplicationContext ctx =
             new AnnotationConfigApplicationContext(ReportGenerator.class)) {   // constructor runs HERE
    ReportGenerator r2 = ctx.getBean(ReportGenerator.class);     // just returns the existing object
}
   BeanFactory: recipe registered. Object created yet? No (lazy).
   BeanFactory: calling getBean()...
      -> ReportGenerator constructor runs NOW
   ...
   ApplicationContext: starting...
      -> ReportGenerator constructor runs NOW
   ApplicationContext: started. Now calling getBean()...
  • DefaultListableBeanFactory is Spring's standard BeanFactory implementation. RootBeanDefinition is a bean recipe ("make an object of this class").
  • You can also pass a plain class (even without annotations) to new AnnotationConfigApplicationContext(...) — Spring registers it as a bean.
ℹ️ Why is "eager" a good thing? If a bean is broken (missing dependency, typo in configuration), an ApplicationContext fails at startup — when you're watching. With lazy creation it could fail hours later, the first time a customer clicks a rare button. Fail fast = safer. (You can make single beans lazy with @Lazy — Topic 25.)

3.4 Two ways to tell Spring about a bean

A) Annotate the class + component scanning 
@Service
public class BookService { ... }
Spring scans packages, finds the annotation, creates the bean. Used for your own classes.
B) @Bean method in a @Configuration class 
@Bean
public Clock clock() {
    return Clock.systemDefaultZone();
}
You write the creation code yourself. Used for classes you can't edit (JDK, libraries) or complex setup.

3.5 The stereotype annotations

A stereotype is a label that describes the role of a class. Spring has four main ones. They all live in package org.springframework.stereotype.

AnnotationRole (layer)Extra behaviourExample
@ComponentGeneric Spring-managed class — "a helper"None — the base of all othersFineCalculator, PasswordGenerator
@ServiceBusiness logic layerNone today (pure documentation of intent)BookService, OrderService
@RepositoryData access layer (database, files)Database exceptions get translated into Spring's DataAccessException family (when that feature is enabled — Spring Boot does it)BookRepository
@ControllerWeb / entry layerSpring MVC treats it as a web request handler (Topic 31). @RestController = @Controller + @ResponseBody.BookController

Look inside @Service (from Spring's source code) and you'll see it is itself annotated with @Component:

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Component                        // <-- this is why scanning finds @Service classes
public @interface Service {
    String value() default "";    // optional bean name
}

This is a meta-annotation (an annotation on an annotation — Topic 18). So @Service, @Repository, @Controller and even @Configuration are all "special kinds of @Component".

@Controller
handles input→ @Service
business rules→ @Repository
data access→ Database
💡 So why not use @Component everywhere? It would work, but the specific stereotypes (1) make your code self-documenting — you see the layer at a glance, (2) give extra behaviour where it exists (@Repository, @Controller), and (3) let tools and AOP target a layer ("log every method in every @Service"). Use the most specific one that fits.

3.6 @ComponentScan — how Spring finds annotated classes

Annotations alone do nothing. Someone must look for them. @ComponentScan on a configuration class tells Spring: "search this package and all its sub-packages".

config/AppConfig.java@Configuration
@ComponentScan(basePackages = "com.course.ioccontainer")   // scan our whole app
public class AppConfig { ... }

Spring then walks through every .class file under com/course/ioccontainer/:

com.course.ioccontainer
├── App.java                     (no annotation → ignored)
├── config/AppConfig.java        @Configuration → bean "appConfig"
├── controller/BookController    @Controller    → bean "bookController"
├── service/BookService          @Service       → bean "bookService"
├── service/FineCalculator       @Component("lateFeeCalculator") → bean "lateFeeCalculator"
├── repository/BookRepository    @Repository    → bean "bookRepository"
├── model/Book                   (record, no annotation → ignored)
└── legacy/ReportGenerator       (no annotation → ignored)
How to write itWhat gets scanned
@ComponentScan (no attributes)The package of the configuration class itself (here com.course.ioccontainer.config) and below. ⚠️ That would miss our services, because they're not under config!
@ComponentScan("com.course.ioccontainer")That package and all sub-packages. (value and basePackages mean the same.)
@ComponentScan(basePackages = {"com.a", "com.b"})Several packages.
@ComponentScan(basePackageClasses = App.class)The package of App — type-safe, survives package renames.
ℹ️ Spring Boot preview @SpringBootApplication includes @ComponentScan with no attributes. That's why in Spring Boot the main class must sit in the top-level package (e.g. com.course.shop) — everything below it gets scanned. Put a class outside that package and Spring won't find it. You'll see this again in Topic 28.

You can also include or exclude classes with filters, e.g. @ComponentScan(basePackages = "com.shop", excludeFilters = @ComponentScan.Filter(type = FilterType.ANNOTATION, classes = Controller.class)). You'll rarely need this.

3.7 @Configuration + @Bean — and when to use which

In our library, BookService needs a java.time.Clock (to know today's date) and FineCalculator needs a java.text.NumberFormat (to print money). These are JDK classes — we can't open them and add @Component. So we use @Bean methods:

config/AppConfig.java@Bean
public Clock clock() {
    return Clock.fixed(Instant.parse("2026-01-15T10:00:00Z"), ZoneOffset.UTC);
}

@Bean(name = {"moneyFormat", "currencyFormat"})
public NumberFormat usDollarFormat() {
    return NumberFormat.getCurrencyInstance(Locale.US);
}
Use @Component / @Service / … whenUse @Bean when
It's your own class and you can add an annotation.The class comes from the JDK or a library (Clock, ObjectMapper, DataSource, RestClient…).
Creating it is simple: "call the constructor and inject".Creating it needs setup code: builder calls, settings, choosing between implementations with an if.
One bean per class.You need several beans of the same class with different settings (e.g. two RestClients for two APIs).
Most of your app: controllers, services, repositories."Infrastructure" objects; configuration of third-party tools.
💡 Why a fixed clock? Injecting a Clock instead of calling LocalDate.now() directly is a professional trick: in production you inject Clock.systemDefaultZone(), in tests (and in this demo) a fixed clock — so "today" is always the same and the output is predictable. It's DI making testing easy again.

3.8 Bean names

Every bean has a unique name (also called its id) inside the container. Here are the rules:

How the bean is definedDefault nameCustom name
@Service public class BookServiceClass name with lower-case first letter: bookService@Service("books")
@Component public class FineCalculatorfineCalculator@Component("lateFeeCalculator") ← we did this
@Bean public Clock clock()The method name: clock@Bean("systemClock") or @Bean(name = "systemClock")
@Bean(name = {"moneyFormat", "currencyFormat"})—First name = real name, the rest are aliases (extra names for the same bean)
ℹ️ A small naming surprise If a class name starts with two capital letters, Spring keeps it as is: class URLParser → bean URLParser (not uRLParser). This follows the JavaBeans naming rules.
⚠️ Names must be unique Two scanned classes in different packages, both called ReportService, would both want the name reportService. Spring stops with ConflictingBeanDefinitionException. Fix: give one a custom name, e.g. @Service("salesReportService").

Typical errors:

  • NoSuchBeanDefinitionException: No bean named 'paymentService' available — no bean with that name (typo? not scanned? forgot the annotation?).
  • NoSuchBeanDefinitionException: No qualifying bean of type '...' available — no bean of that type.
  • NoUniqueBeanDefinitionException: expected single matching bean but found 2 — more than one candidate (Topic 24 fixes this).
⚠️ Reminder getBean is for main() methods and demos. Inside your app, use injection (constructor parameters). Calling getBean from business code hides dependencies — the very problem DI solves.

3.10 How the container starts (step by step)

1. Read config
AppConfig→ 2. Scan packages
collect bean definitions→ 3. Post-process definitions
(placeholders, @Configuration)→ 4. Create singletons
dependencies first→ 5. Inject + initialise→ 6. READY→ 7. close() → destroy
  1. Read configuration — new AnnotationConfigApplicationContext(AppConfig.class) registers AppConfig.
  2. Collect bean definitions — Spring processes @ComponentScan (finds 5 annotated classes) and the @Bean methods (2 more). Still no objects — only recipes.
  3. Post-process definitions — special Spring helpers ("BeanFactoryPostProcessors") can adjust the recipes, e.g. fill in ${...} placeholders (Topic 24).
  4. Create singleton beans — for each recipe, Spring builds the object. If a constructor needs other beans, Spring creates those first (depth-first).
  5. Inject and initialise — dependencies are set, then init callbacks run (Topic 25).
  6. Ready — the constructor call returns; you can use the context.
  7. Close — context.close() (or the end of try-with-resources) destroys beans and runs cleanup callbacks.

Our real output shows step 4 nicely:

=== DEMO 2: Starting the container (scan + @Bean methods) ===
   [container] creating BookRepository
   [container] @Bean method usDollarFormat() called
   [container] creating FineCalculator (bean name: lateFeeCalculator)
   [container] @Bean method clock() called
   [container] creating BookService (got its 3 dependencies)
   [container] creating BookController
   Container is READY.

Spring went to create bookController first (after appConfig, it's the first class the scanner found — packages are scanned in alphabetical order), but its constructor needs BookService. BookService needs BookRepository, FineCalculator and Clock; FineCalculator needs the NumberFormat. So Spring creates the "leaves" first and works its way back up. You never had to think about the order — that's the container's job.

3.11 Historical note: XML configuration

Before annotations (Spring 1.x and 2.x), all beans were declared in XML files. You may still see this in old company projects, so recognise it — but don't use it for new code. Here is roughly what our library would look like (reference only, not in the project):

beans.xml (legacy style — for reference only)<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
           https://www.springframework.org/schema/beans/spring-beans.xsd">

    <bean id="bookRepository" class="com.course.ioccontainer.repository.BookRepository"/>

    <bean id="bookService" class="com.course.ioccontainer.service.BookService">
        <constructor-arg ref="bookRepository"/>
        <constructor-arg ref="lateFeeCalculator"/>
        <constructor-arg ref="clock"/>
    </bean>
</beans>
// loading it (legacy):
ApplicationContext ctx = new ClassPathXmlApplicationContext("beans.xml");

Same ideas (id = bean name, ref = inject another bean), just more typing and no compiler help — a typo in a class name is found only at runtime. Annotations and Java config won.

3.12 Why is the appConfig bean called AppConfig$$SpringCGLIB$$0?

In demo 3 you'll notice the type of appConfig is printed as AppConfig$$SpringCGLIB$$0. Spring created a subclass of your configuration class at runtime (a "proxy") so that calling one @Bean method from another still returns the same singleton. Don't worry about it now — Topic 26 explains it with a demo.

4.1 BookService — a bean with three dependencies

service/BookService.java@Service
public class BookService {

    private final BookRepository bookRepository;   // from scanning (@Repository)
    private final FineCalculator fineCalculator;   // from scanning (@Component)
    private final Clock clock;                     // from a @Bean method

    public BookService(BookRepository bookRepository, FineCalculator fineCalculator, Clock clock) {
        this.bookRepository = bookRepository;
        this.fineCalculator = fineCalculator;
        this.clock = clock;
    }

    public String borrow(String isbn) {
        return bookRepository.findByIsbn(isbn)
                .map(book -> book.available()
                        ? "Borrowed '" + book.title() + "'. Please return by " + LocalDate.now(clock).plusDays(LOAN_DAYS)
                        : "Sorry, '" + book.title() + "' is already borrowed.")
                .orElse("No book with ISBN " + isbn);
    }
}
  • The class has exactly one constructor, so Spring uses it automatically and fills each parameter with a matching bean (by type). No extra annotation is needed — Topic 24 explains @Autowired.
  • Spring doesn't care how a dependency was defined (scanned or @Bean). A bean is a bean.
  • findByIsbn returns an Optional<Book> (Topic 14) — map + orElse handle the "not found" case without null.
  • LocalDate.now(clock) asks the injected clock for "today" — 2026-01-15 in this demo, so the due date is 2026-01-29.

4.2 FineCalculator — custom name

service/FineCalculator.java@Component("lateFeeCalculator")
public class FineCalculator {
    private final NumberFormat moneyFormat;

    public FineCalculator(NumberFormat moneyFormat) {   // the @Bean from AppConfig
        this.moneyFormat = moneyFormat;
    }

    public String fineFor(long daysLate) {
        return moneyFormat.format(daysLate * FINE_PER_DAY);   // 6 days -> "$3.00"
    }
}

6. Common mistakes

⚠️ Mistake: class is outside the scanned package You create com.course.util.TaxCalculator with @Component, but scanning covers only com.course.ioccontainer. Result: No qualifying bean of type 'TaxCalculator' available.
Fix: move the class under the scanned base package (best), or add its package to @ComponentScan.
⚠️ Mistake: @ComponentScan with no package on a config class in a sub-package With no attributes, scanning starts at the configuration class's own package. Our AppConfig is in ...ioccontainer.config — a bare @ComponentScan would find nothing but itself.
Fix: give the base package explicitly, or put the config class in the top-level package.
⚠️ Mistake: annotating an interface instead of the class @Service public interface PaymentService does not create a bean — Spring can't instantiate an interface.
Fix: put @Service on the implementing class (CardPaymentService implements PaymentService).
⚠️ Mistake: forgetting @Configuration on a class with @ComponentScan/@Bean If you pass the class directly to new AnnotationConfigApplicationContext(...) it still mostly works ("lite mode"), but in scanned packages a class without @Configuration is ignored and its @Bean methods are never called.
Fix: always mark configuration classes with @Configuration.
⚠️ Mistake: making data classes into beans Putting @Component on Book or Customer. There is one singleton per bean — but you need thousands of different books!
Fix: beans are the workers (services, repositories, controllers). Data objects (entities, DTOs, records) are created with new or by frameworks like JPA.
🛑 Mistake: misspelled bean name in getBean("...") getBean("BookService") (capital B) → No bean named 'BookService' available. Default names start with a lower-case letter.
Fix: prefer getBean(BookService.class) — the compiler checks class names, not strings.

7. Best practices

  • Use the most specific stereotype: @Service for business logic, @Repository for data access, @Controller/@RestController for web; @Component for other helpers.
  • Use component scanning for your own classes, @Bean for third-party classes and objects that need setup code.
  • Keep one root package and put your configuration/main class at the top, so default scanning covers everything (the Spring Boot convention).
  • Rely on default bean names; add custom names only when you need them (conflicts, multiple beans of the same type).
  • Prefer getBean(Type.class) over string names — and avoid getBean inside application code altogether.
  • Keep beans stateless (no per-user data in fields). A singleton bean is shared by all users and threads (Topic 17!) — Topic 25 explains why this matters.
  • Inject time (Clock) and other "environment" things instead of calling static methods — it makes testing simple.
  • Don't write XML configuration for new code; just be able to read it.

8. Key takeaways

  • BeanFactory is the basic, lazy container; ApplicationContext extends it with events, properties, AOP and eager singleton creation — always use ApplicationContext.
  • AnnotationConfigApplicationContext reads @Configuration and @Component classes.
  • @Component is the base stereotype; @Service, @Repository, @Controller are specialised versions that describe the layer.
  • @ComponentScan finds annotated classes in a package and all its sub-packages.
  • @Bean methods create beans from classes you can't annotate or that need setup code.
  • Default bean names: class name with lower-case first letter, or the @Bean method name. Custom names and aliases are possible.
  • At startup Spring collects bean definitions (recipes), then creates beans dependencies-first, injects them and initialises them.
  • XML configuration is legacy — recognise it, don't write it.

10. Interview questions

Q1. What is the difference between BeanFactory and ApplicationContext?

BeanFactory is the root container interface: it creates beans and injects dependencies, and creates singletons lazily. ApplicationContext extends it and adds enterprise features: eager singleton creation (fail fast), automatic registration of annotation processors and BeanPostProcessors, event publishing, Environment/property sources/profiles, i18n messages and resource loading. In practice you always use an ApplicationContext.

Q2. What are stereotype annotations? Is there a difference between @Component, @Service, @Repository and @Controller?

They mark classes for component scanning and describe their role. @Service, @Repository and @Controller are meta-annotated with @Component, so all are detected by scanning. Differences: @Repository enables persistence exception translation into DataAccessException; @Controller is recognised by Spring MVC as a request handler; @Service currently adds no behaviour but documents the business layer.

Q3. What does @ComponentScan do? What is scanned if no package is given?

It tells Spring to search packages for classes annotated with @Component (or its specialisations) and register them as beans. Without attributes it scans the package of the class carrying the annotation and all sub-packages — which is why a Spring Boot main class goes in the root package.

Q4. When would you use @Bean instead of @Component?

When the class is from a library or the JDK and can't be annotated; when creation needs custom logic (builders, configuration, conditionals); or when you need several differently configured beans of the same class. Use @Component-family annotations for your own simple classes.

Q5. How are default bean names generated?

For scanned components: the simple class name with the first letter in lower case (BookService → bookService), except when the first two letters are upper case (URLParser stays URLParser). For @Bean methods: the method name. Both can be overridden: @Service("name"), @Bean("name"); @Bean also accepts several names (aliases).

Q6. Describe what happens when an ApplicationContext starts.

It loads configuration, scans components and registers bean definitions; runs BeanFactoryPostProcessors (e.g. placeholder resolution, configuration class processing); registers BeanPostProcessors; instantiates all non-lazy singletons, resolving dependencies first and injecting them; runs initialisation callbacks and post-processors (which can create proxies); publishes a "context refreshed" event; and is ready. On close it calls destroy callbacks in reverse order.

Q7. What is a bean definition?

The metadata (recipe) Spring keeps for each bean: class, name and aliases, scope, lazy flag, constructor arguments/dependencies, init and destroy methods, etc. The container builds bean instances from these definitions. Represented in code by the BeanDefinition interface.

Q8. What exceptions can getBean throw?

NoSuchBeanDefinitionException if no bean matches the name/type; NoUniqueBeanDefinitionException (a subclass) if a type lookup finds several candidates; BeanNotOfRequiredTypeException if a bean exists under the name but has a different type; BeansException subclasses if creating the bean fails.

Q9. Is XML configuration still used?

It's supported for backward compatibility and appears in legacy projects, but new projects use annotations and Java configuration (and Spring Boot auto-configuration). Java config is type-safe, refactor-friendly and checked by the compiler.
