7. Encapsulation & Inheritance

Protect your objects' data so nobody can break the rules, and re-use code by building new classes on top of existing ones — the right way.

1. Why this matters

At the end of Topic 6 our BankAccount had a serious problem: any code anywhere could write account.balance = 1000000;. No deposit, no check, no record. In a real bank that is a disaster. Encapsulation fixes this: the class keeps its data private and only allows changes through methods that follow the rules.

The second problem is repetition. A company has managers, developers, testers and interns. All of them have a name, a salary, and can get a raise. Copy-pasting those fields and methods into four classes means four places to fix every bug. Inheritance lets you write the common part once (Employee) and let each specific class extend it.

Where you will see this at work:

  • Every Spring Boot entity (a class saved to a database, Topic 38) uses private fields with getters and setters.
  • Spring and Java libraries are full of class hierarchies: your exceptions extends RuntimeException (Topic 10), your filters extends OncePerRequestFilter (Topic 49).
  • "HAS-A" (composition) is exactly how Spring wires your application: a OrderService has a OrderRepository. That idea becomes dependency injection in Topic 22.

2. Real-life analogy

🏧 Encapsulation = an ATM The cash inside an ATM is locked away (private). You cannot open the machine and grab notes. You can only use the buttons — Withdraw, Deposit, Check balance (public methods). Each button checks the rules first: correct PIN? enough balance? within the daily limit? The bank can completely change the machine's insides without changing the buttons you use.
👨‍👩‍👧 Inheritance = family traits (with your own twist) A child inherits traits from a parent — eye colour, surname — without doing anything. The child can also have their own skills (plays guitar) and can do some things their own way (the parent cooks biryani one way, the child cooks it differently — that's overriding). And before a child can exist, the parent must exist first — that's why the parent's constructor always runs first.
🚗 HAS-A = a car and its engine A car is a vehicle (inheritance). A car has an engine (composition). Mechanics can swap the engine without building a new car.

3. Concepts step by step

3.1 Encapsulation: hide the data, expose safe methods

Encapsulation means wrapping data and the code that works on that data together in one class, and hiding the data from the outside world. Recipe:

  1. Make fields private — visible only inside the class.
  2. Provide public methods for what outsiders are allowed to do.
  3. Put the rules (validation) inside those methods.
class BankAccount {
    private double balance;                 // hidden

    public double getBalance() {            // read access
        return balance;
    }

    public void deposit(double amount) {    // controlled write access
        if (amount <= 0) {
            System.out.println("Rejected: deposit amount must be positive");
            return;
        }
        balance += amount;
    }
}

account.balance = 1_000_000;   // ❌ compile error: balance has private access in BankAccount
account.deposit(500);          // ✅ goes through the rules

Getters and setters

The Java convention (also called the JavaBean convention) for accessor methods:

FieldGetter (read)Setter (write)
private String holderName;public String getHolderName()public void setHolderName(String holderName)
private double balance;public double getBalance()(none on purpose — use deposit/withdraw)
private boolean active;public boolean isActive()public void setActive(boolean active)
ℹ️ Why the naming matters Frameworks rely on it! In Spring Boot, the JSON library Jackson turns getHolderName() into a JSON field "holderName", and JPA/Hibernate uses getters/setters to read and write database columns. Wrong names = missing fields. VS Code can generate them: right-click → Source Action… → Generate Getters and Setters.

A setter with validation

public void setHolderName(String holderName) {
    if (holderName == null || holderName.isBlank()) {
        System.out.println("Rejected: holder name cannot be blank");
        return;                                // keep the old, valid value
    }
    this.holderName = holderName.strip();
}

In real code you would usually throw an exception instead of printing (Topic 10): throw new IllegalArgumentException("Name required");

Read-only fields

Some values should never change after creation — an account number, an order id. Make the field final (can be assigned only once, in the constructor) and give it a getter but no setter.

private final String accountNumber;      // set once in the constructor, never again

Benefits of encapsulation

  • Data is always valid — the class enforces its own rules (no negative balance).
  • Freedom to change the inside — store the balance in paise as a long tomorrow; callers still call getBalance().
  • Easier debugging — the balance can only change in two methods, so you know where to look.
  • Security — sensitive data (like a password hash) can be kept without a getter at all.
💡 Behaviour methods beat dumb setters setBalance(balance + 500) lets callers do the maths (and make mistakes). deposit(500) keeps the logic inside the class. Don't blindly generate a setter for every field — ask "should outsiders really change this?"

3.2 Inheritance: extends

Inheritance lets a new class (the child, subclass, derived class) be built on an existing class (the parent, superclass, base class). The child automatically gets the parent's fields and methods and can add more.

class Employee {                       // parent
    private String name;
    private double salary;
    public void giveRaise(double percent) { ... }
    public void printBasicInfo() { ... }
}

class Manager extends Employee {       // child: Manager IS-A Employee
    private int teamSize;              // extra field
    public void conductMeeting() { ... }   // extra method
}

What the child gets and doesn't get:

Parent memberInherited by the child?
public and protected fields/methodsYes — usable directly
Package-private (no modifier) membersYes, if the child is in the same package (Topic 9)
private fields/methodsThey exist inside the object, but the child cannot access them directly — use the parent's public getters
ConstructorsNo — the child must write its own and call the parent's with super(...)

The IS-A test: inheritance is correct only if the sentence "Child is a Parent" is true. "A Manager is an Employee" ✅. "A SavingsAccount is an Account" ✅. "A Car is an Engine" ❌.

3.3 super and the constructor call order

Before a child object can be built, its parent part must be built. So constructors run from the top of the family tree down:

new ElectricCar(...)→ 1. Vehicle constructor→ 2. Car constructor→ 3. ElectricCar constructor

(Strictly speaking, Object's constructor runs even before Vehicle's.)

The child chooses which parent constructor to call with super(...):

class Car extends Vehicle {
    Car(String brand, int seats) {
        super(brand);          // MUST be the first line: build the Vehicle part first
        this.seats = seats;    // then the Car part
    }
}
  • If you don't write super(...), Java silently inserts super(); (call the parent's no-argument constructor).
  • If the parent has no no-arg constructor, you must call super(...) with arguments, otherwise: compile error "constructor Vehicle in class Vehicle cannot be applied to given types".
  • A constructor can begin with this(...) or super(...), never both.

The word super has two uses (just like this in Topic 6):

SyntaxMeaning
super(...)Call a parent constructor (first line of a constructor only)
super.method()Call the parent's version of a method — very common inside an overriding method
super.fieldThe parent's field (only needed if the child has a field with the same name — avoid that)

3.4 Method overriding

Overriding = a child class provides its own implementation of a method it inherited. Same name, same parameters, same (or compatible) return type.

class Account {
    double calculateInterest() { return 0; }
}

class SavingsAccount extends Account {
    @Override
    double calculateInterest() {           // SavingsAccount's own rule
        return balance * 0.04;
    }
}

@Override is an annotation that asks the compiler to check: "is there really a parent method with this exact signature?" If you misspell it (calculateIntrest) or change a parameter type, you get a compile error instead of a silent bug. Always use it.

Using the parent's version and adding to it:

@Override
String describe() {
    return super.describe() + " (Savings, 4% interest)";
}

Which version runs? The one belonging to the real object, not the variable type:

Account someAccount = new SavingsAccount("S-2", 2_000);
someAccount.describe();     // runs SavingsAccount.describe()

This is called runtime polymorphism — the star of Topic 8.

Rules for overriding

RuleExample
Same method name and parameter listwithdraw(double) overrides withdraw(double); withdraw(int) would be an overload
Return type: same, or a subclass of it ("covariant return")Parent returns Account, child may return SavingsAccount
Cannot make access more restrictiveParent public → child cannot be private
private methods are not inherited, so they can't be overridden
final methods cannot be overriddenfinal void audit() (Topic 9)
static methods are not overridden (a same-named static method in the child just hides the parent's)
Cannot throw new/broader checked exceptions (Topic 10)

Overriding vs overloading — don't mix them up

OverloadingOverriding
WhereSame class (or parent + child)Parent and child classes
Method nameSameSame
ParametersDifferentSame

@Override?NoYes

3.6 The Object class — the root of everything

If a class doesn't say extends, Java makes it extend java.lang.Object. So every class is ultimately a child of Object, and every object has these methods:

MethodDefault behaviourUsually override?
toString()ClassName@hexHashYes — readable text
equals(Object o)Same as ==Yes, for value equality
hashCode()A number based on the object identityYes, together with equals
getClass()Returns the runtime class (EBook)No (it's final)
clone(), wait(), notify(), notifyAll()Copying and thread coordination (advanced)Rarely

Because of this, an Object variable can hold any object: Object anything = new EBook(...);

3.7 The protected modifier

You know private (only this class) and public (everyone). protected sits in between: visible to subclasses (even in other packages) and to classes in the same package.

ModifierSame classSame packageSubclass (other package)Everyone
private✅❌❌❌
(none) package-private✅✅❌❌
protected✅✅✅❌

Packages and this table are covered in depth in Topic 9. For now: prefer private + getters; use protected when you deliberately want subclasses to work with a field or method directly.

3.8 IS-A vs HAS-A: composition over inheritance

IS-A (inheritance)HAS-A (composition)
Howclass Truck extends MotorVehicleclass SportsCar { private Engine engine; }
Sentence test"A truck is a motor vehicle""A car has an engine"
CouplingTight — child depends on parent's internalsLoose — only uses the part's public methods
Change at runtime?No — the parent is fixed at compile timeYes — swap the part (replaceEngine(...))
NumberOnly one parent classAs many parts as you like

"Favour composition over inheritance" is one of the most quoted design rules (from the famous Design Patterns book and Effective Java). Inheritance is powerful but rigid: a change in the parent can break every child. Composition builds objects from small, replaceable parts. Use inheritance only when the IS-A test is clearly true and the child really is a specialised version of the parent.

Example06_CompositionVsInheritance.java (part)class SportsCar {
    private Engine engine;                 // HAS-A
    private final MusicSystem musicSystem; // HAS-A

    SportsCar(String model, Engine engine, MusicSystem musicSystem) {
        this.engine = engine;              // parts are handed IN from outside
        this.musicSystem = musicSystem;
    }

    void start() {
        engine.ignite();                   // delegation: let the part do the work
    }
}
ℹ️ Spring preview Notice that SportsCar does not create its own engine with new — the engine is given to it through the constructor. This is exactly what Spring does with your services: OrderService(OrderRepository repo). Spring builds the parts and hands them in. This is called constructor injection (Topics 22–24). In the next topic you'll make it even more flexible with interfaces.

6. Common mistakes

⚠️ Mistake: public fields "because it's easier" public double balance; lets anyone set any value; you lose all control.
Fix: private fields + methods that enforce the rules.
⚠️ Mistake: getters/setters for everything, with no checks A setter that just does this.x = x for every field is barely better than a public field.
Fix: only add setters that make sense, validate inside them, and prefer behaviour methods (deposit, cancel).
❌ Mistake: forgetting super(...) when the parent has no no-arg constructor Error: constructor Employee in class Employee cannot be applied to given types; required: String,double; found: no arguments.
Fix: make the first line of the child constructor super(name, salary);
⚠️ Mistake: super(...) not as the first statement "call to super must be first statement in constructor".
Fix: move it to the top.
⚠️ Mistake: "overriding" with a typo or different parameters double calculateIntrest() or withdraw(int amount) silently creates a new method; the parent's version still runs.
Fix: always write @Override — the compiler will catch it ("method does not override or implement a method from a supertype").
⚠️ Mistake: trying to access a parent's private field from the child "name has private access in Employee".
Fix: use the parent's getter, or (if appropriate) make it protected.
⚠️ Mistake: using inheritance just to re-use code class Car extends Engine because Car needs ignite(). It fails the IS-A test.
Fix: use composition: give Car an Engine field and delegate.
⚠️ Mistake: reducing visibility when overriding Parent: public String toString(); child: String toString() → "attempting to assign weaker access privileges".
Fix: keep the same (or wider) access, e.g. public.

7. Best practices

  • Make every field private by default. Open access only when you have a reason.
  • Make fields final when they should never change (ids, creation dates). Immutable data = fewer bugs.
  • Validate in constructors and setters so an object can never be in an invalid state. Throw IllegalArgumentException for bad input (Topic 10).
  • Follow the JavaBean naming (getX, isX, setX) — Spring, Jackson and JPA depend on it.
  • Always use @Override.
  • Inherit only for true IS-A relationships and keep hierarchies shallow (2–3 levels). Deep trees become hard to understand.
  • Favour composition over inheritance — build from parts, pass the parts in through the constructor (this is dependency injection in Spring).
  • Don't declare a field with the same name as a parent field (field hiding) — it confuses everyone.
  • If a class isn't designed to be extended, consider making it final (Topic 9). Effective Java: "Design and document for inheritance or else prohibit it."

8. Key takeaways

  • Encapsulation = private data + public methods that enforce rules. Callers can't break your object.
  • Getters/setters follow getX/isX/setX; a field with no setter (and final) is read-only.
  • Inheritance (extends) lets a child reuse and extend a parent. Use it only if "child IS-A parent" is true.
  • Private members and constructors are not accessible/inherited by the child.
  • Parent constructors run first; super(...) picks one; otherwise super() is inserted automatically.
  • Overriding = same signature in the child; the real object decides which version runs. @Override protects you from typos.
  • Java allows single, multilevel and hierarchical inheritance of classes, but not multiple (diamond problem).
  • Every class extends Object; protected = subclasses + same package.
  • HAS-A (composition) is usually more flexible than IS-A — and it's the idea behind Spring's dependency injection.

class Processor {
    private final String model;
    private final int cores;
    Processor(String model, int cores) { this.model = model; this.cores = cores; }
    String describe() { return model + " (" + cores + " cores)"; }
}

class Memory {
    private final int sizeGb;
    Memory(int sizeGb) { this.sizeGb = sizeGb; }
    int getSizeGb() { return sizeGb; }
}

class Computer {
    private final Processor processor;   // HAS-A
    private Memory memory;               // HAS-A (replaceable)

    Computer(Processor processor, Memory memory) {
        this.processor = processor;
        this.memory = memory;
    }

    void upgradeMemory(Memory newMemory) {
        this.memory = newMemory;
    }

    void printSpecs() {
        System.out.println(processor.describe() + ", " + memory.getSizeGb() + " GB RAM");
    }
}
Challenge

6. Spot the design problem. A teammate wrote class ShoppingCart extends ArrayList<Product> "so the cart gets add/remove for free". Explain two problems and sketch a better design.

Hint / solution

Problems: (1) A cart is not a list — it fails the IS-A test. (2) All list methods become part of the cart's public API: anyone can call cart.clear(), cart.set(0, null) or add a product without your stock/price checks — encapsulation is broken. (3) You're tied to ArrayList forever.

Better: composition — the cart has a private list and exposes only what makes sense:

class ShoppingCart {
    private final List<Product> items = new ArrayList<>();

    public void addProduct(Product p) {
        if (p == null) {
            throw new IllegalArgumentException("Product required");
        }
        items.add(p);
    }

    public int itemCount() {
        return items.size();
    }
}

10. Interview questions

Q1. What is encapsulation and what are its benefits?

Bundling data and the methods that operate on it in one class while hiding the data (private) and exposing controlled access through methods. Benefits: data integrity through validation, freedom to change the internal implementation without affecting callers, easier maintenance and debugging, and better security.

Q2. What is inheritance? What is not inherited?

A mechanism where a class (subclass) acquires the fields and methods of another class (superclass) using extends, modelling an IS-A relationship and enabling reuse. Constructors are not inherited; private members are not accessible in the subclass; static methods are not overridden (only hidden).

Q3. Why doesn't Java support multiple inheritance of classes?

To avoid ambiguity — the diamond problem: if two parents provide the same method, which one does the child inherit? It also keeps the object model and constructor chaining simple. Java allows a class to implement multiple interfaces instead (Topic 8).

Q4. In what order are constructors called in an inheritance chain?

From the top down: Object → grandparent → parent → child. Each constructor's first statement is a call to super(...) (explicit or the implicit no-arg super()), so the parent part is fully initialized before the child's constructor body runs.

Q5. Difference between this and super?

this refers to the current object (this.field, this.method(), this(...) for another constructor of the same class). super refers to the parent part of the current object (super.method() for the parent's version, super(...) for a parent constructor). Both this(...) and super(...) must be the first statement, so a constructor can use only one of them.

Q6. Method overloading vs method overriding?

Overloading: same name, different parameter lists, resolved at compile time, usually in the same class. Overriding: same signature in a subclass, replaces inherited behaviour, resolved at runtime based on the actual object (dynamic dispatch), marked with @Override.

Q7. Can we override a static, private or final method?

No. private methods aren't visible to the subclass; final methods are explicitly forbidden from being overridden; static methods belong to the class — a same-signature static method in the subclass hides the parent's, it does not override it.

Q8. What is the purpose of @Override?

It tells the compiler the method is intended to override a superclass (or interface) method. If no such method exists — typo, wrong parameters — compilation fails. It also documents intent for readers.

Q9. What is the difference between IS-A and HAS-A? Why "composition over inheritance"?

IS-A is inheritance (Truck extends Vehicle); HAS-A is composition (a Car has an Engine field). Composition is preferred because it is loosely coupled, allows changing parts at runtime, avoids fragile deep hierarchies, isn't limited to one parent, and doesn't expose unwanted inherited methods.

Q10. What is the Object class? Name some of its methods.

java.lang.Object is the root superclass of every Java class. Methods: toString(), equals(), hashCode(), getClass(), clone(), wait(), notify(), notifyAll() (and the deprecated finalize()).
