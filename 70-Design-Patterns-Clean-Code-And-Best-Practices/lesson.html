1. Why this matters

Code is written once but read and changed hundreds of times — by your teammates, by future-you in six months, by the new joiner. In real companies, most of the cost of software is not writing it, it's changing it: new features, bug fixes, new rules from the business.

Two projects can do exactly the same thing today. In one, adding "student discount" takes 10 minutes and one new class. In the other, it takes 3 days, touches 15 files, and breaks payments in production. The difference is design: principles, patterns and clean code.

Where you will see it at work:

  • Code reviews: "This class does too much (SRP)", "Use a strategy instead of this switch", "Magic number — extract a constant".
  • Interviews: "Explain SOLID with examples", "Which design patterns does Spring use?", "How does @Transactional work?" (answer: Proxy!). These are among the most common Java interview questions.
  • Reading Spring itself: once you know Template Method, Proxy and Strategy, Spring stops being "magic" — it's just well-known patterns.
ℹ️ You've already been using all of this Interfaces (topic 8), constructor injection (24), layered architecture (33), events (52), AOP proxies (27), JdbcTemplate (37), builders like RestClient.builder() (45)… This lesson gives those ideas their official names and shows how they fit together.

2. Real-life analogy

🏗️ Building codes, standard designs, and a tidy workshop
  • SOLID principles are like building codes: "every room needs its own exit", "electrical wiring must not run through the water pipes". They don't tell you what house to build; they keep any house safe to live in and easy to renovate.
  • Design patterns are like standard architectural solutions: a staircase, a load-bearing arch, a two-way light switch. Nobody re-invents the staircase; you say "put a spiral staircase here" and every builder knows what you mean. Patterns give developers a shared vocabulary: "use a Strategy" is one sentence instead of a 20-minute explanation.
  • Clean code is the tidy workshop: tools labelled, each in its place. You can work fast because you don't search for anything.

3.3 S — Single Responsibility Principle

"One reason to change" means: one group of people would ask you to change it. The tax rule changes (finance team), the invoice layout changes (design team), the storage changes (ops team) — three reasons, so three classes.

solid/srp/SrpDemo.java — BADclass InvoiceManager {
    String createAndSave(String customer, List<BigDecimal> prices) {
        BigDecimal total = ...;                      // job 1: calculate (+ tax rule)
        String text = "INVOICE for " + customer ...; // job 2: format
        // job 3: save to a file
    }
}
solid/srp/SrpDemo.java — GOODclass InvoiceCalculator {
    private static final BigDecimal TAX_MULTIPLIER = new BigDecimal("1.18");
    BigDecimal totalWithTax(List<BigDecimal> prices) {
        BigDecimal net = prices.stream().reduce(BigDecimal.ZERO, BigDecimal::add);
        return net.multiply(TAX_MULTIPLIER).setScale(2);
    }
}
class InvoiceFormatter { String format(String customer, BigDecimal total) { ... } }
class InvoiceStore     { void save(String invoiceText) { ... } }

Spring link: layered architecture (topic 33) is SRP at the architecture level: the controller handles HTTP, the service handles business rules, the repository handles the database. A 900-line OrderService that sends emails, builds PDFs and calls the payment API is the most common SRP violation in real projects.

💡 Quick SRP test Try to describe the class in one sentence without the word "and". "It calculates invoice totals" ✅. "It calculates totals and prints and saves" ❌.

3.4 O — Open/Closed Principle

solid/ocp/OcpDemo.java — BADstatic BigDecimal priceBad(String customerType, BigDecimal amount) {
    if (customerType.equals("REGULAR")) {
        return amount;
    } else if (customerType.equals("PREMIUM")) {
        return amount.multiply(new BigDecimal("0.90"));
    }
    // next month: else if ("STUDENT") ... and again ... and again
    return amount;
}
solid/ocp/OcpDemo.java — GOODinterface Discount {
    String name();
    BigDecimal apply(BigDecimal amount);
}
class PremiumDiscount implements Discount { ... 0.90 ... }
class StudentDiscount implements Discount { ... 0.85 ... }   // NEW class, nothing else edited

class Checkout {                         // closed for modification
    BigDecimal total(BigDecimal amount, Discount discount) {
        return discount.apply(amount).setScale(2, RoundingMode.HALF_UP);
    }
}

Spring link: Spring Boot itself is "open for extension": add a @Bean of your own and auto-configuration backs off (@ConditionalOnMissingBean, topic 26). Add a new HandlerInterceptor, a new HealthIndicator, a new @EventListener — without editing Spring. Our DemoRunner is OCP too: a new demo class appears automatically in the List<PatternDemo>.

3.5 L — Liskov Substitution Principle

Named after Barbara Liskov. If Penguin extends Bird and Bird promises fly(), then a penguin must be able to fly — or the inheritance is wrong.

solid/lsp/LspDemo.java — BADclass BadBird { String fly() { return "... is flying"; } }

class BadPenguin extends BadBird {
    @Override
    String fly() {
        throw new UnsupportedOperationException("Penguins cannot fly!");   // surprise!
    }
}
// code written for BadBird now crashes for some birds
solid/lsp/LspDemo.java — GOODinterface Bird { String name(); }
interface FlyingBird extends Bird {
    default String fly() { return name() + " is flying"; }
}
record Sparrow() implements FlyingBird { public String name() { return "Sparrow"; } }
record Penguin() implements Bird { ... String swim() { ... } }

List<FlyingBird> flyers = List.of(new Sparrow(), new Eagle());   // the compiler keeps penguins out

Warning signs of an LSP violation: overriding methods that throw UnsupportedOperationException, empty overrides "because it doesn't apply", or if (x instanceof Penguin) checks in calling code. The famous textbook example is Square extends Rectangle (setting the width of a square also changes its height, surprising callers).

Spring link: you can swap HikariCP for another DataSource, or BCrypt for Argon2 as PasswordEncoder, and Spring's code keeps working — because those implementations honour the interface's contract.

The arrow from the detail points up to the abstraction — the dependency is "inverted". DIP is the principle, Dependency Injection is the technique (pass dependencies in), Spring IoC is the tool that does the injecting (topics 22–24).

3.8 Other principles worth knowing

PrincipleMeaningExample
DRY — Don't Repeat YourselfEvery piece of knowledge has one home.The tax rate lives in ONE constant, not in 7 places.
KISS — Keep It SimpleThe simplest solution that works is usually best.A plain if beats a 4-class pattern for 2 cases.
YAGNI — You Aren't Gonna Need ItDon't build for imaginary future needs.No "plugin system" until a second plugin exists.

⚠️ DRY has limits Two pieces of code that look the same but change for different reasons are not duplication. Merging them creates coupling. "A little copying is better than the wrong abstraction."

3.10 Singleton

Intent: exactly one instance with a global access point. The simplest thread-safe version in plain Java is an enum:

patterns/singleton/SingletonDemo.javaenum AppSettings {
    INSTANCE;
    private final Map<String, String> values = new ConcurrentHashMap<>(Map.of("currency", "INR"));
    String get(String key) { return values.get(key); }
}
AppSettings.INSTANCE.get("currency");

In Spring every bean is a singleton by default — one per container. Spring's version is better than the classic one: it's still injected (so tests can pass a fake), and there are no static getInstance() calls hiding dependencies. Our demo shows context.getBean(SingletonDemo.class) == this is true.

🚫 Singleton + mutable state = bug One singleton bean serves all requests on many threads at once (topic 17). Never store per-request data in a field of a @Service (private User currentUser; ❌). Keep beans stateless, or use thread-safe structures.

3.11 Factory

Intent: put the "which class do I create?" decision in one place. Callers depend only on the interface.

patterns/factory/FactoryDemo.javainterface Notification { String send(String to, String message); }

final class NotificationFactory {
    static Notification create(String channel) {
        return switch (channel.toLowerCase()) {
            case "email" -> new EmailNotification();
            case "sms"   -> new SmsNotification();
            case "push"  -> new PushNotification();
            default -> throw new IllegalArgumentException("Unknown notification channel: " + channel);
        };
    }
}
Notification n = NotificationFactory.create("email");

In Spring the container is the factory (BeanFactory), and every @Bean method is a factory method:

@Configuration
class ClockConfig {
    @Bean                       // a factory method: Spring calls it to create the bean
    Clock clock() {
        return Clock.systemUTC();
    }
}

JDK examples: List.of(...), LocalDate.of(...), Executors.newFixedThreadPool(...) — static factory methods.

3.12 Builder

Intent: create a complex (often immutable) object step by step, readably, with validation at the end. Compare:

new Pizza("LARGE", true, true, false, List.of("mushroom"));   // which boolean is which??

Pizza.builder("LARGE").thinCrust().extraCheese().topping("mushroom").build();   // reads like English
patterns/builder/Pizza.java (core)public final class Pizza {
    private final String size;
    private final List<String> toppings;
    ...
    private Pizza(Builder builder) { ... }                 // only the builder can create it

    public static Builder builder(String size) { return new Builder(size); }

    public static final class Builder {
        private final String size;                         // required
        private boolean thinCrust;                         // optional
        private final List<String> toppings = new ArrayList<>();

        public Builder thinCrust() { this.thinCrust = true; return this; }   // "return this" = chaining
        public Builder topping(String t) { toppings.add(t); return this; }

        public Pizza build() {
            if (!List.of("SMALL", "MEDIUM", "LARGE").contains(size)) {
                throw new IllegalStateException("Unknown size: " + size);
            }
            return new Pizza(this);
        }
    }
}

In Spring: RestClient.builder().baseUrl(...).build(), ResponseEntity.status(201).header(...).body(dto), MockMvcRequestBuilders.get(...).param(...), new SpringApplicationBuilder(...). Lombok's @Builder generates this code for you (topic 33). For small objects, a record with 2–3 fields doesn't need a builder.

3.13 Adapter

Intent: make an existing class with the wrong interface fit the interface your code expects — like a travel plug adapter.

patterns/adapter/AdapterDemo.javainterface PaymentGateway {                       // what OUR code wants
    PaymentResult pay(String account, BigDecimal amount);
}

class LegacyBankSdk {                             // what the old library offers (can't change it)
    int doTransfer(String accountNumber, long amountInCents) { ... }   // 0 = OK
}

class LegacyBankAdapter implements PaymentGateway {
    private final LegacyBankSdk sdk;
    LegacyBankAdapter(LegacyBankSdk sdk) { this.sdk = sdk; }

    public PaymentResult pay(String account, BigDecimal amount) {
        long cents = amount.movePointRight(2).longValueExact();     // translate units
        int code = sdk.doTransfer(account, cents);                    // call old API
        return code == 0 ? new PaymentResult(true, "LEGACY-" + cents)
                         : new PaymentResult(false, "ERROR-" + code); // translate result
    }
}

In Spring: DispatcherServlet can call very different kinds of handlers (annotated controllers, functional routes, old HttpRequestHandlers) because a HandlerAdapter adapts each to one common call. In your own projects, adapters are how you wrap third-party SDKs (payment, SMS, storage) so that the rest of your code depends on your interface — also great for DIP and testing.

3.14 Strategy

Intent: a family of interchangeable algorithms behind one interface; choose one at runtime. The Spring way is beautiful: every strategy is a bean, and Spring can inject them all as a Map keyed by bean name.

patterns/strategy/*.javapublic interface PaymentStrategy { String pay(BigDecimal amount); }

@Component("upi")    public class UpiPayment    implements PaymentStrategy { ... }
@Component("card")   public class CardPayment   implements PaymentStrategy { ... 2% fee ... }
@Component("wallet") public class WalletPayment implements PaymentStrategy { ... }

@Service
public class PaymentService {
    private final Map<String, PaymentStrategy> strategies;   // {"upi"=..., "card"=..., "wallet"=...}

    public PaymentService(Map<String, PaymentStrategy> strategies) {
        this.strategies = strategies;
    }

    public String checkout(String method, BigDecimal amount) {
        PaymentStrategy strategy = strategies.get(method);
        if (strategy == null) {
            throw new IllegalArgumentException("Unsupported payment method: " + method);
        }
        return strategy.pay(amount);
    }
}

No switch, no if/else. Adding "netbanking" = one new @Component("netbanking") class. That's Strategy + Open/Closed + DIP working together. In Spring: PasswordEncoder (BCrypt/Argon2/…), CacheManager (simple/Redis/Caffeine), HttpMessageConverter (JSON/XML chosen per request). In Java: Comparator is a strategy for sorting (topic 11)!

3.15 Observer

Intent: when something happens in one object, all interested objects are notified — without the publisher knowing who they are. (A YouTube channel and its subscribers.)

patterns/observer/*.javapublic record OrderPlacedEvent(String orderId, String customerEmail, BigDecimal total) { }

@Service
public class OrderPlacementService {
    private final ApplicationEventPublisher publisher;
    ...
    public void placeOrder(String orderId, String email, BigDecimal total) {
        // save the order ...
        publisher.publishEvent(new OrderPlacedEvent(orderId, email, total));   // announce
    }
}

@Component
public class EmailListener {
    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) { ... send confirmation ... }
}

@Component
public class InventoryListener {
    @EventListener
    public void onOrderPlaced(OrderPlacedEvent event) { ... reserve stock ... }
}

The order service doesn't depend on email or inventory code. Add an AnalyticsListener tomorrow — zero changes elsewhere. Plain Java version: a subject keeps a List<Listener> and calls each one. Across microservices, the same idea becomes messaging with RabbitMQ/Kafka (topics 57–58). Spring extras: @Async listeners and @TransactionalEventListener (run only after the DB commit — topic 52).

3.16 Template Method

Intent: a base class fixes the steps of an algorithm (the "template"); subclasses fill in some steps.

patterns/templatemethod/TemplateMethodDemo.javaabstract static class ReportGenerator {
    final String generate(List<Sale> sales) {          // final: the order of steps is fixed
        StringBuilder out = new StringBuilder();
        out.append(header()).append('\n');
        for (Sale sale : sales) {
            out.append(row(sale)).append('\n');
        }
        out.append(footer(sales.size()));
        return out.toString();
    }
    protected abstract String header();                // subclasses MUST fill these
    protected abstract String row(Sale sale);
    protected String footer(int rowCount) {            // a "hook": optional override
        return "# " + rowCount + " rows";
    }
}
class CsvReport extends ReportGenerator {
    protected String header() { return "product,qty"; }
    protected String row(Sale s) { return s.product() + "," + s.quantity(); }
}

In Spring — JdbcTemplate is the star example (topic 37). The fixed steps (get connection → create statement → execute → loop over results → translate SQLException → close everything) are in the template. You supply only the variable part — the SQL and a callback:

List<Student> students = jdbcTemplate.query(
        "SELECT id, name FROM students",
        (rs, rowNum) -> new Student(rs.getLong("id"), rs.getString("name")));   // your "step"

Spring uses callbacks (lambdas) instead of subclasses — a modern twist on the same idea. Same for RestTemplate, JmsTemplate, KafkaTemplate, TransactionTemplate.

3.17 Proxy — the key to Spring's "magic"

Intent: a stand-in object with the same interface as the real one, which adds behaviour before/after forwarding the call.

Your controller→ Proxy
begin transaction→ Real OrderService.placeOrder()→ Proxy
commit / rollback 
patterns/proxy/ProxyDemo.java — part 1: JDK dynamic proxyInvocationHandler timing = (proxy, method, args) -> {
    long start = System.nanoTime();
    Object result = method.invoke(real, args);                 // forward to the real object
    System.out.println(method.getName() + " took " + (System.nanoTime() - start) / 1_000_000 + " ms");
    return result;
};
PriceCatalog timed = (PriceCatalog) Proxy.newProxyInstance(
        PriceCatalog.class.getClassLoader(), new Class<?>[] {PriceCatalog.class}, timing);
patterns/proxy/ProxyDemo.java — part 2: Spring ProxyFactory (a mini @Cacheable)MethodInterceptor caching = invocation -> {
    Object key = invocation.getArguments()[0];
    if (cache.containsKey(key)) {
        return cache.get(key);                 // HIT: the real object is not even called
    }
    Object value = invocation.proceed();       // MISS: call the real method
    cache.put(key, value);
    return value;
};
ProxyFactory factory = new ProxyFactory(real);
factory.addAdvice(caching);
PriceCatalog cached = (PriceCatalog) factory.getProxy();

This is exactly how @Transactional, @Cacheable, @Async, @PreAuthorize, @Retry and every aspect (topic 27) work: at startup Spring wraps your bean in a proxy, and other beans receive the proxy. Spring Data repositories and Feign clients are proxies too — you write only an interface, the proxy does the work.

⚠️ The self-invocation trap (explained by Proxy) Inside OrderService, this.placeOrder() calls the real object directly — not the proxy — so @Transactional on placeOrder is silently ignored. Fix: call it from another bean, or move the method to a separate service (topics 27 and 42).

3.18 Three more patterns in one minute

PatternIdeaTiny example
DecoratorWrap an object with the same interface to add a feature; wrappers can be stacked.new BufferedReader(new FileReader(file)) — Java I/O is decorators all the way down.
FacadeOne simple class hiding a complicated subsystem.jdbcTemplate.update(sql, args) hides 20 lines of JDBC; your CheckoutService hides cart + stock + payment + email.
Chain of ResponsibilityA request passes through a chain; each handler may act and pass it on — or stop it.Spring Security filters: CORS → CSRF → JWT auth → authorization (topic 47); servlet filters; interceptors.

Proxy vs Decorator: same shape (wrap an object with the same interface). Proxy controls access (lazy loading, security, transactions); Decorator adds features, often stacked by the caller.

3.19 Anti-patterns and pattern overuse

  • God class — one class that knows and does everything (Utils, Manager, 2,000 lines).
  • Magic numbers / strings — if (status == 3). What is 3?
  • Copy-paste programming — the same bug fixed in 4 places (and forgotten in the 5th).
  • Anemic everything / smart nothing — logic scattered in controllers instead of services/domain.
  • Pattern-itis — AbstractPaymentStrategyFactoryProvider for two cases. Patterns are tools, not goals. Apply one when it solves a real problem you have now (YAGNI, KISS).

Our CleanCodeDemo shows a refactoring. Before:

cleancode/CleanCodeDemo.java — BEFOREstatic double calc(int t, double a, boolean f) {
    double r = 0;
    if (a > 0) {
        if (t == 1) {
            r = a * 0.9;
        } else {
            if (t == 2) {
                r = a * 0.8;
            } else {
                r = a;
            }
        }
        if (f) {
            r = r + 40;
        }
    }
    return r;
}

After:

cleancode/CleanCodeDemo.java — AFTERenum CustomerTier {
    REGULAR("0"), SILVER("10"), GOLD("20");
    private final BigDecimal discountPercent;
    CustomerTier(String discountPercent) { this.discountPercent = new BigDecimal(discountPercent); }
}
enum Delivery { STANDARD, EXPRESS }

private static final BigDecimal EXPRESS_DELIVERY_FEE = new BigDecimal("40");
private static final BigDecimal ONE_HUNDRED = new BigDecimal("100");

static BigDecimal finalPrice(BigDecimal orderAmount, CustomerTier tier, Delivery delivery) {
    requirePositive(orderAmount);                                   // guard clause
    BigDecimal discounted = applyTierDiscount(orderAmount, tier);
    return addDeliveryFee(discounted, delivery).setScale(2, RoundingMode.HALF_UP);
}

private static void requirePositive(BigDecimal amount) {
    if (amount == null || amount.signum() <= 0) {
        throw new IllegalArgumentException("Order amount must be positive, but was " + amount);
    }
}

private static BigDecimal applyTierDiscount(BigDecimal amount, CustomerTier tier) {
    BigDecimal discount = amount.multiply(tier.discountPercent).divide(ONE_HUNDRED);
    return amount.subtract(discount);
}

private static BigDecimal addDeliveryFee(BigDecimal amount, Delivery delivery) {
    return delivery == Delivery.EXPRESS ? amount.add(EXPRESS_DELIVERY_FEE) : amount;
}

The call site went from calc(2, 1000.0, true) to finalPrice(amount, GOLD, EXPRESS) — you can read it aloud. Notice one more improvement: the old version silently returned 0 for a negative amount; the new one fails fast. CleanCodeTest proves both versions agree for valid inputs — refactor only with tests as a safety net.

3.21 Recommended Spring Boot project structure

In topic 33 you met package-by-layer (controller/, service/, repository/). For bigger, enterprise apps most teams prefer package-by-feature: everything about "orders" lives together, so a change to orders touches one folder, and features can later be split into microservices.

3.22 Code review checklist

✅ Before you open (or approve) a pull request
  • Correctness: does it do what the ticket asks? Edge cases (empty list, null, zero, negative, very large)?
  • Tests: new logic has unit tests; bug fixes have a test that failed before; CI is green.
  • Readability: clear names, small methods, no magic numbers, no commented-out code.
  • Design: right layer (no business logic in controllers, no HTTP in repositories); SRP; no duplication.
  • API: correct HTTP methods and status codes, DTOs not entities, validation on input, consistent error format.
  • Database: migration included, indexes for new queries, no N+1, transactions where needed.
  • Security: authorization checked, no secrets in code, no sensitive data in logs or responses.
  • Errors & logging: exceptions not swallowed; useful log messages at the right level.
  • Performance: pagination for lists; no heavy work inside loops; caching considered.
  • Config & docs: new properties documented and with safe defaults; OpenAPI/README updated.
  • Size: the PR is small enough to review in 15–30 minutes.

And be kind: review the code, not the person. Suggest, explain why, and praise good things too.

4.1 The runner: OCP + DI + Strategy in 20 lines

demo/DemoRunner.java@Component
@ConditionalOnProperty(name = "demo.runner.enabled", havingValue = "true", matchIfMissing = true)
public class DemoRunner implements CommandLineRunner {

    private final List<PatternDemo> demos;      // ALL PatternDemo beans, sorted by @Order

    public DemoRunner(List<PatternDemo> demos) {
        this.demos = demos;
    }

    @Override
    public void run(String... args) {
        int number = 1;
        for (PatternDemo demo : demos) {
            System.out.println("=== " + number++ + ". " + demo.title() + " ===");
            demo.run();
        }
    }
}

Each demo class has @Component and @Order(n). Spring injects a List sorted by that order. The runner never changes when a demo is added (Open/Closed). @ConditionalOnProperty lets the tests start the context without printing everything (demo.runner.enabled=false).

Each SOLID demo keeps BAD and GOOD versions as nested classes in one file, so you can compare them side by side. In real code each of those classes would get its own file.

6. Common mistakes

⚠️ Mistake: using patterns everywhere Interfaces with one implementation "just in case", factories for objects created once, 5 layers for a CRUD endpoint.
Fix: start simple (KISS, YAGNI). Introduce a pattern when a second variant or a real pain appears. Refactoring later is cheap when you have tests.
🚫 Mistake: mutable state in singleton beans @Service class CartService { private List<Item> items; } — all users share one cart!
Fix: keep beans stateless; store per-user data in the database, the session, or method variables.
⚠️ Mistake: "my @Transactional/@Cacheable does nothing" Calling the annotated method from the same class (self-invocation), or making it private/final, so the proxy is bypassed.
Fix: call it through another bean; keep such methods public (now you know why — Proxy!).
⚠️ Mistake: inheritance for code reuse class OrderService extends BaseService extends AbstractCrudService ... deep hierarchies that are hard to change, often breaking LSP.
Fix: composition — inject helper beans.
⚠️ Mistake: field injection and new inside services @Autowired private PaymentClient client; or new SmtpMailer() inside a service — hidden dependencies, hard to test (violates DIP).
Fix: constructor injection of interfaces (topic 24).
⚠️ Mistake: refactoring without tests "I just cleaned it up" — and broke the discount for GOLD customers.
Fix: write characterisation tests first (like CleanCodeTest), then refactor in small steps, running tests each time.
⚠️ Mistake: the giant "Utils" / "Helper" / "Manager" class A dumping ground that violates SRP and grows forever.
Fix: move each method to the class that owns the data or the concept.
⚠️ Mistake: comments that lie Code changed, comment didn't.
Fix: make code self-explanatory with names; keep comments for why and update them with the code.

7. Best practices

  • Program to interfaces at boundaries (repositories, external clients, strategies) — not for every class.
  • Constructor injection, final fields, stateless beans.
  • Small, focused classes and methods; one level of abstraction per method.
  • Records for DTOs and value objects; immutability by default.
  • Package-by-feature for growing apps; clear layer responsibilities inside each feature.
  • Prefer Spring's built-in patterns (events, Map of strategies, AOP) over hand-made infrastructure.
  • Boy Scout rule: leave the code a little cleaner than you found it — in small, tested steps.
  • Automate quality: formatters, static analysis (SonarQube), ArchUnit rules, CI gates (topic 68).
  • Security and performance are part of "done": run through the checklists in 3.22–3.24 for every feature.
  • Write for the reader: the next developer is busy and tired — make their life easy.

8. Key takeaways

  • SOLID: one reason to change (S), extend without editing (O), subtypes must be substitutable (L), small interfaces (I), depend on abstractions (D).
  • DIP is the principle, DI the technique, Spring IoC the tool.
  • Spring is built from classic patterns: Singleton beans, Factory (BeanFactory, @Bean), Builder, Adapter, Proxy (AOP, @Transactional), Strategy, Observer (events), Template Method (JdbcTemplate), Chain of Responsibility (filters), Front Controller (DispatcherServlet).
  • Proxy explains the self-invocation trap and why annotated methods must be public.
  • Strategy + a Map<String, Interface> of beans removes switch statements and follows Open/Closed.
  • Clean code: meaningful names, small methods, no magic numbers, guard clauses, enums over codes, comments for "why".
  • Refactor only with tests; don't over-engineer (KISS, YAGNI).
  • Use the code-review, OWASP security and performance checklists on every feature.

class LoggingNotification implements Notification {
    private final Notification inner;
    LoggingNotification(Notification inner) { this.inner = inner; }

    public String send(String to, String message) {
        System.out.println("sending to " + to + "...");
        String result = inner.send(to, message);
        System.out.println("sent");
        return result;
    }
}

class RetryNotification implements Notification {
    private static final int MAX_ATTEMPTS = 3;
    private final Notification inner;
    RetryNotification(Notification inner) { this.inner = inner; }

    public String send(String to, String message) {
        RuntimeException last = null;
        for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
            try {
                return inner.send(to, message);
            } catch (RuntimeException e) {
                last = e;
            }
        }
        throw last;
    }
}

Notification n = new LoggingNotification(new RetryNotification(NotificationFactory.create("sms")));

Same interface, wrapped and stacked — that's Decorator. (Compare: new BufferedReader(new FileReader(f)).)

5. Chain of Responsibility. Build an order-validation chain: StockCheck → FraudCheck → CreditLimitCheck. Each check is a Spring bean with @Order; a OrderValidator runs them in order and stops at the first failure.

Hint / solution
public interface OrderCheck {
    Optional<String> check(Order order);        // empty = OK, otherwise the error message
}

@Component @Order(1) class StockCheck implements OrderCheck { ... }
@Component @Order(2) class FraudCheck implements OrderCheck { ... }
@Component @Order(3) class CreditLimitCheck implements OrderCheck { ... }

@Service
public class OrderValidator {
    private final List<OrderCheck> checks;     // sorted by @Order
    public OrderValidator(List<OrderCheck> checks) { this.checks = checks; }

    public void validate(Order order) {
        for (OrderCheck check : checks) {
            check.check(order).ifPresent(error -> {
                throw new IllegalStateException(error);   // stop the chain
            });
        }
    }
}

This is a simplified version of how Spring Security's filter chain works.

10. Interview questions

Q1. Explain SOLID with an example for each letter.

S: split an InvoiceManager into calculator, formatter, store. O: a Discount interface so new discounts are new classes, not new ifs. L: a Penguin must not extend a Bird that promises fly(); split into Bird/FlyingBird. I: separate Printer, Scanner, Fax interfaces instead of one fat interface. D: OrderService depends on an OrderRepository interface injected via constructor, not on new MySqlOrderDatabase().

Q2. Which design patterns are used in the Spring Framework?

Singleton (default bean scope), Factory (BeanFactory, @Bean, FactoryBean), Proxy (AOP, @Transactional, @Cacheable, Spring Data repositories), Template Method (JdbcTemplate, RestTemplate), Strategy (PasswordEncoder, HttpMessageConverter), Observer (application events), Adapter (HandlerAdapter), Front Controller (DispatcherServlet), Chain of Responsibility (filter chains), Builder (RestClient.builder()), Decorator (bean wrapping), and of course Dependency Injection/IoC.

Q3. How does @Transactional work internally, and when does it NOT work?

Spring creates a proxy (JDK dynamic proxy for interfaces or CGLIB subclass) around the bean. Calls go through the proxy, which starts a transaction, calls the real method, and commits or rolls back (on unchecked exceptions by default). It doesn't apply on self-invocation (calling the method from the same class bypasses the proxy), on private/final methods (CGLIB can't override them), or on objects not managed by Spring.

Q4. Spring singleton vs the GoF Singleton?

GoF Singleton: one instance per class loader, enforced by the class itself (private constructor, static getInstance()), hard to test. Spring singleton: one instance per container per bean definition, created and injected by Spring; the class is a normal class (you could create others), and dependencies are visible and replaceable in tests. Both must be thread-safe — keep them stateless.

Q5. Strategy vs Template Method?

Both vary part of an algorithm. Template Method uses inheritance: the base class fixes the steps and subclasses override some. Strategy uses composition: the whole algorithm is an object you pass in or choose at runtime. Strategy is more flexible (switch at runtime, no subclassing); modern Spring templates mix both by accepting callbacks (lambdas).

Q6. How do you avoid a big switch over types in Spring?

Define an interface, implement each case as a bean, and inject Map<String, MyInterface> (keyed by bean name) or List<MyInterface> with a supports(type) method. Pick the implementation at runtime. New cases = new beans (Open/Closed).

Q7. What is the difference between Proxy, Decorator and Adapter?

Adapter changes the interface (makes an incompatible class fit). Proxy and Decorator keep the same interface: Proxy controls access to the real object (security, lazy loading, transactions, remote calls), Decorator adds responsibilities and is often stacked by the client.

Q8. What makes code "clean"? Give concrete rules.

It reads like well-written prose: intention-revealing names, small methods that do one thing, few parameters, no magic numbers, guard clauses instead of deep nesting, enums instead of codes, no duplicated knowledge, comments that explain why, consistent formatting, meaningful exceptions, immutability where possible, and tests that document behaviour.

Q9. How would you structure a large Spring Boot application?

Package-by-feature (product, order, user…) with controller/service/repository/dto inside each feature, plus a common package for config, security and exception handling. DTOs at the boundary, entities inside, Flyway migrations, profile-specific config, tests mirroring packages. Features communicate via services or events; module boundaries can be enforced with ArchUnit or Spring Modulith.

Q10. Name some OWASP Top 10 risks and how Spring Boot helps.

Broken access control (Spring Security, @PreAuthorize, ownership checks), injection (parameterised queries via JPA/JdbcTemplate), cryptographic failures (BCrypt, HTTPS), security misconfiguration (limit actuator exposure, no stack traces), vulnerable components (keep Spring Boot and dependencies updated, Dependabot), authentication failures (Spring Security, JWT best practices), logging & monitoring failures (structured logs, Actuator metrics, alerting).
