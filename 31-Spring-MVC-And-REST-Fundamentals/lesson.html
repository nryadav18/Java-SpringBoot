1. Why this matters

Open any app on your phone — Swiggy, Amazon, your bank. The screen you see is just the "front". Every time you tap "Show orders" or "Pay", the app sends a message over the internet to a back-end server, and the server answers with data. That conversation almost always uses HTTP and a REST API returning JSON.

Building those back-end APIs is the number-one job of a Spring Boot developer. Mobile apps, React/Angular websites, other microservices and partner companies all talk to your code through REST endpoints. This topic gives you the foundation; topic 32 adds all the details; topics 33–46 make it professional.

2. Real-life analogy

🍽️ A restaurant
  • You (the customer) = the client (browser, mobile app, curl).
  • Your order slip = the HTTP request: what you want (method: "GET me a menu", "POST a new order"), which item (URL), notes like "no onions" (headers), and sometimes details (body).
  • The head waiter at the door = DispatcherServlet: receives every order and decides which cook should handle it.
  • The board saying "pizzas → Mario, curries → Priya" = HandlerMapping.
  • The cook = your controller method.
  • Plating the food nicely = Jackson converting your Java object to JSON.
  • The plate served back + the bill saying "served" or "sorry, sold out" = the HTTP response with a status code (200 OK, 404 Not Found).
  • The waiter doesn't remember you between visits; you show your table number each time = REST is stateless.

3.5 Headers and JSON

Headers are key/value notes about the message. The two you will meet constantly:

  • Content-Type: application/json — "the body I'm sending is JSON".
  • Accept: application/json — "I'd like to receive JSON".

Others: Authorization (login tokens, topic 49), Location (where a new resource lives, topic 32), Cache-Control, User-Agent.

JSON (JavaScript Object Notation) is the text format APIs use for data. It maps naturally to Java:

JSONJava
{ "title": "Clean Code", "year": 2008 } (object)an object/record with fields title, year
[ {...}, {...} ] (array)List<Book>
"text", 42, 4.5, true, nullString, int/long, double/BigDecimal, boolean, null

3.6 What is REST?

REST (REpresentational State Transfer) is a style for designing web APIs, described by Roy Fielding in 2000. It's not a library — it's a set of ideas:

  1. Everything is a resource — a "thing" with an address: a book, an order, a customer.
  2. Each resource has a URI using nouns, usually plural: /api/books (the collection), /api/books/2 (one item).
  3. HTTP methods are the verbs: GET /api/books/2, not /api/getBook?id=2.
  4. Representations: the client receives a representation of the resource (JSON, sometimes XML), not the object itself.
  5. Stateless: every request carries everything needed to understand it. The server keeps no "conversation memory" between requests. This makes scaling easy: any server copy can answer any request.
  6. Use status codes properly (201 for created, 404 for not found…).
❌ Not RESTful✅ RESTful
GET /getAllBooksGET /api/books
POST /createBookPOST /api/books
GET /deleteBook?id=3 (danger: a GET that changes data!)DELETE /api/books/3
Always 200 with {"error":"not found"}404 Not Found

3.7 Spring MVC architecture — the journey of a request

Spring MVC is Spring's web framework (MVC = Model-View-Controller). spring-boot-starter-web brings it and auto-configures it. Here's what happens for GET /api/books/2:

  1. The client sends GET /api/books/2; embedded Tomcat receives it and hands it to Spring's DispatcherServlet.
  2. The DispatcherServlet is the front controller: every request goes through it first. (Spring Boot registered it for you — in the old days that was web.xml.)
  3. It asks the HandlerMapping: "which controller method matches GET + /api/books/2?" At startup Spring read all your @GetMapping/@PostMapping annotations and built this table.
  4. The matching method BookController.getBook(2) is called. Spring fills its parameters (@PathVariable → 2).
  5. The controller calls the service, which returns a Book object.
  6. Because it's a @RestController, the return value goes to an HttpMessageConverter. For JSON that is MappingJackson2HttpMessageConverter, which uses Jackson's ObjectMapper.
  7. The JSON is written into the response body with status 200 OK and Content-Type: application/json.

The same converters work in reverse for @RequestBody: JSON in the request → Java object. You never call Jackson yourself.

ℹ️ "MVC" — where is the View? In server-side web apps (topic 36), the controller returns a view name and a model, and a template engine renders HTML. In REST APIs there is no view: the "view" is the JSON produced by the message converter.

3.9 Mapping annotations

@RestController
@RequestMapping("/api/books")          // class level: common prefix for all methods
public class BookController {

    @GetMapping                        // GET    /api/books
    @GetMapping("/{id}")               // GET    /api/books/2
    @PostMapping                       // POST   /api/books
    @PutMapping("/{id}")               // PUT    /api/books/2

    @DeleteMapping("/{id}")            // DELETE /api/books/2

@GetMapping("/x") is a shortcut for @RequestMapping(value = "/x", method = RequestMethod.GET). Use the shortcuts on methods; use @RequestMapping on the class for the prefix. Quick preview of parameter annotations (topic 32 covers them fully):

        return new Book(newId, title, author, year, price);

id is Long (not long) so a new book sent by a client can have no id (null). withId makes a copy with the server-generated id, because records are immutable.

4.2 BookService — in-memory storage

src/main/java/com/course/restbasics/BookService.java (key parts)@Service
public class BookService {

    private final List<Book> books = new CopyOnWriteArrayList<>();
    private final AtomicLong nextId = new AtomicLong(1);

    public BookService() {
        add(new Book(null, "Clean Code", "Robert C. Martin", 2008, 499.0));
        add(new Book(null, "Effective Java", "Joshua Bloch", 2018, 650.0));
        ...
    }

    public List<Book> findAll() { return List.copyOf(books); }

    public Optional<Book> findById(long id) {
        return books.stream().filter(b -> b.id() == id).findFirst();
    }

    public List<Book> findByAuthor(String author) {
        return books.stream()
                .filter(b -> b.author().toLowerCase().contains(author.toLowerCase()))
                .toList();
    }

    public Book add(Book book) {
        Book saved = book.withId(nextId.getAndIncrement());
        books.add(saved);
        return saved;
    }

    public boolean deleteById(long id) { return books.removeIf(b -> b.id() == id); }
}
⚠️ Why thread-safe collections? Tomcat handles requests on many threads at the same time (topic 17). Two POSTs at the same moment with a plain ArrayList and long counter could lose a book or give two books the same id. CopyOnWriteArrayList and AtomicLong are safe. (A database solves this for us from topic 37 on.)

4.3 BookController — the endpoints

src/main/java/com/course/restbasics/BookController.java@RestController
@RequestMapping("/api/books")
public class BookController {

    private final BookService bookService;

    public BookController(BookService bookService) {
        this.bookService = bookService;
    }

    @GetMapping
    public List<Book> getAllBooks() {
        return bookService.findAll();
    }

    @GetMapping("/{id}")
    public Book getBook(@PathVariable long id) {
        return bookService.findById(id)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "Book " + id + " not found"));
    }

    @GetMapping("/search")
    public List<Book> searchByAuthor(@RequestParam String author) {
        return bookService.findByAuthor(author);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Book addBook(@RequestBody Book book) {
        return bookService.add(book);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void deleteBook(@PathVariable long id) {
        if (!bookService.deleteById(id)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Book " + id + " not found");
        }
    }
}
  • Controller is thin: it translates HTTP ↔ Java and delegates work to the service. Topic 33 makes this a rule.
  • ResponseStatusException — the simplest way to answer with an error status. Spring Boot turns it into a JSON error body. (Topic 35 builds a proper global error handler.)
  • @ResponseStatus(HttpStatus.CREATED) — success status for this method is 201 instead of the default 200.
  • void + 204 No Content — "done, nothing to send back".
  • Why is /search not confused with /{id}? Spring prefers the more specific pattern: a literal path segment beats a {variable}.

6. Common mistakes

⚠️ 415 Unsupported Media Type on POST You forgot the header Content-Type: application/json, so Spring doesn't know the body is JSON.
Fix: add the header (in Postman: Body → raw → JSON).
⚠️ 400 Bad Request: "JSON parse error" The JSON is broken — missing quote, trailing comma, single quotes, or Windows shell quoting ate your quotes.
Fix: validate the JSON; use the REST Client to avoid shell quoting.
⚠️ 405 Method Not Allowed The URL exists but not for that method, e.g. PUT /api/books/2 when there is no @PutMapping, or opening a POST-only URL in the browser (browsers send GET).
⚠️ Using @Controller instead of @RestController Your method returns "Hello" and you get an error like "Circular view path" or a 404/500 looking for a template named Hello.
Fix: use @RestController (or add @ResponseBody).
⚠️ Empty JSON {} for your object Jackson uses getters. A normal class with private fields and no getters produces {}.
Fix: add getters, or use a record.
⚠️ Verbs in URLs and GET that changes data GET /api/deleteBook?id=3: browsers, crawlers and caches may call GET freely — and delete your data.
Fix: nouns in URLs, the method is the verb.
⚠️ Always returning 200 Returning 200 with null or an "error" text when something is missing confuses clients. Use 404/400 etc.
⚠️ Plain curl in Windows PowerShell 5.1 behaves strangely It may be an alias for Invoke-WebRequest with different options. Type curl.exe.

7. Best practices

  • Plural nouns for collections: /api/books, /api/books/{id}. Lower-case, hyphens for multi-word: /api/order-items.
  • Prefix APIs with /api (and later a version, /api/v1 — topic 44).
  • Use the right method and status code; GET must never change data.
  • Keep controllers thin: HTTP in, call a service, HTTP out. No business rules in controllers.
  • Let the server generate ids.
  • Return JSON objects or arrays consistently; don't mix plain text and JSON in one API.
  • Keep a .http file or Postman collection in the repo so teammates can try the API instantly. Document it with OpenAPI (topic 44).
  • Statelessness: don't store per-user conversation state in controller fields — controllers are singletons shared by all requests!

8. Key takeaways

  • HTTP = request (method, URL, headers, body) → response (status code, headers, body).
  • GET reads, POST creates, PUT replaces, PATCH modifies, DELETE removes.
  • 2xx success, 3xx redirect, 4xx client error, 5xx server error.
  • REST: resources with noun URIs, HTTP verbs, JSON representations, stateless.
  • Every request passes through the DispatcherServlet, which uses HandlerMapping to find your method and HttpMessageConverter (Jackson) to write JSON.
  • @RestController = @Controller + @ResponseBody.
  • @RequestMapping on the class + @GetMapping/@PostMapping/… on methods.
  • Test with the browser (GET), curl, the REST Client (.http) and Postman.

10. Interview questions

Q1. What is REST? What are its main constraints?

An architectural style for networked applications: client–server, stateless, cacheable, uniform interface (resources identified by URIs, manipulated through representations, self-descriptive messages, HATEOAS), layered system, and optional code-on-demand. In practice: resource URIs, HTTP methods, status codes, JSON.

Q2. Explain the role of DispatcherServlet.

It is Spring MVC's front controller. It receives every HTTP request, uses HandlerMapping to find the handler method, invokes it via a HandlerAdapter (resolving arguments), and processes the return value — writing it with an HttpMessageConverter for REST or resolving a view for MVC — plus exception resolution.

Q3. Difference between @Controller and @RestController?

@RestController is @Controller + @ResponseBody; return values are serialised into the response body. With @Controller, return values are view names unless the method has @ResponseBody.

Q4. How does Spring convert a Java object to JSON?

Through HttpMessageConverters. With Jackson on the classpath (from spring-boot-starter-web), Boot auto-configures MappingJackson2HttpMessageConverter with an ObjectMapper. It's chosen based on the return type and the Accept header.

Q5. Difference between PUT and PATCH? POST and PUT?

PUT replaces the whole resource and is idempotent; PATCH applies a partial update. POST creates a subordinate resource (server chooses the id) and is not idempotent; PUT targets a known URI.

Q6. What do safe and idempotent mean?

Safe: doesn't change server state (GET, HEAD, OPTIONS). Idempotent: making the same request many times has the same effect as once (GET, PUT, DELETE, HEAD, OPTIONS). POST is neither.

Q7. 401 vs 403? 400 vs 422? 500 vs 503?

401: not authenticated; 403: authenticated but not allowed. 400: malformed request; 422: well-formed but semantically invalid (some APIs use 400 for both). 500: unexpected server error; 503: server temporarily unavailable (overload/maintenance).

Q8. What does "stateless" mean in REST and why is it useful?

The server doesn't keep client session state between requests; each request contains everything needed (e.g., a token). Any instance can serve any request, which simplifies horizontal scaling and load balancing.

Q9. Is a Spring controller thread-safe?

Controllers are singletons used by many request threads concurrently. They are safe as long as they hold no mutable per-request state in fields; use local variables and thread-safe collaborators.
