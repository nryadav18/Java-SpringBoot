1. Why this matters

Until now, every project in this course was one application: one pom.xml, one main method, one jar, one database. That is called a monolith, and it is a perfectly good way to build software.

But when you join a company like Amazon, Netflix, Uber, Swiggy, Flipkart or a big bank, you will hear words like "the payment service", "the order service is down", "call the inventory API". These companies split their systems into many small, independent applications that talk to each other over the network. Those small apps are called microservices.

Why does this matter to you?

  • Jobs: almost every "Java Spring Boot developer" job description says "experience with microservices, Spring Cloud".
  • Interviews: "Monolith vs microservices?", "How do services find each other?", "What is a circuit breaker?" are asked all the time.
  • Design sense: knowing when NOT to use microservices makes you look senior. Many teams regret splitting too early.

This topic is the map of Part F. We first learn the ideas, then build two tiny services. They will work – but you will notice real problems (hard-coded addresses, failures, many URLs). The next topics fix each problem one by one with Spring Cloud.

2. Real-life analogy

🍽️ One big kitchen vs a food court

The monolith = one restaurant with one big kitchen. One team cooks everything: pizza, biryani, ice cream. Easy to start: one building, one manager, one fridge. But as the restaurant grows: the pizza oven breaks and the whole kitchen stops; you want to hire 10 more pizza cooks but they must fit into the same small kitchen; changing the biryani recipe needs a meeting with everyone.

Microservices = a food court. Each stall (pizza, biryani, ice cream) has its own small kitchen, its own staff and its own fridge (= its own database). If the ice cream machine breaks, people can still buy pizza. The pizza stall can add more counters on a busy evening (= scaling one service).

But a food court has new problems too: customers must know where each stall is (→ service discovery), you want one main entrance with a security guard (→ API gateway), all stalls must follow the same rules for prices and hygiene (→ central configuration), and if one stall is very slow you should not wait forever (→ circuit breaker). That is exactly Part F of this course.

3. Concepts step by step

3.1 What is a monolith?

A monolith ("mono" = one, "lith" = stone) is a single application that contains all features of the system. All code is built into one jar and deployed together. All features usually share one database.

A monolith is not bad. Most successful products (including early Amazon, Shopify, Stack Overflow, GitHub) started as monoliths, and some still are. It is simple to develop, test, debug and deploy.

3.2 What are microservices?

Microservices is an architecture style where the system is built as a set of small, independent services. Each service:

  • does one business job (products, orders, payments…),
  • is a separate application (its own Spring Boot project, its own jar, its own process, its own port),
  • owns its own data (its own database or schema),
  • talks to other services only through a network API (REST/HTTP or messages),
  • can be deployed, scaled and changed independently, often by its own small team.
ℹ️ "Micro" does not mean "tiny"A microservice is not measured in lines of code. "Micro" means focused on one business capability. A payment service can easily have 20,000 lines. The important part is that it is independent.

3.3 Monolith vs microservices – the honest comparison

AspectMonolithMicroservices
Start a new project✅ Very fast and simple❌ Slow: many projects, infrastructure needed

Testing & debugging✅ One app to run, one log file❌ Many apps, logs scattered → need tracing
Data consistency✅ Immediately consistent (one DB)❌ Often eventually consistent
Operations cost✅ Low❌ High: Docker, Kubernetes, monitoring, CI/CD per service

3.4 When NOT to use microservices

⚠️ Microservices are a cost you pay to solve SCALE problems – organisational and technical. Do not start with microservices when:
  • You are a small team (say, fewer than 10–15 developers). One team can manage a monolith perfectly well.
  • The product is new and the business domain is still changing. You don't yet know where the right "cut lines" are – a wrong split is very expensive to fix.
  • You don't have automation: CI/CD pipelines, Docker, monitoring, centralized logging. Without them, 10 services = 10× the pain.
  • Your app has no real scaling problem. "Netflix does it" is not a reason.
  • Your features need strong transactions across everything (e.g. a small accounting system).
A popular rule: "Monolith first." Build a modular monolith (clean packages per feature – Topic 33's package-by-feature) and split out a service only when a module has a real reason (different scaling, different team, different release speed).
💡 The "distributed monolith" trapIf your services must always be deployed together, share one database, or call each other in long chains for every request, you have built a distributed monolith: all the costs of microservices with none of the benefits. Avoid it.

3.5 Bounded contexts – how to decide service boundaries (DDD-lite)

Domain-Driven Design (DDD) is a way of designing software around the business. You only need one idea from it now: the bounded context.

A bounded context is an area of the business where a word has one clear meaning. Look at the word "Product" in an online shop:

Context (department)What "Product" means thereData it cares about
CatalogSomething to show and sellname, description, images, price
Inventory / WarehouseA physical box on a shelfstock quantity, warehouse location, weight
OrdersA line in a customer's orderproduct id, name and price at the time of order, quantity
ShippingA parcelsize, weight, address

Each context is a good candidate for a microservice. Instead of one giant Product class with 60 fields that everybody fights over, each service has its own small model. That is why, in our code, order-service has its own ProductDto and does not reuse product-service's Product class.

Good boundaries follow business capabilities (catalog, ordering, payment, shipping), not technical layers. A "database-service" or "validation-service" is a bad split.

ℹ️ Two DDD words you may hearAggregate = a group of objects that change together and are saved together (an Order with its OrderLines). Ubiquitous language = developers and business people use the same words in code and in meetings.

3.6 How do services talk? Synchronous vs asynchronous

There are two main styles of communication:

📞 Synchronous (request/response)

Like a phone call: you ask and you wait for the answer.

Usually REST over HTTP (also gRPC). In Spring: RestClient, WebClient, OpenFeign (Topic 63).

✅ simple, immediate answer
❌ caller is blocked; if the other service is down or slow, the caller suffers too (temporal coupling)

✉️ Asynchronous (messaging / events)

Like sending a letter / WhatsApp message: you send it and continue your work. The receiver handles it when it can.

Through a broker: RabbitMQ (Topic 57), Kafka (Topic 58).

✅ loose coupling, receiver can be down for a while, great for "something happened" events
❌ more moving parts, eventual consistency, harder to debug

order-service— GET /api/products/1 → product-service— waits for JSON ←
order-service— "OrderPlaced" event → Kafka / RabbitMQ→ notification-service+shipping-service

Rule of thumb: use sync when you need the answer right now to continue (order-service needs the price to create the order). Use async to tell others that something happened (order placed → send email, start shipping) – they don't need to answer.

3.7 Database per service

This is the most important – and most broken – rule: each service owns its data, and nobody else touches it directly.

order-service✅ REST API →product-service→products DB
order-service❌ SQL directly →products DB

Why so strict? If order-service reads the products table directly, the product team can never rename a column without breaking orders. The services become secretly glued together through the database. With an API in between, the product team can change their tables freely as long as the API stays the same.

"Own database" can mean a separate database server, a separate schema in one server, or simply separate tables only that service may access. The point is ownership.

ℹ️ But how do I join data from two services?You can't do a SQL JOIN across services. Options: (1) call the other service's API, (2) copy the few fields you need (our Order stores productName and unitPrice), (3) keep a local read-only copy updated by events (CQRS – advanced).

3.9 The key patterns map – your roadmap for Part F

As soon as you have more than one service, the same problems appear in every company. Each problem has a well-known pattern (a standard solution) and Spring Cloud gives you a ready-made tool for it:

ProblemPatternSpring Cloud toolTopic
"Where is product-service? Its IP/port changes, there are 3 copies."Service discovery + client-side load balancingEureka, Spring Cloud LoadBalancer60
"Clients must know 20 URLs; every service re-implements auth, CORS, logging."API gatewaySpring Cloud Gateway61
"Config is copied in 20 projects; changing it needs 20 redeploys."Externalized / centralized configSpring Cloud Config62
"Writing HTTP client code by hand is boring."Declarative REST clientOpenFeign63
"product-service is slow → order-service threads pile up → everything dies."Circuit breaker, retry, timeout, bulkheadResilience4j64
"One user request went through 5 services. Where did it fail?"Distributed tracing, centralized loggingMicrometer Tracing + Zipkin65
"Place order = reserve stock + take payment + create shipment, across 3 DBs."Saga (a chain of local transactions with compensating actions)Events via Kafka/RabbitMQ57, 58 (idea)
ℹ️ Saga in one paragraphThere is no @Transactional across services. A saga splits the business transaction into steps, each a local transaction in one service. If a later step fails, earlier steps are undone with compensating actions: payment failed → order-service cancels the order and inventory-service releases the stock. Choreography = services react to each other's events; orchestration = one "coordinator" tells each service what to do.

4.1 product-service – the data owner

product-service/src/main/java/com/course/msintro/product/ProductController.java@RestController
@RequestMapping("/api/products")
public class ProductController {

    // product-service's OWN data. Nobody else may read it directly.
    private final Map<Long, Product> products = new TreeMap<>(Map.of(
            1L, new Product(1L, "Laptop", 55000.0, 10),
            2L, new Product(2L, "Wireless Mouse", 799.0, 150),
            3L, new Product(3L, "Mechanical Keyboard", 3499.0, 40)
    ));

    @GetMapping
    public Collection<Product> findAll() {
        return products.values();
    }

    @GetMapping("/{id}")
    public ResponseEntity<Product> findById(@PathVariable Long id) {
        Product product = products.get(id);
        if (product == null) {
            return ResponseEntity.notFound().build();   // 404 for the caller
        }
        return ResponseEntity.ok(product);
    }
}

Nothing new here – it's Topic 31/32 material. The architectural point is: this API is the only door to product data. To keep the lesson focused we use a map instead of a database, but imagine it is product-service's own MySQL schema.

4.3 ProductClient – the network call

order-service/src/main/java/com/course/msintro/order/ProductClient.java@Component
public class ProductClient {

    private final RestClient restClient;

    public ProductClient(RestClient.Builder builder,
                         @Value("${product-service.base-url}") String productServiceUrl) {
        // Spring Boot gives us a pre-configured RestClient.Builder (with Jackson etc.)
        this.restClient = builder.baseUrl(productServiceUrl).build();
    }

    public ProductDto getProduct(Long productId) {
        try {
            return restClient.get()
                    .uri("/api/products/{id}", productId)
                    .retrieve()                 // 4xx/5xx -> exception
                    .body(ProductDto.class);    // JSON -> record
        } catch (HttpClientErrorException.NotFound e) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Product " + productId + " not found");
        } catch (ResourceAccessException e) {
            // could not CONNECT: product-service is down or the port is wrong
            throw new ResponseStatusException(HttpStatus.SERVICE_UNAVAILABLE,
                    "product-service is not available right now. Please try again later.");
        }
    }
}

Line by line:

  • RestClient.Builder builder – Spring Boot auto-configures a builder for you (Topic 45). We set the base URL once.
  • @Value("${product-service.base-url}") – reads http://localhost:8081 from application.properties. Still a fixed address.
  • .retrieve().body(ProductDto.class) – sends GET, checks the status and converts the JSON body into our record.
  • HttpClientErrorException.NotFound – product-service answered 404. We pass a clean 404 to our own caller.
  • ResourceAccessException – an I/O problem: connection refused, timeout. This exception type never existed in your monolith. Welcome to distributed systems!

4.4 OrderController – business logic using remote data

order-service/src/main/java/com/course/msintro/order/OrderController.java@PostMapping

    // 3) save in OUR storage
    Order order = new Order(nextId.getAndIncrement(), product.id(), product.name(),

}

6. Common mistakes

⚠️ Mistake: "Port 8081 was already in use"You started the same service twice, or another app uses the port.
Fix: stop the old process (Ctrl+C in its terminal, or ■ in the dashboard). To find who uses a port on Windows: netstat -ano | findstr :8081, then taskkill /PID <pid> /F.
⚠️ Mistake: starting order-service first and expecting it to fail at startuporder-service starts fine without product-service – it only calls it when an order is placed. Services must be able to start in any order; the call fails at request time (503).
Fix: nothing to fix – but understand it. Start product-service first for a smooth demo.
🛑 Mistake: sharing one database between services"It's easier: order-service can just SELECT from the products table." This creates hidden coupling; one schema change breaks other teams.
Fix: each service owns its tables. Others use its API or events.
🛑 Mistake: splitting too early / too smallTen services for a 3-person startup, or "nano-services" like email-validation-service. You get network latency, deployment pain and distributed bugs with no benefit.
Fix: start with a modular monolith; split by business capability when there is a real reason.
⚠️ Mistake: sharing entity classes through a "common" jarA shared common-model.jar with JPA entities used by all services = distributed monolith.
Fix: each service has its own DTOs. Share only truly generic utilities, if anything.
⚠️ Mistake: forgetting that remote calls failCode like restClient.get()...body(...) with no error handling and no timeout. One slow service then blocks all your threads.
Fix: handle errors (like ProductClient), set timeouts (Topic 45) and use a circuit breaker (Topic 64).
⚠️ Mistake: long chains of synchronous callsA → B → C → D for every request. If each is 99% available, the chain is only ~96% available, and latencies add up.
Fix: keep sync chains short; use events (async) for things that don't need an immediate answer.

7. Best practices

  • Monolith first (modular, package-by-feature). Extract services when a module needs independent scaling, deployment or ownership.
  • Split by business capability / bounded context, not by technical layer.
  • Database per service – no shared tables, ever.
  • Design APIs as contracts: version them (/api/v1), never break existing clients, document with OpenAPI (Topic 44).
  • Prefer async events for "something happened" notifications; keep sync calls for "I need the answer now".
  • Design for failure: timeouts, retries with care, circuit breakers, fallbacks.
  • Make services stateless so you can run many copies (12-factor #6, #8).
  • Automate everything: one CI/CD pipeline per service, Docker images, health checks (/actuator/health).
  • Observability from day one: structured logs, correlation/trace ids, metrics (Topics 53, 65).
  • One team owns a service end-to-end ("you build it, you run it"). Conway's law: your architecture will mirror your team structure.

8. Key takeaways

  • A monolith is one deployable app; microservices are many small, independently deployable apps, each owning one business capability and its own data.
  • Microservices trade simplicity for independent scaling, deployment and team autonomy. They are not free.
  • Don't use them for small teams, new/unclear domains or without automation. "Monolith first."
  • Find boundaries with bounded contexts: the same word ("Product") can mean different things in different parts of the business.
  • Services talk synchronously (REST – wait for an answer) or asynchronously (messages/events via a broker).
  • Database per service: never read another service's tables; use its API or events.
  • The 12-factor app rules (config in environment, stateless processes, logs as streams…) make services cloud-ready.
  • Every multi-service system needs discovery, gateway, config, resilience, tracing and a way to do business transactions (saga) – Part F covers them one by one.
  • Our demo works but uses a hard-coded URL and fails with 503 when product-service is down – the starting point for Topic 60.

Easy

Monolith or microservices? For each case decide and give one reason: (a) a 2-developer startup building a recipe-sharing app; (b) a bank with 400 developers whose "loans" module needs releases every day but "core accounts" only once a month; (c) a college project for a library system.

Hint / solution

(a) Monolith – tiny team, domain still changing, no ops capacity. (b) Microservices (at least for loans) – many teams, very different release speeds; independent deployment is a real benefit. (c) Monolith – small scope, one team, no scaling need.

@GetMapping("/search")

                     @Value("${product-service.base-url}") String url) {
    SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
    factory.setConnectTimeout(Duration.ofSeconds(2));
    factory.setReadTimeout(Duration.ofSeconds(2));
    this.restClient = builder.baseUrl(url).requestFactory(factory).build();
}

A read timeout throws ResourceAccessException (cause: SocketTimeoutException), so our existing catch block already returns 503. Remove the sleep afterwards!

Challenge

A third service. Create customer-service on port 8083 with GET /api/customers/{id}. Change order-service so OrderRequest also has customerId, and order-service calls customer-service to check the customer exists (404 if not). Count how many hard-coded URLs order-service now has – and think about what happens with 15 services.

Hint / solution

Copy product-service as a template (change artifactId, package, spring.application.name=customer-service, server.port=8083). In order-service add customer-service.base-url=http://localhost:8083 and a CustomerClient exactly like ProductClient. Call it first in placeOrder.

You now have 2 fixed URLs in order-service. With 15 services and several instances each, keeping these addresses correct by hand becomes impossible – which is why service discovery exists (next topic).

Challenge

Design a saga on paper. "Place order" needs: create order (order-service), reserve stock (inventory-service), charge card (payment-service). Payment fails. Write the steps and the compensating actions for choreography with events.

Hint / solution
  1. order-service creates order with status PENDING → publishes OrderCreated.
  2. inventory-service reserves stock → publishes StockReserved.
  3. payment-service tries to charge → fails → publishes PaymentFailed.
  4. Compensation: inventory-service listens to PaymentFailed → releases the stock; order-service listens → sets order to CANCELLED.

Each step is a local transaction in one service; failures are "undone" by new actions, not by a database rollback.

10. Interview questions

Q1. What is the difference between a monolith and microservices?

A monolith is a single deployable application containing all features, usually with one shared database; components call each other in-process. Microservices split the system into small, independently deployable services, each owning a business capability and its own data, communicating over the network (REST, gRPC, messaging). Microservices give independent deployment/scaling and team autonomy at the cost of distributed-system complexity.

Q2. When would you NOT choose microservices?

Small teams, early-stage products with an unclear domain, no DevOps automation (CI/CD, containers, monitoring), no real scaling or team-autonomy problem, or a need for strong ACID transactions across the whole domain. In those cases a well-structured modular monolith is cheaper and faster. "Monolith first" is a common recommendation.

Q3. What is a bounded context?

A DDD concept: a boundary inside which a domain model and its terms have one consistent meaning. The same word (e.g. "Product", "Customer") can have different models in different contexts (catalog vs shipping). Bounded contexts are natural candidates for microservice boundaries.

Q4. Why "database per service"? How do you query data across services then?

It keeps services loosely coupled: a team can change its schema without breaking others, and services can scale/choose storage independently. To combine data: call the owning service's API, store copies of the fields you need, or maintain read models updated by events (CQRS / API composition at the gateway or a BFF).

Q5. Synchronous vs asynchronous communication – when do you use which?

Synchronous (REST/gRPC) when the caller needs the answer immediately to continue (e.g. price lookup); it creates temporal coupling – if the callee is down, the caller is affected. Asynchronous messaging (Kafka/RabbitMQ) for events and commands that don't need an immediate reply (order placed → email, shipping); it decouples availability and smooths load but brings eventual consistency and more complex debugging.

Q6. How do you handle a transaction that spans several services?

Distributed 2-phase commit is avoided in microservices (slow, fragile). Instead use the Saga pattern: a sequence of local transactions, each publishing an event or triggered by an orchestrator; on failure, previously completed steps are undone by compensating transactions. Choreography (event-driven) or orchestration (central coordinator). Often combined with the Outbox pattern for reliable event publishing.

Q7. Name the common microservice patterns and the Spring Cloud tools for them.

Service discovery – Eureka (or Consul/Kubernetes DNS); client-side load balancing – Spring Cloud LoadBalancer; API gateway – Spring Cloud Gateway; centralized config – Spring Cloud Config; declarative clients – OpenFeign; resilience (circuit breaker, retry, rate limiter, bulkhead) – Resilience4j; distributed tracing – Micrometer Tracing + Zipkin; messaging – Spring Kafka/AMQP, Spring Cloud Stream; sagas – events or an orchestrator.

Q8. What is the 12-factor app? Name a few factors.

A methodology for cloud-native apps: one codebase, explicit dependencies, config in the environment, backing services as attached resources, separate build/release/run, stateless processes, port binding, scale by processes, disposability (fast start, graceful shutdown), dev/prod parity, logs as event streams, admin tasks as one-off processes.

Q9. What is a "distributed monolith"?

A system split into services that are still tightly coupled: shared database, shared model libraries, lock-step deployments, chatty synchronous call chains. It has the operational cost of microservices without their benefits – an anti-pattern.

Q10. In your order-service, product-service is down. What happens and how would you improve it?

The RestClient call throws ResourceAccessException; we translate it into 503. Improvements: timeouts so threads aren't blocked; a circuit breaker with a fallback (Resilience4j) so we fail fast; retries for transient errors; multiple instances behind service discovery/load balancing; caching product data; or making the flow asynchronous where possible.
