39. JPA Queries: Derived, JPQL & Native

Ask the database any question you like — from a one-word method name to hand-written SQL — and get back exactly the data you need.

🎯 What you will learn
  • Derived query methods: Spring writes the query from the method name (findByTitleContainingIgnoreCase, findByPriceBetween, OrderBy, Top/First, exists, count).
  • JPQL with @Query, named (:name) and positional (?1) parameters.
  • Native SQL queries and when you need them.
  • @Modifying bulk UPDATE/DELETE queries.
  • Projections: interface-based, record/DTO-based and dynamic.
  • Specifications and Query by Example for dynamic search forms.
  • Using Optional correctly with single-result queries.

1. Why this matters

In topic 38 you could load one product by id or all products. Real applications need much more:

  • "Show all books by Tolkien."
  • "Search for 'java' in the title, ignoring upper/lower case."
  • "Books between 10 and 20 euros, cheapest first."
  • "The 3 most expensive books."
  • "How many books per genre?" (a report)
  • "Raise all fantasy prices by 10%." (a bulk update)
  • A search form where the user fills in some of 5 filters.

Loading everything with findAll() and filtering in Java would be terribly slow with 1 million rows. The database must do the filtering. This lesson shows the five tools Spring Data JPA gives you to do that, from the easiest to the most powerful.

ℹ️ At work In a typical Spring Boot project, most repository methods are derived queries, a few are @Query JPQL, and a handful (reports, database-specific features) are native SQL. Search screens with many optional filters use Specifications (or Querydsl). Knowing which tool to pick is a skill interviewers check.

2. Real-life analogy

📚 Asking a librarian You walk into a library and want some books. You have several ways to ask:
1. Use the ready-made request form — tick boxes like "Author = ___", "Sort by = ___". The librarian knows exactly what to do. → Derived query methods (the method name is the form).
2. Write your request in the library's own language — "all Books whose title contains 'java'". You talk about books and titles, not shelves. → JPQL (talks about entities and fields).
3. Go into the storage room yourself with the floor plan — "shelf B, rows 3 to 7". Very powerful, but you must know how the building is organised, and the plan is different in every library. → Native SQL (tables and columns of one specific database).
4. "I only need the titles, not the whole books" → Projections.
5. "Change the price sticker on every fantasy book" in one go → @Modifying bulk update.

3.2 Derived query methods — the method name is the query

Spring Data reads the name of your method, splits it into pieces, and builds the query. The pattern is:

find / exists / count / delete+ (Top3 / First / Distinct)+ By+ Property + Keyword+ And / Or ...+ (OrderBy Property Asc/Desc) 
List<Book> findByTitleContainingIgnoreCase(String text);
//         \__/\___/\________/\_________/
//         find By  property   keywords

Hibernate turns it into this SQL (copied from the console):

select b1_0.id, b1_0.author, b1_0.available, ... b1_0.title
from books b1_0
where upper(b1_0.title) like upper(?) escape '\'

And Spring wraps your argument in %...% automatically. Zero SQL from you!

The four "subjects": find, exists, count, delete

List<Book>     findByAuthor(String author);          // rows

Other prefixes mean the same as find: read, get, query, search, stream. Most teams stick to find.

💡 Rule of thumb Use Optional<T> for methods that should find at most one row (by a unique column like ISBN, email, SKU). Then in the service: .orElseThrow(() -> new ResourceNotFoundException(...)) or .map(BookResponse::from). Never call .get() without checking.

When the method name becomes too long

findByPublishedYearGreaterThanEqualOrderByPublishedYearDesc is in our project on purpose — to show it works, but also that it is hard to read. When a name gets longer than about 3 conditions, switch to @Query.

ℹ️ Spring checks the names at startup If you write findByTitel (typo), the application fails to start with No property 'titel' found for type 'Book'. That's great: you learn about the mistake immediately, not in production.

3.3 JPQL with @Query

JPQL (Jakarta Persistence Query Language) looks like SQL, but it talks about entities and fields, not tables and columns:

JPQL (Java names)SQL (database names)
SELECT b FROM Book bSELECT * FROM books
WHERE b.publishedYear > 2000WHERE published_year > 2000
SELECT b.title FROM Book bSELECT title FROM books

Because JPQL uses Java names, Hibernate can translate it into the correct SQL dialect for H2, MySQL, PostgreSQL... — your query stays portable.

BookRepository.java@Query("""
        SELECT b FROM Book b
        WHERE LOWER(b.title)  LIKE LOWER(CONCAT('%', :keyword, '%'))
           OR LOWER(b.author) LIKE LOWER(CONCAT('%', :keyword, '%'))
        ORDER BY b.title
        """)
List<Book> searchByKeyword(@Param("keyword") String keyword);
  • b is an alias (a short nickname) for each Book.
  • :keyword is a named parameter, bound by @Param("keyword"). Values are sent safely as PreparedStatement parameters — no SQL injection.
  • The """ text block (topic 15) keeps long queries readable.
  • Like derived queries, JPQL is checked at startup: a typo in b.titel stops the app with a clear error.

Named vs positional parameters

@Query("SELECT b FROM Book b WHERE b.pages > ?1 ORDER BY b.pages DESC")   // ?1 = first argument
List<Book> findThickBooks(int minPages);

@Query("SELECT b FROM Book b WHERE b.pages > :minPages")                   // named - clearer
List<Book> findThickBooks2(@Param("minPages") int minPages);

Prefer named parameters: you can reorder method arguments without breaking the query, and the query explains itself.

ℹ️ Do I always need @Param? Spring Boot's Maven parent compiles with the -parameters flag, so Spring can read parameter names and @Param is often optional. Writing it anyway is safer and clearer, so this course always does.

Useful JPQL features

SELECT b FROM Book b WHERE b.genre IN :genres                      -- collection parameter
SELECT b FROM Book b WHERE b.price BETWEEN :min AND :max
SELECT b.author, COUNT(b) FROM Book b GROUP BY b.author HAVING COUNT(b) > 1
SELECT DISTINCT b.author FROM Book b
SELECT b FROM Book b WHERE b.genre = com.course.jpaqueries.entity.Genre.FANTASY   -- enum constant
SELECT b FROM Book b JOIN b.author a WHERE a.country = 'UK'         -- joins (topic 40)

3.4 Native SQL queries

Sometimes you need real SQL: a database-specific function, a window function, a query tuned by a DBA, or a reporting query over tables that have no entity. Add nativeQuery = true:

@Query(value = """
        SELECT * FROM books
        WHERE published_year BETWEEN :fromYear AND :toYear
        ORDER BY published_year
        """, nativeQuery = true)
List<Book> findPublishedBetweenNative(@Param("fromYear") int fromYear, @Param("toYear") int toYear);
JPQLNative SQL
Names usedEntity & field names (Book, publishedYear)Table & column names (books, published_year)
Portable across databases✅ Yes❌ Often not
Checked at startup✅ Yes❌ Only when it runs
DB-specific featuresLimited✅ Everything
ReturnsEntities, DTOs, scalarsEntities (if all columns), interface projections, Object[]
⚠️ Native = your responsibility Hibernate doesn't check native SQL at startup, and the query may break when you switch from H2 to MySQL. Use it when JPQL can't do the job, and cover it with a test.

3.5 @Modifying — bulk UPDATE and DELETE

To raise the price of every fantasy book, you could load them all, call setPrice on each and let dirty checking update them one by one. With 50,000 books that means 50,000 UPDATE statements. A single bulk statement is much faster:

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("UPDATE Book b SET b.price = b.price * :factor WHERE b.genre = :genre")
int applyPriceFactor(@Param("genre") Genre genre, @Param("factor") BigDecimal factor);
  • @Modifying tells Spring "this is not a SELECT". Without it you get "Query executed via 'getResultList()' must be a select query".
  • It needs a transaction: put @Transactional on the service method (or you get TransactionRequiredException).
  • The return value is the number of rows changed.
  • Bulk statements go directly to the database and skip the persistence context. Entities you already loaded still have the old price. clearAutomatically = true empties the persistence context after the query so the next read is fresh. flushAutomatically = true writes pending changes before the bulk query so they are not lost.
  • Bulk updates skip entity callbacks like @UpdateTimestamp and @Version increments. Set those columns yourself in the query if you need them.

3.6 Projections — fetch only what you need

Loading a whole entity when the screen only shows the title and author wastes memory and bandwidth. A projection returns a smaller shape.

a) Interface-based projection

dto/BookSummary.javapublic interface BookSummary {
    String getTitle();
    String getAuthor();
}

// in the repository:
List<BookSummary> findSummariesByGenre(Genre genre);

Generated SQL — only two columns!

select b1_0.title, b1_0.author from books b1_0 where b1_0.genre=?

Note the method name: findSummariesByGenre. Anything between find and By is ignored, so we can use it to make the name clearer.

b) Class-based (record/DTO) projection

public record AuthorStats(String author, Long bookCount, Double averagePrice) { }

@Query("""
        SELECT new com.course.jpaqueries.dto.AuthorStats(b.author, COUNT(b), AVG(b.price))
        FROM Book b
        GROUP BY b.author
        ORDER BY COUNT(b) DESC, b.author
        """)
List<AuthorStats> authorStatistics();

The SELECT new ... part is a constructor expression: JPQL calls the record's constructor for every row. You must write the fully qualified class name, and the types must match (COUNT returns Long, AVG returns Double). Records and simple DTOs can also be used with derived queries, if the constructor parameter names match the entity fields.

c) Native query + interface projection

@Query(value = "SELECT genre AS genre, COUNT(*) AS total FROM books GROUP BY genre ORDER BY total DESC",
       nativeQuery = true)
List<GenreCount> countBooksPerGenre();     // interface GenreCount { String getGenre(); long getTotal(); }

Here the SQL column aliases (AS genre, AS total) must match the getter names.

d) Dynamic projection — the caller chooses

<T> List<T> findByAuthorIgnoreCase(String author, Class<T> type);

repository.findByAuthorIgnoreCase("tolkien", BookSummary.class);  // light
repository.findByAuthorIgnoreCase("tolkien", Book.class);         // full entities
Projection typeHowProsCons
InterfaceInterface with gettersLeast code, works with derived queriesProxy objects, a bit "magic"
Record / DTOSELECT new ... or matching constructorPlain, fast, type-safe objects; ideal for APIsLong class name in JPQL
DynamicClass<T> parameterOne method, many shapesLess obvious to readers

3.7 Specifications — build the WHERE clause at runtime

A search form has 4 optional filters: genre, title, max price, available. That's 24 = 16 combinations. You can't write 16 repository methods! A Specification is one small condition object; you combine only the ones the user filled in.

repository/BookSpecifications.javapublic static Specification<Book> hasGenre(Genre genre) {
    return (root, query, cb) -> cb.equal(root.get("genre"), genre);
}
public static Specification<Book> priceAtMost(BigDecimal max) {
    return (root, query, cb) -> cb.lessThanOrEqualTo(root.get("price"), max);
}
  • root = "the Book row". root.get("price") = its price.
  • cb = CriteriaBuilder, a factory of conditions: equal, like, lessThan, between, and, or...
  • It is a lambda (topic 13) — Specification is a functional interface.

To use them, the repository also extends JpaSpecificationExecutor<Book>, which adds findAll(Specification), count(spec), exists(spec), and paging variants:

public interface BookRepository extends JpaRepository<Book, Long>, JpaSpecificationExecutor<Book> { ... }

// service: add only the filters that were sent
List<Specification<Book>> specs = new ArrayList<>();
if (genre != null)    specs.add(BookSpecifications.hasGenre(genre));
if (maxPrice != null) specs.add(BookSpecifications.priceAtMost(maxPrice));
List<Book> result = repository.findAll(Specification.allOf(specs));   // AND of all

// or directly:
repository.findAll(hasGenre(Genre.PROGRAMMING).and(priceAtMost(new BigDecimal("48"))));

("genre" as a String is not type-safe. Big projects generate a "metamodel" class Book_ so they can write root.get(Book_.genre). Another popular alternative library is Querydsl.)

3.8 Query by Example (QBE) — "find things that look like this"

You create an example ("probe") object, fill in the fields you care about, and ask: find everything similar.

Book probe = new Book(null, "martin", null, null, null, 0, 0, false);

ExampleMatcher matcher = ExampleMatcher.matching()
        .withIgnoreNullValues()                                       // null = don't care
        .withIgnoreCase()
        .withStringMatcher(ExampleMatcher.StringMatcher.CONTAINING)   // LIKE %martin%
        .withIgnorePaths("publishedYear", "pages", "available");      // primitives can't be null

List<Book> books = repository.findAll(Example.of(probe, matcher));   // Clean Code, Refactoring

Every JpaRepository supports QBE already (it extends QueryByExampleExecutor). It is nice for simple "filter by these text fields" screens, but it cannot do ranges (price < 20) or OR between different fields. For those, use Specifications.

3.9 Which one should I choose?

Simple 1–3 conditions?→Derived query
Complex / joins / GROUP BY / DTO?→@Query JPQL
DB-specific SQL feature?→Native query
Optional filters from a form?→Specifications (or QBE)
Change many rows?→@Modifying + @Transactional

4.1 Loading sample data: data.sql + defer-datasource-initialization

application.propertiesspring.jpa.hibernate.ddl-auto=create-drop
spring.jpa.defer-datasource-initialization=true

Spring Boot runs data.sql for embedded databases. By default it runs before Hibernate creates the tables — so the INSERT would fail with "Table BOOKS not found". The defer flag changes the order: tables first, then data.sql. Note the INSERTs don't include the id column, so the identity column generates 1–13 and later inserts don't collide.

4.2 The enum column

entity/Book.java@Enumerated(EnumType.STRING)
@Column(nullable = false, length = 20)
private Genre genre;

Default EnumType.ORDINAL stores the position (0, 1, 2...). If someone later inserts a new genre in the middle of the enum, all the existing numbers mean something else. STRING stores "FANTASY" — safe and readable.

4.4 The service — Optional, transactions, Specifications, QBE

service/BookService.java@Service
@Transactional(readOnly = true)
public class BookService {

    public BookResponse oldest() {
        return repository.findFirstByOrderByPublishedYearAsc()
                .map(BookResponse::from)                                   // Optional<Book> -> Optional<BookResponse>
                .orElseThrow(() -> new ResourceNotFoundException("The library is empty"));
    }

    @Transactional                     // bulk update needs a WRITE transaction
    public Map<String, Object> applyPriceFactor(Genre genre, BigDecimal factor) {
        if (factor.signum() <= 0) throw new IllegalArgumentException("factor must be positive");
        int updated = repository.applyPriceFactor(genre, factor);
        return Map.of("genre", genre, "factor", factor, "booksUpdated", updated);
    }

    public List<BookResponse> filter(Genre genre, String title, BigDecimal maxPrice, Boolean available) {
        List<Specification<Book>> specs = new ArrayList<>();
        if (genre != null) specs.add(BookSpecifications.hasGenre(genre));
        if (title != null && !title.isBlank()) specs.add(BookSpecifications.titleContains(title));
        if (maxPrice != null) specs.add(BookSpecifications.priceAtMost(maxPrice));
        if (available != null) specs.add(BookSpecifications.isAvailable(available));
        return toResponses(repository.findAll(Specification.allOf(specs)));
    }
}

Notice Boolean available (wrapper, not boolean) in filter: null means "the user didn't choose", which a primitive can't express.

4.5 The controller

Each endpoint maps to one service method, e.g. GET /api/books/search?keyword=tolkien → JPQL, GET /api/books/stats/genres → native, GET /api/books/filter?... → Specifications. @PathVariable Genre genre converts the text FANTASY into the enum automatically; an unknown value causes MethodArgumentTypeMismatchException, which our handler turns into a friendly 400.

src/test/java/com/course/jpaqueries/BookRepositoryTest.java@DataJpaTest

    @Test
    void modifyingUpdateChangesPrices() {

        assertThat(updated).isEqualTo(2);

                        .and(BookSpecifications.priceAtMost(new BigDecimal("48")))

6. Common mistakes

⚠️ "No property 'titel' found for type 'Book'" A typo in a derived method name, or using the column name (findByPublished_year) instead of the field name.
Fix: use the exact Java field name: findByPublishedYear.
⚠️ Using table names in JPQL @Query("SELECT b FROM books b") → "books is not mapped".
Fix: JPQL uses the entity name: FROM Book b. Only native queries use books.
⚠️ Forgetting @Modifying or @Transactional An UPDATE in @Query without @Modifying → "must be a select query". Without a transaction → TransactionRequiredException.
Fix: @Modifying on the repository method, @Transactional on the calling service method.
⚠️ Reading stale data after a bulk update You loaded a book, ran a bulk price update, read the book again — and saw the old price, because it came from the persistence context.
Fix: @Modifying(clearAutomatically = true).
⚠️ Optional return type, but many rows match Optional<Book> findByAuthor(String a) → IncorrectResultSizeDataAccessException for Tolkien (2 books).
Fix: Optional only for unique columns; otherwise return List.
🛑 Building queries by string concatenation "SELECT b FROM Book b WHERE b.title = '" + title + "'" (e.g. with entityManager.createQuery) opens the door to SQL/JPQL injection.
Fix: always use parameters (:title), derived queries or Specifications.
⚠️ Wrong types in a constructor expression record AuthorStats(String author, int bookCount, BigDecimal avg) → "Cannot instantiate class" / no matching constructor.
Fix: COUNT → Long, AVG → Double, SUM of BigDecimal → BigDecimal.

7. Best practices

  • Start with derived queries; move to @Query when the name gets longer than ~3 conditions.
  • Prefer JPQL over native SQL — portable and checked at startup. Use native only for things JPQL can't do, and test them.
  • Always use parameters, never concatenate user input into queries.
  • Return projections/DTOs for read-only screens and reports — fewer columns, less memory, no accidental lazy loading.
  • Use existsBy/countBy instead of loading entities just to check or count.
  • Use Optional for single results and handle the empty case in the service.
  • Bulk updates: @Modifying(clearAutomatically = true, flushAutomatically = true) + @Transactional; remember they skip entity callbacks and versioning.
  • Dynamic filters → Specifications (or Querydsl), not dozens of methods.
  • Add database indexes for columns you filter/sort on often (e.g. @Table(indexes = @Index(columnList = "author")) or a Flyway migration).
  • Never return huge lists — add paging (next topic!).
  • Watch the SQL log while developing; write a @DataJpaTest for every non-trivial query.

8. Key takeaways

  • Derived queries: find/exists/count/delete + By + Property + Keyword — Spring writes the query from the name and validates it at startup.
  • Keywords: And, Or, Between, LessThan, Containing, IgnoreCase, In, True, OrderBy, Top/First...
  • JPQL (@Query) uses entity/field names and named parameters (:name + @Param).
  • Native SQL (nativeQuery = true) uses table/column names — powerful but not portable.
  • @Modifying + @Transactional for bulk UPDATE/DELETE; use clearAutomatically.
  • Projections (interface, record with SELECT new, dynamic) fetch only needed columns.
  • Specifications and Query by Example build queries at runtime for optional filters.
  • Optional<T> for "0 or 1" results; List<T> for many.

10. Interview questions

Q1. How do derived query methods work?

At startup Spring Data parses the method name (subject like find…By, exists…By, count…By; then property expressions and keywords like And, Between, IgnoreCase, OrderBy), validates the properties against the entity and builds a JPA criteria query. Invalid names make the application fail on startup.

Q2. What is the difference between JPQL and SQL?

JPQL is an object-oriented query language that works on entities and their fields (FROM Book b WHERE b.publishedYear) and is translated by the JPA provider into SQL for the configured database. SQL works on tables and columns and is database-specific. JPQL is portable and validated at startup; native SQL gives access to all database features.

Q3. When would you use a native query?

For database-specific features (window functions, JSON operators, full-text search, hints), heavily tuned reporting queries, or tables without entities. Downsides: not portable, not validated at startup, and results map less naturally (interface projections or Object[]).

Q4. What does @Modifying do and what are clearAutomatically / flushAutomatically?

@Modifying marks a @Query as an INSERT/UPDATE/DELETE so it's executed with executeUpdate(), returning the affected row count; it requires a transaction. Bulk queries bypass the persistence context, so flushAutomatically flushes pending changes before the query and clearAutomatically clears the persistence context afterwards to avoid stale entities.

Q5. What are projections? Name the types.

Projections return a subset of entity data. Interface-based (closed projections with getters; Spring creates proxies, and only needed columns are selected), class-based/DTO (records or classes via constructor expressions SELECT new ... or matching constructor parameters), and dynamic projections (<T> List<T> findBy...(…, Class<T> type)). Open projections with @Value SpEL also exist but select all columns.

Q6. Named vs positional parameters?

Positional: ?1, ?2 bound by argument order. Named: :name bound with @Param("name") (or the compiled parameter name). Named parameters are more readable and robust when arguments are reordered. Both are bound as prepared-statement parameters, preventing injection.

Q7. What is the Specification API and when do you use it?

A Specification<T> wraps a JPA Criteria predicate (toPredicate(root, query, cb)). Specifications are composable with and/or/not, and executed via JpaSpecificationExecutor. They are ideal for dynamic searches where filters are optional and combined at runtime.

Q8. What is Query by Example and its limitations?

QBE builds a query from a probe entity plus an ExampleMatcher (ignore nulls, case, string matching). It's simple for equality/LIKE on several fields, but cannot express ranges, OR across properties, or nested groupings, and primitive fields need explicit ignoring.

Q9. What happens if a method returns Optional<T> but the query finds two rows?

Spring throws IncorrectResultSizeDataAccessException (wrapping JPA's NonUniqueResultException). Single-result return types should only be used for queries that are unique by design, e.g. by a unique column or with findFirst/findTop1.

Q10. How do Top / First work and what SQL do they produce?

findTop3By... / findFirst3By... limit the result size, usually combined with OrderBy. Hibernate translates the limit into the database dialect — e.g. FETCH FIRST ? ROWS ONLY (H2, PostgreSQL, Oracle) or LIMIT ? (MySQL). Without a number, First means 1.
