29. Configuration Properties & Profiles

Keep settings OUT of your Java code, read them safely, switch between dev and prod with one word, and keep secrets out of Git.

🎯 What you will learn
  • application.properties vs application.yml — the same configuration written both ways.
  • Common built-in properties such as server.port and spring.application.name.
  • Reading custom values with @Value (with defaults).
  • Type-safe configuration with @ConfigurationProperties on a record, plus validation at startup.
  • Profiles: application-dev.yml, application-prod.yml, spring.profiles.active.
  • The external configuration order (command line > environment variables > files).
  • Environment variables for secrets, and good advice about .env files.

1. Why this matters

Your app runs in several places: on your laptop, on a test server, and in production. Each place needs different settings:

SettingOn your laptop (dev)In production (prod)
DatabaseH2 in memoryReal MySQL server
Port808080 / 443 behind a load balancer
Log levelDEBUG (lots of detail)INFO / WARN (quiet)
Payment API keyA free test keyThe real secret key

If these values were written inside Java code, you would need to change code and rebuild for every environment — slow and risky. And a password in code ends up in Git, where anyone with access can read it. Real incidents have happened because a secret key was pushed to a public GitHub repo.

Spring Boot's answer: one jar, configured from outside. The code stays the same; only the configuration changes. This idea is also rule #3 of the famous "Twelve-Factor App" guidelines: store config in the environment. You will use it in every Spring project, every day.

2. Real-life analogy

📺 The TV and its settings menu

A TV factory builds one model of TV and ships it to many countries. The factory does not build a different TV for each home. Instead, each owner opens the settings menu: language, brightness, channel list, Wi-Fi password.

  • The TV = your jar (same everywhere).
  • The settings menu = application.yml.
  • "Picture modes" like Cinema or Sports = profiles (dev, prod): a whole group of settings switched with one choice.
  • The remote control overriding everything for tonight = command-line arguments (highest priority).
  • The Wi-Fi password you type in privately, never printed in the manual = secrets in environment variables.

3. Concepts step by step

3.1 Where Spring Boot looks for configuration

At startup Spring Boot automatically reads src/main/resources/application.properties and/or application.yml (they end up inside the jar). You don't need @PropertySource like in topic 26 — it just works. All values go into Spring's Environment, which every bean can read.

3.2 .properties vs .yml — the same config written two ways

.properties = one key=value per line, with dots in the key. .yml (YAML) = a tree; indentation shows nesting.

⚠️ YAML rules for beginners Use spaces, never TABs. Put a space after the colon (port: 8080, not port:8080). Quote values that start with special characters ("+91...", "*", "@"). Same indentation = same level.

3.4 Your own properties with @Value

You can invent your own keys (shop.welcome-message) and inject them with @Value("${...}"):

@Value("${spring.application.name}")            // required: startup fails if missing
private String appName;

@Value("${shop.welcome-message:Welcome!}")      // default after the colon
private String welcomeMessage;

@Value("${features.new-checkout:false}")        // "true"/"false" text -> boolean
private boolean newCheckoutEnabled;

${key:default} means "the value of key, or default if nobody set it". Spring converts the text to the field's type (int, boolean, Duration…).

ℹ️ @Value is fine for one or two values But when you have a group of related settings, @Value strings get copied around, have no auto-complete and are easy to mistype. A typo like ${shop.dicount-percent} only fails at runtime. For groups, use @ConfigurationProperties.

3.5 Type-safe configuration with @ConfigurationProperties

Idea: describe a group of settings as a Java type, and let Spring Boot fill it from every key that starts with a prefix. A record (topic 15) is perfect — immutable, short and clear:

@ConfigurationProperties(prefix = "shop")
public record ShopProperties(
        String name,
        String currency,
        int discountPercent,           // from shop.discount-percent
        Duration sessionTimeout,       // "30m" -> Duration.ofMinutes(30)
        List<String> supportedPaymentMethods,
        Contact contact) {             // nested group shop.contact.*

    public record Contact(String email, String phone) { }
}

Then you register it (we use @ConfigurationPropertiesScan on the main class) and inject it like any bean:

public ConfigController(ShopProperties shop) { this.shop = shop; }
...
shop.discountPercent();   // 5 - a real int, checked by the compiler
application.yml
shop.discount-percent: 5→ binding → ShopProperties record
discountPercent = 5→ inject → Any bean

Relaxed binding: Spring matches discount-percent (kebab-case, recommended in files), discountPercent, discount_percent and the environment variable SHOP_DISCOUNTPERCENT to the same Java component discountPercent.

Default values: use @DefaultValue("INR") on a record component — used when the key is missing.

3.6 Validating configuration at startup

Add spring-boot-starter-validation, put @Validated on the class and constraint annotations on the components:

@Validated
@ConfigurationProperties(prefix = "shop")
public record ShopProperties(
        @NotBlank String name,
        @Min(0) @Max(50) @DefaultValue("0") int discountPercent,
        @NotEmpty List<String> supportedPaymentMethods,
        @Valid Contact contact) {                    // @Valid = validate inside the nested record too
    public record Contact(@Email @NotBlank String email, String phone) { }
}

Now a wrong value stops the app immediately with a clear message — this is the real output when starting with --shop.discount-percent=80:

3.7 Profiles — groups of settings for each environment

A profile is a named set of configuration. Spring Boot loads application.yml first, then application-{profile}.yml for each active profile, and the profile file overrides matching keys.

application.yml
shared by all+ application-dev.yml
only when "dev" is active= final config
Keyapplication.ymlapplication-dev.ymlapplication-prod.ymlResult with devResult with prod
shop.nameShopEasyShopEasy (DEV)ShopEasyShopEasy (DEV)ShopEasy
shop.discount-percent5200200
shop.currencyINR––INRINR
server.port8080–808180808081
features.new-checkoutfalsetruefalsetruefalse

Activating a profile (any one of these):

# in application.yml (a default for the team):
spring.profiles.active: dev

# command line (overrides the file):
java -jar app.jar --spring.profiles.active=prod
mvn spring-boot:run -Dspring-boot.run.profiles=prod

# environment variable (typical in Docker / Kubernetes):
$env:SPRING_PROFILES_ACTIVE="prod"      # PowerShell
export SPRING_PROFILES_ACTIVE=prod      # Linux / macOS

Several profiles at once: --spring.profiles.active=prod,mysql (later ones win on conflicts). Profiles also switch beans on and off with @Profile("dev") exactly as in topic 26. If no profile is active, Spring Boot uses the profile named default.

ℹ️ One file, many profiles You can also put several profiles in one YAML file separated by --- and spring.config.activate.on-profile: prod. Separate files are easier for beginners, so we use them.

3.8 Externalized configuration — who wins?

The same key can be set in many places. Spring Boot has a fixed order. Higher in the table wins. (Simplified — the full list in the docs has 15+ entries.)

PrioritySourceExample
1 (highest)Command-line arguments--server.port=9000
2Java system propertiesjava -Dserver.port=9000 -jar app.jar
3OS environment variablesSERVER_PORT=9000
4Profile files outside the jar./config/application-prod.yml
5Normal files outside the jar./application.yml next to the jar
6Profile files inside the jarapplication-prod.yml in resources
7 (lowest)Normal files inside the jarapplication.yml in resources

Easy way to remember: "the closer to the moment of starting, the stronger". Files packed in the jar are the defaults; the operator starting the app can override anything without rebuilding.

Environment variable names: uppercase, replace dots and dashes with underscores: server.port → SERVER_PORT, shop.discount-percent → SHOP_DISCOUNTPERCENT (dashes are simply removed), spring.profiles.active → SPRING_PROFILES_ACTIVE.

3.9 Secrets: environment variables, not Git

Passwords, API keys and tokens must never be committed. Use a placeholder in the file, and give the real value through an environment variable:

payment:
  api-key: ${PAYMENT_API_KEY:not-set}    # env var, or "not-set" if missing
# PowerShell (only for this terminal window):
$env:PAYMENT_API_KEY="sk_test_12345678"
mvn spring-boot:run

In production, the platform injects the variable (Docker -e, Kubernetes Secrets, cloud secret managers, CI secrets — topics 66–69).

⚠️ About .env files
  • A .env file is a simple text file with KEY=value lines, used by Docker Compose (topic 67) and many tools to set environment variables.
  • Spring Boot does not read .env by itself. Docker Compose, your IDE run configuration or a tool loads it into the environment, and Spring reads the environment.
  • Always add .env to .gitignore. Commit a .env.example with fake values so teammates know which variables exist.
  • Never print secrets in logs or return them from an API (our /config/secret endpoint only shows a masked value).

4.3 ShopProperties

src/main/java/com/course/configprops/ShopProperties.java@Validated
@ConfigurationProperties(prefix = "shop")
public record ShopProperties(
        @NotBlank String name,
        @NotBlank @DefaultValue("INR") String currency,
        @Min(0) @Max(50) @DefaultValue("0") int discountPercent,
        @Positive @DefaultValue("10") int maxItemsPerOrder,
        @DefaultValue("30m") Duration sessionTimeout,
        @NotEmpty List<String> supportedPaymentMethods,
        @Valid Contact contact
) {
    public record Contact(@Email @NotBlank String email, String phone) { }
}

Line by line:

  • prefix = "shop" — only keys beginning with shop. are bound.
  • Each record component maps to a key: maxItemsPerOrder ← shop.max-items-per-order.
  • Duration understands 30m, 10s, 2h, 500ms. (There is also DataSize for 10MB.)
  • List<String> is filled from the YAML list.
  • @Valid Contact contact — without @Valid, the rules inside Contact would be ignored.

6. Common mistakes

❌ Mistake: TABs or wrong indentation in YAML Error like found character '\t' that cannot start any token or values silently ending up under the wrong parent.
Fix: use 2 spaces per level. In VS Code, the status bar shows "Spaces: 2" — click it to convert tabs.
⚠️ Mistake: "Could not resolve placeholder 'shop.welcom-message'" A typo in a @Value key, or a key with no value and no default.
Fix: check the spelling, or add a default: ${key:default}. Better: move groups of values into @ConfigurationProperties.
⚠️ Mistake: profile file named wrongly application_dev.yml or dev-application.yml is ignored. The pattern is exactly application-{profile}.yml.
⚠️ Mistake: @ConfigurationProperties class is never filled You forgot @ConfigurationPropertiesScan / @EnableConfigurationProperties → "No qualifying bean of type ShopProperties".
Fix: add one of them (or, for a normal class, @Component).
⚠️ Mistake: validation annotations are ignored You forgot @Validated on the class, @Valid on a nested object, or the spring-boot-starter-validation dependency.
⚠️ Mistake: having BOTH application.properties and application.yml Both are loaded (properties wins on conflicts). Debugging which value you get becomes painful. Pick one format per project.
❌ Mistake: committing secrets spring.datasource.password=SuperSecret123 in Git stays in history forever, even if you delete it later.
Fix: ${DB_PASSWORD} placeholders + environment variables; .env in .gitignore; rotate any leaked secret immediately.
⚠️ Mistake: putting spring.profiles.active inside a profile file Spring Boot does not allow activating profiles from application-dev.yml (it fails at startup). Set it in application.yml, on the command line or as an env var.

7. Best practices

  • Prefer @ConfigurationProperties records for anything more than one value; validate them with @Validated.
  • Use kebab-case keys in files (max-items-per-order) and a clear prefix per feature (shop.*, payment.*).
  • Defaults in application.yml, differences in profile files. Keep profile files small.
  • Common profile names: dev, test, prod (plus technology profiles like mysql in topic 43).
  • Secrets only via environment variables or a secret manager (Vault, AWS Secrets Manager, Kubernetes Secrets). Never in Git, never in logs.
  • Same jar everywhere. Never rebuild to change a setting; change the environment instead.
  • Don't hard-code spring.profiles.active: prod into the packaged jar — let the server choose.
  • Document your custom keys (the configuration processor + Javadoc comments on the record give auto-complete help).
  • In microservices, configuration can be centralised in a Config Server (topic 62).

8. Key takeaways

  • Spring Boot reads application.properties / application.yml automatically — same keys, two formats.
  • @Value("${key:default}") reads single values.
  • @ConfigurationProperties(prefix=...) on a record = type-safe, validated groups of settings with relaxed binding.
  • @Validated + Bean Validation stops the app at startup when config is wrong.
  • Profiles: application-{profile}.yml overrides the base file; activate with spring.profiles.active.
  • Priority: command line > system properties > environment variables > files outside the jar > files inside the jar.
  • Secrets come from environment variables via ${ENV_VAR} placeholders. .env files stay out of Git.

10. Interview questions

Q1. What is the difference between @Value and @ConfigurationProperties?

@Value injects single values by key and supports SpEL. @ConfigurationProperties binds a whole group of keys with a prefix to a typed object with relaxed binding, JSR-303 validation and IDE metadata. Use @ConfigurationProperties for structured configuration.

Q2. What is a Spring profile and how do you activate one?

A named set of configuration and beans for an environment. Activate with spring.profiles.active in a config file, --spring.profiles.active=prod, -Dspring.profiles.active=prod, the env var SPRING_PROFILES_ACTIVE, or @ActiveProfiles in tests.

Q3. Explain the order of precedence of configuration sources in Spring Boot.

Roughly: command-line args > Java system properties > OS environment variables > profile-specific files outside the jar > application files outside the jar > profile-specific files inside the jar > application files inside the jar > defaults. Later/more specific sources override earlier ones.

Q4. What is relaxed binding?

Spring Boot maps different spellings of a key to the same property: my-prop, myProp, my_prop and MYPROP/MY_PROP env vars all bind to a field myProp in a @ConfigurationProperties class.

Q5. How do you validate configuration properties?

Add spring-boot-starter-validation, annotate the properties class with @Validated and its fields with constraints like @NotBlank, @Min; use @Valid for nested objects. Invalid values make startup fail with a descriptive message.

Q6. How do you manage secrets in a Spring Boot application?

Never commit them. Reference them with placeholders (${DB_PASSWORD}) and supply via environment variables, Docker/Kubernetes secrets, or a secret manager (Vault, AWS Secrets Manager, Azure Key Vault), optionally through Spring Cloud Config/Vault integrations. Don't log them.

Q7. application.properties vs application.yml — which is better?

Functionally equivalent. YAML is hierarchical and less repetitive, good for nested/list config; properties are simpler and less error-prone regarding indentation. Choose one per project. If both exist, both are loaded and .properties takes precedence for the same key.

Q8. How can you have a different bean in dev and prod?

Annotate the bean classes or @Bean methods with @Profile("dev") / @Profile("prod") (or @ConditionalOnProperty). Only beans of active profiles are created.

Q9. Where can application.yml live outside the jar?

In the current directory, in a config/ subdirectory of the current directory, or any location given by spring.config.location / spring.config.additional-location. You can also import files with spring.config.import. External files override the packaged ones.
