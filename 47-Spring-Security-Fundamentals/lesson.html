1. Why this matters

Until now every API we built was wide open. Anybody who knew the URL could read, change or delete data. In a real company that is unthinkable. A bank API must know who is calling before it shows a balance. A shop must make sure only staff can change prices. A hospital system must hide patient records from everyone except doctors.

Spring Security is the standard way to protect Spring applications. Almost every Spring Boot project you will meet at work uses it. It is powerful, but it has a reputation for being "magic" and confusing. The good news: once you understand one picture – the filter chain – everything else falls into place. This lesson builds that picture slowly.

ℹ️ Where you will see this at work Login screens, "Access denied" pages, admin-only buttons, API keys and tokens, "Your session expired" messages, CORS errors in the browser console… All of these are Spring Security (or something like it) doing its job. Topics 47–50 cover the whole journey: 47 fundamentals → 48 users in a database → 49 JWT tokens → 50 OAuth2 / "Login with Google".

2. Real-life analogy

✈️ Think of an airport

Authentication = the passport check. At the counter an officer looks at your passport and your face. The question is only: "Are you really the person you claim to be?" If you cannot prove it, you do not get in at all.

Authorization = the boarding pass. Now they know who you are. But your boarding pass says Gate 12, Economy. You may not walk into the Business lounge or board the flight to Tokyo. The question is: "Is this person allowed to do this?"

The security checkpoints = the filter chain. Every traveller passes the same row of checkpoints in the same order: ticket scan → passport → baggage scanner → gate. Each checkpoint does one job and either lets you through to the next one or stops you. Spring Security works exactly like this: every HTTP request walks through a row of filters.

401 vs 403. No passport at all? "Sorry, who are you?" → 401 Unauthorized. Valid passport but trying to enter the pilots' room? "We know who you are, but you are not allowed" → 403 Forbidden.

3. Concepts step by step

3.1 Authentication vs Authorization

These two long words are the heart of security. People mix them up all the time, even in interviews, so let us fix them in our heads now.

Authentication (AuthN)Authorization (AuthZ)
QuestionWho are you?What are you allowed to do?
HappensFirstAfter authentication
ProofPassword, token, fingerprint, certificateRoles / permissions of the known user
Failure status401 Unauthorized (badly named – it really means "unauthenticated")403 Forbidden
Spring Security pieceAuthenticationManager, UserDetailsService, PasswordEncoderauthorizeHttpRequests(...), hasRole(...), @PreAuthorize (topic 48)
💡 Memory trickAuthentication = identity card. Authorization = permission. You need the first before the second makes any sense.

3.2 What happens when you just add the starter?

Take any web project and add one dependency:

pom.xml<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Restart the app. Without writing a single line of code, Spring Boot's auto-configuration (topic 28) does all of this:

  • Every URL is locked. Even /api/books that worked a minute ago now answers 401.
  • It creates one user called user with a random password printed in the console:
Using generated security password: 8e557245-73e2-4286-969a-ff57fe326336

This generated password is for development use only. Your security configuration must be updated before running your application in production.
  • A browser gets an automatic login page at /login and a logout page at /logout.
  • curl / Postman can use HTTP Basic: curl -u user:8e557245-... http://localhost:8080/api/books.
  • Protection against common attacks is switched on: CSRF tokens, security headers (X-Content-Type-Options, X-Frame-Options, cache control…), session fixation protection.

You can fix the default user's name and password in application.properties – handy for a quick demo:

spring.security.user.name=admin
spring.security.user.password=secret
spring.security.user.roles=ADMIN
ℹ️ "Secure by default" Spring Security prefers to lock too much rather than too little. Your job is to open up what should be public and to describe the rest. As soon as you declare your own SecurityFilterChain and UserDetailsService beans (we do that in this project), the generated user and password disappear.

3.3 Filters – the checkpoints in front of your controllers

A servlet filter is a small piece of code that the web server (Tomcat) runs before a request reaches Spring MVC's DispatcherServlet (remember the diagram from topic 31). A filter can look at the request, change it, stop it (for example answer 401 immediately), or pass it on to the next filter.

Spring Security is, at its core, a list of filters. Here is the full picture – read it from left to right, the way a request travels:

Three names in that picture are worth knowing:

  • DelegatingFilterProxy – a normal servlet filter registered in Tomcat. It knows nothing about security; it simply hands the request to a Spring bean.
  • FilterChainProxy – that Spring bean (named springSecurityFilterChain). It picks the right SecurityFilterChain for this URL and runs its filters.
  • SecurityFilterChain – your configuration: the list of filters and rules. You can even have several chains (e.g. one for /api/**, one for the website).

The most important filters, in the order they run:

FilterIts one job
SecurityContextHolderFilterLoads the "who is logged in" information for this request (e.g. from the HTTP session) and cleans it up afterwards.
HeaderWriterFilterAdds protective response headers (X-Content-Type-Options: nosniff, X-Frame-Options, cache control…).
CorsFilterAnswers browser CORS "preflight" requests (3.10).
CsrfFilterFor POST/PUT/DELETE: checks that a valid CSRF token is present (3.9).
LogoutFilterHandles POST /logout.
UsernamePasswordAuthenticationFilterHandles the login form: POST /login with username + password.
BasicAuthenticationFilterReads the Authorization: Basic ... header and logs the user in for this request.
AnonymousAuthenticationFilterIf nobody logged in so far, marks the request as "anonymous user".
ExceptionTranslationFilterCatches security exceptions from the filters after it and turns them into 401 (ask for login) or 403 (access denied).
AuthorizationFilterThe final gate: checks your authorizeHttpRequests rules. Allowed → go to the controller. Not allowed → throws an exception.
💡 See it with your own eyes This project sets logging.level.org.springframework.security=DEBUG. At startup you will see a line like Will secure any request with filters: DisableEncodeUrlFilter, WebAsyncManagerIntegrationFilter, SecurityContextHolderFilter, HeaderWriterFilter, CorsFilter, CsrfFilter, LogoutFilter, UsernamePasswordAuthenticationFilter, DefaultResourcesFilter, DefaultLoginPageGeneratingFilter, DefaultLogoutPageGeneratingFilter, BasicAuthenticationFilter, ... and for every request a log of which filter is running. Reading that log is the best way to learn.

3.4 The main characters: who does what during login?

When a filter (Basic or form) receives a username and password, it does not check them itself. It asks a small team of objects:

ObjectSimple meaning
Authentication"A user's ID card" – name (principal), credentials, and authorities. Before login it holds the typed password; after login it is marked authenticated.
GrantedAuthorityOne permission string, e.g. ROLE_ADMIN or REPORT_READ.
SecurityContext / SecurityContextHolderThe "pocket" where the current request's Authentication is kept. Technically a ThreadLocal (topic 17): each request thread has its own pocket.
AuthenticationManagerThe "reception desk" that receives a login attempt and decides yes/no by asking its providers.
DaoAuthenticationProviderThe standard username + password checker.
UserDetailsServiceYou provide this. One method: loadUserByUsername(String) → returns a UserDetails.
UserDetailsWhat Spring needs to know about a user: username, password hash, authorities, enabled/locked flags.
PasswordEncoderYou provide this. Hashes passwords and checks matches(raw, hash).

3.5 Your own rules: the SecurityFilterChain bean (Lambda DSL)

To describe your own rules, you create a @Bean method that receives an HttpSecurity builder, configures it, and returns http.build(). Each part is configured with a lambda (topic 13) – this style is called the Lambda DSL (DSL = "domain specific language", a mini language for one job).

SecurityConfig.java (core part)@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/public/**", "/error").permitAll()
            .requestMatchers(HttpMethod.GET, "/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated()
        )
        .httpBasic(Customizer.withDefaults())
        .formLogin(Customizer.withDefaults());
    return http.build();
}

Read it like English: "Public URLs: everyone. GET on admin URLs: only role ADMIN. Any other request: must be logged in. People may log in with HTTP Basic or with a login form." Customizer.withDefaults() means "switch this feature on with its default settings".

RuleMeaning
permitAll()Everybody, even anonymous users.
authenticated()Any logged-in user, whatever their role.
hasRole("ADMIN")User must have authority ROLE_ADMIN (Spring adds the ROLE_ prefix for you).
hasAnyRole("ADMIN", "TEACHER")At least one of these roles.
hasAuthority("REPORT_READ")Exact authority string, no prefix added (topic 48).
denyAll()Nobody. Useful to block old endpoints.
⚠️ Order matters: first match wins Rules are checked top to bottom and the first matching rule decides. Put specific rules first and the catch-all anyRequest() last. If you write anyRequest().authenticated() first, Spring refuses to start: "Can't configure requestMatchers after anyRequest".
ℹ️ Old tutorials: WebSecurityConfigurerAdapter Many blog posts extend a class called WebSecurityConfigurerAdapter and use .antMatchers(...) and .and(). That class was removed in Spring Security 6 (Spring Boot 3). Today you declare a SecurityFilterChain bean, use requestMatchers(...) and the Lambda DSL – exactly like this lesson.

3.6 In-memory users

The simplest UserDetailsService keeps users in a Map in memory. Spring ships one: InMemoryUserDetailsManager.

@Bean
public UserDetailsService userDetailsService(PasswordEncoder encoder) {
    UserDetails student = User.withUsername("student")
            .password(encoder.encode("student123"))   // store the HASH, never the plain text
            .roles("USER")                            // becomes authority "ROLE_USER"
            .build();
    UserDetails admin = User.withUsername("admin")
            .password(encoder.encode("admin123"))
            .roles("USER", "ADMIN")
            .build();
    return new InMemoryUserDetailsManager(student, admin);
}

Roles vs authorities: internally Spring only knows authorities (plain strings). A role is just an authority that starts with ROLE_. .roles("ADMIN") stores ROLE_ADMIN; hasRole("ADMIN") checks for ROLE_ADMIN. Same thing, two spellings.

⚠️ In-memory users are for demos only They vanish on restart, nobody can register, and passwords live in your source code. Topic 48 moves users into a database.

3.7 Passwords: why hashing, and why BCrypt?

Imagine your database is stolen (it happens to big companies every year). What does the thief see?

Storage methodThief seesVerdict
Plain textstudent123❌ Disaster. People reuse passwords – now their email is also hacked.
Encryption (two-way)x8Gh2... – but the key is usually on the same server❌ Steal the key → read all passwords.
Fast hash (MD5, SHA-256)5e884898da...❌ Graphics cards try billions of guesses per second; "rainbow tables" reverse common passwords instantly.
BCrypt (slow, salted hash)$2a$10$BXvSBHNhnNKb70yO925NG.33EZ0...✅ Each guess is deliberately slow, and a random salt makes every hash unique.

A hash is a one-way function: easy to go from password → hash, practically impossible to go back. At login we do not "decrypt" anything. We hash what the user typed and compare. BCrypt adds two extras:

  • Salt – a random value mixed into each hash. Two users with the password student123 get different hashes, so one cracked hash does not reveal the other.
  • Cost factor (work factor) – the number of rounds (210 = 1024 by default). Checking one password takes ~0.1 s: nothing for a user logging in, but a nightmare for an attacker trying billions.

Anatomy of a BCrypt hash (60 characters):

$2a$+ 10$+ BXvSBHNhnNKb70yO925NG.+ 33EZ0SL5b5WL0kv2zxKlw8g7sjdlWhu

algorithm version · cost (210 rounds) · 22-char salt · 31-char hash

Our project's PasswordHashingDemo prints this at startup (real output from a run):

---- BCrypt demo ----
hash #1 = $2a$10$BXvSBHNhnNKb70yO925NG.33EZ0SL5b5WL0kv2zxKlw8g7sjdlWhu
hash #2 = $2a$10$HGbyWnsTih5wTMymH3rVGO9WBEGbODCq5hTD7INtW/0eeiyoM.atm
Same password, different hashes? true
matches("student123", hash #1) = true
matches("student123", hash #2) = true
matches("wrong",      hash #1) = false

How can matches work if the hashes differ? Because the salt is stored inside the hash string. BCrypt reads the salt and cost from it, hashes the typed password the same way, and compares.

ℹ️ {bcrypt} and {noop} prefixes If you do not declare a PasswordEncoder bean, Spring uses a DelegatingPasswordEncoder that expects a prefix telling which algorithm was used: {bcrypt}$2a$10$..., or {noop}secret for plain text (demo only). Without a prefix you get the famous error "There is no PasswordEncoder mapped for the id null". Declaring a BCryptPasswordEncoder bean, as we do, avoids that. Other good algorithms: Argon2, SCrypt, PBKDF2.

3.8 HTTP Basic vs Form login

Both are ways for the user to hand over a username and password. They suit different clients:

HTTP BasicForm login
Who uses itScripts, curl, Postman, server-to-serverHumans in a browser
HowHeader on every request: Authorization: Basic c3R1ZGVudDpzdHVkZW50MTIzHTML form posts to /login once; then a session cookie JSESSIONID is sent automatically
Server remembers you?No (password sent each time)Yes, in the HTTP session
LogoutNot really (client just stops sending)POST /logout destroys the session
Enable with.httpBasic(Customizer.withDefaults()).formLogin(Customizer.withDefaults())

That strange Basic header value is just Base64 of username:password. Base64 is an encoding, not encryption – anybody can decode it:

PS> [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String("c3R1ZGVudDpzdHVkZW50MTIz"))
student:student123
🔒 Always HTTPS in production With HTTP Basic (and with form login too) the password travels over the network. Without HTTPS anyone on the same Wi-Fi can read it. Locally we use plain HTTP for learning; real servers must use HTTPS (TLS).

Both at once? Yes – our project enables both. When a protected URL is called without login, Spring looks at the request: a browser (it sends Accept: text/html) is redirected (302) to the login page; curl and other API clients get 401 with the header WWW-Authenticate: Basic realm="Realm".

3.9 CSRF – what it is and when to disable it

CSRF = Cross-Site Request Forgery. The attack works because browsers send cookies automatically.

🏦 The trick You are logged in to mybank.com (your browser holds the session cookie). In another tab you open a funny cat website. Hidden on that page is a form that silently POSTs to mybank.com/transfer?to=thief&amount=1000. Your browser happily attaches your bank cookie – and the bank thinks you sent it.

The defence: for every state-changing request (POST, PUT, PATCH, DELETE), the server demands a secret CSRF token that only its own pages know (for example a hidden field in the form). The cat website cannot read that token, so its forged request is rejected with 403. Spring Security does this automatically – that is why a plain curl -X POST to a cookie-based app fails with 403.

When may you switch it off? When the client does not use cookies for authentication – for example a pure REST API that is called with an Authorization header (HTTP Basic or a token, topic 49). A foreign website cannot make the browser add that header by itself, so CSRF is impossible.

// Option A - our project: keep CSRF for the browser pages, ignore it for the REST API
.csrf(csrf -> csrf.ignoringRequestMatchers("/api/**"))

// Option B - a 100% stateless API without sessions or cookies (topic 49)
.csrf(csrf -> csrf.disable())
⚠️ Do not disable CSRF "because POST did not work" If your app uses session cookies (form login, server-side pages like Thymeleaf from topic 36), keep CSRF on. Thymeleaf forms add the token automatically.

3.10 CORS with Spring Security

Recap from topic 32: browsers follow the same-origin policy. JavaScript on http://localhost:3000 (say a React app) may not read responses from http://localhost:8080 unless the server says it is OK with Access-Control-Allow-Origin headers. For "non-simple" requests (e.g. with an Authorization header) the browser first sends a preflight: an OPTIONS request without credentials.

That is the problem: if security runs first, it sees an unauthenticated OPTIONS request and answers 401 – the browser then blocks the real call. The fix is to let Spring Security handle CORS first with .cors(...) and a CorsConfigurationSource bean:

.cors(Customizer.withDefaults())   // uses the CorsConfigurationSource bean below

@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("http://localhost:3000"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    config.setAllowCredentials(true);
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", config);
    return source;
}
ℹ️ CORS is not a lock on your server CORS only tells browsers which other websites may read your responses. curl and Postman ignore it completely. It protects users' browsers; it does not replace authentication.

3.11 401 vs 403 – three requests traced step by step

Let us follow three real requests through our project's filter chain. These traces are the most important part of this lesson.

Trace A – anonymous user calls GET /api/me

curl (no header)→ BasicAuthFilter: no header, skip→ AnonymousFilter: "anonymous"→ AuthorizationFilter: needs authenticated ✗→ ExceptionTranslation: anonymous → 401 
HTTP/1.1 401
WWW-Authenticate: Basic realm="Realm"

Trace B – student calls GET /api/admin/stats

curl -u student:student123→ BasicAuthFilter: decode, AuthenticationManager ✓, store in SecurityContext→ AuthorizationFilter: hasRole ADMIN? has only ROLE_USER ✗→ ExceptionTranslation: known user → 403

Trace C – admin calls GET /api/admin/stats

curl -u admin:admin123→ BasicAuthFilter ✓→ AuthorizationFilter: ROLE_ADMIN ✓→ DispatcherServlet → AdminController→ 200 JSON
💡 The rule of thumb 401 = "I don't know who you are – please (re)authenticate". 403 = "I know exactly who you are – and the answer is no." A wrong password is also a 401, because authentication failed.

4.1 SecurityConfig.java – the whole security in one class

src/main/java/com/course/securitybasics/config/SecurityConfig.java@Configuration
@EnableWebSecurity // optional in Spring Boot, but it documents intent
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**", "/error").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .httpBasic(Customizer.withDefaults())
            .formLogin(Customizer.withDefaults())
            .logout(Customizer.withDefaults())
            .csrf(csrf -> csrf.ignoringRequestMatchers("/api/**"))
            .cors(Customizer.withDefaults());
        return http.build();
    }
    // + userDetailsService(...), passwordEncoder(), corsConfigurationSource()
}

Line by line:

  • "/error" is permitted on purpose. When a controller throws, Spring Boot forwards to /error to build the JSON error. If /error were protected, an anonymous caller would see a confusing 401 instead of the real 400/404/500.
  • HttpMethod.GET limits the admin rule to GET requests. Any other method on /api/admin/** falls through to anyRequest().authenticated().
  • .logout(...) adds POST /logout. Because CSRF is on for non-API URLs, logout must come from a page holding the token (Spring's GET /logout confirmation page does that).

4.2 Reading the current user in a controller

web/StudentController.java@GetMapping("/me")
public Map<String, Object> me(Authentication authentication) {
    List<String> roles = authentication.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority)
            .toList();
    return Map.of("username", authentication.getName(), "roles", roles);
}

@PostMapping("/feedback")
@ResponseStatus(HttpStatus.CREATED)
public Map<String, String> feedback(@RequestBody FeedbackRequest request, Principal principal) {
    return Map.of("from", principal.getName(), "message", request.message(), "status", "received");
}

Spring MVC can inject Authentication or java.security.Principal straight into a handler method – it takes them from the SecurityContextHolder that BasicAuthenticationFilter filled earlier in the chain. Topic 48 shows more ways (@AuthenticationPrincipal).

6. Common mistakes

⚠️ Mistake: hasRole("ROLE_ADMIN") hasRole adds ROLE_ itself. Spring stops you at startup with "ROLE_ADMIN should not start with ROLE_ since ROLE_ is automatically prepended when using hasRole. Consider using hasAuthority instead."
Fix: hasRole("ADMIN") – or hasAuthority("ROLE_ADMIN") if you want the full string.
⚠️ Mistake: putting anyRequest() first Rules are checked top-down; anyRequest() must be the last line or the app fails at startup.
Fix: most specific rules first, the catch-all last.
⚠️ Mistake: POST/PUT/DELETE always return 403 Usually CSRF: your client sends no CSRF token.
Fix: for a stateless API called with an Authorization header, ignore/disable CSRF for those URLs. For cookie-based browser apps, send the token instead.
⚠️ Mistake: "There is no PasswordEncoder mapped for the id null" You stored a plain password (.password("secret")) without an encoder bean and without a {noop}/{bcrypt} prefix.
Fix: declare a BCryptPasswordEncoder bean and store encoder.encode("secret").
⚠️ Mistake: copying WebSecurityConfigurerAdapter code from old blogs It does not exist in Spring Boot 3; antMatchers and authorizeRequests are gone or deprecated.
Fix: SecurityFilterChain bean + authorizeHttpRequests + requestMatchers + Lambda DSL.
⚠️ Mistake: CORS configured only in Spring MVC @CrossOrigin or WebMvcConfigurer.addCorsMappings alone: the preflight is rejected by security (401) before MVC ever sees it.
Fix: add .cors(...) to the filter chain (it picks up a CorsConfigurationSource bean).
🔥 Mistake: logging or returning passwords Never log request.getPassword(), never put the hash in a JSON response, never commit real passwords to Git.
⚠️ Mistake: curl in PowerShell behaves strangely In Windows PowerShell 5.1, curl means Invoke-WebRequest and -u does not work.
Fix: type curl.exe, or use the requests.http file.

7. Best practices

  • Deny by default. End your rules with anyRequest().authenticated() (or denyAll()) and open only what must be public.
  • One place for URL rules. Keep them in one SecurityConfig class so reviewers can see the whole picture.
  • Hash with BCrypt (or Argon2). Never store plain or reversibly encrypted passwords.
  • HTTPS everywhere outside your laptop. Basic auth and session cookies are only as safe as the connection.
  • Keep CSRF on for cookie/session-based browser apps; disable it only for truly stateless token APIs.
  • Allow-list CORS origins; never use * together with credentials.
  • Do not reveal details. "Invalid username or password" – never "user not found" vs "wrong password" (that helps attackers guess usernames).
  • Test your security rules like any other feature: 200, 401 and 403 cases for each important URL (see SecurityRulesTest).
  • Keep Spring Boot up to date – security fixes arrive through dependency updates.

8. Key takeaways

  • Authentication = who are you (fail → 401). Authorization = what may you do (fail → 403).
  • Adding spring-boot-starter-security locks everything and creates user user with a generated password.
  • Spring Security is a chain of filters in front of the DispatcherServlet; AuthorizationFilter is the last gate.
  • You describe rules in a SecurityFilterChain bean with the Lambda DSL; first matching rule wins.
  • Users come from a UserDetailsService; passwords are checked by a PasswordEncoder (BCrypt: slow + salted).
  • The logged-in user lives in the SecurityContextHolder (one per request thread).
  • HTTP Basic suits API clients; form login + session cookie suits browsers.
  • CSRF protects cookie-based apps; ignore/disable it only for stateless APIs. Configure CORS through .cors(...).

Challenge

Two filter chains. Split the configuration into two SecurityFilterChain beans: one for /api/** (HTTP Basic only, CSRF disabled, stateless) and one for everything else (form login, CSRF on). Use securityMatcher and @Order.

Hint / solution
@Bean
@Order(1)
public SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")                  // this chain only handles /api/**
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/public/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .csrf(csrf -> csrf.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
    return http.build();
}

@Bean
@Order(2)
public SecurityFilterChain webChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());       // CSRF stays ON
    return http.build();
}
// FilterChainProxy asks each chain in @Order: "do you match this URL?" and uses the first that does.

10. Interview questions

Q1. What is the difference between authentication and authorization?

Authentication verifies identity ("who are you?") using credentials such as a password or token. Authorization decides access ("are you allowed to do this?") based on roles/permissions of the authenticated user. Authentication comes first. Failures map to 401 and 403 respectively.

Q2. Explain the Spring Security filter chain.

Tomcat calls DelegatingFilterProxy, which delegates to the Spring bean FilterChainProxy. It selects the matching SecurityFilterChain and runs its ordered filters: context loading, headers, CORS, CSRF, logout, authentication filters (form, Basic, bearer…), anonymous, ExceptionTranslationFilter, and finally AuthorizationFilter. Only if all pass does the request reach the DispatcherServlet.

Q3. What is the difference between 401 and 403?

401 Unauthorized means the request is not authenticated (missing or invalid credentials); the response usually includes WWW-Authenticate. 403 Forbidden means the user is authenticated but lacks permission. Spring's ExceptionTranslationFilter chooses: anonymous user → entry point (401/redirect to login); known user → access denied handler (403).

Q4. Why BCrypt and not SHA-256 for passwords?

SHA-256 is designed to be fast, which helps attackers brute-force billions of guesses per second. BCrypt is deliberately slow (configurable cost) and uses a per-password random salt, defeating rainbow tables and making identical passwords produce different hashes.

Q5. What are UserDetailsService and UserDetails?

UserDetailsService is an interface with one method, loadUserByUsername, used by DaoAuthenticationProvider to fetch a user. It returns a UserDetails: username, password hash, authorities and account status flags. You implement it to plug in any user store (memory, JPA, LDAP…).

Q6. What is CSRF and when is it safe to disable protection?

Cross-Site Request Forgery tricks a logged-in user's browser into sending a state-changing request to another site, using cookies sent automatically. Spring defends with a synchronizer token. It is safe to disable for stateless APIs that do not use cookies for authentication (e.g. Bearer tokens in a header), because a foreign site cannot add that header.

Q7. Difference between hasRole and hasAuthority?

Both check granted authorities. hasRole("ADMIN") automatically prefixes ROLE_ and checks ROLE_ADMIN; hasAuthority("ADMIN") checks the exact string. Roles are conventionally coarse groups, authorities fine-grained permissions.

Q8. How is security configured in Spring Boot 3 compared with older versions?

WebSecurityConfigurerAdapter was removed in Spring Security 6. You now expose a SecurityFilterChain bean (and UserDetailsService, PasswordEncoder beans), use authorizeHttpRequests + requestMatchers, and the Lambda DSL instead of .and() chaining.

Q9. Why must CORS be configured in Spring Security and not only in MVC?

The browser's preflight OPTIONS request carries no credentials. Security filters run before MVC and would reject it with 401. http.cors() adds a CorsFilter early in the chain that answers preflights using the CorsConfigurationSource.

Q10. Where is the currently logged-in user stored during a request?

In the SecurityContext, held by SecurityContextHolder – by default in a ThreadLocal, so each request thread has its own. With sessions, SecurityContextHolderFilter loads it from the HttpSession at the start of each request.
