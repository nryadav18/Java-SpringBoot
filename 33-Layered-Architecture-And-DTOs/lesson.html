33. Layered Architecture & DTOs

Organise a Spring Boot API the way real companies do: a thin controller, a smart service, a swappable repository, and DTOs that protect your data.

1. Why this matters

In topics 31 and 32 we built small APIs where the controller did almost everything: it held a list, searched it, changed it and returned it. That is fine for 50 lines of code. But real applications have hundreds of endpoints, many developers and years of changes.

Imagine a controller method that reads the JSON, checks ten business rules, writes SQL, sends an email and builds the response — all in one place. Now imagine:

  • Your manager says: "We are moving from MySQL to PostgreSQL." → you must edit every controller.
  • A mobile team says: "Please don't send us the employee salary!" → but your code returns the whole database object.
  • You want to write a unit test for the "email must be unique" rule → but it is buried inside HTTP code.

Layered architecture fixes all three problems. It is the structure you will find in almost every Spring Boot project at work. When you join a new team, the first thing you will see is folders named controller, service, repository, dto… After this lesson you will know exactly what lives in each one and why.

ℹ️ Where you will see this Banking apps, e-commerce backends, HR systems, government portals — nearly every Spring Boot codebase follows this pattern. Interviewers also love asking "What is the role of the service layer?" and "Why use DTOs?".

2. Real-life analogy

🍽️ Think of a restaurant
  • The waiter (Controller) takes your order, writes it on a slip, and later brings the plate. The waiter does not cook.
  • The chef (Service) knows the recipes and the rules: "no peanuts for allergic guests", "steak must rest 5 minutes". The chef does not talk to customers.
  • The storeroom keeper (Repository) fetches and stores ingredients. They do not care what dish you are making.
  • The order slip and the plated dish (DTOs). You never walk into the kitchen and grab raw ingredients from the fridge (the Entity). You get a nicely prepared plate that contains only what you ordered.
If the restaurant changes its supplier (database), the waiter and customers do not notice. If a new waiter joins, the recipes stay the same. Each person has one job.

3. Concepts step by step

3.1 The three layers

A layer is simply a group of classes with the same kind of job. Requests flow down through the layers, and answers flow back up.

HTTP client
browser / mobile / curl→ Controller
web layer→ Service
business layer→ Repository
data layer→ Storage
Map / database

The golden rule: each layer only talks to the layer directly below it. The controller never touches the repository. The repository never knows a controller exists.

3.2 Responsibilities table

LayerAnnotation✅ Does❌ Never does
Controller@RestControllerMaps URLs, reads path/query/body, calls the service, picks the HTTP status, returns DTOsBusiness rules, SQL, touching the repository, returning entities
Service@ServiceBusiness rules ("email must be unique"), coordinates repositories, mapping, transactions (topic 42)Knowing about HTTP (ResponseEntity, status codes, HttpServletRequest)
Repository@RepositorySave, load, update, delete dataBusiness decisions, HTTP, DTOs
DTO(plain record)Carries data in and out of the APILogic, database annotations
Entity / Model(@Entity in topic 38)Represents what we storeBeing sent directly to clients
Mapper@ComponentConverts DTO ⇄ EntityBusiness rules

3.3 Why layers? (the five big benefits)

  1. Separation of concerns — each class has one job, so it is short and easy to read.
  2. Easy to change — swap the database? Only the repository changes. Add a GraphQL or Thymeleaf front-end? Only add a new controller; the service is reused.
  3. Easy to test — you can test the service's rules without starting a web server (see EmployeeServiceTest).
  4. Team work — one developer works on the API, another on business rules, with fewer merge conflicts.
  5. Reuse — the same EmployeeService.create(...) is used by the REST controller AND by the startup data loader.

3.4 Before and after

Here is the "everything in the controller" style. It works, but it mixes three jobs:

❌ Fat controller (don't do this)@RestController
public class EmployeeController {
    private final Map<Long, Employee> db = new HashMap<>();   // storage IN the controller

    @PostMapping("/api/employees")
    public Employee create(@RequestBody Employee e) {          // entity used as input
        for (Employee x : db.values()) {                       // business rule IN the controller
            if (x.getEmail().equals(e.getEmail())) throw new RuntimeException("dup");
        }
        e.setId((long) db.size() + 1);
        db.put(e.getId(), e);
        return e;                                               // returns salary + HR notes!
    }
}

And the layered version. Each piece is tiny and has a clear name:

✅ Thin controller@PostMapping
public ResponseEntity<EmployeeResponse> create(@RequestBody EmployeeRequest request) {
    EmployeeResponse created = employeeService.create(request);   // one call to the service
    URI location = ServletUriComponentsBuilder.fromCurrentRequest()
            .path("/{id}").buildAndExpand(created.id()).toUri();
    return ResponseEntity.created(location).body(created);       // 201 + DTO
}
✅ Service holds the rulepublic EmployeeResponse create(EmployeeRequest request) {
    if (repository.existsByEmail(request.email())) {
        throw new DuplicateEmailException(request.email());
    }
    Employee saved = repository.save(mapper.toEntity(request));
    return mapper.toResponse(saved);
}

3.5 What is a DTO? And what is an Entity?

DTO stands for Data Transfer Object. It is a simple object whose only job is to carry data across a boundary — for example, from the client into your API (a request DTO) or from your API back to the client (a response DTO).

An Entity (or domain model) is the object that represents what you store. In topic 38 it will get @Entity and map to a database table. In this project it is the plain class Employee.

Entity (Employee)DTO (EmployeeRequest / EmployeeResponse)
PurposeRepresents stored dataRepresents the API's input/output "contract"
Shape decided byThe database / domainWhat the client needs
Contains sensitive fields?Yes (salary, notes, password hash…)Only what is safe to share
Mutable?Usually yes (setters)Usually no (records)
Has annotations like@Entity, @Id, @Column@NotBlank, @Email (topic 34), @JsonProperty
How many?One per conceptOften several per concept (create, update, response, summary…)

3.6 Why never expose entities directly?

ProblemWhat goes wrongHow a DTO fixes it
🔓 Data leaksSalary, password hashes, internal notes appear in JSONThe response DTO simply has no such field
✍️ Mass assignmentA client sends "id": 1 or "role": "ADMIN" and Jackson happily sets itThe request DTO has no id / role, so it is ignored
💥 Tight couplingRenaming a DB column renames a JSON field and breaks the mobile appDTO stays the same; only the mapper changes
🔁 Infinite JSONJPA relationships (topic 40) like Customer ↔ Order loop foreverDTOs contain only flat, chosen data
🐢 Lazy-loading errorsLazyInitializationException when Jackson touches unloaded relationsMapping happens inside the service, before the response
🎯 Wrong shapeClient wants fullName, entity has first/lastDTO can have computed fields

Try it in this project: send a POST with "id": 999 and "internalNotes": "...". Both are silently ignored, because EmployeeRequest does not have those components. Jackson (by default in Spring Boot) ignores unknown JSON fields.

3.7 Records as DTOs

A record (topic 15) is a short way to write an immutable data class. Java writes the constructor, the accessor methods, equals, hashCode and toString for you.

dto/EmployeeRequest.javapublic record EmployeeRequest(
        String firstName,
        String lastName,
        String email,
        String department,
        BigDecimal salary
) { }
  • Jackson can read JSON into a record (it uses the constructor) and write a record as JSON (it uses the accessors).
  • Accessors have no "get" prefix: request.email(), not request.getEmail().
  • Because records are immutable, nobody can change a DTO halfway through the request — fewer surprises.
💡 Rule of thumb Use records for DTOs, and normal classes for entities (JPA needs a no-argument constructor and setters, which records cannot give).

3.8 Mapping: converting between DTO and Entity

Somebody has to copy request.firstName() into employee.setFirstName(...). We put that code in one dedicated class: the mapper.

mapper/EmployeeMapper.java (key part)public EmployeeResponse toResponse(Employee employee) {
    return new EmployeeResponse(
            employee.getId(),
            employee.getFirstName() + " " + employee.getLastName(),   // computed field
            employee.getEmail(),
            employee.getDepartment());                               // salary NOT copied
}

Where should mapping happen? Two common choices:

  • In the service (what we do): the service accepts and returns DTOs. Controllers stay super thin. This is the most common style.
  • In the controller: the service works only with entities, and the controller maps. Also valid; some teams prefer services to be DTO-free.

Pick one style and use it consistently across the project.

MapStruct — a generated mapper

Writing mappers by hand is boring for entities with 30 fields. MapStruct is a library that generates the mapper code at compile time from an interface. You write:

@Mapper(componentModel = "spring")          // generated class becomes a Spring bean
public interface EmployeeMapStructMapper {
    @Mapping(target = "fullName", expression = "java(e.getFirstName() + \" \" + e.getLastName())")
    EmployeeResponse toResponse(Employee e);

    @Mapping(target = "id", ignore = true)
    Employee toEntity(EmployeeRequest request);
}

…and MapStruct writes the EmployeeMapStructMapperImpl class with all the copying. It needs the org.mapstruct:mapstruct dependency plus its annotation processor in pom.xml. It is fast (plain Java, no reflection) and widely used. For learning, a manual mapper is clearer — that is why this project uses one. (Other libraries such as ModelMapper use reflection at runtime; they are slower and hide mistakes, so many teams avoid them.)

3.9 The repository behind an interface

The service depends on EmployeeRepository — an interface. Today the only implementation is InMemoryEmployeeRepository, which stores employees in a ConcurrentHashMap.

EmployeeService→ depends on → «interface»
EmployeeRepository← implemented by ← InMemoryEmployeeRepository
today JdbcEmployeeRepository
topic 37 JpaRepository
topic 38

Spring finds exactly one bean that implements the interface and injects it. When we write a database version later, we delete (or disable) the in-memory class and the service does not change at all. This is loose coupling from topic 8, and dependency injection from topic 24, working together.

ℹ️ Notice the method names save, findById (returning Optional), findAll, existsById, deleteById are exactly the names Spring Data JPA uses. In topic 38 our interface will simply extend JpaRepository<Employee, Long> and Spring will write the implementation for us.

3.10 Package-by-layer vs package-by-feature

There are two popular ways to arrange packages.

📁 Package-by-layer (this project) 
com.course.layered
├── controller
│   └── EmployeeController
├── service
│   └── EmployeeService
├── repository
│   ├── EmployeeRepository
│   └── InMemoryEmployeeRepository
├── dto
├── mapper
├── model
└── exception

✅ Very easy for beginners. ✅ Common in tutorials and small apps.
❌ In a big app, one feature is spread over 7 folders.

📦 Package-by-feature 
com.course.hr
├── employee
│   ├── EmployeeController
│   ├── EmployeeService
│   ├── EmployeeRepository
│   ├── EmployeeMapper
│   └── dto/...
├── department
│   ├── DepartmentController
│   └── ...
└── common
    └── exception/...

✅ Everything about "employee" is in one place. ✅ Classes can be package-private (better encapsulation). ✅ Easier to split into microservices later.
❌ Slightly less obvious for total beginners.

Many enterprise teams use package-by-feature on the outside and layers on the inside. The capstone project (topic 71) uses that style. Both are fine — the important thing is that the layering rules (who calls whom) stay the same.

3.11 Lombok — less boilerplate (explained, but not used here)

Look at Employee.java: 8 fields and 16 getter/setter methods. That repetitive code is called boilerplate. Lombok is a library that generates it at compile time from annotations.

import lombok.Getter;
import lombok.Setter;
import lombok.NoArgsConstructor;

@Getter                 // generates getId(), getFirstName(), ...
@Setter                 // generates setId(...), setFirstName(...), ...
@NoArgsConstructor      // generates public Employee() { }
public class Employee {
    private Long id;
    private String firstName;
    // ... no getters/setters written by hand!
}

@Service
@RequiredArgsConstructor   // generates a constructor for all FINAL fields
public class EmployeeService {
    private final EmployeeRepository repository;   // injected through that constructor
    private final EmployeeMapper mapper;
}
Lombok annotationGenerates
@Getter / @SetterGetters / setters for fields
@NoArgsConstructorEmpty constructor
@AllArgsConstructorConstructor with every field
@RequiredArgsConstructorConstructor with every final field — perfect for constructor injection
@ToString, @EqualsAndHashCodetoString, equals, hashCode
@DataAll of the above together (avoid on JPA entities!)
@BuilderA builder: Employee.builder().firstName("Asha").build()
@Slf4jA log field (topic 30)

If your team uses Lombok, you need three things:

  1. The dependency in pom.xml (version managed by the Spring Boot parent): 
    <dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>
  2. The annotation processor configured for the compiler (needed reliably since JDK 23, recommended always): 
    <plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>${lombok.version}</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
  3. VS Code setup: the "Extension Pack for Java" already includes Lombok support (in the Language Support for Java extension). If VS Code shows red errors like "getFirstName() is undefined" even though Maven compiles, run Ctrl+Shift+P → "Java: Clean Java Language Server Workspace" and reload. In IntelliJ, enable Settings → Build → Compiler → Annotation Processors → Enable annotation processing.
💡 Our choice for this course This project does not use Lombok. Reasons: (1) you can see every line of code that runs, (2) records already remove most boilerplate for DTOs, (3) no IDE plugin surprises. You will meet Lombok in many real projects, so now you can read it confidently. A good compromise used by many teams: records for DTOs, Lombok @Getter/@Setter for entities, @RequiredArgsConstructor for services.

    private String department;

A normal mutable class. Notice its toString() deliberately skips the salary, so it never ends up in a log file by accident (topic 30).

4.2 The repository — interface + in-memory implementation

repository/InMemoryEmployeeRepository.java (key part)@Repository
public class InMemoryEmployeeRepository implements EmployeeRepository {

    private final Map<Long, Employee> storage = new ConcurrentHashMap<>();
    private final AtomicLong idSequence = new AtomicLong(0);   // like a DB auto-increment

    @Override
    public Employee save(Employee employee) {
        if (employee.getId() == null) {
            employee.setId(idSequence.incrementAndGet());     // new -> give it an id
        }
        storage.put(employee.getId(), employee);              // insert or replace
        return employee;
    }

    @Override
    public Optional<Employee> findById(Long id) {
        return Optional.ofNullable(storage.get(id));
    }
    // findAll, findByDepartment, existsByEmail, existsById, deleteById ...
}
  • Line by line: save behaves like a database: no id → insert with a new id; has id → update (replace).
  • ConcurrentHashMap + AtomicLong are thread-safe. Tomcat serves each request on its own thread (topic 17), so two POSTs at the same moment must not get the same id.
  • findById returns Optional so the caller is forced to think about "not found".
  • There is no "email must be unique" check here. The repository only stores; the rule belongs to the service.

4.3 The service — business rules

service/EmployeeService.java (key parts)@Service
public class EmployeeService {

    private final EmployeeRepository repository;   // the INTERFACE
    private final EmployeeMapper mapper;

    public EmployeeService(EmployeeRepository repository, EmployeeMapper mapper) {
        this.repository = repository;              // constructor injection (topic 24)
        this.mapper = mapper;
    }

    public EmployeeResponse update(Long id, EmployeeRequest request) {
        Employee existing = getExisting(id);                      // 404 if missing
        boolean emailChanged = !existing.getEmail().equalsIgnoreCase(request.email());
        if (emailChanged && repository.existsByEmail(request.email())) {
            throw new DuplicateEmailException(request.email());   // 409
        }
        mapper.updateEntity(existing, request);                   // copy new values
        return mapper.toResponse(repository.save(existing));      // entity -> DTO
    }

    private Employee getExisting(Long id) {
        return repository.findById(id)
                .orElseThrow(() -> new EmployeeNotFoundException(id));
    }
}
  • The service throws exceptions instead of returning status codes. It does not know HTTP exists.
  • The exceptions carry @ResponseStatus(HttpStatus.NOT_FOUND) / CONFLICT, so Spring turns them into 404 / 409. (Topic 35 shows a cleaner, central way with @RestControllerAdvice.)
  • departmentSummary() shows that a service can produce DTOs that do not match any stored object (a report).

4.4 The controller — thin and boring (that's a compliment!)

controller/EmployeeController.java (key parts)@RestController
@RequestMapping("/api/employees")
public class EmployeeController {

    private final EmployeeService employeeService;

    public EmployeeController(EmployeeService employeeService) {
        this.employeeService = employeeService;
    }

    @GetMapping
    public List<EmployeeResponse> getAll(@RequestParam(required = false) String department) {
        return employeeService.findAll(department);
    }

    @GetMapping("/{id}")
    public EmployeeResponse getOne(@PathVariable Long id) {
        return employeeService.findById(id);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        employeeService.delete(id);
        return ResponseEntity.noContent().build();     // 204
    }
}

The controller only ever sees EmployeeRequest and EmployeeResponse. There is no import ...model.Employee in this file at all — a nice quick check that the entity never leaks out.

6. Common mistakes

⚠️ Mistake: returning the entity from the controller public Employee getOne(...) works, so beginners keep it. Then salary and password hashes appear in JSON.
Fix: Controllers return only DTOs. Quick check: the controller file should not import your model/entity package.
⚠️ Mistake: business logic in the controller "if email exists, return 409" written inside the controller. Now the data loader, a scheduled job or a second controller can skip that rule.
Fix: Rules live in the service. Every entry point (REST, startup loader, messaging) goes through the service.
⚠️ Mistake: the controller calls the repository directly "It's just a simple findAll, why go through the service?" Then next month someone adds a filter rule in the service and this endpoint doesn't get it.
Fix: Always go controller → service → repository, even for trivial calls. A one-line service method is fine.
⚠️ Mistake: the service returns ResponseEntity or uses status codes That ties the business layer to HTTP, so it cannot be reused by a message listener or a batch job.
Fix: The service returns data or throws meaningful exceptions. The web layer decides the HTTP status.
⚠️ Mistake: depending on the concrete repository class private final InMemoryEmployeeRepository repo; — now switching to a database means editing the service.
Fix: Depend on the interface EmployeeRepository.
🛑 Mistake: one DTO for everything, including id Reusing the response DTO as the request DTO lets clients send "id", "role", "createdAt"… (mass assignment).
Fix: Separate request and response DTOs. Only put fields the client is allowed to set into the request DTO.
⚠️ Mistake: forgetting to copy a new field in the mapper You add phone to the entity and DTO, but the response always shows null.
Fix: Keep all mapping in the mapper class and write small mapper tests (see EmployeeMapperTest). MapStruct can even warn you about unmapped fields.
⚠️ Mistake: putting classes outside the main package A controller in package com.course.controllers (not under com.course.layered) is never scanned, so you get 404 for every URL.
Fix: All packages must be below the package of the @SpringBootApplication class.

7. Best practices

  • Thin controllers, rich services. If a controller method is longer than ~10 lines, logic is probably leaking into it.
  • Never expose entities. Use request DTOs for input and response DTOs for output.
  • Use records for DTOs; use normal classes for entities.
  • Name DTOs by purpose: CreateEmployeeRequest, UpdateEmployeeRequest, EmployeeResponse, EmployeeSummary. Avoid vague names like EmployeeDTO2.
  • Depend on interfaces between service and repository. It makes swapping and mocking easy.
  • Constructor injection with final fields everywhere (with or without Lombok's @RequiredArgsConstructor).
  • One mapper per aggregate (e.g. EmployeeMapper). For large projects consider MapStruct.
  • Throw domain exceptions (EmployeeNotFoundException) from the service; translate them to HTTP in one place (topic 35).
  • Package-by-feature for medium/large apps; keep the same layer rules inside each feature.
  • Keep "transaction boundaries" in the service — that is where @Transactional will go in topic 42.
  • Don't over-engineer: a tiny prototype may not need a mapper class. But any API that other people use deserves DTOs.

8. Key takeaways

  • Layers: Controller (HTTP) → Service (business rules) → Repository (data). Each talks only to the one below.
  • Layers give separation of concerns, easy testing, easy change and reuse.
  • A DTO is the API's input/output contract; an Entity is what you store. Never return entities directly.
  • Separate request and response DTOs protect against data leaks and mass assignment.
  • Records are ideal DTOs: immutable, short and Jackson-friendly.
  • A mapper class keeps all DTO ⇄ entity conversion in one place; MapStruct can generate it.
  • The service depends on a repository interface, so storage can be swapped (in-memory → JDBC → JPA) without changes.
  • Package-by-layer is simple; package-by-feature scales better.
  • Lombok generates boilerplate (@Getter, @Setter, @RequiredArgsConstructor) but needs annotation-processing setup; this course keeps plain Java + records.

10. Interview questions

Q1. Explain layered architecture in a Spring Boot application.

The code is split into the web layer (@RestController: HTTP mapping, DTOs, status codes), the service layer (@Service: business rules, transactions, orchestration) and the data access layer (@Repository: persistence). Each layer depends only on the one below it, which gives separation of concerns, testability and the ability to change one layer without touching others.

Q2. What is a DTO and why do we use it?

A Data Transfer Object is a simple object that carries data across a boundary — for example between the API and its clients. We use DTOs to control exactly what is exposed (no sensitive fields), to prevent mass assignment, to decouple the API contract from the database schema, to avoid JPA problems like lazy loading and infinite recursion during JSON serialization, and to shape data for the client (computed fields, summaries).

Q3. Why should you not return JPA entities directly from a REST controller?

It leaks internal/sensitive fields, couples your public API to your database schema, can trigger LazyInitializationException or N+1 queries when Jackson walks relations, can cause infinite recursion with bidirectional relationships, and if entities are also used as input it allows clients to set fields they should not (id, role). DTOs avoid all of this.

Q4. Where should DTO-to-entity mapping happen?

Commonly in the service layer (the service accepts and returns DTOs, using a mapper component), which keeps controllers very thin. Some teams map in the controller and keep services entity-only. Either is acceptable if applied consistently. The mapping code itself should live in a dedicated mapper (hand-written or generated by MapStruct), not scattered around.

Q5. What is the difference between @Component, @Service, @Repository and @Controller?

All four mark a class as a Spring bean found by component scanning. @Service and @Controller/@RestController mainly document the role (and @Controller enables request mapping). @Repository additionally enables exception translation: persistence exceptions are converted into Spring's DataAccessException hierarchy.

Q6. Why should the service depend on a repository interface?

Programming to an interface gives loose coupling: the implementation (in-memory, JDBC, JPA, a remote service) can change without changing the service, and tests can pass a fake or a Mockito mock. With Spring Data JPA, the interface is all you write — Spring generates the implementation.

Q7. Package-by-layer vs package-by-feature — which do you prefer?

Package-by-layer groups by technical role (controller, service…) — simple, good for small apps. Package-by-feature groups by business capability (employee, order…) — related code stays together, classes can be package-private, features can be extracted into modules or microservices more easily. For anything beyond a small app I prefer package-by-feature with clear layers inside each feature.

Q8. What is Lombok? Any downsides?

Lombok is an annotation processor that generates boilerplate (getters, setters, constructors, builders, loggers) at compile time. Downsides: it needs IDE/annotation-processor setup, it hides code (harder to debug or read for newcomers), @Data/@EqualsAndHashCode/@ToString on JPA entities can cause performance problems or infinite loops with relationships, and it hooks into compiler internals so JDK upgrades sometimes require a Lombok upgrade. Records remove much of the need for DTOs.

Q9. What is MapStruct and how is it different from ModelMapper?

MapStruct generates plain Java mapping code at compile time from an annotated interface, so it is as fast as hand-written code and reports unmapped fields as compiler warnings/errors. ModelMapper maps at runtime using reflection and naming conventions — easier to start with but slower and errors appear only at runtime.

Q10. Should a service method ever return ResponseEntity?

No. ResponseEntity is an HTTP concept and belongs to the web layer. The service should return domain data or DTOs and signal problems with exceptions; the controller (or a @RestControllerAdvice) decides the HTTP status. This keeps the service reusable from other entry points such as message listeners, schedulers or tests.
