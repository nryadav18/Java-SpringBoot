1. Why this matters

Up to now your apps ran on localhost. Real users can't reach your laptop, and your laptop goes to sleep. Deployment means putting your app on a computer that is always on, reachable from the internet, and able to survive problems: crashes, too many users, new versions, broken servers.

"It works on my machine" is the start. Production asks harder questions:

  • What happens when the app crashes at 3 a.m.? (Who restarts it?)
  • How do we release version 2 without downtime?
  • Where do we keep the database password? (Not in Git!)
  • How does the load balancer know an instance is healthy?
  • Black Friday: how do we go from 2 to 10 instances?

Kubernetes has become the standard answer in medium and large companies — most Java backend job ads mention it. But it's not the only answer, and for many projects it's overkill. This lesson gives you the map of options and then hands-on Kubernetes basics so that you can read, write and discuss the YAML files you'll meet at work.

2. Real-life analogy

🍽️ Kubernetes is a restaurant manager You (the owner) don't cook every dish yourself. You tell the manager: "I always want 2 cooks making biryani (Deployment, replicas: 2)."
  • Each cook at a station is a Pod. The kitchens (computers) are Nodes.
  • If a cook faints, the manager immediately hires a replacement (self-healing).
  • Customers don't shout at a specific cook; they order at the counter, which passes orders to whichever cook is free (Service = stable address + load balancing).
  • Before giving a new cook orders, the manager asks: "Are you ready?" (readiness probe). Every few minutes: "Are you OK?" — no answer → replace him (liveness probe).
  • The recipe card on the wall that all cooks read (ConfigMap); the safe with the supplier's credit card (Secret).
  • The restaurant's front door with signs "Dine-in → left, Takeaway → right" (Ingress).
  • New menu? The manager replaces cooks one at a time so the kitchen never closes (rolling update).

3.2 Option 1 in detail: a VM with systemd

systemd is the program on most Linux systems that starts and supervises services (like "Services" on Windows). You describe your app in a .service file; systemd starts it at boot, restarts it if it crashes, and collects its logs (journalctl).

deploy/menu-service.service (key lines)[Service]
User=menuapp
EnvironmentFile=/etc/menu-service.env
ExecStart=/usr/bin/java -Xms256m -Xmx512m -XX:+ExitOnOutOfMemoryError -jar /opt/menu-service/app.jar
SuccessExitStatus=143
Restart=on-failure

SuccessExitStatus=143: when Java stops because of SIGTERM it exits with code 143 (128 + 15); this tells systemd that's a normal stop, not a failure. Usually you also put Nginx in front as a reverse proxy that handles HTTPS (free certificates from Let's Encrypt).

3.3 Option 2 in detail: PaaS in 5 clicks

On Render or Railway: New → Web Service → connect GitHub repo. It detects the Dockerfile (from topic 66) and builds it. Set environment variables (SPRING_PROFILES_ACTIVE=prod, DB password) in the dashboard. Most PaaS give you a PORT env var — map it with server.port=${PORT:8080}. Free tiers change often, so check current pricing.

3.5 JVM memory inside containers

A container has a memory limit (say 512 MiB). If the process uses more, the kernel kills it: OOMKilled. Java's memory = heap + metaspace + thread stacks + other native memory. So the heap must be smaller than the limit.

  • -XX:MaxRAMPercentage=75.0 — heap max = 75% of the container limit (512 MiB → ~384 MiB). Modern Java (10+) reads the container limit automatically.
  • -XX:+ExitOnOutOfMemoryError — if the heap is full, exit immediately so Kubernetes restarts the pod (instead of limping along).
  • We pass them via JAVA_TOOL_OPTIONS (the JVM reads this env var by itself; it prints "Picked up JAVA_TOOL_OPTIONS..." at startup — that's normal).

Our /api/info shows maxHeapMb so you can see the effect.

3.6 Graceful shutdown

When a pod is deleted (new version, scaling down), Kubernetes sends SIGTERM ("please stop") and, after terminationGracePeriodSeconds, SIGKILL ("stop NOW"). With server.shutdown=graceful Spring Boot, on SIGTERM:

SIGTERM→ readiness = REFUSING_TRAFFIC→ stop accepting new requests→ finish running requests (≤ 20 s)→ close DB pool, exit

Our preStop hook (sleep 10) gives Kubernetes a few seconds to remove the pod from the Service before Spring stops accepting connections, so no request hits a closing door. Rule: preStop (10 s) + Spring timeout (20 s) < terminationGracePeriodSeconds (45 s).

3.7 What is Kubernetes?

Kubernetes (often written K8s — "K", 8 letters, "s") is an open-source container orchestrator, originally from Google. You tell it the desired state ("3 copies of image X, reachable on port 80") and its controllers work non-stop to make the actual state match. This is called declarative configuration: you describe what, not how.

ℹ️ Compose vs Kubernetes Docker Compose (topic 67) runs containers on one machine. Kubernetes runs them on a cluster of many machines, with self-healing, rolling updates, auto-scaling and service discovery built in. Same images, different "manager".

3.8 Cluster, nodes and the control plane

  • Cluster — the whole set of machines managed by Kubernetes.
  • Node — one machine (VM or physical) in the cluster that runs your containers.
  • Control plane — the "brain": the API server (what kubectl talks to), the scheduler (decides which node runs a pod), controllers (keep desired = actual), and etcd (the database of the cluster state). In managed clusters (EKS, GKE, AKS) the cloud runs it for you.

3.10 Anatomy of every Kubernetes YAML

Every object has the same four top-level keys:

apiVersion: apps/v1        # which API group/version defines this kind
kind: Deployment           # what type of object
metadata:                  # name, labels, namespace
  name: menu-service
  labels:
    app: menu-service
spec:                      # the DESIRED STATE - different for every kind
  replicas: 2

Kubernetes adds a fifth one itself, status (the actual state), which you see with kubectl get deployment menu-service -o yaml.

3.11 Labels and selectors: how objects find each other

Labels are sticky notes on objects (app: menu-service). Selectors say "I mean everything with this sticky note". There are no direct links by name between a Service and its pods — only labels:

Service selector
app: menu-service→ matches → Pod labels
app: menu-service← creates ← Deployment template
labels: app: menu-service

If the labels don't match exactly (a typo!), the Service has no endpoints and every request fails. kubectl get endpoints menu-service shows which pod IPs it found.

3.12 Probes: liveness, readiness, startup

ProbeQuestionIf it fails…Spring Boot endpoint
startupProbe"Have you finished starting?"Keep waiting (up to the limit), then restart. Other probes don't run until it succeeds./actuator/health/liveness
livenessProbe"Are you alive, or stuck forever?"Restart the container./actuator/health/liveness
readinessProbe"Can you take traffic right now?"Remove from the Service (no restart). Added back when it passes./actuator/health/readiness

Spring Boot tracks two states for this (LivenessState: CORRECT/BROKEN, ReadinessState: ACCEPTING_TRAFFIC/REFUSING_TRAFFIC). The probe endpoints are switched on automatically when Spring detects Kubernetes; we set management.endpoint.health.probes.enabled=true so you can also try them locally.

⚠️ Don't put the database in the liveness check If the DB is down and liveness fails, Kubernetes restarts ALL your pods in a loop — which doesn't fix the DB and makes things worse. By default Spring Boot's liveness group contains only the app's own state. External checks may go into readiness (with care).

3.13 ConfigMaps and Secrets → environment variables

envFrom:
  - configMapRef:
      name: menu-service-config   # every key becomes an env var
  - secretRef:
      name: menu-service-secret

Combined with Spring Boot's relaxed binding, APP_RESTAURANT_NAME in the ConfigMap becomes app.restaurant-name in our AppProperties record. The same image runs in dev, staging and prod; only the ConfigMap/Secret differ.

🚫 Secrets are base64, NOT encrypted echo ZGVtbw== | base64 -d → "demo". Anyone who can read the Secret object or the YAML file can read the value. Protect Secrets with RBAC (access rules), enable encryption at rest in the cluster, and never commit real secret YAML to Git (use Sealed Secrets, External Secrets Operator, Vault or your cloud's secret manager).

3.15 Rolling updates and rollbacks

Change the image tag (e.g. menu-service:1.0.1) and apply. With maxSurge: 1 and maxUnavailable: 0, Kubernetes starts one new pod, waits until it is ready, then terminates one old pod, and repeats. Users see no downtime — if readiness probes and graceful shutdown are correct. Something wrong? kubectl rollout undo deployment/menu-service goes back to the previous version.

3.16 Resources: requests and limits

  • requests — what the pod is guaranteed; the scheduler uses it to pick a node with enough room. 250m = 250 millicores = ¼ CPU.
  • limits — the maximum. Exceeding the memory limit → OOMKilled. Exceeding CPU → slowed down (throttled). Many teams set a memory limit but no CPU limit for Java (JVM startup needs CPU bursts).

3.19 What comes next (names you'll hear)

  • HorizontalPodAutoscaler (HPA) — adds/removes pods based on CPU or custom metrics.
  • Helm — a package manager / templating tool for Kubernetes YAML ("charts"). Kustomize — overlays per environment, built into kubectl apply -k.
  • GitOps with Argo CD / Flux — the cluster syncs itself from YAML in a Git repo; CI (topic 68) just updates the image tag.
  • StatefulSet (databases), Job/CronJob (batch tasks), PersistentVolume (storage).
  • In Kubernetes you often don't need Eureka or Spring Cloud Config: Services give discovery, ConfigMaps give config (topics 60, 62).

4.1 Configuration from the environment

src/main/java/com/course/k8sdemo/config/AppProperties.java@ConfigurationProperties(prefix = "app")
public record AppProperties(String restaurantName, String welcomeMessage, String paymentApiKey) {

    public String maskedPaymentApiKey() {
        if (paymentApiKey == null || paymentApiKey.length() < 4) {
            return "(not set)";
        }
        return "****" + paymentApiKey.substring(paymentApiKey.length() - 4);
    }
}

Locally the values come from application.properties; in Kubernetes from env vars APP_RESTAURANT_NAME etc. The secret is only ever shown masked (****9f2a) — never log or return real secrets.

Inside a pod, the hostname is the pod's name. Call through the Service a few times and you'll see the two pods take turns.

4.3 Readiness on demand

src/main/java/com/course/k8sdemo/ops/ReadinessController.java (part)@PostMapping("/off")
public Map<String, Object> off() {
    AvailabilityChangeEvent.publish(publisher, this, ReadinessState.REFUSING_TRAFFIC);
    return current();
}

Publishing an AvailabilityChangeEvent changes what /actuator/health/readiness returns (503 OUT_OF_SERVICE). Kubernetes notices within a few seconds and stops routing to this pod — without restarting it. Spring Boot does the same thing automatically during graceful shutdown. (Real apps would secure or remove such an endpoint.)

4.5 k8s/deployment.yaml — the important parts

k8s/deployment.yamlapiVersion: apps/v1
kind: Deployment
metadata:
  name: menu-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: menu-service
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: menu-service
    spec:
      terminationGracePeriodSeconds: 45
      securityContext:
        runAsNonRoot: true
      containers:
        - name: app
          image: menu-service:1.0.0
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: menu-service-config
            - secretRef:
                name: menu-service-secret
          resources:
            requests:
              cpu: "250m"
              memory: "384Mi"
            limits:
              memory: "512Mi"
          startupProbe:
            httpGet: { path: /actuator/health/liveness, port: http }
            periodSeconds: 5
            failureThreshold: 30
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: http }
            periodSeconds: 10
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: http }
            periodSeconds: 5
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 10"]

(The real file uses the long YAML form for probes, with comments; { ... } is the same thing written on one line.) Read it top to bottom as a sentence: "Keep 2 pods labelled app=menu-service; update them one at a time; each runs image menu-service:1.0.0 as non-root on port 8080 with env from the ConfigMap and Secret, gets ¼ CPU and up to 512 MiB, is checked by three probes, and waits 10 s before shutting down."

ℹ️ Why a numeric user in the Dockerfile? runAsNonRoot: true makes Kubernetes check the image's user. With a name (USER spring) it can't verify it's not root and refuses to start the pod. So our Dockerfile uses USER 1001.

6. Common mistakes

⚠️ Mistake: ErrImagePull / ImagePullBackOff The cluster can't find the image: it isn't in a registry, the name/tag is wrong, or minikube/kind doesn't have your local image.
Fix: kubectl describe pod → Events; load the image (minikube image load, kind load docker-image) or push to a registry; with :latest tags the default pull policy is Always — use a fixed tag.
⚠️ Mistake: CrashLoopBackOff The app starts and dies repeatedly (bad config, missing env var, DB unreachable).
Fix: kubectl logs <pod> --previous shows the crash; fix config and re-apply.
⚠️ Mistake: OOMKilled Heap set too big (or no heap limit) for the container memory limit.
Fix: -XX:MaxRAMPercentage=75.0, realistic limits; check with kubectl describe pod → Last State.
⚠️ Mistake: liveness probe too aggressive The JVM needs 20 s to start, liveness starts checking after 5 s → Kubernetes kills it before it's up, forever.
Fix: use a startupProbe (as we do) or a generous initialDelaySeconds.
⚠️ Mistake: Service selector doesn't match pod labels Requests time out; kubectl get endpoints menu-service shows <none>.
Fix: make spec.selector of the Service equal the pod template labels.
⚠️ Mistake: "connection refused localhost:8080" from kubectl kubectl has no cluster configured (no context), so it tries a default address.
Fix: enable Kubernetes in Docker Desktop (or start minikube/kind) and check kubectl config current-context.
⚠️ Mistake: ConfigMap changed but app shows old values Env vars are read only when the container starts.
Fix: kubectl rollout restart deployment/menu-service.
🚫 Mistake: real secrets committed in secret.yaml Base64 is not encryption.
Fix: create secrets outside Git (kubectl create secret ...) or use Sealed Secrets / External Secrets / Vault.
⚠️ Mistake: shell-form ENTRYPOINT without exec ENTRYPOINT java -jar app.jar runs Java as a child of sh; SIGTERM never reaches Java → no graceful shutdown, killed after the grace period.
Fix: exec form ["java","-jar","app.jar"] (or exec java ... inside sh -c).

7. Best practices

  • Pick the simplest platform that works; move to Kubernetes when you need it.
  • 12-factor config: one image, config via env vars; secrets from a secret manager.
  • Always define probes: startup (slow JVM start), liveness (own state only), readiness (can serve).
  • Graceful shutdown + preStop, and terminationGracePeriodSeconds longer than both.
  • Set requests and memory limits; size the heap with MaxRAMPercentage.
  • At least 2 replicas for anything important, maxUnavailable: 0 for zero-downtime updates; add a PodDisruptionBudget for node maintenance.
  • Immutable image tags (version or commit SHA from CI — topic 68), never latest in production.
  • Security: non-root user, read-only root filesystem where possible, minimal images, namespaces + RBAC, network policies.
  • Log to stdout in JSON; collect centrally; add trace ids (topic 65).
  • Keep YAML in Git, deploy via CI/CD or GitOps (Argo CD) — not by hand-typing kubectl edit in production.
  • Use Helm or Kustomize for per-environment differences instead of copy-pasting YAML.

8. Key takeaways

  • Options range from a VM with systemd, through PaaS and container services, to Kubernetes — trade-off between control and effort.
  • Production checklist: profiles, external secrets, health checks, stdout/JSON logs, JVM memory flags, graceful shutdown, migrations.
  • Kubernetes is declarative: you describe desired state in YAML, controllers make it real and keep it so.
  • Pod = running container(s); Deployment = N pods + rolling updates; Service = stable address + load balancing; ConfigMap/Secret = configuration; Ingress = HTTP entry.
  • Labels and selectors connect objects.
  • Spring Boot Actuator provides /actuator/health/liveness and /readiness for probes; liveness failure = restart, readiness failure = no traffic.
  • kubectl apply -f, get, describe, logs, port-forward, rollout are your daily tools.
  • Docker Desktop, minikube or kind give you a free local cluster.

10. Interview questions

Q1. What is the difference between a Pod, a ReplicaSet and a Deployment?

A Pod is the smallest deployable unit: one or more containers sharing network and storage. A ReplicaSet ensures a given number of identical pods run. A Deployment manages ReplicaSets and adds declarative updates: rolling updates, rollbacks and history. You normally create Deployments, not pods or ReplicaSets directly.

Q2. Why do we need a Service if pods have IP addresses?

Pods are ephemeral; their IPs change whenever they're recreated or scaled. A Service gives a stable virtual IP and DNS name and load-balances across all ready pods selected by labels.

Q3. Liveness vs readiness vs startup probe?

Startup: has the app finished starting (other probes wait until it passes). Liveness: is the app alive — failure triggers a container restart. Readiness: can the app serve traffic now — failure removes the pod from Service endpoints without restart. In Spring Boot: /actuator/health/liveness and /actuator/health/readiness.

Q4. ConfigMap vs Secret?

Both provide configuration as env vars or files. ConfigMaps are for non-sensitive data. Secrets are for sensitive data: stored base64-encoded, can be encrypted at rest, restricted with RBAC and not shown by default in some outputs. Base64 itself is not encryption, so secret YAML must not be committed in plain form.

Q5. How does a rolling update achieve zero downtime?

The Deployment creates new pods (up to maxSurge) and only removes old ones when new ones are ready (respecting maxUnavailable). It needs correct readiness probes and graceful shutdown (SIGTERM handling, preStop delay) so traffic only goes to ready pods and in-flight requests finish.

Q6. How do you size JVM memory in a container?

Set a container memory limit and let the JVM size the heap relative to it with -XX:MaxRAMPercentage (e.g. 75%), leaving room for metaspace, threads and native memory. Exceeding the limit causes OOMKilled. Add -XX:+ExitOnOutOfMemoryError so the pod restarts cleanly.

Q7. What does server.shutdown=graceful do?

On shutdown (SIGTERM) Spring Boot stops accepting new requests, waits for active ones to finish up to spring.lifecycle.timeout-per-shutdown-phase, and then closes the context. It also moves readiness to REFUSING_TRAFFIC.

Q8. What is an Ingress and how is it different from a LoadBalancer Service?

An Ingress is an HTTP(S) routing rule (host/path-based) implemented by an Ingress controller (e.g. NGINX); one entry point can route to many Services and terminate TLS. A LoadBalancer Service provisions an external (L4) load balancer for a single Service.

Q9. Which deployment option would you choose for a small startup's single Spring Boot app?

Usually a PaaS (Render, Railway, Heroku, Cloud Run) or a single VM with systemd/Docker: fast, cheap, little operations work. Kubernetes adds complexity that only pays off with many services, teams or scaling needs.

Q10. A pod is in CrashLoopBackOff. How do you debug it?

kubectl describe pod (events, last state, exit code, OOMKilled?), kubectl logs <pod> --previous for the crashed container's logs, check env/config (ConfigMap/Secret names and keys), image tag, probes (too aggressive liveness?) and resource limits.
