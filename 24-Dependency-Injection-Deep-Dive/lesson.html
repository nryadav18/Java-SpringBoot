24. Dependency Injection Deep Dive

Master every way Spring can hand dependencies to your beans — and know how to fix the errors when it can't decide or gets stuck.

1. Why this matters

Dependency Injection is the heart of Spring. Every controller, service and repository you write in Spring Boot gets its collaborators through DI. So questions like these come up daily at work:

  • "We have card, UPI and PayPal payment classes. How do I tell Spring which one to use here?"
  • "How do I read the delivery fee from a configuration file instead of hard-coding 40.0?"
  • "The SMS module is installed only for some customers. How do I depend on it only if it exists?"
  • "Startup fails with 'Requested bean is currently in creation: Is there an unresolvable circular reference?' — what now?"

DI is also one of the most asked interview topics for Java developers: "constructor vs field injection", "@Primary vs @Qualifier" and "circular dependencies" appear in almost every Spring interview.

2. Real-life analogy

🛵 A food-delivery rider gets their equipment

A new delivery rider joins QuickBite. They need a bike, a phone and a delivery bag. There are three ways the company could give them:

  • Constructor injection — on the joining day, the rider gets everything at once in a welcome kit. They can't start work without it. From minute one, the rider is complete. ✅
  • Setter injection — the rider starts first, and the bag is "delivered later". For a while the rider is working without a bag. Fine for optional extras (like a rain jacket), risky for essentials.
  • Field injection — someone sneaks into the rider's locker at night and puts the phone there. It works, but nobody can see from the outside what the rider needs, and you can't easily train a rider outside the company.

When the manager says "give the rider a payment terminal" and there are three types, the company needs a rule: "unless told otherwise, give the card terminal" (@Primary), or the order is specific: "this rider gets the UPI terminal" (@Qualifier).

3. Concepts step by step

3.1 The three styles of injection

Spring can hand a dependency to your bean in three ways.

① Constructor injection — dependencies are constructor parameters.

order/CheckoutService.java@Service
public class CheckoutService {

    private final PaymentGateway paymentGateway;   // final: set once, never null afterwards
    private final ShopSettings shopSettings;

    public CheckoutService(PaymentGateway paymentGateway, ShopSettings shopSettings) {
        this.paymentGateway = paymentGateway;
        this.shopSettings = shopSettings;
    }
}

② Setter injection — Spring creates the object (no-arg constructor), then calls a setter marked @Autowired.

order/ReceiptService.java@Service
public class ReceiptService {

    private ReceiptPrinter printer;               // cannot be final

    @Autowired                                    // required: tells Spring to call this setter
    public void setPrinter(ReceiptPrinter printer) {
        this.printer = printer;
    }
}

③ Field injection — @Autowired directly on a field. Spring writes into the private field using reflection (Topic 18).

order/LegacyAuditService.java@Service
public class LegacyAuditService {

    @Autowired
    private ReceiptPrinter receiptPrinter;        // hidden dependency, cannot be final
}

💡 The rule used by the Spring team itself "Use constructor injection for mandatory dependencies and setter injection for optional ones." Field injection is easy to type, but IntelliJ even shows a warning for it ("Field injection is not recommended"). You will see it in older projects — recognise it, but don't write it.

3.2 @Autowired — and when it's optional

@Autowired means "Spring, please inject a matching bean here". Where you need it:

Situation@Autowired needed?
Class has exactly one constructor❌ No (since Spring 4.3). Spring uses it automatically. This is the modern style.
Class has several constructors✅ Yes, on the one Spring should use (otherwise Spring looks for a no-arg constructor).
Setter injection✅ Yes, on the setter.
Field injection✅ Yes, on the field.
Parameters of a @Bean method❌ No — always injected.
@Service
public class DeliveryEstimator {
    private final MapsClient maps;
    private final int bufferMinutes;

    @Autowired                                     // two constructors -> mark the one for Spring
    public DeliveryEstimator(MapsClient maps) {
        this(maps, 10);
    }

    DeliveryEstimator(MapsClient maps, int bufferMinutes) {   // used by tests
        this.maps = maps;
        this.bufferMinutes = bufferMinutes;
    }
}

@Autowired is in package org.springframework.beans.factory.annotation. (The Java standard also has @Inject from jakarta.inject which does the same — you may see it in some projects.)

3.3 How Spring finds a match — "by type" first

When Spring needs to fill a parameter of type PaymentGateway, it looks for beans whose type is PaymentGateway (or implements/extends it). Then:

Find beans by TYPE→ 0 found?
error (unless optional)→ 1 found?
inject it ✅→ 2+ found?
@Qualifier → @Primary → parameter name → error

With several candidates Spring narrows down in this order:

  1. @Qualifier("name") on the injection point → take that exact bean.
  2. Exactly one candidate marked @Primary → take it.
  3. A candidate whose bean name equals the parameter/field name → take it (a fallback; needs the -parameters compiler flag for constructor parameters — our pom sets it).
  4. Still undecided → NoUniqueBeanDefinitionException: expected single matching bean but found 3: cardPayment,paypal,upiPayment.

3.4 Multiple implementations: @Primary

QuickBite has three PaymentGateway beans. Most of the app should use card payments, so we mark that one as the default:

payment/CardPayment.java@Component
@Primary                 // "the default PaymentGateway when nobody says which one"
@Order(1)
public class CardPayment implements PaymentGateway { ... }

Now CheckoutService(PaymentGateway paymentGateway, ...) receives CardPayment — without mentioning it anywhere.

@Primary also works on @Bean methods:

@Bean
@Primary
public Clock clock() { return Clock.systemUTC(); }

3.5 Multiple implementations: @Qualifier

Express checkout must always use UPI. We point at the exact bean by its name:

order/ExpressCheckoutService.java@Service
public class ExpressCheckoutService {

    private final PaymentGateway paymentGateway;

    public ExpressCheckoutService(@Qualifier("upiPayment") PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}
@Primary@Qualifier
Placed onThe bean (class or @Bean method)The injection point (parameter / field / setter) — and optionally on the bean, to give it a qualifier label
Meaning"I am the default choice""I want this specific one"
Who decidesThe bean providerThe bean consumer
When both apply@Qualifier wins — a specific request beats a general default.
ℹ️ Avoid typos in qualifier strings @Qualifier("upiPaymnet") (typo) fails at startup with "No qualifying bean". In bigger projects teams create constants (PaymentNames.UPI) or custom qualifier annotations (an annotation such as @Upi that is itself annotated with @Qualifier), so the compiler catches mistakes.

3.6 Injecting ALL beans of a type: List and Map

Sometimes you don't want one payment gateway — you want all of them, e.g. to show the options on the checkout page. Just ask for a collection:

payment/PaymentRegistry.java@Component
public class PaymentRegistry {

    private final List<PaymentGateway> allGateways;               // all beans, sorted by @Order
    private final Map<String, PaymentGateway> gatewaysByName;     // key = bean name

    public PaymentRegistry(List<PaymentGateway> allGateways,
                           Map<String, PaymentGateway> gatewaysByName) {
        this.allGateways = allGateways;
        this.gatewaysByName = gatewaysByName;
    }

    public String payWith(String beanName, double amount) {
        PaymentGateway gateway = gatewaysByName.get(beanName);    // "paypal", "upiPayment", ...
        if (gateway == null) throw new IllegalArgumentException("Unknown payment method: " + beanName);
        return gateway.pay(amount);
    }
}
  • List<PaymentGateway> → every bean of that type. Order is controlled with @Order(1), @Order(2)… (lower number = earlier).
  • Map<String, PaymentGateway> → key is the bean name. Note PayPalPayment is named "paypal" by @Component("paypal").
  • This is the Strategy pattern for free: add a new @Component class WalletPayment implements PaymentGateway and it appears automatically — no if/else or switch to edit.
💡 Real-world use Validation rules, discount rules, report exporters (PDF/Excel/CSV), notification channels — any time you have "many interchangeable handlers", inject a List or Map of them.

3.7 @Value — injecting settings, not beans

Hard-coding values like the delivery fee in Java code is bad: changing it means recompiling and redeploying. Instead we keep settings in a properties file (key = value lines):

src/main/resources/application.propertiesshop.name=QuickBite
shop.delivery-fee=40.0
shop.free-delivery-above=300
shop.max-items-per-order=20
shop.cities=Hyderabad,Pune,Chennai

Two pieces connect this file to your beans:

  1. @PropertySource on a configuration class loads the file into Spring's Environment (a central "settings store" — Topic 26).
  2. @Value("${key}") on a parameter/field injects one value. ${...} is a placeholder: "replace me with the setting called key".
config/AppConfig.java@Configuration
@ComponentScan("com.course.di")
@PropertySource("classpath:application.properties")     // classpath: = from src/main/resources
public class AppConfig {

    @Bean
    public static PropertySourcesPlaceholderConfigurer propertyPlaceholderConfigurer() {
        return new PropertySourcesPlaceholderConfigurer();
    }
}
config/ShopSettings.java@Component
public class ShopSettings {

    public ShopSettings(@Value("${shop.name}") String shopName,
                        @Value("${shop.delivery-fee}") double deliveryFee,
                        @Value("${shop.free-delivery-above:500}") double freeDeliveryAbove,
                        @Value("${shop.max-items-per-order}") int maxItemsPerOrder,
                        @Value("${shop.support-email:help@quickbite.example}") String supportEmail,
                        @Value("${shop.cities}") String[] cities) {
        ...
    }
}
SyntaxMeaning
${shop.name}Value of key shop.name. Missing key → startup error (with the configurer bean).
${shop.free-delivery-above:500}Use the key; if it's missing, use the default after the colon: 500.
${shop.support-email:help@quickbite.example}Key not in the file → default is injected.
${shop.cities} into String[]Comma-separated text is split into an array automatically.
#{...}Not a placeholder but a SpEL expression (calculations, other beans). Topic 26.

Spring converts the text from the file into the parameter's type: "40.0" → double, "20" → int, "true" → boolean.

ℹ️ What is PropertySourcesPlaceholderConfigurer? It's a Spring helper that replaces ${...} placeholders. Without it, plain Spring still resolves placeholders in a "lenient" way — but an unknown key is silently injected as the literal text "${shop.typo}". With the bean, an unknown key fails fast with Could not resolve placeholder 'shop.typo'. It must be a static @Bean because it has to exist before other beans are created. Spring Boot registers it automatically and also loads application.properties without @PropertySource — Topic 29.

3.8 Optional dependencies

By default every dependency is required: if no matching bean exists, startup fails with NoSuchBeanDefinitionException: No qualifying bean of type 'SmsGateway' available. When a dependency is truly optional, say so:

notify/OrderNotifier.java@Component
public class OrderNotifier {

    private final Optional<SmsGateway> smsGateway;            // way 1: java.util.Optional
    private final ObjectProvider<SmsGateway> smsProvider;     // way 2: Spring's ObjectProvider
    private SmsGateway backupSms;                             // way 3: optional setter

    public OrderNotifier(Optional<SmsGateway> smsGateway, ObjectProvider<SmsGateway> smsProvider) {
        this.smsGateway = smsGateway;
        this.smsProvider = smsProvider;
    }

    @Autowired(required = false)                              // not called if no bean exists
    public void setBackupSms(SmsGateway backupSms) { this.backupSms = backupSms; }

    public String notifyCustomer(String phone, String text) {
        if (smsGateway.isPresent()) {
            smsGateway.get().sendSms(phone, text);
            return "SMS sent";
        }
        return "No SMS gateway installed -> skipped SMS";
    }
}
WayWhen no bean existsBest for
Optional<T> parameterOptional.empty()Simple "maybe there is one" with constructor injection
ObjectProvider<T>getIfAvailable() returns null; getIfAvailable(() -> fallback) returns a fallbackOptional and lazy lookups; also very useful with prototype beans (Topic 25)
@Autowired(required = false)Setter/field is simply not set (stays null)Optional setter injection

3.9 Circular dependencies

A circular dependency is when beans depend on each other in a circle:

InventoryService→ needs → PricingService→ needs → InventoryService↺

With constructor injection, Spring must create PricingService before it can call InventoryService's constructor — but creating PricingService requires an InventoryService first. Chicken and egg! Spring detects this and stops:

BeanCurrentlyInCreationException: Error creating bean with name 'inventoryService':
Requested bean is currently in creation: Is there an unresolvable circular reference
or an asynchronous initialization dependency?

A circle like this usually means a design problem: two classes are too entangled, or responsibilities are in the wrong place. Fixes, from best to worst:

  1. Redesign: extract the shared part into a third bean. Here, both services only needed the stock level. We moved that into StockLevels, and both depend on it. The arrows now point one way:
    FixedInventoryService→ StockLevels← FixedPricingService
  2. Merge the two classes if they are really one responsibility.
  3. Use events (Topic 52): A publishes "stock changed", B listens — A doesn't need B any more.
  4. @Lazy on one constructor parameter — Spring injects a placeholder proxy and creates the real bean later. It works, but hides the design smell. Use as a last resort.
⚠️ "But with field injection the circle works!" In plain Spring, field/setter injection can quietly "solve" some cycles by injecting a half-finished bean. That is not a feature to rely on. Since Spring Boot 2.6, circular references are forbidden by default (spring.main.allow-circular-references=false) — so such code fails as soon as it moves to Spring Boot. Constructor injection finds the problem early, which is a good thing.

4.2 Demo 6 – catching the circular dependency

App.javatry (AnnotationConfigApplicationContext broken =
             new AnnotationConfigApplicationContext("com.course.circular.broken")) {
    System.out.println("(should never get here)");
} catch (Exception e) {
    Throwable root = e;
    while (root.getCause() != null) {      // dig to the deepest cause
        root = root.getCause();
    }
    System.out.println("FAILED as expected -> " + root.getClass().getSimpleName());
    System.out.println(root.getMessage());
}
  • new AnnotationConfigApplicationContext("package.name") scans a package directly (no config class needed).
  • Spring wraps errors in several layers (UnsatisfiedDependencyException → … → BeanCurrentlyInCreationException). The deepest cause usually has the clearest message — a useful habit for reading any Java stack trace (Topic 10).
  • Spring also logs a WARNING: Exception encountered during context initialization - cancelling refresh attempt... line (red in some terminals). That's Spring's own log — expected here.

6. Common mistakes

⚠️ Mistake: NoUniqueBeanDefinitionException after adding a second implementation Everything worked with one PaymentGateway. You add UpiPayment, and suddenly startup fails: expected single matching bean but found 2.
Fix: mark the default with @Primary, and/or use @Qualifier where a specific one is needed — or inject a List/Map if you need all of them.
⚠️ Mistake: field is null — "but I wrote @Autowired!" Usually because the object was created with new LegacyAuditService() — Spring never saw it, so it never injected anything. Or the class isn't a bean (no stereotype annotation, outside the scanned package).
Fix: let Spring create the object and get it via injection. With constructor injection this mistake is impossible: new forces you to pass the dependencies.
⚠️ Mistake: forgetting @Autowired on a setter The setter is never called; the field stays null; NullPointerException later.
Fix: setters need @Autowired. (Single constructors don't.)
⚠️ Mistake: @Value on a static field @Value("${shop.name}") private static String name; stays null — Spring injects into objects, not classes.
Fix: use a normal (preferably constructor) parameter.
⚠️ Mistake: ${...} not replaced — you see the literal text ${shop.name} The properties file wasn't loaded (missing @PropertySource, wrong file name, file not in src/main/resources), and no placeholder configurer is registered.
Fix: check the @PropertySource path, and register the static PropertySourcesPlaceholderConfigurer so mistakes fail loudly.
⚠️ Mistake: mixing ${} and #{} @Value("#{shop.name}") is a SpEL expression looking for a bean called shop, not a property.
Fix: properties use ${...}. SpEL (#{...}) is for expressions — Topic 26.
🛑 Mistake: "fixing" a circular dependency by switching to field injection It may hide the error in plain Spring, but the design problem stays and Spring Boot will refuse it by default.
Fix: redesign — extract shared logic into a third bean, merge classes, or use events.

7. Best practices

  • Constructor injection for all required dependencies, with private final fields. Leave out @Autowired when there's one constructor.
  • Setter injection only for genuinely optional dependencies; never field injection in production code (it's OK in test classes).
  • Too many constructor parameters (5+)? The class probably does too much. Split it (Single Responsibility — Topic 70).
  • Depend on interfaces and choose implementations with @Primary (a sensible default) and @Qualifier (exceptions).
  • Use List/Map injection instead of long if/else chains choosing an implementation.
  • Never hard-code settings like URLs, fees, limits, passwords. Put them in properties and inject with @Value (or, in Spring Boot, the type-safe @ConfigurationProperties — Topic 29).
  • Provide sensible defaults (${key:default}) for non-critical settings; leave critical ones without defaults so a missing value fails fast.
  • Treat circular dependencies as a design bug, not a configuration puzzle.

8. Key takeaways

  • Three injection styles: constructor (preferred), setter (optional deps), field (avoid).
  • @Autowired is optional on a single constructor; required on setters, fields and when there are several constructors.
  • Spring matches by type; with several candidates it uses @Qualifier, then @Primary, then the parameter name, else it fails.
  • @Primary = default chosen by the provider; @Qualifier = specific choice by the consumer, and it wins.
  • Ask for List<T> (ordered with @Order) or Map<String, T> (bean name → bean) to get all implementations.
  • @PropertySource loads a properties file; @Value("${key:default}") injects values with automatic type conversion.
  • Optional dependencies: Optional<T>, ObjectProvider<T>, or @Autowired(required = false).
  • Circular dependencies fail with BeanCurrentlyInCreationException; fix them by redesigning.

Challenge

Fix the cycle with @Lazy. In circular/broken/PricingService, put @Lazy (from org.springframework.context.annotation) on the constructor parameter. Run. Does demo 6 still fail? Explain in your own words what Spring injected, and why the lesson still calls redesign the better fix.

The broken context now starts, so demo 6 prints "(should never get here)". Spring injected a lazy-resolution proxy — a stand-in object of a generated subclass of InventoryService. Redesign removes the cause instead of hiding it. (Remove @Lazy afterwards so the demo shows the error again.)

    }
}

10. Interview questions

Q1. What types of dependency injection does Spring support? Which is recommended and why?

Constructor, setter and field injection. Constructor injection is recommended: it allows final (immutable) fields, guarantees the object is fully initialised, makes dependencies explicit, enables plain unit tests without Spring or reflection, detects circular dependencies early and makes "too many dependencies" visible. Setter injection suits optional dependencies; field injection should be avoided outside tests.

Q2. Is @Autowired required on a constructor?

Not if the class has exactly one constructor (since Spring 4.3) — Spring uses it automatically. If there are several constructors, you must annotate the one Spring should use; otherwise Spring tries the default no-arg constructor.

Q3. How does Spring resolve which bean to inject when there are multiple candidates?

It matches by type first. If several beans match, it applies @Qualifier at the injection point; otherwise it prefers a single @Primary candidate (or the highest @Priority); as a last fallback it matches the bean name to the parameter/field name. If it still can't decide, it throws NoUniqueBeanDefinitionException.

Q4. What's the difference between @Primary and @Qualifier?

@Primary is declared on a bean and makes it the default among candidates of the same type. @Qualifier is declared at the injection point (and optionally on the bean) to request a specific bean. @Qualifier takes precedence over @Primary.

Q5. How can you inject all implementations of an interface?

Inject a List<Interface> (ordered by @Order/Ordered), a Map<String, Interface> (keys are bean names), or use ObjectProvider<Interface> and stream over it. This is commonly used to implement the Strategy pattern.

Q6. How do you inject values from a properties file?

Load the file with @PropertySource("classpath:file.properties") (Spring Boot loads application.properties automatically) and inject with @Value("${key}") or @Value("${key:default}"). Spring converts the string to the target type. For groups of settings, Spring Boot's @ConfigurationProperties is the type-safe alternative.

Q7. What is the difference between ${...} and #{...} in @Value?

${...} is a property placeholder resolved from the Environment (properties files, system properties, environment variables). #{...} is a SpEL expression evaluated at runtime — it can do arithmetic, call methods and reference other beans. They can be combined: #{'${shop.name}'.toUpperCase()}.

Q8. How do you declare an optional dependency?

Use Optional<T> as the parameter type, use ObjectProvider<T> and call getIfAvailable(), use @Autowired(required = false) on a setter/field, or annotate the parameter with @Nullable.

Q9. What is a circular dependency and how do you resolve it?

Two or more beans that depend on each other directly or indirectly (A → B → A). With constructor injection Spring can't create either and throws BeanCurrentlyInCreationException. The best fix is a redesign: extract the shared logic into a third bean, merge the classes, or decouple with events. A workaround is @Lazy on one injection point (injects a proxy). Spring Boot 2.6+ forbids circular references by default.

Q10. Why is field injection considered bad practice?

Fields can't be final; dependencies are hidden; the class can't be instantiated in a valid state without Spring (tests need reflection or a Spring context); it hides classes with too many dependencies; and it couples the class to the DI container.
