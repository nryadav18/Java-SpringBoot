Build stateless login for a REST API: log in once, get a signed token, and send it with every request – the way modern web and mobile apps work.

1. Why this matters

In topic 48 the client sent the password with every request (HTTP Basic). That works, but it is not how the apps on your phone behave. When you open a food-delivery app, you log in once; for weeks the app talks to the server without asking for your password again. The secret behind that is usually a token – and the most popular token format is the JWT (JSON Web Token, pronounced "jot").

JWTs are everywhere in enterprise Java jobs:

  • Single-page apps (React, Angular, Vue) and mobile apps calling a Spring Boot REST API.
  • Microservices (Part F): one service checks the token without asking a central session store.
  • OAuth2 / OpenID Connect (topic 50): access tokens and ID tokens from Google, Keycloak, Auth0 are JWTs.

It is also one of the most common interview topics for Spring developers. In this lesson you build the whole thing yourself, so nothing feels like magic.

2. Real-life analogy

🎟️ The music festival wristband

At the entrance you show your ticket and ID card once (login with username + password). Staff put a wristband on your arm (the token). Printed on it: your name, VIP (your role), and valid Saturday only (the expiry).

At every stage and bar (every API endpoint), staff simply look at the wristband. They do not phone the ticket office to ask "is this person allowed?". The wristband itself carries the proof. That is stateless: the server keeps no list of who is inside.

The wristband has a tamper-proof seal (the signature). If you scratch out "Standard" and write "VIP", the seal is broken and staff reject it immediately.

But: if you lose the wristband, whoever finds it can use it until Saturday ends – staff cannot tell the difference. That is why tokens should be short-lived, and why apps use a refresh token – like going back to the entrance desk to swap an expiring wristband for a fresh one.

3. Concepts step by step

3.1 Sessions vs tokens

Session-based (topic 47 form login): after login the server creates a session – a little record in its memory – and gives the browser a cookie with the session id (JSESSIONID). On each request the server looks the id up: "ah, session 7F3A… is alice".

Token-based (this topic): after login the server creates a signed token that contains "this is alice, role USER, valid until 10:15" and gives it to the client. The server stores nothing. On each request it checks the signature and reads the content.

Session + cookieJWT (Bearer token)
Server stateStores every session (memory, Redis…)None – stateless
Scaling to many serversNeeds sticky sessions or a shared session storeEasy – any instance can verify the signature
Sent howCookie, automatically by the browserAuthorization header, added by the app's code
ClientsMainly browsersBrowsers, mobile apps, other services, curl
CSRF riskYes (cookies auto-sent) → CSRF protection neededNo (header not auto-sent) → CSRF can be disabled
Logout / revokeEasy: delete the sessionHard: the token stays valid until it expires (see 3.11)
SizeTiny idBigger (hundreds of bytes) on every request
ℹ️ Neither is "better" Classic server-rendered websites (Thymeleaf, topic 36) are perfectly served by sessions. JWTs shine for APIs consumed by many kinds of clients and for distributed systems.

3.2 Anatomy of a JWT

Here is a real token our project produced when alice logged in (colours added):

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGljZSIsInJvbGVzIjpbIlJPTEVfVVNFUiJdLCJpc3MiOiJmb29kLWRlbGl2ZXJ5LWFwaSIsImlhdCI6MTc5MTUyMDkxMCwiZXhwIjoxNzkxNTIxODEwfQ.ZyVYy5_bqki9XHJEsCorErXbFaHLpNQ34Q6RH0Fhhx4

Three parts separated by dots. Each part is Base64URL-encoded (Base64 with URL-safe characters and no = padding). Decode them and you get:

① Header 
{"alg":"HS256"}

Which algorithm signed it. HS256 = HMAC with SHA-256.

② Payload (claims) 
{
  "sub": "alice",
  "roles": ["ROLE_USER"],
  "iss": "food-delivery-api",
  "iat": 1791520910,
  "exp": 1791521810
}

Facts ("claims") about the user. iat/exp are seconds since 1970 (exp = iat + 900 s = 15 min).

③ Signature 
HMACSHA256(
  base64url(header) + "." +
  base64url(payload),
  SECRET_KEY)

A fingerprint of ① + ② made with our secret key.

ClaimNameMeaning
subSubjectWho the token is about (username or user id)
issIssuerWho created the token
audAudienceWho the token is meant for (which API)
iatIssued atCreation time
expExpirationAfter this moment the token is invalid
nbfNot beforeNot valid before this moment
jtiJWT idUnique id (useful for blacklisting)
roles(custom)Anything you like – keep it small and non-secret
🔓 A JWT is signed, NOT encrypted Anybody holding the token can decode the payload – try pasting one into https://jwt.io (only with test tokens!), or in PowerShell: [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String("eyJhbGciOiJIUzI1NiJ9")) → {"alg":"HS256"}. Never put passwords, card numbers or other secrets in the payload. (Encrypted JWTs exist – "JWE" – but are rarely needed.)

3.3 How the signature stops tampering

Suppose alice decodes her token, changes "roles":["ROLE_USER"] to ["ROLE_ADMIN"], encodes it again and sends it.

  1. Our server takes header + modified payload and computes HMAC-SHA256 with its secret key.
  2. The result is completely different from the signature alice sent (she does not know the key, so she could not recompute it).
  3. JJWT throws SignatureException → our filter ignores the token → 401.

So: reading a token needs nothing; creating or changing a valid token needs the secret key. Protect that key like a master password.

AlgorithmTypeKeysUsed when
HS256 (this project)Symmetric (HMAC)One shared secret signs and verifiesThe same application issues and checks tokens
RS256 / ES256Asymmetric (RSA / elliptic curve)Private key signs, public key verifiesA separate auth server issues tokens, many APIs verify with the public key (topic 50)

3.6 The secret key

For HS256 the key must be at least 256 bits = 32 bytes of random data. Random bytes are not printable text, so we store them as Base64 in the properties:

application.propertiesapp.jwt.secret=${JWT_SECRET:VPRUfjavGU03Le4EyEe/zdh5sHYm5ZtiWXxqhb3pf0o=}
app.jwt.expiration=15m
app.jwt.issuer=food-delivery-api

${JWT_SECRET:...} means "use the environment variable JWT_SECRET if it exists, otherwise this development default" (topic 29). Generate your own secret:

PS> [Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))
Q2xrKp9...=                        (44 characters = 32 bytes)

$ openssl rand -base64 32          (Git Bash / Linux / macOS)

In Java the Base64 text becomes a key object:

SecretKey key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(properties.secret()));

If the key is shorter than 256 bits, JJWT refuses with WeakKeyException – a good thing. A key like "mysecret" could be brute-forced.

The three settings are bound to a record with @ConfigurationProperties (topic 29):

security/JwtProperties.java@ConfigurationProperties(prefix = "app.jwt")
public record JwtProperties(String secret, Duration expiration, String issuer) { }

3.7 JwtService – create, read, verify

security/JwtService.java (key parts)public String generateToken(UserDetails user) {
    Instant now = Instant.now();
    List<String> roles = user.getAuthorities().stream().map(GrantedAuthority::getAuthority).toList();

    return Jwts.builder()
            .subject(user.getUsername())                               // "sub"
            .claim("roles", roles)                                     // custom claim
            .issuer(properties.issuer())                               // "iss"
            .issuedAt(Date.from(now))                                  // "iat"
            .expiration(Date.from(now.plus(properties.expiration())))  // "exp"
            .signWith(signingKey)                                      // HS256
            .compact();                                                // "xxx.yyy.zzz"
}

public String extractUsername(String token) {
    return parseClaims(token).getSubject();
}

public boolean isTokenValid(String token, UserDetails user) {
    try {
        Claims claims = parseClaims(token);
        return user.getUsername().equals(claims.getSubject())
                && properties.issuer().equals(claims.getIssuer());
    } catch (JwtException | IllegalArgumentException e) {
        return false;
    }
}

private Claims parseClaims(String token) {
    return Jwts.parser()
            .verifyWith(signingKey)       // check the signature with OUR key
            .build()
            .parseSignedClaims(token)     // also rejects EXPIRED tokens and unsigned ("alg":"none") tokens
            .getPayload();
}

What can go wrong while parsing – each is a subclass of JwtException:

ExceptionCause
ExpiredJwtExceptionexp is in the past
SignatureExceptionPayload changed, or signed with another key
MalformedJwtExceptionNot a valid JWT at all (e.g. abc.def.ghi)
UnsupportedJwtExceptionWrong kind of token, e.g. unsigned

3.8 JwtAuthenticationFilter – our own security filter

Spring Security has a filter for Basic and one for form login – but none for "our" JWTs. So we write one. It extends OncePerRequestFilter, a Spring base class that guarantees the filter runs exactly once per request (even on internal forwards like /error).

security/JwtAuthenticationFilter.java (core)@Override
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                FilterChain filterChain) throws ServletException, IOException {

    String header = request.getHeader(HttpHeaders.AUTHORIZATION);
    if (header == null || !header.startsWith("Bearer ")) {     // (1) no token
        filterChain.doFilter(request, response);               //     continue as anonymous
        return;
    }
    String token = header.substring(7);                        // (2) cut "Bearer "

    try {
        String username = jwtService.extractUsername(token);   // (3) throws if fake/expired
        if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
            UserDetails user = userDetailsService.loadUserByUsername(username);   // (4)
            if (jwtService.isTokenValid(token, user)) {
                UsernamePasswordAuthenticationToken authentication =
                        new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                authentication.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                SecurityContext context = SecurityContextHolder.createEmptyContext();
                context.setAuthentication(authentication);       // (5) "this request = alice"
                SecurityContextHolder.setContext(context);
            }
        }
    } catch (JwtException | IllegalArgumentException | UsernameNotFoundException e) {
        log.debug("Rejected JWT: {}", e.getMessage());          // (6) stay anonymous, never log the token
    }
    filterChain.doFilter(request, response);                    // (7) ALWAYS continue
}
  • (1) No header is not an error here. Public URLs like /api/auth/login must work without a token. The decision is made later by AuthorizationFilter.
  • (4) We load the user from the database. That costs one query per request, but a deleted user's token stops working immediately. A fully stateless alternative builds the authorities from the roles claim instead (exercise 4).
  • (5) The credentials are null: we never need the password again after login.
  • (6) An invalid token just leaves the request anonymous → protected URLs answer 401 through the entry point.
⚠️ Why the filter is NOT a @Component Spring Boot automatically registers every Filter bean as a normal servlet filter for all URLs. A @Component JWT filter would then run twice: once in the security chain and once outside it. We avoid that by creating it with new inside SecurityConfig. (Alternative: keep it a bean and disable the extra registration with a FilterRegistrationBean whose setEnabled(false).)

3.9 The stateless SecurityFilterChain

security/SecurityConfig.java (core)http
    .csrf(AbstractHttpConfigurer::disable)            // no cookies -> no CSRF risk
    .httpBasic(AbstractHttpConfigurer::disable)       // the only way in is a token
    .formLogin(AbstractHttpConfigurer::disable)
    .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/auth/**", "/error").permitAll()
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .anyRequest().authenticated()
    )
    .exceptionHandling(ex -> ex.authenticationEntryPoint(jsonUnauthorizedEntryPoint()))
    .addFilterBefore(new JwtAuthenticationFilter(jwtService, userDetailsService),
                     UsernamePasswordAuthenticationFilter.class);

Our filter slots into the chain from topic 47:

SecurityContextHolderFilter→ HeaderWriterFilter→ LogoutFilter→ JwtAuthenticationFilter (ours)→ AnonymousAuthenticationFilter→ ExceptionTranslationFilter→ AuthorizationFilter→ Controller
ℹ️ Why a custom AuthenticationEntryPoint? The entry point decides what an anonymous user gets for a protected URL. Basic auth's entry point sends 401; form login's redirects to /login. We disabled both, so Spring falls back to Http403ForbiddenEntryPoint – anonymous users would get a confusing 403. Our lambda returns a proper 401 with WWW-Authenticate: Bearer and a small JSON body.

3.10 AuthController: register and login

For login we re-use Spring Security's own password checking via the AuthenticationManager (made injectable with a small bean):

security/SecurityConfig.java@Bean
public AuthenticationManager authenticationManager(AuthenticationConfiguration configuration) throws Exception {
    return configuration.getAuthenticationManager();   // built from our UserDetailsService + PasswordEncoder
}
auth/AuthService.java (login)public AuthResponse login(LoginRequest request) {
    Authentication authentication = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(request.username(), request.password()));
    // wrong password? -> BadCredentialsException -> ApiExceptionHandler -> 401
    UserDetails user = (UserDetails) authentication.getPrincipal();
    return toResponse(user);   // generate token + build {"accessToken":..,"tokenType":"Bearer",..}
}

register works like topic 48 (validate, check duplicates, BCrypt, role USER) and then returns a token straight away, so the new user is logged in.

3.11 Request traces

Trace 1 – valid token, GET /api/orders

Bearer eyJ…→ JwtFilter: signature ✓ exp ✓ → user alice→ SecurityContext: alice / ROLE_USER→ AuthorizationFilter: authenticated ✓→ 200

Trace 2 – tampered or expired token

Bearer eyJ…(changed)→ JwtFilter: SignatureException → log, stay anonymous→ AuthorizationFilter: authenticated ✗→ EntryPoint → 401 JSON

Trace 3 – valid USER token on /api/admin/dashboard

Bearer eyJ… (alice)→ JwtFilter ✓ alice / ROLE_USER→ AuthorizationFilter: hasRole ADMIN ✗→ AccessDeniedHandler → 403

Trace 4 – POST /api/auth/login (no token)

no header→ JwtFilter: nothing to do→ AuthorizationFilter: permitAll ✓→ AuthController → AuthenticationManager → token

3.12 Token expiry and the refresh-token idea

Because the server stores nothing, it cannot "cancel" a JWT before exp. If a token is stolen, the thief can use it until it expires. Hence the golden rule: access tokens must be short-lived (5–15 minutes). But nobody wants to type their password every 15 minutes. The solution is a second token:

Access tokenRefresh token
PurposeCall the APIGet a new access token
LifetimeShort (e.g. 15 min)Long (e.g. 7–30 days)
Sent toEvery API requestOnly POST /api/auth/refresh
Server stores it?NoYes (database) – so it can be revoked
Login→ access (15 min) + refresh (7 days)→ API calls with access token→ 401 expired→ POST /refresh with refresh token→ new access (+ new refresh, "rotation")

Logout = delete the refresh token in the database; the access token dies on its own within minutes. Other revocation tricks: a blacklist of token ids (jti) until they expire, or a tokenVersion column on the user that is put into the token and increased on "log out everywhere". Our project keeps it simple (access token only) – exercise 5 adds refresh tokens. In topic 50 you will see that an OAuth2 server (Keycloak) gives you refresh tokens out of the box.

3.13 Security best practices for JWTs

RuleWhy
HTTPS onlyA token is as good as a password while it lives. On plain HTTP anyone on the network can copy it.
Short expiry for access tokensLimits the damage of a stolen token.
Nothing sensitive in the payloadIt is only Base64 – readable by anyone.
Strong random secret, ≥ 256 bits, from env/secret manager, never in GitWhoever has the key can mint admin tokens.
Verify signature, exp, iss (and aud)JJWT checks signature + exp; we also check the issuer.
Never accept "alg":"none"A classic attack. parseSignedClaims rejects unsigned tokens.
Do not log tokensLogs are read by many people and tools.
Rotate keys occasionally (use a kid header to support old + new keys)Limits damage of a leaked key.

Where should a browser app keep the token? There is no perfect answer:

StorageRiskNotes
JavaScript memory (a variable)Lost on page reloadSafest against XSS theft; combine with a refresh token in an HttpOnly cookie
localStorage / sessionStorageXSS: any injected script can read itSimple and common, but only with strict XSS protection
HttpOnly + Secure + SameSite cookieJavaScript cannot read it; but cookies are auto-sent → think about CSRF againOften recommended for browser apps ("Backend for Frontend" pattern)
Mobile apps–Use the OS secure storage (Android Keystore, iOS Keychain)

6. Common mistakes

⚠️ Mistake: header without Bearer (or without the space) Authorization: eyJ... or Authorization: Bearer:eyJ... → the filter ignores it → 401.
Fix: exactly Authorization: Bearer <token> – the word Bearer, one space, the token.
⚠️ Mistake: anonymous users get 403 instead of 401 With Basic and form login disabled, Spring uses Http403ForbiddenEntryPoint.
Fix: configure an authenticationEntryPoint that returns 401 (as in our SecurityConfig), or use new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED).
⚠️ Mistake: WeakKeyException: ... is not secure enough for any JWT HMAC-SHA algorithm Your secret is shorter than 256 bits, or you passed a plain string like "mysecret".
Fix: 32+ random bytes, Base64-encoded, decoded with Decoders.BASE64.
⚠️ Mistake: Unable to find an implementation for interface io.jsonwebtoken... Only jjwt-api was added.
Fix: also add jjwt-impl and jjwt-jackson (runtime scope), same version.
⚠️ Mistake: the JWT filter as @Component It is auto-registered for every URL as well, runs outside the security chain, and you get confusing double processing.
Fix: create it with new in the config, or disable the auto-registration with a FilterRegistrationBean.
⚠️ Mistake: expecting "logout" to kill the token The server stores nothing, so a JWT stays valid until exp, even after the user "logged out".
Fix: short-lived access tokens + server-side refresh tokens (or a blacklist) – section 3.12.
⚠️ Mistake: tutorials with setSubject, parserBuilder, parseClaimsJws That is the JJWT 0.11 API.
Fix: use the 0.12 names (table in 3.5).
🔥 Mistake: secrets in the token or in Git Passwords/personal data in claims are readable by anyone; a committed signing key lets anyone forge admin tokens.
Fix: minimal claims; secret via JWT_SECRET environment variable or a secret manager.
⚠️ Mistake: browser app gets CORS errors A React app on another port sends a preflight OPTIONS without a token.
Fix: add .cors(Customizer.withDefaults()) and a CorsConfigurationSource bean allowing the Authorization header (topic 47, 3.10).

7. Best practices

  • Prefer a proven authorization server (Keycloak, Auth0, Okta, Spring Authorization Server) for big systems – topic 50. Self-made JWT, like here, is fine for one app, and great for understanding.
  • Access tokens: 5–15 minutes. Refresh tokens: stored server-side, rotated on each use, revocable.
  • Keep claims small: id/username, roles, issuer, expiry. Load the rest from the database when needed.
  • Validate signature, expiry, issuer, audience. Allow a small clock skew (Jwts.parser().clockSkewSeconds(30)) between servers.
  • Return the same 401 message for wrong username and wrong password.
  • Use HTTPS, strict CORS, and protect browser apps against XSS if tokens live in JavaScript.
  • Rate-limit /api/auth/login to slow down password guessing.
  • Write tests for: valid token, missing token, tampered token, expired token, wrong role.

8. Key takeaways

  • Token auth is stateless: the server keeps no session; the client sends Authorization: Bearer <jwt> on every request.
  • A JWT = header.payload.signature, Base64URL-encoded. Signed, not encrypted – anyone can read the payload.
  • The signature (HS256 + secret key) makes any change detectable; only the key holder can create valid tokens.
  • JJWT 0.12.6: Jwts.builder()...signWith(key).compact() to create; Jwts.parser().verifyWith(key).build().parseSignedClaims(t) to verify (incl. expiry).
  • A OncePerRequestFilter reads the header, validates the token and fills the SecurityContext; it is added with addFilterBefore.
  • Stateless chain: CSRF off, no session, no Basic/form, custom 401 entry point, /api/auth/** public.
  • Login uses the AuthenticationManager (UserDetailsService + BCrypt), then returns a token.
  • Short expiry + refresh tokens solve the "cannot revoke" problem; HTTPS and a strong, secret key are mandatory.

10. Interview questions

Q1. What is a JWT and what are its parts?

A compact, URL-safe token format (RFC 7519): header.payload.signature. The header names the algorithm, the payload holds claims (sub, exp, iss, custom ones), and the signature is computed over header + payload with a key. Parts are Base64URL-encoded.

Q2. Is a JWT encrypted? Can the client change it?

A normal (JWS) token is only signed, so anyone can read it – never put secrets in it. The client cannot change it without invalidating the signature, because it does not know the signing key.

Q3. Sessions vs JWT – advantages and disadvantages?

JWT: stateless, scales horizontally, works for non-browser clients, no CSRF when sent in a header. Downsides: hard to revoke, larger requests, payload readable, key management. Sessions: easy revocation and small cookies, but server state and CSRF protection are needed.

Q4. How do you implement JWT authentication in Spring Security?

Public login endpoint that authenticates via AuthenticationManager and returns a signed token; a OncePerRequestFilter that extracts the Bearer token, validates it and sets an Authentication in the SecurityContextHolder; a stateless SecurityFilterChain (CSRF off, STATELESS sessions, custom 401 entry point) with addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class).

Q5. How do you log out / revoke a JWT?

You cannot change a token already issued. Options: short-lived access tokens + server-stored refresh tokens that you delete; a denylist of jti values until expiry; a per-user token version checked on each request; or rotating the signing key (revokes everyone).

Q6. What is a refresh token?

A long-lived credential used only at a token endpoint to obtain new short-lived access tokens without re-entering the password. It is stored server-side so it can be revoked, and is usually rotated (single use).

Q7. HS256 vs RS256?

HS256 uses one shared secret for signing and verifying (symmetric) – fine when one application does both. RS256 uses a private key to sign and a public key to verify (asymmetric) – needed when many services verify tokens issued by a central authorization server, which publishes its public keys via JWKS.

Q8. Why can CSRF be disabled for a JWT API?

CSRF exploits credentials that the browser sends automatically (cookies). A token in the Authorization header is added by application code; a malicious site cannot make the browser add it. If you put the JWT in a cookie, CSRF protection is needed again.

Q9. Where should a SPA store the JWT?

Trade-offs: memory (safe from XSS persistence, lost on reload), localStorage (XSS can steal it), HttpOnly Secure SameSite cookie (not readable by JS, but needs CSRF consideration). A common robust setup: short access token in memory + refresh token in an HttpOnly cookie, or a Backend-for-Frontend.

Q10. What does OncePerRequestFilter guarantee and why use it?

That doFilterInternal runs only once per request, even when the request is forwarded/dispatched internally (e.g. to /error). That avoids validating the token twice or overwriting the context.
