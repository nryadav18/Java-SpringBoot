1. Why this matters

So far, all your data lived in variables and collections. When the program stopped, everything was gone. In Topic 16 you saved data to files — better, but files are hard to search, hard to share between many users, and easy to corrupt if two programs write at once.

Almost every real backend application stores its data in a database: users, products, orders, payments, students. A Spring Boot backend is, most of the time, "a program that receives HTTP requests and reads/writes a database".

JDBC (Java DataBase Connectivity) is Java's standard way to talk to relational databases. Even when you later use Spring Data JPA (Topic 38) and never write JDBC code yourself, it is JDBC underneath: Hibernate generates SQL and runs it through JDBC; Spring Boot configures a JDBC connection pool (HikariCP). When something goes wrong — a slow query, "connection refused", a deadlock, a constraint violation — the error messages are JDBC errors. Knowing JDBC makes you the person who can fix them.

ℹ️ The road ahead Topic 19: raw JDBC (you feel the pain) → Topic 37: Spring JdbcTemplate (half the code) → Topic 38: Spring Data JPA (almost no code). Learning them in this order means you'll understand what each tool does for you.

2. Real-life analogy

📞 Calling a foreign library with an interpreter
  • The database is a huge, well-organised library in another country. It only understands its own language: SQL.
  • JDBC is the standard phone system Java uses to call any library. The buttons are always the same: dial, ask, listen, hang up.
  • The JDBC driver is the interpreter on the line who translates for one specific library (MySQL, PostgreSQL, H2, Oracle). Change the library → change the interpreter, but you keep using the same phone.
  • A Connection is one phone call. Opening a call takes time, so you don't want to dial again for every single question — that's why apps keep a connection pool (a bank of always-open phone lines).
  • A PreparedStatement is a printed request form with blank boxes ("Book title: ____"). Whatever someone writes in the box is treated as a title — never as a new instruction to the librarian. That's why it stops SQL injection.
  • A ResultSet is the list of answers the librarian reads to you, one line at a time.
  • A transaction is like a bank transfer form: either the whole form is processed, or none of it.

3. Concepts step by step

3.1 Databases and SQL in 10 minutes

A relational database (MySQL, PostgreSQL, Oracle, SQL Server, H2...) stores data in tables, like spreadsheets:

id (PRIMARY KEY)nameemailmarks
1Ashaasha@college.edu91
2Benben@college.edu72
3Chenchen@college.edu85
  • A table holds one kind of thing (students). A row (record) is one student. A column is one property (name), with a fixed type (INT, VARCHAR(100), DECIMAL(10,2), DATE...).
  • The primary key (id) uniquely identifies each row. AUTO_INCREMENT lets the database pick the next number.
  • Constraints are rules the database enforces: NOT NULL, UNIQUE, CHECK (balance >= 0), FOREIGN KEY (link to another table — Topic 40).

SQL (Structured Query Language) is the language to talk to it. Creating a table (this is "DDL" — data definition):

CREATE TABLE students (
    id     INT AUTO_INCREMENT PRIMARY KEY,
    name   VARCHAR(100) NOT NULL,
    email  VARCHAR(150) NOT NULL,
    marks  INT          NOT NULL,
    CONSTRAINT uk_students_email UNIQUE (email)
);

The four CRUD operations (this is "DML" — data manipulation):

CRUDSQLExample
CreateINSERTINSERT INTO students (name, email, marks) VALUES ('Asha', 'asha@college.edu', 91);
ReadSELECTSELECT id, name FROM students WHERE marks >= 85 ORDER BY marks DESC;
UpdateUPDATEUPDATE students SET marks = 78 WHERE id = 2;
DeleteDELETEDELETE FROM students WHERE id = 3;

A few more SQL words you'll meet: COUNT(*), AVG(marks), GROUP BY, JOIN (combine tables), LIKE 'A%' (text pattern), LIMIT 10.

🚫 Never forget WHERE UPDATE students SET marks = 0; or DELETE FROM students; without a WHERE changes/deletes every row. Experienced developers have done this in production — once.
ℹ️ What is H2? H2 is a small database written in Java. It can run inside your program, in memory — no installation, no server, perfect for learning and tests. Its SQL is very close to MySQL/PostgreSQL. We switch to a real MySQL server in Topic 43.

3.2 JDBC architecture

The java.sql package (part of the JDK) contains mostly interfaces: Connection, PreparedStatement, ResultSet... The driver (a JAR you add as a dependency) contains the real classes that implement them. This is "programming to an interface" from Topic 8: switch from H2 to MySQL by changing the driver and the URL — your DAO code stays the same (as long as the SQL is standard).

  • DriverManager looks at the URL prefix (jdbc:h2:) and picks the right driver from the classpath. Since JDBC 4 (Java 6) drivers register themselves — old tutorials with Class.forName("com.mysql.jdbc.Driver") are outdated.
  • A Connection is an expensive, limited resource (a network socket + a session on the database server). Always close it — use try-with-resources.

3.4 Statement vs PreparedStatement

To run SQL you need a statement object from the connection:

// Statement: you give it a complete SQL string
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery("SELECT * FROM students WHERE id = " + id);   // ❌ string gluing

// PreparedStatement: SQL with ? placeholders, values set separately
PreparedStatement ps = conn.prepareStatement("SELECT * FROM students WHERE id = ?");
ps.setInt(1, id);                     // fill the 1st ? (counting starts at 1!)
ResultSet rs2 = ps.executeQuery();    // ✅

3.5 SQL injection — the most famous security bug

Imagine a login/search feature that builds SQL by gluing in what the user typed:

String sql = "SELECT id, name FROM students WHERE email = '" + emailFromUser + "'";

A normal user types asha@college.edu → fine. A hacker types: ' OR '1'='1. The SQL becomes:

SELECT id, name FROM students WHERE email = '' OR '1'='1'

'1'='1' is always true, so the database returns every student. With other inputs an attacker could log in without a password, read other tables, or even run '; DROP TABLE students; --. SQL injection is consistently on the OWASP Top 10 list of web security risks, and it has caused real data breaches of millions of records.

With a PreparedStatement, the SQL text is fixed (WHERE email = ?) and the value travels separately. The database looks for an email that is literally ' OR '1'='1 and finds nothing:

SQL: WHERE email = ?+ value: "' OR '1'='1"→ DB treats value as plain text → 0 rows
🚫 Golden rule Never put user input into SQL with +. Always use ? placeholders. (Table and column names can't be placeholders — if they must be dynamic, check them against a fixed allow-list.)

3.6 Reading results with ResultSet

A ResultSet is like a cursor pointing before the first row. Each call to next() moves it one row down and returns false when there are no more rows.

try (ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {                       // for each row
        int id      = rs.getInt("id");         // read columns by name...
        String name = rs.getString("name");
        int marks   = rs.getInt(4);            // ...or by position (1-based)
        System.out.println(id + " " + name + " " + marks);
    }
}
SQL typeJava getterJava setter
INTgetIntsetInt
BIGINTgetLongsetLong
VARCHARgetStringsetString
DECIMAL (money!)getBigDecimalsetBigDecimal
BOOLEANgetBooleansetBoolean
DATE / TIMESTAMPgetObject(col, LocalDate.class) / LocalDateTime.classsetObject(i, localDate)
⚠️ NULL trap rs.getInt("marks") returns 0 when the column is NULL. Use rs.wasNull() right after, or rs.getObject("marks", Integer.class) which returns null.

Turning the current row into an object is called mapping. We put it in one method, mapRow(ResultSet). Spring calls this a RowMapper (Topic 37), and JPA does it automatically (Topic 38).

3.7 The DAO pattern

A DAO (Data Access Object) is one class that holds all SQL for one table. The rest of the application calls clean methods like dao.findById(5) and never sees SQL or JDBC.

JdbcDemoApp (business code)→ StudentDao: save / findById / findAll / updateMarks / deleteById→ JDBC → H2

Benefits: SQL is in one place, business code is easier to read and test, and you can later swap the implementation (JDBC → JPA) without touching the callers. In Spring this becomes the Repository layer (Topic 33).

3.8 Transactions: all or nothing

A transaction groups several SQL statements into one unit that either fully succeeds or has no effect at all. The classic example is a bank transfer:

BEGIN→ 1. Asha −300→ 2. Ben +300→ COMMIT ✅
BEGIN→ 1. Asha −300→ 💥 crash→ ROLLBACK ↩ (Asha gets her 300 back)

By default JDBC is in auto-commit mode: every single statement is its own transaction and is saved immediately. To group statements:

try (Connection conn = Database.getConnection()) {
    conn.setAutoCommit(false);          // 1. start a transaction
    try {
        withdraw(conn, fromId, amount);   // all statements use the SAME connection
        deposit(conn, toId, amount);
        conn.commit();                  // 2. save everything
    } catch (SQLException | RuntimeException e) {
        conn.rollback();                // 3. undo everything
    }
}

Transactions give the ACID guarantees (Topic 42 goes deeper):

LetterMeaningBank example
AtomicityAll or nothingNever "money left Asha but never reached Ben"
ConsistencyRules (constraints) always holdCHECK (balance >= 0) is never broken
IsolationParallel transactions don't see each other's half-done workOthers don't see the moment when money is "in the air"
DurabilityOnce committed, it survives crashesAfter "transfer successful", a power cut won't undo it
ℹ️ Spring preview In Spring you write @Transactional on a method and Spring does setAutoCommit(false), commit() and rollback() for you — using an AOP proxy (Topic 27) around your method. Same idea, zero boilerplate.

3.9 SQLException

Almost every JDBC method can throw SQLException — a checked exception. Useful information inside it:

  • getMessage() — human-readable text from the driver.
  • getSQLState() — a standard 5-character code. Codes starting with 23 mean "integrity constraint violation" (e.g. 23505 = duplicate unique value).
  • getErrorCode() — the vendor-specific code (different for MySQL, Oracle, H2).

Because it's checked and vendor-specific, every DAO method needs throws SQLException or try/catch. Spring translates these into a clean hierarchy of unchecked exceptions (DataIntegrityViolationException, DuplicateKeyException...) so your code doesn't have to care which database you use.

3.10 Connection pooling — the idea

Opening a database connection is slow (network handshake, login, session setup — often 10–100 ms). Our StudentDao opens a new one in every method. For a learning demo that's fine; for a web server handling 1,000 requests per second it would be a disaster.

A connection pool opens, say, 10 connections at startup and lends them out. When your code calls close(), the connection is not really closed — it's returned to the pool for the next request. Exactly like the thread pool in Topic 17, but for database connections.

Request needs DB→ Borrow from pool (instant)→ Run SQL→ close() = give back to pool

In Java, pools implement the javax.sql.DataSource interface. The most popular is HikariCP, and Spring Boot configures it automatically when you add a database dependency (Topic 37). A taste of how it looks without Spring:

HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:h2:mem:college");
config.setMaximumPoolSize(10);
DataSource dataSource = new HikariDataSource(config);

try (Connection conn = dataSource.getConnection()) {   // borrowed, not created
    ...
}                                                      // returned, not closed

Database.java

src/main/java/com/course/jdbcbasics/Database.javapublic static final String URL = "jdbc:h2:mem:college;DB_CLOSE_DELAY=-1";

public static Connection getConnection() throws SQLException {
    return DriverManager.getConnection(URL, USER, PASSWORD);
}

public static void createSchema() throws SQLException {
    String schemaSql = """
            DROP TABLE IF EXISTS students;
            CREATE TABLE students ( ... );
            CREATE TABLE accounts (
                ...
                CONSTRAINT balance_not_negative CHECK (balance >= 0)
            );
            INSERT INTO accounts (id, owner, balance) VALUES (1, 'Asha', 1000.00);
            ...
            """;
    try (Connection conn = getConnection();
         Statement stmt = conn.createStatement()) {
        stmt.execute(schemaSql);
    }
}

DB_CLOSE_DELAY=-1 matters: an in-memory H2 database normally disappears when its last connection closes. Because our DAO opens and closes a connection in every method, we ask H2 to keep the database alive until the JVM exits. The CHECK constraint makes the database itself refuse negative balances. Here a plain Statement is fine — the SQL contains no user input.

StudentDao.java — save() with generated keys

src/main/java/com/course/jdbcbasics/StudentDao.javapublic Student save(Student student) throws SQLException {
    String sql = "INSERT INTO students (name, email, marks) VALUES (?, ?, ?)";

    try (Connection conn = Database.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {

        ps.setString(1, student.name());
        ps.setString(2, student.email());
        ps.setInt(3, student.marks());
        ps.executeUpdate();

        try (ResultSet keys = ps.getGeneratedKeys()) {
            keys.next();
            int newId = keys.getInt(1);
            return new Student(newId, student.name(), student.email(), student.marks());
        }
    }
}
  • Three ? placeholders, filled with setString/setInt by 1-based position.
  • RETURN_GENERATED_KEYS asks the database for the new AUTO_INCREMENT id, so we can return a Student that has its id. (JPA's save() does the same — Topic 38.)
  • Records are immutable, so we return a new Student with the id.

StudentDao.java — findById() with Optional

src/main/java/com/course/jdbcbasics/StudentDao.javapublic Optional<Student> findById(int id) throws SQLException {
    String sql = "SELECT id, name, email, marks FROM students WHERE id = ?";
    try (Connection conn = Database.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {
        ps.setInt(1, id);
        try (ResultSet rs = ps.executeQuery()) {
            if (rs.next()) {
                return Optional.of(mapRow(rs));
            }
            return Optional.empty();
        }
    }
}

private Student mapRow(ResultSet rs) throws SQLException {
    return new Student(rs.getInt("id"), rs.getString("name"),
                       rs.getString("email"), rs.getInt("marks"));
}

Returning Optional forces the caller to think about "not found" — the demo prints not found for id 99. findAll() uses while (rs.next()) instead of if. updateMarks and deleteById return executeUpdate() == 1, i.e. "was a row actually changed?".

BankTransferService.java

src/main/java/com/course/jdbcbasics/BankTransferService.javatry (Connection conn = Database.getConnection()) {
    conn.setAutoCommit(false);                       // BEGIN
    try (PreparedStatement withdraw = conn.prepareStatement(withdrawSql);
         PreparedStatement deposit  = conn.prepareStatement(depositSql)) {

        withdraw.setBigDecimal(1, amount); withdraw.setInt(2, fromId);
        withdraw.executeUpdate();                    // step 1

        if (simulateCrash) {
            throw new IllegalStateException("Server crashed between the two updates!");
        }

        deposit.setBigDecimal(1, amount); deposit.setInt(2, toId);
        deposit.executeUpdate();                     // step 2

        conn.commit();                               // COMMIT
    } catch (SQLException | RuntimeException e) {
        conn.rollback();                             // ROLLBACK
    } finally {
        conn.setAutoCommit(true);
    }
}

Three scenarios run: a normal transfer (commit), a crash between the two steps (rollback — balances unchanged), and a transfer bigger than the balance (the CHECK constraint makes step 1 fail → rollback). Notice we use BigDecimal for money — never double (0.1 + 0.2 ≠ 0.3 in floating point!).

6. Common mistakes

🚫 Mistake: building SQL with string concatenation Opens the door to SQL injection.
Fix: PreparedStatement with ? placeholders — always.
⚠️ Mistake: not closing Connection / Statement / ResultSet Leaked connections eventually exhaust the database ("Too many connections") or the pool ("Connection is not available, request timed out").
Fix: try-with-resources for every JDBC object.
⚠️ Mistake: parameter index starting at 0 ps.setString(0, ...) throws "Invalid value 0 for parameter parameterIndex".
Fix: JDBC indexes start at 1 — for parameters and for columns.
⚠️ Mistake: reading the ResultSet without calling next() The cursor starts before the first row; rs.getString(...) immediately fails ("No data is available").
Fix: if (rs.next()) or while (rs.next()).
⚠️ Mistake: executeQuery() for INSERT/UPDATE
Fix: executeQuery for SELECT, executeUpdate for data changes.
⚠️ Mistake: using different connections inside one transaction A transaction belongs to one connection. If step 1 and step 2 each call Database.getConnection(), they are separate transactions and rollback won't undo step 1.
Fix: pass the same Connection to every step (Spring does this for you by binding the connection to the current thread).
⚠️ Mistake: "No suitable driver found for jdbc:..." The driver JAR isn't on the classpath, or the URL is misspelled.
Fix: check the dependency in pom.xml and the URL prefix (jdbc:h2:, jdbc:mysql:).
⚠️ Mistake: H2 in-memory "Table not found" in the second method Without DB_CLOSE_DELAY=-1, the in-memory DB is deleted when the last connection closes.
Fix: add ;DB_CLOSE_DELAY=-1 to the URL (or keep one connection open).
⚠️ Mistake: using double for money
Fix: DECIMAL column + BigDecimal in Java.

7. Best practices

  • PreparedStatement for everything that contains a value.
  • try-with-resources for Connection, PreparedStatement, ResultSet.
  • Keep SQL in DAO/repository classes — one per table/aggregate. Business code calls methods, not SQL.
  • Select only the columns you need (SELECT id, name rather than SELECT *) — clearer and safer when the table changes.
  • Use a connection pool (DataSource, HikariCP) in any real application. Spring Boot gives you one automatically.
  • Don't hard-code credentials; read URL/user/password from configuration or environment variables (Topic 29).
  • Let the database protect data with constraints (NOT NULL, UNIQUE, CHECK, foreign keys) — your Java checks are a second line, not the only one.
  • Keep transactions short and group only the statements that truly belong together.
  • Use BigDecimal for money and java.time types for dates (setObject/getObject).
  • In real projects, use Spring's tools (JdbcTemplate / JPA) — raw JDBC is for learning, special cases, and understanding.

8. Key takeaways

  • Relational databases store data in tables; SQL's CRUD commands are INSERT, SELECT, UPDATE, DELETE.
  • JDBC = standard java.sql interfaces + a database-specific driver JAR.
  • DriverManager.getConnection(url, user, pw) → Connection → PreparedStatement → executeQuery/executeUpdate → ResultSet.
  • Never concatenate user input into SQL — PreparedStatement with ? prevents SQL injection.
  • JDBC indexes start at 1; call rs.next() before reading a row.
  • A DAO keeps all SQL for one table in one class (later: Spring repositories).
  • Transactions: setAutoCommit(false) → commit() or rollback() on the same connection. Spring: @Transactional.
  • Real apps use a connection pool (HikariCP); Spring Boot configures it for you.
  • Raw JDBC is verbose — that pain is why JdbcTemplate and JPA exist.

10. Interview questions

Q1. What is JDBC and what is a JDBC driver?

JDBC is the standard Java API (java.sql, javax.sql) for connecting to relational databases and executing SQL. It is mostly interfaces. A JDBC driver is a vendor-supplied library that implements those interfaces for a particular database (MySQL, PostgreSQL, H2...), translating JDBC calls into that database's network protocol.

Q2. What is the difference between Statement and PreparedStatement?

A Statement executes a complete SQL string; if user input is concatenated into it, it is vulnerable to SQL injection. A PreparedStatement uses a precompiled SQL template with ? placeholders and binds values separately with typed setters. It prevents SQL injection, handles quoting/types, and can be reused efficiently. (CallableStatement is for stored procedures.)

Q3. What is SQL injection and how do you prevent it?

An attack where user input is interpreted as part of the SQL command, e.g. ' OR '1'='1 turning a filter into "always true", or appending destructive commands. Prevent it with parameterized queries (PreparedStatement / ORM parameters), never concatenating input, validating input, allow-listing dynamic identifiers, and least-privilege database accounts.

Q4. executeQuery vs executeUpdate vs execute?

executeQuery runs a SELECT and returns a ResultSet. executeUpdate runs INSERT/UPDATE/DELETE/DDL and returns the number of affected rows. execute runs any SQL and returns true if the result is a ResultSet (then use getResultSet()), otherwise use getUpdateCount().

Q5. How do you manage transactions in JDBC?

Disable auto-commit with conn.setAutoCommit(false), execute all statements on the same connection, call conn.commit() if all succeed, and conn.rollback() in the catch block if anything fails. Optionally use savepoints (conn.setSavepoint()) and set isolation levels with setTransactionIsolation. Restore auto-commit afterwards, especially with pooled connections.

Q6. What is connection pooling and why is it important?

Creating a physical DB connection is expensive. A pool (e.g. HikariCP) keeps a set of open connections and lends them to callers; close() returns the connection to the pool. This reduces latency, limits the number of concurrent DB connections, and improves throughput. Applications obtain connections from a DataSource rather than DriverManager. Spring Boot auto-configures HikariCP.

Q7. What is a DAO?

A Data Access Object encapsulates all persistence logic for an entity/table behind a simple interface (save, findById, findAll, delete...). It separates business logic from data access, centralizes SQL, and allows changing the persistence technology. In Spring it corresponds to a @Repository.

Q8. Why do we prefer Spring JdbcTemplate or JPA over plain JDBC?

Plain JDBC requires repetitive boilerplate (opening/closing resources, iterating ResultSets, mapping rows, handling checked SQLExceptions, manual transactions). JdbcTemplate removes resource handling and translates exceptions into Spring's unchecked DataAccessException hierarchy; JPA/Spring Data additionally maps objects to tables automatically and generates queries. Both integrate with declarative @Transactional.

Q9. What does ACID mean?

Atomicity (all or nothing), Consistency (constraints/rules always hold), Isolation (concurrent transactions don't see each other's uncommitted changes, depending on the isolation level), Durability (committed data survives crashes).
