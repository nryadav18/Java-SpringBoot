1. Why this matters

In topic 19 you wrote raw JDBC: open a connection, write SQL as a String, set parameters one by one, loop over a ResultSet, copy each column into a Java object, close everything. In topic 37, JdbcTemplate removed the connection and closing work — but you still wrote every SQL statement and every RowMapper by hand.

Now imagine a real shop with 40 tables: products, customers, orders, payments, reviews... Writing INSERT, UPDATE, SELECT and a mapper for each of them is a lot of boring, repetitive, error-prone code.

Spring Data JPA removes almost all of it. You describe your Java class once with a few annotations, declare one small interface, and you can immediately save, find, update and delete objects. The SQL is generated for you.

ℹ️ Where you will see this at work Spring Data JPA is the most common way Spring Boot applications talk to relational databases (MySQL, PostgreSQL, Oracle, SQL Server). In almost every Spring Boot job interview you will be asked about entities, repositories, ddl-auto, lazy loading and transactions. Topics 38–43 are the "database block" of this course — this lesson is the foundation for all of them.

2. Real-life analogy

🌍 Think of a professional translator You speak English (Java objects). The database speaks a different language (tables, rows and SQL).
With raw JDBC you had to learn the database language and speak it yourself, word by word.
With JPA you hire a translator (Hibernate). You simply say "please keep this Product for me", and the translator says INSERT INTO products ... to the database. When you ask "give me product 5", the translator sends a SELECT, reads the answer and hands you back a ready-made Product object.
JPA is the rule book every translator must follow. Hibernate is the actual translator you hired. Spring Data JPA is a friendly receptionist in front of the translator: you just fill in a simple form (repository.save(product)) and she handles the conversation for you.

3. Concepts step by step

3.1 The problem: objects and tables are different worlds

In Java we think in objects: a Product has fields, methods, references to other objects. In a relational database we think in tables: rows and columns, linked by ids. These two worlds do not match perfectly. People call this the object–relational mismatch.

ORM = Object Relational Mapping. An ORM tool is a library that translates automatically between the two worlds:

Java worldDatabase world
Class ProductTable products
Field priceColumn price
One Product objectOne row
Field annotated @IdPrimary key column
new Product(...) + save()INSERT INTO products ...
findById(5)SELECT ... WHERE id = 5
product.setPrice(...) inside a transactionUPDATE products SET price = ...
deleteById(5)DELETE FROM products WHERE id = 5

3.2 JPA vs Hibernate vs Spring Data JPA — three layers

Beginners often mix these three names. They are three layers stacked on top of each other:

NameWhat it isAnalogyPackage / artifact
JPA (Jakarta Persistence API)A specification: a set of interfaces and annotations (@Entity, @Id, EntityManager). No real code inside.The rule bookjakarta.persistence.*
HibernateThe most popular implementation of JPA. It really generates and runs the SQL. (Others: EclipseLink.)The translatororg.hibernate.*
Spring Data JPAA Spring project on top of JPA that creates repository classes for you from interfaces.The receptionistorg.springframework.data.jpa.*
ℹ️ javax vs jakarta Old tutorials use javax.persistence.Entity. Since Spring Boot 3 the package is jakarta.persistence.Entity. If you copy an old example and it does not compile, change javax to jakarta.

One starter brings all three layers (plus the HikariCP connection pool from topic 37):

3.3 Your first entity

An entity is a normal Java class whose objects are stored in a table. You turn a class into an entity with annotations:

entity/Product.java (short version)@Entity                          // 1. "JPA, please manage this class"
@Table(name = "products")        // 2. optional: the table name
public class Product {

    @Id                                                  // 3. primary key
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // 4. database generates the id
    private Long id;

    @Column(nullable = false, length = 100)              // 5. column rules
    private String name;

    private int stock;           // no annotation = still a column called "stock"

    protected Product() { }      // 6. JPA needs a no-argument constructor
    // ... other constructor, getters, setters
}
AnnotationMeaningRequired?
@EntityMarks the class as a JPA entity. Hibernate will map it to a table.Yes
@Table(name="products")Chooses the table name. Without it the table is named after the class (product).No
@IdThe primary key field. Every entity needs exactly one.Yes
@GeneratedValueLet the database/JPA create the id value instead of you.No (but usual)
@ColumnColumn details: name, nullable, length, unique, precision/scale, updatable.No
@Transient"Do NOT store this field" (e.g. a calculated value).No

Rules an entity must follow:

  • A no-argument constructor (public or protected). Hibernate first creates an empty object, then fills its fields from the row.
  • Not final, and not a record. Hibernate needs to change fields and sometimes create a subclass (a proxy).
  • Use wrapper type Long for the id, not long. null means "not saved yet"; a primitive would be 0, which is confusing.

3.4 @GeneratedValue strategies

Who creates the next id (1, 2, 3...)? You choose a strategy:

StrategyHow it worksGood for
IDENTITYThe database column is auto-increment. The id is known only after the INSERT.MySQL, H2, SQL Server. Simple and most common for beginners. Used in this course.
SEQUENCEUses a database sequence object (a number generator). Hibernate can fetch ids in blocks, which allows batch inserts.PostgreSQL, Oracle. Best performance.
TABLEUses a special table to store the "next id". Slow (needs locking).Almost never — legacy only.
AUTO (default)Hibernate picks one for the database (usually SEQUENCE).Quick demos — but be explicit in real code.
@GeneratedValue(strategy = GenerationType.UUID)A random UUID like 3f2a... (JPA 3.1+). Field type UUID.Ids that must be unguessable or created on many servers.

3.5 Automatic audit fields: @CreationTimestamp / @UpdateTimestamp

Almost every business table has "when was this row created?" and "when was it last changed?". Hibernate can fill these for you:

@CreationTimestamp                       // set once, at INSERT
@Column(name = "created_at", updatable = false)
private LocalDateTime createdAt;

@UpdateTimestamp                         // refreshed at every UPDATE
@Column(name = "updated_at")
private LocalDateTime updatedAt;

These come from org.hibernate.annotations (Hibernate-specific, not plain JPA). updatable = false is a safety belt: even if someone calls a setter, the column is never changed by an UPDATE.

ℹ️ Alternative: Spring Data auditing Spring Data also offers @CreatedDate, @LastModifiedDate, @CreatedBy, @LastModifiedBy together with @EnableJpaAuditing and @EntityListeners(AuditingEntityListener.class). It is useful when you also want to record who made the change (with Spring Security, topic 48). For timestamps only, the Hibernate annotations are the simplest.

3.6 The repository: an interface with no class

repository/ProductRepository.javapublic interface ProductRepository extends JpaRepository<Product, Long> {
}

That's it. JpaRepository<Product, Long> says: "a repository for Product entities whose @Id is a Long". You remember Repository<T, ID> from topic 12 (Generics) — this is the real thing.

At startup Spring Data sees the interface and creates a proxy object (topic 27) that implements it. When you call save(), the proxy calls a ready-made class called SimpleJpaRepository, which uses JPA's EntityManager, which uses Hibernate, which sends SQL.

ProductService→ Repository proxy→ SimpleJpaRepository→ EntityManager (Hibernate)→ JDBC → H2

The interface hierarchy (each level adds methods):

Repository→ CrudRepository→ ListCrudRepository→ JpaRepository

(PagingAndSortingRepository is also mixed into JpaRepository — see topic 41.)

You can also add your own methods, and Spring builds the query from the method name:

These are called derived queries. Topic 39 is entirely about them, plus JPQL and native SQL.

3.8 Entity lifecycle states

This is the most important "under the hood" idea in JPA. Hibernate keeps a little notebook of the entities it is currently watching. This notebook is called the persistence context (one per transaction, roughly). An entity object is always in one of four states:

StateWhat it meansHow you get there
Transient (new)Just a Java object. JPA has never seen it. No row in the database, usually no id.new Product(...)
Managed (persistent)Hibernate is watching it. Any change you make is written to the database automatically at the end of the transaction.save() / persist(), or loading it with findById() inside a transaction
DetachedHas an id and a row exists, but Hibernate stopped watching it. Changes are NOT saved.Transaction ended, or detach() / clear()
RemovedScheduled for deletion. The DELETE runs at flush/commit.delete() / remove()

Dirty checking — updates without save()

Because a managed entity is watched, this code really updates the database even though there is no save() call:

@Transactional
public void increasePrice(Long id) {
    Product p = repository.findById(id).orElseThrow();  // p is MANAGED
    p.setPrice(p.getPrice().multiply(new BigDecimal("1.10")));
    // no save() needed: at commit Hibernate compares p with its original snapshot,
    // sees the price is "dirty" (changed) and sends:  UPDATE products SET price=? ... WHERE id=?
}

This is called dirty checking. Calling save() anyway is harmless and many teams do it for readability. But you must understand why it works without it — interviewers love this question.

💡 Flush vs commit Flush = "send the pending SQL to the database now" (still inside the transaction, can still be rolled back). Commit = "make it permanent". Hibernate flushes automatically before commit and before queries that need fresh data. You rarely call flush yourself.

3.9 spring.jpa.hibernate.ddl-auto — who creates the tables?

DDL = Data Definition Language: CREATE TABLE, ALTER TABLE, DROP TABLE. Hibernate can generate DDL from your entities. The ddl-auto property decides what it does at startup:

ValueWhat happens at startupUse it when
noneNothing. Hibernate does not touch the schema.Production (tables managed by Flyway — topic 43).
validateChecks that tables/columns match the entities; fails startup if not. Changes nothing.Production, as a safety check.
updateAdds missing tables/columns. Never drops anything. Can't rename or fix types.Quick prototypes only. Dangerous in production.
createDrops all tables and creates them fresh. All data lost.Tests, demos.
create-dropLike create, and also drops the tables when the app stops.In-memory DB, tests. Default for embedded H2 (we set it explicitly anyway).
🛑 Never in production create or create-drop against a real database deletes all customer data on restart. Even update is risky: it may silently do the wrong thing. In production use validate or none plus a migration tool (Flyway, topic 43).

3.10 Seeing the SQL: show-sql and format_sql

application.propertiesspring.jpa.show-sql=true

Now every statement appears in the console, nicely indented:

Hibernate:
    insert
    into
        products
        (created_at, description, name, price, sku, stock_quantity, updated_at, id)

The ? are parameters (Hibernate uses PreparedStatement — safe from SQL injection, topic 19). 3.12 Why DTOs and not the entity in the API?

You learned this in topic 33, and with JPA it becomes even more important:

  • Security: if the controller accepts Product as @RequestBody, a client could send "id": 1 or "createdAt" and overwrite data ("mass assignment").
  • Stability: renaming a column should not break your mobile app's JSON.
  • Lazy loading problems: entities with relationships can explode when turned into JSON (topic 40).
JSON→ ProductRequest (record)→ Service builds Product entity→ save()→ ProductResponse (record)→ JSON

3.13 spring.jpa.open-in-view — one warning you will see

Spring Boot logs a warning at startup if you don't set this property. "Open Session In View" keeps the database session open until the HTTP response is fully written. It sounds convenient, but it hides lazy-loading mistakes and keeps database connections busy for longer. We switch it off (false) and load everything we need inside the service. You'll understand the full reason in topic 40.

4.1 The entity — Product.java

entity/Product.java@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;

    @Column(length = 500)
    private String description;

    @Column(nullable = false, unique = true, length = 30)
    private String sku;

    @Column(nullable = false, precision = 10, scale = 2)  // DECIMAL(10,2)
    private BigDecimal price;

    @Column(name = "stock_quantity", nullable = false)
    private int stock;

    @CreationTimestamp
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @UpdateTimestamp
    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    protected Product() { }   // for JPA only

    public Product(String name, String description, String sku, BigDecimal price, int stock) { ... }
    // getters + setters (no setId / setCreatedAt on purpose)
}
  • BigDecimal for money: double has rounding errors (0.1 + 0.2 = 0.30000000000000004). precision = 10, scale = 2 means up to 10 digits, 2 after the decimal point.
  • name = "stock_quantity": the Java field and the column can have different names.
  • Even without name, Spring Boot converts camelCase to snake_case: a field createdAt becomes column created_at.
  • The generated table (watch your console at startup):
Hibernate:
    create table products (
        price numeric(10,2) not null,
        stock_quantity integer not null,
        created_at timestamp(6) not null,
        id bigint generated by default as identity,
        updated_at timestamp(6),
        sku varchar(30) not null unique,
        name varchar(100) not null,
        description varchar(500),
        primary key (id)
    )

4.3 The service — where JPA is used

service/ProductService.java@Service
@Transactional(readOnly = true)
public class ProductService {

    private final ProductRepository repository;

    public ProductService(ProductRepository repository) { this.repository = repository; }

    public List<ProductResponse> findAll() {
        return repository.findAll().stream().map(ProductResponse::from).toList();
    }

    @Transactional
    public ProductResponse create(ProductRequest request) {
        if (repository.existsBySku(request.sku())) {
            throw new DuplicateResourceException("A product with SKU '" + request.sku() + "' already exists");
        }
        Product product = new Product(request.name(), request.description(), request.sku(),
                request.price(), request.stock());   // TRANSIENT
        Product saved = repository.save(product);    // MANAGED, id filled in
        return ProductResponse.from(saved);
    }

    @Transactional
    public ProductResponse update(Long id, ProductRequest request) {
        Product product = getProductOrThrow(id);     // MANAGED
        // ... duplicate SKU check ...
        product.setName(request.name());
        product.setPrice(request.price());
        // ... other setters ...
        return ProductResponse.from(repository.saveAndFlush(product));
    }

    private Product getProductOrThrow(Long id) {
        return repository.findById(id)
                .orElseThrow(() -> new ResourceNotFoundException("Product", id));
    }
}
  • @Transactional(readOnly = true) on the class: all methods run in a read-only transaction by default. Write methods override it with a plain @Transactional. Transactions are explained fully in topic 42; for now: "everything inside the method succeeds together or fails together".
  • In update() the setters alone would be enough (dirty checking). We call saveAndFlush so the UPDATE runs immediately and updatedAt is already filled in the response.
  • findById(...).orElseThrow(...) is the standard pattern: missing id → custom exception → 404.

4.4 The controller

controller/ProductController.java@PostMapping
public ResponseEntity<ProductResponse> create(@Valid @RequestBody ProductRequest request) {
    ProductResponse created = service.create(request);
    URI location = ServletUriComponentsBuilder.fromCurrentRequest()
            .path("/{id}").buildAndExpand(created.id()).toUri();
    return ResponseEntity.created(location).body(created);   // 201 + Location header
}

@DeleteMapping("/{id}")
public ResponseEntity<Void> delete(@PathVariable Long id) {
    service.delete(id);
    return ResponseEntity.noContent().build();               // 204
}

Nothing JPA-specific here — and that is the point of layers. The controller does not know whether the data lives in a List, JDBC or JPA.

4.6 The tests — ProductRepositoryTest.java

src/test/java/com/course/jpabasics/ProductRepositoryTest.java@DataJpaTest
class ProductRepositoryTest {

    @Autowired ProductRepository repository;
    @Autowired EntityManager entityManager;

    @Test
    void entityLifecycleStates() {
        Product product = newMouse();                       // TRANSIENT
        assertThat(entityManager.contains(product)).isFalse();

        entityManager.persist(product);                     // MANAGED
        assertThat(entityManager.contains(product)).isTrue();

        entityManager.flush();
        entityManager.detach(product);                      // DETACHED
        assertThat(entityManager.contains(product)).isFalse();

        Product managedCopy = entityManager.merge(product); // a MANAGED copy
        entityManager.remove(managedCopy);                  // REMOVED
        entityManager.flush();
        assertThat(repository.findById(product.getId())).isEmpty();
    }
}

@DataJpaTest starts only the JPA part of Spring with an in-memory database, and rolls back each test's transaction at the end. entityManager.contains(x) answers "is x managed right now?" — a perfect way to see the lifecycle states. The dirtyCheckingUpdatesAutomatically test proves that a setter alone produces an UPDATE.

6. Common mistakes

⚠️ Mistake: "No default constructor for entity" You added a constructor with parameters and forgot the no-argument one. Hibernate cannot create the object.
Fix: add protected Product() { }.
⚠️ Mistake: "Not a managed type: class ...Product" The entity is in a package that is not under the main application class's package, or you used javax.persistence.Entity instead of jakarta.persistence.Entity.
Fix: put entities under com.course.jpabasics (or a sub-package) and import from jakarta.persistence.
⚠️ Mistake: Ignoring the return value of save() repository.save(product); return product.getId(); — for a new entity this usually works, but when save does a merge it returns a different object, and changes on the old one are lost.
Fix: always use the result: Product saved = repository.save(product);
⚠️ Mistake: Calling findById(id).get() If the id doesn't exist, .get() throws NoSuchElementException → an ugly 500 error.
Fix: findById(id).orElseThrow(() -> new ResourceNotFoundException(...)).
⚠️ Mistake: H2 console says "Database not found" The JDBC URL in the login screen defaults to jdbc:h2:~/test, a different database.
Fix: type exactly the URL from application.properties: jdbc:h2:mem:shopdb.
⚠️ Mistake: Table or column named with a reserved word An entity called Order or User, or a field called value/order, creates SQL like create table order — a syntax error, because ORDER is an SQL keyword.
Fix: @Table(name = "orders"), @Table(name = "app_users"), @Column(name = "sort_order").
🛑 Mistake: ddl-auto=create on a real database One restart and all the data is gone.
Fix: validate or none in production, Flyway for schema changes (topic 43).
⚠️ Mistake: Returning entities from controllers Works in this tiny example, but leaks internal fields, allows mass assignment and breaks with relationships (infinite JSON, lazy errors — topic 40).
Fix: request/response DTOs, as in this project.

7. Best practices

  • Entities are internal. Use DTOs (records) at the API boundary.
  • Repositories only in services. Controllers call services, services call repositories.
  • Put @Transactional on service methods, with readOnly = true for reads.
  • Use BigDecimal for money and java.time types for dates.
  • Be explicit with column rules (nullable, length, unique) — and validate in DTOs too. The database is the last line of defence.
  • Use Long ids with IDENTITY (MySQL) or SEQUENCE (PostgreSQL). Don't expose sequential ids publicly if they reveal business info — consider UUIDs.
  • Watch the SQL during development (show-sql or logging.level.org.hibernate.SQL=DEBUG). If you don't know what SQL your code produces, you will have performance surprises.
  • Turn off open-in-view and fetch what you need in the service.
  • Production: ddl-auto=validate + Flyway migrations.
  • Test repositories with @DataJpaTest — fast and isolated.

8. Key takeaways

  • ORM maps classes ↔ tables, fields ↔ columns, objects ↔ rows, and writes the SQL for you.
  • JPA = the standard (rule book), Hibernate = the implementation, Spring Data JPA = generated repositories on top.
  • An entity needs @Entity, an @Id and a no-arg constructor. @GeneratedValue(IDENTITY) lets the DB create ids.
  • interface XRepository extends JpaRepository<X, Long> gives you save, findById, findAll, existsById, count, deleteById... for free.
  • Entities are transient, managed, detached or removed. Managed entities are saved automatically at commit (dirty checking).
  • ddl-auto: create-drop for learning/tests, validate/none in production.
  • show-sql + format_sql and the H2 console let you see what happens.
  • @CreationTimestamp / @UpdateTimestamp fill audit fields automatically.

10. Interview questions

Q1. What is the difference between JPA, Hibernate and Spring Data JPA?

JPA (Jakarta Persistence) is a specification — annotations and interfaces like @Entity and EntityManager, with no implementation. Hibernate is an implementation (ORM framework) of JPA that actually generates and executes SQL. Spring Data JPA is a Spring abstraction on top of JPA that generates repository implementations from interfaces (CRUD methods, derived queries, paging), reducing boilerplate.

Q2. What is ORM and what problem does it solve?

Object-Relational Mapping translates between objects in code and rows in relational tables. It removes repetitive JDBC code (SQL strings, mapping ResultSets to objects), handles the object/relational mismatch (types, identity, relationships) and adds features like caching, lazy loading and dirty checking.

Q3. What are the entity lifecycle states?

Transient (new object, unknown to JPA), Managed (in the persistence context; changes are synchronized with the DB at flush/commit), Detached (has an identity but is no longer tracked, e.g. after the transaction ends), Removed (scheduled for deletion at flush/commit). persist, merge, detach and remove move entities between the states.

Q4. What is dirty checking?

Hibernate keeps a snapshot of each managed entity when it is loaded. At flush time it compares the current field values with the snapshot and automatically issues UPDATE statements for changed ("dirty") entities. That is why modifying a managed entity inside a transaction is saved without calling save().

Q5. What does save() do internally?

SimpleJpaRepository.save() checks whether the entity is new (by default: id is null, or version is null). If new, it calls entityManager.persist() and returns the same object; otherwise it calls entityManager.merge(), which returns a (possibly different) managed instance. Therefore you should always use the returned value.

Q6. Explain the ddl-auto options. Which do you use in production?

none (do nothing), validate (check schema matches entities), update (add missing tables/columns), create (drop and recreate), create-drop (create, then drop on shutdown; default for embedded DBs). In production: validate or none, with schema managed by a migration tool such as Flyway or Liquibase.

Q7. What are the @GeneratedValue strategies?

IDENTITY (auto-increment column; id known after insert; disables JDBC batch inserts in Hibernate), SEQUENCE (database sequence; supports pre-allocation and batching; preferred on PostgreSQL/Oracle), TABLE (separate key table; slow), AUTO (provider chooses), and UUID (JPA 3.1).

Q8. Why does an entity need a no-argument constructor and why can't it be a record?

JPA providers instantiate entities via reflection using the no-arg constructor, then populate fields. They may also create runtime subclasses (proxies) for lazy loading. Records are final and immutable with no no-arg constructor, so they cannot be entities — but they are great as DTOs and projections.

Q9. What is the difference between findById and getReferenceById?

findById hits the database immediately (or the persistence context) and returns an Optional. getReferenceById returns a lazy proxy without querying; the SELECT happens only when you access a non-id field, and it throws EntityNotFoundException then if the row doesn't exist. It is useful for setting foreign keys without loading the related entity.

Q10. Why should you not expose JPA entities directly in REST APIs?

It couples the API to the database schema, risks mass-assignment (clients setting ids or internal fields), can leak sensitive columns, and with relationships leads to lazy-loading exceptions and infinite JSON recursion. DTOs give a stable, explicit contract.
