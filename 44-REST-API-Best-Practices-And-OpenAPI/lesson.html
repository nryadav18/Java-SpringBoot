1. Why this matters

An API is a product for other developers: the mobile team, the frontend team, a partner company, or you in six months. If your URLs are random, your status codes are always 200, and every error looks different, those developers lose hours guessing. They write bugs. They send you angry messages.

A well-designed API is predictable. Once you have used one endpoint, you can guess how the others work. And a well-documented API answers questions before they are asked.

In companies you will hear: "Is it in Swagger?" That means: "Is the endpoint documented in the OpenAPI page?" Frontend developers open that page every day to see what to send and what comes back. After this lesson your APIs will have that page — generated automatically from your code.

ℹ️ Nothing magical Most of this lesson is rules and habits, not new Spring features. You already know @GetMapping, ResponseEntity, Pageable and @RestControllerAdvice. Now we use them in a professional, consistent way.

2. Real-life analogy

🍽️ Think of a good restaurant menu
  • The menu sections are clear nouns: Starters, Mains, Desserts → like /tasks, /users, /orders.
  • You order, change or cancel with standard actions — you don't need a special word for each dish → like GET, POST, PUT, PATCH, DELETE.
  • The waiter answers with clear standard replies: "Coming right up" (201), "Sorry, we're out of that" (404), "We can't make it like that" (400).
  • When the restaurant changes its menu, regulars can still ask for the old menu for a while → API versioning.
  • The menu with photos, ingredients and prices is the documentation → OpenAPI / Swagger UI. Nobody has to walk into the kitchen to ask.
  • If you say "I'd like order #42" twice because the waiter didn't hear, you don't get two meals → idempotency.

3. Concepts step by step

3.1 Resource naming rules

In REST, a URL names a resource (a thing), and the HTTP method says what to do with it. So URLs contain nouns, never verbs.

Rule✅ Good❌ Bad
Use nouns, not verbsGET /tasksGET /getAllTasks
Use plural nouns for collections/tasks, /tasks/42/task, /taskList
Use the HTTP method for the actionDELETE /tasks/42POST /tasks/42/delete
Lower-case, words with hyphens/order-items/OrderItems, /order_items
Nest only for real ownership, max ~2 levels/projects/7/tasks/companies/1/projects/7/tasks/42/comments/3/likes
Filters go in the query string/tasks?status=DONE/tasks/done, /doneTasks
No file extensions/tasks/42 + Accept header/tasks/42.json
No trailing slash/tasks/tasks/
Prefix and version/api/v1/tasks/myapp/rest/services/tasks
💡 What about actions that are not CRUD? Sometimes an action really is a verb, like "send this invoice by email". Options: model it as a sub-resource (POST /invoices/42/emails — "create an email for invoice 42"), or a state change (PATCH /invoices/42 {"status":"SENT"}). A small number of action URLs like POST /orders/42/cancel is acceptable when it is clearer — just be consistent.

3.2 Methods: safe and idempotent

Two important words:

  • Safe = does not change anything on the server (just reading).
  • Idempotent = doing it once or 10 times leaves the server in the same state. Like pressing a lift button many times — the lift still comes once.
MethodMeaningSafe?Idempotent?Typical success code
GETRead✅✅200
POSTCreate (or start a process)❌❌201 + Location
PUTReplace the whole resource❌✅200 (or 204)
PATCHChange some fields❌Usually* 200
DELETERemove❌✅204

* PATCH {"status":"DONE"} is idempotent; PATCH {"increaseBy": 1} is not. Design patches as "set to value" whenever you can.

Why do we care? Networks fail. A mobile app sends a request, the connection drops, and the app does not know whether the server received it. For idempotent methods the app can simply retry. For POST, a retry could create a duplicate order or payment! The solution is an Idempotency-Key:

Client: POST + Idempotency-Key: abc→ Server: new key → create task 13, remember abc→13→ 201 Created
Client retries: same key abc→ Server: key known → return task 13 again→ 200 OK (no duplicate!)

Payment companies like Stripe use exactly this pattern. Our TaskService shows a simple version.

ℹ️ DELETE twice? The first DELETE returns 204, the second returns 404 in our API. That is still idempotent: idempotency is about the server state (task is gone either way), not about getting the same status code.

CodeNameUse it when...

💡 Easy memory trick 2xx = "it worked", 4xx = "you (client) made a mistake", 5xx = "we (server) made a mistake". Never return 200 with {"error": "..."} inside.

3.4 Consistent response format

Single resources: return the object itself ({"id":1,"title":"..."}). No need to wrap it in {"data": ...}.

Lists: always return a page object with the same shape everywhere:

{
  "content": [ { "id": 1, ... }, { "id": 2, ... } ],
  "page": 0,
  "size": 10,
  "totalElements": 12,
  "totalPages": 2,
  "first": true,
  "last": false
}

Why not return Spring's Page<T> directly? Its JSON is big, full of internal fields, and Spring Data itself logs a warning that the format is not guaranteed to be stable. Our own PageResponse<T> record is small, clear and under our control. (Alternative: @EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO) gives a stable PagedModel format.)

Other consistency rules:

  • JSON field names in camelCase everywhere (Jackson's default).
  • Dates in ISO-8601: "2030-01-31", "2030-01-31T10:15:30Z".
  • Enums as readable strings: "IN_PROGRESS", not numbers.
  • Money as a decimal number or string plus a currency — never floating-point maths.

3.5 One error format: ProblemDetail

In topic 35 you met ProblemDetail, Spring's implementation of the standard RFC 9457 (it replaced RFC 7807). Using the standard means clients can use one piece of code to show every error.

HTTP/1.1 404
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/task-not-found",   // a URI that identifies the error KIND
  "title": "Task not found",                                     // short, same for every error of this kind
  "status": 404,
  "detail": "Task with id 999 was not found",                    // this specific case
  "instance": "/api/v1/tasks/999",                               // which request
  "taskId": 999,                                                 // extra properties are allowed
  "timestamp": "2026-10-09T04:37:16Z"
}

Validation errors get an extra errors map so a form can show each message next to its field:

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Validation failed",
  "status": 400,
  "detail": "One or more fields are invalid",
  "errors": { "title": "must not be blank", "dueDate": "must be a date in the present or in the future" }
}

3.6 Filtering, sorting and pagination conventions

NeedConventionExample
Filter by a fieldquery parameter with the field name?status=TODO&priority=HIGH
Free-text searchsearch or q?search=demo
Rangemin/max or from/to prefixes?dueFrom=2030-01-01&dueTo=2030-01-31
Sortsort=field,direction, repeatable (Spring's default)?sort=priority,desc&sort=dueDate,asc
Pagepage (0-based in Spring) and size?page=1&size=20
Limit page sizea server-side maximumspring.data.web.pageable.max-page-size=100

Two safety rules: always cap the page size (otherwise ?size=1000000 can take down your database), and whitelist sort fields (an unknown field would otherwise cause a 500 error, and sorting by un-indexed columns can be slow).

ℹ️ Offset vs cursor pagination page/size (offset) is simple and fine for most apps. Very large or fast-changing lists (social feeds) use cursor pagination: ?after=eyJpZCI6MTIzfQ&limit=20. You'll see it in big public APIs.

3.7 API versioning strategies

Once clients use your API, you cannot break it. A breaking change is: renaming or removing a field, changing a type, making an optional field required, changing a URL or status code. Adding a new optional field is not breaking.

When you must break, you publish a new version and keep the old one alive for a while.

StrategyExampleProsCons
URI pathGET /api/v2/tasksVery visible, easy to test in a browser, easy routing/caching. Most common.URL changes between versions
Custom headerX-API-Version: 2Clean, stable URLsInvisible in a browser; easy to forget
Media type (content negotiation)Accept: application/vnd.course.task.v2+json"Purest" RESTComplex for clients and docs
Query parameter/tasks?version=2SimpleMixes versioning with filtering

Our project shows URI versioning (TaskController for v1, TaskV2Controller for v2) and header versioning (HeaderVersionedTaskController).

ℹ️ In newer Spring Spring Framework 7 / Spring Boot 4 add first-class API versioning (@GetMapping(version = "2")). In Spring Boot 3.5 we do it with paths or headers = "X-API-Version=2", as shown here.

3.8 HATEOAS (brief)

HATEOAS = "Hypermedia As The Engine Of Application State". Big name, simple idea: a response contains links telling the client what it can do next, like links on a web page.

{
  "id": 3,
  "title": "Fix login bug",
  "status": "TODO",
  "_links": {
    "self":     { "href": "http://localhost:8080/api/v1/tasks/3" },
    "complete": { "href": "http://localhost:8080/api/v1/tasks/3", "method": "PATCH" },
    "all":      { "href": "http://localhost:8080/api/v1/tasks" }
  }
}

Spring supports it with spring-boot-starter-hateoas (EntityModel, WebMvcLinkBuilder.linkTo(...)). In practice, most company APIs skip HATEOAS and rely on OpenAPI docs instead — but know the word for interviews.

3.9 OpenAPI and Swagger — what are they?

  • OpenAPI is a standard format (JSON or YAML) that describes an API: every URL, method, parameter, request body, response and error. Machines can read it.
  • Swagger UI is a web page that reads an OpenAPI file and shows it nicely, with a "Try it out" button to call the API from the browser.
  • springdoc-openapi is the library that generates the OpenAPI file from your Spring controllers at runtime — no hand-writing.
Your @RestControllers + DTOs→ springdoc scans them→ /v3/api-docs (OpenAPI JSON)→ /swagger-ui.html (web page)

One dependency is all you need:

pom.xml<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.8.9</version>   <!-- not managed by Spring Boot, so we write the version -->
</dependency>

Even with zero annotations, you already get a working Swagger page. The annotations below only make it better. The OpenAPI file can also generate client code (TypeScript, Kotlin, Java...) with tools like OpenAPI Generator — the frontend team will love you.

3.11 Global info and groups

An OpenAPI bean sets the "cover page" (title, version, contact, license, servers). GroupedOpenApi beans split a big API into several documents — for example one per version, or "public" vs "admin". Swagger UI shows a drop-down to switch between them, and each group has its own JSON at /v3/api-docs/<group>.

@Bean
public GroupedOpenApi v1Api() {
    return GroupedOpenApi.builder()
            .group("v1")                 // name in the drop-down and in /v3/api-docs/v1
            .pathsToMatch("/api/v1/**")  // which endpoints belong to this group
            .build();
}

4.2 A documented controller method

task/TaskController.java@RestController
@RequestMapping("/api/v1/tasks")
@Tag(name = "Tasks", description = "Create, read, update and delete tasks")
public class TaskController {

    @Operation(summary = "Get one task by id")
    @ApiResponses({
            @ApiResponse(responseCode = "200", description = "The task"),
            @ApiResponse(responseCode = "404", description = "No task with this id",
                    content = @Content(mediaType = "application/problem+json",
                            schema = @Schema(implementation = ProblemDetail.class)))
    })
    @GetMapping("/{id}")
    public TaskResponse getById(@Parameter(description = "Task id", example = "1") @PathVariable Long id) {
        return service.findById(id);
    }

Read it top to bottom: @Tag puts the endpoint in the "Tasks" section; @Operation gives it a title; @ApiResponses tells readers "you may get 200 or 404, and the 404 body looks like a ProblemDetail"; @Parameter explains id. Delete all of them and the endpoint still works — documentation annotations never change behaviour.

4.3 The list endpoint: filtering, sorting, paging

task/TaskController.java@GetMapping
public PageResponse<TaskResponse> list(
        @RequestParam(required = false) TaskStatus status,
        @RequestParam(required = false) TaskPriority priority,
        @RequestParam(required = false) String search,
        @ParameterObject @PageableDefault(size = 10, sort = "id", direction = Sort.Direction.ASC) Pageable pageable) {
    return service.search(status, priority, search, pageable);
}

Spring converts ?status=TODO to the enum automatically; a wrong value like ?status=SLEEPING becomes a 400 ProblemDetail. Pageable is built from page, size and sort (topic 41). The repository uses the "null means ignore this filter" trick:

task/TaskRepository.java@Query("""
        SELECT t FROM Task t
        WHERE (:status IS NULL OR t.status = :status)
          AND (:priority IS NULL OR t.priority = :priority)
          AND (:search IS NULL OR LOWER(t.title) LIKE LOWER(CONCAT('%', :search, '%')))
        """)
Page<Task> search(@Param("status") TaskStatus status,
                  @Param("priority") TaskPriority priority,
                  @Param("search") String search,
                  Pageable pageable);

And the service guards the sort fields:

task/TaskService.javaprivate static final Set<String> SORTABLE_FIELDS =
        new TreeSet<>(Set.of("id", "title", "status", "priority", "dueDate", "createdAt"));

for (Sort.Order order : pageable.getSort()) {
    if (!SORTABLE_FIELDS.contains(order.getProperty())) {
        throw new InvalidSortPropertyException(order.getProperty(), SORTABLE_FIELDS);   // → 400

4.4 POST with 201, Location and Idempotency-Key

task/TaskController.java@PostMapping
public ResponseEntity<TaskResponse> create(
        @RequestHeader(name = "Idempotency-Key", required = false) String idempotencyKey,
        @Valid @RequestBody TaskCreateRequest request) {

    TaskService.CreateResult result = service.create(request, idempotencyKey);

    URI location = ServletUriComponentsBuilder.fromCurrentRequest()   // http://localhost:8080/api/v1/tasks
            .path("/{id}")                                             //   + /{id}
            .buildAndExpand(result.task().id())                        //   → /api/v1/tasks/13
            .toUri();

    if (result.replayed()) {
        return ResponseEntity.ok().location(location).body(result.task());   // 200: already created before
    }
    return ResponseEntity.created(location).body(result.task());             // 201: brand new
}

6. Common mistakes

⚠️ Mistake: verbs in URLs /api/createTask, /api/tasks/delete/5.
Fix: nouns + HTTP methods: POST /api/v1/tasks, DELETE /api/v1/tasks/5.
⚠️ Mistake: always returning 200 even for errors, with {"success": false} inside.
Fix: use real status codes; clients, proxies and monitoring tools all rely on them.
⚠️ Mistake: POST returns 200 and no Location
Fix: ResponseEntity.created(location).body(dto).
⚠️ Mistake: returning unlimited lists GET /tasks returns 500,000 rows.
Fix: paginate every collection endpoint and set spring.data.web.pageable.max-page-size.
⚠️ Mistake: breaking clients silently renaming title to name in v1.

🛑 Mistake: leaking internals in errors Stack traces, SQL, class names in the response help attackers.

7. Best practices

  • Design first, then code. Agree on URLs, bodies and errors with the API consumers (some teams even write the OpenAPI YAML first — "contract-first").
  • Be consistent more than "perfect": same naming, same page shape, same error shape everywhere.
  • DTOs, not entities, in requests and responses (topic 33) — your API stays stable when the database changes.
  • Validate at the boundary and return field-level errors (topic 34).
  • Paginate every list, cap the page size, whitelist sort fields.
  • Version only on breaking changes; announce deprecations (e.g. a Deprecation/Sunset response header) and give clients time.
  • Make retries safe: idempotent PUT/DELETE, Idempotency-Key for important POSTs (payments, orders).
  • Document everything that a consumer needs: every status code, examples, which fields are required.
  • Protect or disable Swagger UI in production if the API is private: springdoc.swagger-ui.enabled=false, or secure it.
  • Use HTTPS, and never put secrets or personal data in URLs (they end up in logs).
  • Consider caching headers (ETag, Cache-Control) for read-heavy resources, and rate limiting (429) for public APIs.

8. Key takeaways

  • URLs are plural nouns (/api/v1/tasks/42); the HTTP method is the verb.
  • Use the right status: 200, 201 + Location, 204, 400, 401, 403, 404, 409, 500.
  • GET/PUT/DELETE are idempotent; make POST retries safe with an Idempotency-Key.
  • One list shape (content + paging numbers) and one error shape (ProblemDetail, RFC 9457).
  • Filter, sort and page with query parameters; cap sizes and whitelist sort fields.
  • Version on breaking changes — URI versioning (/api/v2) is the most common; headers also work.
  • HATEOAS = links to next actions in the response; known in interviews, rare in practice.
  • springdoc generates /v3/api-docs and /swagger-ui.html from your code.
  • @Tag, @Operation, @ApiResponse, @Parameter, @Schema enrich the docs; GroupedOpenApi splits them.

10. Interview questions

Q1. What makes an API "RESTful"?

Resources identified by URIs, manipulated through a uniform interface (standard HTTP methods), representations (usually JSON), stateless requests (each request carries all needed info), meaningful status codes, cacheability where applicable, and — in strict REST — hypermedia links (HATEOAS).

Q2. What is the difference between PUT and PATCH?

PUT replaces the entire resource with the representation sent — missing fields become empty/default. PATCH applies a partial change — only the sent fields are modified. PUT is idempotent by definition; PATCH is idempotent only if designed as "set" operations.

Q3. What does idempotent mean and which HTTP methods are idempotent?

Repeating the same request has the same effect on server state as sending it once. GET, HEAD, OPTIONS, PUT and DELETE are idempotent; POST is not (and PATCH not necessarily). Idempotency allows safe retries after network failures.

Q4. How do you make POST requests safe to retry?

Use an Idempotency-Key header: the client generates a unique key per logical operation; the server stores key → result and, if the same key arrives again, returns the stored result instead of executing again. Keys are stored durably (DB unique constraint / Redis) with an expiry.

Q5. 401 vs 403?

401 Unauthorized means "not authenticated" — no or invalid credentials; the client should log in. 403 Forbidden means "authenticated but not allowed" — logging in again won't help.

Q6. Which API versioning strategies do you know? Which do you prefer?

URI path (/v1/), custom request header, media type / Accept header, and query parameter. URI versioning is most common because it's explicit, easy to test, route and cache. Header/media-type versioning keep URLs stable but are less visible. Version only for breaking changes and deprecate old versions with a timeline.

Q7. What is OpenAPI, and how is it different from Swagger?

OpenAPI is the specification format (JSON/YAML) describing an HTTP API. Swagger was the original name of the spec (up to 2.0) and is now the name of a tool family (Swagger UI, Swagger Editor, Codegen). In Spring Boot 3, springdoc-openapi generates the OpenAPI 3 document from controllers and serves Swagger UI.

Q8. Name the main springdoc/OpenAPI annotations and what they do.

@Tag groups endpoints; @Operation documents an endpoint (summary/description); @ApiResponse(s) documents status codes and bodies; @Parameter documents parameters; @Schema documents models/fields with examples and constraints; @Hidden excludes; @ParameterObject flattens objects like Pageable. Global info comes from an OpenAPI bean and groups from GroupedOpenApi beans.

Q9. What is ProblemDetail?

Spring 6's implementation of RFC 9457 (formerly RFC 7807) "Problem Details for HTTP APIs": a standard JSON error body (type, title, status, detail, instance + custom properties) with media type application/problem+json. It gives every API a consistent, machine-readable error format.

Q10. How do you design pagination for a REST API?

Query parameters page/size (or offset/limit) and sort; a default and a maximum page size; a stable sort order; and a response containing the items plus metadata (total elements/pages, current page, first/last) or next/prev links. For huge or real-time data, cursor-based pagination avoids deep-offset performance problems and duplicates.
