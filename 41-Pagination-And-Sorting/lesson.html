1. Why this matters

So far our GET /api/products returned findAll() — every row. That's fine for 3 products. Now imagine an online shop with 1 million products:

  • The database reads 1 million rows.
  • Hibernate creates 1 million Java objects → the server runs out of memory (OutOfMemoryError).
  • Jackson writes hundreds of megabytes of JSON; the phone app downloads them over mobile data.
  • And the user only looks at the first 20 anyway!

Pagination means returning a small piece ("page") at a time: products 1–20, then 21–40... Sorting decides the order: cheapest first, newest first, A–Z. Every serious list endpoint at work — search results, order history, admin tables, feeds — uses both.

2. Real-life analogy

📖 A book and its table of contents A 600-page book isn't printed on one giant sheet. You read page by page. The page number tells you where you are, and the cover says "600 pages" so you know how much is left — that's Page with totalPages.
A social-media feed is different: you just keep scrolling and the app asks "is there more?". It never tells you "you are on page 37 of 52,881". That's Slice — it only knows whether a next page exists, which is cheaper.
And sorting is the book's index: by name, by date, by price.

3. Concepts step by step

3.1 What pagination does in SQL

A page is defined by two numbers: the page index (starting at 0) and the page size. From them the database computes how many rows to skip:

page = 2, size = 10→ skip 2 × 10 = 20 rows→ return rows 21–30

Hibernate generates the right SQL for your database (H2 version below, copied from the console). MySQL would get LIMIT ?, ?.

select p1_0.id, p1_0.category, ... from products p1_0
order by p1_0.price desc
offset ? rows
fetch first ? rows only

3.3 Repository methods with paging

You get findAll(Pageable) and findAll(Sort) for free (from JpaRepository, which includes PagingAndSortingRepository). And any query method can take a Pageable or Sort as its last parameter:

Page<Product>  findByCategoryIgnoreCase(String category, Pageable pageable);
Slice<Product> findSliceByCategoryIgnoreCase(String category, Pageable pageable);
List<Product>  findTop5ByCategoryIgnoreCase(String category, Sort sort);

@Query(value = "SELECT p FROM Product p WHERE p.stock < :threshold",
       countQuery = "SELECT COUNT(p) FROM Product p WHERE p.stock < :threshold")
Page<Product> findLowStock(@Param("threshold") int threshold, Pageable pageable);

3.4 Page vs Slice vs List

A Page needs to know the total number of matching rows. So Spring runs two queries: the page itself and a COUNT:

select ... from products p1_0 order by p1_0.price desc offset ? rows fetch first ? rows only
select count(p1_0.id) from products p1_0

On a huge table with complex filters, the COUNT can be slower than the page query itself! A Slice skips the count. It asks for size + 1 rows: if the extra row exists, hasNext() is true.

Useful methods on Page/Slice: getContent(), getNumber() (current index), getSize(), getNumberOfElements() (rows on this page), hasNext(), nextPageable(), and map(...) to convert entities to DTOs while keeping the paging info:

Page<ProductResponse> dtoPage = productPage.map(ProductResponse::from);

3.5 Pageable straight from the URL

Spring MVC can build the Pageable for you. Just declare it as a controller parameter:

public PageResponse<ProductResponse> list(@PageableDefault(size = 10, sort = "id") Pageable pageable) {
    return service.list(pageable);
}

spring.data.web.pageable.max-page-size=50          # hard limit (default 2000!)
spring.data.web.pageable.page-parameter=page
spring.data.web.pageable.size-parameter=size
spring.data.web.sort.sort-parameter=sort
spring.data.web.pageable.one-indexed-parameters=false   # true => first page is ?page=1
spring.data.web.pageable.serialization-mode=via-dto     # how a returned Page<T> becomes JSON
⚠️ The default maximum is 2000 Without max-page-size, anyone can request ?size=2000 on every call. Lower it to what your UI really needs (20–100). This is a simple protection against accidental or malicious heavy requests.

3.7 The response shape

A front-end developer needs the items and enough information to draw the page buttons. Our own record gives a clear, stable contract:

public record PageResponse<T>(List<T> content, int page, int size, long totalElements,
                              int totalPages, boolean first, boolean last, String sort) {
    public static <T> PageResponse<T> from(Page<T> page) { ... }
}
{
  "content": [ {"id":28,"name":"Scarf","price":204.99,...}, ... ],
  "page": 0, "size": 3, "totalElements": 60, "totalPages": 20,
  "first": true, "last": false, "sort": "price: DESC"
}

What about returning Page<T> directly?

Returning Spring's PageImpl as JSON used to produce a big, unstable structure (with pageable, sort, empty...), and Spring Data 3.3+ logs a warning about it. With spring.data.web.pageable.serialization-mode=via-dto (or @EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)), Spring converts it to a stable PagedModel:

{
  "content": [ ... ],
  "page": { "size": 2, "number": 1, "totalElements": 60, "totalPages": 30 }
}

Both are fine. A custom record gives you full control (e.g. add first/last); PagedModel is zero code. Pick one style for your whole API and stick to it.

3.8 Sorting safely

With ?sort=... the client chooses the property. Two problems:

  1. A non-existent property (?sort=foo) throws PropertyReferenceException → 500 if unhandled.
  2. Sorting by an un-indexed or internal column (e.g. a password hash, or a huge text column) can be slow or leak information.

Solution: a whitelist of allowed sort fields, checked in the service, plus a handler that returns 400:

public static final Set<String> SORTABLE_FIELDS = Set.of("id", "name", "category", "price", "stock", "createdAt");

private void validateSort(Sort sort) {
    for (Sort.Order order : sort) {
        if (!SORTABLE_FIELDS.contains(order.getProperty())) {
            throw new IllegalArgumentException("Cannot sort by '" + order.getProperty() + "'. Allowed: " + SORTABLE_FIELDS);
        }
    }
}
💡 Always have a unique tie-breaker If 30 products cost 9.99 and you sort only by price, the database may return them in a different order on each request — the same product can appear on page 1 and page 2, another never. Add a unique field as the last sort order: Sort.by("price").and(Sort.by("id")).

3.9 Search filters + paging

Filtering and paging go together: "Electronics between 50 and 150, most expensive first, page 0 of size 3". With Specifications (topic 39) it is one call:

Page<Product> page = repository.findAll(Specification.allOf(specs), pageable);

Spring applies the WHERE clause to both the page query and the COUNT query, so totalElements is the number of matching products (5), not of all products (60).

3.10 Offset paging vs keyset (cursor) paging — good to know

Offset paging (OFFSET 100000 ROWS) gets slower on deep pages, because the database still walks through the skipped rows. And if rows are inserted while the user is paging, items can shift between pages. Very large feeds use keyset/cursor paging instead: "give me 20 items with id > lastSeenId". Spring Data 3.1+ supports it with ScrollPosition / Window<T>. For admin tables and normal search pages, offset paging is perfectly fine.

4.2 Service: building the PageRequest yourself

Sometimes you prefer plain parameters (sortBy, direction), e.g. to document them clearly in OpenAPI (topic 44) or when paging isn't coming from HTTP:

service/ProductService.javapublic PageResponse<ProductResponse> listManual(int page, int size, String sortBy, String direction) {
    if (page < 0) throw new IllegalArgumentException("page must be 0 or greater");
    if (size < 1 || size > MAX_PAGE_SIZE) throw new IllegalArgumentException("size must be between 1 and " + MAX_PAGE_SIZE);

    Sort sort = Sort.by(Sort.Direction.fromString(direction), sortBy)   // "asc"/"desc"
            .and(Sort.by("id"));                                         // tie-breaker
    validateSort(sort);

    Pageable pageable = PageRequest.of(page, size, sort);
    return PageResponse.from(repository.findAll(pageable).map(ProductResponse::from));
}

Notice: here we must enforce the max size — the max-page-size property only applies to Pageable parameters resolved by Spring MVC.

4.3 Service: Slice and search

service/ProductService.javapublic SliceResponse<ProductResponse> slice(String category, Pageable pageable) {
    var slice = (category == null)
            ? repository.findAllBy(pageable)
            : repository.findSliceByCategoryIgnoreCase(category, pageable);
    return SliceResponse.from(slice.map(ProductResponse::from));
}

public PageResponse<ProductResponse> search(String category, String q, BigDecimal minPrice,
                                            BigDecimal maxPrice, Pageable pageable) {
    List<Specification<Product>> specs = new ArrayList<>();
    if (category != null && !category.isBlank()) specs.add(ProductSpecifications.categoryIs(category));
    if (q != null && !q.isBlank()) specs.add(ProductSpecifications.nameContains(q));
    if (minPrice != null) specs.add(ProductSpecifications.priceAtLeast(minPrice));
    if (maxPrice != null) specs.add(ProductSpecifications.priceAtMost(maxPrice));
    return PageResponse.from(repository.findAll(Specification.allOf(specs), pageable).map(ProductResponse::from));
}

6. Common mistakes

⚠️ Thinking the first page is 1 ?page=1 returns the second page. Pages start at 0.
Fix: tell your front-end team, or set spring.data.web.pageable.one-indexed-parameters=true.
⚠️ Loading everything and paging in Java findAll().stream().skip(page*size).limit(size) — still reads every row.
Fix: pass a Pageable to the repository so the database pages.
⚠️ Using the column name in sort ?sort=created_at → PropertyReferenceException: No property 'created' found.
Fix: use the Java field: ?sort=createdAt.
⚠️ No tie-breaker in the sort Items jump between pages or appear twice.
Fix: add id as the last sort order.
⚠️ No max page size The default limit is 2000 rows per request.
Fix: spring.data.web.pageable.max-page-size=50 (and validate manual parameters yourself).
⚠️ JOIN FETCH of a collection with paging Hibernate warns "HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory" — it loads everything and pages in memory.
Fix: page the parent entities only, then load children separately (second query with WHERE parent.id IN :ids or batch fetching).
⚠️ Slow COUNT queries Complex @Query with joins → the auto-derived count query is slow or even invalid.
Fix: provide countQuery = "...", or use Slice when totals aren't needed.

7. Best practices

  • Every list endpoint is paged. No exceptions for "small" tables — they grow.
  • Sensible defaults and a hard maximum (default-page-size, max-page-size).
  • Whitelist sortable fields and always add a unique tie-breaker.
  • Index the columns you filter and sort on most (@Table(indexes = ...) or Flyway).
  • Return a stable response shape — your own record or PagedModel (via-dto) — never raw PageImpl.
  • Map to DTOs with page.map(...), inside the transaction.
  • Use Slice for infinite scroll or when COUNT is expensive; consider keyset paging (Window/ScrollPosition) for very deep feeds.
  • Be consistent across the API: same parameter names (page, size, sort) and same response format everywhere (more in topic 44).

8. Key takeaways

  • Never return whole tables: page with Pageable (page index from 0 + size + sort).
  • PageRequest.of(page, size, sort) builds one; Sort.by("field").descending().and(...) builds orders.
  • Any repository method can take Pageable/Sort as its last parameter.
  • Page = content + totals (extra COUNT query); Slice = content + hasNext (no count).
  • A Pageable controller parameter is filled from ?page=&size=&sort=; @PageableDefault sets defaults.
  • Configure spring.data.web.pageable.default-page-size, max-page-size, serialization-mode=via-dto.
  • Return a clean shape: content, page, size, totalElements, totalPages.
  • Filters + paging: findAll(spec, pageable) — totals reflect the filtered rows.

10. Interview questions

Q1. How do you implement pagination in Spring Data JPA?

Pass a Pageable (usually PageRequest.of(page, size, sort)) as the last parameter of a repository method returning Page<T>, Slice<T> or List<T>. In controllers, declare a Pageable parameter and Spring MVC resolves it from page, size and sort query parameters.

Q2. What is the difference between Page and Slice?

Page extends Slice and additionally knows the total number of elements and pages, which requires an extra count query. Slice only knows whether there's a next slice (it fetches size + 1 rows), so it's cheaper — good for infinite scrolling.

Q3. How do you sort by multiple fields?

Sort.by("category").ascending().and(Sort.by("price").descending()), or Sort.by(Order.asc("category"), Order.desc("price")); via HTTP: ?sort=category,asc&sort=price,desc.

Q4. How do you limit the page size a client can request?

Set spring.data.web.pageable.max-page-size (default 2000) for resolved Pageable parameters, and validate manually for custom parameters. Also set a sensible default-page-size and @PageableDefault.

Q5. Why add a unique field as a tie-breaker in sorting?

Without a deterministic order, rows with equal sort values may be returned in different orders between queries, causing duplicates or missing items across pages. Adding a unique column (e.g. id) makes the order total and stable.

Q6. What is the problem with deep offset pagination and how can you solve it?

OFFSET n forces the database to scan and discard n rows, so deep pages get slower, and concurrent inserts can shift items between pages. Keyset (seek/cursor) pagination filters by the last seen sort key (WHERE id > :lastId), which uses indexes efficiently. Spring Data supports it with ScrollPosition.keyset() and Window<T>.

Q7. Why shouldn't you return PageImpl directly as JSON?

Its JSON structure is an implementation detail and not guaranteed to be stable across Spring Data versions (Spring warns about it). Use your own DTO, or enable VIA_DTO serialization so Spring renders a stable PagedModel.

Q8. What happens if you combine JOIN FETCH on a collection with paging?

Hibernate can't apply LIMIT/OFFSET in SQL because rows are multiplied by the join, so it fetches all rows and paginates in memory (warning HHH90003004) — a performance and memory risk. Page the root entities first and load collections in a second query or with batch fetching.

Q9. When do you need a custom countQuery?

When a paged @Query is complex (joins, group by, native SQL) and Spring can't derive an efficient or valid count query automatically. You provide countQuery (or countProjection) explicitly.
