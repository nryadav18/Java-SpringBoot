64. Resilience with Resilience4j

Keep your service alive and friendly when the services it depends on are slow, broken or overloaded — with circuit breakers, retries, time limits, rate limits and bulkheads.

1. Why this matters

In a monolith, a method call never “times out” — the code is in the same process. In microservices, every call crosses the network, and the network will fail sometimes: a service restarts, a database is slow, a deployment goes wrong, a cloud zone has trouble.

The question is not “will a dependency fail?” but “what happens to my service when it does?”

Picture an online store. Product pages show stock levels from inventory-service. One Friday evening inventory's database gets slow and every call takes 30 seconds:

  1. Each product page request in store-service waits 30 s, holding one Tomcat thread (Tomcat has 200 by default).
  2. Friday traffic: 50 requests per second. After 4 seconds all 200 threads are waiting.
  3. Now every request to the store hangs — even the “About us” page that does not need inventory at all.
  4. The API gateway and the mobile backend that call the store also start to hang…

One sick service has knocked over the whole shop. This is a cascading failure. Resilience patterns stop the chain reaction: fail fast, give a sensible fallback (“stock: probably available”), and give the sick service time to recover.

ℹ️ Where you will see this at work Netflix made the circuit breaker famous with its library Hystrix (now retired). Resilience4j is its modern, lightweight successor and the default choice in Spring Boot 3 projects. Payment gateways, airline booking systems and banks use exactly these patterns, and “how do you handle a failing downstream service?” is one of the most common microservice interview questions.

2. Real-life analogy

⚡ Dominoes and the electric fuse box

The problem — dominoes: stand dominoes in a row and push the first one. Each one knocks over the next until all are down. Services that wait forever on each other behave the same way: one failure topples the chain.

The solution — the fuse (circuit breaker) in your home:

  • Normally the switch is closed — electricity flows (calls go through).
  • A short circuit happens → the breaker trips open. Electricity stops at once, so the wires do not catch fire (we stop calling the sick service and answer immediately with a fallback).
  • After a while you carefully flip it back to test: half open. If the lights work, it stays on (closed). If it trips again, it goes back to open.

Other everyday versions of today's patterns:

  • Retry — the phone line is busy, you call again a few seconds later.
  • Time limiter — “if the pizza is not here in 30 minutes, I cook noodles instead.”
  • Rate limiter — a nightclub bouncer lets in only 10 people per minute.
  • Bulkhead — a ship is split into watertight compartments; one leaking room does not sink the whole ship.

3. Concepts step by step

3.1 Cascading failure in a picture

Mobile app→ waits → API gateway→ waits → store-service
all threads busy→ waits → inventory-service
slow DB 🔥

The fix is to put a protective layer between store-service and inventory-service that decides, for every call: Should I even try? How long do I wait? Should I try again? What do I answer if it fails?

3.2 Resilience4j in one table

Resilience4j is a small Java library made of independent modules. You pick only what you need.

ModuleQuestion it answersAnnotationException when it blocks a call
CircuitBreakerIs this dependency sick? Then stop calling it for a while.@CircuitBreakerCallNotPermittedException
RetryWas it a short hiccup? Try again.@Retry(rethrows the last error)
TimeLimiterTaking too long? Stop waiting.@TimeLimiterTimeoutException
RateLimiterToo many calls per second? Reject some.@RateLimiterRequestNotPermitted
BulkheadToo many calls at the same moment? Reject extras.@BulkheadBulkheadFullException

3.3 The circuit breaker state machine

StateWhat happens to a callHow it leaves this state
CLOSED (healthy)Goes to the downstream. Result (success / failure / slow) is recorded in a sliding window.When the window has at least minimum-number-of-calls and the failure rate (or slow rate) reaches the threshold → OPEN.
OPEN (tripped)Rejected immediately with CallNotPermittedException — no network call. Fallback answers in ~1 ms.After wait-duration-in-open-state → HALF_OPEN.
HALF_OPEN (testing)Only permitted-number-of-calls-in-half-open-state calls go through; others are rejected.If those trial calls are mostly OK → CLOSED; otherwise → OPEN again.

Why is fail-fast good? Two reasons. (1) Our threads are free again — the store stays fast. (2) The sick service gets a break instead of being hammered by thousands of calls while it tries to recover.

3.4 The sliding window

The breaker judges health using recent calls only:

  • COUNT_BASED — the last N calls (e.g. last 6). Good for steady traffic.
  • TIME_BASED — the calls of the last N seconds. Good when traffic goes up and down.

Example with window 6, minimum 4 calls, threshold 50 %:

✔✘✘✘ → 4 calls, 3 failed = 75 % ≥ 50 %OPEN!

Which errors count as “failure”? You decide with record-exceptions and ignore-exceptions. A 404 or 400 is usually our mistake, not a sick service → ignore it. A 500 or a timeout → record it.

3.5 Retry

Many failures are short: a pod restarting, a lost network packet. Trying again after a small pause often works.

resilience4j:
  retry:
    instances:
      inventory:
        max-attempts: 3                    # 1 normal try + 2 retries
        wait-duration: 500ms
        enable-exponential-backoff: true   # 500 ms, 1 s, 2 s ...
        exponential-backoff-multiplier: 2
        retry-exceptions:                  # only errors that may go away by themselves
          - org.springframework.web.client.HttpServerErrorException
          - org.springframework.web.client.ResourceAccessException
        ignore-exceptions:
          - org.springframework.web.client.HttpClientErrorException   # 4xx: retrying will not help
⚠️ Retry is a double-edged sword
  • If 1 000 clients each retry 3 times, the struggling service suddenly receives 3 000 calls — a retry storm. Use backoff (growing waits), maybe with random jitter, and few attempts.
  • Only retry idempotent operations (safe to repeat: GET, or POST with an idempotency key). Retrying “charge credit card” may charge twice!

3.6 TimeLimiter

A time limiter stops waiting after a fixed time. Because it must be able to walk away from a call that is still running, it works on asynchronous results: the method must return a CompletableFuture (or a reactive Mono/Flux).

@TimeLimiter(name = "inventorySlow", fallbackMethod = "stockAsyncFallback")
public CompletableFuture<StockInfo> getStockWithTimeLimit(String sku) {
    return CompletableFuture.supplyAsync(() -> inventoryClient.fetchStock(sku));
}
ℹ️ TimeLimiter vs HTTP read timeout For plain blocking HTTP calls, the simplest “time limit” is the read timeout on the HTTP client (topic 63 for Feign, SimpleClientHttpRequestFactory.setReadTimeout for RestClient). Always set it. @TimeLimiter is for async code or when you need a fallback for “too slow”. Note: when it gives up, the background work may keep running until the HTTP read timeout ends it — so keep both.

3.7 RateLimiter

Limits how many calls are allowed per time period: “3 calls per 10 seconds”. Use it to protect an expensive operation, to respect a partner API's quota (“max 100 calls per minute”), or to stop one client from flooding you.

resilience4j:
  ratelimiter:
    instances:
      deals:
        limit-for-period: 3          # permits per period
        limit-refresh-period: 10s    # length of a period
        timeout-duration: 0          # do not wait for a permit, reject at once

3.8 Bulkhead

Limits how many calls run at the same moment. If report generation is heavy, allow only 2 at a time; the 3rd caller is rejected (or waits a little). This keeps threads free for everything else — one slow feature cannot eat the whole thread pool.

RateLimiterBulkhead
LimitsCalls per time periodCalls in progress at once
Example“max 100 per minute”“max 10 at the same time”
ProtectsThe downstream / a quotaOur own threads / resources

Resilience4j has two bulkhead types: SEMAPHORE (default — just a counter, runs on the caller's thread) and THREADPOOL (separate thread pool, needs a CompletableFuture return type).

3.9 Fallback methods

A fallback is the “plan B” answer. Rules for a fallback method:

  • It lives in the same class as the protected method.
  • It has the same return type.
  • It has the same parameters, plus one extra exception parameter at the end.
  • You can write several fallbacks with different exception types; Resilience4j picks the closest match.
@Retry(name = "inventory", fallbackMethod = "stockFallback")
@CircuitBreaker(name = "inventory")
public StockInfo getStock(String sku) { ... }

// circuit is OPEN - we did not even try
private StockInfo stockFallback(String sku, CallNotPermittedException ex) { ... }

// any other failure, after retries were used up
private StockInfo stockFallback(String sku, Exception ex) { ... }

Good fallbacks: a cached / last-known value, a default (“stock unknown — order anyway, we will confirm by email”), an empty list, or a clear error. Bad fallback: quietly returning wrong data (e.g. “price = 0”).

3.10 Order of the annotations — and the “retry never happens” trap

When several annotations sit on one method, Resilience4j applies them in a fixed order (outermost first):

Retry( CircuitBreaker( RateLimiter( TimeLimiter( Bulkhead( your method)))))

So every retry attempt passes through the circuit breaker and is counted. Now the trap:

🚨 Fallback on the inner annotation swallows the error If you write @Retry(name="x") @CircuitBreaker(name="x", fallbackMethod="fb"), the circuit breaker (inner) catches the error and returns the fallback value. The Retry (outer) sees a successful result and never retries.
Fix: put the fallbackMethod on the outermost annotation — @Retry — as our code does.

You can change the order with properties like resilience4j.retry.retry-aspect-order and resilience4j.circuitbreaker.circuit-breaker-aspect-order (higher number = applied first / outer), but the default is fine for most cases.

3.12 Spring Cloud CircuitBreaker — the alternative way

Spring Cloud offers a vendor-neutral abstraction: spring-cloud-starter-circuitbreaker-resilience4j (with the Spring Cloud 2025.0.0 BOM). Instead of annotations you use a factory in code:

@Service
class StockServiceProgrammatic {
    private final CircuitBreakerFactory<?, ?> cbFactory;
    private final InventoryClient client;

    StockServiceProgrammatic(CircuitBreakerFactory<?, ?> cbFactory, InventoryClient client) {
        this.cbFactory = cbFactory;
        this.client = client;
    }

    StockInfo getStock(String sku) {
        return cbFactory.create("inventory")
                .run(() -> client.fetchStock(sku),                    // the protected call
                     throwable -> new StockInfo(sku, -1, "fallback", throwable.getMessage()));
    }
}

This starter is also what powers Feign fallbacks (spring.cloud.openfeign.circuitbreaker.enabled=true, topic 63). Both approaches use the same Resilience4j engine. This lesson uses the direct resilience4j-spring-boot3 annotations because they cover all five modules with the least code.

4.1 The downstream with a chaos switch

inventory-service/…/InventoryController.java (core)private final AtomicReference<ChaosMode> mode = new AtomicReference<>(ChaosMode.OK);

@GetMapping("/{sku}")
public StockResponse getStock(@PathVariable String sku) throws InterruptedException {
    int callNo = callCounter.incrementAndGet();
    ChaosMode current = mode.get();
    log.info("Call #{} for {} (chaos mode = {})", callNo, sku, current);

    if (current == ChaosMode.FAIL) {
        throw new ResponseStatusException(HttpStatus.INTERNAL_SERVER_ERROR, "Simulated database crash");
    }
    if (current == ChaosMode.SLOW) {
        Thread.sleep(slowDelayMs.get());
    }
    return new StockResponse(sku, stock.getOrDefault(sku, 0), "inventory-service");
}

@PostMapping("/chaos")
public Map<String, Object> setChaos(@RequestParam ChaosMode mode,
                                    @RequestParam(defaultValue = "4000") long delayMs) { ... }

This kind of switch is a tiny version of chaos engineering — deliberately breaking things to prove your system survives (Netflix's “Chaos Monkey”).

4.3 The service — five patterns, five methods

store-service/…/service/StockService.java (circuit breaker + retry)@Retry(name = "inventory", fallbackMethod = "stockFallback")
@CircuitBreaker(name = "inventory")
public StockInfo getStock(String sku) {
    StockInfo fresh = inventoryClient.fetchStock(sku);
    lastKnownStock.put(sku, fresh);       // remember for bad times
    return fresh;
}

private StockInfo stockFallback(String sku, CallNotPermittedException ex) {
    return lastKnownOrUnknown(sku, "Circuit breaker is OPEN - inventory-service is resting");
}

private StockInfo stockFallback(String sku, Exception ex) {
    return lastKnownOrUnknown(sku, "inventory-service failed: " + ex.getClass().getSimpleName());
}

lastKnownStock is a small map that remembers the last good answer per product. The fallback serves that value (marked "fallback-last-known") — slightly old stock is far better than an error page.

StockService.java (rate limiter + bulkhead)@RateLimiter(name = "deals", fallbackMethod = "dealsFallback")
public List<String> todaysDeals() { ... }

private List<String> dealsFallback(RequestNotPermitted ex) {
    return List.of("Too many requests - please try again in a few seconds.");
}

@Bulkhead(name = "report", fallbackMethod = "reportFallback")
public String buildReport(String sku) throws InterruptedException {
    Thread.sleep(3000);                   // pretend this is heavy work
    return "Stock report for " + sku + " is ready";
}

private String reportFallback(String sku, BulkheadFullException ex) {
    return "Report service busy (max 2 at a time). Please retry shortly.";
}

Note dealsFallback has only the exception parameter — because todaysDeals() has no parameters.

6. Common mistakes

🚨 Mistake: “my @CircuitBreaker does nothing” Usual causes: (1) spring-boot-starter-aop is missing; (2) the method is called from inside the same class (this.getStock()) — the AOP proxy is bypassed (topic 27); (3) the method is private; (4) the class is not a Spring bean.
Fix: add AOP, call the method from another bean, make it public.
⚠️ Mistake: wrong fallback signature Error: NoSuchMethodException ... fallback method or the fallback is never used.
Fix: same return type, same parameters in the same order, plus one Throwable/Exception parameter at the end, in the same class.
⚠️ Mistake: fallback on the inner annotation With @Retry + @CircuitBreaker(fallbackMethod=...) retries never happen. Put the fallback on @Retry (outermost).
⚠️ Mistake: counting 4xx as failures A user asking for an unknown product (404) opens the circuit and now nobody can see stock.
Fix: ignore-exceptions: HttpClientErrorException (or list only real failures in record-exceptions).
⚠️ Mistake: instance name typo @CircuitBreaker(name = "inventroy") silently creates a new breaker with default settings — your YAML is ignored.
Fix: keep names in constants, and check /actuator/circuitbreakers lists exactly the names you expect.
⚠️ Mistake: @TimeLimiter on a normal method TimeLimiter needs CompletableFuture (or reactive types). On a method returning StockInfo it fails. For blocking calls use the HTTP client's read timeout.
⚠️ Mistake: retrying non-idempotent calls Retrying “place order” or “charge card” can create duplicates. Retry only safe operations or use idempotency keys.
⚠️ Mistake: the fallback hides problems forever Everything “works”, but nobody notices inventory has been down for 3 hours.
Fix: log in fallbacks, export metrics, and set alerts on the breaker state (Grafana / Prometheus).

7. Best practices

  • Timeouts first. Every remote call needs connect + read timeouts. Resilience patterns build on top of that.
  • Circuit breaker on every remote dependency (one instance per downstream service, not per method).
  • Meaningful fallbacks: cached data, defaults, degraded features (“recommendations unavailable”) — and be honest in the response (a flag like our source).
  • Retry carefully: few attempts (2–3), exponential backoff + jitter, only for transient errors and idempotent operations.
  • Tune from real data: set thresholds from your latency percentiles (p99) and normal error rates; start with defaults and adjust.
  • Don't let an OPEN breaker fail your health check (allow-health-indicator-to-fail: false), or orchestrators may restart healthy pods.
  • Monitor and alert on resilience4j_circuitbreaker_state metrics; log state transitions.
  • Use shared configs.default and override per instance to keep YAML short.
  • Bulkhead slow features so they can't eat all Tomcat threads.
  • Test failure on purpose (chaos switches, Toxiproxy, WireMock delays) — resilience you never tested is a guess.
  • Resilience at the edge too: Spring Cloud Gateway (topic 61) has a CircuitBreaker filter and RequestRateLimiter.

8. Key takeaways

  • Remote calls fail; without protection one slow service causes a cascading failure.
  • Circuit breaker: CLOSED (count) → OPEN (fail fast) → HALF_OPEN (test) → CLOSED/OPEN.
  • Retry for short hiccups (with backoff, idempotent only); TimeLimiter stops waiting (async); RateLimiter limits calls per period; Bulkhead limits concurrent calls.
  • Setup: resilience4j-spring-boot3 2.2.0 + spring-boot-starter-aop + YAML instances.
  • Fallback = same signature + exception parameter; the closest exception type wins.
  • Default order: Retry(CircuitBreaker(RateLimiter(TimeLimiter(Bulkhead(method))))) — put the fallback on the outermost.
  • Watch it with /actuator/circuitbreakers, /actuator/circuitbreakerevents, health and metrics.
  • Ignore 4xx errors; record 5xx and timeouts.

9. Practice exercises

Easy

Tune the breaker. Change the circuit breaker so it opens only at 70 % failures and stays open for 20 seconds. Repeat the demo and confirm with /actuator/circuitbreakers.

        failure-rate-threshold: 70

With 1 success + 3 failures (75 %) it still opens. Try a window where 2 of 4 fail (50 %) — now it stays CLOSED.

Easy

See the events. Break inventory, make 3 calls, then open /actuator/circuitbreakerevents. Find the STATE_TRANSITION event and write down from which state to which.

Hint / solution

You will see entries like "type":"ERROR" (each failed attempt), "type":"STATE_TRANSITION","stateTransition":"CLOSED_TO_OPEN", then "type":"NOT_PERMITTED" for rejected calls. After healing: OPEN_TO_HALF_OPEN and HALF_OPEN_TO_CLOSED.

10. Interview questions

Q1. What is a cascading failure and how do you prevent it?

A failure that spreads: a slow/broken service makes its callers wait, they run out of threads and become slow/broken too, and so on up the chain. Prevent it with timeouts, circuit breakers (fail fast), bulkheads (isolate resources), sensible fallbacks, and limited retries with backoff.

Q2. Explain the states of a circuit breaker.

CLOSED: calls pass, outcomes are recorded in a sliding window. When the failure rate or slow-call rate exceeds its threshold (after the minimum number of calls) it goes OPEN: calls are rejected immediately with CallNotPermittedException. After the wait duration it goes HALF_OPEN: a limited number of trial calls are allowed; if they succeed it returns to CLOSED, otherwise back to OPEN.

Q3. Count-based vs time-based sliding window?

Count-based aggregates the last N calls; time-based aggregates calls from the last N seconds. Time-based fits bursty or low/variable traffic; count-based is simple for steady traffic.

Q4. Difference between RateLimiter and Bulkhead?

RateLimiter limits the number of calls per time period (throughput, e.g. 100/minute). Bulkhead limits the number of concurrent calls (e.g. 10 at once) to isolate resources like threads. Semaphore bulkhead uses a counter on the caller thread; thread-pool bulkhead uses a dedicated pool.

Q5. In which order are Resilience4j annotations applied?

By default Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( function ))))). Retry is outermost, so each retry attempt is counted by the circuit breaker. The order can be changed with the *-aspect-order properties.

Q6. Why might a retry never happen when combined with a circuit breaker?

If the fallbackMethod is defined on the inner @CircuitBreaker, the breaker converts the exception into a fallback value; the outer Retry sees success and does not retry. Put the fallback on the outermost annotation (Retry).

Q7. What rules must a fallback method follow?

Same class, same return type, same parameter list plus one trailing exception parameter (Throwable or a subtype). Multiple overloaded fallbacks can exist; the one with the most specific matching exception type is used.

Q8. Which exceptions should open a circuit breaker?

Those that signal the downstream is unhealthy: 5xx responses, connection errors, timeouts. Client errors (4xx — validation, not found) should be ignored, otherwise bad user input could open the circuit for everyone.

Q9. Hystrix vs Resilience4j?

Hystrix (Netflix) is in maintenance mode since 2018, built around thread-pool isolation and Java 6-style APIs. Resilience4j is lightweight, functional (decorators), modular (pick only needed modules), based on Java 8+, integrates with Spring Boot 3, Micrometer and reactive types. Spring Cloud replaced Hystrix with the Spring Cloud CircuitBreaker abstraction backed by Resilience4j.

Q10. How do you monitor circuit breakers in production?

Actuator endpoints (/actuator/circuitbreakers, /circuitbreakerevents, health indicator) and Micrometer metrics (resilience4j_circuitbreaker_state, _calls, _failure_rate) scraped by Prometheus and shown in Grafana with alerts on OPEN state; plus logging of state-transition events.
