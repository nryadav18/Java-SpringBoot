1. Why this matters

Until now every Spring Boot app in this course used Spring MVC on Tomcat. Tomcat gives each incoming request its own thread (remember Topic 17: "each request = a thread"). That thread does the work and, very often, simply waits: it waits for the database, waits for another microservice, waits for a file.

A waiting thread is not free. Each thread uses memory (about 0.5–1 MB of stack) and Tomcat has a limited pool (200 threads by default). If 200 requests are all waiting for a slow service, request number 201 must queue — even though the CPU is doing almost nothing!

Reactive programming fixes this. Instead of "wait for the answer", the code says "call me back when the answer arrives". A small number of threads can then serve thousands of connections, because no thread ever sits idle waiting.

Where you will meet it at work:

  • Spring Cloud Gateway (Topic 61) is built on WebFlux. You will configure it even if you never write reactive code yourself.
  • WebClient is used in many MVC apps too, to call other services.
  • Streaming apps: live dashboards, stock tickers, chat, notifications, IoT sensor data.
  • "Gateway-like" services that mostly call other services and combine the results.
ℹ️ Honest note from your trainerMost enterprise Spring Boot apps are still Spring MVC — and that is fine. You learn WebFlux so you can read reactive code confidently, use WebClient, work with Spring Cloud Gateway, and choose wisely. Section 3.12 tells you when NOT to use it.

2. Real-life analogy

🍽️ Two kinds of restaurant waiters

Blocking restaurant: A waiter takes your order, walks to the kitchen and stands there until your food is cooked. Only then does he come back and serve another table. With 10 waiters you can serve only 10 tables at a time. More customers? Hire more waiters (more threads, more memory).

Non-blocking (reactive) restaurant: A waiter takes your order, gives it to the kitchen, and immediately goes to take the next order. When the kitchen rings the bell ("your food is ready!"), any free waiter picks it up and serves it. With just 2 waiters you can serve 50 tables, because nobody stands still.

The kitchen bell = a callback / event. The waiters = the few event-loop threads of Netty. The order slip = a Mono/Flux: a promise that food will arrive later.

3. Concepts step by step

3.1 Blocking vs non-blocking in code

Look at these two ways to get a user:

// BLOCKING: the current thread stops on this line until the DB answers.
User user = userRepository.findById(1L).orElseThrow();
System.out.println(user.getName());

// NON-BLOCKING: we get back a "promise" immediately. The lambda runs LATER,
// when the data arrives. The current thread is free right away.
Mono<User> userMono = reactiveUserRepository.findById(1L);
userMono.subscribe(u -> System.out.println(u.getName()));

In the second version, findById returns instantly with a Mono<User> — think of it as an order slip. The real data comes later, and our lambda is called then.

3.2 Reactive Streams – the standard

Reactive Streams is a tiny standard (now also inside Java as java.util.concurrent.Flow) that defines how a producer and consumer talk asynchronously and with backpressure. It has just 4 interfaces:

InterfaceRoleEveryday picture
Publisher<T>Produces data itemsThe kitchen
Subscriber<T>Consumes items: onSubscribe, onNext, onError, onCompleteThe customer at the table
SubscriptionThe link between them: request(n), cancel()"Bring me 2 more dishes, please" / "I'm leaving"
Processor<T,R>Both subscriber and publisher (a middle step)A waiter who adds sauce on the way

The conversation always follows the same order:

subscribe()→ onSubscribe(subscription)→ request(n)→ onNext(item) × n→ onComplete() or onError(e)

You will almost never implement these interfaces yourself. Project Reactor (the library Spring uses) gives us two ready-made publishers: Mono and Flux.

3.3 Mono and Flux

Mono<T>
0 or 1 item, then complete (or an error).
Like Optional — but arriving later.
Examples: find one product, save, delete, one HTTP response.
Flux<T>
0, 1, 2 … or infinite items, then complete (or an error).
Like a List/Stream — but items arrive over time.
Examples: all products, live prices, chat messages.
Mono<String> one   = Mono.just("Asha");                 // exactly one value
Mono<String> none  = Mono.empty();                      // completes with no value
Mono<String> boom  = Mono.error(new IllegalStateException("oops"));

Flux<String>  many = Flux.just("apple", "banana", "cherry");
Flux<Integer> nums = Flux.range(1, 5);                  // 1,2,3,4,5
Flux<String>  list = Flux.fromIterable(List.of("a", "b"));
Flux<Long>    tick = Flux.interval(Duration.ofSeconds(1)); // 0,1,2,... forever

3.4 Rule #1: nothing happens until you subscribe

A Mono/Flux is a recipe, not a meal. Building the chain only writes the recipe. Cooking starts when someone calls subscribe(). In a WebFlux app the framework subscribes for you when it writes the HTTP response — you just return the Mono/Flux from your controller.

playground/ReactorPlayground.java (part 1)Flux<String> fruits = Flux.just("apple", "banana", "cherry")
        .doOnNext(f -> System.out.println("  producing " + f));
System.out.println("  (pipeline built, nothing printed yet)");
fruits.subscribe(f -> System.out.println("  got " + f));
  (pipeline built, nothing printed yet)
  producing apple
  got apple
  producing banana
  got banana
  producing cherry
  got cherry
💡 Same idea as Java StreamsIn Topic 14, intermediate operations were lazy until a terminal operation ran. Reactor is the same — subscribe() is the "terminal operation". The big difference: a Java Stream pulls data now on your thread; a Flux pushes data whenever it arrives, possibly on another thread.

3.5 The everyday operators

OperatorWhat it doesTiny example
mapTransform each item synchronously (1 in → 1 out).map(String::toUpperCase)
filterKeep only items that match.filter(n -> n % 2 == 0)
flatMapFor each item, start another async call (returns Mono/Flux) and merge the results.flatMap(id -> repo.findById(id))
concatMapLike flatMap but one at a time, keeps the order.concatMap(this::callApi)
zipWait for several sources and combine them pair by pairMono.zip(userMono, ordersMono)
switchIfEmptyUse another Mono/Flux if nothing was emitted.switchIfEmpty(Mono.error(...))
defaultIfEmptyUse a default value if nothing was emitted.defaultIfEmpty("guest")
onErrorResumeOn error, switch to a fallback publisher.onErrorResume(e -> Mono.just(cached))
onErrorReturnOn error, emit one fallback value.onErrorReturn(0)
delayElementsWait a bit before each item (without blocking).delayElements(Duration.ofMillis(100))

collectListFlux<T> → Mono<List<T>>.collectList()

map and filter

Flux.range(1, 10)                 // 1..10
        .filter(n -> n % 2 == 0)  // 2,4,6,8,10
        .map(n -> n * n)          // 4,16,36,64,100
        .subscribe(n -> System.out.print(n + " "));
// Output: 4 16 36 64 100

map vs flatMap — the most important difference

Use map when the transformation is a normal, instant function (returns a plain value). Use flatMap when the transformation itself is asynchronous (returns a Mono or Flux) — for example a database or HTTP call.

// WRONG: map with an async function gives a "box inside a box"
Flux<Mono<String>> wrong = Flux.just(1L, 2L).map(id -> findUserName(id));

// RIGHT: flatMap subscribes to each inner Mono and "flattens" the results
Flux<String> names = Flux.just(1L, 2L, 3L).flatMap(id -> findUserName(id));
ℹ️ flatMap does not keep orderflatMap runs the inner calls at the same time, so the fastest answer comes first. In our playground the result is [user-3, user-2, user-1] because user-3 was the fastest. Need the original order? Use concatMap (one by one) or flatMapSequential (parallel, but re-ordered).

zip — combine results that arrive at different times

// Both calls start together. Total time = the SLOWER one, not the sum.
Mono<ProductDetails> details = Mono.zip(findById(id), stockFor(id))
        .map(tuple -> new ProductDetails(tuple.getT1(), tuple.getT2()));

Errors — onErrorResume

In Reactor an error is a signal that travels down the chain, like an item. When an error happens, the stream ends. You cannot use normal try/catch around a Mono (the error happens later, on another thread), so you use error operators instead:

Flux.just(10, 5, 0, 2)
        .map(n -> 100 / n)                  // 100/0 throws ArithmeticException
        .onErrorResume(ex -> Flux.just(-1)) // replace the error with a fallback
        .subscribe(n -> System.out.print(n + " "));
// Output: 10 20 -1     (2 is never processed - the error ended the original stream)

delayElements — time without blocking

Flux.just("tick", "tock", "tick")
        .delayElements(Duration.ofMillis(100))   // no Thread.sleep! a timer fires later
        .subscribe(System.out::println);

3.6 Backpressure (simple version)

Backpressure means: the consumer tells the producer how much it can handle. Imagine a conveyor belt of sushi. If the chef puts plates faster than you can eat, plates fall on the floor. With backpressure you say "send me 2 plates", eat them, then "send me 2 more".

Producer (Flux)→ items → Consumer
Producer (Flux)← request(2) ← Consumer 
Flux.range(1, 6)
        .doOnRequest(n -> System.out.println("upstream was asked for " + n))
        .limitRate(2)   // ask for at most 2 at a time
        .subscribe(n -> System.out.println("received " + n));
  upstream was asked for 2
  received 1
  received 2
  upstream was asked for 2
  received 3
  ...

Over HTTP, backpressure is mostly handled for you by TCP flow control and Netty. Operators like limitRate, onBackpressureBuffer and onBackpressureDrop exist for when a fast source (e.g. sensor events) is faster than the consumer.

3.8 Style 1 – annotated controllers

Good news: it looks almost exactly like Spring MVC. Same annotations, just reactive return types.

@RestController
@RequestMapping("/api/products")
public class ProductController {

    @GetMapping
    public Flux<Product> all() { return service.findAll(); }          // JSON array

    @GetMapping("/{id}")
    public Mono<Product> one(@PathVariable Long id) { return service.findById(id); }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Mono<Product> create(@RequestBody Product p) { return service.create(p); }
}

3.9 Style 2 – functional routes

The functional style separates routing (which URL goes where) from handling (what to do). Everything is plain Java code — no annotations on the handler methods. Some teams like it because all routes are visible in one place.

@Bean
public RouterFunction<ServerResponse> functionalRoutes(GreetingHandler handler) {
    return route(GET("/fn/hello"), handler::hello)
            .andRoute(GET("/fn/products"), handler::products);
}

// in GreetingHandler:
public Mono<ServerResponse> hello(ServerRequest request) {
    String name = request.queryParam("name").orElse("learner");
    return ServerResponse.ok().bodyValue("Hello, " + name + "!");
}

Familiar if you know Spring MVCRoutes are code: easy to compose, conditionally add, test
Uses @PathVariable, @RequestBodyUses request.pathVariable("id"), request.bodyToMono(X.class)

3.10 Server-Sent Events (SSE)

Normally HTTP is "one request → one response → connection closed". With Server-Sent Events the server keeps the response open and pushes events one by one. The browser has built-in support (new EventSource(url)). It is simpler than WebSockets when data only flows server → client.

@GetMapping(value = "/prices", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<PriceTick> prices() {
    return Flux.interval(Duration.ofSeconds(1))     // one item per second
            .map(seq -> new PriceTick(seq, "Laptop", randomPrice(), LocalTime.now()))
            .take(10);                               // then complete
}

On the wire every item looks like this (a blank line separates events):

data:{"sequence":0,"product":"Laptop","price":919.84,"time":"10:01:30"}

data:{"sequence":1,"product":"Laptop","price":883.82,"time":"10:01:31"}

Browser side (just for your information):

// JavaScript in a web page
const source = new EventSource("/api/stream/prices");
source.onmessage = e => console.log(JSON.parse(e.data));

3.11 WebClient – the reactive HTTP client

You met WebClient briefly in Topic 45. In a WebFlux app it is the way to call other services, because it does not block.

3.12 R2DBC – reactive SQL databases

JDBC (and so JPA/Hibernate) is blocking: the thread waits for the database. If you call JPA inside WebFlux, you freeze an event-loop thread — the whole point is lost. R2DBC (Reactive Relational Database Connectivity) is a non-blocking driver API for SQL databases (H2, PostgreSQL, MySQL, MariaDB, SQL Server, Oracle).

3.13 When NOT to use reactive

🚫 Do not go reactive just because it sounds modern
  • Your app uses JPA/Hibernate or other blocking libraries heavily → stay with Spring MVC. Mixing blocking calls into WebFlux is worse than plain MVC.
  • Simple CRUD apps with normal traffic → MVC is simpler to write, read, debug and test.
  • Your team is new to reactive → the learning curve (and stack traces!) is steep.
  • CPU-heavy work (image processing, big calculations) → reactive does not make the CPU faster.
  • Java 21+ virtual threads (newer Java) let blocking MVC code scale to many waiting requests too, with simpler code. Many teams now prefer that.
Good fits: gateways, streaming (SSE/WebSockets), services that mostly call many other services, very high numbers of concurrent, mostly-waiting connections.

3.14 Testing with StepVerifier

How do you test something that produces values later? StepVerifier (from reactor-test) subscribes for you and checks each signal in order:

StepVerifier.create(Flux.range(1, 6).filter(n -> n % 2 == 0).map(n -> n * n))
        .expectNext(4, 16, 36)   // exactly these items, in this order
        .verifyComplete();       // and then a completion signal

StepVerifier.create(Flux.just(10, 0).map(n -> 100 / n))
        .expectNext(10)
        .expectError(ArithmeticException.class)
        .verify();

Virtual time lets you test slow, time-based streams instantly:

StepVerifier.withVirtualTime(() -> Flux.interval(Duration.ofMinutes(20)).take(3))
        .expectSubscription()
        .thenAwait(Duration.ofHours(1))   // "fast forward" one hour - takes milliseconds
        .expectNext(0L, 1L, 2L)
        .verifyComplete();

For HTTP endpoints, WebTestClient is the reactive version of MockMvc (Topic 46).

4.4 The service – real operators in action

product/ProductService.javapublic Mono<Product> findById(Long id) {
    return repository.findById(id)
            .switchIfEmpty(Mono.error(
                    new ResponseStatusException(HttpStatus.NOT_FOUND, "Product " + id + " not found")));
}

public Mono<Void> delete(Long id) {
    return findById(id).flatMap(repository::delete);   // async step after async step
}

public Mono<Integer> stockFor(Long productId) {
    return Mono.just((int) (productId * 7 % 20))
            .delayElement(Duration.ofMillis(300));      // pretend slow remote call
}

public Mono<ProductDetails> details(Long id) {
    return Mono.zip(findById(id), stockFor(id))         // both run at the same time
            .map(tuple -> new ProductDetails(tuple.getT1(), tuple.getT2()));
}

Line by line:

  • repository.findById(id) returns an empty Mono when no row exists (not null, not an exception).
  • switchIfEmpty(Mono.error(...)) turns "empty" into an error. ResponseStatusException is understood by WebFlux and becomes a 404 response.
  • flatMap(repository::delete): delete returns Mono<Void> (async!), so we must use flatMap, not map.
  • Mono.zip subscribes to both Monos at once and gives a Tuple2 with getT1() and getT2().

4.5 The WebClient demo

client/CatalogClientController.java@GetMapping("/summary")
public Mono<CatalogSummary> summary() {
    return webClient.get()
            .uri("/api/products")
            .retrieve()
            .bodyToFlux(Product.class)
            .timeout(Duration.ofSeconds(3))
            .map(Product::getPrice)
            .collectList()                                  // Flux -> Mono<List>
            .map(prices -> new CatalogSummary(
                    prices.size(),
                    prices.stream().reduce(BigDecimal.ZERO, BigDecimal::add),
                    "via WebClient"))
            .onErrorResume(ex -> Mono.just(
                    new CatalogSummary(0, BigDecimal.ZERO, "fallback (catalog unavailable)")));
}

The WebClient calls our own /api/products endpoint, as if it were another microservice. That way the demo works offline. The base URL comes from app.webclient.base-url in WebClientConfig.

6. Common mistakes

🚫 Mistake: calling .block() inside a controller or service Product p = repository.findById(id).block(); freezes an event-loop thread. With only a few such threads, the whole server can stall. In WebFlux it even throws IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-2.
Fix: return the Mono and chain with map/flatMap. Use block() only in main methods or tests.
⚠️ Mistake: building a chain and never subscribing 
public Mono<Void> save(Product p) {
    repository.save(p);          // BUG: Mono created and thrown away - nothing is saved!
    return Mono.empty();
}
Fix: return repository.save(p).then(); — return the chain so WebFlux subscribes.
⚠️ Mistake: map with an async function .map(id -> repo.findById(id)) gives Flux<Mono<Product>> and the inner Monos never run.
Fix: use flatMap when the function returns a Mono/Flux.
⚠️ Mistake: using JPA / JDBC / RestTemplate inside WebFlux They are blocking. Your reactive app becomes slower than plain MVC.
Fix: use R2DBC (or reactive Mongo/Redis) and WebClient. If you really must call a blocking library, wrap it: Mono.fromCallable(() -> blockingCall()).subscribeOn(Schedulers.boundedElastic()).
⚠️ Mistake: try/catch around a Mono The error happens later, after your method has returned, so the catch never runs.
Fix: use onErrorResume, onErrorReturn, onErrorMap, doOnError.
⚠️ Mistake: both starter-web and starter-webflux in the pom Boot starts Tomcat + MVC, and you wonder why your app is not reactive.
Fix: keep only spring-boot-starter-webflux.
⚠️ Mistake: forgetting verify() in StepVerifier StepVerifier.create(flux).expectNext(1) without .verify()/.verifyComplete() checks nothing — the test is always green.
Fix: always end with a verify... call.
⚠️ Mistake: @Entity / jakarta.persistence.Id on R2DBC entities R2DBC ignores JPA annotations.
Fix: use org.springframework.data.annotation.Id and org.springframework.data.relational.core.mapping.Table.

7. Best practices

  • Choose the stack on purpose. Default to Spring MVC; choose WebFlux for streaming, gateways and high-concurrency I/O-bound services.
  • Be reactive end-to-end. Web layer, HTTP client, database driver — all non-blocking. One blocking call breaks the chain.
  • Never block on event-loop threads. If you must use a blocking library, isolate it with subscribeOn(Schedulers.boundedElastic()).
  • Always add timeout() to remote calls, and a fallback with onErrorResume where it makes sense.
  • Keep chains readable. Extract steps into small, well-named methods that return Mono/Flux. Avoid deeply nested flatMaps.
  • Log with doOnNext/doOnError, and use .log() or .checkpoint("name") while debugging to see signals.
  • Reuse one WebClient per target service (it is thread-safe), built from the Boot-provided WebClient.Builder.
  • Test with StepVerifier and use virtual time for time-based streams so tests stay fast.
  • Limit infinite streams (take, client disconnects) and think about backpressure for fast producers.

8. Key takeaways

  • Blocking code parks a thread while waiting; non-blocking code frees the thread and continues when data arrives.
  • Reactive Streams = Publisher, Subscriber, Subscription, Processor + backpressure (request(n)).
  • Mono = 0..1 item, Flux = 0..N items. Nothing happens until someone subscribes.
  • map for plain transformations, flatMap for async ones; zip combines; onErrorResume recovers.
  • WebFlux runs on Netty; controllers return Mono/Flux; functional routes are an alternative style.
  • produces = TEXT_EVENT_STREAM_VALUE + a Flux = Server-Sent Events.
  • WebClient is the non-blocking HTTP client; R2DBC is the non-blocking SQL access.
  • Never call block() in reactive code; never use JPA/JDBC in WebFlux.
  • Reactive is not always better — choose it for I/O-heavy, high-concurrency or streaming needs.
  • Test with StepVerifier (and WebTestClient for endpoints).

@GetMapping("/compare/{id1}/{id2}")
public Mono<String> compare(@PathVariable Long id1, @PathVariable Long id2) {

10. Interview questions

Q1. What is the difference between blocking and non-blocking I/O?

With blocking I/O the calling thread stops and waits until the operation finishes (e.g. a DB query), so it cannot do anything else. With non-blocking I/O the call returns immediately and the result is delivered later via a callback/event, so the thread can serve other work in the meantime. Non-blocking lets a few threads handle many concurrent connections.

Q2. What is the difference between Mono and Flux?

Both are Reactor implementations of the Reactive Streams Publisher. Mono emits at most one item (0..1) then completes or errors — like an async Optional. Flux emits 0..N items (possibly infinite) then completes or errors — like an async stream/list.

Q3. What is the difference between map and flatMap?

map applies a synchronous function, one item in → one item out. flatMap applies a function that returns a Publisher (Mono/Flux), subscribes to it and merges the results, so it is used for asynchronous steps such as database or HTTP calls. flatMap runs inner publishers concurrently and does not preserve order; concatMap does.

Q4. What is backpressure?

A mechanism where the subscriber controls how many items it wants via Subscription.request(n), so a fast producer cannot overwhelm a slow consumer. Reactor offers strategies such as limitRate, onBackpressureBuffer, onBackpressureDrop and onBackpressureLatest.

Q5. What does "nothing happens until you subscribe" mean?

Reactor publishers are lazy (cold). Operators only describe a pipeline. Execution starts on subscribe(). In WebFlux the framework subscribes to the Mono/Flux returned by a controller. A common bug is creating a Mono (e.g. repository.save(x)) and not returning/subscribing to it, so nothing runs.

Q6. Spring MVC vs Spring WebFlux — when would you choose each?

MVC: thread-per-request on a Servlet container, simple, huge ecosystem, works with JPA/JDBC — best default for most CRUD apps. WebFlux: event loop on Netty, non-blocking end-to-end, good for high concurrency with lots of waiting (calling many services), streaming (SSE/WebSocket) and gateways. Don't choose WebFlux if your dependencies are blocking or the team isn't experienced; with Java 21 virtual threads MVC can also scale well.

Q7. Why can't you use JPA in a WebFlux app, and what do you use instead?

JPA/Hibernate is built on JDBC, which is blocking; calling it on an event-loop thread blocks the loop and kills throughput. Use R2DBC (Spring Data R2DBC) for SQL databases, or reactive drivers for MongoDB/Redis/Cassandra. If unavoidable, wrap blocking calls with subscribeOn(Schedulers.boundedElastic()).

Q8. How do you handle errors in a reactive chain?

With error operators: onErrorResume (fallback publisher), onErrorReturn (fallback value), onErrorMap (translate exception), doOnError (side effect such as logging), retry/retryWhen. An error is a terminal signal — the original sequence ends. In WebFlux, @ExceptionHandler/@ControllerAdvice and ResponseStatusException also work.

Q9. How do you test reactive code?

With StepVerifier from reactor-test: StepVerifier.create(publisher).expectNext(...).expectError(...).verifyComplete(). For time-based operators use StepVerifier.withVirtualTime and thenAwait. For endpoints use WebTestClient. Always finish with a verify call.

Q10. What are Server-Sent Events and how do you implement them in WebFlux?

SSE is a standard where the server keeps an HTTP response open and pushes text events (data: ...) to the client; browsers support it via EventSource. In WebFlux you return a Flux from a handler with produces = MediaType.TEXT_EVENT_STREAM_VALUE (or Flux<ServerSentEvent<T>> for id/event name control). It is one-way (server → client); use WebSockets for two-way.
