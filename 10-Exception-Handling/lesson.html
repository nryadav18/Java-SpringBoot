10. Exception Handling

Make your programs survive bad input, missing files and broken networks — and when they do fail, fail with a clear message you can debug in minutes.

1. Why this matters

In a perfect world, users type correct data, files always exist, and databases never go down. In the real world:

  • A user types "abc" into the "quantity" box.
  • A customer tries to withdraw ₹5000 from an account holding ₹3000.
  • The database server restarts in the middle of an order.
  • A bug sends null where an object was expected.

Without exception handling, any of these crashes the whole program. On a web server that's a disaster: one bad request could stop service for everyone. Exception handling lets you:

  1. Separate the normal "happy path" code from the error-handling code.
  2. Recover where possible (ask again, retry, use a default).
  3. Report clearly where it isn't — a good message + a stack trace that points to the exact line.
  4. Clean up reliably (close files and connections) no matter what.
ℹ️ Where you'll see it at workIn Spring Boot you'll throw exceptions like ResourceNotFoundException from services, and a single @RestControllerAdvice class turns them into neat JSON errors with HTTP status 404 or 400 (Topic 35). Spring's @Transactional rolls back the database when an unchecked exception is thrown (Topic 42). Everything there builds on this lesson.

2. Real-life analogy

✈️ Think of a flight
  • The normal plan (the try block): board, take off, fly, land.
  • Something unexpected happens — an engine warning. The pilot "throws" an alert.
  • If the pilot can handle it (restart the engine), that's a catch right there.
  • If not, the alert goes up to air-traffic control — the problem propagates to someone who can deal with it.
  • No matter what happened — normal landing or emergency landing — the crew always opens the doors and lets passengers out. That's finally.
  • The black box recording exactly what happened, step by step, is the stack trace.
And checked vs unchecked? A checked exception is like bad weather: it's expected to happen sometimes, so the airline must have a plan (the compiler forces you). An unchecked exception is like the pilot forgetting to refuel — a mistake that should be fixed, not "handled".

3. Concepts step by step

3.1 What is an exception?

An exception is an object that Java creates and "throws" when something goes wrong while the program is running. The object carries information: what type of problem (its class), a message, and where it happened (the stack trace).

int pizzas = 10;
int friends = 0;
int each = pizzas / friends;   // Java creates an ArithmeticException object and THROWS it
System.out.println(each);      // never runs

If nobody catches it, the program stops and prints:

Exception in thread "main" java.lang.ArithmeticException: / by zero
	at Pizza.main(Pizza.java:4)

Four exceptions you will meet as a beginner:

ExceptionCauseExample
ArithmeticExceptionInteger division by zero10 / 0
ArrayIndexOutOfBoundsExceptionIndex outside the arraymarks[5] when length is 3
NullPointerException (NPE)Using a variable that points to nothingString s = null; s.length();
NumberFormatExceptionText isn't a valid numberInteger.parseInt("12a")
ℹ️ Compile-time errors are differentA missing semicolon is a compile error — the program never even starts. Exceptions happen at runtime, while the program is running, usually because of data or environment.

3.2 The Throwable hierarchy (family tree)

All exceptions are classes, organised with inheritance (Topic 7). At the top is Throwable — "anything that can be thrown".

BranchMeaningShould you catch it?
ErrorSerious JVM problems: out of memory, stack overflow.No. The program usually can't recover.
Exception (not Runtime)Checked: problems outside your control — file missing, network down.Yes, or declare with throws (compiler forces you).
RuntimeExceptionUnchecked: usually programming bugs or invalid arguments.Optional. Better: fix the bug / validate input.
💡 Why the hierarchy mattersA catch block catches the named class and all its children. catch (IOException e) also catches FileNotFoundException and NoSuchFileException because they extend IOException. That's polymorphism (Topic 8) at work.

3.3 Checked vs unchecked

This is the most-asked exception question in interviews, so let's make it crystal clear.

CheckedUnchecked
ExtendsException (but not RuntimeException)RuntimeException (or Error)
Checked byThe compiler — "checked" at compile timeNobody at compile time
Must handle?Yes: catch it or declare throwsNo
Typical causeOutside world: files, network, databaseBugs: null, bad index, bad argument
ExamplesIOException, SQLException, InterruptedExceptionNullPointerException, IllegalArgumentException, ArithmeticException

Try to read a file without handling the checked exception:

String text = Files.readString(Path.of("orders.txt"));   // readString is declared "throws IOException"
error: unreported exception IOException; must be caught or declared to be thrown

The compiler is saying: "this can fail for reasons outside your control. Tell me your plan."

ℹ️ The modern trendMany developers (and Spring itself) prefer unchecked exceptions for application errors, because checked exceptions force every method in between to write throws. Spring converts checked database exceptions (SQLException) into unchecked DataAccessException. You still need to understand both.

3.4 try / catch / finally

try {
    // risky code: the normal plan
} catch (SomeException e) {
    // runs ONLY if SomeException (or a child) was thrown in try
} finally {
    // ALWAYS runs: after success, after a catch, even after a return
}

How the flow works:

try starts→ exception at line X?→ yes → skip rest of try → matching catch→ finally→ code after
try starts→ no exception→ try finishes (catch skipped)→ finally→ code after

Example from Example02_TryCatchFinally.java — an ATM must always return your card:

try {
    System.out.println("try: start");
    if (amount > cashInAtm) {
        throw new IllegalStateException("Not enough cash in ATM");
    }
    System.out.println("try: dispensing Rs." + amount);   // skipped when the exception happens
} catch (IllegalStateException e) {
    System.out.println("catch: " + e.getMessage());
} finally {
    System.out.println("finally: card returned");          // always
}
  • A try must be followed by at least one catch or a finally (or be a try-with-resources).
  • Variables declared inside try { } are not visible in catch or finally (block scope, Topic 4).
  • After the exception is caught, the program continues normally after the whole try/catch/finally.

Useful methods on the exception object

MethodReturnsExample result
e.getMessage()The message text/ by zero
e.toString() (or just print e)Class name + messagejava.lang.ArithmeticException: / by zero
e.getClass().getSimpleName()Short class nameArithmeticException
e.getCause()The wrapped original exception (or null)see 3.9
e.printStackTrace()Prints the full stack trace to the error streamsee 3.10

3.5 Multiple catch blocks and multi-catch

One try can have several catch blocks. Java checks them top to bottom and runs the first match only. So: specific first, general last.

try {
    String[] parts = expression.split("/");
    int a = Integer.parseInt(parts[0]);
    int b = Integer.parseInt(parts[1]);
    return String.valueOf(a / b);
} catch (ArithmeticException e) {        // specific
    return "Cannot divide by zero";
} catch (NumberFormatException e) {      // specific
    return "Not a number";
} catch (RuntimeException e) {           // general "everything else" LAST
    return "Bad format, expected a/b";
}

If you put RuntimeException first, the compiler refuses: exception ArithmeticException has already been caught — the later blocks could never run.

Multi-catch (Java 7+) handles several unrelated types in one block with |:

} catch (NumberFormatException | ArrayIndexOutOfBoundsException e) {
    System.out.println("Input problem (" + e.getClass().getSimpleName() + ")");
}

Rule: the types in a multi-catch must not be parent and child of each other (that would be pointless).

3.6 finally — always runs (almost)

finally runs even if the try block executes return:

static String shopStatus() {
    try {
        return "OPEN";
    } finally {
        System.out.println("finally: closing the shop");   // printed BEFORE the caller receives "OPEN"
    }
}

The only ways to skip finally are System.exit() or the JVM itself dying (power cut, kill).

❌ Never return from finallyIt silently overrides the value returned by try and swallows any exception that was on its way out. Use finally only for clean-up.

3.7 try-with-resources

A resource is something you must close when done: a file, a database connection, a network socket. Forgetting to close leaks them, and eventually the system runs out (e.g. "too many open files", or the database refuses new connections).

The old way was long and easy to get wrong:

DbConnection conn = null;
try {
    conn = new DbConnection("DB-1");
    conn.query("SELECT * FROM orders");
} finally {
    if (conn != null) {      // the constructor itself might have failed
        conn.close();
    }
}

Java 7 added try-with-resources. Declare the resource in parentheses after try, and Java closes it for you:

try (DbConnection conn = new DbConnection("DB-2")) {
    conn.query("SELECT * FROM products");
}   // conn.close() is called automatically here — success OR failure
  • Works with any class that implements AutoCloseable (one method: close()). BufferedReader, FileWriter, Scanner, JDBC Connection... all do.
  • Several resources: separate with ;. They are closed in reverse order (last opened, first closed) — like stacking plates.
  • The resource is closed before any catch or finally block runs.
  • If both the body and close() throw, the body's exception is the main one; the close exception is attached as a suppressed exception (e.getSuppressed()). Nothing is lost.
class DbConnection implements AutoCloseable {
    @Override
    public void close() {
        System.out.println("[" + name + "] connection closed");
    }
}
💡 Rule of thumbIf a class has a close() method, open it in try-with-resources. Always.

3.8 throw vs throws

Two words that look alike but do different jobs:

What is it?A statement — an actionPart of a method signature — a warning label

Followed byOne exception object: throw new X("msg");One or more exception classes: throws IOException, SQLException

// throw: validate input and refuse bad data ("fail fast")
static void bookTicket(String name, int age, int seats) {
    if (age < 18) {
        throw new IllegalArgumentException("Age must be 18 or more for an A-rated movie, got " + age);
    }
    ...
}

// throws: this method doesn't handle the checked IOException; its caller must
static void paymentGateway() throws IOException {
    throw new IOException("Bank server not reachable");
}

Propagation — how an exception travels

When an exception is thrown, Java looks for a matching catch in the current method. If there isn't one, the method stops immediately and the exception moves to the caller, then the caller's caller... all the way up. If it reaches the top of main uncaught, the program crashes.

paymentGateway() throws↑ bookingCounter() — no catch, passes it up↑ main() — catch (IOException e) ✔

Standard JDK exceptions you should throw yourself (no need to invent new ones for these):

ExceptionThrow it when...
IllegalArgumentExceptionA method received a bad argument (negative amount, empty name).
IllegalStateExceptionThe object is in the wrong state for this call (order already shipped, ATM empty).
NullPointerException via Objects.requireNonNull(x, "x must not be null")A required argument is null.
UnsupportedOperationExceptionThe operation isn't supported (e.g. modifying an unmodifiable list).

3.9 Custom exceptions

Built-in names like IllegalStateException are generic. In business code, a specific name tells the story instantly: InsufficientBalanceException, AccountNotFoundException, OrderAlreadyShippedException.

Creating one is easy — extend Exception (checked) or RuntimeException (unchecked):

Example06_CustomExceptions.java// CHECKED: callers are forced to handle it
class InsufficientBalanceException extends Exception {
    private final double balance;
    private final double requested;

    InsufficientBalanceException(String accountNo, double balance, double requested) {
        super("Insufficient balance in " + accountNo + ": balance Rs." + balance + ", requested Rs." + requested);
        this.balance = balance;
        this.requested = requested;
    }

    double getShortfall() { return requested - balance; }   // extra info for the caller
}

// UNCHECKED: callers may handle it if they want
class AccountNotFoundException extends RuntimeException {
    AccountNotFoundException(String accountNo) {
        super("Account not found: " + accountNo);
    }
    AccountNotFoundException(String message, Throwable cause) {
        super(message, cause);
    }
}

Recipe:

  1. Name ends in Exception.
  2. Choose the parent: RuntimeException (most common today) or Exception.
  3. Call super(message) so getMessage() works. Add a (message, cause) constructor for chaining.
  4. Optionally add fields with extra details (amount, id) — they help the caller react.
ℹ️ serialVersionUID?If you compile with all warnings on (javac -Xlint:all) you'll see serializable class ... has no definition of serialVersionUID. Exceptions are "serializable" (they can be turned into bytes). You can add private static final long serialVersionUID = 1L; to silence it. It's only a warning — safe to ignore for now.

3.10 Exception chaining (wrapping)

Programs are built in layers. A low-level layer fails with a technical message ("connection refused on port 5432"); the caller of the service needs a business message ("Could not place order 42"). But developers debugging still need the technical reason. Solution: wrap the original exception as the cause of the new one.

try {
    repository.save(orderId);
} catch (IOException e) {
    throw new OrderProcessingException("Could not place order " + orderId, e);   // e = cause
}
IOException
"connection refused"→ wrapped in → OrderProcessingException
"Could not place order 42"

The stack trace now shows both, joined by "Caused by:". e.getCause() returns the inner exception.

❌ Losing the causethrow new OrderProcessingException("Could not place order") without e throws away the real reason. At 2 a.m., debugging a production issue, you'll have no idea what actually failed. Always pass the cause.

3.11 Reading a stack trace

A stack trace is the exception's "black box recording": the chain of method calls that were active when it was thrown. Here's real output from Example01_WhatIsAnException.java:

java.lang.ArithmeticException: / by zero                                              ← 1. WHAT happened
	at Example01_WhatIsAnException.splitBill(Example01_WhatIsAnException.java:97)        ← 2. WHERE it happened
	at Example01_WhatIsAnException.calculateShare(Example01_WhatIsAnException.java:102)  ← 3. who called it
	at Example01_WhatIsAnException.main(Example01_WhatIsAnException.java:79)             ← 4. ...who called that

How to read it, step by step:

  1. First line: exception type + message. Often enough to understand the problem.
  2. First "at" line: the exact method, file and line number where it was thrown. Open that line first.
  3. Lines below: the path of calls that led there, newest at top, oldest (main) at the bottom.
  4. Look for the first line that is your code (not java.base/... or library code) — the bug is usually there.
  5. If you see "Caused by:", scroll to the last "Caused by" — that's the root cause.
  6. ... 8 more means "the remaining lines are the same as in the trace above" — Java shortens repeats.
💡 In VS CodeFile names with line numbers in the terminal are clickable (Ctrl + click) and jump straight to the line.
ℹ️ Helpful NullPointerExceptionsSince Java 14 an NPE tells you which variable was null: Cannot invoke "String.length()" because "customerName" is null. Huge time saver.

try {
    String text = Files.readString(Path.of("missing-orders.txt"));

The actual exception is NoSuchFileException, a child of IOException, so catch (IOException e) catches it. The helper printKind uses instanceof RuntimeException to decide whether an exception is checked.

4.3 Example06 — the bank

void withdraw(double amount) throws InsufficientBalanceException {
    if (amount > balance) {
        throw new InsufficientBalanceException(number, balance, amount);
    }
    balance -= amount;
}

Account findAccount(String number) {
    for (Account a : accounts) {
        if (a.getNumber().equals(number)) return a;
    }
    throw new AccountNotFoundException(number);   // never return null
}

Notice findAccount throws instead of returning null. Returning null just moves the problem: the caller forgets to check and gets an NPE far away from the real cause. In transfer we look up both accounts before moving any money, so a missing account can't leave us with money withdrawn but not deposited. (Real databases solve this with transactions — Topic 42.)

6. Common mistakes

❌ Mistake: swallowing exceptions 
try {
    saveOrder();
} catch (Exception e) {
    // nothing here... 🙈
}
The error disappears silently, the order is not saved, and nobody knows why.
Fix: at minimum log it (later: a logger, Topic 30), or let it propagate. An empty catch is almost always a bug.
⚠️ Mistake: catching Exception (or Throwable) blindly catch (Exception e) also catches NPEs and other bugs you never intended to handle, hiding them.
Fix: catch the specific exceptions you can actually handle. Catch-all is OK only at the very top level (e.g. a global handler that logs and returns HTTP 500).
⚠️ Mistake: general catch before specific catch (Exception e) followed by catch (IOException e) → compile error exception IOException has already been caught.
Fix: specific first, general last.
⚠️ Mistake: using exceptions for normal flow try { return list.get(i); } catch (IndexOutOfBoundsException e) { return null; } instead of checking i < list.size().
Fix: exceptions are for exceptional situations. They're slower and make the code harder to read. Check conditions first.
⚠️ Mistake: losing the cause when wrapping throw new MyException("failed"); inside catch (IOException e).
Fix: throw new MyException("failed", e);
⚠️ Mistake: only printing e.getMessage() Some exceptions (like NPE in older Java) have a null message. You print "null" and learn nothing.
Fix: print/log the whole exception (e) or its stack trace.
⚠️ Mistake: forgetting to close resources Opening a BufferedReader or DB connection without closing it leaks it.
Fix: try-with-resources.
⚠️ Mistake: confusing throw and throws throws new Exception() or void m() throw IOException are syntax errors.
Fix: throw + object inside methods; throws + class names in signatures.

7. Best practices

  • Fail fast: validate arguments at the start of a method and throw IllegalArgumentException with a clear message (include the bad value!).
  • Catch only what you can handle. If you can't do anything useful, let it propagate.
  • Never swallow exceptions. Log them, rethrow, or wrap them — never ignore.
  • Specific over general: catch (NoSuchFileException e) > catch (IOException e) > catch (Exception e).
  • Use try-with-resources for everything closeable.
  • Wrap with cause when crossing layers (repository → service → controller).
  • Write meaningful custom exceptions for business rules (InsufficientBalanceException), usually unchecked in Spring apps.
  • Don't return null to signal "not found" — throw an exception or (Topic 14) return an Optional.
  • Handle in one place: in web apps, a global exception handler converts exceptions to HTTP responses. Don't sprinkle try/catch in every controller.
  • Never show stack traces to end users — they leak internal details (security risk). Log them for developers; show users a friendly message.
  • Use finally (or try-with-resources) for clean-up only — no return in finally.

8. Key takeaways

  • An exception is an object thrown at runtime when something goes wrong; uncaught, it crashes the thread.
  • Throwable → Error (don't catch) and Exception → RuntimeException (unchecked) + others (checked).
  • Checked = compiler forces catch-or-declare; unchecked = optional, usually bugs.
  • try / catch (specific first) / finally (always runs); multi-catch with |.
  • try-with-resources closes AutoCloseable objects automatically, in reverse order.
  • throw = throw an object now; throws = signature warning. Exceptions propagate up the call stack.
  • Custom exceptions: extend RuntimeException or Exception, pass message (and cause) to super.
  • Chain exceptions with a cause; read stack traces top-down, find your first line, and look for the last "Caused by".

9. Practice exercises

Easy

1. Safe division. Write safeDivide(int a, int b) that returns a / b, but prints "Cannot divide by zero" and returns 0 when b is 0. Use try/catch (not an if).

Hint / solution
public class SafeDivide {
    static int safeDivide(int a, int b) {
        try {
            return a / b;
        } catch (ArithmeticException e) {
            System.out.println("Cannot divide by zero");
            return 0;
        }
    }

    public static void main(String[] args) {
        System.out.println(safeDivide(10, 2));   // 5
        System.out.println(safeDivide(10, 0));   // Cannot divide by zero, then 0
    }
}

3. Age validator. Write static int parseAge(String text) that converts text to an int and throws IllegalArgumentException with a clear message if the text is not a number (keep the original exception as the cause) or if the age is outside 0–120. Test with "25", "abc", "150".

public class AgeValidator {
    static int parseAge(String text) {
        int age;
        try {
            age = Integer.parseInt(text.trim());
        } catch (NumberFormatException e) {
            throw new IllegalArgumentException("Age must be a number, got: '" + text + "'", e);
        }
        if (age < 0 || age > 120) {
            throw new IllegalArgumentException("Age must be 0-120, got: " + age);
        }
        return age;

        for (String in : inputs) {
            try {
                System.out.println("OK: " + parseAge(in));
            } catch (IllegalArgumentException e) {
                System.out.println("Invalid: " + e.getMessage());
            }
        }
    }
}

10. Interview questions

Q1. What is an exception? Exception vs Error?

An exception is an object representing an abnormal event during execution, which disrupts the normal flow. Both Exception and Error extend Throwable. Error represents serious JVM problems (OutOfMemoryError, StackOverflowError) that applications normally shouldn't catch; Exception represents conditions an application may want to handle.

Q2. Checked vs unchecked exceptions?

Checked exceptions (subclasses of Exception excluding RuntimeException) are verified by the compiler: you must catch them or declare them with throws (e.g. IOException, SQLException). Unchecked exceptions (RuntimeException and Error subclasses) aren't enforced (e.g. NPE, IllegalArgumentException) and usually indicate programming errors.

Q3. Difference between throw and throws?

throw is a statement that throws one exception instance: throw new IllegalStateException("..."). throws is in a method signature and declares the exception types the method may pass to its caller: void read() throws IOException.

Q4. Does finally always execute? Can try exist without catch?

Yes, finally runs whether or not an exception occurs, even after return — except when the JVM exits (System.exit, crash, kill). And yes: try may be followed only by finally, and try-with-resources may have neither catch nor finally.

Q5. What is try-with-resources and what is a suppressed exception?

A try statement that declares resources implementing AutoCloseable; they're closed automatically in reverse order at the end of the block. If the body throws and close() also throws, the close exception is added to the primary exception as suppressed, accessible via getSuppressed().

Q6. What happens if you catch a parent exception before a child exception?

Compile error: "exception X has already been caught", because the child catch block would be unreachable. Catch blocks must go from most specific to most general.

Q7. How do you create a custom exception? Checked or unchecked?

Extend Exception (checked) or RuntimeException (unchecked), provide constructors that call super(message) and super(message, cause), and optionally add fields. Use checked when the caller can reasonably recover and you want to force handling; most modern frameworks (Spring) favour unchecked exceptions for business errors, handled centrally.

Q8. What is exception chaining and why is it useful?

Wrapping a caught exception as the cause of a new, higher-level exception (new ServiceException("msg", e)). It lets each layer report in its own terms while preserving the root cause for debugging; stack traces show it as "Caused by:" and code can retrieve it with getCause().

Q9. final vs finally vs finalize?

final is a modifier (constant variable, non-overridable method, non-extendable class). finally is a block that always runs after try/catch. finalize() was a method called by the GC before reclaiming an object — deprecated since Java 9; use try-with-resources/Cleaner instead.

Q10. What are best practices for exception handling?

Catch specific exceptions; never swallow them; don't catch Exception/Throwable blindly; use try-with-resources; include context in messages; preserve causes when wrapping; don't use exceptions for control flow; fail fast with validation; handle them centrally in web apps and never expose stack traces to users.
