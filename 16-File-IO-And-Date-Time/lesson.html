1. Why this matters

Variables live in memory and vanish when the program stops. Files survive. In real projects you will constantly:

  • Import data — a bank uploads a CSV of transactions, HR uploads an Excel/CSV of new employees.
  • Export reports — monthly sales CSV, invoices, logs.
  • Read configuration — Spring Boot reads application.properties from a file at startup (topic 29).
  • Handle uploads and downloads — profile pictures, PDFs (topic 54).

And almost every business record has a date or time: when an order was placed, when a loan is due, when a user registered, when a token expires. Getting dates wrong causes real bugs: wrong interest, deliveries shown on the wrong day, tokens that expire in the wrong time zone. In Spring Data JPA (topic 38) your entities will have fields like:

private LocalDate dateOfBirth;
@CreationTimestamp
private LocalDateTime createdAt;
private Instant lastLoginAt;

This lesson gives you the solid foundation for both.

2. Real-life analogy

📮 Path = address, Files = the postman A Path is like an address written on an envelope: "output/notes.txt". Writing an address doesn't build a house — the file may or may not exist. Files is the postman who actually goes there and does things: delivers (write), picks up (read), checks if anyone lives there (exists), moves people (move), or demolishes (delete).
🪣 Buffered = carrying water in a bucket, not a spoon Reading a file one character at a time is like moving water with a spoon — every trip to the disk is slow. A buffer is a bucket: fetch a big chunk at once, then hand out characters from memory. That's what BufferedReader/BufferedWriter do.
🕰️ Wall clock vs world clock LocalDateTime is the time on your wall clock: "15 March, 10:00". Meaningless to someone in New York unless you say where it is. ZonedDateTime is the wall clock plus the city ("10:00 in Kolkata"). Instant is the single global timeline every clock agrees on — like a satellite's timestamp in UTC.

3. Concepts step by step

3.1 java.io vs java.nio.file

Java has two file APIs. You'll see both in real code:

java.io (Java 1.0, "classic")java.nio.file (Java 7+, "NIO.2", modern)
File/folder addressjava.io.Filejava.nio.file.Path
OperationsMethods on File + stream classesStatic helpers in Files
ErrorsMany methods return false silently (e.g. delete())Clear exceptions (NoSuchFileException…)
One-linersNo — you build reader chainsFiles.readString, Files.writeString, Files.lines
Use today?When an old API requires itYes — prefer this

Inside java.io there are two families:

  • Byte streams — InputStream/OutputStream (and FileInputStream…): raw bytes, for images, PDFs, any binary data.
  • Character streams — Reader/Writer (and FileReader, BufferedReader…): text, with a character encoding such as UTF-8.
ℹ️ What is a character encoding? Files store bytes; text is characters. An encoding is the rulebook that maps characters to bytes. UTF-8 is the worldwide standard and handles every language (₹, é, தமிழ், 中文). Always state it explicitly (StandardCharsets.UTF_8) so your program behaves the same on Windows, Linux and Mac.

3.2 Path — the address

Path outputDir = Path.of("output");                  // relative: from the current folder
Path notes     = outputDir.resolve("notes.txt");     // output/notes.txt  (join paths safely)
Path absolute  = Path.of("D:", "Java-SpringBoot");   // D:\Java-SpringBoot on Windows

notes.getParent();      // output
notes.toAbsolutePath(); // D:\Java-SpringBoot\16-File-IO-And-Date-Time\output\notes.txt

A relative path is resolved from the current working directory — the folder your terminal is in when you type java .... This is the #1 source of "file not found" confusion for beginners (see Mistakes).

💡 Separators Windows uses \, Linux/Mac use /. Path.of("output", "archive", "2026") and resolve(...) pick the right one for you. In Java strings, a single backslash must be written "\\" — another reason to let Path do the work.

3.4 try-with-resources — never leak a file handle

When a program opens a file, the operating system gives it a file handle. Handles are limited; and on Windows an open file can't be deleted or moved by others. So every opened file must be closed — even if an exception happens halfway.

try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String line;
    while ((line = reader.readLine()) != null) {   // null = end of file
        System.out.println(line);
    }
}   // reader.close() is called HERE automatically - success or exception

Any object implementing AutoCloseable can go in the try ( ... ) brackets. You can declare several, separated by ; — they're closed in reverse order. The Stream returned by Files.lines and Files.list is also AutoCloseable, so put it in try-with-resources too.

3.5 BufferedReader and BufferedWriter

File on disk→ FileReader (chars)→ BufferedReader (bucket + readLine)→ your code

The classic way wraps one class in another ("decorator" pattern): new BufferedReader(new FileReader(file, UTF_8)). The NIO shortcut gives the same thing in one call: Files.newBufferedReader(path, UTF_8).

  • reader.readLine() — next line without the newline, or null at the end.
  • reader.lines() — the rest of the file as a Stream<String>.
  • writer.write(text) + writer.newLine() — writes a platform-correct line break.

When to use which? For small files, Files.readAllLines/writeString are simplest. For large files or line-by-line processing, use Files.lines or a BufferedReader, which keep only a little in memory.

3.6 Reading CSV files

CSV (Comma-Separated Values) is a plain-text table: the first line is usually a header, each next line is a row, and values are separated by commas. Excel can open and save it.

id,name,department,marks,joinedOn
1,Asha,CSE,92,2024-07-15
2,Ravi,ECE,67,2024-07-20

The recipe:

  1. Read lines (readAllLines or Files.lines).
  2. Skip the header (i = 1 or .skip(1)) and blank lines.
  3. split(",") each line into columns; check the column count.
  4. Convert text to types: Integer.parseInt, Double.parseDouble, LocalDate.parse.
  5. Catch NumberFormatException/DateTimeParseException per row, record the error with the line number, and continue — one bad row shouldn't stop an import of 10,000 rows.
  6. Build objects (records) and process them (streams).
⚠️ Simple split has limits Real CSV can contain commas inside quotes ("Chennai, TN") or line breaks inside a value. split(",") can't handle those. In production use a library such as Apache Commons CSV or OpenCSV. Also note: "a,b,".split(",") drops the empty last value — use split(",", -1) to keep it (see Example07).

3.7 Serialization — and why JSON is used instead

Serialization = converting an object into a sequence of bytes, so it can be saved to a file or sent over a network. Deserialization = rebuilding the object from those bytes.

Java object→ serialize →bytes (file / network)→ deserialize →Java object (new copy)

Java's built-in way:

class UserAccount implements Serializable {        // marker interface, no methods
    private static final long serialVersionUID = 1L;
    private String username;
    private transient String password;              // transient = NOT saved
}

try (ObjectOutputStream out = new ObjectOutputStream(Files.newOutputStream(file))) {
    out.writeObject(user);
}
try (ObjectInputStream in = new ObjectInputStream(Files.newInputStream(file))) {
    UserAccount loaded = (UserAccount) in.readObject();
}
  • Serializable is a marker interface — no methods; it just gives permission.
  • serialVersionUID is a version number. If the class changes and the numbers don't match, reading old data fails with InvalidClassException.
  • transient fields are skipped (they come back as null/0) — good for passwords or values you can recalculate.
Java serializationJSON
Binary, not human-readableText — you can read and edit it
Only Java can read itEvery language: JavaScript, Python, Kotlin, Swift…
Breaks easily when classes changeTolerant: extra/missing fields can be ignored
Known security risk: deserializing untrusted bytes can run malicious codeJust data — much safer to parse
Used by: old RMI, some caches/sessionsUsed by: REST APIs, config, messaging (Kafka, RabbitMQ), NoSQL

That's why Spring Boot REST APIs send and receive JSON. The Jackson library (included with spring-boot-starter-web) converts your objects/records to JSON and back automatically — you'll see it in topic 31. Learn what serialization is (interviews love it), but don't use Java serialization in new code.

3.8 Why java.time? (The old Date/Calendar problem)

Before Java 8, Java had java.util.Date and Calendar. They were famously bad: mutable (anyone could change your date), months counted from 0 (January = 0!), confusing time-zone handling, and not thread-safe formatters. In Java 8, java.time fixed all of this. Rule: always use java.time; only convert to Date when an old library forces you to.

All java.time classes are immutable and thread-safe: methods like plusDays return a new object.

LocalDate d = LocalDate.of(2026, 3, 15);
d.plusDays(14);              // ❌ result thrown away - d is still 15 March!
d = d.plusDays(14);          // ✅ keep the new object

💡 Time zone IDs Use region IDs like Asia/Kolkata, Europe/London, America/New_York — not fixed offsets like +05:30. Regions know about daylight-saving time changes; fixed offsets don't.

3.10 Period, Duration and ChronoUnit

Period age = Period.between(LocalDate.of(1998, 8, 20), LocalDate.of(2026, 3, 15));
age.getYears();   // 27   (age.toString() = "P27Y6M23D")

Duration worked = Duration.between(LocalTime.of(9, 15), LocalTime.of(18, 40));
worked.toHours();        // 9
worked.toMinutesPart();  // 25   (worked.toString() = "PT9H25M")

ChronoUnit.DAYS.between(LocalDate.of(2026, 3, 15), LocalDate.of(2026, 5, 4));   // 50
  • Period = calendar amounts ("2 months"). A month isn't a fixed number of days, so Period is about dates.
  • Duration = exact time amounts ("90 minutes"). Used for timeouts, e.g. Spring's spring.mvc.async.request-timeout=30s or JWT expiry in topic 49.
  • ChronoUnit.X.between(a, b) = total count of one unit (total days, total hours).
  • The strings like P27Y6M23D and PT9H25M are the ISO-8601 format: P = period, T = time part.

3.11 DateTimeFormatter — dates ↔ text

By default, toString() and parse() use the international ISO format (2026-03-15, 2026-03-15T16:05) — and that's what JSON APIs should use. For screens, reports and user input you choose a pattern:

yyyy (or uuuu)year2026
MM / MMM / MMMMmonth number / short name / full name03 / Mar / March
dd / dday of month (2 digits / no padding)05 / 5

DateTimeFormatter indian = DateTimeFormatter.ofPattern("dd-MM-yyyy");
meeting.format(DateTimeFormatter.ofPattern("dd/MM/yyyy HH:mm"));   // 15/03/2026 16:05
LocalDate d = LocalDate.parse("05-09-2026", indian);               // 2026-09-05
LocalDate.parse("2026/01/10", indian);                             // DateTimeParseException
🚫 MM vs mm MM = month, mm = minutes. "dd-mm-yyyy" is a classic bug that prints minutes where the month should be. Similarly HH (24h) vs hh (12h).
ℹ️ "31-04-2026" was accepted? By default, parsing is smart: an impossible day like 31 April is adjusted to 30 April (Example06 shows this). To reject it, use strict parsing: DateTimeFormatter.ofPattern("dd-MM-uuuu").withResolverStyle(ResolverStyle.STRICT) (note uuuu instead of yyyy in strict mode).

Day/month names depend on the language, so pass a Locale (Locale.ENGLISH) when you use MMM/EEE, otherwise output changes with the computer's language settings.

3.12 java.time in Spring (preview)

  • JPA entities map LocalDate → SQL DATE, LocalDateTime → TIMESTAMP, Instant → TIMESTAMP (WITH TIME ZONE) automatically (topic 38).
  • Jackson writes them to JSON as ISO strings: "createdAt": "2026-03-15T18:45:00"; customise with @JsonFormat(pattern = "dd-MM-yyyy") (topic 32).
  • Validation: @Past LocalDate dateOfBirth, @Future LocalDate deliveryDate (topic 34).
  • Testing: inject a Clock and use LocalDate.now(clock) so tests can fix "today" — the same idea as the fixed report date in Example07.

6. Common mistakes

⚠️ Mistake: "NoSuchFileException: students.csv" although the file is there Relative paths are resolved from the current working directory, not from where the .java file is. If your terminal is in D:\Java-SpringBoot, Java looks for D:\Java-SpringBoot\students.csv.
Fix: cd into the topic folder first, print Path.of("").toAbsolutePath() to see where Java is looking, or use a fallback like findInputFile in Example03.
⚠️ Mistake: not closing files / streams 
Stream<String> lines = Files.lines(path);   // file stays open!
long n = lines.count();
Fix: always try (Stream<String> lines = Files.lines(path)) { ... }. Same for readers, writers, input/output streams.
⚠️ Mistake: forgetting the encoding Old constructors like new FileReader("a.txt") (without charset) use the computer's default encoding, so "₹" or "é" can turn into garbage on another machine. Fix: pass StandardCharsets.UTF_8 everywhere.
⚠️ Mistake: overwriting when you meant to append Files.writeString(log, line) replaces the file each time. Fix: add StandardOpenOption.CREATE, StandardOpenOption.APPEND.
⚠️ Mistake: readAllLines on a 5 GB file Loads everything into memory → OutOfMemoryError. Fix: process line by line with Files.lines or BufferedReader.
🚫 Mistake: swallowing IOException catch (IOException e) { } hides real problems (disk full, no permission). Fix: log it with a helpful message, or rethrow as an unchecked exception (throw new UncheckedIOException(e)).
⚠️ Mistake: ignoring the result of a date method date.plusDays(1); does nothing to date — java.time objects are immutable. Fix: date = date.plusDays(1);
⚠️ Mistake: wrong pattern letters "dd-mm-yyyy" (minutes!), "YYYY" (week-based year — wrong around New Year), "hh" without a. Fix: "dd-MM-yyyy", "HH:mm", and test with dates near 31 December.
⚠️ Mistake: using LocalDateTime for global events "Sale ends at 2026-03-15T23:59" — in which country? Fix: store moments as Instant (or ZonedDateTime/OffsetDateTime) and convert to the user's zone only for display.
⚠️ Mistake: using new Date(), Calendar or SimpleDateFormat in new code Mutable, confusing (January = 0) and SimpleDateFormat isn't thread-safe — a real problem in multi-threaded web servers. Fix: java.time + DateTimeFormatter (immutable and thread-safe — keep one as a static final constant).

7. Best practices

  • Prefer Path + Files over java.io.File in new code.
  • Always use try-with-resources for anything you open, including Files.lines/Files.list streams.
  • Always specify UTF-8 explicitly.
  • Stream big files line by line; use readAllLines/readString only for small ones.
  • Validate input files row by row, collect errors with line numbers, and report them — don't stop at the first bad row (unless the business requires all-or-nothing).
  • Use a CSV library (Apache Commons CSV, OpenCSV) for real-world CSV with quotes and commas.
  • Never deserialize untrusted data with ObjectInputStream. Use JSON for data exchange.
  • Never trust user-supplied file names — ../../windows/system32 is a "path traversal" attack (topic 54 shows how to sanitize).
  • Store timestamps as Instant/UTC, convert to local zones only for display. Use LocalDate for pure dates (birthdays).
  • Use ISO-8601 (2026-03-15T16:05:00Z) in APIs, logs and files; custom patterns only for humans.
  • Make "now" injectable (a Clock or a parameter) so code that depends on today's date can be tested.
  • Keep formatters as constants: static final DateTimeFormatter DATE_FORMAT = ....

8. Key takeaways

  • Path is an address; Files does the work (readAllLines, readString, writeString, lines, copy, move, delete).
  • File operations throw the checked IOException; handle it properly.
  • try-with-resources guarantees files are closed — always use it.
  • BufferedReader.readLine() returns null at end of file; buffering makes I/O fast.
  • CSV import = read lines → skip header → split → convert → collect errors → build objects.
  • Serialization turns objects into bytes (Serializable, transient, serialVersionUID), but JSON is the modern, safe, cross-language choice.
  • Use java.time: LocalDate/LocalTime/LocalDateTime for wall-clock values, ZonedDateTime for zones, Instant for machine timestamps.
  • Period = years/months/days, Duration = hours/minutes/seconds, ChronoUnit.DAYS.between = total count.
  • java.time objects are immutable — keep the returned value.
  • DateTimeFormatter.ofPattern("dd-MM-yyyy") formats and parses; MM = month, mm = minutes.

10. Interview questions

Q1. What is the difference between java.io and java.nio.file?

java.io is the original stream-based API (File, FileInputStream, BufferedReader…); many File methods report failure by returning false. java.nio.file (Java 7, "NIO.2") introduced Path and the Files utility class with clearer exceptions, symbolic-link and attribute support, directory walking, and convenient one-liners (readAllLines, readString, lines). New code should prefer NIO.2; the two interoperate via file.toPath() and path.toFile().

Q2. Byte streams vs character streams?

Byte streams (InputStream/OutputStream) handle raw 8-bit bytes — for binary data like images or PDFs. Character streams (Reader/Writer) handle text and apply a character encoding (e.g. UTF-8). InputStreamReader bridges bytes to characters.

Q3. Why use BufferedReader/BufferedWriter?

They keep an in-memory buffer, so the program reads/writes large chunks instead of hitting the disk for every character — dramatically fewer system calls and better performance. BufferedReader also adds readLine() and lines(); BufferedWriter adds newLine().

Q4. What is try-with-resources and why is it important for I/O?

A try (Resource r = ...) { } statement (Java 7) that automatically calls close() on every declared AutoCloseable resource when the block exits, normally or via exception, in reverse order of declaration. Exceptions thrown by close() are attached as "suppressed" exceptions. It prevents file-handle leaks and locked files.

Q5. Files.readAllLines vs Files.lines?

readAllLines eagerly loads the whole file into a List<String> — simple, but memory-heavy for big files. lines returns a lazily populated Stream<String> that reads as you consume it, suitable for large files; it holds an open file handle and must be closed (try-with-resources).

Q6. What is serialization? What are transient and serialVersionUID?

Serialization converts an object graph into a byte stream (ObjectOutputStream.writeObject) and deserialization reconstructs it (ObjectInputStream.readObject); the class must implement the marker interface Serializable. transient fields are excluded and come back with default values. serialVersionUID is a version identifier checked on deserialization; a mismatch throws InvalidClassException. Declare it explicitly to control compatibility.

Q7. Why do modern systems prefer JSON over Java serialization?

JSON is human-readable, language-independent, tolerant of schema changes, and safe to parse. Java native serialization is Java-only, brittle across class changes, and deserializing untrusted data is a well-known remote-code-execution risk. Spring Boot uses Jackson to map objects to JSON for REST APIs and messaging.

Q8. LocalDateTime vs ZonedDateTime vs Instant — when to use each?

LocalDateTime: a date-time with no zone — a "wall clock" value, fine when everything happens in one known zone or for user-entered values. ZonedDateTime: date-time plus a region zone — correct for scheduling across zones and handling daylight-saving rules. Instant: an exact point on the UTC timeline — best for machine timestamps (logs, audit columns, token expiry). A common practice: store Instant/UTC, display in the user's zone.

Q9. Period vs Duration?

Period is a date-based amount in years, months and days (e.g. age, "add 1 month" respecting month lengths). Duration is a time-based amount in seconds and nanoseconds (shown as hours/minutes), e.g. timeouts, elapsed time. Use ChronoUnit.X.between for a total count of a single unit.

Q10. Why was java.time introduced? What was wrong with Date and Calendar?

Date/Calendar are mutable (not thread-safe, easy to corrupt), have confusing APIs (0-based months, Date years offset from 1900), mix date and time concepts, and SimpleDateFormat isn't thread-safe. java.time (JSR-310, Java 8) provides immutable, thread-safe, clearly separated types (LocalDate, Instant, ZonedDateTime…), fluent arithmetic, proper time-zone support and the thread-safe DateTimeFormatter.
