1. Why this matters

Imagine a mobile app screen that shows a list of book titles with the author's name. With a typical REST API you might do this:

  1. GET /api/books → returns every field of every book (description, ISBN, price, stock, ...). The phone only needed the title. This is over-fetching: downloading data you throw away.
  2. For each book, GET /api/authors/{id} to get the author's name. 20 books = 20 extra calls. This is under-fetching: one endpoint does not give enough, so you make many round trips.

GraphQL (created at Facebook in 2012, open-sourced in 2015) solves both. The client sends one request that describes exactly the shape of data it wants, and the server returns exactly that shape:

query {
  books {
    title
    author { name }
  }
}

Where you will see it at work: GitHub's public API v4, Shopify, Netflix, Airbnb, and many companies with several front-ends (web, Android, iOS) that each need different data from the same backend. A "Backend For Frontend" or API aggregation layer is often GraphQL.

2. Real-life analogy

🍱 Fixed thali vs. à-la-carte ordering

REST is like a fixed thali (set meal). Each counter (endpoint) gives you a fixed plate. Want rice and dal? The "lunch" counter gives you rice, dal, sabzi, roti, salad and sweet — you leave half of it (over-fetching). Want dessert from another restaurant's menu too? Walk to another counter and queue again (under-fetching, many round trips).

GraphQL is like ordering à la carte from one waiter. You hand one order slip: "rice, dal, and the chef's name". The waiter (the single /graphql endpoint) goes to the right kitchen stations (resolvers) and brings back one tray with exactly what you wrote — nothing more.

The menu is the schema: you can only order what is on it, and the waiter rejects an order for something that isn't (a validation error).

3.2 The schema – the menu of your API

In GraphQL you start with the schema (this is called "schema-first"). It is written in SDL (Schema Definition Language) in a file ending with .graphqls. Spring Boot loads every *.graphqls file from src/main/resources/graphql/.

    bookById(id: ID!): Book
}

type Book {
    id: ID!
    title: String!
    pages: Int!
    author: Author!
}

type Author {
    id: ID!
    name: String!
    books: [Book!]!
}

    title: String!
    pages: Int!
    authorId: ID!
}

There is also a third root type, Subscription, for real-time updates over WebSocket. We will only mention it.

3.3 Writing queries (the client side)

A query mirrors the schema. You pick fields, and you can go as deep as relationships allow:

# Simple
{ books { title } }

# With an argument and nested object
query {
  bookById(id: 1) {
    title
    pages
    author { name country }
  }
}

# Mutation (write)
mutation {
  addBook(input: { title: "Spring Boot Up and Running", pages: 300, authorId: 3 }) {
    id
    title
  }
}

Over HTTP, every query is a JSON POST to /graphql:

POST /graphql
Content-Type: application/json

{ "query": "{ bookById(id: 1) { title pages } }" }

The response always has a data key with exactly the requested shape:

{ "data": { "bookById": { "title": "Effective Java", "pages": 412 } } }

Variables keep the query text constant and pass values separately (safer and cacheable — like a PreparedStatement in Topic 19):

{
  "query": "mutation AddBook($input: BookInput!) { addBook(input: $input) { id title } }",
  "variables": { "input": { "title": "Spring Boot Up and Running", "pages": 300, "authorId": 3 } }
}

3.4 How Spring answers a query – resolvers

The server answers a query field by field. For each field there is a small function called a resolver (graphql-java calls it a DataFetcher). Spring for GraphQL lets you write resolvers as annotated controller methods.

POST /graphql→ Parse & validate
against the schema→ Query.books
@QueryMapping→ Book.author (for each book)
@BatchMapping→ JSON {"data": ...}

Simple fields like title need no resolver: Spring reads them from your object automatically (record component, getter or field with the same name).

AnnotationResolvesExample
@QueryMappingA field of type Query. The method name = field name.public List<Book> books()
@MutationMappingA field of type Mutationpublic Book addBook(@Argument BookInput input)
@SchemaMappingA field of any type (the general form). @QueryMapping is a shortcut for @SchemaMapping(typeName="Query").@SchemaMapping(typeName="Author", field="books")
@BatchMappingA field for many parent objects at once (N+1 fix)public Map<Book, Author> author(List<Book> books)
@ArgumentBinds one GraphQL argument to a parameter (with type conversion)bookById(@Argument Long id)
@ControllerMarks the class (not @RestController!)

3.5 Nested fields with @SchemaMapping

Our Author record has no books field, but the schema says Author.books. So Spring looks for a resolver. The parent object (the source) is passed as a parameter:

@SchemaMapping(typeName = "Author", field = "books")
public List<Book> books(Author author) {          // author = the parent object
    return repository.findBooksByAuthorId(author.id());
}

Important: this method runs only if the client asks for books inside an author. If they don't, no work is done. That is another win over REST.

3.6 The N+1 problem and @BatchMapping

You met N+1 with JPA in Topic 40. GraphQL has the same trap. Suppose we resolve Book.author the naive way:

// NAIVE - called once PER BOOK
@SchemaMapping(typeName = "Book", field = "author")
public Author author(Book book) {
    return repository.findAuthorById(book.authorId()).orElseThrow();
}

Query { books { title author { name } } } with 100 books runs 1 query for the books + 100 author queries = N+1.

books() → 1 query→ author(book1) → query
author(book2) → query
... × N

@BatchMapping collects all the books first and calls your method once with the whole list. You load all authors in one go (WHERE id IN (...)) and return a Map from each book to its author:

@BatchMapping                                     // field name = method name "author", type = Book
public Map<Book, Author> author(List<Book> books) {
    List<Long> ids = books.stream().map(Book::authorId).toList();
    Map<Long, Author> byId = repository.findAuthorsByIds(ids).stream()
            .collect(Collectors.toMap(Author::id, Function.identity()));
    return books.stream()
            .collect(Collectors.toMap(Function.identity(), b -> byId.get(b.authorId())));
}
books() → 1 query→ author(all books) → 1 query= 2 queries total
ℹ️ Behind the scenes: DataLoader@BatchMapping is built on graphql-java's DataLoader, which collects keys during a request and loads them in batches (and caches within the request). @BatchMapping is the easy way; you can register a BatchLoaderRegistry for full control. The parent type (Book) must have proper equals/hashCode — records give you that for free.

3.7 Error handling

In GraphQL, the HTTP status is almost always 200, even when something fails. Errors go into an errors array next to data:

{
  "errors": [{
    "message": "Book 99 does not exist",
    "locations": [{ "line": 1, "column": 12 }],
    "path": ["deleteBook"],
    "extensions": { "classification": "NOT_FOUND" }
  }],
  "data": null
}

Kinds of errors:

KindWhenClassification
Syntax / validationBad query text or unknown field ({ books { isbn } }) — rejected before any resolver runsInvalidSyntax, ValidationError
Your exceptions, mappedA resolver throws and you map itNOT_FOUND, BAD_REQUEST, UNAUTHORIZED, FORBIDDEN
Unmapped exceptionsAnything else thrown in a resolverINTERNAL_ERROR with a generic message (no stack trace leaks)

To map your own exceptions, use @GraphQlExceptionHandler in a @ControllerAdvice — the GraphQL twin of @ExceptionHandler from Topic 35:

@ControllerAdvice
public class GraphQlErrorHandler {

    @GraphQlExceptionHandler
    public GraphQLError handleNotFound(BookNotFoundException ex, DataFetchingEnvironment env) {
        return GraphqlErrorBuilder.newError(env)     // adds path + locations
                .errorType(ErrorType.NOT_FOUND)
                .message(ex.getMessage())
                .build();
    }
}

GraphQL also supports partial results: if one field fails, the other fields can still return data, and the failing field becomes null with an entry in errors.

3.8 GraphiQL – the playground in your browser

With spring.graphql.graphiql.enabled=true, open http://localhost:8080/graphiql. You get an editor with auto-complete (press Ctrl+Space), a documentation explorer built from your schema, and a Run button. GraphQL APIs are self-describing because clients can ask the server for its schema (this is called introspection).

⚠️ Production noteDisable GraphiQL in production (use a profile), and consider limiting introspection and query depth so attackers cannot send huge, deeply nested queries.

4.4 The controller – queries and mutations

library/BookController.java (queries & mutations)@Controller
public class BookController {

    @QueryMapping                                     // schema: books: [Book!]!
    public List<Book> books() {
        return repository.findAllBooks();
    }

    @QueryMapping                                     // schema: bookById(id: ID!): Book
    public Book bookById(@Argument Long id) {         // "1" (ID) converted to Long
        return repository.findBookById(id).orElse(null);   // null is OK: Book has no "!"
    }

    @MutationMapping                                  // schema: addBook(input: BookInput!): Book!
    public Book addBook(@Argument BookInput input) {
        if (input.pages() <= 0) {
            throw new IllegalArgumentException("pages must be greater than 0");
        }
        repository.findAuthorById(input.authorId())
                .orElseThrow(() -> new BookNotFoundException("Author " + input.authorId() + " does not exist"));
        return repository.save(new Book(null, input.title(), input.pages(), input.authorId()));
    }

    @MutationMapping                                  // schema: deleteBook(id: ID!): Boolean!
    public boolean deleteBook(@Argument Long id) {
        if (!repository.deleteBook(id)) {
            throw new BookNotFoundException("Book " + id + " does not exist");
        }
        return true;
    }
}

Notice how method names match schema field names. If the names differ, use @QueryMapping(name = "bookById"). At startup Spring Boot checks that schema fields have resolvers and logs a schema mapping inspection report listing any unmapped fields — read it when something returns null unexpectedly.

6. Common mistakes

⚠️ Mistake: method name does not match the schema field Schema says bookById, Java method is getBook. The field always returns null and the startup log reports it as unmapped.
Fix: rename the method or use @QueryMapping(name = "bookById"). Check the "schema mapping inspection" log at startup.
⚠️ Mistake: schema file in the wrong place or with the wrong extension A file named schema.graphql in src/main/resources/ is ignored, and the app fails with "No GraphQL schema files found".
Fix: put it in src/main/resources/graphql/ and name it *.graphqls (or *.gqls).
⚠️ Mistake: forgetting @Argument public Book bookById(Long id) — Spring does not know that id is a GraphQL argument, and startup fails or the value is missing.
Fix: public Book bookById(@Argument Long id).
⚠️ Mistake: using @RestController GraphQL controllers are annotated with @Controller. A @RestController with @QueryMapping methods still works, but it confuses readers and can mix in MVC behavior.
Fix: use plain @Controller.
⚠️ Mistake: returning null for a non-null (!) field If books: [Book!]! resolves to null, GraphQL reports an error and nulls the parent ("null bubbling").
Fix: return an empty list instead of null; only make fields non-null when they truly always have a value.
🚫 Mistake: resolving relations one by one (N+1) A @SchemaMapping that hits the database per parent object becomes very slow with long lists.
Fix: use @BatchMapping (or a DataLoader) for any field that loads related data.
⚠️ Mistake: expecting HTTP 404/400 status codes GraphQL answers 200 with an errors array. Front-end code that only checks the status will think everything worked.
Fix: always check the errors field in the response.

7. Best practices

  • Design the schema first, together with front-end developers. It is your API contract.
  • Use input types for mutations and return the changed object so the client can update its view.
  • Use variables in client queries instead of building query strings by hand.
  • Batch every relationship with @BatchMapping/DataLoader to avoid N+1.
  • Paginate lists (e.g. arguments first/after or page/size; Spring for GraphQL supports the "Connection" pagination pattern with Spring Data).
  • Protect the server: limit query depth/complexity, set timeouts, disable GraphiQL and restrict introspection in production.
  • Secure resolvers with Spring Security method security (@PreAuthorize works on controller methods, Topic 48).
  • Evolve, don't version: add new fields freely, mark old ones @deprecated(reason: "...") and remove them later.
  • Map exceptions to clear error types; never leak stack traces.
  • Keep business logic in services; the GraphQL controller should be thin, just like a REST controller (Topic 33).

8. Key takeaways

  • GraphQL = one endpoint (/graphql) where the client asks for exactly the fields it needs.
  • It fixes REST's over-fetching (too much data) and under-fetching (too many calls).
  • The schema (.graphqls) defines types, Query, Mutation and inputs; ! means non-null.
  • Spring for GraphQL maps fields to methods: @QueryMapping, @MutationMapping, @SchemaMapping, with @Argument for arguments.
  • Nested fields are resolved only when requested.
  • @BatchMapping solves the N+1 problem by loading related data for all parents at once.
  • Errors come back in an errors array (usually with HTTP 200); map them with @GraphQlExceptionHandler.
  • GraphiQL (/graphiql) is a great playground; disable it in production.
  • Test with @GraphQlTest + GraphQlTester.

@BatchMapping(typeName = "Author", field = "books")
public Map<Author, List<Book>> booksOfAuthors(List<Author> authors) {

Hint / solution
@QueryMapping
public List<Book> books(@Argument int page, @Argument int size) {
    if (size > 50) {
        throw new IllegalArgumentException("size must be 50 or less");  // mapped to BAD_REQUEST
    }
    return repository.findAllBooks().stream()
            .skip((long) page * size)
            .limit(size)
            .toList();
}

Default values in the schema (= 0, = 10) are used when the client leaves the arguments out.

10. Interview questions

Q1. What is GraphQL and how is it different from REST?

GraphQL is a query language and runtime for APIs. Clients send queries to a single endpoint describing exactly which fields they need, and the server returns data in that shape, validated against a strongly typed schema. REST exposes many resource URLs with server-defined response shapes and uses HTTP methods and status codes. GraphQL reduces over- and under-fetching but makes HTTP caching, file uploads and rate limiting harder.

Q2. What are over-fetching and under-fetching?

Over-fetching: an endpoint returns more data than the client needs (wasted bandwidth). Under-fetching: one endpoint returns too little, so the client must make extra requests (more round trips, often N+1 calls). GraphQL lets the client request exactly the fields and nested data it needs in one call.

Q3. What are Query, Mutation and Subscription?

They are the three root operation types. Query reads data (fields may run in parallel), Mutation changes data (top-level fields run in order), and Subscription pushes a stream of events to the client, usually over WebSocket.

Q4. What is a resolver, and how do you write one in Spring?

A resolver (DataFetcher) is a function that produces the value for one field. In Spring for GraphQL you write them as methods in a @Controller annotated with @QueryMapping, @MutationMapping, @SubscriptionMapping, @SchemaMapping or @BatchMapping; arguments are bound with @Argument, and the parent object is passed for nested fields. Simple fields are resolved from properties automatically.

Q5. Explain the N+1 problem in GraphQL and how to fix it.

When a list of N parents is returned and a nested field is resolved per parent with its own data-store call, you get 1 + N calls. Fix it with batching: the DataLoader pattern collects all keys during execution and loads them in one call. In Spring, @BatchMapping receives the list of parents and returns a Map<Parent, Child> (or a Mono<Map>/Flux).

Q6. How are errors returned in GraphQL?

Usually with HTTP 200 and an errors array containing message, locations, path and extensions (e.g. a classification). Partial data may be returned alongside errors. In Spring you map exceptions with @GraphQlExceptionHandler in a @ControllerAdvice or a DataFetcherExceptionResolverAdapter; unmapped exceptions become INTERNAL_ERROR without details.

Q7. What does "!" mean in a schema, and what is the difference between type and input?

! marks a non-null field or argument. [Book!]! is a non-null list of non-null books. A type describes output objects that resolvers return; an input describes objects passed as arguments. Inputs cannot have resolvers or fields of output types.

Q8. How do you test a Spring GraphQL controller?

Use @GraphQlTest(MyController.class) to start only the GraphQL slice and inject GraphQlTester; send a document, then assert with .path("...").entity(...) or .errors(). Mock or @Import dependencies. For full end-to-end tests use @SpringBootTest with @AutoConfigureHttpGraphQlTester.

Q9. What are the security concerns specific to GraphQL?

Clients can craft very deep or expensive queries (denial of service), introspection exposes the full schema, and a single endpoint makes per-URL authorization and rate limiting less useful. Mitigations: max query depth/complexity, timeouts, pagination limits, disabling introspection/GraphiQL in production, field-level authorization (e.g. @PreAuthorize), and persisted queries.
