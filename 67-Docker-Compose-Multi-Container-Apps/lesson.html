1. Why this matters

In topic 66 you put one Spring Boot app into one container. Nice! But a real application is never alone. Even a small online shop needs:

  • the Spring Boot app itself,
  • a database (MySQL or PostgreSQL),
  • often a cache (Redis), a message broker (RabbitMQ / Kafka), maybe a fake mail server for testing.

With plain Docker you would type a long docker run ... command for each one, create a network by hand, remember all the passwords, start them in the right order, and type it all again tomorrow. That is slow and easy to get wrong.

Docker Compose lets you write all of that down once, in a single YAML file called docker-compose.yml. Then:

docker compose up -d     # start EVERYTHING
docker compose down      # stop EVERYTHING

Where you will see it at work:

  • Day one at a new job: "Clone the repo and run docker compose up." Your whole local environment is ready in two minutes — no installing MySQL on your laptop.
  • Integration testing on a developer machine or in CI (topic 68).
  • Demos and small servers: many small companies run their whole product on one VM with Compose.
  • You already used it in this course! Topics 43 (MySQL), 51 (Redis), 57 (RabbitMQ), 58 (Kafka) and 65 (Zipkin) all had a docker-compose.yml. Now you will finally understand every line.

2. Real-life analogy

🎼 Compose is the orchestra's sheet music Each musician (container) knows how to play their own instrument — the violinist is your Spring Boot app, the drummer is MySQL, the flute is Redis. But somebody has to write down who plays, in which order, who waits for whom, and who sits next to whom. That is the sheet music = docker-compose.yml. The conductor (docker compose up) reads it and starts everybody correctly. The violinist does not start before the drummer gives the beat (depends_on + healthcheck). And everyone in the orchestra calls each other by name ("Hey, mysql!"), not by seat number (IP address).
🏠 Second analogy: a shared house The network is the house: everyone inside can talk to each other by name. Ports are the front doors to the street (your PC). A volume is the storage room in the basement: even if a roommate moves out (container removed), the boxes (data) stay.

3. Concepts step by step

3.1 The problem: doing it by hand with docker run

Without Compose, starting our app + MySQL looks like this (do NOT type it, just look at how painful it is):

docker network create library-net
docker volume create mysql-data
docker run -d --name mysql --network library-net ^
  -e MYSQL_ROOT_PASSWORD=root123 -e MYSQL_DATABASE=librarydb ^
  -e MYSQL_USER=library -e MYSQL_PASSWORD=library123 ^
  -v mysql-data:/var/lib/mysql -p 3307:3306 mysql:8.4
# ...wait until MySQL is ready (how long? nobody knows)...
docker build -t library-app:1.0.0 .
docker run -d --name app --network library-net ^
  -e SPRING_PROFILES_ACTIVE=docker -e DB_HOST=mysql ^
  -p 8080:8080 library-app:1.0.0

Seven commands, many flags, a "wait" you have to guess. With Compose all of this becomes one file and one command.

3.2 What is Docker Compose?

Docker Compose is a tool (built into Docker Desktop and Docker Engine as the docker compose sub-command) that:

  1. reads a YAML file describing several containers ("services"),
  2. creates the network(s) and volume(s) they need,
  3. builds images when needed,
  4. starts the containers in the right order,
  5. and can stop and remove all of them again with one command.
ℹ️ docker compose vs docker-compose The old tool was a separate Python program called docker-compose (with a dash). Today it is "Compose V2", a plugin: docker compose (with a space). Use the space version. The file name docker-compose.yml is still fine (compose.yaml is also accepted). You also do not need the old version: "3.8" line at the top any more — it is ignored.

3.3 YAML in 2 minutes

YAML is a text format for configuration. You met it in topic 29 (application.yml). The rules that matter here:

  • Indentation is meaning. Use spaces, never tabs. Two spaces per level is the habit.
  • key: value — a map entry. A space after the colon is required.
  • - item — a list item.
  • # starts a comment.
  • Quote values that look like numbers or contain : — e.g. "8080:8080", "3306".
services:            # a map
  app:               # a key inside "services"
    ports:           # a list follows
      - "8080:8080"  # list item (quoted because of the colon)

3.5 Services

A service is one kind of container in your app: app, mysql, redis. The name you choose (the key under services:) is very important — it becomes the hostname other containers use.

Each service gets its container either from a ready-made image or by building one:

KeyMeaningExample
image:Download (pull) this image from Docker Hub and run it.image: mysql:8.4
build:Build an image from a Dockerfile in this folder.build: .
build: + image:Build it AND give the result this name/tag.our app service

3.6 Ports: "HOST:CONTAINER"

Same as docker run -p in topic 66. The left number is the port on your PC; the right number is the port inside the container.

ports:
  - "3307:3306"   # localhost:3307 on your PC  →  port 3306 inside the mysql container
💡 Containers don't need ports to talk to each other ports: is only for traffic coming from outside (your browser, your DB tool). Inside the network the app talks to mysql:3306 directly — the container port — even if you removed the ports: line from mysql. In production you often don't publish the database port at all: safer.

3.7 Networks and "service name = hostname"

Compose puts all services on a network (we named ours backend; if you don't name one, Compose creates <project>_default automatically). Docker runs a small DNS server on that network. DNS is the "phone book" of networks: you ask for a name, it answers with an IP address.

app asks: "where is mysql?"→ Docker DNS→ "172.20.0.2"→ app connects to 172.20.0.2:3306

That is why our Spring config says jdbc:mysql://mysql:3306/librarydb. Container IPs change every restart; names don't.

🚫 The #1 beginner bug: localhost inside a container Inside the app container, localhost means the app container itself — not your PC and not MySQL. So jdbc:mysql://localhost:3306/... fails with "Communications link failure / Connection refused". Use the service name: mysql.
Who connects?Address to use
App running inside Compose → MySQLmysql:3306 (service name + container port)
App running on your PC (mvn spring-boot:run) → MySQL in Composelocalhost:3307 (host port)
DBeaver / MySQL Workbench on your PC → MySQL in Composelocalhost:3307
Your browser → app in Composelocalhost:8080

3.8 Environment variables: environment, env_file and .env

Containers are configured with environment variables (key=value pairs the operating system gives to a program). There are three related ideas — beginners mix them up, so let's separate them clearly:

ThingWho reads it?Purpose
environment: in a serviceThe container (your app / MySQL)Set variables inside that one container.
env_file: - app.envThe containerSame, but read the list of variables from a file.
.env file next to the compose fileCompose itselfFills in ${VARIABLE} placeholders in docker-compose.yml before anything starts.
environment:
  MYSQL_PASSWORD: ${DB_PASSWORD:-library123}
  #               │   │            └─ default if DB_PASSWORD is not set anywhere
  #               │   └─ name looked up in your shell or in .env
  #               └─ ${...} = "substitute a value here"

So the flow for a password is: .env → Compose substitutes it into the YAML → environment: passes it into the container → Spring Boot reads ${DB_PASSWORD} in application-docker.properties.

.env
DB_PASSWORD=s3cret→ docker-compose.yml
${DB_PASSWORD}→ container env
DB_PASSWORD=s3cret→ Spring property
${DB_PASSWORD}
💡 Spring Boot reads env vars automatically ("relaxed binding") An env var SPRING_DATASOURCE_URL overrides the property spring.datasource.url. Rule: UPPER CASE, dots become underscores. That's why LOGGING_LEVEL_COM_COURSE=DEBUG in app.env sets logging.level.com.course=DEBUG. You saw the priority order in topic 29: env vars beat application.properties.

3.9 Volumes: where data lives

A container's own file system is temporary. Delete the container → its files are gone. For a database that would be a disaster. Volumes store files outside the container.

TypeSyntaxStored where?Use it for
Named volumemysql-data:/var/lib/mysqlManaged by Docker (you don't care where)Database data, anything the app writes
Bind mount./db/init.sql:/docker-entrypoint-initdb.d/01-init.sql:roA real file/folder on your PCConfig files, init scripts, source code in dev

The :ro at the end means read-only: the container may read the file but not change it.

Named volumes must also be declared at the bottom of the file under the top-level volumes: key.

⚠️ down vs down -v docker compose down removes containers and the network but keeps named volumes → your books are still there next time. docker compose down -v also deletes the volumes → all data is gone (useful when you want a fresh start, scary in production).

3.10 depends_on and healthchecks — starting in the right order

If the app starts before MySQL is ready, Spring Boot fails with "Connection refused" and exits. We need: "start app only after mysql is really ready".

A plain depends_on: [mysql] only waits until the MySQL container has started — but MySQL needs 10–30 seconds more to initialise. That's not enough.

The fix has two parts:

  1. A healthcheck on mysql: a command Docker runs regularly. Exit code 0 = healthy.
  2. depends_on with condition: service_healthy on app.
mysql:
  healthcheck:
    test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD --silent"]
    interval: 10s      # run the check every 10 s
    timeout: 5s        # a check that takes longer counts as failed
    retries: 10        # after 10 failures in a row → "unhealthy"
    start_period: 30s  # failures during the first 30 s don't count

app:
  depends_on:
    mysql:
      condition: service_healthy   # wait for the green light
conditionWaits until…
service_started (default)the container has started (not necessarily ready)
service_healthyits healthcheck passes ✅ — use this for databases
service_completed_successfullya one-time job (e.g. a migration container) finished with exit code 0
ℹ️ What is $$? Compose replaces $NAME in the YAML with values from .env. We want the shell inside the container to read $MYSQL_ROOT_PASSWORD instead, so we write $$ = "a literal dollar sign, please don't touch".

Our app service also has a healthcheck: it calls Spring Boot Actuator's /actuator/health (topic 53) with curl. docker compose ps then shows (healthy) next to each service.

3.11 restart policies

ValueBehaviour
no (default)Never restart automatically.
on-failureRestart only if the process crashed (exit code ≠ 0).
alwaysAlways restart, even after you stopped it and Docker restarts.
unless-stoppedLike always, but respects a manual docker compose stop. Good default.

3.12 Profiles: optional services (Redis)

Sometimes you want a service only sometimes. Give it profiles: ["cache"] and it is skipped by a normal docker compose up. Start it on demand:

docker compose --profile cache up -d
⚠️ Compose profiles ≠ Spring profiles Same word, two different things. Compose profiles choose which containers start. Spring profiles (SPRING_PROFILES_ACTIVE=docker) choose which properties files the app loads. Our project uses both.

3.13 build and up --build

For our app service Compose runs the Dockerfile (a multi-stage build like in topic 66: Maven builds the jar, then a small JRE image runs it). Important:

  • docker compose up builds the image only if it does not exist yet.
  • After changing Java code, use docker compose up -d --build to rebuild — otherwise you run the OLD code and wonder why nothing changed.

3.14 The project name

The top-level name: library sets the project name. All resources get it as a prefix: containers library-app-1, library-mysql-1, network library_backend, volume library_mysql-data. Without it, Compose uses the folder name.

3.16 Spring Boot's own Docker Compose support (bonus)

Since Spring Boot 3.1 there is a dependency spring-boot-docker-compose. When it's on the classpath and you run the app from your IDE, Spring Boot itself runs docker compose up and sets the datasource URL for you. It's handy in development. We don't use it here because we want you to understand the manual way first — the dependency only hides these same steps.

4.1 docker-compose.yml — line by line

docker-compose.yml (part 1: the database)name: library

services:
  mysql:
    image: mysql:8.4
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:-root123}
      MYSQL_DATABASE: ${DB_NAME:-librarydb}
      MYSQL_USER: ${DB_USER:-library}
      MYSQL_PASSWORD: ${DB_PASSWORD:-library123}
    ports:
      - "3307:3306"
    volumes:
      - mysql-data:/var/lib/mysql
      - ./db/init.sql:/docker-entrypoint-initdb.d/01-init.sql:ro
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD --silent"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s
  • image: mysql:8.4 — the official MySQL image, version pinned. Never use latest: tomorrow it could be a different major version.
  • MYSQL_ROOT_PASSWORD, MYSQL_DATABASE, MYSQL_USER, MYSQL_PASSWORD — documented settings of the MySQL image. On the first start (empty volume) it creates the database and the user. Changing them later has no effect unless you wipe the volume.
  • "3307:3306" — we publish to 3307 so it doesn't clash with a MySQL you may have installed on Windows.
  • mysql-data:/var/lib/mysql — /var/lib/mysql is where MySQL keeps its files. We put that folder in a named volume.
  • /docker-entrypoint-initdb.d/ — a special folder: the MySQL image runs every .sql file there on first start. We bind-mount our init.sql into it.
docker-compose.yml (part 2: our app)  app:
    build:
      context: .
      dockerfile: Dockerfile
    image: library-app:1.0.0
    restart: unless-stopped
    depends_on:
      mysql:
        condition: service_healthy
    environment:
      SPRING_PROFILES_ACTIVE: docker
      DB_HOST: mysql
      DB_PORT: "3306"
      DB_NAME: ${DB_NAME:-librarydb}
      DB_USER: ${DB_USER:-library}
      DB_PASSWORD: ${DB_PASSWORD:-library123}
    env_file:
      - app.env
    ports:
      - "8080:8080"
    networks:
      - backend
    healthcheck:
      test: ["CMD", "curl", "-fs", "http://localhost:8080/actuator/health"]
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 40s
  • build.context: . — the folder that is sent to Docker for building. .dockerignore filters it.
  • SPRING_PROFILES_ACTIVE: docker — activates application-docker.properties.
  • DB_HOST: mysql — the service name. DB_PORT: "3306" — the container port, not 3307!
  • Notice that the app and MySQL read the same ${DB_USER} / ${DB_PASSWORD} from .env — one source of truth, they always match.
  • Inside the app's healthcheck, localhost is correct: the check runs inside the app container and checks the app itself.
docker-compose.yml (part 3: optional redis, networks, volumes)  redis:
    image: redis:7.4-alpine
    profiles: ["cache"]
    ...

networks:
  backend:
    driver: bridge

volumes:
  mysql-data:

bridge is the normal single-machine network driver. mysql-data: with nothing after the colon means "a named volume with default settings".

4.2 application-docker.properties — the bridge between Compose and Spring

src/main/resources/application-docker.propertiesspring.datasource.url=jdbc:mysql://${DB_HOST:mysql}:${DB_PORT:3306}/${DB_NAME:librarydb}
spring.datasource.username=${DB_USER:library}
spring.datasource.password=${DB_PASSWORD:library123}
spring.jpa.hibernate.ddl-auto=validate

In Spring, ${DB_HOST:mysql} means "the value of DB_HOST, or mysql if missing" (Spring uses : for the default; Compose uses :- — small difference, easy to mix up). The table is created by init.sql, so Hibernate only validates that the entity matches it.

The default application.properties uses H2 instead, so you can still run the app with mvn spring-boot:run and no Docker at all. Same Java code, different config: that's the twelve-factor "config in the environment" idea from topic 59.

6. Common mistakes

🚫 Mistake: using localhost to reach another container jdbc:mysql://localhost:3306/librarydb inside the app container → Communications link failure.
Fix: use the service name: jdbc:mysql://mysql:3306/librarydb.
⚠️ Mistake: using the HOST port between containers Writing mysql:3307 in the app's config. 3307 exists only on your PC.
Fix: container-to-container always uses the container port (3306).
⚠️ Mistake: plain depends_on without a healthcheck The app starts while MySQL is still initialising and crashes.
Fix: add a healthcheck to mysql and condition: service_healthy to the app (and restart: unless-stopped as a safety net).
⚠️ Mistake: "I changed my code but nothing changed" docker compose up reused the old image.
Fix: docker compose up -d --build.
⚠️ Mistake: "I changed MYSQL_PASSWORD but login fails" The MySQL image only reads these variables on the first start with an empty volume. The old user/password are stored in the volume.
Fix: in development, docker compose down -v and start again (this deletes data!). Same reason init.sql runs only once.
⚠️ Mistake: "port is already allocated" Something on your PC already uses 8080 or 3307 (maybe the app from mvn spring-boot:run is still running).
Fix: stop the other program, or change the LEFT number: "8081:8080".
⚠️ Mistake: tabs or wrong indentation in YAML Errors like "yaml: line 12: did not find expected key" or "services.app Additional property ... is not allowed".
Fix: spaces only; run docker compose config to validate.
🚫 Mistake: committing .env with real passwords Once in Git history, a secret is compromised.
Fix: .env in .gitignore, commit only .env.example. If it happened, change the password.
⚠️ Mistake: running docker compose down -v "to fix things" It deletes your database. Fine on your laptop, a disaster on a server.
Fix: use plain down unless you really want to wipe data.

7. Best practices

  • Pin image versions (mysql:8.4, redis:7.4-alpine), never latest.
  • Healthchecks for every service and depends_on: condition: service_healthy for real readiness.
  • Secrets out of the YAML and out of Git: .env + .env.example. In production, use a real secret store (Kubernetes Secrets, Vault, cloud secret managers — topic 69).
  • Named volumes for data, bind mounts for config/init files (read-only :ro when possible).
  • Don't publish database ports in production — only the app (or the gateway) needs to be reachable from outside.
  • Make your app resilient anyway: even with healthchecks, the database can restart later. Spring Boot's Hikari pool reconnects; restart: unless-stopped covers crashes.
  • One concern per container: app and DB in separate services, never both in one container.
  • Use the same images everywhere: the image you test locally with Compose is the one CI builds (topic 68) and Kubernetes runs (topic 69).
  • Keep the default profile Docker-free (H2) so a newcomer can still run mvn spring-boot:run with nothing installed.
  • Know the limits: Compose runs on one machine. For many machines, self-healing and rolling updates you need an orchestrator like Kubernetes (topic 69).
  • Use compose.override.yml (auto-loaded) for personal local tweaks, and -f docker-compose.prod.yml for environment-specific variations, instead of copying the whole file.

8. Key takeaways

  • Docker Compose describes a multi-container app in one YAML file and starts/stops it with one command.
  • A service = one kind of container; its name is its hostname on the Compose network.
  • ports: "HOST:CONTAINER" is only for access from your PC; containers talk via service:containerPort.
  • environment/env_file set variables in a container; .env fills ${...} in the YAML.
  • Spring Boot reads env vars automatically (relaxed binding) — perfect for container config.
  • Named volumes keep data across down; down -v deletes it.
  • depends_on + condition: service_healthy + a healthcheck = correct start order.
  • up -d --build after code changes; logs -f, ps, exec to look inside.
  • Compose profiles select optional services; Spring profiles select config files — different things.

4. Run the app on your PC against MySQL in Docker. Start only MySQL with Compose and run the app with mvn spring-boot:run using the docker profile. Which host and port must you use?

From your PC the database is localhost:3307 (the published HOST port). Only containers on the network use mysql:3306. Use the password from your .env in $env:DB_PASSWORD if you changed it.

Challenge

5. Connect Redis for real. Using what you learned in topic 51, make the app cache GET /api/books in Redis when it runs in Compose. Start Redis with the cache profile and point the app to it.

Hint / solution
  1. Add spring-boot-starter-data-redis and spring-boot-starter-cache to pom.xml, @EnableCaching on the main class, @Cacheable("books") on a service method that returns the list (and @CacheEvict(value = "books", allEntries = true) on create).
  2. In application-docker.properties: spring.cache.type=redis, spring.data.redis.host=${REDIS_HOST:redis}, spring.data.redis.port=6379.
  3. In the default application.properties: spring.cache.type=simple so the laptop run needs no Redis.
  4. Remove profiles: ["cache"] from redis (or always start with --profile cache) and add redis: condition: service_healthy to the app's depends_on.
  5. docker compose up -d --build, call the endpoint twice, then docker compose exec redis redis-cli keys "*" → you see books::SimpleKey [].
Challenge

6. Two environments. Create docker-compose.prod.yml that removes the MySQL published port, sets LOGGING_LEVEL_COM_COURSE=INFO and limits the app's memory to 512 MB. Start with both files.

Hint / solution
# docker-compose.prod.yml - merged ON TOP of docker-compose.yml
services:
  mysql:
    ports: !reset []          # remove the port list from the base file
  app:
    environment:
      LOGGING_LEVEL_COM_COURSE: INFO
    deploy:
      resources:
        limits:
          memory: 512m
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
docker compose -f docker-compose.yml -f docker-compose.prod.yml config   # check the merge

Values in environment beat values from env_file. !reset is a Compose YAML tag that clears a value from an earlier file.

10. Interview questions

Q1. What is Docker Compose and when would you use it?

A tool to define and run multi-container applications from one YAML file. You use it for local development environments (app + DB + cache + broker), integration tests, demos and simple single-host deployments. It is not a cluster orchestrator — for multiple machines, scaling and self-healing you use Kubernetes.

Q2. How do two containers in the same Compose project talk to each other?

Compose creates a network for the project; Docker's embedded DNS resolves each service name to the container's IP. So the app connects to mysql:3306 — service name and container port. Published host ports are not needed for container-to-container traffic.

Q3. What is the difference between ports and expose?

ports publishes a container port on the host (reachable from your PC/outside). expose only documents a port for other services on the network; it doesn't publish to the host. Containers on the same network can reach each other's ports anyway.

Q4. Does depends_on guarantee that the database is ready?

Not by itself. The short form only waits for the container to start. To wait for readiness, define a healthcheck on the database and use depends_on: db: condition: service_healthy. The application should still retry/reconnect, because the DB can restart later.

Q5. Named volume vs bind mount?

A named volume is managed by Docker and ideal for persistent data (database files); it survives container removal and down, but not down -v. A bind mount maps a specific host path into the container; good for config files, init scripts or live source code in development, but depends on the host's folder structure.

Q6. What is the .env file, and how is it different from env_file?

.env next to the compose file is read by Compose for variable substitution (${VAR}) in the YAML. env_file: in a service loads variables into that container. They can be combined; neither should hold production secrets in Git.

Q7. How does a Spring Boot app in a container get its database URL?

Through environment variables. Either directly via relaxed binding (SPRING_DATASOURCE_URL → spring.datasource.url) or via placeholders in a profile-specific properties file (${DB_HOST:mysql}), with SPRING_PROFILES_ACTIVE selecting the profile. The image stays the same for all environments; only configuration changes (12-factor).

Q8. What's the difference between docker compose down, down -v and stop?

stop stops containers but keeps them. down stops and removes containers and networks, keeps volumes. down -v additionally removes named volumes — all persisted data is lost.

Q9. Why does docker compose up not pick up my code changes?

It reuses an existing image for services with build:. Use docker compose up --build (or docker compose build first) to rebuild the image.

Q10. What are Compose profiles?

A way to mark services as optional: services with profiles: [name] start only when that profile is activated (--profile name or COMPOSE_PROFILES). Useful for debug tools, admin UIs or optional dependencies like Redis.
