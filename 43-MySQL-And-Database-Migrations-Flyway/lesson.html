43. MySQL & Database Migrations with Flyway

Move your app from the toy H2 database to a real MySQL server, and let Flyway build and change your tables safely with versioned SQL scripts.

1. Why this matters

Until now, every project used H2. H2 is a database that lives inside your Java program, in memory. It is perfect for learning: nothing to install, and it starts in a second. But it has one big problem: when the app stops, all data is gone.

Real companies keep their data in a database server: a separate program, often on a separate machine, that keeps data on disk for years. Popular choices are MySQL, PostgreSQL, Oracle and SQL Server. In this lesson we use MySQL because it is free, very popular, and you will see it in many job descriptions.

As soon as data must live for years, a second question appears: "How do we change the tables safely?" Your app version 1 has a books table. Version 2 needs a new isbn column. The production database already has 2 million books in it. You cannot drop the table and create it again! You need a tool that applies small, ordered, recorded changes to the database. That tool is a database migration tool, and the most popular one in the Spring world is Flyway.

ℹ️ Where you will see this at work Almost every Spring Boot project in a company has a folder src/main/resources/db/migration full of files like V1__init.sql, V2__add_orders.sql, ... and a docker-compose.yml so developers can start the database locally. After this lesson, those folders will look familiar.

2. Real-life analogy

🏠 Think of renovating a house with a logbook

Your database is a house where people already live (the data). You cannot knock it down every time you want a change.

  • H2 is a tent: quick to set up, great for a weekend trip, but it disappears when you leave.
  • MySQL is the real house: solid, permanent, people live in it for years.
  • Flyway migrations are numbered work orders: "Order 1: build the walls. Order 2: put in furniture. Order 3: add a window."
  • flyway_schema_history is the logbook on the wall. The builder writes down every order that is finished. When the builder arrives, he reads the logbook and only does the orders that are not done yet.
  • ddl-auto=update is like letting a stranger walk in and "fix things as he thinks best", with no logbook. Maybe fine for a tent — scary for a house full of people.

3. Concepts step by step

3.1 H2 vs MySQL — what really changes?

H2 (in-memory)MySQL (server)

Data after restartGoneKept on disk
Install needed?No — just a Maven dependencyYes — a server (Docker makes it 1 command)

Many apps can share it?NoYes, over the network
JDBC URLjdbc:h2:mem:librarydbjdbc:mysql://localhost:3306/librarydb

The good news: thanks to JPA and Spring Data, your Java code does not change. Hibernate speaks the right "dialect" of SQL for each database. You only change configuration.

BookService→ BookRepository (Spring Data)→ Hibernate→ JDBC driver→ H2 or MySQL

Only the last two boxes change. Everything you wrote before stays the same.

3.2 Starting MySQL with Docker Compose

Installing MySQL directly on Windows works, but it is slow and messy. Docker lets us run MySQL in a "container" — a small, isolated box that has MySQL already installed inside. (We study Docker deeply in topics 66–67. For now, you only need 3 commands.)

A docker-compose.yml file describes which containers we want. Here is ours, line by line:

docker-compose.ymlservices:
  mysql:                                  # a name we choose for this container
    image: mysql:8.4                      # the official MySQL image, version 8.4 (LTS)
    container_name: course-mysql-43
    environment:
      MYSQL_ROOT_PASSWORD: root_pass      # password for the admin user "root"
      MYSQL_DATABASE: librarydb           # create this database on first start
      MYSQL_USER: library_user            # create an app user ...
      MYSQL_PASSWORD: library_pass        # ... with this password
    ports:
      - "3306:3306"                       # <your PC port>:<container port>
    volumes:
      - mysql-data:/var/lib/mysql         # keep the data even if the container is removed
    healthcheck:                          # Docker checks: "is MySQL ready?"
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-proot_pass"]
      interval: 10s
      retries: 10

volumes:
  mysql-data:
docker compose up -d        # start in the background (-d = detached)
docker compose ps           # wait until STATUS shows (healthy)
docker compose down         # stop (data is kept in the volume)
docker compose down -v      # stop AND delete the data
💡 Tip Port 3306 is MySQL's default port. If you already have MySQL installed on Windows, port 3306 is busy. Change the left side, e.g. "3307:3306", and use localhost:3307 in the URL.

3.3 The MySQL driver: mysql-connector-j

A JDBC driver is a translator library that lets Java talk to one kind of database (we met drivers in topic 19). For MySQL the official driver is:

pom.xml<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>   <!-- needed only when the app RUNS, not to compile -->
</dependency>

No <version> tag: the Spring Boot parent already knows a tested version. Old tutorials use mysql:mysql-connector-java — that is the old name. Use com.mysql:mysql-connector-j.

3.5 Profiles: H2 by default, MySQL on demand

Remember profiles from topic 29? A profile is a named set of settings that you switch on when starting the app. We use:

FileWhen it is usedDatabase
application.propertiesAlways (the base)H2 in-memory
application-mysql.propertiesOnly with profile mysql; its values override the baseMySQL
mvn spring-boot:run                                        # H2
mvn spring-boot:run -Dspring-boot.run.profiles=mysql       # MySQL
java -jar target/flyway-mysql-1.0.0.jar --spring.profiles.active=mysql
ℹ️ dev / prod naming Many teams call the profiles dev (H2 or a local DB) and prod (the real server). We named ours mysql so it is obvious what it does. The idea is identical.

3.6 Why ddl-auto=update is dangerous

In topic 38 we used spring.jpa.hibernate.ddl-auto. Quick reminder of its values:

ValueWhat Hibernate does at startupSafe for production?
create-dropCreate tables, drop them at shutdown❌ Never
createDrop and re-create tables (all data lost!)❌ Never
updateTry to change tables to match entities❌ No
validateOnly check that tables match entities; fail if not✅ Yes (with Flyway)
noneDo nothing✅ Yes

Why is update bad?

  • It never deletes or renames. Rename the field name → fullName and you get a new empty column; the old data stays in the old column, forgotten.
  • No history. Nobody knows which change happened when, or on which server.
  • No review. The SQL is invented at runtime. Your team never reads it before it touches production.
  • Different results on different machines. Two servers may end up with slightly different tables.
  • It cannot move data (e.g. "split full_name into first_name and last_name").
🛑 Rule of thumb create/update are for experiments only. Real projects use Flyway (or Liquibase) + ddl-auto=validate.

3.7 What is Flyway?

Flyway is a library that runs SQL scripts against your database in version order, exactly once each, and records what it did. Spring Boot runs Flyway automatically at startup when flyway-core is on the classpath — before Hibernate starts. So by the time Hibernate validates, the tables already exist.

App starts→ DataSource ready→ Flyway: run new V-files→ Hibernate: validate→ App ready ✅ 
pom.xml<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<!-- Since Flyway 10, MySQL support is a separate module -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
⚠️ Don't forget flyway-mysql Without it, the H2 profile works but MySQL fails with Unsupported Database: MySQL 8.4. (PostgreSQL needs flyway-database-postgresql in the same way.)

3.8 Migration file naming rules

Flyway looks in src/main/resources/db/migration (the default location). The file name is very strict:

V3__add_isbn_column.sql
│ │ │                 └── extension: .sql
│ │ └── description: underscores become spaces ("add isbn column")
│ └── TWO underscores (separator)
└── V + version number (1, 2, 3 ... or 1.1, 2025.01.15 ...)
PrefixTypeRuns
VVersioned migrationExactly once, in version order
RRepeatable migration (e.g. R__create_views.sql)Again every time its content changes; after all V-files
UUndo migrationOnly in paid Flyway editions — ignore it

Good names: V1__create_books_table.sql, V2__insert_sample_books.sql, V3__add_isbn_column.sql. Bad names: V1_create.sql (one underscore — silently ignored!), v1__create.sql (lowercase v), create_tables.sql (no version).

3.9 The flyway_schema_history table — Flyway's logbook

The first time Flyway runs, it creates a table called flyway_schema_history. After each script it adds one row:

installed_rankversiondescriptionscriptchecksumsuccess
11create books tableV1__create_books_table.sql-1203984711true
22insert sample booksV2__insert_sample_books.sql584930210true
33add isbn columnV3__add_isbn_column.sql99887766true

Next startup, Flyway compares the files with this table:

  • Versions already in the table → skipped (already done).
  • New versions (say you add V4__...) → run now, then recorded.
  • A file whose content changed after it ran → the checksum (a fingerprint number of the file) no longer matches → Flyway stops the app with a "checksum mismatch" error. This protects you from editing history.
🛑 Golden rule of migrations Once a migration has run on any shared database (test server, production), never edit it. If it was wrong, write a new migration that fixes it.

3.10 One set of scripts for H2 and MySQL

Our H2 URL has MODE=MySQL;DATABASE_TO_LOWER=TRUE. This asks H2 to accept MySQL-style SQL (like AUTO_INCREMENT) and to keep names lower-case like MySQL. Then the same V-files work on both. Keep the SQL simple and standard (CREATE TABLE, ALTER TABLE ... ADD COLUMN, INSERT, CREATE INDEX).

ℹ️ When SQL must differ If a script truly needs MySQL-only syntax, you can use vendor folders: spring.flyway.locations=classpath:db/migration/{vendor} — Spring replaces {vendor} with h2 or mysql. Most teams instead test against the real database using Testcontainers (below).

3.11 Useful Flyway properties

PropertyDefaultMeaning
spring.flyway.enabledtrueTurn Flyway on/off

3.12 Testcontainers (a mention)

Testcontainers is a Java library that starts a real Docker container (e.g. MySQL 8.4) from inside a JUnit test, and throws it away after the test. So your tests run against the same database as production, not against H2. Spring Boot supports it with @ServiceConnection:

@SpringBootTest
@Testcontainers
class BookRepositoryMySqlTest {

    @Container
    @ServiceConnection   // Spring Boot reads URL/user/password from the container automatically
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.4");

    // ... tests run on a real MySQL, Flyway migrations included
}

You need Docker running and the org.testcontainers:mysql + junit-jupiter test dependencies. We will touch testing in topic 46; for now just remember the name.

4.1 The migrations

src/main/resources/db/migration/V1__create_books_table.sqlCREATE TABLE books (
    id             BIGINT        NOT NULL AUTO_INCREMENT,
    title          VARCHAR(200)  NOT NULL,
    author         VARCHAR(100)  NOT NULL,
    price          DECIMAL(10,2) NOT NULL,
    published_year INT,
    created_at     TIMESTAMP     DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);

AUTO_INCREMENT lets the database pick the next id. That matches @GeneratedValue(strategy = GenerationType.IDENTITY) in the entity. DECIMAL(10,2) stores money exactly (10 digits, 2 after the dot) — matching a Java BigDecimal.

V2__insert_sample_books.sqlINSERT INTO books (title, author, price, published_year) VALUES ('Clean Code', 'Robert C. Martin', 450.00, 2008);
INSERT INTO books (title, author, price, published_year) VALUES ('Effective Java', 'Joshua Bloch', 599.00, 2018);
-- ... 2 more
V3__add_isbn_column.sqlALTER TABLE books ADD COLUMN isbn VARCHAR(20);

UPDATE books SET isbn = '978-0132350884' WHERE title = 'Clean Code';
UPDATE books SET isbn = '978-0134685991' WHERE title = 'Effective Java';

CREATE INDEX idx_books_author ON books (author);

V3 shows the real power: the table already has data, and we change it without losing anything. That is a "schema evolution".

4.2 The entity must match the tables

book/Book.java@Entity
@Table(name = "books")
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // AUTO_INCREMENT
    private Long id;

    @Column(nullable = false, length = 200)
    private String title;
    // ...
    @Column(nullable = false, precision = 10, scale = 2)  // DECIMAL(10,2)
    private BigDecimal price;

    @Column(name = "published_year")
    private Integer publishedYear;

    @Column(length = 20)
    private String isbn;                                 // added by V3

    @CreationTimestamp
    @Column(name = "created_at", updatable = false)
    private LocalDateTime createdAt;
    // constructors, getters, setters ...
}

With ddl-auto=validate, Hibernate checks at startup that table books exists and that each field has a matching column with a compatible type. Try deleting V3 (on H2): the app fails with "Schema-validation: missing column [isbn] in table [books]". That early failure is a feature, not a bug.

4.4 DatabaseInfoController — see it with your own eyes

config/DatabaseInfoController.java@GetMapping("/api/db-info")
public Map<String, Object> dbInfo() throws SQLException {
    Map<String, Object> info = new LinkedHashMap<>();
    info.put("activeProfiles", Arrays.asList(environment.getActiveProfiles()));

    try (Connection connection = dataSource.getConnection()) {      // borrow from the pool
        DatabaseMetaData meta = connection.getMetaData();
        info.put("database", meta.getDatabaseProductName() + " " + meta.getDatabaseProductVersion());
        info.put("jdbcUrl", meta.getURL());
    }                                                                // ... and give it back

    List<String> applied = Arrays.stream(flyway.info().applied())    // rows of flyway_schema_history
            .map(DatabaseInfoController::describe)
            .toList();
    info.put("appliedMigrations", applied);
    return info;
}

Spring Boot creates the DataSource and the Flyway objects as beans, so we just ask for them in the constructor (constructor injection, topic 24).

4.5 Service and controller

The BookService and BookController are the same style you know from topics 33–38: DTOs in and out, @Transactional(readOnly = true) at class level, @Transactional on write methods, BookNotFoundException → 404. The important lesson: none of them knows which database is used.

6. Common mistakes

⚠️ Mistake: one underscore in the file name V4_add_stock.sql is silently ignored by Flyway. Your new column never appears and Hibernate validation fails.
Fix: always two underscores: V4__add_stock.sql.
🛑 Mistake: editing a migration that already ran You fix a typo in V2__... and restart: "Validate failed: Migration checksum mismatch for migration version 2".
Fix: undo your edit and write V4__fix_typo.sql. On your own throw-away database only, you may also docker compose down -v to start fresh.
⚠️ Mistake: forgetting flyway-mysql Error: Unsupported Database: MySQL 8.4.
Fix: add the org.flywaydb:flyway-mysql dependency.
⚠️ Mistake: "Communications link failure" / "Connection refused" The app cannot reach MySQL.
Fix: is Docker Desktop running? Did you run docker compose up -d? Is the container (healthy)? Is the port right (3306 vs 3307)?
⚠️ Mistake: "Access denied for user" Wrong username/password, or the volume was created earlier with different passwords (MySQL reads the MYSQL_* variables only on the very first start).
Fix: check the properties; if you changed passwords in compose, run docker compose down -v and start again.
⚠️ Mistake: keeping ddl-auto=update together with Flyway Now two tools change the schema and you never know who did what.
Fix: Flyway creates and changes, Hibernate only validates.
⚠️ Mistake: "Schema-validation: missing column" You added a field to the entity but no migration.
Fix: add a new V<n>__...sql with ALTER TABLE ... ADD COLUMN ....
⚠️ Mistake: using MySQL-only SQL in a migration that also runs on H2 e.g. ENGINE=InnoDB or backticks in some places may fail on H2.
Fix: keep scripts portable, use vendor folders, or test on real MySQL with Testcontainers.

7. Best practices

  • Flyway owns the schema; Hibernate only validates. ddl-auto=validate (or none) everywhere except quick experiments.
  • Migrations are immutable. Once merged and run, never edit — add a new version.
  • Small migrations, one purpose each: V7__add_orders_table.sql, not V7__lots_of_changes.sql.
  • Review migrations in pull requests like Java code — they touch the most valuable thing you have: data.
  • Backward compatible changes for zero-downtime deploys: add a column first (nullable), deploy code, then remove the old one in a later release ("expand and contract").
  • Never put real passwords in properties files or Git. Use environment variables (${DB_PASSWORD}) or a secrets manager.
  • Use a dedicated app user (not root) with only the permissions it needs.
  • Test against the real database (Testcontainers) in CI, because H2 is "almost" MySQL, not exactly MySQL.
  • Keep spring.flyway.clean-disabled=true (the default) — clean drops all objects.
  • Tune the connection pool (spring.datasource.hikari.*) only after measuring; defaults are good.
  • Alternative tool: Liquibase (XML/YAML/SQL changelogs). Same idea; Flyway is simpler because it is plain SQL.

8. Key takeaways

  • H2 in-memory is for learning; real apps use a database server such as MySQL.
  • docker compose up -d gives you MySQL 8.4 in seconds; down -v wipes it.
  • MySQL needs com.mysql:mysql-connector-j and a jdbc:mysql://host:port/db URL.
  • Profiles let one codebase run on H2 (default) and MySQL (--spring.profiles.active=mysql).
  • ddl-auto=update is unsafe for production: no history, no review, never drops/renames.
  • Flyway runs V<n>__description.sql files once each, in order, before Hibernate starts.
  • flyway_schema_history records what ran, with checksums; editing old files breaks startup on purpose.
  • For MySQL you also need the flyway-mysql module.
  • Testcontainers runs a real database in Docker for your tests.

9. Practice exercises

Easy

See the logbook. Start the app with H2, open the H2 console and run a query that shows the version, description, script and success columns of Flyway's history table.

Hint / solution
SELECT version, description, script, success
FROM flyway_schema_history
ORDER BY installed_rank;
Easy

Add a migration. Add a stock column (integer, not null, default 0) to books, and set stock 10 for "Clean Code". Add the field to the entity and the response DTO.

Hint / solution
V4__add_stock_column.sqlALTER TABLE books ADD COLUMN stock INT NOT NULL DEFAULT 0;
UPDATE books SET stock = 10 WHERE title = 'Clean Code';
Book.java@Column(nullable = false)
private int stock;

public int getStock() { return stock; }

Then add int stock to BookResponse and pass book.getStock() in from(...). Restart: the log shows "Migrating ... to version 4".

Medium

Break it on purpose. (a) Change a price inside V2__insert_sample_books.sql and restart with the mysql profile (data persisted). What happens? (b) Why does the same edit not fail on H2?

Hint / solution

(a) Flyway stops with "Migration checksum mismatch for migration version 2" because the file's fingerprint differs from the one stored in flyway_schema_history. Revert the edit (or, on a throw-away DB, docker compose down -v). (b) H2 in-memory starts empty every time, so there is no history to compare with — Flyway simply runs all scripts again. This is exactly why H2-only testing can hide problems.

Medium

New table with a foreign key. Add a reviews table (id, book_id → books.id, rating 1–5, comment) with a migration that works on both H2 and MySQL. Add a Review entity with @ManyToOne Book book.

Hint / solution

    id       BIGINT       NOT NULL AUTO_INCREMENT,
    book_id  BIGINT       NOT NULL,
    rating   INT          NOT NULL,
    comment  VARCHAR(500),
    PRIMARY KEY (id),
    CONSTRAINT fk_reviews_book FOREIGN KEY (book_id) REFERENCES books (id)
);
@Entity

Rename a column safely. The business wants author renamed to author_name. Write the migration and the entity change. Then explain how you would do it with zero downtime when old and new app versions run at the same time.

@Column(name = "author_name", nullable = false, length = 100)
private String author;   // the Java name can stay the same!

Also update the derived query only if you rename the Java field. Zero downtime ("expand and contract"): release 1 adds author_name and copies data (UPDATE books SET author_name = author), code writes to both columns; release 2 reads only author_name; release 3 drops author. Each step is its own migration.

10. Interview questions

Q1. What is a database migration tool and why do we need one?

It applies versioned, ordered schema changes (SQL scripts) to a database and records which ones ran. It gives us a repeatable, reviewable history of the schema, so every environment (dev, test, prod) ends up identical, and changes can be applied to databases that already contain data.

Q2. Why shouldn't we use spring.jpa.hibernate.ddl-auto=update in production?

It generates SQL at runtime with no review and no history; it never drops or renames columns (renames create new empty columns); it can't migrate data; and results can differ between environments. Use Flyway/Liquibase for changes and validate or none for Hibernate.

Q3. How does Flyway know which migrations to run?

It reads the flyway_schema_history table in the target database. Any migration version not recorded there (and newer than the current version) is executed in version order, then recorded with its checksum, execution time and success flag.

Q4. What is the naming convention for Flyway migrations?

V<version>__<description>.sql — capital V, a version (1, 2, 1.1 ...), two underscores, a description with underscores for spaces. R__name.sql are repeatable migrations re-run when their checksum changes. Default location: classpath:db/migration.

Q5. What happens if you modify a migration that has already been applied?

On the next start, validation detects a checksum mismatch and Flyway fails the startup. The fix is to revert the change and create a new migration. (flyway repair exists to realign checksums, but it should be used carefully and rarely.)

Q6. How do you run the same Spring Boot app against H2 locally and MySQL in another environment?

Put shared settings and H2 in application.properties, MySQL settings in application-mysql.properties (or -prod), include both drivers, and activate with --spring.profiles.active=mysql or the SPRING_PROFILES_ACTIVE environment variable. JPA code doesn't change because Hibernate picks the dialect from the connection.

Q7. In what order do Flyway and Hibernate run at startup?

Spring Boot makes the EntityManagerFactory depend on Flyway, so Flyway migrates first, then Hibernate starts and (with validate) checks entities against the migrated schema.

Q8. How do you introduce Flyway into a project whose production database already has tables?

Create a baseline: write V1__baseline.sql that matches the current schema (for new environments) and set spring.flyway.baseline-on-migrate=true (with baseline-version=1) so Flyway marks the existing database as version 1 and only runs V2+ there.

Q9. What is Testcontainers and why prefer it over H2 for repository tests?

A library that starts real services (MySQL, PostgreSQL, Kafka...) in Docker containers during tests. Tests then run against the same database engine as production, catching SQL dialect differences, constraint behaviour and migration issues that H2 might hide. With Spring Boot, @ServiceConnection wires the connection automatically.

Q10. Flyway vs Liquibase?

Both version database changes. Flyway uses plain SQL files and a simple versioning model — easy to learn. Liquibase uses changelogs (XML/YAML/JSON/SQL) with database-independent change types, rollbacks and preconditions — more features, more complexity. Both integrate with Spring Boot out of the box.
