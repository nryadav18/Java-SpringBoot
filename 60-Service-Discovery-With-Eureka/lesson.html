1. Why this matters

In Topic 59, order-service had this line in its configuration:

product-service.base-url=http://localhost:8081

On your laptop that is fine. In a real company it breaks very quickly:

  • Addresses change. In the cloud (Docker, Kubernetes, AWS) a service gets a new IP address every time it restarts or moves to another machine.
  • Many copies. On Black Friday you run 10 copies of product-service. Which one should order-service call? All of them, taking turns!
  • Copies come and go. Auto-scaling adds copies when traffic is high and removes them at night. One copy crashes. Nobody can update config files that fast.

Service discovery solves this: every service registers itself in a central registry ("I am product-service, I'm at 10.0.3.17:8081"), and callers ask the registry by name. Netflix built Eureka for exactly this, and Spring Cloud makes it a few lines of configuration. Even if your company uses Kubernetes (which has discovery built in, Topic 69), the idea is the same – and "How do services find each other?" is a classic interview question.

2. Real-life analogy

🏬 The shopping mall information desk

A big mall has hundreds of shops. Shops open, close and move to other floors all the time. Printing a fixed map in every visitor's pocket would not work.

Instead, the mall has an information desk (= Eureka server). When a shop opens, the shop manager registers at the desk: "Pizza Corner, floor 2, shop 14". Every few minutes the manager calls the desk: "still open!" (= heartbeat). If the desk hears nothing for a while, it removes the shop from the list (= eviction).

A visitor (= order-service) only knows the name "Pizza Corner". They ask the desk, get the current location, and walk there. If Pizza Corner has two counters (= two instances), the visitor goes to one this time and the other next time (= load balancing). Smart visitors even keep a photo of the directory (= the client's local cache of the registry), so they don't queue at the desk for every visit – and can still find shops if the desk is briefly closed.

3. Concepts step by step

3.1 The problem in one picture

order-service→ http://localhost:8081 →product-service #1 (8081)
product-service #2 (8091)← never used 😢

The second copy is useless because order-service only knows one fixed address. And if #1 dies, every order fails even though #2 is healthy.

3.2 Service registry and service discovery

  • Service registry – a small database of "service name → list of live instances (host, port, status)". Eureka server is one.
  • Registration – at startup a service tells the registry about itself; then it sends heartbeats regularly.
  • Discovery – a caller looks up a name in the registry and gets the list of instances.
  • Load balancing – the caller picks one instance from the list (round-robin by default).

Notice: the request itself does not go through Eureka. Eureka only answers "where is it?" – then order-service calls product-service directly.

3.3 Client-side vs server-side discovery

Client-side discovery (Eureka + Spring Cloud LoadBalancer)Server-side discovery (Kubernetes Service, AWS ELB)
Who picks the instance?The caller (order-service) itselfA load balancer / proxy in the middle
Caller needsA discovery client libraryJust one stable address (DNS name)
Extra network hopNoYes (through the load balancer)
Language-neutral?No – each language needs a client libraryYes

In this topic we use client-side discovery. On Kubernetes, teams often drop Eureka and use the built-in Service DNS instead – the concepts you learn here still apply.

3.4 What is Spring Cloud? And the BOM

Spring Cloud is a family of projects (on top of Spring Boot) for distributed systems: Netflix Eureka, Gateway, Config, OpenFeign, Circuit Breaker, LoadBalancer, Stream and more. Each has its own version number, so Spring Cloud publishes a release train – a set of versions that are tested together. The train is named by year: 2025.0.0 (code name "Northfields") matches Spring Boot 3.5.x.

You import the train as a BOM (Bill Of Materials, Topic 20) in <dependencyManagement>. It adds no libraries – it only fixes their versions, so you write dependencies without <version>:

pom.xml (every Spring Cloud project in Part F)<properties>
    <java.version>17</java.version>
    <spring-cloud.version>2025.0.0</spring-cloud.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
⚠️ Versions must matchSpring Cloud 2025.0.x ↔ Boot 3.5.x; 2024.0.x ↔ Boot 3.4.x; 2023.0.x ↔ Boot 3.2/3.3. A mismatched pair often fails at startup with a "compatibility verifier" error. Check the table on spring.io/projects/spring-cloud when you upgrade.

3.5 The Eureka server

A Eureka server is just a Spring Boot app with one dependency and one annotation:

  • Dependency: spring-cloud-starter-netflix-eureka-server
  • Annotation: @EnableEurekaServer on the main class
  • Port: 8761 by tradition. The web dashboard is at http://localhost:8761; the REST API at /eureka/apps.

Since the server itself also contains a Eureka client, a standalone server must be told not to register with itself: eureka.client.register-with-eureka=false and fetch-registry=false.

3.6 Eureka clients: registration, heartbeats, leases

Any service with spring-cloud-starter-netflix-eureka-client on the classpath automatically:

  1. Registers at startup under its spring.application.name (shown in UPPER CASE in the dashboard, e.g. PRODUCT-SERVICE).
  2. Sends a heartbeat (lease renewal) every 30 s (default).
  3. If Eureka gets no heartbeat for 90 s (lease expiration), the instance is evicted (removed).
  4. Fetches the registry every 30 s and caches it locally – so lookups are fast and survive a short Eureka outage.
  5. On graceful shutdown (Ctrl+C) it de-registers immediately.
ℹ️ No annotation needed on clientsOld tutorials put @EnableEurekaClient or @EnableDiscoveryClient on the client. @EnableEurekaClient no longer exists, and @EnableDiscoveryClient is optional – the starter dependency is enough.

⚠️ Why things feel slow by defaultWith default settings, a newly started instance may take up to ~1–2 minutes to be used by callers (heartbeat + server cache + client fetch + load-balancer cache). That's why our demo uses short "DEV ONLY" intervals. Keep the defaults in production – shorter intervals mean more network traffic.

3.7 Self-preservation mode

If many instances suddenly stop sending heartbeats, Eureka assumes it is a network problem (not that all services died) and stops evicting anyone. The dashboard shows a red warning: "EMERGENCY! EUREKA MAY BE INCORRECTLY CLAIMING INSTANCES ARE UP WHEN THEY'RE NOT."

In production that is a safety feature (better to keep a stale entry than to delete healthy services). On a laptop, where you stop services all the time, it is confusing – so our dev server sets eureka.server.enable-self-preservation=false.

3.8 Client-side load balancing with @LoadBalanced

Spring Cloud ships Spring Cloud LoadBalancer (included with the Eureka client starter). To use it with RestClient:

@Bean
@LoadBalanced                                   // add the load-balancing interceptor
public RestClient.Builder loadBalancedRestClientBuilder() {
    return RestClient.builder();
}

// later:  builder.baseUrl("http://product-service").build()

What happens on GET http://product-service/api/products/1?

RestClient→ LoadBalancer interceptor→ "product-service"? → local registry copy→ [8081, 8091] → round-robin picks 8091→ GET http://localhost:8091/api/products/1

product-service is not a real host name. Without @LoadBalanced you get UnknownHostException: product-service. The same annotation works on RestTemplate and WebClient.Builder beans, and OpenFeign (Topic 63) uses the load balancer automatically.

💡 DiscoveryClient – the low-level APIYou can also inject DiscoveryClient and call getInstances("product-service") to see the raw list. Our /api/orders/discovery endpoint does that for learning. In normal code prefer @LoadBalanced clients.

3.9 Running two instances

Instances of one service share the same spring.application.name but need different ports and a unique instance-id. With Maven you override the port from the command line:

mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=8091"

The quotes are needed in PowerShell. --server.port=8091 is a Spring Boot command-line property – it beats application.yml (Topic 29's precedence table).

3.10 High availability (production)

If Eureka is down, clients keep working with their cached registry, but new instances can't register. In production you run 2–3 Eureka servers that replicate to each other ("peers"): each server lists the others in eureka.client.service-url.defaultZone (comma-separated), and clients list all of them.

4.3 order-service – discovering by name

order-service/src/main/java/com/course/discovery/order/RestClientConfig.java@Configuration
public class RestClientConfig {

    @Bean
    @LoadBalanced
    public RestClient.Builder loadBalancedRestClientBuilder() {
        return RestClient.builder();
    }

    @Bean
    public RestClient productRestClient(@LoadBalanced RestClient.Builder builder) {
        return builder.baseUrl("http://product-service").build();   // a NAME, not a host
    }
}

Why two beans? The first bean is the builder that Spring Cloud decorates with the load-balancer interceptor (the @LoadBalanced on the parameter makes sure we get exactly that builder). The second is a ready-to-use client with the base URL set, injected into ProductClient.

order-service/src/main/java/com/course/discovery/order/ProductClient.javapublic ProductDto getProduct(Long productId) {
    try {
        return productRestClient.get()
                .uri("/api/products/{id}", productId)   // http://product-service/api/products/1
                .retrieve()
                .body(ProductDto.class);
    } catch (HttpClientErrorException.NotFound e) {
        throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Product " + productId + " not found");
    } catch (HttpStatusCodeException e) {
        throw new ResponseStatusException(HttpStatus.SERVICE_UNAVAILABLE,
                "product-service answered " + e.getStatusCode() + " - is at least one instance running?");
    } catch (ResourceAccessException | IllegalStateException e) {
        // could not connect, or "No instances available for product-service"
        throw new ResponseStatusException(HttpStatus.SERVICE_UNAVAILABLE,
                "No reachable product-service instance: " + e.getMessage());
    }
}

6. Common mistakes

⚠️ Mistake: UnknownHostException: product-serviceThe RestClient was not load-balanced: you used a plain RestClient.create() or injected Boot's normal builder.
Fix: create the client from a builder bean annotated with @LoadBalanced, and inject it with @LoadBalanced RestClient.Builder.
⚠️ Mistake: "No instances available for product-service" right after startupRegistration and cache refresh take time (with defaults: up to ~1–2 minutes).
Fix: wait a little, check the dashboard; in dev use the shorter intervals from our YAML.
⚠️ Mistake: the 2nd instance replaces the 1st in the dashboardBoth instances got the same instance-id.
Fix: eureka.instance.instance-id: ${spring.application.name}:${server.port}.
⚠️ Mistake: wrong service name in the URLhttp://productservice/... or a typo in spring.application.name. Names are matched case-insensitively, but must otherwise be identical.
Fix: copy the name exactly from the dashboard.
⚠️ Mistake: Spring Cloud and Boot versions don't matche.g. Spring Cloud 2023.0.x with Boot 3.5 → startup error "Spring Boot [3.5.6] is not compatible with this Spring Cloud release train".
Fix: Boot 3.5.x ↔ Spring Cloud 2025.0.x.
⚠️ Mistake: instance registered with a strange IP (VPN, Docker, Wi-Fi adapter)Calls time out because the registered address is not reachable.
Fix: on a laptop set eureka.instance.hostname: localhost; in containers set prefer-ip-address: true or the correct hostname.
🛑 Mistake: "EMERGENCY! EUREKA MAY BE INCORRECTLY CLAIMING INSTANCES ARE UP"Self-preservation kicked in; dead instances stay listed and calls to them fail.
Fix: in dev, disable self-preservation (as we did). In production keep it on and investigate the network.

7. Best practices

  • Run 2–3 Eureka servers in production (peer replication) – the registry must not be a single point of failure.
  • Keep the default intervals (30 s / 90 s) in production; short intervals only in dev.
  • Keep self-preservation ON in production.
  • Give every instance a unique instance-id and make the registered address reachable from other services.
  • Use health checks: eureka.client.healthcheck.enabled=true (with actuator) makes Eureka use the real /actuator/health status.
  • Combine discovery with timeouts, retries and circuit breakers (Topic 64): the instance list can briefly contain a dead instance.
  • For many languages or on Kubernetes, consider server-side discovery (K8s Services) or Consul instead of Eureka.
  • Use the Caffeine cache for Spring Cloud LoadBalancer in production (the startup warning tells you so).
  • Secure the Eureka dashboard/API (e.g. Spring Security with basic auth) – it reveals your whole system map.

8. Key takeaways

  • Service discovery replaces hard-coded host:port with lookups by service name.
  • Eureka server = registry: one starter + @EnableEurekaServer, dashboard on 8761.
  • Eureka clients register automatically (starter on the classpath), send heartbeats, and cache the registry locally.
  • The Spring Cloud BOM 2025.0.0 pairs with Spring Boot 3.5.x and manages all Spring Cloud versions.
  • @LoadBalanced RestClient.Builder + http://product-service = client-side load balancing (round-robin) via Spring Cloud LoadBalancer.
  • Run several instances with different ports and a unique instance-id; they share one application name.
  • Eureka only answers "where?"; the actual call goes directly from service to service.
  • Defaults are slow on purpose (30 s / 90 s); self-preservation protects against network partitions.

Challenge

Hint / solution
// NOTE: do NOT annotate this class with @Configuration (it must not be picked up by component scan)
public class RandomLbConfig {
    @Bean
    ReactorLoadBalancer<ServiceInstance> randomLoadBalancer(Environment env,
            LoadBalancerClientFactory factory) {
        String name = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new RandomLoadBalancer(
                factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
    }
}

// on any @Configuration class in order-service:
@LoadBalancerClient(name = "product-service", configuration = RandomLbConfig.class)

10. Interview questions

Q1. What is service discovery and why is it needed?

A mechanism for services to find the network location of other services dynamically. In cloud environments instances have changing IPs, are scaled up/down and fail; a registry keeps the current list of live instances so callers can look them up by logical name instead of hard-coded addresses.

Q2. Client-side vs server-side discovery?

Client-side: the caller queries the registry and chooses an instance itself (Eureka + Spring Cloud LoadBalancer, Netflix Ribbon in the past). Server-side: the caller sends requests to a router/load balancer that queries the registry (Kubernetes Service, AWS ELB). Client-side saves a hop but needs a library per language; server-side is language-neutral.

Q3. How does a Eureka client stay registered? What is a lease?

It registers at startup, then renews its lease with a heartbeat every 30 s by default. If the server receives no renewal for the lease expiration duration (90 s default), it evicts the instance. On graceful shutdown the client cancels its lease immediately.

Q4. What is Eureka's self-preservation mode?

When the number of renewals drops below an expected threshold (e.g. due to a network partition), Eureka stops evicting instances, assuming the problem is the network rather than the services. It favours availability (AP in CAP terms) over accuracy; callers may get stale instances and must handle failures.

Q5. What does @LoadBalanced do?

It marks a RestClient.Builder/RestTemplate/WebClient.Builder bean so Spring Cloud adds a load-balancer interceptor. URLs whose host is a service id (http://product-service) are resolved through the discovery client to a concrete instance chosen by Spring Cloud LoadBalancer (round-robin by default).

Q6. What happens if the Eureka server goes down?

Existing clients keep working using their locally cached registry, so calls continue. But new instances can't register, and changes (instances dying/starting) are not propagated. That's why production runs multiple peer-replicated Eureka servers.

Q7. Do you still need @EnableEurekaClient / @EnableDiscoveryClient?

No. @EnableEurekaClient was removed; @EnableDiscoveryClient is optional. Having spring-cloud-starter-netflix-eureka-client on the classpath auto-configures registration and discovery. It can be turned off with eureka.client.enabled=false.

Q8. Why can it take a long time before a new instance receives traffic?

Several caches stack up: the instance's first heartbeat/registration, the server's response cache (30 s), the client's registry fetch interval (30 s), and the load balancer's cache (35 s). Tuning these lowers the delay at the cost of more traffic.

Q9. What is the Spring Cloud release train / BOM?

Spring Cloud is many sub-projects with independent versions. A release train (e.g. 2025.0.0) is a tested set of compatible versions, imported as the BOM spring-cloud-dependencies in dependencyManagement. Each train supports a specific Spring Boot line (2025.0 ↔ Boot 3.5).

Q10. Eureka vs Kubernetes service discovery?

Kubernetes provides discovery via Services and DNS (server-side, language-neutral, built in). On Kubernetes many teams skip Eureka and call http://product-service resolved by K8s DNS, optionally using Spring Cloud Kubernetes. Eureka fits VM-based or mixed environments and gives client-side load balancing control.
