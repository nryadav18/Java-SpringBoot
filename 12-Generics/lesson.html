12. Generics

Understand the <T> you see everywhere, write your own type-safe reusable classes and methods, and decode signatures like JpaRepository<Product, Long> without fear.

1. Why this matters

Imagine writing a class that stores something — a product, a student, a number. Without generics you have two bad options:

  1. Write ProductBox, StudentBox, IntegerBox… the same code copy-pasted many times.
  2. Write one ObjectBox that holds Object — then cast everything you take out, and discover mistakes only when the program crashes at runtime.

Generics (Java 5, 2004) give you a third option: write the code once with a placeholder type T, and let the compiler check every use. Benefits:

  • Type safety — wrong types are compile errors, not runtime crashes.
  • No casts — cleaner code.
  • Reuse — one class/method for all types.
ℹ️ Where you'll see it at workSpring is full of generics: interface ProductRepository extends JpaRepository<Product, Long> (Topic 38), ResponseEntity<ProductDto> (Topic 32), Optional<User>, Page<Order> (Topic 41), KafkaTemplate<String, OrderEvent> (Topic 58). You won't write complex generic code every day — but you'll read it every single day.

2. Real-life analogy

🥡 Think of labelled food containers
  • An unlabelled box (Object) can hold anything. When you open it you must guess what's inside ("I think it's rice…") — that's a cast. If you guessed wrong, you find out at dinner time (runtime crash).
  • A labelled container — "RICE ONLY" — is Box<Rice>. Anyone trying to put soup in it is stopped at the kitchen door (compile time). When you open it, you know it's rice.
  • The container design is the same for rice, dal and sugar. You make the design once (Box<T>) and just change the label.
  • A label like "any grain" is a bounded type: Box<T extends Grain> — rice and wheat are fine, soup isn't.

3. Concepts step by step

3.1 The problem generics solve

Example01_WhyGenerics.java — without genericsList emails = new ArrayList();    // "raw" list: holds Object
emails.add("asha@mail.com");
emails.add(42);                   // compiler doesn't complain!

for (Object o : emails) {
    String email = (String) o;    // cast needed... and it CRASHES for 42
}
ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String
Example01_WhyGenerics.java — with genericsList<String> emails = new ArrayList<>();
emails.add("asha@mail.com");
emails.add(42);                   // ❌ compile error: int cannot be converted to String

for (String email : emails) {     // no cast
    ...
}
💡 The core ideaGenerics move errors from runtime (users see a crash) to compile time (you see a red underline in VS Code). Compile errors are cheap; production crashes are expensive.

3.2 Generic classes

Add a type parameter in angle brackets after the class name, then use it like a normal type inside:

class Box<T> {              // T = "some type, chosen later"
    private final T item;

    Box(T item) { this.item = item; }

    T get() { return item; }
}

Using it — you choose T (the type argument):

Box<String>  giftBox = new Box<>("Gift card");   // T = String
Box<Integer> cashBox = new Box<>(500);           // T = Integer
Box<Product> prodBox = new Box<>(new Product("Headphones", 1999));

String s = giftBox.get();     // no cast
int cash = cashBox.get();     // auto-unboxing

Think of Box<T> as a template. Box<String> means "imagine every T in the class replaced by String".

A generic wrapper you'll reuse in Spring

Many companies wrap all REST responses like this. Spring's own ResponseEntity<T> is the same idea.

3.3 Generic methods

Sometimes only one method needs to be generic, not the whole class. Declare the type parameter before the return type:

//      ↓ "this method has its own type parameter T"
static <T> T firstOrDefault(List<T> items, T defaultValue) {
    return items.isEmpty() ? defaultValue : items.get(0);
}

Reading the signature left to right: "static, for some type T, returns a T, takes a list of T and a default T".

String city = firstOrDefault(List.of("Pune", "Delhi"), "(none)");   // T = String (inferred)
Integer n   = firstOrDefault(List.of(10, 20), 0);                    // T = Integer (inferred)

Type inference: Java works out T from the arguments, so you almost never write it. The explicit form exists for rare cases: Example03_GenericMethods.<String>firstOrDefault(...).

You've already used many generic methods from the JDK: List.of(...), Map.of(...), Arrays.asList(...), Collections.max(...).

ℹ️ Generic class vs generic methodIn a generic class, T is fixed when you create the object (new Box<String>) and shared by all its methods. In a generic method, T is chosen fresh on each call. Static methods can't use the class's T, so static helpers are always generic methods (like ApiResponse.success).

3.4 Bounded types — <T extends Something>

With plain <T>, Java knows nothing about T — it could be a String, a Dog, anything — so you may only call Object methods (toString, equals…). Try to add up numbers:

static <T> double sum(List<T> numbers) {
    double total = 0;
    for (T n : numbers) total += n.doubleValue();   // ❌ cannot find symbol: doubleValue()
    return total;
}

A bound promises something about T, and unlocks its methods:

static <T extends Number> double sum(List<T> numbers) {   // T must be Number or a subclass
    double total = 0;
    for (T n : numbers) total += n.doubleValue();          // ✅ every Number has doubleValue()
    return total;
}

sum(List.of(10, 20, 30));       // 60.0  (Integer extends Number)
sum(List.of(20.5, 100.25));     // 120.75 (Double extends Number)
sum(List.of("a", "b"));         // ❌ compile error: String is not a Number

In a bound, extends means "extends or implements" — it works for interfaces too:

static <T extends Comparable<T>> T max(List<T> items) {
    T best = items.get(0);
    for (T item : items) {
        if (item.compareTo(best) > 0) best = item;      // allowed: T is Comparable
    }
    return best;
}

max(List.of(78, 92, 85));              // 92
max(List.of("Asha", "Ravi", "Meena")); // "Ravi"

Multiple bounds use & (a class, if any, must come first, then interfaces):

static <T extends Payable & Comparable<T>> T highestPaid(List<T> people) { ... }

Bounds work on classes too: class Statistics<T extends Number> — new Statistics<String>(...) won't compile.

3.5 Wildcards — ?, ? extends, ? super

The surprise that makes wildcards necessary

Integer is a Number. So surely a List<Integer> is a List<Number>? No!

List<Integer> quantities = new ArrayList<>(List.of(10, 20));
List<Number> nums = quantities;   // ❌ incompatible types: List<Integer> cannot be converted to List<Number>

Why? If it were allowed, this would compile:

nums.add(3.14);                     // a Double is a Number, so List<Number> accepts it...
Integer q = quantities.get(2);      // ...but quantities is a List<Integer> → 💥

Java protects you by making generic types invariant: List<Integer> and List<Number> are unrelated types. But then how do we write one method total(...) that accepts a list of Integers and a list of Doubles? With wildcards.

WildcardRead asAcceptsCan READ asCan ADD
List<?>"list of something"Any listObjectNothing (only null)
List<? extends Number>"list of Number or a subtype"List<Integer>, List<Double>, List<Number>Number ✅Nothing ❌
List<? super Integer>"list of Integer or a supertype"List<Integer>, List<Number>, List<Object>Object onlyInteger ✅

? extends — for reading (the list "produces" values for you)

static double total(List<? extends Number> numbers) {
    double sum = 0;
    for (Number n : numbers) sum += n.doubleValue();   // safe: whatever it is, it's a Number
    // numbers.add(5);   ❌ it might really be a List<Double> - adding an Integer would break it
    return sum;
}

total(List.of(10, 20, 30));   // ✅ List<Integer>
total(List.of(1.25, 2.5));    // ✅ List<Double>

? super — for writing (the list "consumes" values you give it)

static void addOneTwoThree(List<? super Integer> target) {
    target.add(1);     // safe: the list holds Integer or something bigger (Number, Object)
    target.add(2);
    target.add(3);
    // Integer x = target.get(0);   ❌ it might be a List<Object> - reads give Object only
}

addOneTwoThree(new ArrayList<Integer>());   // ✅
addOneTwoThree(new ArrayList<Number>());    // ✅
addOneTwoThree(new ArrayList<Object>());    // ✅
addOneTwoThree(new ArrayList<Double>());    // ❌ Double is not a parent of Integer

PECS — the one rule to remember

💡 PECS = Producer Extends, Consumer Super
  • If a parameter gives you values (you read from it) → it's a Producer → ? extends T.
  • If a parameter takes values (you write into it) → it's a Consumer → ? super T.
  • Both read and write → no wildcard, use exact T.
Shopping analogy: the shop shelf produces items (you take from it — extends); your shopping bag consumes items (you put into it — super). 
// The classic: same shape as java.util.Collections.copy
static <T> void copy(List<? extends T> source, List<? super T> destination) {
    for (T item : source) {
        destination.add(item);
    }
}

copy(dogs, shelter);   // read Dogs from List<Dog>, write them into List<Animal>
List<Dog>
producer: ? extends Animal→ copy → List<Animal>
consumer: ? super Dog
ℹ️ Where to use wildcardsWildcards belong in method parameters (to make your methods flexible). Don't use them in return types or variable declarations — callers would get an awkward List<? extends X> they can't add to.

3.6 Type erasure (simple version)

Here's a secret: generics exist only at compile time. The compiler checks all your <T> rules, inserts the casts you used to write by hand, and then erases the type arguments. At runtime, List<String> and List<Integer> are both just ArrayList.

Your code:
List<String> names→ javac checks types → Bytecode:
List names + (String) casts→ JVM runs → No idea about <String>

Why? Backward compatibility: in 2004 there were millions of lines of pre-generics Java code and libraries. Erasure let old and new code run together on the same JVM.

Consequences (limits) you should know:

You can't…BecauseInstead
new T()At runtime nobody knows what T isPass a Class<T> ("type token") or a factory
new T[10]SameList<T>, or Array.newInstance(type, n)
x instanceof List<String>Runtime only sees Listx instanceof List<?>
Overload save(List<String>) and save(List<Integer>)Both erase to save(List): "name clash: same erasure"Use different method names
static T value;One static field is shared by Box<String>, Box<Integer>…Make it non-static, or use a generic static method
Box<int>Erased T becomes Object; primitives aren't ObjectsBox<Integer>
List<String> names = new ArrayList<>();
List<Integer> numbers = new ArrayList<>();
names.getClass() == numbers.getClass();   // true - both are just ArrayList at runtime
⚠️ Raw types switch the safety offA method that takes a raw List can put a String into your List<Integer> ("heap pollution"). The crash happens much later, when you read it. That's why the compiler warns about raw types — never ignore those warnings.

3.7 Generic interfaces — Repository<T, ID>

Interfaces can be generic too. This is exactly how Spring Data works, so let's build a tiny version:

Example07_GenericRepository.javainterface Repository<T, ID> {
    T save(T entity);
    Optional<T> findById(ID id);
    List<T> findAll();
    boolean existsById(ID id);
    void deleteById(ID id);
    long count();
}

T = the entity type (Student, Book…). ID = the type of its id (Integer, String, Long…). Now one implementation serves every entity:

interface Entity<ID> {
    ID getId();
}

class InMemoryRepository<T extends Entity<ID>, ID> implements Repository<T, ID> {
    protected final Map<ID, T> store = new LinkedHashMap<>();

    public T save(T entity) {
        store.put(entity.getId(), entity);   // works because T extends Entity<ID>
        return entity;
    }

    public Optional<T> findById(ID id) {
        return Optional.ofNullable(store.get(id));
    }
    ...
}

Repository<Book, String> books = new InMemoryRepository<>();
books.findById("ISBN-111");   // ✅
books.findById(5);            // ❌ compile error: ID is String for this repository

A specific repository can extend the generic one and add its own queries:

interface StudentRepository extends Repository<Student, Integer> {
    List<Student> findByYear(int year);
}
ℹ️ Optional<T> in 20 secondsfindById returns an Optional<Student> — a small box that either holds a student or is empty. It forces the caller to think about "not found" instead of getting a surprise null. Useful methods: isPresent(), get(), orElse(default), orElseThrow(). Full lesson in Topic 14.
💡 The Spring Data previewIn Topic 38 you'll write only this: 
public interface StudentRepository extends JpaRepository<Student, Long> {
    List<Student> findByYear(int year);
}
No implementation class at all — Spring generates it at startup. Now you know what <Student, Long> means: T = Student, ID = Long.

3.8 Reading real-world generic signatures

With what you know, you can decode real JDK signatures. Take Collections.max:

public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)
  • <T ...> — a generic method.
  • T extends Comparable<? super T> — T can be compared with T or something above it (a consumer of T's — PECS!).
  • Collection<? extends T> — reads T's from the collection (a producer).
  • Returns a T.

Don't worry if that still looks dense — the point is that every piece follows the rules from this lesson.

4.1 Example02 — static generic factory methods

static <T> ApiResponse<T> success(T data) {
    return new ApiResponse<>(true, data, null);
}

Read it as: "for some type T, return an ApiResponse<T>, given a T". The method is static, so it can't use the class's T — it declares its own. The call ApiResponse.success(new Product(...)) infers T = Product.

Shelf<E>.items() returns List.copyOf(items) — a read-only copy, so outside code can't sneak elements past put.

4.2 Example04 — bounds unlock methods

    return max(people);    // OK: T is Comparable<T>, which is what max() requires
}

Employee implements Payable, Comparable<Employee>, so it satisfies both bounds.

4.3 Example05 — the shelter

feedAll(List<? extends Animal>) accepts both List<Dog> and List<Cat>. Without the wildcard (List<Animal>), neither would be accepted. copy(dogs, shelter) shows PECS: T is inferred as Dog; source is List<? extends Dog>, destination List<? super Dog> = List<Animal>.

4.4 Example06 — type tokens

class Factory<T> {
    private final Class<T> type;          // remembers T at runtime

    T create() throws Exception {
        return type.getDeclaredConstructor().newInstance();   // reflection creates the object
    }
}

new Factory<>(Product.class).create();   // a new Product

Product.class is a runtime object describing the Product class. Because erasure removes T, we hand that object over explicitly. You'll see this pattern in Spring: restClient.get().retrieve().body(Product.class), context.getBean(OrderService.class). Reflection itself is Topic 18.

4.5 Example07 — one implementation, many entities

class InMemoryRepository<T extends Entity<ID>, ID> implements Repository<T, ID> { ... }

class InMemoryStudentRepository extends InMemoryRepository<Student, Integer>
                                implements StudentRepository { ... }

The bound T extends Entity<ID> is what lets save call entity.getId(). Student implements Entity<Integer> and Book implements Entity<String>, so the same code stores both — with full compile-time checking of id types.

The line books.findById("ISBN-999").map(Book::getTitle).orElse("Not in library") is a preview of Optional + method references (Topics 13–14): "if found, take the title; otherwise use this text".

6. Common mistakes

❌ Mistake: using raw types List list = new ArrayList(); or Box b = new Box("x"); — no type checks, casts everywhere, runtime crashes.
Fix: always supply the type: List<String>, Box<String>. Treat "unchecked" / "rawtypes" warnings as errors.
⚠️ Mistake: expecting List<Integer> to be a List<Number> incompatible types: List<Integer> cannot be converted to List<Number>.
Fix: make the parameter List<? extends Number>.
⚠️ Mistake: trying to add to a ? extends list numbers.add(5) on a List<? extends Number> → compile error (int cannot be converted to CAP#1 — "CAP#1" is the compiler's name for "the unknown type").
Fix: use ? super Integer for lists you write into (PECS).
⚠️ Mistake: calling methods on an unbounded T item.getPrice() inside <T> → cannot find symbol.
Fix: add a bound: <T extends Product> (or an interface like <T extends Priced>).
⚠️ Mistake: new T(), new T[n], instanceof T Impossible because of erasure.
Fix: pass a Class<T>, use a List<T>, or let the caller supply objects.
⚠️ Mistake: putting the method's <T> in the wrong place static T <T> first(...) or static first<T>(...) are syntax errors.
Fix: static <T> T first(...) — modifiers, then <T>, then the return type.
⚠️ Mistake: shadowing the class's T Inside class Box<T>, writing a method <T> void put(T x) creates a new, different T that hides the class's T — confusing bugs.
Fix: instance methods should just use the class's T; give method-level parameters different names (<U>).
⚠️ Mistake: over-engineering Making every class generic "just in case" makes code hard to read.
Fix: add generics when you really have 2+ types sharing the same logic.

7. Best practices

  • Never use raw types in new code. Always parameterize: List<Order>, Map<String, Integer>.
  • Use the diamond new ArrayList<>() to avoid repeating types.
  • Use standard names: T, E, K, V, ID, R.
  • Use bounds to express real requirements (T extends Comparable<T>), not to restrict "just because".
  • Apply PECS in method parameters to make APIs flexible; avoid wildcards in return types.
  • Prefer List<T> over T[] in generic code — arrays and generics don't mix well.
  • Use @SuppressWarnings("unchecked") only on the smallest possible scope, with a comment explaining why it's safe.
  • Generic interfaces (like Repository<T, ID>) + one implementation = big reuse. This is exactly how Spring Data, Spring's Converter<S, T> and ResponseEntity<T> are designed.

8. Key takeaways

  • Generics = type parameters; they give type safety (errors at compile time) and remove casts.
  • Generic class: class Box<T>; use: Box<String> b = new Box<>("x");. No primitives — use wrappers.
  • Generic method: static <T> T first(List<T> list); T is inferred from arguments.
  • Bounded type: <T extends Number> lets you call Number's methods; & for multiple bounds.
  • List<Integer> is not a List<Number> (invariance).
  • Wildcards: ? unknown, ? extends T for reading (producer), ? super T for writing (consumer) — PECS.
  • Type erasure: types are checked at compile time then removed; so no new T(), no instanceof List<String>.
  • Repository<T, ID> is the pattern behind Spring Data's JpaRepository<Entity, Id>.

Easy

1. Generic Pair with swap. Write class Pair<A, B> with getFirst(), getSecond() and a method Pair<B, A> swap(). Test with new Pair<>("Asha", 91).

Hint / solution
public class PairDemo {
    public static void main(String[] args) {
        Pair<String, Integer> p = new Pair<>("Asha", 91);
        Pair<Integer, String> s = p.swap();
        System.out.println(p.getFirst() + " " + p.getSecond());   // Asha 91
        System.out.println(s.getFirst() + " " + s.getSecond());   // 91 Asha
    }
}

class Pair<A, B> {
    private final A first;
    private final B second;

    Pair(A first, B second) {
        this.first = first;
        this.second = second;
    }

    A getFirst()  { return first; }
    B getSecond() { return second; }

    Pair<B, A> swap() {
        return new Pair<>(second, first);
    }
}
Easy

2. Generic count. Write a generic method static <T> int countOccurrences(List<T> list, T target) that counts how many elements equals the target. Test with Strings and Integers.

Hint / solution
import java.util.List;

public class CountDemo {
    static <T> int countOccurrences(List<T> list, T target) {
        int count = 0;
        for (T item : list) {
            if (item.equals(target)) count++;
        }
        return count;
    }

    public static void main(String[] args) {
        System.out.println(countOccurrences(List.of("veg", "spicy", "veg"), "veg"));   // 2

3. Bounded average. Write static <T extends Number> double average(List<T> values) that returns 0 for an empty list. Then explain why average(List.of("a")) doesn't compile.

Hint / solution
import java.util.List;

public class AverageDemo {
    static <T extends Number> double average(List<T> values) {
        if (values.isEmpty()) return 0;
        double sum = 0;
        for (T v : values) sum += v.doubleValue();
        return sum / values.size();
    }

    public static void main(String[] args) {
        System.out.println(average(List.of(80, 90, 100)));   // 90.0
        System.out.println(average(List.of(2.5, 3.5)));      // 3.0
        System.out.println(average(List.of()));              // 0.0
    }
}

String is not a subclass of Number, so it's outside the bound T extends Number — the compiler rejects it.

5. Generic cache. Build class SimpleCache<K, V> with put(K, V), Optional<V> get(K), int size() and a maximum size given in the constructor. When full, adding a new key removes the oldest entry. (Hint: a LinkedHashMap keeps insertion order; remove its first key.)

Hint / solution
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Optional;

public class CacheDemo {
    public static void main(String[] args) {
        SimpleCache<String, Double> prices = new SimpleCache<>(2);
        prices.put("Pen", 20.0);
        prices.put("Book", 250.0);
        prices.put("Bag", 899.0);                         // cache full → "Pen" removed
        System.out.println(prices.get("Pen").isPresent()); // false
        System.out.println(prices.get("Bag").orElse(0.0)); // 899.0
        System.out.println(prices.size());                 // 2
    }
}

class SimpleCache<K, V> {
    private final int maxSize;
    private final Map<K, V> data = new LinkedHashMap<>();

    SimpleCache(int maxSize) {
        this.maxSize = maxSize;
    }

    void put(K key, V value) {
        if (!data.containsKey(key) && data.size() == maxSize) {
            K oldest = data.keySet().iterator().next();   // first key = oldest
            data.remove(oldest);
        }
        data.put(key, value);
    }

    Optional<V> get(K key) {
        return Optional.ofNullable(data.get(key));
    }

    int size() {
        return data.size();
    }
}

Spring's caching (Topic 51) is far more powerful, but it's built on the same generic key → value idea.

10. Interview questions

Q1. What are generics and why were they introduced?

Generics (Java 5) let classes, interfaces and methods take type parameters. They provide compile-time type safety, eliminate explicit casts, and enable reusable algorithms and containers that work with many types.

Q2. What is type erasure?

The compiler uses generic type information for checking, inserts necessary casts, and then removes (erases) type arguments from the bytecode; type parameters are replaced by their bound (or Object). It keeps compatibility with pre-generics code. Consequences: no new T(), no generic arrays, no instanceof List<String>, overloads differing only by type argument clash, and List<String>.class doesn't exist.

Q3. Is List<Integer> a subtype of List<Number>?

No. Generic types are invariant. Otherwise you could add a Double to a list of Integers through the List<Number> reference. Use List<? extends Number> to accept lists of any Number subtype. (Arrays, by contrast, are covariant — Integer[] is a Number[] — and fail at runtime with ArrayStoreException.)

Q4. Explain ? extends T vs ? super T (PECS).

? extends T: the list contains T or a subtype — you can safely read T, but can't add. ? super T: the list contains T or a supertype — you can safely add T, but reads return Object. PECS: Producer Extends, Consumer Super. Example: Collections.copy(List<? super T> dest, List<? extends T> src).

Q5. What is a bounded type parameter? Can you have multiple bounds?

<T extends X> restricts T to X or its subtypes (X may be a class or interface) and allows calling X's methods on T. Multiple bounds: <T extends A & B & C>, where at most one is a class and it must be listed first.

Q6. Difference between List<?>, List<Object> and raw List?

List<Object> is a list of Objects — accepts any element but you can only pass an actual List<Object> to it. List<?> is a list of some unknown type — any list can be passed, but you can't add (except null). Raw List disables generic checks entirely (unsafe, legacy only).

Q7. What's the difference between a generic class and a generic method?

A generic class declares type parameters for the whole class, fixed per instance (new Box<String>()). A generic method declares its own type parameters before its return type, chosen per call and usually inferred from arguments; static methods can only be generic this way.

Q8. Why can't you create an instance or array of a type parameter? How do you work around it?

Because of erasure, T isn't known at runtime. Work-arounds: pass a Class<T> type token and use reflection, pass a factory/supplier, or use List<T> instead of T[] (or Array.newInstance).

Q9. Can primitives be used as type arguments?

No. Type arguments must be reference types. Use wrapper classes (Integer, Double…); autoboxing converts automatically (with a small performance cost — which is why specialised types like IntStream exist).

Q10. How do generics appear in Spring Data repositories?

CrudRepository<T, ID> / JpaRepository<T, ID> are generic interfaces: T is the entity type, ID its primary-key type. Declaring interface ProductRepository extends JpaRepository<Product, Long> gives type-safe save(Product), Optional<Product> findById(Long), etc., implemented by Spring at runtime.
