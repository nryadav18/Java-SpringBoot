1. Why this matters

It is 2 a.m. A customer says: "I paid for my pizza but the order never arrived." Your app runs on a server in the cloud. You can't attach a debugger, you can't add breakpoints. The only evidence you have is the log — the diary your application wrote while it was running.

Good logs answer: What happened? When? For which order? Which request? Which error? Bad logs (or no logs) mean hours of guessing.

Why not just System.out.println?

System.out.printlnA real logger
No time stamp, no thread, no class nameEvery line has time, level, thread, class automatically
Always prints — you can't switch it off without changing codeTurn levels up/down per package via configuration, even at runtime
Only goes to the consoleConsole, files, rolling archives, central log systems
No severity — an error looks like a helloLevels: TRACE, DEBUG, INFO, WARN, ERROR
Slow and synchronized for heavy useOptimised, can be asynchronous

In companies, logs are collected into tools like ELK (Elasticsearch + Kibana), Grafana Loki, Splunk or Datadog, where support teams search them. You will see that in topic 65. Every professional Java developer is expected to log well.

2. Real-life analogy

✈️ An aeroplane's black box and the pilot's logbook

A pilot writes a logbook: "10:02 take-off from Hyderabad", "10:45 light turbulence, seat-belt sign on", "11:30 engine 2 warning — switched to backup". Each entry has a time, a severity and a short, clear message.

  • Routine entries ("take-off") = INFO.
  • "Light turbulence" = WARN — unusual, but handled.
  • "Engine warning" = ERROR — needs attention.
  • The engineers' detailed sensor readings = DEBUG/TRACE — normally not printed, but recorded when investigating a problem.
  • The flight number written on every page = the request id (MDC): it lets you pull out every entry belonging to one flight.
  • The logbook never contains passengers' passport numbers = don't log personal data.

3. Concepts step by step

3.1 SLF4J + Logback — "the plug and the socket"

Java has several logging libraries (Logback, Log4j2, java.util.logging). To avoid tying your code to one of them, the Java world uses SLF4J (Simple Logging Facade for Java): an interface you call in your code. Behind it, an implementation does the real writing. Spring Boot's default is Logback.

Your code
log.info(...)→ SLF4J API
org.slf4j.Logger→ Logback
formats & writes→ Console / file

This is "programming to an interface" again (topic 8)! You can switch Logback to Log4j2 by changing dependencies — your code doesn't change. Every Spring Boot starter brings spring-boot-starter-logging (SLF4J + Logback + bridges for other libraries), so you add nothing to the pom.

3.2 Creating a logger — one per class

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@Service
public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void placeOrder() {
        log.info("Order placed");
    }
}
  • private — the logger belongs to this class only.
  • static final — created once and shared, not once per object.
  • OrderService.class — gives the logger the name com.course.loggingdemo.OrderService. Names matter: levels are configured by name (package) later.
⚠️ Import the right Logger! VS Code may offer java.util.logging.Logger or org.apache.logging.... Choose org.slf4j.Logger and org.slf4j.LoggerFactory.
ℹ️ Lombok shortcut (later) From topic 33 you may see @Slf4j on a class: Lombok generates exactly this logger line for you. Same result.

3.3 The five log levels

ERRORSomething failed and needs attention. A request could not be completed."Payment gateway call failed for order 1001"
WARNSomething unexpected, but the app coped. Might become a problem."Invalid quantity 99 rejected", "Retrying call (2/3)"

How filtering works: a logger set to a level prints that level and everything more serious.

3.4 Parameterized logging with {}

// ❌ String concatenation - builds the string EVEN IF debug is switched off
log.debug("Order " + id + " for " + customer + " has " + items.size() + " items");

// ✅ Placeholders - the string is only built if the level is enabled
log.debug("Order {} for {} has {} items", id, customer, items.size());

Each {} is replaced by the next argument, in order. It is shorter, more readable and faster. For truly expensive work (building a big report just for a log), guard it:

if (log.isDebugEnabled()) {
    log.debug("Full report: {}", buildExpensiveReport());
}

3.5 Logging exceptions correctly

try {
    restaurantClient.notify(orderId);
} catch (IllegalStateException ex) {
    log.error("Could not notify restaurant for order {}", orderId, ex);   // ✅ ex LAST, no {} for it
}

When the last argument is an exception, SLF4J prints the message plus the full stack trace. Common wrong versions:

log.error("Failed: " + ex.getMessage());   // ❌ stack trace lost - you won't know WHERE it failed
ex.printStackTrace();                       // ❌ bypasses logging config, goes to System.err
log.error("Failed", ex); throw ex;          // ⚠️ "log and throw" - the same error gets logged twice or more

3.6 Configuring levels in application.properties

# everything: INFO (the default)
logging.level.root=INFO
# our code: more detail
logging.level.com.course.loggingdemo=DEBUG
# a noisy library: quieter
logging.level.org.apache.catalina=WARN
# helpful when debugging requests/SQL:
logging.level.org.springframework.web=DEBUG
logging.level.org.hibernate.SQL=DEBUG

Levels are inherited by package: setting com.course to DEBUG applies to com.course.loggingdemo.OrderService too, unless a more specific setting exists. Because they are normal properties, you can use profiles (topic 29) and command-line args: --logging.level.com.course=TRACE.

Log groups let you name several packages together:

logging.group.food=com.course.loggingdemo,com.course.payments
logging.level.food=TRACE

Spring Boot has built-in groups web and sql: logging.level.web=DEBUG.

3.8 Logging to a file — the easy way

Without any XML, two properties are enough:

logging.file.name=logs/food-delivery.log
logging.logback.rollingpolicy.max-file-size=10MB
logging.logback.rollingpolicy.max-history=7

Spring Boot then writes to the console and the file, and starts a new file ("rolls over") when it reaches 10 MB, keeping 7 days of archives. For most apps, this is enough.

3.9 logback-spring.xml — full control

When you need custom patterns, several files, or different setups per profile, create src/main/resources/logback-spring.xml. Its building blocks:

ElementQuestion it answers
<appender>Where do logs go? (ConsoleAppender, RollingFileAppender…)
<encoder><pattern>How does a line look?
<rollingPolicy>When to start a new file and how many old files to keep?
<logger name="..." level="...">Which package logs at which level?
<root>The default level and appenders for everything
<springProfile name="prod">Settings only for a profile (Spring extension)
<springProperty>Read a value from application.properties (Spring extension)
ℹ️ Why "-spring" in the name? Logback itself would read logback.xml very early, before Spring is ready. With logback-spring.xml, Spring Boot loads it at the right time and adds the <springProfile> and <springProperty> tags. Always use the -spring name in Boot apps.

Pattern cheat sheet:

TokenPrints
%d{yyyy-MM-dd HH:mm:ss.SSS}Date/time
%-5levelLevel, padded to 5 characters so columns line up
%threadThread name
%logger{36}Logger name, shortened to ~36 characters
%msg / %nThe message / new line
%X{requestId}A value from the MDC (next section); %X{requestId:-none} prints "none" if missing
%clr(...)Colour in the console (Spring Boot converter)

Rolling: SizeAndTimeBasedRollingPolicy starts a new file each day or when the size limit is reached, names old files like food-delivery-2026-10-09.0.log.gz (compressed because of .gz), and deletes files older than maxHistory days or beyond totalSizeCap. Without rolling, one log file grows forever and eventually fills the disk — a real cause of production outages.

3.10 MDC — a request id on every line

A web server handles many requests at once. Their log lines get mixed:

10:01:01 INFO  OrderService - Validating order for customer Asha
10:01:01 INFO  OrderService - Validating order for customer Ravi
10:01:01 ERROR OrderService - Payment failed        <-- whose payment??

MDC (Mapped Diagnostic Context) is a small per-thread map provided by SLF4J. Put a value in at the start of a request, and the log pattern %X{requestId} prints it on every line logged on that thread — even from classes that know nothing about HTTP:

10:01:01 INFO  [req:2a546f48] OrderService - Validating order for customer Asha
10:01:01 INFO  [req:7c1e90b3] OrderService - Validating order for customer Ravi
10:01:01 ERROR [req:7c1e90b3] OrderService - Payment failed        <-- Ravi's!
Request arrives→ Filter: MDC.put("requestId", ...)→ Controller → Service logs→ finally: MDC.remove(...)

We put it in a servlet filter — code that runs before every request reaches a controller. Because Tomcat reuses threads, the MDC must be cleared in finally; otherwise the next request on that thread would carry the old id. In microservices (topic 65) the same idea becomes a trace id that travels between services.

3.11 What to log — and what NEVER to log

✅ Do log
  • Business events: order placed, payment succeeded, user registered (with ids).
  • Calls to external systems and their outcome/time.
  • Warnings: rejected input, retries, fallbacks.
  • Errors with stack traces and context (which order? which user id?).
  • Startup information: version, profile, port.
❌ Never log
  • Passwords (even wrong ones!), PINs, OTPs.
  • Full card numbers, CVV, bank account numbers.
  • Access tokens, JWTs, API keys, session ids.
  • Personal data (PII): Aadhaar/PAN/passport numbers, full addresses, phone numbers, health data — mask or omit.
  • Whole request bodies "just in case" — they often contain all of the above.

Laws like GDPR (Europe) and India's DPDP Act treat leaked personal data seriously, and logs are often read by many people and kept for months. If you really need to identify something, log a masked form (************1111) or an internal id instead.

4.1 OrderService — levels in action

src/main/java/com/course/loggingdemo/OrderService.java (key parts)private static final Logger log = LoggerFactory.getLogger(OrderService.class);

public Order placeOrder(String customer, String item, int quantity, String cardNumber) {
    log.trace("placeOrder() called with customer={}, item={}, quantity={}", customer, item, quantity);
    log.debug("Validating order for customer {}", customer);

    if (quantity <= 0 || quantity > MAX_QUANTITY) {
        log.warn("Rejected order from {}: invalid quantity {} (allowed 1-{})", customer, quantity, MAX_QUANTITY);
        throw new IllegalArgumentException("Quantity must be between 1 and " + MAX_QUANTITY);
    }

    log.debug("Charging card {}", maskCard(cardNumber));      // NEVER the full number

    long id = idSequence.incrementAndGet();
    Order order = new Order(id, customer, item, quantity, "PLACED");
    orders.put(id, order);

    log.info("Order {} placed: {} x {} for customer {}", id, quantity, item, customer);
    return order;
}

public void notifyRestaurant(long orderId) {
    try {
        throw new IllegalStateException("Restaurant system timed out");
    } catch (IllegalStateException ex) {
        log.error("Could not notify restaurant for order {}", orderId, ex);   // ex last = stack trace
    }
}

static String maskCard(String cardNumber) {
    if (cardNumber == null || cardNumber.length() < 4) return "****";
    return "*".repeat(cardNumber.length() - 4) + cardNumber.substring(cardNumber.length() - 4);
}

Notice how each message carries context (order id, customer, quantity) — a log line without context ("Error occurred") is almost useless.

4.2 RequestIdFilter — MDC

src/main/java/com/course/loggingdemo/RequestIdFilter.java@Component
public class RequestIdFilter extends OncePerRequestFilter {

    public static final String HEADER = "X-Request-Id";
    public static final String MDC_KEY = "requestId";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String requestId = request.getHeader(HEADER);
        if (requestId == null || requestId.isBlank()) {
            requestId = UUID.randomUUID().toString().substring(0, 8);
        }
        MDC.put(MDC_KEY, requestId);
        response.setHeader(HEADER, requestId);
        try {
            filterChain.doFilter(request, response);   // go on to the controller
        } finally {
            MDC.remove(MDC_KEY);                       // ALWAYS clean up
        }
    }
}
  • OncePerRequestFilter — a Spring base class guaranteeing the filter runs once per request. Being a @Component, Spring Boot registers it automatically.
  • If the caller already sent an X-Request-Id, we reuse it — so one id can follow a request through several services.
  • We return the id in the response header. A customer can quote it to support, and support finds every related line with one search.

4.3 logback-spring.xml

src/main/resources/logback-spring.xml (key parts)<configuration>
    <include resource="org/springframework/boot/logging/logback/defaults.xml"/>
    <springProperty scope="context" name="APP_NAME" source="spring.application.name" defaultValue="app"/>
    <property name="LOG_DIR" value="logs"/>
    <property name="LINE_PATTERN"
              value="%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [req:%X{requestId:-none}] %logger{36} - %msg%n"/>

    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} %clr(%-5level) [%thread] [req:%X{requestId:-none}] %clr(%logger{36}){cyan} - %msg%n</pattern>
        </encoder>
    </appender>

    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_DIR}/${APP_NAME}.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <fileNamePattern>${LOG_DIR}/${APP_NAME}-%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
            <maxFileSize>10MB</maxFileSize>
            <maxHistory>7</maxHistory>
            <totalSizeCap>100MB</totalSizeCap>
        </rollingPolicy>
        <encoder><pattern>${LINE_PATTERN}</pattern></encoder>
    </appender>

    <springProfile name="prod">
        <logger name="com.course.loggingdemo" level="INFO"/>
    </springProfile>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
    </root>
</configuration>

Read it top to bottom: reuse Boot's defaults (for %clr), read the app name from properties, define a pattern, define two appenders (console and rolling file), lower our package to INFO in prod, and send everything at INFO and above to both appenders. The logging.level.* properties are still applied on top, which is why our DEBUG lines appear in dev.

6. Common mistakes

⚠️ Mistake: "my DEBUG messages don't show" The default level is INFO.
Fix: logging.level.your.package=DEBUG. Check that the package name matches your logger's class.
⚠️ Mistake: wrong logger import Using java.util.logging.Logger or Log4j classes directly. Code compiles but formatting/levels behave differently.
Fix: always org.slf4j.Logger + LoggerFactory.
⚠️ Mistake: wrong class in getLogger Copy-pasting LoggerFactory.getLogger(OrderService.class) into PaymentService. Logs now claim to come from the wrong class and level settings get confusing.
⚠️ Mistake: losing the stack trace log.error("Failed: " + ex.getMessage()). You see "Failed: null" and no idea where.
Fix: log.error("Failed to ... {}", id, ex).
⚠️ Mistake: counting the {} wrong log.info("Order {} for {}", id) prints a literal {}. More arguments than {} are ignored (except a final exception).
❌ Mistake: logging secrets or personal data log.info("Login attempt user={} password={}", user, password). Now everyone with log access knows the password.
Fix: never log credentials; mask or skip PII.
⚠️ Mistake: forgetting MDC.remove() Threads are reused, so the next request shows the previous request's id. Always clean up in finally.
⚠️ Mistake: naming the file logback.xml Then <springProfile> doesn't work and it may load before Spring is ready. Use logback-spring.xml.
⚠️ Mistake: DEBUG everywhere in production Gigabytes of logs per hour, slow app, huge storage bills, and real problems hidden in noise. Use INFO in prod and raise levels temporarily when needed (Actuator /loggers, topic 53).

7. Best practices

  • One private static final Logger per class, named after the class.
  • Always use {} placeholders; pass exceptions as the last argument.
  • Pick levels deliberately: INFO tells the story, WARN = handled oddities, ERROR = needs action, DEBUG/TRACE = developer details.
  • Include context (ids, counts, durations): "Order 1001 placed in 120 ms" beats "Done".
  • Log an error once, where it is handled — avoid "log and rethrow" at every layer.
  • Add a correlation/request id with MDC; return it in a response header.
  • Never log secrets or PII; add tests for masking where it matters.
  • Roll and cap log files (size, history, total size cap).
  • In containers, log to the console (stdout) and let the platform collect it (Docker/Kubernetes, topics 66–69). Many teams use JSON logs: Spring Boot 3.4+ supports logging.structured.format.console=ecs (or logstash) for structured output.
  • Different levels per profile: DEBUG in dev, INFO in prod.

8. Key takeaways

  • Use a logger, not System.out: time, level, thread, class, configurable output.
  • SLF4J is the API you call; Logback is Spring Boot's default implementation. Nothing to add to the pom.
  • Levels: TRACE < DEBUG < INFO < WARN < ERROR; default INFO; a level shows itself and everything more serious.
  • log.info("Order {} placed", id); exception as last argument for stack traces.
  • Configure with logging.level.<package>, logging.file.name, or logback-spring.xml for full control.
  • Rolling file appenders prevent full disks.
  • MDC + %X{requestId} ties all lines of a request together; clear it in finally.
  • Never log passwords, tokens, card numbers or personal data.

10. Interview questions

Q1. What is SLF4J and why use it instead of Logback directly?

SLF4J is a logging facade (API). Code depends only on the facade; the actual implementation (Logback, Log4j2…) is chosen by dependencies. This decouples application and library code from a specific logging framework. Spring Boot uses SLF4J with Logback by default.

Q2. Name the log levels in order and when you would use each.

TRACE (very detailed flow), DEBUG (diagnostic details for developers), INFO (normal significant events), WARN (unexpected but handled situations), ERROR (failures needing attention). A logger enabled at a level outputs that level and all higher ones.

Q3. Why are parameterized messages ({}) better than string concatenation?

The message is only formatted if the level is enabled, avoiding wasted string building; they are also cleaner. For expensive argument computation, additionally guard with isDebugEnabled().

Q4. How do you change log levels in Spring Boot?

With logging.level.<logger-name>=LEVEL in properties/YAML, via command-line args or env vars, per profile, in logback-spring.xml, or at runtime via Actuator's /actuator/loggers endpoint.

Q5. What is the difference between logback.xml and logback-spring.xml?

logback.xml is loaded by Logback directly, too early for Spring. logback-spring.xml is loaded by Spring Boot, which enables Spring extensions such as <springProfile> and <springProperty>. Spring recommends the -spring variant.

Q6. What is MDC and how is it used?

Mapped Diagnostic Context — a thread-local key/value map whose values can be printed in the log pattern with %X{key}. Typically a filter puts a request/correlation id at the start of a request and removes it in finally, so all log lines of that request can be correlated.

Q7. What is a rolling file appender?

An appender that switches to a new log file based on time and/or size and deletes or compresses old files according to a policy (e.g., SizeAndTimeBasedRollingPolicy with maxFileSize, maxHistory, totalSizeCap), preventing unbounded log growth.

Q8. What should never be logged?

Credentials (passwords, OTPs), secrets (API keys, tokens, session ids), payment data (card numbers, CVV) and personal data (government ids, contact details, health data). Mask or omit them to comply with security standards (PCI-DSS) and privacy laws (GDPR, DPDP).

Q9. How do you log an exception properly?

Pass the exception as the last argument: log.error("Failed to process order {}", id, ex). This prints the stack trace. Avoid printStackTrace() and logging only getMessage(); avoid logging the same exception at multiple layers.
