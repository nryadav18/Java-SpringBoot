1. Why this matters

Your manager asks: "Log every call to every service method, with its arguments and result. And measure how long the slow ones take." The online shop has 40 service classes with 300 methods. Without AOP you would paste this into every method:

public String placeOrder(String item, int quantity) {
    System.out.println("START placeOrder " + item + ", " + quantity);   // logging
    long start = System.nanoTime();                                     // timing
    try {
        // ... the 3 lines of REAL business logic ...
        System.out.println("END placeOrder returned " + orderId);        // logging
        return orderId;
    } catch (RuntimeException e) {
        System.out.println("placeOrder FAILED: " + e.getMessage());     // logging
        throw e;
    } finally {
        System.out.println("took " + (System.nanoTime() - start) / 1_000_000 + " ms");   // timing
    }
}

Three lines of business logic drowned in fifteen lines of "plumbing" — copied 300 times. Change the log format? Edit 300 methods. Forget one? No logs there.

Logging, timing, security checks, transactions, caching, retries… these are cross-cutting concerns: they cut across many classes, but have nothing to do with the business logic itself. AOP (Aspect-Oriented Programming) lets you write such code once, in one class, and declare where it applies.

Even if you never write an aspect at work, you will use AOP every day: @Transactional (Topic 42), @Cacheable (Topic 51), @Async (Topic 52) and @PreAuthorize (Topic 48) are all implemented with Spring AOP proxies. Understanding proxies explains why they sometimes "don't work".

2. Real-life analogy

🏢 The security desk and CCTV of an office building

The people in an office (your service methods) do their jobs: accounting, design, sales. They don't check visitors' IDs, record who came in, or note the time — the building does that, for every office, at the entrance.

  • The security guard and the CCTV are aspects — one place for a concern that affects all offices.
  • "Check ID before entering", "log the time after leaving", "film the whole visit (around)" are advice — what to do and when.
  • "Only for offices on floors 3–5" or "only for rooms with a red sticker" is a pointcut — where it applies. The red sticker is our custom annotation @LogExecutionTime.
  • Each actual visit to an office is a join point.
  • The reception desk that every visitor must pass through, instead of walking directly into the office, is the proxy.
  • ⚠️ If an employee walks from their office into the office next door through an internal door, they never pass reception — nothing is checked or logged. That's the self-invocation gotcha.

3. Concepts step by step

3.1 Cross-cutting concerns

Picture the application as layers (controllers, services, repositories) drawn as vertical columns. Logging, security and transactions run horizontally across all of them:

Typical cross-cutting concerns: logging/auditing, performance measurement, security checks, transactions, caching, retrying failed calls, input validation, exception translation.

3.2 The AOP vocabulary

AOP has some fancy words. Here they are in plain English, with the matching piece of our project:

TermPlain meaningIn our project

3.3 Switching AOP on

Two things are needed:

  1. The dependency spring-aspects (it brings aspectjweaver, which contains the @Aspect/@Before… annotations and the pointcut language). 
    pom.xml<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-aspects</artifactId>
    <version>6.2.11</version>
</dependency>
  2. @EnableAspectJAutoProxy on a configuration class: 
    config/AppConfig.java@Configuration
@ComponentScan("com.course.aop")
@EnableAspectJAutoProxy
public class AppConfig { }

@EnableAspectJAutoProxy registers a BeanPostProcessor (remember Topic 25!). After each bean is initialised, it asks: "does any aspect's pointcut match a method of this bean?" If yes, it returns a proxy instead of the bean. Everyone who injects that bean gets the proxy.

ℹ️ Spring Boot — add spring-boot-starter-aop and AOP is enabled automatically (no @EnableAspectJAutoProxy needed). Many starters (data-jpa, cache…) already include it.

3.4 Writing an aspect

aspect/LoggingAspect.java@Aspect                 // this class is an aspect
@Component              // ...and a Spring bean - REQUIRED, or Spring never finds it
@Order(2)
public class LoggingAspect {

    @Before("execution(* com.course.aop.service.*.*(..))")
    public void logBefore(JoinPoint joinPoint) {
        System.out.println("[LOG @Before] " + joinPoint.getSignature().getName()
                + " args=" + Arrays.toString(joinPoint.getArgs()));
    }
}

Read it as: "Before the execution of any method of any class in package com.course.aop.service, run logBefore." The JoinPoint parameter gives information about the intercepted call:

MethodReturns
getSignature().getName()Method name, e.g. placeOrder
getSignature().getDeclaringType()The class/interface declaring the method
getSignature().toShortString()e.g. OrderService.generateMonthlyReport()
getArgs()The arguments as Object[]
getTarget() / getThis()The real object / the proxy

3.5 The five advice types

AdviceRuns…Can accessTypical use
@Beforebefore the methodargumentslogging, security/validation checks (throw to block the call)
@AfterReturningafter a normal returnthe return value (returning = "result")log results, audit successful actions
@AfterThrowingafter an exceptionthe exception (throwing = "ex")error logging, alerting, exception translation
@Afterafter the method either way (like finally)argumentsreleasing resources, "finished" logs
@Aroundaround the method — you decide when (and if) it runseverything; can change args and resulttiming, transactions, caching, retry
aspect/LoggingAspect.java@AfterReturning(pointcut = "com.course.aop.aspect.CommonPointcuts.businessLayer()", returning = "result")
public void logAfterReturning(JoinPoint joinPoint, Object result) {        // "result" name must match
    System.out.println("[LOG @AfterReturning] " + methodName(joinPoint) + " returned " + result);
}

@AfterThrowing(pointcut = "com.course.aop.aspect.CommonPointcuts.businessLayer()", throwing = "ex")
public void logAfterThrowing(JoinPoint joinPoint, Exception ex) {          // "ex" name must match
    System.out.println("[LOG @AfterThrowing] " + methodName(joinPoint) + " threw " + ex.getMessage());
}

@After("com.course.aop.aspect.CommonPointcuts.businessLayer()")
public void logAfter(JoinPoint joinPoint) {
    System.out.println("[LOG @After] " + methodName(joinPoint) + " finished (success or not)");
}
ℹ️ @AfterThrowing doesn't swallow the exception It only observes it. The exception continues to the caller (our main() still catches it). To actually handle or replace an exception, use @Around with try/catch.

3.6 @Around — the most powerful advice

aspect/PerformanceAspect.java@Around("com.course.aop.aspect.CommonPointcuts.timedMethods()")
public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
    long start = System.nanoTime();
    try {
        return joinPoint.proceed();          // call the real method - DON'T FORGET THIS!
    } finally {
        long millis = (System.nanoTime() - start) / 1_000_000;
        System.out.println(joinPoint.getSignature().toShortString() + " took " + millis + " ms");
    }
}
  • It receives a ProceedingJoinPoint — a JoinPoint with a proceed() method.
  • proceed() runs the next advice in the chain and finally the real method. If you never call it, the method never runs.
  • You must return the result of proceed() (return type Object), or callers get null.
  • It must declare throws Throwable, because the real method may throw anything.
  • You can call proceed(newArgs) with changed arguments, call it several times (retry!), or skip it and return a cached value. That's exactly how @Cacheable and @Transactional work.
💡 Use the weakest advice that does the job Need only a "before" log? Use @Before. It's simpler and you can't accidentally forget proceed(). Use @Around when you need before and after with shared state (like a start time), or control over the call.

3.7 Pointcut expressions

The most common pointcut designator is execution(...). Its pattern mirrors a method declaration:

execution( modifiers?  return-type  declaring-type?.method-name(params)  throws? )

execution( public      String       com.course.aop.service.OrderService.placeOrder(String, int) )
execution(             *            com.course.aop.service.*.*(..) )
              │          │                  │              │ │  └─ (..) = any number of any parameters
              │          │                  │              │ └─ any method name
              │          │                  │              └─ any class in the package
              │          │                  └─ package
              │          └─ * = any return type
              └─ modifiers are optional
ExpressionMatches
execution(* com.course.aop.service.*.*(..))Any method of any class directly in package service
execution(* com.course.aop..*.*(..)).. in a package = this package and all sub-packages
execution(* com.course.aop.service.*.place*(..))Methods whose name starts with place
execution(public String *(..))Any public method returning String
execution(* *(String, ..))Methods whose first parameter is a String
within(com.course.aop.payment..*)Every method of every class in payment and below

A && B, A || B, !ACombine expressions

Named pointcuts: instead of repeating long expressions, declare them once with @Pointcut on an empty method and refer to them by name:

aspect/CommonPointcuts.javapublic class CommonPointcuts {

    @Pointcut("execution(* com.course.aop.service.*.*(..)) || within(com.course.aop.payment..*)")
    public void businessLayer() { }

    @Pointcut("@annotation(com.course.aop.annotation.LogExecutionTime)")
    public void timedMethods() { }

    @Pointcut("execution(* com.course.aop.service.*.place*(..))")
    public void placingOrders() { }
}

// usage in any aspect (fully qualified name of the pointcut method):
@Before("com.course.aop.aspect.CommonPointcuts.businessLayer()")

Argument binding with args(...) gives you typed parameters instead of an Object[]:

aspect/ValidationAspect.java@Before("com.course.aop.aspect.CommonPointcuts.placingOrders() && args(item, quantity)")
public void checkQuantity(String item, int quantity) {     // names match args(item, quantity)
    if (quantity > 100) {
        throw new IllegalArgumentException("Quantity " + quantity + " too large for " + item);
    }                                                      // throwing here = the real method never runs
}

3.8 A custom annotation as a pointcut: @LogExecutionTime

Package-based pointcuts are "all or nothing". Often you want developers to opt in per method. Create a marker annotation:

annotation/LogExecutionTime.java@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)          // must be RUNTIME so Spring can see it
public @interface LogExecutionTime { }

Bind an @Around advice to @annotation(...) (as in PerformanceAspect), then simply annotate methods:

@LogExecutionTime
public String generateMonthlyReport() throws InterruptedException { ... }

This is exactly the pattern of Spring's own annotations: @Transactional, @Cacheable, @Async, @PreAuthorize are all "markers" that an aspect/interceptor looks for.

3.9 Several aspects on one method: @Order

When several aspects match the same method, @Order on the aspect class decides the nesting. Lower number = outer layer (runs first on the way in, last on the way out):

caller→ @Order(1) PerformanceAspect→ @Order(2) LoggingAspect→ @Order(3) ValidationAspect→ real method

That's why in the output the [TIME] lines surround the [LOG] lines, and why LoggingAspect still logs the exception thrown by the inner ValidationAspect. Within one aspect, don't rely on the order of two advice methods of the same type — split them into separate aspects if order matters.

3.10 How Spring AOP works: proxies

Spring AOP never changes your class's bytecode. It wraps the bean in a proxy — a generated object that looks like your bean, runs the advice, and delegates to the real object:

Spring uses two proxy technologies:

JDK dynamic proxyCGLIB proxy
HowBuilt into the JDK (java.lang.reflect.Proxy). Creates a class that implements the same interfaces as the bean.Generates a subclass of the bean's class at runtime (library bundled inside Spring).
RequiresThe bean implements at least one interfaceThe class isn't final; advised methods aren't final/private
You can inject it as…Only the interface type (PaymentService), not CardPaymentServiceThe class type or any interface
Class name in our outputjdk.proxy3.$Proxy49OrderService$$SpringCGLIB$$0
Used whenPlain Spring default (proxyTargetClass = false) for interface-based beansBeans without interfaces, or always when proxyTargetClass = true — Spring Boot's default

Our demo 1 shows both: OrderService has no interface → CGLIB; CardPaymentService implements PaymentService → JDK proxy. AopUtils tells you which:

App.javaAopUtils.isJdkDynamicProxy(bean);     // true for paymentService
AopUtils.isCglibProxy(bean);          // true for orderService
AopUtils.getTargetClass(bean);        // the real class behind the proxy
⚠️ Limits of Spring AOP (because it uses proxies)
  • Only Spring beans can be advised — not objects you create with new.
  • Only method execution join points (no field access, no constructors).
  • private and final methods can't be intercepted; static methods neither. Keep advised methods public.
  • Calls from inside the same object bypass the proxy — next section.
For the rare cases needing more, the full AspectJ framework weaves bytecode at compile or load time. Spring AOP covers 99% of business needs.

3.11 The self-invocation gotcha ⚠️

This is the most important practical lesson of the topic. Look at placeBulkOrders:

service/OrderService.javapublic List<String> placeBulkOrders(List<String> items) {
    List<String> ids = new ArrayList<>();
    for (String item : items) {
        ids.add(this.placeOrder(item, 1));      // "this" is the TARGET, not the proxy!
    }
    return ids;
}

From main() we call orderService.placeBulkOrders(...) on the proxy → advice runs for placeBulkOrders. The proxy calls the target. Inside the target, this.placeOrder(...) is a plain Java call on the target object itself — it never passes through the proxy, so no advice runs for the inner calls:

main()→ Proxy ✅ advice→ target.placeBulkOrders()→ this. → target.placeOrder() ❌ no advice 
=== DEMO 6a: Self-invocation - inner calls are NOT advised ===
   [LOG  @Before]         OrderService.placeBulkOrders args=[[Cable, Charger]]
      (business logic) saved ORD-2: 1 x Cable
      (business logic) saved ORD-3: 1 x Charger
   [LOG  @AfterReturning] OrderService.placeBulkOrders returned [ORD-2, ORD-3]

Notice also that ValidationAspect would not check the inner calls either — a quantity of 500 would slip through!

🛑 Why this matters so much: @Transactional @Transactional (Topic 42) is implemented with exactly this kind of proxy. If a method in a service calls another @Transactional method of the same class, the inner annotation is silently ignored — no new transaction, no rollback rules. The same applies to @Cacheable, @Async, @PreAuthorize. Countless "Spring bug" reports are really this.

Fixes, best first:

  1. Move the outer method to another bean (our BulkOrderService). It receives the proxy by injection, so each call is advised. Usually also better design.
  2. Inject the bean into itself lazily: public OrderService(@Lazy OrderService self) and call self.placeOrder(...). Works, but looks odd.
  3. AopContext.currentProxy() with @EnableAspectJAutoProxy(exposeProxy = true) — couples your code to Spring AOP; avoid.

6. Common mistakes

⚠️ Mistake: the aspect never runs — missing @Component @Aspect alone does not make a bean. Spring never sees the class.
Fix: @Aspect and @Component (or register it with @Bean).
⚠️ Mistake: the aspect never runs — AOP not enabled In plain Spring, forgetting @EnableAspectJAutoProxy (or the spring-aspects dependency) means no proxies are created.
Fix: add both. In Spring Boot, add spring-boot-starter-aop.
🛑 Mistake: @Around without proceed() or without returning its result The real method never runs, or every caller gets null.
Fix: return joinPoint.proceed(); — always.
⚠️ Mistake: expecting advice on internal calls (self-invocation) this.otherMethod() bypasses the proxy — also for @Transactional, @Cacheable, @Async.
Fix: move the method into another bean and call it through the injected reference.
⚠️ Mistake: advising private or final methods Proxies can't override them, so nothing happens — no error, just silence.
Fix: advised methods should be public and non-final.
⚠️ Mistake: injecting the implementation class of a JDK-proxied bean With proxyTargetClass = false, injecting CardPaymentService (the class) fails with No qualifying bean of type 'com.course.aop.payment.CardPaymentService' available — the bean in the container is a jdk.proxy3.$Proxy49 that only implements PaymentService. (Looking it up by name with getBean("cardPaymentService", CardPaymentService.class) gives BeanNotOfRequiredTypeException instead.)
Fix: inject the interface (PaymentService) — good practice anyway — or use @EnableAspectJAutoProxy(proxyTargetClass = true).
⚠️ Mistake: pointcut too broad execution(* *(..)) matches every method of every bean — including Spring's own infrastructure and your aspects' collaborators. Slow, noisy and sometimes broken startup.
Fix: always restrict to your own packages or annotations.
⚠️ Mistake: custom annotation with default retention Without @Retention(RetentionPolicy.RUNTIME) the annotation isn't visible at runtime, so @annotation(...) never matches.

7. Best practices

  • Use AOP only for genuinely cross-cutting concerns. Business rules belong in business code where people can see them.
  • Prefer annotation-based pointcuts (@LogExecutionTime) for opt-in behaviour, and narrow package-based pointcuts for "whole layer" behaviour.
  • Keep pointcuts in one CommonPointcuts class and reuse them by name.
  • Use the simplest advice type that works; @Around only when needed.
  • Keep advice fast and safe — it runs on every matching call. Never let a logging aspect throw.
  • Set @Order explicitly when several aspects can apply to the same method.
  • In real apps, log with SLF4J (Topic 30), not System.out, and never log passwords or card numbers in argument logs.
  • Remember the proxy rules: public methods, called from another bean.

8. Key takeaways

  • Cross-cutting concerns (logging, security, transactions, caching) are written once in an aspect instead of copied into every method.
  • Aspect = advice (what/when) + pointcut (where). Join point = a method execution. Target = the real object. Proxy = the wrapper. Weaving = linking them (at runtime in Spring).
  • Advice types: @Before, @AfterReturning, @AfterThrowing, @After, @Around (must call proceed() and return its result).
  • Pointcuts: execution(...), within(...), @annotation(...), args(...), bean(...), combined with && || !.
  • Enable with spring-aspects + @EnableAspectJAutoProxy (Boot: spring-boot-starter-aop); aspects need @Aspect + @Component.
  • Spring creates a JDK proxy for interface-based beans and a CGLIB subclass otherwise (Boot uses CGLIB always).
  • Self-invocation bypasses the proxy — the same reason @Transactional on an internally called method is ignored.

Medium

A retry aspect. Create @Retry(times = 3) and an @Around aspect that calls proceed() up to times times when an exception is thrown. Test it with a method that fails the first two calls and succeeds on the third.

Hint / solution 
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Retry { int times() default 3; }

@Aspect
@Component
public class RetryAspect {
    @Around("@annotation(retry)")                 // binds the annotation instance to the parameter
    public Object retry(ProceedingJoinPoint pjp, Retry retry) throws Throwable {
        Throwable last = null;
        for (int attempt = 1; attempt <= retry.times(); attempt++) {
            try {
                return pjp.proceed();
            } catch (Exception e) {
                last = e;
                System.out.println("   attempt " + attempt + " failed: " + e.getMessage());
            }
        }
        throw last;
    }
}

// in a bean:
private int calls = 0;

@Retry(times = 3)
public String callFlakyCourierApi() {
    if (++calls < 3) throw new IllegalStateException("courier API timeout");
    return "courier booked";
}

@annotation(retry) with a parameter named retry binds the actual annotation, so you can read times(). Real projects use Spring Retry or Resilience4j (Topic 64) — built on the same idea.

Without @Lazy, the bean would need itself to be constructed — a circular dependency (Topic 24). @Lazy injects a lazy-resolution proxy that looks up the real (AOP-proxied) orderService bean when first used. 10. Interview questions

Q1. What is AOP and what problem does it solve?

Aspect-Oriented Programming modularises cross-cutting concerns — logic needed in many places but unrelated to business rules (logging, security, transactions, caching, metrics). Instead of scattering and duplicating that code, you write it once in an aspect and declare where it applies with pointcuts. Result: cleaner business code, less duplication, consistent behaviour.

Q2. Explain aspect, advice, join point, pointcut and weaving.

Aspect: a module containing a cross-cutting concern. Advice: the action taken and when (before/after/around). Join point: a point in program execution where advice can apply — in Spring AOP, a method execution. Pointcut: a predicate selecting join points. Weaving: linking aspects with target objects; Spring AOP does it at runtime by creating proxies, AspectJ can do it at compile or load time.

Q3. What advice types exist? When would you use @Around?

@Before, @AfterReturning, @AfterThrowing, @After (finally) and @Around. Use @Around when you need control over the invocation: timing, transactions, caching (skip the call), retries (call several times), modifying arguments or the return value, or translating exceptions. It must call proceed() and return its result.

Q4. How does Spring AOP work internally?

An auto-proxy creator (a BeanPostProcessor registered by @EnableAspectJAutoProxy) checks each bean after initialisation; if any advisor's pointcut matches, it returns a proxy wrapping the bean. Calls on the proxy go through a chain of method interceptors (the advice, ordered by @Order) and finally reach the target.

Q5. JDK dynamic proxy vs CGLIB proxy?

A JDK dynamic proxy implements the target's interfaces and can be used only through those interfaces. A CGLIB proxy is a runtime-generated subclass of the target class, so it works without interfaces but cannot intercept final/private methods or proxy final classes. Plain Spring uses JDK proxies when interfaces exist (unless proxyTargetClass = true); Spring Boot defaults to CGLIB.

Q6. Why doesn't advice (or @Transactional) apply when a method calls another method of the same class?

Self-invocation: the internal call uses this, the target object, so it bypasses the proxy where advice lives. Fixes: move the method to another bean, inject a (lazy) self-reference, or use AopContext.currentProxy() with exposeProxy = true; or use AspectJ weaving.

Q7. Which Spring features are built on AOP?

@Transactional, @Cacheable/@CacheEvict, @Async, method security (@PreAuthorize, @Secured), @Retryable (Spring Retry), @Validated method validation, and Resilience4j annotations in Spring Boot.

Q8. What are the limitations of Spring AOP compared to AspectJ?

Only method-execution join points; only Spring-managed beans; no interception of private/final/static methods or constructors; self-invocation isn't advised; slight runtime overhead of proxies. AspectJ removes these limits at the cost of a special compiler or load-time weaving agent.

Q9. How do you control the order of multiple aspects?

Annotate aspect classes with @Order(n) or implement Ordered. Lower values have higher precedence: they run first on the way in and last on the way out (outermost). Ordering between advice methods of the same type inside one aspect isn't something to rely on — split them into separate aspects.

Q10. Write a pointcut matching all public methods of classes annotated with @Service in package com.shop.

execution(public * com.shop..*.*(..)) && @within(org.springframework.stereotype.Service)
