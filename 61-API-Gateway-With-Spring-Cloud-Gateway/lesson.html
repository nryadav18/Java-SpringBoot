Give your whole system ONE front door: route requests to the right service, rewrite paths, add headers, log and protect every call in one place.

1. Why this matters

After Topic 60, services find each other by name. But what about the outside world – the React website, the Android app, a partner company?

  • They would need to know every service address: products on 8081, orders on 8082, users on 8083… With 30 services that's 30 URLs, and they change.
  • Each service would have to implement authentication, CORS, logging, rate limiting itself – 30 copies of the same code, 30 chances for a security hole.
  • You can't freely reorganise services (split, merge, rename) without breaking every mobile app already installed on users' phones.
  • Internal services would be exposed directly to the internet.

An API gateway fixes all of this: clients talk to one address (e.g. https://api.myshop.com), and the gateway forwards each request to the right service. Practically every microservice system in industry has one – Spring Cloud Gateway, Kong, NGINX, AWS API Gateway, Azure APIM… The ideas you learn here are the same everywhere.

2. Real-life analogy

🏨 The hotel reception

When you arrive at a big hotel, you don't walk into the kitchen, the laundry or the manager's office yourself. You go to reception (= the gateway), the single front door.

  • You say "I'd like room service" – reception routes your request to the kitchen (= route + predicate: "requests about food go to the kitchen").
  • Reception checks your room key card before passing anything on (= authentication filter).
  • They write your request in the log book with a ticket number (= logging filter + correlation id).
  • They translate "I want breakfast in my room" into the kitchen's internal form "ORDER-RS-204" (= RewritePath / headers).
  • If one guest calls 200 times a minute, reception politely refuses (= rate limiting).

The kitchen can move to another floor, hire more cooks or change its internal process – guests don't notice anything. They always talk to reception.

3.2 Spring Cloud Gateway – reactive and servlet flavours

Spring Cloud Gateway is built on Spring WebFlux and runs on Netty (non-blocking, Topic 55). A gateway mostly waits for other services, so a non-blocking server that handles thousands of connections with a few threads is a great fit.

Since Spring Cloud 2025.0 the artifacts were renamed to make the flavour explicit:

Artifact (2025.0)Runs onNotes
spring-cloud-starter-gateway-server-webfluxWebFlux / Netty (reactive)We use this. The classic, most-used gateway.
spring-cloud-starter-gateway-server-webmvcSpring MVC / Tomcat (servlet)Newer flavour, routes written differently (functional or YAML).
spring-cloud-starter-gatewayWebFluxThe old name – still resolves in 2025.0 but is deprecated.

The configuration prefix also moved: spring.cloud.gateway.server.webflux.routes. Older tutorials show spring.cloud.gateway.routes – in 2025.0 that old prefix is deprecated (it is on its way out), so always use the new one in new projects.

🛑 Don't add spring-boot-starter-web to the gatewayThe reactive gateway needs WebFlux. If Spring MVC (spring-boot-starter-web) is also on the classpath, Boot starts a servlet app and the gateway fails with an error like "Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway".

3.3 Routes, predicates and filters

A gateway is configured with a list of routes. Each route has:

  • id – a unique name (for logs and the actuator).
  • uri – where to send the request: http://host:port, https://... or lb://service-name (via the load balancer + Eureka).
  • predicates – conditions: "does this request belong to this route?" All must be true. (A predicate is just a yes/no test – like Predicate<T> in Topic 13.)
  • filters – changes applied to the request on the way in and/or the response on the way out.
Request→ Route predicate handler mapping
which route matches?→ Filter chain (pre)
global + route filters→ Proxied service→ Filter chain (post)→ Response

3.4 lb:// and the discovery locator

uri: lb://product-service means: "ask Spring Cloud LoadBalancer (which asks Eureka) for an instance of product-service". So the gateway also gets load balancing for free. This needs the Eureka client starter in the gateway.

The discovery locator (discovery.locator.enabled: true) goes one step further: it automatically creates a route for every registered service, using the service id as the first path part:

http://localhost:8080/product-service/api/products/3   →   product-service  /api/products/3

Great for learning and quick tests. In production most teams prefer explicit routes so they control exactly what is public.

3.5 Global filters vs route filters, and the reactive style

  • Route filters (GatewayFilter) apply only to the routes where you list them.
  • Global filters (GlobalFilter beans) apply to every route. Perfect for logging, auth, correlation ids. The order is set with Ordered.getOrder() – lower numbers run first (on the way in) and last (on the way out).

A filter has one method: Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain).

  • ServerWebExchange – holds the request and the response (the reactive cousin of HttpServletRequest/Response).
  • chain.filter(exchange) – "pass it on to the next filter / the service".
  • Mono<Void> – "a promise that this work finishes later, with no value". You return it; you never block on it.
  • Code before chain.filter(...) = "pre" (on the way in); code in .then(...) = "post" (on the way out).
  • To stop a request: set a status on the response and return exchange.getResponse().setComplete(); – the service is never called.
⚠️ Never block in a gateway filterNo Thread.sleep, no JDBC call, no blocking RestClient. The gateway has only a few event-loop threads; blocking one freezes many requests. Use reactive APIs (WebClient, reactive Redis).

3.6 Rate limiting (mention)

Rate limiting = "each client may only make N requests per time unit". It protects services from abuse and accidental floods (a buggy app in a retry loop). Spring Cloud Gateway has the RequestRateLimiter filter using a token bucket algorithm stored in Redis (so all gateway instances share the counters):

# needs spring-boot-starter-data-redis-reactive + a running Redis (Topic 51)
filters:
  - name: RequestRateLimiter
    args:
      redis-rate-limiter.replenishRate: 10    # 10 tokens added per second
      redis-rate-limiter.burstCapacity: 20    # bucket size (short bursts allowed)
      key-resolver: "#{@userKeyResolver}"     # a KeyResolver bean: who is "the client"?

When the bucket is empty the gateway answers 429 Too Many Requests. We don't run it in this project to avoid needing Redis – Exercise 6 lets you try it.

Some details:

  • RewritePath=/shop/(?<segment>.*), /api/$\{segment} – a Java regex with a named group segment. /shop/products/2 → segment = products/2 → new path /api/products/2. In YAML you write $\{segment} (with a backslash) so Spring doesn't treat ${...} as a property placeholder.
  • The rewrite route lists two path patterns so /shop/products (no trailing part) also matches.
  • Routes are checked in order; the first match wins. Put specific routes before general ones.
  • No route matches → the gateway itself answers 404.

4.3 LoggingGlobalFilter – correlation id and timing

api-gateway/src/main/java/com/course/gateway/apigateway/LoggingGlobalFilter.java@Component
public class LoggingGlobalFilter implements GlobalFilter, Ordered {

    private static final Logger log = LoggerFactory.getLogger(LoggingGlobalFilter.class);
    public static final String CORRELATION_HEADER = "X-Correlation-Id";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        long start = System.currentTimeMillis();

        // ---- ON THE WAY IN ----
        String correlationId = exchange.getRequest().getHeaders().getFirst(CORRELATION_HEADER);
        if (correlationId == null || correlationId.isBlank()) {
            correlationId = UUID.randomUUID().toString();
        }
        final String id = correlationId;

        // requests are immutable -> build a modified copy
        ServerHttpRequest requestWithId = exchange.getRequest().mutate()
                .header(CORRELATION_HEADER, id)
                .build();
        ServerWebExchange newExchange = exchange.mutate().request(requestWithId).build();
        newExchange.getResponse().getHeaders().add(CORRELATION_HEADER, id);

        log.info("--> {} {} (correlationId={})",
                requestWithId.getMethod(), requestWithId.getURI().getPath(), id);

        // ---- pass on, then ON THE WAY OUT ----
        return chain.filter(newExchange).then(Mono.fromRunnable(() -> {
            long tookMs = System.currentTimeMillis() - start;
            log.info("<-- {} {} status={} took={}ms",
                    requestWithId.getMethod(), requestWithId.getURI().getPath(),
                    newExchange.getResponse().getStatusCode(), tookMs);
        }));
    }

    @Override
    public int getOrder() {
        return Ordered.HIGHEST_PRECEDENCE;   // run first
    }
}

Step by step:

  1. Read X-Correlation-Id from the request; create a UUID if the client didn't send one.
  2. Request objects are immutable, so mutate() creates a copy with the extra header, and we build a new exchange around it.
  3. We also put the id on the response so the client (and support team) can quote it.
  4. chain.filter(newExchange) continues the chain and returns a Mono that completes when the response is done. .then(Mono.fromRunnable(...)) runs our "after" code at that moment.

Log output looks like:

INFO ... LoggingGlobalFilter : --> GET /api/products/1 (correlationId=f6444f3e-122a-4468-b11d-a89a1f294be1)
INFO ... LoggingGlobalFilter : <-- GET /api/products/1 status=200 OK took=21ms

In Topic 65 you'll replace this home-made id with real distributed tracing (trace ids propagated automatically).

4.4 ApiKeyGlobalFilter – stopping a request

api-gateway/src/main/java/com/course/gateway/apigateway/ApiKeyGlobalFilter.java@Override
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    ServerHttpRequest request = exchange.getRequest();
    boolean isCreateOrder = HttpMethod.POST.equals(request.getMethod())
            && request.getURI().getPath().startsWith("/api/orders");

    if (isCreateOrder) {
        String givenKey = request.getHeaders().getFirst("X-API-KEY");
        if (!expectedApiKey.equals(givenKey)) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();   // stop: service never called
        }
    }
    return chain.filter(exchange);                         // allowed: continue
}

@Override
public int getOrder() {
    return Ordered.HIGHEST_PRECEDENCE + 1;                 // right after logging
}

The key comes from gateway.api-key in application.yml (injected with @Value). In real life you would validate a JWT here (Spring Security for WebFlux with oauth2-resource-server, Topic 50) and forward the user id to the services in a header.

4.5 product-service and order-service

They are the Topic 60 services with small additions. product-service shows which headers arrived:

product-service/src/main/java/com/course/gateway/product/ProductController.java@GetMapping("/headers")
public Map<String, String> showGatewayHeaders(
        @RequestHeader(value = "X-Request-Source", defaultValue = "(none - you called me directly)") String source,
        @RequestHeader(value = "X-Correlation-Id", defaultValue = "(none)") String correlationId) {
    Map<String, String> result = new LinkedHashMap<>();
    result.put("servedBy", instanceName);
    result.put("X-Request-Source", source);        // from AddRequestHeader
    result.put("X-Correlation-Id", correlationId); // from LoggingGlobalFilter
    return result;
}

order-service stores the X-Request-Source header in each order (requestSource), so you can see whether an order came through the gateway or directly. Note that order-service calls product-service directly by name (@LoadBalanced RestClient) – internal service-to-service calls usually don't go back out through the public gateway.

6. Common mistakes

🛑 Mistake: adding spring-boot-starter-web to the gatewayStartup fails ("Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway") or the gateway doesn't route.
Fix: the reactive gateway uses WebFlux only. Remove starter-web (or use the separate gateway-server-webmvc flavour on purpose).
⚠️ Mistake: routes are ignored (every request is 404)You used an old tutorial's prefix spring.cloud.gateway.routes, or wrong YAML indentation.
Fix: use spring.cloud.gateway.server.webflux.routes for 2025.0 and check /actuator/gateway/routes to see what was loaded.
⚠️ Mistake: 503 Service Unavailable right after startupThe gateway log says No servers available for service: product-service – the gateway's Eureka cache doesn't know the service yet.
Fix: wait 10–30 s (or start the gateway last); check the Eureka dashboard.
⚠️ Mistake: RewritePath with ${segment} in YAMLSpring tries to resolve ${segment} as a property and fails ("Could not resolve placeholder").
Fix: write $\{segment} in YAML/properties.
⚠️ Mistake: path doesn't match the service's pathPath=/products/** forwards /products/1, but the service expects /api/products/1 → 404 from the service.
Fix: keep paths aligned or add RewritePath/PrefixPath/StripPrefix.
⚠️ Mistake: blocking code in a filterCalling a JDBC repository or a blocking RestClient inside a GlobalFilter stalls the event loop; the whole gateway slows down.
Fix: use reactive clients (WebClient, reactive Redis) and return Monos.
⚠️ Mistake: services still reachable directlyThe gateway checks the API key, but anyone who knows :8082 can skip it.
Fix: in production, put services in a private network (Docker network, Kubernetes, VPC) so only the gateway is public – and let services validate tokens too ("zero trust").

7. Best practices

  • Keep the gateway thin: routing and cross-cutting concerns only – no business logic.
  • Prefer explicit routes over the discovery locator in production; expose only what clients need.
  • Do authentication at the gateway (JWT/OAuth2) and pass identity downstream; services still authorize what the user may do.
  • Add timeouts (spring.cloud.gateway.server.webflux.httpclient.connect-timeout/response-timeout) and circuit breakers to routes.
  • Use rate limiting for public APIs (429 + Retry-After).
  • Generate or forward a correlation/trace id for every request (Topic 65).
  • Run several gateway instances behind a cloud load balancer – the gateway must not be a single point of failure.
  • Configure CORS once at the gateway (globalcors) instead of in every service.
  • Version public APIs (/api/v1/...) and use rewrite rules to evolve internal paths without breaking clients.
  • Watch /actuator/gateway/routes and gateway metrics (Micrometer) in your monitoring.

8. Key takeaways

  • An API gateway is the single entry point: clients know one address, services stay hidden and free to change.
  • It centralises cross-cutting concerns: routing, load balancing, auth, rate limiting, CORS, logging.
  • Spring Cloud Gateway is reactive (WebFlux + Netty). For 2025.0 use spring-cloud-starter-gateway-server-webflux and the spring.cloud.gateway.server.webflux.* prefix.
  • A route = id + uri + predicates (when) + filters (what to change).
  • lb://service-name resolves instances through Eureka and load-balances.
  • Built-in filters: AddRequestHeader, AddResponseHeader, RewritePath, StripPrefix, Retry, CircuitBreaker, RequestRateLimiter…
  • A custom GlobalFilter runs for every route; code before chain.filter() is "pre", .then(...) is "post"; setComplete() stops a request.
  • Never block inside the gateway; keep it free of business logic.

9. Practice exercises

Easy

Versioned public path. Add a route so GET /api/v1/products/1 reaches product-service's /api/products/1.

Hint / solution
- id: products-v1
  uri: lb://product-service
  predicates:
    - Path=/api/v1/products/**
  filters:
    - RewritePath=/api/v1/(?<segment>.*), /api/$\{segment}

Put it before any route that would also match. Check it in /actuator/gateway/routes.

Easy

Method predicate. Make the order-route accept only GET and POST. What happens with DELETE /api/orders/1?

Hint / solution
predicates:
  - Path=/api/orders/**
  - Method=GET,POST

Both predicates must be true. A DELETE matches no explicit route; the discovery locator only matches /order-service/**, so the gateway answers 404.

Medium

Response-time header. Extend LoggingGlobalFilter to add a response header X-Response-Time-Ms. Careful: headers can only be changed before the response is committed.

Hint / solution
newExchange.getResponse().beforeCommit(() -> {
    long took = System.currentTimeMillis() - start;
    newExchange.getResponse().getHeaders().add("X-Response-Time-Ms", String.valueOf(took));
    return Mono.empty();
});
return chain.filter(newExchange).then(...);

beforeCommit runs just before the status and headers are sent – the last safe moment to add headers.

Medium

Custom route filter. Write a GatewayFilterFactory named BlockWeekend that you can add to a single route (- BlockWeekend) and that returns 503 on Saturdays and Sundays.

Hint / solution
@Component
public class BlockWeekendGatewayFilterFactory
        extends AbstractGatewayFilterFactory<Object> {

    @Override
    public GatewayFilter apply(Object config) {
        return (exchange, chain) -> {
            DayOfWeek day = LocalDate.now().getDayOfWeek();
            if (day == DayOfWeek.SATURDAY || day == DayOfWeek.SUNDAY) {
                exchange.getResponse().setStatusCode(HttpStatus.SERVICE_UNAVAILABLE);
                return exchange.getResponse().setComplete();
            }
            return chain.filter(exchange);
        };
    }
}

The class name must end with GatewayFilterFactory; the part before it (BlockWeekend) is the name you use in YAML.

10. Interview questions

Q1. What is an API gateway and why do microservices need one?

A server that is the single entry point for clients. It routes requests to backend services and handles cross-cutting concerns (authentication, rate limiting, CORS, logging, SSL termination, request/response transformation). It hides the internal topology, reduces client complexity and avoids duplicating these concerns in every service.

Q2. Explain route, predicate and filter in Spring Cloud Gateway.

A route is the basic building block: id, destination URI, predicates and filters. Predicates are conditions on the request (path, method, header, host, time…) that decide whether a route matches. Filters modify the request before it is sent downstream and/or the response afterwards (headers, path rewrite, retry, circuit breaker, rate limit).

Q3. GlobalFilter vs GatewayFilter?

A GlobalFilter applies to all routes automatically (ordered via Ordered). A GatewayFilter (usually created by a GatewayFilterFactory) is attached to specific routes in configuration. Both are merged into one ordered chain per request.

Q4. Why is Spring Cloud Gateway reactive? What does that mean for your code?

A gateway is I/O-bound: it mostly waits on downstream services. WebFlux/Netty handles many concurrent connections with a small number of event-loop threads. Consequently filters must be non-blocking, return Mono<Void>, and use reactive clients; blocking calls would starve the event loop. (Since 2023.0 there is also a servlet-based "Gateway Server MVC".)

Q5. What does lb://product-service mean?

The URI scheme lb tells the gateway to resolve the service id through Spring Cloud LoadBalancer, which gets instances from the discovery client (Eureka) and picks one (round-robin by default).

Q6. How would you implement authentication at the gateway?

Use Spring Security WebFlux with oauth2-resource-server in the gateway to validate JWTs (signature, expiry, issuer), reject invalid requests with 401, and forward the token or extracted user claims downstream. Or use the TokenRelay filter with an OAuth2 client login. Services should still verify authorization for their own resources.

Q7. How does rate limiting work in Spring Cloud Gateway?

The RequestRateLimiter filter with RedisRateLimiter implements a token bucket per key (resolved by a KeyResolver, e.g. user id, API key or IP). replenishRate tokens are added per second up to burstCapacity; each request consumes tokens; when empty it returns 429. Redis keeps counters consistent across gateway instances.

Q8. API gateway vs load balancer vs service mesh?

A load balancer (L4/L7) distributes traffic among instances of one service. An API gateway is an L7 entry point with routing across many services plus API concerns (auth, rate limiting, transformations) for north-south (client→system) traffic. A service mesh (Istio, Linkerd) handles east-west (service→service) traffic with sidecar proxies for mTLS, retries and observability.

Q9. What is the discovery locator?

A feature that automatically creates a route for each service in the discovery registry: /{serviceId}/** → lb://{serviceId} with the prefix stripped. Convenient, but it exposes every registered service, so production systems usually define explicit routes.

Q10. Doesn't the gateway become a single point of failure / bottleneck?

It can, so you run multiple stateless gateway instances behind a cloud/hardware load balancer, keep it free of heavy logic, use non-blocking I/O, set timeouts and circuit breakers so a slow service cannot exhaust it, and monitor it closely.
