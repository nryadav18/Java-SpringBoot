1. Why this matters

Until now, every program you wrote did one thing at a time: line 1, then line 2, then line 3. That is fine for small programs. But real software must often do many things at once:

  • A web server must answer 500 users at the same moment. It cannot say "please wait, I am busy with another user".
  • A food-delivery app loads the restaurant list, your address, and your offers all at once, so the screen appears quickly.
  • A bank processes thousands of transfers per second and must never lose a single rupee, even when two transfers touch the same account.

Java has supported this from day one through threads. And here is the big reason this topic is in a Spring Boot course:

ℹ️ The Spring Boot connection When you build a REST API with Spring Boot, it runs inside an embedded web server called Tomcat. Tomcat keeps a pool of threads (200 by default). Every HTTP request is handled by one of these threads. So your controller and service code is always running on many threads at the same time — even if you never write the word Thread. If you don't understand thread safety, you can write bugs that appear only when many users use your app. Later you will also use @Async and @Scheduled (Topic 52), which are built on the thread pools you learn today.

Interviewers love this topic too: "What is a race condition?", "synchronized vs volatile?", "What is a deadlock?" are very common questions for Java backend jobs.

2. Real-life analogy

🍳 A restaurant kitchen
  • The restaurant is a process — it has its own building, fridge and money (its own memory).
  • Each cook is a thread — cooks work at the same time inside the same kitchen and share the same fridge (they share memory).
  • If two cooks grab the last tomato at the same moment, there is a fight — that is a race condition.
  • A rule "only one cook may open the fridge at a time; take the fridge key first" is synchronized (a lock).
  • Hiring a new cook for every single order would be crazy and slow. Instead, the restaurant keeps 3 cooks and gives them orders from a queue — that is a thread pool (ExecutorService).
  • When you order, you get a token number. You can do other things and collect your food later — that token is a Future.
  • Cook A holds the knife and waits for the cutting board; Cook B holds the cutting board and waits for the knife. Both wait forever — a deadlock.

3. Concepts step by step

3.1 Process vs Thread

A process is a running program. When you open Chrome and VS Code, you have (at least) two processes. Each process has its own memory; one process cannot simply read another's variables.

A thread is a "path of execution" inside a process — a worker that runs your code line by line. One process can have many threads, and all threads in a process share the same heap memory (the same objects).

ProcessThread
What is it?A running programA worker inside a program
MemoryOwn, separate memoryShares heap (objects) with other threads of the same process; has its own stack (local variables)
Cost to createHeavy (slow)Lighter (but not free!)
CommunicationHard (files, network, pipes)Easy (shared objects) — but dangerous if not careful
ExampleYour Spring Boot app (one JVM)Each request handler thread inside it

Every Java program starts with one thread called main. It runs your main method. You can create more threads from there.

💡 Important rule to remember Local variables (inside a method) live on the thread's own stack → each thread has its own copy → always safe.
Fields of objects live on the shared heap → many threads can see the same object → this is where bugs happen.

3.2 Concurrency vs Parallelism

Two words you will hear a lot:

  • Concurrency = dealing with many tasks at once (they make progress by taking turns). One cook who switches between 3 pans is concurrent.
  • Parallelism = really doing many tasks at the exact same moment. Three cooks with three pans are parallel. This needs multiple CPU cores.

Your laptop probably has 4–16 cores, so Java threads can run truly in parallel. The operating system's scheduler decides which thread runs on which core and when. You cannot control the order — that is why output order changes between runs.

3.3 Creating threads — three ways

Way 1: extend Thread and override run(). run() holds the job.

class DownloadThread extends Thread {
    @Override
    public void run() {
        System.out.println("Downloading in " + Thread.currentThread().getName());
    }
}

Thread t1 = new DownloadThread();
t1.start();   // creates a NEW thread, which then calls run()

Way 2: implement Runnable. Runnable is just a task with one method void run(). You give the task to a Thread (the worker).

class EmailTask implements Runnable {
    @Override
    public void run() {
        System.out.println("Sending email...");
    }
}

Thread t2 = new Thread(new EmailTask(), "emailer");   // task + optional name
t2.start();

Way 3: lambda. Runnable is a functional interface (one abstract method — you learned this in Topic 13), so a lambda is the shortest way:

Thread t3 = new Thread(() -> System.out.println("Resizing photo..."), "photo-worker");
t3.start();
WayProsCons
extends ThreadSimple to readYour class can't extend anything else (Java has single inheritance); mixes "task" and "worker"
implements RunnableTask is separate from worker; class can extend another class; the same task can be given to a thread poolA bit more typing
Lambda (Runnable)Shortest; most common in modern codeLong logic inside a lambda becomes hard to read — move it to a method
🚫 start() vs run() — the #1 beginner trap t.start() creates a new thread and that new thread calls run().
t.run() is just a normal method call — it runs in the current thread. No new thread is created! Example01 shows this: calling run() prints [main].
Also: you can call start() only once per Thread object. A second call throws IllegalThreadStateException.

3.4 The thread lifecycle

A thread moves through states. You can ask for the state with t.getState(). The states are values of the enum Thread.State:

StateMeaning in simple wordsHow it gets there
NEWThread object exists, but not started yetnew Thread(...)
RUNNABLERunning, or ready to run as soon as a CPU core is freestart()
BLOCKEDWaiting to get a lock that another thread holdsTrying to enter a synchronized block that is busy

TIMED_WAITINGWaiting, but only for a limited timeThread.sleep(ms), join(ms)
TERMINATEDFinished — run() has returned (or threw an exception)End of run()

3.5 sleep, join and interrupt

  • Thread.sleep(500) — pause the current thread for 500 milliseconds. It is a static method: it always sleeps the thread that calls it.
  • t.join() — the current thread waits until thread t has finished. Like a parent waiting at the school gate until the child comes out.
  • t.interrupt() — politely ask t to stop. If t is sleeping or waiting, it wakes up with an InterruptedException.
Thread chef = new Thread(() -> {
    try {
        Thread.sleep(300);                     // chef pauses (TIMED_WAITING)
        System.out.println("Pasta is ready!");
    } catch (InterruptedException e) {         // checked exception - must be handled
        System.out.println("Interrupted!");
    }
});
chef.start();
chef.join();                                   // main waits for the chef
System.out.println(chef.getState());           // TERMINATED
ℹ️ Why is InterruptedException checked? Because Java wants you to decide what to do when someone asks your thread to stop. If you cannot handle it properly, the polite thing is to restore the flag: Thread.currentThread().interrupt(); — you will see this in the helper methods of the examples.

3.6 The race condition — the most important bug in this topic

A race condition happens when two or more threads read and change the same shared data at the same time, and the final result depends on who was faster.

Look at this innocent line: likes++;. It looks like one step, but the CPU actually does three:

1. READ likes (e.g. 41)→ 2. ADD 1 (42)→ 3. WRITE likes = 42

Now imagine two threads doing it at the same time:

TimeThread AThread Blikes in memory
1reads 4141
2reads 4141
3adds 1 → 42, writes 4242
4adds 1 → 42, writes 4242 ❌ (should be 43)

One "like" was lost. This is called a lost update. Example03 runs 2 threads × 100,000 clicks and usually gets something like 137,452 instead of 200,000. The number changes on every run — that is what makes these bugs so nasty.

The part of code that touches shared data and must not be run by two threads at once is called the critical section.

3.7 synchronized — one thread at a time

Every Java object has a hidden lock (also called a monitor). The keyword synchronized says: "to enter this code, a thread must first take this object's lock". Only one thread can hold a lock at a time. The others wait in the BLOCKED state.

class SafeLikeCounter {
    private int likes = 0;

    synchronized void like() {      // locks on 'this' object
        likes++;
    }

    synchronized int getLikes() {   // reading also needs the lock to see the latest value
        return likes;
    }
}

You can also lock just a small block instead of the whole method. Smaller locked areas = less waiting = faster:

private final Object lock = new Object();

void like() {
    validate();                 // runs in parallel, no lock needed
    synchronized (lock) {       // only this part is locked
        likes++;
    }
}
FormWhich lock is used
synchronized void m()The object itself (this)
static synchronized void m()The class object (MyClass.class) — one lock for all instances
synchronized (someObject) { ... }someObject
⚠️ Locks have a price Threads waiting for a lock do nothing useful. Lock only what you must, for as short a time as possible. And never call slow things (network, database) while holding a lock if you can avoid it.

3.8 volatile — "always read the fresh value"

For speed, each CPU core has its own cache. A thread may keep reading an old copy of a variable from its cache and never notice that another thread changed it. This is a visibility problem.

Marking a field volatile tells Java: "reads and writes of this variable always go to main memory, so every thread sees the latest value".

private volatile boolean running = true;

public void run() {
    while (running) {   // sees the change made by another thread
        processOrder();
    }
}

public void stop() { running = false; }

3.9 Thread pools with ExecutorService

Creating a new Thread for every small task is expensive (each thread needs memory for its stack, about 1 MB, and time to create). And if 10,000 users arrive, 10,000 threads could crash your machine.

A thread pool creates a fixed number of worker threads once and reuses them. You just submit tasks; they wait in a queue until a worker is free.

Your code: submit(task)→ Task queue [t4, t5, t6...]→ Worker threads (1, 2, 3)→ Result (Future) 
ExecutorService kitchen = Executors.newFixedThreadPool(3);  // 3 cooks

kitchen.submit(() -> System.out.println("Cooking order 1"));  // Runnable: no result
kitchen.submit(() -> System.out.println("Cooking order 2"));

kitchen.shutdown();                                    // stop accepting new tasks
kitchen.awaitTermination(5, TimeUnit.SECONDS);          // wait for running ones to finish
Factory methodWhat you getWhen
Executors.newFixedThreadPool(n)Exactly n threadsMost common; predictable
Executors.newSingleThreadExecutor()1 thread, tasks run one by one in orderBackground jobs that must not overlap
Executors.newCachedThreadPool()Creates threads as needed, reuses idle onesMany short tasks (careful: no upper limit!)
Executors.newScheduledThreadPool(n)Can run tasks after a delay or repeatedlyTimers ("every 10 seconds") — Spring's @Scheduled uses this idea
⚠️ Always shut down your pool Pool threads are not daemon threads: if you forget shutdown(), your program may never exit. (In Spring, the framework manages pools for you and shuts them down when the app stops.)

3.10 Callable and Future — tasks that return a result

Runnable.run() returns void and cannot throw checked exceptions. When you need a result, use Callable<V>, whose method is V call() throws Exception.

When you submit a Callable, you immediately get back a Future<V> — a "token" for a result that will exist later.

Callable<Double> calculateBill = () -> {
    Thread.sleep(200);      // slow work
    return 249.50;
};

Future<Double> futureBill = kitchen.submit(calculateBill);
System.out.println(futureBill.isDone());   // false - still working
Double bill = futureBill.get();            // WAITS here until the result is ready
System.out.println(bill);                  // 249.5
Future methodWhat it does
get()Waits (blocks) and returns the result. Throws ExecutionException if the task failed.
get(2, TimeUnit.SECONDS)Waits at most 2 seconds, else TimeoutException
isDone()Is the task finished?
cancel(true)Try to cancel the task

The weakness of Future: the only way to use the result is to call get() and block. You cannot say "when it's ready, do this next". That is what CompletableFuture fixes.

3.11 CompletableFuture — chaining async steps

CompletableFuture (Java 8+) lets you build a pipeline of steps that run when the previous one finishes, without blocking in between. It feels like the Streams API (Topic 14), but over time.

String title = CompletableFuture
        .supplyAsync(() -> fetchProductName(1))      // 1. start in background
        .thenApply(name -> name.toUpperCase())       // 2. transform when ready
        .thenApply(name -> "*** " + name + " ***")   // 3. transform again
        .join();                                     // 4. wait for the final value
// *** WIRELESS MOUSE ***

thenCombine is the star for backend work: call two services in parallel and combine the answers. Two calls of 300 ms each take ~300 ms total instead of 600 ms:

CompletableFuture<String> nameF  = CompletableFuture.supplyAsync(() -> fetchProductName(1), pool);
CompletableFuture<Double> priceF = CompletableFuture.supplyAsync(() -> fetchPrice(1), pool);

String line = nameF.thenCombine(priceF, (name, price) -> name + " costs Rs." + price).join();
💡 Which threads run supplyAsync? Without a second argument, the shared ForkJoinPool.commonPool(). In real applications pass your own pool: supplyAsync(task, myPool). Spring's @Async methods can return CompletableFuture — you will meet them in Topic 52.

3.12 Thread-safe tools: Atomic classes and ConcurrentHashMap

The package java.util.concurrent gives you ready-made thread-safe classes, so you often don't need synchronized at all.

AtomicInteger / AtomicLong — a number with thread-safe operations. Internally they use a special CPU instruction called compare-and-swap (CAS), which is very fast and needs no lock.

AtomicInteger visits = new AtomicInteger(0);
visits.incrementAndGet();          // safe "++"
visits.addAndGet(10);              // safe "+= 10"
visits.compareAndSet(11, 0);       // "if it is 11, set it to 0" - atomically

ConcurrentHashMap — a Map that many threads can use at the same time. A normal HashMap is not thread-safe: updates get lost and its internal structure can even break.

Map<String, Integer> pageVisits = new ConcurrentHashMap<>();
pageVisits.merge("/home", 1, Integer::sum);                  // atomic "count + 1"
userCache.computeIfAbsent(101, id -> loadUserFromDb(id));    // atomic "load if missing"
⚠️ Thread-safe map ≠ thread-safe code This is still a race, even with ConcurrentHashMap:
if (!map.containsKey(k)) { map.put(k, v); } — two threads can both pass the if.
Use the atomic single-call methods instead: putIfAbsent, computeIfAbsent, merge, compute.
Not thread-safeThread-safe alternative

ℹ️ Immutable objects are always thread-safe If an object can never change after creation (like String, records with immutable fields, LocalDate, List.of(...)), many threads can share it with zero risk. That is one big reason modern Java loves immutability.

3.13 Deadlock

A deadlock happens when two (or more) threads each hold a lock and wait for the lock the other holds. Nobody can move. The program does not crash — it just freezes forever, which is even worse.

Thread 1 holds Account A 🔒→ wants → Account B 🔒 (held by Thread 2)
Thread 2 holds Account B 🔒→ wants → Account A 🔒 (held by Thread 1)

Four conditions are all needed for a deadlock: (1) locks are exclusive, (2) a thread holds one lock while waiting for another, (3) locks can't be taken away by force, (4) there is a circular wait. Break any one and there is no deadlock.

How to avoid it:

  • Lock ordering — always take locks in the same global order (e.g. smaller account id first). This breaks the circular wait. Example08 does exactly this.
  • Timeouts — ReentrantLock.tryLock(1, SECONDS) gives up instead of waiting forever.
  • Hold fewer locks — keep locked areas small; avoid calling other objects' synchronized methods while holding a lock.
  • Use higher-level tools (ConcurrentHashMap, Atomic*, queues) instead of manual locks.

To find a deadlock in a frozen program, take a thread dump: run jstack <pid> (comes with the JDK; find the pid with jps). It prints "Found one Java-level deadlock" with the details.

3.14 Why this matters for web servers and Spring

User 1 request→Tomcat thread http-nio-8080-exec-1→Same ProductController object
User 2 request→Tomcat thread http-nio-8080-exec-2→Same ProductController object
  • Spring creates one object (a "singleton bean") of each controller and service. All request threads use that same object at the same time.
  • So: never store per-request data in fields of controllers/services. Use method parameters and local variables. Example09 shows what goes wrong otherwise: users get other users' greetings!
  • Fields that hold other beans (like a repository) are fine, because they are set once at startup and never changed.
  • Shared counters/caches must use thread-safe types (AtomicInteger, ConcurrentHashMap).
  • Later you'll use @Async (run a method on a background pool), @Scheduled (run every N seconds), and @Transactional (tied to the current thread).
ℹ️ Virtual threads (Java 21+) Normal Java threads ("platform threads") map 1:1 to operating-system threads, which are heavy — you can have thousands, not millions. Java 21 added virtual threads: super-light threads managed by the JVM, so you can have millions of them. A web server can then use one cheap virtual thread per request. Spring Boot 3.2+ can switch to them with one property (spring.threads.virtual.enabled=true) — but only on Java 21+. This course uses Java 17, so we just mention them. Everything you learned today (race conditions, thread safety) still applies to virtual threads.

Example04 — volatile

The worker loops while (running). Main sleeps 200 ms then calls stop(), which sets running = false. Because the field is volatile, the worker sees the change and exits. Try removing volatile: on many machines the JIT compiler then "optimizes" the loop to while(true) and the program hangs.

Example06 — CompletableFuture

Four mini-scenarios: a simple chain (supplyAsync → thenApply → join), two parallel calls combined (thenCombine), a failing "review service" with a fallback (exceptionally returns 0.0 instead of crashing the page), and allOf to wait for three calls before building the page.

Example06_CompletableFuture.java (fallback)double rating = CompletableFuture
        .supplyAsync(() -> fetchRating(1), pool)     // throws IllegalStateException
        .exceptionally(ex -> {
            System.out.println("Could not load rating: " + ex.getCause().getMessage());
            return 0.0;                                // fallback value
        })
        .join();

6. Common mistakes

🚫 Mistake: calling run() instead of start() The code runs, but in the current thread — no parallelism at all.
Fix: always call start() (or, better, submit the task to an ExecutorService).
⚠️ Mistake: using count++ or a HashMap from many threads It "works on my machine" with one user, and loses data in production with many.
Fix: use AtomicInteger, ConcurrentHashMap, or synchronized.
⚠️ Mistake: thinking volatile makes count++ safe volatile only guarantees visibility, not atomicity.
Fix: AtomicInteger.incrementAndGet().
⚠️ Mistake: forgetting shutdown() on an ExecutorService The program never ends because pool threads are still alive.
Fix: shutdown() + awaitTermination(...) (or try-with-resources on Java 19+, where ExecutorService became AutoCloseable).
⚠️ Mistake: swallowing InterruptedException catch (InterruptedException e) { } hides the stop request.
Fix: stop the work, or at least call Thread.currentThread().interrupt() to restore the flag.
⚠️ Mistake: calling future.get() immediately after submit() pool.submit(task).get() waits right away — you gained nothing over running it directly.
Fix: submit all tasks first, then collect results (or use CompletableFuture.allOf).
🚫 Mistake: storing request data in fields of a Spring bean One controller object serves all users at once (Example09).
Fix: keep controllers and services stateless: use parameters and local variables.
⚠️ Mistake: locking in different orders Leads to deadlocks under load.
Fix: pick one global lock order and always follow it.

7. Best practices

  • Prefer high-level tools: ExecutorService and CompletableFuture over raw new Thread(); java.util.concurrent classes over manual synchronized/wait/notify.
  • Prefer immutability: immutable objects (records, String, List.of) need no locking.
  • Keep shared mutable state to a minimum. Less sharing = fewer bugs.
  • Keep locked sections short and never do slow I/O while holding a lock if possible.
  • Name your threads (or use a ThreadFactory) — it makes logs and thread dumps readable. Spring lets you set a thread-name prefix for its pools.
  • Size pools deliberately: CPU-heavy work ≈ number of cores (Runtime.getRuntime().availableProcessors()); I/O-heavy work (waiting for DB/network) can use more.
  • Always shut down pools you create; in Spring, let the framework own them (as beans).
  • Handle failures in async code (exceptionally, handle) — an exception in a background thread is easy to miss.
  • Spring beans should be stateless. If you need per-request data, pass it as parameters.
  • Test concurrency by running code many times with many threads; such bugs rarely show up in a single run.

8. Key takeaways

  • A process is a running program; threads are workers inside it that share the same heap memory.
  • Create threads with Thread, Runnable or a lambda — and always call start(), not run().
  • Thread states: NEW → RUNNABLE → (BLOCKED / WAITING / TIMED_WAITING) → TERMINATED. sleep pauses, join waits for another thread.
  • A race condition happens when threads change shared data at the same time; count++ is not atomic.
  • synchronized = one thread at a time (atomicity + visibility); volatile = visibility only.
  • Thread pools (ExecutorService) reuse threads; Callable returns a value via a Future.
  • CompletableFuture chains async steps: supplyAsync, thenApply, thenCombine, exceptionally, join.
  • Use AtomicInteger and ConcurrentHashMap for shared counters and maps.
  • A deadlock is a circular wait for locks; avoid it with a consistent lock order.
  • In Spring Boot each request runs on its own thread, so beans must be stateless and thread-safe. Java 21 adds virtual threads.

Challenge

Producer–consumer. One "orders" thread puts 10 order numbers into a BlockingQueue<Integer> (use ArrayBlockingQueue with capacity 3). Two "delivery" threads take orders from the queue and print who delivers which order. Use a special value (e.g. -1, called a "poison pill") to tell consumers to stop.

Hint / solution
BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(3);

Thread producer = new Thread(() -> {
    try {
        for (int i = 1; i <= 10; i++) {
            queue.put(i);                 // blocks if the queue is full
            System.out.println("Placed order " + i);
        }
        queue.put(-1); queue.put(-1);     // one poison pill per consumer
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});

Runnable deliver = () -> {
    try {
        while (true) {
            int order = queue.take();     // blocks if the queue is empty
            if (order == -1) break;
            System.out.println(Thread.currentThread().getName() + " delivers order " + order);
            Thread.sleep(100);
        }
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};

Thread d1 = new Thread(deliver, "Rider-1");
Thread d2 = new Thread(deliver, "Rider-2");
producer.start(); d1.start(); d2.start();
producer.join(); d1.join(); d2.join();

This pattern is exactly what message brokers like RabbitMQ and Kafka do between applications (Topics 57–58).

Challenge

Create and break a deadlock. Write two objects pen and paper. Student-1 locks pen then paper; Student-2 locks paper then pen. Observe the freeze with jstack. Then fix it using a ReentrantLock with tryLock(500, TimeUnit.MILLISECONDS) — if a student can't get both, they release what they hold and try again.

Hint / solution
ReentrantLock pen = new ReentrantLock();
ReentrantLock paper = new ReentrantLock();

void write(String who, ReentrantLock first, ReentrantLock second) throws InterruptedException {
    while (true) {
        if (first.tryLock(500, TimeUnit.MILLISECONDS)) {
            try {
                if (second.tryLock(500, TimeUnit.MILLISECONDS)) {
                    try {
                        System.out.println(who + " is writing");
                        return;                       // success
                    } finally { second.unlock(); }
                }
            } finally { first.unlock(); }             // give back and retry
        }
        Thread.sleep(50);                             // small back-off
    }
}

10. Interview questions

Q1. What is the difference between a process and a thread?

A process is a running program with its own memory space. A thread is a unit of execution inside a process. Threads of the same process share heap memory (objects), but each has its own stack (local variables, call frames). Threads are cheaper to create and communicate easily, but shared memory brings thread-safety problems.

Q2. What is the difference between start() and run()?

start() asks the JVM to create a new thread, which then calls run(). Calling run() directly is a normal method call in the current thread — no concurrency. start() can be called only once per Thread object.

Q3. Runnable vs Callable?

Runnable.run() returns nothing and cannot throw checked exceptions. Callable<V>.call() returns a value of type V and may throw checked exceptions. Submitting a Callable to an ExecutorService gives you a Future<V>.

Q4. What is a race condition? How do you prevent it?

A race condition is when the result depends on the timing of threads accessing shared mutable data — e.g. two threads doing count++ and losing an update because increment is read-modify-write. Prevent it with mutual exclusion (synchronized, ReentrantLock), atomic classes (AtomicInteger), thread-safe collections (ConcurrentHashMap), or by avoiding shared mutable state (immutability, local variables).

Q5. What is the difference between synchronized and volatile?

volatile guarantees visibility: a write by one thread is immediately seen by others, and it prevents certain reorderings. It does not make compound actions atomic. synchronized provides both mutual exclusion (only one thread in the block) and visibility (changes are flushed when the lock is released). Use volatile for simple flags, synchronized/atomics for read-modify-write.

Q6. Why use a thread pool instead of creating threads manually?

Creating threads is expensive (memory for stacks, OS work). A pool reuses a limited number of threads, controls the maximum concurrency (protects the machine from thousands of threads), queues extra tasks, and provides a clean API (submit, Future, shutdown). Web servers like Tomcat use a thread pool for requests.

Q7. Future vs CompletableFuture?

Future only lets you check isDone() or block with get(). CompletableFuture implements Future and adds non-blocking composition: thenApply, thenCompose, thenCombine, allOf/anyOf, error handling with exceptionally/handle, and can be completed manually. It allows building async pipelines without blocking threads.

Q8. What is a deadlock and how can you avoid it?

A deadlock is when two or more threads wait forever for locks held by each other (circular wait). Avoid it by acquiring locks in a consistent global order, using timeouts (tryLock), holding as few locks as possible for as short as possible, and preferring higher-level concurrency utilities. Detect with a thread dump (jstack), which reports Java-level deadlocks.

Q9. How does ConcurrentHashMap differ from HashMap and Collections.synchronizedMap?

HashMap is not thread-safe. Collections.synchronizedMap wraps every method with one lock — safe but only one thread at a time. ConcurrentHashMap allows concurrent reads and fine-grained locking/CAS for writes (per bucket), so it scales much better, offers atomic operations (putIfAbsent, computeIfAbsent, merge), and its iterators never throw ConcurrentModificationException. It does not allow null keys or values.

Q10. Are Spring singleton beans thread-safe?

Not automatically. Spring creates one instance and all request threads use it concurrently. A bean is thread-safe only if it is stateless (or its state is immutable or managed with thread-safe types). That is why controllers and services should not keep per-request data in fields; dependencies injected once at startup are fine.
