51. Caching with Redis

Make slow endpoints fast by remembering answers: Spring's cache annotations first with a simple in-memory cache, then with a real Redis server, TTLs and JSON values.

1. Why this matters

Imagine your online shop has a product page. Every time someone opens it, your app runs a database query. The query takes 50 ms. That sounds fast. But on a sale day, 2,000 people open the same page every second. Now your database runs the same query 2,000 times per second and gives the same answer every time. The database gets tired, everything slows down, and customers leave.

A cache fixes this. The first time, you ask the database and you remember the answer in a fast place. The next 1,999 times, you give the remembered answer. The database relaxes, and the page loads in about 1 ms.

Caching gives you three wins:

  • Lower latency – latency means "how long one request waits". Reading from memory is thousands of times faster than a database or a remote API.
  • Less load – your database, or an external API you pay for per call, gets far fewer requests.
  • Better resilience – if a slow service has a short hiccup, recently cached data can still be served.

How big is the difference? Rough numbers that every backend developer keeps in mind:

Where the data comes fromTypical timeCompared with RAM
A Java object already in memory (RAM)~0.0001 ms (100 nanoseconds)1×
Redis on the same network~0.2 – 1 msthousands of times slower than RAM, but still very fast
A simple SQL query~2 – 50 msmuch slower
A remote HTTP API (e.g. currency rates)~100 – 500 msvery slow

Where you will meet caching at work: product catalogs, user profiles and permissions, currency exchange rates, country/city lists, configuration values, results of expensive reports, tokens from an external login provider, and session data. Redis is one of the most popular tools in the world for this, and "Have you used Redis caching?" is a very common interview question.

2. Real-life analogy

👩‍🍳 The chef's counter and the storeroom A chef in a busy restaurant keeps salt, oil and chopped onions on the counter right next to the stove. The full stock lives in the storeroom at the back of the building. Walking to the storeroom takes 2 minutes; grabbing from the counter takes 2 seconds.
  • The storeroom is your database – complete and reliable, but slow to reach.
  • The counter is your cache – small, fast, holds only the things used most often.
  • "Onions are on the counter" = a cache hit. "No onions here, walk to the storeroom" = a cache miss.
  • Chopped onions go bad after a few hours, so the chef throws them away = TTL (time to live) and expiry.
  • The counter is small; when it is full, the least-used item goes back = eviction.
  • If the storeroom gets a new, better oil, the old bottle on the counter must be replaced, or the chef keeps using the old one = cache invalidation, the hard part!
If there are three chefs, each with their own counter, they may have different onions. A shared counter in the middle that all chefs use is what Redis gives you: one cache shared by many copies of your application.

3. Concepts step by step

3.1 The vocabulary of caching

WordSimple meaning
CacheA fast key → value store that keeps copies of data that is slow to get.
KeyThe "label" used to find a value, e.g. 1 for product 1, or laptops for a search.
Cache hitThe key was found in the cache. Fast answer, the slow source is not touched.
Cache missThe key was not found. We must load from the slow source (and usually store it).
Hit ratiohits ÷ (hits + misses). 0.95 means 95% of reads were served from the cache. Higher is better.
TTL (time to live)How long an entry may stay before it expires automatically, e.g. 10 minutes.
EvictionRemoving entries – because the TTL ran out, the cache is full, or we removed it on purpose.
Stale dataA cached value that is older than the real data in the database. The main risk of caching.
InvalidationRemoving or refreshing cache entries when the real data changes, so they are not stale.
ℹ️ A famous joke"There are only two hard things in computer science: cache invalidation and naming things." – Phil Karlton. You will see why in section 3.12.

3.2 What should (and should not) be cached?

Good to cache ✅Bad to cache ❌
Read often, changes rarely (product details, categories, country list)Changes every second (live stock count during a flash sale, a bank balance)
Expensive to compute (reports, recommendations)Cheap to compute (adding two numbers)
Slow external APIs (exchange rates, weather)Data that must be 100% correct right now (payment status)
Same answer for many usersUnique per request with almost no repeats (the cache only fills up)

Rule of thumb: measure first. Cache the things that are actually slow and actually repeated.

3.3 The cache-aside pattern

"Cache-aside" (also called "lazy loading") is the pattern you will use 90% of the time. The cache sits beside the database. The application does the work:

  1. Look in the cache using the key.
  2. Hit? Return the cached value. Done.
  3. Miss? Load from the database, put the value into the cache, then return it.
  4. When data is changed, update or remove the cache entry.

Other patterns exist. You do not need them today, but know their names for interviews:

PatternHow it worksNote
Cache-asideApp reads cache, on miss loads DB and fills cache.Most common. Spring's @Cacheable does exactly this.
Read-throughApp only talks to the cache; the cache itself loads from the DB on a miss.Needs a cache product with a "loader".
Write-throughEvery write goes to cache AND database at the same time.Cache always fresh, writes a bit slower. @CachePut is similar.
Write-behind (write-back)Write to the cache now, write to the DB later in batches.Fast but risky: data can be lost if the cache crashes.

3.4 Caching by hand – and why we don't

You could write cache-aside yourself with a Map:

private final Map<Long, Product> cache = new ConcurrentHashMap<>();

public Product getProduct(Long id) {
    Product cached = cache.get(id);
    if (cached != null) {
        return cached;                       // HIT
    }
    Product loaded = repository.findById(id) // MISS -> slow database
            .orElseThrow();
    cache.put(id, loaded);                   // remember it
    return loaded;
}

It works, but look at the problems: caching code is mixed with business code, it is repeated in every method, there is no TTL, no size limit, and switching to Redis means rewriting everything. This is a cross-cutting concern – exactly what AOP (topic 27) is for.

3.5 Spring's cache abstraction

Spring gives you a cache abstraction: you put annotations on methods, and Spring does the cache-aside work for you. "Abstraction" means your code does not care which cache product is used. Two interfaces make this possible:

  • Cache – one named cache, e.g. "products". It has get(key), put(key, value), evict(key), clear().
  • CacheManager – owns all the caches and gives you one by name: cacheManager.getCache("products").

Spring Boot picks a CacheManager implementation for you, based on what is on the classpath and the property spring.cache.type:

spring.cache.typeCacheManagerWhere data livesWhen to use
simpleConcurrentMapCacheManagerA ConcurrentHashMap inside your JVMLearning, tests, tiny apps. Default if nothing else is found.
caffeineCaffeineCacheManagerInside your JVM, with size limit & TTLFast local cache for a single instance.
redisRedisCacheManagerA separate Redis serverSeveral app instances need one shared cache.
jcacheJCacheCacheManagerEhcache 3, Hazelcast…Standard JSR-107 providers.
noneNoOpCacheManagerNowhereSwitch caching off (e.g. in some tests).

The starter is spring-boot-starter-cache:

pom.xml<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>

3.6 Step 1: switch caching on with @EnableCaching

@Configuration
@EnableCaching          // without this line, every cache annotation is silently IGNORED
public class CacheConfig { }

What happens behind the scenes? Spring wraps every bean that has cache annotations in a proxy (a "stand-in" object, topic 27). Callers talk to the proxy. The proxy checks the cache and only calls the real method on a miss.

Controller→ Cache proxy
key in cache?→ miss → Real ProductService method→ Database

On a hit, the proxy returns the cached value and the real method is never called – you will not even see its log line.

3.7 @Cacheable – "remember the answer"

@Cacheable(cacheNames = "products", key = "#id")
public Product getProductById(Long id) {
    return repository.findById(id).orElseThrow(() -> new ProductNotFoundException(id));
}
  • cacheNames = "products" – which cache to use (value is an alias for the same thing).
  • key = "#id" – the key is the value of the parameter called id. Call with 1 → key 1.
  • First call with id 1: miss → method runs → result stored under key 1.
  • Second call with id 1: hit → method skipped → cached product returned.
  • If the method throws an exception, nothing is cached. A "not found" is asked again next time.

How keys are made

If you do not write a key, Spring builds one from all parameters (the default SimpleKeyGenerator):

Method parametersDefault key
noneSimpleKey.EMPTY
one parameter, e.g. (Long id)the parameter itself: 1
several, e.g. (String category, int page)SimpleKey [laptops, 0]

The key attribute uses SpEL (Spring Expression Language, topic 26). The most useful expressions:

SpELMeaningExample
#idthe parameter named idkey = "#id"
#p0 / #a0the first parameter (by position)key = "#p0"
#request.emaila property of a parameter objectkey = "#request.email"
#category.toLowerCase()call a method on a parameternormalise keys
#id + '-' + #langcombine several values"1-en"
#root.methodNamethe method's nameuseful for shared caches
#resultthe return value (only in unless, @CachePut key, and @CacheEvict after the call)key = "#result.id"
ℹ️ Why can Spring see the name "id"?Java normally forgets parameter names after compiling. The Spring Boot parent POM compiles with the -parameters flag, which keeps them. That is why #id works. If you ever see "Null key returned for cache operation", the names were lost – use #p0 or check the compiler settings.

condition and unless

@Cacheable(cacheNames = "productSearch",
           key = "#category.toLowerCase()",
           condition = "#category.length() >= 3",   // checked BEFORE the call
           unless = "#result.isEmpty()")             // checked AFTER the call
public List<Product> searchByCategory(String category) { ... }
AttributeEvaluatedIf true…Can use #result?
conditionbefore the method runscaching is used (look up + store)No
unlessafter the method runsthe result is not storedYes

So: searching "ph" (2 letters) is never cached; a search that finds nothing is not cached either.

sync = true – protecting against a stampede

Imagine the cache entry for a very popular product expires, and 500 requests arrive in the same millisecond. All 500 see a miss and all 500 query the database. This is a cache stampede (also "thundering herd"). With @Cacheable(cacheNames = "products", sync = true), only one thread loads the value; the others wait for it. (sync cannot be combined with unless.)

3.8 @CachePut – "always run, then refresh the cache"

@CachePut(cacheNames = "products", key = "#id")
public Product updatePrice(Long id, BigDecimal newPrice) {
    ...                       // ALWAYS runs
    return updatedProduct;    // the return value REPLACES the cache entry for key id
}

Use it on update methods. After the update, readers immediately get the new value from the cache, with no extra database call. Important: the method must return the object you want cached. A void method with @CachePut would cache null.

⚠️ Never put @Cacheable and @CachePut on the same methodThey want opposite things (skip vs always run).

3.9 @CacheEvict – "forget it"

@CacheEvict(cacheNames = "products", key = "#id")                // remove ONE entry
public void deleteProduct(Long id) { ... }

@CacheEvict(cacheNames = "productSearch", allEntries = true)     // empty the WHOLE cache
public void importNewCatalog() { ... }

@CacheEvict(cacheNames = "products", key = "#id", beforeInvocation = true)
public void riskyDelete(Long id) { ... }   // evict even if the method throws

By default eviction happens after the method finishes successfully. If the method throws, the entry stays. beforeInvocation = true changes that.

3.10 @Caching and @CacheConfig

Java does not allow the same annotation twice in this case, so to do several cache operations on one method, group them with @Caching:

@Caching(
    put   = @CachePut(cacheNames = "products", key = "#id"),
    evict = @CacheEvict(cacheNames = "productSearch", allEntries = true)
)
public Product updatePrice(Long id, BigDecimal newPrice) { ... }

@CacheConfig on the class sets defaults for every method so you don't repeat yourself:

@Service
@CacheConfig(cacheNames = "products")
public class ProductService {
    @Cacheable(key = "#id")   // uses "products" from @CacheConfig
    public Product get(Long id) { ... }
}

3.11 The default in-memory cache – great for learning, limited in production

With only spring-boot-starter-cache and @EnableCaching, Spring Boot uses ConcurrentMapCacheManager. It needs no installation, which is why our project uses it by default. But it has real limits:

  • No TTL – entries live until the app stops or you evict them.
  • No size limit – it can grow until you run out of memory.
  • Per instance – if you run 3 copies of the app behind a load balancer, there are 3 separate caches. You evict in one copy; the other two still serve the old price.
  • Lost on restart – a restart empties it ("cold cache").

Caffeine fixes the first two (local, with TTL and size). Redis fixes all four.

3.12 What is Redis?

Redis (REmote DIctionary Server) is an open-source, in-memory key-value data store. Think of it as a giant HashMap that runs as its own server, which all your app instances can share over the network. It is extremely fast because data lives in RAM, and it supports expiry (TTL) on every key out of the box. It is also used for sessions, rate limiting, leaderboards and queues – but here we use it as a cache.

Some Redis commands you will use (run them in redis-cli):

CommandWhat it does
PINGHealth check – answers PONG.
SET name "Asha" / GET nameStore / read a value.
KEYS *List all keys (fine for learning; never in production – it blocks Redis. Use SCAN).
TTL products::1Seconds left before the key expires (-1 = never, -2 = gone).
DEL products::1Delete one key.
FLUSHALLDelete everything (local learning only!).

Step 1 – dependency. spring-boot-starter-data-redis brings the Lettuce Redis client, RedisTemplate and RedisCacheManager.

Step 2 – a Redis server. The easiest way is Docker. Our docker-compose.yml:

Step 3 – tell Spring where Redis is and to use it for caching. We do this only in a redis profile (topic 29), so the default profile keeps working without Docker:

src/main/resources/application-redis.propertiesspring.cache.type=redis
spring.data.redis.host=localhost
spring.data.redis.port=6379
spring.data.redis.timeout=2s
# spring.data.redis.password=${REDIS_PASSWORD}   # secrets come from environment variables
⚠️ Why we set spring.cache.type=simple in the default profile When spring-boot-starter-data-redis is on the classpath, Spring Boot's auto-configuration sees a Redis connection factory and chooses RedisCacheManager automatically. Without Redis running, the first cached call would fail with RedisConnectionFailureException. Setting spring.cache.type=simple explicitly keeps the default profile Redis-free. (The app still starts without Redis, because the Lettuce client only connects when it is first used.)

That's it – your @Cacheable code does not change at all. That is the power of the abstraction.

3.14 TTL – making entries expire

There are two ways to set a TTL for Redis caches.

Option A – a property (simple, same TTL for every cache):

spring.cache.redis.time-to-live=10m
spring.cache.redis.cache-null-values=false
spring.cache.redis.key-prefix=shop:
spring.cache.redis.use-key-prefix=true

Option B – a RedisCacheConfiguration bean (full control; what our project does):

config/CacheConfig.java@Bean
@Profile("redis")
public RedisCacheConfiguration redisCacheConfiguration() {
    return RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(10))
            .disableCachingNullValues()
            .serializeKeysWith(SerializationPair.fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer()));
}

@Bean
@Profile("redis")
public RedisCacheManagerBuilderCustomizer perCacheTtlCustomizer(RedisCacheConfiguration defaults) {
    return builder -> builder
            .withCacheConfiguration("productSearch", defaults.entryTtl(Duration.ofMinutes(1)))
            .withCacheConfiguration("products", defaults);
}
ℹ️ Bean beats propertyOnce you define your own RedisCacheConfiguration bean, the spring.cache.redis.* properties are no longer applied. Pick one approach and stick with it.

How to choose a TTL? Ask: "How old may this data be before a customer notices or it causes harm?" Product descriptions: maybe an hour. Prices: a few minutes (and evict on change). Exchange rates: 1 minute. There is no magic number – it's a business decision.

3.15 Serialization – how Java objects become bytes in Redis

Redis stores bytes, not Java objects. Serialization = turning an object into bytes; deserialization = the reverse.

JDK serialization (default)JSON (GenericJackson2JsonRedisSerializer)
Needs implements Serializable?Yes – otherwise an error at runtimeNo
Readable in redis-cli?No – binary garbage like \xac\xed\x00\x05sr...Yes – {"@class":"...Product","id":1,...}
Other languages can read it?No (Java only)Yes
Rename/move a class?Old entries breakOld entries break too (class name stored), but easier to debug

With JSON, a cached product looks something like this in Redis (shortened):

127.0.0.1:6379> GET products::1
"{\"@class\":\"com.course.caching.product.Product\",\"id\":1,\"name\":\"Dell XPS 13\",\"category\":\"laptops\",\"price\":...}"
127.0.0.1:6379> TTL products::1
(integer) 583

The @class field is type information. GenericJackson2JsonRedisSerializer stores it so it knows which Java class to create when reading back. Notice the key format: cacheName::key → products::1.

3.16 Cache invalidation pitfalls (read this twice!)

PitfallWhat goes wrongFix
Forgetting to evict on update/deleteUsers see old prices for hours@CachePut / @CacheEvict on every write path + a TTL as safety net
Forgetting related cachesSingle product refreshed, but the search list still shows the old priceEvict dependent caches too (allEntries = true on search lists)
Data changed outside the appA DBA runs an SQL UPDATE; your cache never hears about itTTL; or an admin "clear cache" endpoint
Local caches with many instancesInstance A evicts; instance B still serves stale dataUse a shared cache (Redis)
Self-invocationthis.getProductById() inside the same class never hits the cacheCall through another bean (the proxy)
Caching mutable objects (local cache)Someone changes the returned object → the cached copy changes tooCache immutable objects (records) or copies
Bad keysTwo different methods share a cache with the same key → wrong type returnedOne cache per kind of data; explicit keys
Stampede after expiryHundreds of threads reload the same entrysync = true; slightly random TTLs

4.1 The slow repository

product/ProductRepository.java (key parts)public ProductRepository(@Value("${app.slow-database.delay-ms:2000}") long delayMs) { ... }

public Optional<Product> findById(Long id) {
    simulateSlowQuery("SELECT * FROM product WHERE id = " + id);
    return Optional.ofNullable(table.get(id));
}

private void simulateSlowQuery(String sql) {
    int hit = databaseHits.incrementAndGet();          // count every REAL call
    log.info("DATABASE HIT #{} -> {} (takes {} ms)", hit, sql, delayMs);
    Thread.sleep(delayMs);                              // pretend to be slow (inside try/catch)
}

The delay comes from a property (app.slow-database.delay-ms) so the test can set it to 0. The counter databaseHits lets us prove that a cache hit never reaches the repository. Also note findByCategory returns a plain ArrayList – see "Common mistakes" for why.

4.2 The service – where caching happens

product/ProductService.java (key parts)@Cacheable(cacheNames = CacheNames.PRODUCTS, key = "#id")
public Product getProductById(Long id) {
    log.info("Cache MISS for product {} - loading from the database", id);
    return repository.findById(id).orElseThrow(() -> new ProductNotFoundException(id));
}

@Cacheable(cacheNames = CacheNames.PRODUCT_SEARCH, key = "#category.toLowerCase()",
           condition = "#category.length() >= 3", unless = "#result.isEmpty()")
public List<Product> searchByCategory(String category) { ... }

@Caching(
    put   = @CachePut(cacheNames = CacheNames.PRODUCTS, key = "#result.id"),
    evict = @CacheEvict(cacheNames = CacheNames.PRODUCT_SEARCH, allEntries = true))
public Product createProduct(String name, String category, BigDecimal price) { ... }

@Caching(
    put   = @CachePut(cacheNames = CacheNames.PRODUCTS, key = "#id"),
    evict = @CacheEvict(cacheNames = CacheNames.PRODUCT_SEARCH, allEntries = true))
public Product updatePrice(Long id, BigDecimal newPrice) { ... }

@Caching(evict = {
    @CacheEvict(cacheNames = CacheNames.PRODUCTS, key = "#id"),
    @CacheEvict(cacheNames = CacheNames.PRODUCT_SEARCH, allEntries = true) })
public void deleteProduct(Long id) { ... }

Read it like a story:

  • Read one – remember it under its id. The log line "Cache MISS…" only appears on a miss, because on a hit the method body never runs.
  • Search – remember the list under the lower-case category, but not for short terms and not when empty.
  • Create – the new id is only known after saving, so the key is #result.id. Every search list might now be missing the new product, so we clear the whole productSearch cache.
  • Update – overwrite the cached product with the new one and clear the search lists (they contain the old price).
  • Delete – remove the product and the search lists.

Notice inside updatePrice we call repository.findById(id), not this.getProductById(id). A call through this skips the proxy, so it would never use the cache.

4.3 The controller – measuring the speed-up

web/ProductController.java (key parts)@GetMapping("/{id}")
public ResponseEntity<Product> getOne(@PathVariable Long id) {
    return timed(() -> productService.getProductById(id));
}

private <T> ResponseEntity<T> timed(Supplier<T> call) {
    long start = System.nanoTime();
    T body = call.get();
    long tookMs = (System.nanoTime() - start) / 1_000_000;
    return ResponseEntity.ok().header("X-Response-Time-Ms", String.valueOf(tookMs)).body(body);
}

timed is a small generic helper (topic 12) that takes a Supplier (topic 13), runs it, and adds the time as a response header. GET /api/products/stats returns the real database-hit counter.

4.4 Looking inside the caches with CacheManager

web/CacheAdminController.java (key parts)for (String name : cacheManager.getCacheNames()) {
    Cache cache = cacheManager.getCache(name);
    Object nativeCache = cache == null ? null : cache.getNativeCache();
    if (nativeCache instanceof ConcurrentMap<?, ?> map) {   // in-memory cache: show keys
        result.put(name, map.keySet());
    } else {                                               // Redis: look with redis-cli
        result.put(name, "stored in Redis - inspect with: docker exec -it course-redis redis-cli KEYS '*'");
    }
}

You can inject CacheManager anywhere and work with caches by code – useful for an admin "clear cache" button. getNativeCache() returns the real underlying store (a ConcurrentMap for the simple cache).

6. Common mistakes

⚠️ Mistake: forgetting @EnableCachingThe app runs, no error, but every call is slow. The annotations are simply ignored.
Fix: add @EnableCaching to a @Configuration class (or the main class).
⚠️ Mistake: calling a cached method from the same class 
public Product getWithDiscount(Long id) {
    Product p = getProductById(id);   // "this.getProductById" - NO cache, proxy is bypassed!
    ...
}
Fix: put the cached method in another bean and inject it, so the call goes through the proxy. The same rule applies to @Transactional and @Async.
⚠️ Mistake: caching private methodsProxies can only intercept public methods called from outside. Annotations on private methods do nothing.
Fix: cache public service methods.
🛑 Mistake: Redis says "Could not read JSON ... ImmutableCollections$ListN" Lists created by stream().toList() or List.of(...) are hidden JDK classes with no public constructor. They can be written to Redis as JSON, but Jackson cannot create them when reading back.
Fix: return a normal new ArrayList<>(...) from cached methods (our repository does), or use a typed serializer.
🛑 Mistake: SerializationException ... DefaultSerializer requires a Serializable payload You use Redis with the default JDK serializer and your class does not implement Serializable.
Fix: configure JSON serialization (GenericJackson2JsonRedisSerializer) as in CacheConfig.
⚠️ Mistake: RedisConnectionFailureException: Unable to connect to Redis You started with the redis profile but Redis is not running – or you forgot spring.cache.type=simple in the default profile while the Redis starter is present.
Fix: docker compose up -d, check with docker ps, or run without the profile.
⚠️ Mistake: updating data but not the cacheA new endpoint updates the product name, but nobody added @CachePut/@CacheEvict to it. Users see the old name until restart.
Fix: every write path must touch the cache, and always set a TTL as a safety net.
⚠️ Mistake: changing a cached class and reading old entriesYou rename a field or move the Product class; old JSON in Redis no longer matches and reading fails.
Fix: clear the cache on deployment (or change the key prefix/cache name for the new version).

7. Best practices

  • Measure before caching. Cache what is slow and repeated. Every cache adds complexity and a risk of stale data.
  • Always set a TTL for Redis caches. Even with perfect eviction code, a TTL saves you when data changes outside the app.
  • Cache at the service layer, not in controllers or repositories – the service knows the business meaning of the data.
  • Cache DTOs / immutable records, not JPA entities. Entities have lazy relationships and Hibernate proxies that do not serialize well.
  • Use JSON serialization in Redis – readable, debuggable, no Serializable requirement.
  • Keep cache names in constants and use explicit, readable keys.
  • Use different TTLs per cache depending on how fast the data changes.
  • Never cache secrets or personal data without thinking about who can read Redis. Protect Redis with a password/ACL and never expose port 6379 to the internet.
  • The app must survive a cache outage. Redis down should mean "slower", not "broken". (Spring lets you register a CacheErrorHandler that logs errors and falls back to the method.)
  • Monitor the hit ratio with Actuator's cache metrics (topic 53). A cache with a 5% hit ratio is just overhead.
  • In production, use a managed Redis (AWS ElastiCache, Azure Cache for Redis, Redis Cloud) rather than running your own.

8. Key takeaways

  • A cache keeps copies of slow-to-get data in a fast place. Hit = fast; miss = load and store.
  • Cache-aside is the standard pattern, and @Cacheable implements it for you.
  • @EnableCaching turns caching on; Spring uses AOP proxies, so self-calls and private methods are not cached.
  • @Cacheable = read-through-the-cache; @CachePut = always run & refresh; @CacheEvict = remove; @Caching = combine.
  • Keys are SpEL expressions (#id, #result.id); condition is checked before, unless after the call.
  • The default ConcurrentMapCache needs no setup but has no TTL, no size limit and is per instance.
  • Redis is a shared, in-memory key-value server; add spring-boot-starter-data-redis and set spring.cache.type=redis.
  • Configure TTL and JSON serialization with a RedisCacheConfiguration bean (or spring.cache.redis.* properties).
  • Invalidation is the hard part: evict on every write, evict related caches, and keep a TTL as a safety net.

Challenge

Survive a Redis outage. Run with the redis profile, then stop Redis (docker compose stop). Calls now fail with 500. Make the app fall back to the database instead, logging a warning.

Hint / solution
@Configuration
@EnableCaching
public class CacheConfig implements CachingConfigurer {

    private static final Logger log = LoggerFactory.getLogger(CacheConfig.class);

    @Override
    public CacheErrorHandler errorHandler() {
        return new SimpleCacheErrorHandler() {
            @Override
            public void handleCacheGetError(RuntimeException e, Cache cache, Object key) {
                log.warn("Cache GET failed for {}::{} - using the database. {}", cache.getName(), key, e.getMessage());
            }
            @Override
            public void handleCachePutError(RuntimeException e, Cache cache, Object key, Object value) {
                log.warn("Cache PUT failed for {}::{}", cache.getName(), key);
            }
            @Override
            public void handleCacheEvictError(RuntimeException e, Cache cache, Object key) {
                log.warn("Cache EVICT failed for {}::{}", cache.getName(), key);
            }
        };
    }
    // ... existing beans ...
}

When a cache GET fails and the handler does not rethrow, Spring treats it as a miss and calls the real method. Lower spring.data.redis.timeout (e.g. 500ms) so the fallback is quick. Careful: a failed EVICT means stale data may remain in Redis when it comes back – a short TTL limits the damage.

10. Interview questions

Q1. What is caching and why do we use it?

Caching stores copies of data that is slow or expensive to get (DB queries, remote APIs, heavy calculations) in a fast store, usually memory. It reduces latency, reduces load on the database or external services, and can improve resilience. The cost is complexity and the risk of stale data.

Q2. Explain the cache-aside pattern.

The application checks the cache first. On a hit it returns the cached value. On a miss it loads from the database, stores the value in the cache, then returns it. On writes the application updates or evicts the cache entry. Spring's @Cacheable + @CacheEvict implement this pattern.

Q3. Difference between @Cacheable, @CachePut and @CacheEvict?

@Cacheable skips the method if the key is in the cache, otherwise runs it and stores the result. @CachePut always runs the method and puts the result into the cache (used for updates). @CacheEvict removes one entry (by key) or all entries (allEntries = true), after the method by default or before with beforeInvocation = true.

Q4. How does Spring caching work internally? Why does a call from the same class not use the cache?

@EnableCaching registers an AOP interceptor (CacheInterceptor). Spring creates a proxy around beans with cache annotations; the proxy checks the cache before delegating to the real object. A call like this.method() happens inside the real object, so it never passes through the proxy, and caching (like @Transactional) is skipped. Fix: call through another bean.

Q5. What is the difference between condition and unless?

condition is evaluated before the method call; if false, the cache is not used at all for that call. unless is evaluated after the call and can use #result; if true, the result is not stored. Example: condition = "#name.length() > 2", unless = "#result == null".

Q6. Why use Redis instead of the default in-memory cache?

The default ConcurrentMapCache lives in one JVM: no TTL, no size limit, lost on restart, and each instance has its own copy, so instances can disagree. Redis is a separate shared server: all instances see the same data, entries can have TTLs, data survives app restarts, and it has eviction policies and monitoring.

Q7. How do you configure TTL for Redis caches in Spring Boot?

Either with spring.cache.redis.time-to-live=10m, or with a RedisCacheConfiguration bean using entryTtl(Duration.ofMinutes(10)). Per-cache TTLs are set with a RedisCacheManagerBuilderCustomizer and withCacheConfiguration("name", config). If you define the bean, the properties are ignored.

Q8. What serialization does RedisCacheManager use and why would you change it?

By default, JDK serialization: binary, Java-only, unreadable in redis-cli, and objects must implement Serializable. Most teams switch to JSON with GenericJackson2JsonRedisSerializer (stores type info in @class) or a typed Jackson2JsonRedisSerializer, which is readable and language-neutral.

Q9. What is a cache stampede and how do you prevent it?

When a popular entry expires, many concurrent requests miss at the same time and all hit the database. Prevent it with @Cacheable(sync = true) (one thread loads, others wait), randomised TTLs so entries do not all expire together, or refreshing hot entries before they expire.

Q10. What are common cache invalidation problems?

Forgetting to evict on some write path, not evicting dependent caches (lists/aggregates), data changed outside the application, local caches in multi-instance deployments, and serialized class changes after a deploy. Mitigations: evict/put on every write, TTL as a safety net, shared cache, clear caches on deploy, and cache only data that tolerates slight staleness.
