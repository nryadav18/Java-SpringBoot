Learn to pass small pieces of behaviour around like values — the skill that unlocks Streams, modern Java and almost every Spring configuration you will write.

1. Why this matters

Until now, every time you wanted to give Java a piece of behaviour — "sort these books by title length", "do this when the button is clicked" — you had to wrap that behaviour inside an object. Usually that meant writing a whole class, or an anonymous class with five lines of ceremony around one line of real logic.

In 2014, Java 8 added lambdas: a short way to write "here is a small function, use it". Overnight, Java code became shorter and easier to read. Today lambdas are everywhere:

  • Streams (next topic) are built entirely on lambdas: orders.stream().filter(o -> o.getTotal() > 500).
  • Sorting: employees.sort(Comparator.comparing(Employee::getSalary)).
  • Spring Security config uses the "Lambda DSL": http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated()).
  • Spring Data: repo.findById(id).orElseThrow(() -> new NotFoundException(id)).
  • Threads & async (topic 17): CompletableFuture.supplyAsync(() -> loadPrice()).

If you cannot read lambdas comfortably, modern Java and Spring code will look like magic symbols. After this lesson, they will look like plain English.

2. Real-life analogy

📝 The sticky note for the house-sitter Imagine you go on holiday and a friend looks after your house.
  • Old way (named class): You hire a company, sign a contract, give them a job title "Plant Waterer", and the contract says "water the plants". Lots of paperwork for one job.
  • Anonymous class: No company, but you still write a full formal letter: "Dear Sir/Madam, I hereby request that you perform the duty of… water the plants. Regards."
  • Lambda: You stick a note on the fridge: "plants → water them". Done.
The job is the same each time. A lambda simply removes the paperwork and keeps only the instruction. And the "fridge" — the place that expects one specific kind of instruction — is the functional interface.
🔌 Second picture: a plug socket A functional interface is like a socket with exactly one shape. A lambda is any plug that fits that shape. Predicate is a socket shaped "give me a thing, I answer yes/no". Any lambda that takes one value and returns true/false fits it.

3. Concepts step by step

3.1 The problem: behaviour wrapped in too much code

Suppose a library app needs to sort book titles from shortest to longest. List.sort needs a Comparator — an object with a compare(a, b) method. Before Java 8 you wrote an anonymous class:

books.sort(new Comparator<String>() {          // 1. create an object of a nameless class
    @Override
    public int compare(String a, String b) {   // 2. repeat the method signature
        return a.length() - b.length();        // 3. the ONLY line we care about
    }
});

Six lines, but only one line is our actual idea. Everything else is "boilerplate" (repeated ceremony code).

3.2 The solution: a lambda

books.sort((a, b) -> a.length() - b.length());

Read the arrow -> as "goes to" or "becomes": "a and b become a.length() minus b.length()".

(a, b)→ a.length() - b.length()

Left of the arrow: parameters (the inputs). Right of the arrow: the body (what to do with them). Java already knows sort needs a Comparator<String>, so it figures out that a and b are Strings. This guessing is called type inference.

ℹ️ What is a lambda, really? A lambda is an anonymous function — a function without a name — that Java turns into an object implementing an interface. You can store it in a variable, pass it to a method, or return it from a method, just like a number or a String.

3.3 Functional interfaces — the "socket" a lambda plugs into

A lambda cannot exist on its own. It always needs a target type: an interface that has exactly one abstract method. Such an interface is called a functional interface (also called a SAM interface — Single Abstract Method).

@FunctionalInterface
interface DiscountRule {
    double apply(double price);   // exactly ONE abstract method
}

DiscountRule tenPercentOff = price -> price * 0.90;   // the lambda IS the apply() method
System.out.println(tenPercentOff.apply(1000));         // 900.0

What happens here, step by step:

  1. Java sees the variable type DiscountRule.
  2. It looks for the single abstract method: double apply(double price).
  3. It checks the lambda fits: one input → returns a double. ✅
  4. It creates an object whose apply method runs price * 0.90.
  5. Nothing is calculated yet! The code runs only when we call tenPercentOff.apply(1000).
💡 What does @FunctionalInterface do? It is optional. It tells the compiler: "please make sure this interface has exactly one abstract method". If a teammate later adds a second abstract method, the build fails immediately with a clear error instead of breaking every lambda in the project. default and static methods do not count — a functional interface can have as many of those as it likes.

3.4 Lambda syntax — every variant

ShapeExampleNotes
No parameters() -> System.out.println("Hi")Empty brackets are required.
One parameterprice -> price * 0.9Brackets optional for exactly one untyped parameter.
One parameter with brackets(price) -> price * 0.9Same as above.
Explicit type(double price) -> price * 0.9Brackets required when you write the type.

Expression body vs block body:

// Expression body: a single expression, its value is returned automatically
BillCalculator simple = (price, qty) -> price * qty;

// Block body: several statements, 'return' needed
BillCalculator withTax = (price, qty) -> {
    double subtotal = price * qty;
    double tax = subtotal * 0.18;
    return subtotal + tax;
};
⚠️ Mixing rules You cannot mix typed and untyped parameters: (double price, qty) -> ... does not compile. Either type all of them or none of them.

3.5 Lambdas are values: passing behaviour to methods

This is the big idea. A method can accept behaviour as a parameter, so the caller decides what happens:

static void printFinalPrice(double price, DiscountRule rule) {
    System.out.println("Price " + price + " -> final " + rule.apply(price));
}

printFinalPrice(1200, p -> p * 0.90);                  // Price 1200.0 -> final 1080.0
printFinalPrice(1200, p -> p > 1000 ? p - 200 : p);    // Price 1200.0 -> final 1000.0

One method, unlimited discount rules — no if/else chain, no new classes. This style is called functional programming or "behaviour parameterisation".

3.6 Built-in functional interfaces (java.util.function)

You rarely need to write your own interface like DiscountRule. Java ships ready-made ones in the package java.util.function. Learn these "shapes" and you can read 90% of lambda code:

InterfaceShape (input → output)Method you callThink of it asExample
Runnable (java.lang)() → nothingrun()"just do it"() -> System.out.println("Open")
Supplier<T>() → Tget()"give me one"() -> "ORD-1001"
Consumer<T>T → nothingaccept(t)"use / print / save it"msg -> System.out.println(msg)
Predicate<T>T → booleantest(t)"is it true?"age -> age >= 18
Function<T,R>T → Rapply(t)"convert it"word -> word.length()
BiFunction<T,U,R>(T, U) → Rapply(t, u)"combine two into a result"(price, qty) -> price * qty
UnaryOperator<T>T → Tapply(t)"change it, same type"s -> s.toUpperCase()
BinaryOperator<T>(T, T) → Tapply(a, b)"merge two of the same"(a, b) -> a + b
Comparator<T> (java.util)(T, T) → intcompare(a, b)"which comes first?"(a, b) -> a.compareTo(b)
💡 How to pick the right one Ask two questions: "How many inputs?" and "What comes out?"
  • Nothing in, something out → Supplier
  • Something in, nothing out → Consumer
  • Something in, yes/no out → Predicate
  • Something in, something else out → Function
  • Same type in and out → UnaryOperator
ℹ️ Primitive versions Generics only work with objects, so Predicate<Integer> boxes every int into an Integer. For speed, Java also has primitive variants: IntPredicate, IntFunction<R>, ToIntFunction<T>, IntUnaryOperator, IntBinaryOperator, DoubleSupplier, and others. Same idea, no boxing. You will meet some of them with IntStream in the next topic.

3.7 Method references — an even shorter lambda

Often a lambda does nothing except call one method that already exists:

Consumer<String> printer = msg -> System.out.println(msg);

Java lets you write just the method's address with the double-colon operator :::

Consumer<String> printer = System.out::println;   // "use System.out's println method"

Read :: as "use the method …". There are exactly 4 kinds:

#KindSyntaxLambda equivalent
1Static methodInteger::parseInts -> Integer.parseInt(s)
2Instance method of a particular object (you already have the object)System.out::println
shopName::length		x -> System.out.println(x)
() -> shopName.length()
3Instance method of an arbitrary object of a type (the object is the first parameter)String::toUpperCase
String::compareToIgnoreCase		s -> s.toUpperCase()
(a, b) -> a.compareToIgnoreCase(b)
4ConstructorStudent::new
ArrayList::new		name -> new Student(name)
() -> new ArrayList<>()
💡 Kind 2 vs Kind 3 — the trick to tell them apart Look at what is on the left of ::.
  • A variable / object (System.out, shopName) → kind 2. The object is fixed.
  • A class name but the method is not static (String::toUpperCase) → kind 3. The object will be supplied later as the first argument.

Method references are just shorthand — use them when they make the code clearer. If you need extra logic (s -> s.trim().toUpperCase()), keep the lambda.

3.8 The "effectively final" rule

A lambda can use local variables from the method around it — this is called capturing. But there is one rule: the variable must be final or effectively final (never changed after it got its value).

double taxRate = 0.18;                                  // assigned once, never changed
Function<Double, Double> addTax = p -> p + p * taxRate; // ✅ OK

double rate = 0.18;
rate = 0.12;                                            // changed!
Function<Double, Double> bad = p -> p * rate;           // ❌ compile error:
// "local variables referenced from a lambda expression must be final or effectively final"

Why this rule? A lambda may run later, maybe on another thread, after the method has already finished and its local variables are gone. So Java copies the value into the lambda. If the variable could still change, the copy and the original would disagree — confusing bugs. Making it "never changes" removes the problem.

ℹ️ Fields are different Fields (instance or static variables) live on the heap, not on the method's stack, so lambdas can change them: Runnable click = () -> clickCounter++; compiles if clickCounter is a field. Be careful with this in multi-threaded code (topic 17).
ℹ️ this inside a lambda In an anonymous class, this means the anonymous object. In a lambda, this means the surrounding object — a lambda does not create a new scope. That is one small difference between the two.

3.9 Composing lambdas — building big behaviour from small pieces

The built-in interfaces have default methods that glue lambdas together, like LEGO bricks.

Function: andThen and compose

Function<Double, Double> discount = p -> p - 100;
Function<Double, Double> gst      = p -> p * 1.18;

discount.andThen(gst).apply(1000.0);   // (1000 - 100) * 1.18 = 1062.0  -> discount FIRST
discount.compose(gst).apply(1000.0);   // (1000 * 1.18) - 100 = 1080.0  -> gst FIRST
f.andThen(g)= input→f→g→result
f.compose(g)= input→g→f→result

Function.identity() is a function that returns its input unchanged (x -> x). It is handy in Streams, e.g. building a map keyed by the object itself.

Predicate: and, or, negate, Predicate.not

Predicate<Product> isElectronics = p -> p.getCategory().equals("Electronics");
Predicate<Product> isCheap       = p -> p.getPrice() < 1000;

isElectronics.and(isCheap)      // both must be true      (like &&)
isElectronics.or(isCheap)       // at least one true      (like ||)
isElectronics.negate()          // opposite               (like !)
Predicate.not(isCheap)          // static version of negate, Java 11+

Consumer: andThen — do one thing, then another, with the same input:

Consumer<String> log   = m -> System.out.println("LOG  : " + m);
Consumer<String> email = m -> System.out.println("EMAIL: " + m);
log.andThen(email).accept("Order #77 shipped");

Comparator helpers — the most used composition in real projects:

products.sort(Comparator.comparing(Product::getPrice));                    // cheapest first
products.sort(Comparator.comparing(Product::getPrice).reversed());         // most expensive first
products.sort(Comparator.comparing(Product::getCategory)
        .thenComparing(Product::getPrice, Comparator.reverseOrder()));     // category, then price desc
names.sort(Comparator.naturalOrder());                                     // A..Z
names.sort(Comparator.nullsLast(Comparator.naturalOrder()));               // nulls at the end

Comparator.comparing(keyExtractor) takes a Function that pulls out the "sort key" and builds the comparator for you. Much safer than writing a.getPrice() - b.getPrice() by hand (subtraction can overflow and does not work for double).

6. Common mistakes

⚠️ Mistake: changing a captured local variable 
int total = 0;
prices.forEach(p -> total += p);   // ❌ total must be effectively final
Fix: don't mutate outside state from a lambda. Use a loop, or (next topic) a stream: int total = prices.stream().mapToInt(Integer::intValue).sum();
⚠️ Mistake: forgetting return in a block body (or adding it in an expression body) 
Function<Integer, Integer> square = x -> { x * x; };      // ❌ not a statement, no return
Function<Integer, Integer> square2 = x -> return x * x;   // ❌ 'return' not allowed without { }
Fix: x -> x * x or x -> { return x * x; }
⚠️ Mistake: assigning a lambda to a non-functional type 
Object o = () -> System.out.println("hi");   // ❌ Object is not a functional interface
var r = () -> System.out.println("hi");      // ❌ 'var' gives no target type
Fix: always give a functional interface type: Runnable r = () -> ...;
⚠️ Mistake: thinking a lambda runs when it is created Writing Runnable r = () -> sendEmail(); does not send an email. It only describes the job. The job runs when someone calls r.run().
⚠️ Mistake: calling the wrong method name predicate.apply(x) or supplier.apply() do not compile. Each interface has its own method: test, apply, accept, get, run, compare. Keep the table in 3.6 handy.
🚫 Mistake: writing a comparator with subtraction (a, b) -> a.getPrice() - b.getPrice() does not compile for double (compare must return int) and can overflow for large ints.
Fix: Comparator.comparing(Product::getPrice) or Integer.compare(a, b) / Double.compare(a, b).
⚠️ Mistake: giant multi-line lambdas A 25-line lambda is hard to read, test and debug (stack traces show lambda$main$0). Fix: move the logic into a well-named private method and use a method reference: orders.forEach(this::sendInvoice).

7. Best practices

  • Keep lambdas short — ideally one line. If it grows, extract a method and use a method reference.
  • Prefer built-in interfaces (Predicate, Function…) over creating your own. Create your own only when a domain name adds meaning (e.g. DiscountRule) — and then annotate it with @FunctionalInterface.
  • Use method references when they read better: map(String::trim) is clearer than map(s -> s.trim()). But x -> x + 1 is fine as a lambda.
  • Name parameters meaningfully: order -> order.getTotal() beats o -> o.getTotal() in long chains; single letters are okay for tiny lambdas.
  • No side effects in lambdas used for filtering/mapping — they should only compute a result. Side effects belong in Consumers like forEach.
  • Use Comparator.comparing(...) and its helpers (thenComparing, reversed, nullsLast) instead of hand-written compare logic.
  • Store reusable rules as constants (static final Predicate<Order> IS_PAID = ...) and compose them.
  • Handle checked exceptions explicitly: built-in interfaces cannot throw checked exceptions, so wrap them in a try/catch inside a helper method rather than inside a long lambda.

8. Key takeaways

  • A lambda is a short, nameless function: (parameters) -> body.
  • A lambda needs a functional interface (exactly one abstract method) as its target type. @FunctionalInterface asks the compiler to check this.
  • Lambdas replace most anonymous classes, removing boilerplate.
  • Learn the shapes: Supplier ()→T, Consumer T→(), Predicate T→boolean, Function T→R, BiFunction (T,U)→R, UnaryOperator T→T, BinaryOperator (T,T)→T.
  • Method references (::) are shorthand for lambdas that just call one method — 4 kinds: static, particular object, arbitrary object, constructor.
  • Captured local variables must be effectively final.
  • Compose behaviour with andThen/compose, and/or/negate, and Comparator.comparing().thenComparing().reversed().
  • A lambda runs only when its interface method is called.
  • Streams (next topic) and much of Spring's configuration are built on exactly these ideas.

6. Your own functional interface. Create @FunctionalInterface interface Validator<T> { boolean validate(T value); } and give it a default method and(Validator<T> other) that returns a new validator passing only if both pass. Use it to validate a password: length ≥ 8 AND contains a digit.

Hint / solution 
@FunctionalInterface
interface Validator<T> {
    boolean validate(T value);

    default Validator<T> and(Validator<T> other) {
        return value -> this.validate(value) && other.validate(value);
    }
}

Validator<String> longEnough = p -> p.length() >= 8;
Validator<String> hasDigit   = p -> p.chars().anyMatch(Character::isDigit);
Validator<String> strong     = longEnough.and(hasDigit);

System.out.println(strong.validate("secret"));      // false
System.out.println(strong.validate("secret123"));   // true

This is exactly how Predicate.and is written inside the JDK. A default method does not break the "one abstract method" rule.

10. Interview questions

Q1. What is a lambda expression in Java?

A lambda is a short way to write an anonymous function — a block of code with parameters and a body but no name — introduced in Java 8. Syntax: (params) -> expression or (params) -> { statements; }. It provides an implementation for the single abstract method of a functional interface, so behaviour can be passed around like data.

Q2. What is a functional interface? Is @FunctionalInterface mandatory?

An interface with exactly one abstract method (default and static methods don't count; methods from Object like equals don't count either). Examples: Runnable, Comparator, Predicate. The annotation is not mandatory — any interface with one abstract method works with lambdas — but it makes the compiler enforce the rule and documents the intent.

Q3. Explain Predicate, Function, Consumer and Supplier.

Predicate<T>: takes T, returns boolean (test). Function<T,R>: takes T, returns R (apply). Consumer<T>: takes T, returns nothing (accept). Supplier<T>: takes nothing, returns T (get). Variants: BiFunction, BiConsumer, BiPredicate, UnaryOperator, BinaryOperator, and primitive versions like IntPredicate.

Q4. What are method references? Name the four types.

A compact form of a lambda that only calls an existing method, using ::. Types: (1) static method Math::abs; (2) instance method of a particular object System.out::println; (3) instance method of an arbitrary object of a type String::length; (4) constructor ArrayList::new.

Q5. What does "effectively final" mean and why do lambdas require it?

A local variable that is never reassigned after initialisation, even without the final keyword. Lambdas capture a copy of local variable values because the lambda may run after the method has returned (or on another thread). Requiring the variable to be unchanging guarantees the copy is always correct and avoids race conditions. Fields are not subject to this rule.

Q6. Differences between a lambda and an anonymous class?

Lambdas work only with functional interfaces; anonymous classes can implement any interface or extend a class and can have multiple methods and their own fields. Inside a lambda, this refers to the enclosing instance; in an anonymous class it refers to the anonymous object. Anonymous classes generate a separate .class file; lambdas are created at runtime via invokedynamic, which is usually lighter. Lambdas cannot shadow local variables of the enclosing scope.

Q7. What's the difference between Function.andThen and Function.compose?

f.andThen(g) runs f first, then g on its result: g(f(x)). f.compose(g) runs g first, then f: f(g(x)).

Q8. Can a functional interface have default and static methods? Can it extend another interface?

Yes, any number of default and static methods (e.g. Predicate has and, or, negate, and static not, isEqual). It can extend another interface as long as the total number of abstract methods stays one.

Q9. Can a lambda throw a checked exception?

Only if the functional interface's method declares it. Callable<V>.call() declares throws Exception, so a Callable lambda may throw checked exceptions. Function.apply does not, so inside a Function lambda you must catch checked exceptions (or wrap them in an unchecked one), or define your own functional interface that declares throws.

Q10. Why are lambdas important for Spring developers?

Spring APIs are designed around them: Spring Security's Lambda DSL for HttpSecurity, Optional.orElseThrow(() -> ...) with Spring Data repositories, CommandLineRunner/ApplicationRunner beans, RestClient/WebClient callbacks, TransactionTemplate.execute(status -> ...), JdbcTemplate RowMappers, and Streams for transforming entities to DTOs.
