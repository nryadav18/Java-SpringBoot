48. Spring Security with Database Users & Roles

Store users and roles in a database, let people register with hashed passwords, and protect both URLs and individual methods – including "only the owner may see this".

🎯 What you will learn
  • Implement UserDetails and UserDetailsService on top of a JPA entity (AppUser + Role).
  • Build a registration endpoint that hashes passwords with BCrypt.
  • Role-based access with hasRole, permission-based access with hasAuthority, both in requestMatchers.
  • Method security: @EnableMethodSecurity, @PreAuthorize("hasRole('ADMIN')"), and SpEL owner checks like #username == authentication.name.
  • Get the current user with @AuthenticationPrincipal and SecurityContextHolder.
  • Seed the first admin user and test secured endpoints with @WithMockUser, @WithUserDetails and httpBasic().
📋 Before you start — you should know: Topic 47 · Security fundamentals, Topic 38 · Spring Data JPA, Topic 34 · Validation and Topic 27 · AOP (proxies).

1. Why this matters

In topic 47 our two users were written into the Java code. That is fine for a demo, but a real application needs much more:

  • New people must be able to sign up while the app is running.
  • Users must survive a restart – they live in a database.
  • An admin must be able to lock or delete accounts and give people roles.
  • Rules become more personal: "A customer may see their own orders, not everybody's." URL rules alone cannot express that.

This is what nearly every business application does: an online shop, a college portal, a hospital system. After this lesson you can build the user-management backbone of such an app.

2. Real-life analogy

🏨 Think of a hotel

The guest register (a big book at reception) is our database table of users.

The receptionist who looks up your name in the book when you show your ID is the UserDetailsService. She does not decide anything – she just finds your entry and hands it to the security guard.

Checking in (filling in the form, choosing a PIN) is registration. The hotel never writes your PIN in the book – only a scrambled version (a hash).

Your key card carries roles: Guest opens your room and the gym; Staff opens every floor; Manager also opens the office. That is hasRole(...).

"Only your own room": two guests both have the role Guest, but card 214 opens only room 214. The lock looks at the data (the room number) and the person. That is @PreAuthorize("#username == authentication.name") – method security with an owner check.

The very first manager cannot be created by "another manager" – the owner sets them up when the hotel opens. That is our admin seeder.

3. Concepts step by step

3.1 The plan: replace the in-memory user store

The good news: the authentication machinery from topic 47 stays exactly the same. We only swap one piece – where users come from.

BasicAuthenticationFilter→ AuthenticationManager→ DaoAuthenticationProvider→ JpaUserDetailsService (new)→ AppUserRepository→ H2 / MySQL table

Topic 47: InMemoryUserDetailsManager. Topic 48: our own JpaUserDetailsService that reads the app_users table. Everything else – BCrypt, filters, 401/403 – works unchanged. This is "programming to an interface" (topic 8) paying off.

3.2 The data model: AppUser and Role

We need two things per user: who they are (username + password hash) and what they may do (roles). Our model:

user/AppUser.java (key part)@Entity
@Table(name = "app_users")
public class AppUser {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 50)
    private String username;

    @Column(nullable = false, length = 100)      // BCrypt hash = 60 chars
    private String password;

    private boolean enabled = true;

    @ElementCollection(fetch = FetchType.EAGER)  // roles are needed at EVERY login
    @CollectionTable(name = "user_roles", joinColumns = @JoinColumn(name = "user_id"))
    @Enumerated(EnumType.STRING)
    @Column(name = "role", nullable = false)
    private Set<Role> roles = new HashSet<>();
}
  • Why AppUser and not User? Spring Security already has a class User, and user is a reserved word in some databases.
  • @ElementCollection stores a collection of simple values (our enum) in a side table – no extra entity needed.
  • FetchType.EAGER – roles are loaded together with the user. Otherwise you hit a LazyInitializationException (topic 40) when Spring reads the authorities after the transaction is closed.
  • EnumType.STRING stores "ADMIN" rather than a number; adding a new enum value later cannot scramble existing data.

Our Role enum also lists permissions (fine-grained rights):

user/Role.javapublic enum Role {
    USER(Set.of("NOTE_WRITE")),
    ADMIN(Set.of("REPORT_READ", "USER_DELETE"));
    ...
    public String asAuthority() { return "ROLE_" + name(); }
}
ℹ️ Alternative: Role as its own entity Many projects use a roles table and @ManyToMany Set<Role> roles with a join table (topic 40). That lets admins create new roles at runtime without redeploying. An enum is simpler and perfectly fine when the set of roles is fixed – which is the common case.

3.3 UserDetails and UserDetailsService with JPA

Spring Security does not know our AppUser class. It speaks only the UserDetails "language". So we write a small adapter (a translator):

security/SecurityUser.java (key part)public class SecurityUser implements UserDetails {
    private final Long id;
    private final String username;
    private final String password;
    private final boolean enabled;
    private final Set<GrantedAuthority> authorities;

    public SecurityUser(AppUser user) {
        this.id = user.getId();
        this.username = user.getUsername();
        this.password = user.getPassword();
        this.enabled = user.isEnabled();
        this.authorities = toAuthorities(user.getRoles());  // ADMIN -> ROLE_ADMIN, REPORT_READ, USER_DELETE
    }
    public Long getId() { return id; }                       // our own extra!
    @Override public String getUsername() { return username; }
    @Override public String getPassword() { return password; }
    @Override public Collection<? extends GrantedAuthority> getAuthorities() { return authorities; }
    @Override public boolean isEnabled() { return enabled; }
}

And the service that looks users up:

security/JpaUserDetailsService.java@Service
public class JpaUserDetailsService implements UserDetailsService {
    private final AppUserRepository userRepository;
    ...
    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        return userRepository.findByUsername(username)
                .map(SecurityUser::new)
                .orElseThrow(() -> new UsernameNotFoundException("User not found: " + username));
    }
}

Because it is a @Service bean implementing UserDetailsService, Spring Boot automatically wires it, together with our PasswordEncoder bean, into the DaoAuthenticationProvider. No extra configuration.

3.4 Trace: what happens when alice logs in?

Request: curl -u alice:alice123 http://localhost:8080/api/me

  1. BasicAuthenticationFilter decodes the header → username alice, password alice123.
  2. It asks the AuthenticationManager, which delegates to DaoAuthenticationProvider.
  3. The provider calls JpaUserDetailsService.loadUserByUsername("alice") → Hibernate runs select ... from app_users where username='alice' (+ roles).
  4. The row is wrapped in a SecurityUser with authorities ROLE_USER, NOTE_WRITE.
  5. The provider calls passwordEncoder.matches("alice123", "$2a$10$...") → true. It checks isEnabled() → true.
  6. An authenticated UsernamePasswordAuthenticationToken (principal = our SecurityUser) is put into the SecurityContextHolder.
  7. AuthorizationFilter: /api/me needs authenticated() → OK → controller runs.

If the username does not exist or the password is wrong, step 3 or 5 fails with a BadCredentialsException → 401. Spring deliberately reports both cases the same way so attackers cannot discover which usernames exist.

3.5 Registration with BCrypt

user/UserService.java (register)@Transactional
public UserResponse register(RegisterRequest request) {
    if (userRepository.existsByUsername(request.username())) {
        throw new UsernameTakenException(request.username());           // -> 409 Conflict
    }
    String hash = passwordEncoder.encode(request.password());           // "bob12345" -> "$2a$10$..."
    AppUser saved = userRepository.save(new AppUser(request.username(), hash, Set.of(Role.USER)));
    return UserResponse.from(saved);                                    // DTO without password
}

Four security rules hide in these few lines:

  1. Hash before saving. The plain password never reaches the database.
  2. The server chooses the role. The request has no "role" field. If it did, anybody could register as ADMIN (a real-world bug called mass assignment).
  3. Validate input (@Valid + @Size(min = 8, max = 72)): BCrypt only uses the first 72 bytes, and short passwords are weak.
  4. Never return the password (not even the hash). The response DTO simply has no such field.

The URL must be public, otherwise nobody could ever create an account: .requestMatchers(HttpMethod.POST, "/api/auth/register").permitAll().

3.6 Roles vs authorities (permissions) in URL rules

Recap: Spring only stores authorities (strings). A role is an authority with the ROLE_ prefix. Our users get both kinds:

UserRoles in DBAuthorities Spring sees
aliceUSERROLE_USER, NOTE_WRITE
adminADMIN, USERROLE_ADMIN, ROLE_USER, REPORT_READ, USER_DELETE, NOTE_WRITE

    .requestMatchers(PathRequest.toH2Console()).permitAll()
    .requestMatchers("/error").permitAll()
    .requestMatchers("/api/admin/**").hasRole("ADMIN")              // == hasAuthority("ROLE_ADMIN")
    .requestMatchers("/api/reports/**").hasAuthority("REPORT_READ") // a permission
    .anyRequest().authenticated()

ExpressionTrue when the user has…
hasRole("ADMIN")ROLE_ADMIN
hasAnyRole("ADMIN", "MANAGER")ROLE_ADMIN or ROLE_MANAGER

💡 Roles or permissions? Roles are who you are (job title). Permissions are what you can do. Checking permissions in code (hasAuthority("REPORT_READ")) means you can later give that one right to a new role (say AUDITOR) without touching every rule. Small apps: roles are enough. Bigger apps: roles that bundle permissions – like our enum.

3.7 Method security: @EnableMethodSecurity + @PreAuthorize

URL rules guard the doors. Method security guards individual actions – on services, not just controllers. Switch it on once:

@Configuration
@EnableWebSecurity
@EnableMethodSecurity      // without this, @PreAuthorize is silently IGNORED!
public class SecurityConfig { ... }

Then annotate methods:

user/UserService.java@PreAuthorize("hasAuthority('USER_DELETE')")
@Transactional
public void deleteUser(Long id) { ... }

How does it work? Exactly like @Transactional (topic 42): Spring wraps the bean in an AOP proxy (topic 27). Before the real method runs, the proxy evaluates the expression. False → it throws AccessDeniedException → ExceptionTranslationFilter turns it into 403.

Controller→ Proxy: evaluate "hasAuthority('USER_DELETE')"→ ✓ real deleteUser() / ✗ AccessDeniedException → 403
AnnotationWhen checkedNotes
@PreAuthorize("...")Before the methodFull SpEL, can use arguments. Most used.
@PostAuthorize("...")After the methodCan inspect returnObject (e.g. owner of a loaded entity).
@Secured("ROLE_ADMIN")BeforeOld, no SpEL. Needs @EnableMethodSecurity(securedEnabled = true).
@RolesAllowed("ADMIN")BeforeJakarta standard (JSR-250). Needs jsr250Enabled = true.
⚠️ Self-invocation gotcha (again!) Like @Transactional, the check runs only when the call goes through the proxy. If a method inside UserService calls this.deleteUser(5), there is no security check. Call protected methods from another bean.

3.8 SpEL owner checks: "only your own notes"

SpEL (Spring Expression Language, topic 26) lets the rule look at method arguments and the current user:

note/NoteService.java@PreAuthorize("#username == authentication.name or hasRole('ADMIN')")
@Transactional(readOnly = true)
public List<NoteResponse> findNotesOf(String username) { ... }
SpEL pieceMeaning
#usernameThe method parameter named username.
authenticationThe current Authentication; authentication.name = logged-in username.
principalThe principal object – here our SecurityUser, so principal.id works too.
returnObjectOnly in @PostAuthorize: the value the method returned.
and, or, !Combine conditions.
@beanName.method(...)Call any Spring bean, e.g. @noteSecurity.isOwner(#id, authentication) for complex rules.

Trace:

alice → GET /api/users/alice/notes→ "alice" == "alice" ✓→ 200 + her notes
alice → GET /api/users/admin/notes→ "admin" == "alice" ✗, hasRole ADMIN ✗→ 403
admin → GET /api/users/alice/notes→ names differ, but hasRole ADMIN ✓→ 200
ℹ️ Where does the owner come from when creating? Never from the request body. NoteController.create passes me.getUsername() from the logged-in user. Otherwise alice could send "owner":"bob" and create notes in bob's name.

3.10 Seeding the first admin

Only admins may manage users… so who creates the first admin? The application itself, at startup, if it does not exist yet:

config/DataSeeder.java@Override
@Transactional
public void run(String... args) {
    if (!users.existsByUsername("admin")) {
        users.save(new AppUser("admin", passwordEncoder.encode("admin123"), Set.of(Role.ADMIN, Role.USER)));
    }
    ...
}

The "only if missing" check makes it safe to run on every start (it is idempotent). In production read the password from an environment variable (@Value("${ADMIN_PASSWORD}")), or insert the admin with a Flyway migration (topic 43) using a pre-computed BCrypt hash.

3.12 Bonus: the H2 console behind Spring Security

The H2 console (topic 37) breaks as soon as security is on: it needs a POST without a CSRF token and runs inside HTML frames, which the default X-Frame-Options: DENY header blocks. Our config fixes all three – for learning only:

.requestMatchers(PathRequest.toH2Console()).permitAll()           // reach it without login
.csrf(csrf -> csrf.disable())                                       // (our API is stateless anyway)
.headers(h -> h.frameOptions(frame -> frame.sameOrigin()))        // allow frames from our own site

4.1 The full SecurityConfig

security/SecurityConfig.java@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.POST, "/api/auth/register").permitAll()
                .requestMatchers(PathRequest.toH2Console()).permitAll()
                .requestMatchers("/error").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .requestMatchers("/api/reports/**").hasAuthority("REPORT_READ")
                .anyRequest().authenticated()
            )
            .httpBasic(Customizer.withDefaults())
            .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable())
            .headers(headers -> headers.frameOptions(frame -> frame.sameOrigin()));
        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

SessionCreationPolicy.STATELESS tells Spring never to create an HTTP session. With HTTP Basic, the client sends credentials on every request anyway, so a session cookie would only add risk (and then CSRF would matter again). Notice there is no UserDetailsService bean here – the @Service is found automatically.

4.2 The exception handler – and a trap

web/ApiExceptionHandler.java@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(UsernameTakenException.class)
    public ProblemDetail usernameTaken(UsernameTakenException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, ex.getMessage());
    }
}

We deliberately do not add @ExceptionHandler(Exception.class). A catch-all would also catch the AccessDeniedException thrown by @PreAuthorize inside the controller call and turn a correct 403 into a wrong 500. If you need a catch-all, re-throw AccessDeniedException and AuthenticationException or add a dedicated handler returning 403.

6. Common mistakes

⚠️ Mistake: @PreAuthorize does nothing You forgot @EnableMethodSecurity. The annotations are then ignored silently – everyone gets in.
Fix: add @EnableMethodSecurity to a @Configuration class, and write a test that expects 403.
⚠️ Mistake: storing ROLE_ADMIN and then calling .roles("ROLE_ADMIN") User.roles(...) adds the prefix itself and throws "ROLE_ADMIN cannot start with ROLE_ (it is automatically added)".
Fix: decide one convention: store ADMIN and use .roles()/hasRole(), or store ROLE_ADMIN and use .authorities()/hasAuthority().
⚠️ Mistake: LazyInitializationException at login Roles mapped LAZY, read later by Spring after the repository's transaction closed.
Fix: fetch = FetchType.EAGER for roles (they are tiny), or a JOIN FETCH query in findByUsername.
⚠️ Mistake: @AuthenticationPrincipal SecurityUser me is null in tests @WithMockUser creates Spring's own User, not your SecurityUser, so the cast fails and Spring injects null.
Fix: use @WithUserDetails("alice") (loads the real principal) for such endpoints.
⚠️ Mistake: #username in SpEL is null SpEL reads parameter names from the compiled class. Maven (via the Spring Boot parent) compiles with -parameters; some IDE setups do not.
Fix: keep the Boot parent's compiler settings, or name the parameter explicitly with @P("username") (org.springframework.security.core.parameters.P).
⚠️ Mistake: catch-all exception handler turns 403 into 500 @ExceptionHandler(Exception.class) swallows AccessDeniedException.
Fix: do not catch everything, or handle AccessDeniedException explicitly with 403.
🔥 Mistake: letting the client choose its role A role field in RegisterRequest = anybody can become ADMIN.
Fix: the server assigns Role.USER; only admins promote users through a protected endpoint.
🔥 Mistake: returning the entity from the controller Returning AppUser directly serialises the password hash to JSON.
Fix: always map to a DTO (UserResponse) without the password (topic 33).

7. Best practices

  • Defence in depth: URL rules for broad areas (/api/admin/**) plus @PreAuthorize on sensitive service methods.
  • Put method security on services, not only controllers – services can be called from many places (schedulers, message listeners…).
  • Owner checks belong in the service (or a dedicated bean like @noteSecurity.isOwner(...)), and the owner always comes from the authenticated user.
  • Permissions over roles in code for bigger systems: check hasAuthority("REPORT_READ"), map roles → permissions in one place.
  • Unique, case-consistent usernames (e.g. store lower-case emails) with a database UNIQUE constraint.
  • Account status: use enabled/locked flags to block users instead of deleting them (keeps history).
  • Rate-limit login and registration and consider account lockout after many failures (brute-force protection).
  • Seed admins safely: password from environment/secret store, force a change on first login in real systems.
  • Test the negative cases: for each protected endpoint at least one 401 and one 403 test.

8. Key takeaways

  • To use a database, implement UserDetailsService.loadUserByUsername with a JPA repository – the rest of Spring Security stays the same.
  • UserDetails is Spring's view of a user; an adapter (SecurityUser) keeps the entity clean and adds extra fields.
  • Registration: validate, check duplicates, hash with BCrypt, assign the default role on the server, return a DTO without password.
  • hasRole("X") checks ROLE_X; hasAuthority("Y") checks the exact string Y.
  • @EnableMethodSecurity + @PreAuthorize protect methods via AOP proxies; SpEL can compare arguments with authentication.name.
  • Current user: @AuthenticationPrincipal in controllers, SecurityContextHolder anywhere on the request thread.
  • Seed the first admin at startup only if missing.
  • Test with @WithMockUser, @WithUserDetails, httpBasic() from spring-security-test.

10. Interview questions

Q1. How do you load users from a database in Spring Security?

Implement UserDetailsService (one method, loadUserByUsername) using a repository, return a UserDetails (own adapter or Spring's User), and expose it as a bean together with a PasswordEncoder. Spring Boot wires both into a DaoAuthenticationProvider.

Q2. What should happen in a registration endpoint, security-wise?

Validate input, reject duplicate usernames (409), hash the password with BCrypt, assign the default role server-side (never from the request), save, and return a DTO without any password data. The endpoint itself must be permitAll; consider rate limiting and email verification.

Q3. Difference between URL-based security and method security?

URL rules (authorizeHttpRequests) run in the filter chain and only see the request (path, method). Method security (@PreAuthorize) runs around a bean method via an AOP proxy and can use method arguments, return values and beans – ideal for ownership and business-level rules. Use both.

Q4. What does @PreAuthorize("#username == authentication.name") do?

Before the method runs, it compares the method parameter username with the name of the authenticated user. If false, an AccessDeniedException is thrown (403). Parameter names must be available (compiled with -parameters) or annotated with @P.

Q5. @PreAuthorize vs @PostAuthorize vs @Secured?

@PreAuthorize checks before invocation with SpEL. @PostAuthorize checks after, with access to returnObject (careful: the method's side effects already happened). @Secured is the older annotation taking role names only, no SpEL; it must be enabled with securedEnabled = true.

Q6. How do you get the currently logged-in user?

In a controller: @AuthenticationPrincipal MyUserDetails me, or an Authentication/Principal parameter. Anywhere on the request thread: SecurityContextHolder.getContext().getAuthentication(). Note it is thread-bound, so async code needs context propagation.

Q7. Why could @PreAuthorize be ignored even when enabled?

Self-invocation: calling the method from inside the same class bypasses the proxy. Also: the class is not a Spring bean (created with new), or the method is private/final (cannot be proxied).

Q8. @WithMockUser vs @WithUserDetails?

@WithMockUser creates a fake User with given username/roles/authorities without touching your user store – fast and isolated. @WithUserDetails loads the user via your real UserDetailsService, so the principal is your custom type – needed when code uses @AuthenticationPrincipal with that type or relies on DB state.

Q9. Roles vs authorities – how would you design permissions for a large app?

Store roles on users and map each role to a set of fine-grained permissions (authorities). Check permissions in code (hasAuthority("ORDER_REFUND")), so changing which roles may refund needs no code change – only the mapping (enum or database tables).

Q10. How do you create the first admin user safely?

Seed it at startup only if it does not exist (idempotent), or via a DB migration. Take the password from an environment variable/secret manager, never hard-code it in production, and require a password change on first login.
