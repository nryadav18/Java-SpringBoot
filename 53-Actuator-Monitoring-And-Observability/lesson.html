1. Why this matters

On your laptop you can see everything: the console, the debugger, the logs. In production your app runs on a server you never see, maybe as five copies behind a load balancer, used by thousands of people. Now the important questions are:

  • Is the app alive? Can it reach its database and the payment provider?
  • How fast are the requests? Did they get slower after yesterday's release?
  • How many errors (HTTP 500s) per minute?
  • Is memory slowly filling up? How many threads are busy?
  • Which version is deployed right now?
  • How many orders did we get in the last hour, and how many failed to pay? (business metrics!)

Monitoring means collecting such numbers and alerting when something looks wrong. Observability is a slightly bigger idea: your system gives out enough information (logs, metrics and traces) that you can understand why something is wrong, even for problems you did not predict.

Spring Boot makes this easy with Actuator: add one dependency and you get production-ready endpoints for health, info, metrics and more. Every serious Spring Boot service in companies has Actuator switched on – Kubernetes uses its health endpoints to restart sick pods, and Prometheus/Grafana read its metrics for dashboards and alerts.

2. Real-life analogy

🚗 The dashboard of a car You don't open the engine to know if your car is OK. The dashboard tells you:
  • Warning lights (engine, oil, battery) → /actuator/health: UP or DOWN, and which part is the problem.
  • Speedometer, fuel gauge, rev counter → /actuator/metrics: live numbers. Some only go up (the odometer = a counter), some go up and down (fuel = a gauge), some measure how long things take (lap time = a timer).
  • The registration papers (model, year, owner) → /actuator/info.
  • The mechanic's diagnostic port → the more detailed endpoints (/env, /beans, /threaddump). Very useful – but you don't let strangers plug into it! That is why we expose endpoints carefully.
  • A fleet manager's control room watching 500 cars on big screens → Prometheus + Grafana, collecting the dashboards of all your app instances in one place.

3.4 Exposing endpoints safely

Two separate ideas:

  • Access / enabled – does the endpoint exist at all? Almost all endpoints exist by default (except shutdown).
  • Exposure – can it be reached over HTTP? By default only health is exposed over the web.
application.properties# expose a chosen list over HTTP (comma-separated)
management.endpoints.web.exposure.include=health,info,metrics,prometheus,loggers

# or: everything except a few (only behind Spring Security!)
# management.endpoints.web.exposure.include=*
# management.endpoints.web.exposure.exclude=env,heapdump,threaddump

# Spring Boot 3.4+: control access per endpoint (none | read-only | unrestricted)
# management.endpoint.loggers.access=read-only
🛑 Never do this on a public servermanagement.endpoints.web.exposure.include=* without Spring Security exposes your configuration and lets anyone download a heap dump full of passwords and tokens. Real companies have been hacked this way.

Three good ways to protect Actuator in production:

  1. Expose only what you need (health, info, prometheus).
  2. A separate management port that only the internal network can reach: management.server.port=9090. The firewall then blocks 9090 from the internet.
  3. Spring Security (topic 47): allow /actuator/health for everyone, everything else only for an ACTUATOR/ADMIN role:
http.authorizeHttpRequests(auth -> auth
        .requestMatchers(EndpointRequest.to("health", "info")).permitAll()
        .requestMatchers(EndpointRequest.toAnyEndpoint()).hasRole("ACTUATOR")
        .anyRequest().authenticated());

In our project the default profile exposes a safe set, and a dev profile (application-dev.properties) exposes everything – for learning on your own machine only.

3.5 Health checks

/actuator/health combines many health indicators. Spring Boot adds them automatically for the things it finds: diskSpace, ping, db (if a DataSource exists), redis, mail, rabbit, kafka…

StatusMeaningHTTP status of /health
UPWorking200
DOWNBroken503 Service Unavailable
OUT_OF_SERVICEDeliberately taken out of service503
UNKNOWNCannot tell200

The overall status is the "worst" of all components: one DOWN makes everything DOWN. Load balancers only look at the HTTP status – 200 = send traffic, 503 = don't.

Details are hidden by default (you only see {"status":"UP"}). Show them with:

management.endpoint.health.show-details=always        # never | when-authorized | always
management.endpoint.health.show-components=always

Liveness and readiness probes

Kubernetes (topic 69) asks two different questions:

ProbeQuestionIf it fails…URL
Liveness"Is the app alive, or stuck forever?"Kubernetes restarts the container/actuator/health/liveness
Readiness"Can the app handle requests right now?"Kubernetes stops sending traffic (no restart)/actuator/health/readiness
management.endpoint.health.probes.enabled=true
# readiness also depends on our payment gateway check
management.endpoint.health.group.readiness.include=readinessState,paymentGateway
⚠️ Don't put external systems into livenessIf the database is down and liveness fails, Kubernetes restarts ALL your pods again and again – which does not fix the database. External dependencies belong in readiness (or just the main health), never in liveness.

3.6 A custom HealthIndicator

For your own important dependency (a payment provider, an SFTP server, a licence), implement HealthIndicator:

health/PaymentGatewayHealthIndicator.java@Component
public class PaymentGatewayHealthIndicator implements HealthIndicator {

    @Override
    public Health health() {
        try {
            long latencyMs = paymentGateway.ping();
            return Health.up().withDetail("provider", "DemoPay").withDetail("latencyMs", latencyMs).build();
        } catch (Exception ex) {
            return Health.down().withDetail("provider", "DemoPay").withDetail("error", ex.getMessage()).build();
        }
    }
}

The component name comes from the bean name minus "HealthIndicator": paymentGatewayHealthIndicator → paymentGateway. Result:

"paymentGateway":{"status":"UP","details":{"provider":"DemoPay","latencyMs":42}}

3.8 Metrics and Micrometer

A metric is a number measured over time: requests per second, memory used, orders placed. Spring Boot uses Micrometer for metrics. Micrometer is to metrics what SLF4J is to logging: one API in your code, many back-ends (Prometheus, Datadog, New Relic, CloudWatch, Dynatrace…).

Modern metrics are dimensional: a metric has a name plus tags (key=value labels). One metric http.server.requests with tags uri, method, status lets you ask "how many POST /api/orders returned 500?"

Built-in metrics you get for free:

MetricWhat it measures
http.server.requestsEvery HTTP request: count, total time, max – tagged by uri, method, status, outcome, exception
jvm.memory.used / jvm.memory.maxHeap and non-heap memory
jvm.gc.pauseGarbage collection pauses
jvm.threads.liveNumber of threads
process.cpu.usage, system.cpu.usageCPU
hikaricp.connections.activeDatabase connection pool usage (if you have a DB)
logback.eventsNumber of log lines per level – a sudden rise in error is a great alert!
cache.getsCache hits/misses (topic 51)
application.started.timeHow long startup took

Look at one, and filter by tag:

GET /actuator/metrics/http.server.requests
GET /actuator/metrics/http.server.requests?tag=uri:/api/orders&tag=method:POST
GET /actuator/metrics/jvm.memory.used?tag=area:heap

3.9 Custom metrics: the four meter types

Inject MeterRegistry (the place where all meters are registered) and create meters:

MeterBehaviourExamples
CounterOnly goes up (resets on restart)orders placed, emails sent, login failures
GaugeA current value; up and down; read when askedpending orders, queue size, active users
TimerHow long + how often (count, total time, max, percentiles)order processing time, external API call time
DistributionSummaryDistribution of non-time valuesorder amount, uploaded file size
order/OrderService.java (excerpts)// Counter with tags - one time series per (paymentMethod, status) combination
Counter.builder("shop.orders.placed")
        .description("Number of orders placed")
        .tag("paymentMethod", normalise(paymentMethod))
        .tag("status", result.status().name())
        .register(registry)          // returns the existing counter if already registered
        .increment();

// Timer - created once in the constructor, then used for every order
this.processingTimer = Timer.builder("shop.orders.processing")
        .description("Time taken to process (pay) an order")
        .publishPercentileHistogram()
        .register(registry);
Order result = processingTimer.record(() -> { ... return order; });

// Gauge - Micrometer calls countPending() whenever the value is read
Gauge.builder("shop.orders.pending", this, OrderService::countPending)
        .register(registry);

// DistributionSummary - how big are our orders?
this.orderAmounts = DistributionSummary.builder("shop.orders.amount").baseUnit("euros").register(registry);
orderAmounts.record(amount.doubleValue());
⚠️ Tag cardinality – the #1 metrics mistake"Cardinality" = how many different values a tag can have. Each different combination of tag values creates a new time series that is stored forever. A tag like paymentMethod (4 values) is fine. A tag like userId, email or orderId (millions of values) will blow up memory in your app and in Prometheus. That's why our code maps unknown payment methods to "other".

Naming rules: lower case, words separated by dots, start with your domain (shop.orders.placed). Micrometer converts names for each back-end (Prometheus: shop_orders_placed_total).

ℹ️ Annotation styleMicrometer also has @Timed and @Counted annotations, and the newer Observation API (@Observed) that creates a metric AND a trace span at once (topic 65). They need AOP support (spring-boot-starter-aop plus aspect beans). We use the programmatic API here because it shows clearly what happens.

3.10 Prometheus

Prometheus is a free, open-source monitoring database. Every few seconds it pulls ("scrapes") metrics from your app's /actuator/prometheus URL and stores them with timestamps. You can then query history and set up alerts.

pom.xml<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
    <scope>runtime</scope>
</dependency>
Spring Boot app
/actuator/prometheus← scrape every 5 s ← Prometheus
stores time series← PromQL queries ← Grafana
dashboards & alerts

The Prometheus text format looks like this (real output from our app):

shop_orders_placed_total{application="order-service",paymentMethod="upi",status="PAID"} 1.0
shop_orders_pending{application="order-service"} 0.0
shop_orders_amount_euros_count{application="order-service"} 1
shop_orders_amount_euros_sum{application="order-service"} 12.5
shop_orders_processing_seconds_count{application="order-service"} 1
shop_orders_processing_seconds_bucket{application="order-service",le="0.1"} 1

Notice: dots became underscores, counters got _total, timers became _seconds_*, and the base unit "euros" was appended. The application tag comes from management.metrics.tags.application – it is added to every metric so one dashboard can show many services.

A few PromQL (Prometheus Query Language) examples to try in the Prometheus UI:

PromQLMeaning
rate(shop_orders_placed_total[1m])Orders per second, averaged over the last minute
sum by (paymentMethod) (shop_orders_placed_total)Total orders per payment method
histogram_quantile(0.95, sum by (le) (rate(shop_orders_processing_seconds_bucket[5m])))95th-percentile processing time
sum(rate(http_server_requests_seconds_count{status=~"5.."}[1m]))Server errors per second
jvm_memory_used_bytes{area="heap"}Heap memory used
ℹ️ What is a percentile?"p95 = 180 ms" means 95% of requests were faster than 180 ms and 5% were slower. Averages hide slow requests; percentiles show what your unhappiest users experience. That's why we call publishPercentileHistogram().

3.11 Grafana

Grafana draws beautiful dashboards from Prometheus data and can send alerts (email, Slack…). Our docker-compose.yml starts both, and a provisioning file adds Prometheus as a data source automatically. You can import ready-made community dashboards: in Grafana go to Dashboards → New → Import and enter ID 4701 ("JVM (Micrometer)"), or search grafana.com for "Spring Boot".

3.12 Changing log levels at runtime

Production runs at INFO. A customer reports a strange problem. You need DEBUG logs – but restarting means losing the situation. The loggers endpoint changes the level live:

GET  /actuator/loggers/com.course.observability
{"configuredLevel":"INFO","effectiveLevel":"INFO"}

POST /actuator/loggers/com.course.observability
Content-Type: application/json
{"configuredLevel":"DEBUG"}
-> 204 No Content

GET  /actuator/loggers/com.course.observability
{"configuredLevel":"DEBUG","effectiveLevel":"DEBUG"}

Send {"configuredLevel": null} to go back to the configured level. The change is lost on restart, which is usually what you want.

4.1 How the payment gateway connects everything

PaymentGateway is a tiny bean with an AtomicBoolean up. Three classes use it:

  • PaymentGatewayHealthIndicator calls ping() → health UP/DOWN.
  • OrderService checks isUp() → order becomes PAID or PENDING → the shop.orders.pending gauge rises.
  • PaymentGatewayAdminController flips the switch so you can watch the whole system react.

6. Common mistakes

⚠️ Mistake: "/actuator/metrics gives 404"Only health is exposed over HTTP by default.
Fix: add it to management.endpoints.web.exposure.include.
⚠️ Mistake: "/actuator/info is empty {}"Since Spring Boot 2.6 the env info contributor is off by default, so info.* properties are ignored.
Fix: management.info.env.enabled=true, and add the build-info goal for build data.
🛑 Mistake: exposure.include=* in production without securityAnyone can read /env, download /heapdump (with passwords and tokens inside), or change log levels.
Fix: expose only what you need, use a separate internal management port, and protect the rest with Spring Security.
⚠️ Mistake: high-cardinality tags.tag("userId", userId) creates one time series per user – memory explodes in your app and in Prometheus.
Fix: tags must have a small, fixed set of values (status, method, region). Put ids in logs or traces instead.
⚠️ Mistake: creating a new Timer/Counter object on every call with newMeters must be registered in the MeterRegistry, otherwise nobody sees them.
Fix: always use the builders with .register(registry) (it returns the existing meter if the name+tags already exist), and keep long-lived meters in fields.
⚠️ Mistake: a Gauge on a temporary objectMicrometer keeps only a weak reference to the object you give a Gauge. If that object is garbage-collected, the gauge shows NaN.
Fix: point gauges at long-lived objects such as a Spring bean (we use this, the OrderService singleton).
⚠️ Mistake: slow health checksA health indicator that runs a 5-second query is called by the load balancer every few seconds and makes everything slow.
Fix: keep checks cheap (a ping, SELECT 1), use timeouts, and don't put external systems into liveness.
⚠️ Mistake: Prometheus target is DOWN in DockerInside a container, localhost means the container itself, not your PC.
Fix: use host.docker.internal:8080 as the target (our prometheus.yml does).

7. Best practices

  • Add Actuator to every service from day one. It costs almost nothing.
  • Expose the minimum over HTTP (health, info, prometheus); use a separate management port and/or Spring Security for the rest.
  • show-details=when-authorized in production, so the public only sees UP/DOWN.
  • Enable liveness/readiness probes on Kubernetes; external dependencies go to readiness only.
  • Publish build and git info so you always know what is deployed.
  • Add business metrics (orders, payments, sign-ups), not just technical ones – they catch problems that technical metrics miss.
  • Use a common application tag and consistent, dotted metric names with a domain prefix.
  • Watch the "four golden signals": latency, traffic, errors, saturation (CPU/memory/pool usage).
  • Alert on symptoms (error rate, p95 latency) rather than on every small cause, and avoid alert fatigue.
  • Use percentiles (p95, p99), not only averages.
  • Combine with structured logs (topic 30) and tracing (topic 65) for full observability.

8. Key takeaways

  • Observability = logs + metrics + traces. Actuator gives you production-ready endpoints with one dependency.
  • Only /actuator/health is exposed over HTTP by default; choose more with management.endpoints.web.exposure.include.
  • /env, /heapdump, /configprops are sensitive – never expose them publicly.
  • Health = combination of indicators; one DOWN → overall DOWN → HTTP 503. Custom checks implement HealthIndicator.
  • Liveness → restart; readiness → stop traffic. Enable with management.endpoint.health.probes.enabled=true.
  • /info is built from info.* properties (enable the env contributor), build-info, git, java/os and custom InfoContributors.
  • Micrometer meters: Counter (up only), Gauge (current value), Timer (duration), DistributionSummary (sizes/amounts); tags must be low-cardinality.
  • micrometer-registry-prometheus adds /actuator/prometheus; Prometheus scrapes it, Grafana draws it.
  • /actuator/loggers changes log levels at runtime without a restart.

Medium

A disk-quota health check. Write a ReportsFolderHealthIndicator that is DOWN when the folder reports/ does not exist and shows the number of files as a detail when it does.

Hint / solution
@Component
public class ReportsFolderHealthIndicator implements HealthIndicator {
    private final Path folder = Path.of("reports");

    @Override
    public Health health() {
        if (!Files.isDirectory(folder)) {
            return Health.down().withDetail("folder", folder.toAbsolutePath().toString())
                                .withDetail("error", "folder missing").build();
        }
        try (Stream<Path> files = Files.list(folder)) {
            return Health.up().withDetail("files", files.count()).build();
        } catch (IOException e) {
            return Health.down(e).build();
        }
    }
}

It appears as reportsFolder in /actuator/health. Create the folder and refresh to see it turn UP.

10. Interview questions

Q1. What is Spring Boot Actuator?

A Spring Boot module (spring-boot-starter-actuator) that adds production-ready features: endpoints for health, info, metrics, environment, loggers, beans, mappings, thread dumps and more, over HTTP and JMX. It integrates with Micrometer for metrics and is the basis for monitoring and Kubernetes probes.

Q2. Which endpoints are exposed by default, and how do you expose more safely?

Over HTTP only health. Use management.endpoints.web.exposure.include/exclude. Protect with Spring Security (EndpointRequest matchers), a separate management.server.port reachable only internally, and show-details=when-authorized. Never expose env/heapdump publicly.

Q3. How do you write a custom health check?

Create a bean implementing HealthIndicator (or extend AbstractHealthIndicator) and return Health.up()/down().withDetail(...).build(). The name in /health is the bean name without the "HealthIndicator" suffix. Keep it fast and side-effect free.

Q4. Difference between liveness and readiness probes?

Liveness answers "is the process alive or stuck?" – failure makes Kubernetes restart the container. Readiness answers "can it take traffic now?" – failure removes it from the load balancer without restarting. External dependencies belong in readiness, not liveness. Spring Boot exposes them at /actuator/health/liveness and /readiness.

Q5. What is Micrometer?

A vendor-neutral metrics facade ("SLF4J for metrics"). Code records metrics through MeterRegistry and meters (Counter, Gauge, Timer, DistributionSummary, LongTaskTimer); registries for Prometheus, Datadog, CloudWatch, etc. export them. Spring Boot auto-configures it and adds many built-in metrics.

Q6. Counter vs Gauge vs Timer?

Counter: monotonically increasing count (requests, errors). Gauge: current value that goes up and down, sampled when read (queue size, active sessions). Timer: measures durations and counts of events, providing count, total time, max and optionally percentiles/histograms (request latency).

Q7. What is tag cardinality and why does it matter?

The number of distinct values a tag can take. Each unique tag combination is a separate time series. High-cardinality tags (user id, order id, full URL with ids) create huge numbers of series, exhausting memory in the app and the monitoring backend. Use bounded values; Spring uses URI templates (/api/orders/{id}) for exactly this reason.

Q8. How does Prometheus get metrics from a Spring Boot app?

Add micrometer-registry-prometheus and expose the prometheus endpoint. Prometheus pulls (scrapes) /actuator/prometheus on an interval defined in its scrape_configs, stores the time series, and Grafana queries it with PromQL for dashboards and alerts.

Q9. How can you change a log level in production without restarting?

With the loggers endpoint: POST /actuator/loggers/{logger.name} with {"configuredLevel":"DEBUG"}; send null to reset. The endpoint must be exposed and should be secured.

Q10. How do you show the application version in /actuator/info?

Enable the env contributor (management.info.env.enabled=true) and set info.app.version=@project.version@ (Maven resource filtering), and/or add the build-info goal of spring-boot-maven-plugin which generates build-info.properties. The git-commit-id plugin adds commit information.
