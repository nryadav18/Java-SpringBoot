68. CI/CD with GitHub Actions

Make a robot build and test your Spring Boot app on every push, block broken code from being merged, and publish a Docker image automatically.

1. Why this matters

Imagine a team of 8 developers working on the same Spring Boot project. Every day each of them changes code. Questions appear:

  • "Does the project still compile after Priya's change?"
  • "Did Rahul's change break the shipping price calculation?"
  • "Who builds the jar / Docker image for the release, and on which machine?" (Answer in many old companies: "Bob, on his laptop, on Friday evening." 😱)

CI/CD answers all of these with automation: a server (GitHub Actions, Jenkins, GitLab CI…) runs your build and tests on every single change, in a clean environment, and reports a ✅ or ❌. If tests fail, the change can't be merged. If everything is green, the same pipeline can package and ship the app.

Where you will see it at work: everywhere. Every professional team has a pipeline. In your first week you'll open a pull request and wait for "All checks have passed". Interviewers often ask "How does your CI/CD pipeline look?" — after this lesson you can answer with confidence.

2. Real-life analogy

🏭 A car factory assembly line In an old workshop, each mechanic built a whole car alone and tested it at the end — problems were found late and were expensive to fix. A modern factory uses an assembly line: after every station, an automatic quality check runs. A bad part is caught immediately, at the station that made it.
  • Continuous Integration (CI) = every new part (your commit) is fitted into the car and checked right away (build + tests).
  • Continuous Delivery = every car that passes all checks is driven to the parking lot, ready to be sold. A manager decides when it goes to the showroom (a human clicks "deploy").
  • Continuous Deployment = the car goes straight to the showroom automatically, no human click.
GitHub Actions is the conveyor belt and the robots; ci.yml is the list of stations.

3. Concepts step by step

3.1 CI vs CD vs CD

TermWhat happens automaticallyHuman step?
Continuous IntegrationEvery push/PR: compile, run tests, maybe code analysis. Developers merge small changes often (daily).Someone reviews & merges the PR.
Continuous DeliveryCI + package the app (jar / Docker image) so it is always releasable, often deployed to a test/staging environment.A person clicks "Approve / Deploy to production".
Continuous DeploymentEverything, including production deployment, on every green change to main.None — needs very good tests and monitoring.
git push→ Build→ Test→ Package (jar / image)→ Deploy staging→ Deploy production

"CI" covers the first three boxes. Continuous Delivery adds packaging + staging and stops before production for approval. Continuous Deployment runs all the way.

3.2 Git refresher (just enough)

Git is a version-control system: it remembers every saved version ("commit") of your project. GitHub is a website that hosts Git repositories and adds pull requests, issues and Actions. You need Git installed (git --version; download from git-scm.com if missing).

CommandMeaning
git initStart tracking this folder as a repository (creates a hidden .git folder).
git statusWhat changed? What is staged?
git add .Stage all changes ("put them in the box").
git commit -m "message"Save a snapshot with a description ("seal the box").
git branch -M mainRename the current branch to main.
git switch -c feature/express-feeCreate and move to a new branch — a parallel line of work.
git remote add origin <url>Connect to the repository on GitHub.
git push -u origin mainUpload your commits to GitHub.
git pullDownload others' commits.

A pull request (PR) is a request on GitHub: "please merge my branch into main". Teammates review the code, and — this is where CI comes in — GitHub runs the workflow and shows the result on the PR.

branch→ commits→ push→ open PR→ CI runs ✅/❌→ review→ merge to main

3.3 GitHub Actions vocabulary

WordMeaningIn our file

3.4 Anatomy of a workflow file

name: CI                       # shown in the Actions tab

on:                            # WHEN
  push:
    branches: [ main ]

jobs:                          # WHAT
  build:                       # job id (your choice)
    runs-on: ubuntu-latest     # WHERE
    steps:                     # HOW, in order
      - uses: actions/checkout@v4          # a reusable action
      - run: echo "Hello from the runner"  # a shell command

That's a complete, valid workflow. Everything else is detail.

3.6 Setting up Java with actions/setup-java

A fresh runner has some Java, but you want exactly the version your project uses. actions/setup-java@v4 installs it and (with cache: maven) saves ~/.m2/repository between runs — so Maven doesn't download 100 MB of dependencies every time. The cache key is the hash of your pom.xml; change the pom and the cache refreshes.

- uses: actions/setup-java@v4
  with:
    distribution: temurin   # same JDK vendor you installed locally
    java-version: '17'      # quoted: YAML would otherwise read numbers like 17.0 strangely
    cache: maven

3.7 Why mvn -B verify?

Remember the Maven lifecycle from topic 20: validate → compile → test → package → verify → install → deploy. Running verify runs everything up to it: compile, unit tests, build the jar, plus checks bound to verify (our JaCoCo report, integration tests with Failsafe, quality gates). If any test fails, Maven exits with a non-zero code → the step fails → the job is red ❌.

-B = batch mode: no interactive prompts, no colourful progress bars that fill logs with garbage.

💡 The golden rule CI should run the same command you run locally. If mvn -B verify passes on your laptop, it should pass on the runner. Avoid magic that only exists in the pipeline.

3.8 Secrets

To push to Docker Hub the pipeline needs credentials. Never write them in the YAML (it's in Git, everyone can read it). Instead:

  1. On Docker Hub: Account settings → Personal access tokens → Generate (Read & Write). A token can be revoked without changing your password.
  2. On GitHub: repo Settings → Secrets and variables → Actions → New repository secret: DOCKERHUB_USERNAME and DOCKERHUB_TOKEN.
  3. In the workflow: ${{ secrets.DOCKERHUB_TOKEN }}. GitHub replaces it at runtime and prints *** if it appears in logs.
ℹ️ GITHUB_TOKEN and permissions Every run also gets an automatic token called GITHUB_TOKEN to talk to GitHub itself (e.g. to push to GitHub's own registry ghcr.io). The permissions: block limits what it may do. We set contents: read — the principle of least privilege.
⚠️ PRs from forks don't get secrets For safety, workflows triggered by pull requests from forked repositories cannot read your secrets. That's why our docker job runs only on push to main.

3.9 Building and pushing a Docker image

The official Docker actions make this easy:

ActionJob
docker/setup-buildx-action@v3Enables BuildKit/Buildx (faster builds, caching).
docker/login-action@v3Logs in to Docker Hub (or ghcr.io, AWS ECR…) with secrets.
docker/build-push-action@v6docker build + docker push with tags and cache.

We tag every image twice: latest (convenient) and ${{ github.sha }} — the full commit id. With the commit tag you can always answer "which code is running in production?" and roll back to an exact version.

Our Dockerfile in this topic is single-stage: it copies target/app.jar that the build job already compiled and tested. That's the "build once, deploy many" principle: the exact bytes that passed tests are the ones you ship. (The multi-stage Dockerfile from topic 66/67 is also fine in CI; then the image builds its own jar.)

3.10 Passing files between jobs: artifacts

Each job runs on a different, fresh machine. Files from build do not magically appear in docker. We use actions/upload-artifact@v4 in the first job and actions/download-artifact@v4 in the second. Artifacts also appear on the run's summary page for download — handy for test reports.

3.11 Branch protection: making CI mandatory

A red ❌ is just a picture unless it blocks merging. On GitHub: Settings → Branches → Add branch ruleset (or "branch protection rule") for main:

  • ☑ Require a pull request before merging (no direct pushes to main), optionally with 1+ approvals.
  • ☑ Require status checks to pass → choose "Build & test". Now a PR with failing tests cannot be merged.
  • ☑ Require branches to be up to date; ☑ block force pushes.

3.12 Environments and approvals (Continuous Delivery)

In Settings → Environments create production and add Required reviewers. Our deploy job says environment: production, so the run pauses and waits until a reviewer clicks "Approve and deploy". Remove the reviewers and it becomes Continuous Deployment. Environments can also hold their own secrets (e.g. production DB password).

4.1 The application under test

src/main/java/com/course/cicd/shipping/ShippingService.javastatic final BigDecimal BASE_FEE = new BigDecimal("5.00");
static final BigDecimal PRICE_PER_KG = new BigDecimal("2.00");
static final BigDecimal EXPRESS_MULTIPLIER = new BigDecimal("1.5");
static final double MAX_WEIGHT_KG = 30.0;

public ShippingQuote quote(double weightKg, boolean express) {
    if (weightKg <= 0 || weightKg > MAX_WEIGHT_KG) {
        throw new IllegalArgumentException("Weight must be greater than 0 and at most ...");
    }
    BigDecimal cost = BASE_FEE.add(PRICE_PER_KG.multiply(BigDecimal.valueOf(weightKg)));
    if (express) {
        cost = cost.multiply(EXPRESS_MULTIPLIER);
    }
    return new ShippingQuote(weightKg, express, cost.setScale(2, RoundingMode.HALF_UP));
}

Small on purpose. What matters: it's a business rule that someone could break by accident, and tests guard it.

4.3 ci.yml — the build job

.github/workflows/ci.yml (part 1)name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    name: Build & test
    runs-on: ubuntu-latest
    steps:
      - name: Check out code
        uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'
          cache: maven

      - name: Build and test with Maven
        run: mvn -B verify

      - name: Upload test reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-reports
          path: |
            target/surefire-reports/
            target/site/jacoco/
          retention-days: 7

      - name: Upload jar
        uses: actions/upload-artifact@v4
        with:
          name: app-jar
          path: target/app.jar
  • on: — three triggers: pushes to main, PRs targeting main, and a manual button.
  • concurrency — if you push twice in a minute, the first (now outdated) run is cancelled. Saves minutes.
  • actions/checkout@v4 — the runner starts EMPTY; this step downloads your repo. Forgetting it is a classic error ("no POM in this directory").
  • @v4 — the action's version. Always pin a version (big companies even pin the full commit SHA).
  • if: always() — normally later steps are skipped after a failure. For reports we want them especially after a failure.
  • path: | — the | means "multi-line text follows" in YAML.

4.4 ci.yml — the docker job

.github/workflows/ci.yml (part 2)  docker:
    name: Build & push Docker image
    needs: build
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with:
          name: app-jar
          path: target
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/shipping-app:latest
            ${{ secrets.DOCKERHUB_USERNAME }}/shipping-app:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
  • needs: build — wait for build and run only if it was green.
  • if: — skip for pull requests; only real pushes to main publish images.
  • download-artifact puts app.jar back into target/, where the Dockerfile expects it.
  • context: . — build from the checked-out folder (including the downloaded jar).
  • cache-from/to: type=gha — store Docker layer cache in GitHub's cache for faster rebuilds.

6. Common mistakes

⚠️ Mistake: the workflow never runs The file is not at <repo-root>/.github/workflows/, has the wrong extension, or the branch in on.push.branches is master while yours is main.
Fix: check the path and branch names exactly.
⚠️ Mistake: forgetting actions/checkout Maven says "The goal you specified requires a project to execute but there is no POM in this directory".
Fix: first step of every job that needs the code: uses: actions/checkout@v4.
⚠️ Mistake: YAML indentation "Invalid workflow file … unexpected value 'steps'".
Fix: spaces only; steps must be inside the job; the GitHub Actions VS Code extension highlights these errors.
🚫 Mistake: secrets in the YAML or in logs Writing password: myRealPassword or run: echo $TOKEN with a token built in a way GitHub can't mask.
Fix: always ${{ secrets.X }}; use access tokens, not passwords; rotate a leaked token immediately.
⚠️ Mistake: "works on my machine" differences Tests depend on your timezone, file paths with \, a local MySQL, or test order.
Fix: make tests self-contained (H2 / Testcontainers, fixed clocks, Path.of), run mvn -B verify from a clean clone.
⚠️ Mistake: skipping tests to "make CI green" mvn -DskipTests or @Disabled everywhere.
Fix: a red build is information — fix the cause. A pipeline without tests only proves that the code compiles.
⚠️ Mistake: Docker job fails with "denied: requested access to the resource is denied" The image name's first part doesn't match your Docker Hub user, or the token is read-only.
Fix: tag as <your-user>/shipping-app, create a Read & Write token.
⚠️ Mistake: only using latest You can't tell which code is running or roll back.
Fix: tag with the commit SHA (or a version like 1.4.2) as well.

7. Best practices

  • Keep the pipeline fast (aim < 10 minutes): Maven cache, fast unit tests, run slow tests separately or nightly.
  • Fail fast: compile and unit tests first; expensive steps (Docker, deploy) later and only on main.
  • Same command locally and in CI (mvn -B verify). Consider the Maven Wrapper (./mvnw) so everyone uses the same Maven version.
  • Protect main: PRs only, required status checks, at least one review.
  • Small PRs, merged often — the real meaning of "continuous integration".
  • Build once, deploy many: the same tested artifact/image goes to staging and then production; only configuration differs.
  • Immutable, traceable tags: commit SHA or semantic version.
  • Least privilege: permissions: block, scoped tokens, environment-specific secrets, pin action versions.
  • Automate updates and scanning: Dependabot, CodeQL, image scanning (e.g. Trivy), SonarCloud quality gate.
  • Make failures easy to read: upload test reports, name steps clearly.
  • Deployment needs a safety net: health checks, readiness probes and easy rollback (topic 69).

8. Key takeaways

  • CI = build + test every change automatically; Continuous Delivery = always releasable, human approves production; Continuous Deployment = fully automatic.
  • A GitHub Actions workflow (YAML in .github/workflows/) is triggered by events and contains jobs of steps running on runners.
  • actions/checkout + actions/setup-java (with cache: maven) + mvn -B verify is the standard Java CI recipe.
  • Jobs run on separate machines: use needs: for order and artifacts to share files.
  • Secrets live in repository settings and are read with ${{ secrets.NAME }}.
  • docker/login-action + docker/build-push-action publish images; tag with the commit SHA.
  • Branch protection with required checks is what actually stops broken code.
  • Add quality tools: JaCoCo, Dependabot, SonarQube/SonarCloud, CodeQL.

2. Add a test and see CI catch a bug. Add a rule "orders of exactly 0.1 kg cost 5.20" as a test, push on a branch and open a PR. Then introduce a bug and watch the PR turn red.

Hint / solution
@Test
void tinyParcel() {
    assertThat(service.quote(0.1, false).cost()).isEqualByComparingTo("5.20");
}

Because we use BigDecimal.valueOf(0.1), the result is exactly 5.20. With plain double math you could get 5.2000000000000002 — a nice reminder why money uses BigDecimal.

Medium

3. Matrix build. Run the build job on Java 17 and Java 21 to check your app works on the next LTS.

Hint / solution
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        java: [ '17', '21' ]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ matrix.java }}
          cache: maven
      - run: mvn -B verify

GitHub starts two jobs in parallel: "build (17)" and "build (21)". Note: the artifact names must then be unique, e.g. name: test-reports-${{ matrix.java }}.

Medium

4. Enforce coverage. Make mvn verify fail if line coverage drops below 80%.

Hint / solution

Add a third execution to the JaCoCo plugin:

<execution>
    <id>check</id>
    <phase>verify</phase>
    <goals><goal>check</goal></goals>
    <configuration>
        <rules>
            <rule>
                <element>BUNDLE</element>
                <limits>
                    <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.80</minimum>
                    </limit>
                </limits>
            </rule>
        </rules>
    </configuration>
</execution>

Now CI fails automatically when someone adds code without tests.

    permissions:
      contents: read
      packages: write          # allow pushing to ghcr.io
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { name: app-jar, path: target }
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository_owner }}/shipping-app:${{ github.sha }}

Note: ghcr.io image names must be lowercase.

10. Interview questions

Q1. What is the difference between Continuous Integration, Continuous Delivery and Continuous Deployment?

CI: every change is merged frequently and automatically built and tested. Continuous Delivery: in addition, every green build is packaged and kept deployable (often auto-deployed to staging); production release is a manual decision. Continuous Deployment: every green change goes to production automatically, with no manual gate.

Q2. Explain workflow, job, step, runner and action in GitHub Actions.

A workflow is a YAML file in .github/workflows triggered by events. It contains jobs; each job runs on a runner (a VM/container) and consists of ordered steps. A step either runs a shell command (run) or uses an action (uses), a reusable published component like actions/setup-java. Jobs run in parallel unless linked with needs.

Q3. How do you speed up a Maven build in CI?

Cache the local repository (setup-java with cache: maven), use -B and maybe -T 1C for parallel modules, keep unit tests fast, split slow integration tests into another job or schedule, use concurrency to cancel outdated runs, and cache Docker layers (type=gha).

Q4. How do you handle secrets in a pipeline?

Store them in the CI system's encrypted secrets (repository/environment secrets), reference them as ${{ secrets.NAME }}, never in code or logs. Use scoped, revocable tokens, least-privilege permissions, environment-specific secrets with approvals, and ideally short-lived credentials via OIDC to clouds instead of long-lived keys.

Q5. Why tag Docker images with the commit SHA instead of only latest?

latest is mutable and ambiguous. A SHA (or semantic version) tag is immutable and traceable: you know exactly which code runs, can reproduce it, and can roll back to a known image.

Q6. What does "build once, deploy many" mean?

Build and test the artifact (jar/image) once, then promote that same artifact through environments (test → staging → prod), changing only configuration. Rebuilding per environment risks shipping something different from what was tested.

Q7. How do you prevent broken code from reaching the main branch?

Branch protection/rulesets: require pull requests, required status checks (CI must pass), required reviews, up-to-date branches, no force pushes. Combine with good automated tests and quality gates (coverage, static analysis).

Q8. Why use mvn verify rather than mvn package or mvn install in CI?

verify runs everything up to and including verification checks (integration tests via Failsafe, coverage checks, quality plugins) after packaging. package stops earlier and skips those checks; install additionally copies the artifact to the runner's local repo, which is pointless on a throw-away runner.

Q9. What tools improve code quality and security in a pipeline?

JaCoCo (coverage), SonarQube/SonarCloud (static analysis & quality gate), Checkstyle/Spotless (style), Dependabot/Renovate (dependency updates), OWASP Dependency-Check or Snyk (vulnerable libraries), CodeQL (code security scanning), Trivy (container image scanning).

Q10. Name other CI/CD tools besides GitHub Actions.

Jenkins (Jenkinsfile, self-hosted), GitLab CI/CD, Azure DevOps Pipelines, CircleCI, Bitbucket Pipelines, TeamCity; for Kubernetes GitOps deployments Argo CD or Flux.
