1. Why this matters

In the last topic, RabbitMQ delivered a message to a consumer and then deleted it. That's perfect for tasks ("send this email"). But many companies want something more: a permanent, replayable record of everything that happened — every click, every payment, every order status change — that many systems can read, each at its own speed, even days later.

That is event streaming, and Apache Kafka (created at LinkedIn, open-sourced in 2011) is the industry standard for it. Kafka handles millions of events per second and keeps them for as long as you configure (days, weeks, forever).

Where you'll see it at work:

  • Microservices publishing domain events ("OrderPaid") that other services react to.
  • Activity tracking and analytics pipelines (clicks, views, searches).
  • Log and metrics aggregation from hundreds of servers.
  • Data integration: syncing databases, search indexes and data warehouses (Kafka Connect, change data capture).
  • Real-time processing: fraud detection, live dashboards (Kafka Streams, Flink).

Banks, ride-hailing apps, e-commerce sites and streaming services all run Kafka. Knowing its basic concepts is expected of a modern backend developer.

2. Real-life analogy

📰 A newspaper archive vs. a mailbox

RabbitMQ is a mailbox: the letter is delivered to one person and, once read, it's gone.

Kafka is a newspaper printing house with an archive. Every day new pages are printed and added to the end of the archive (an append-only log). Pages are numbered in order (the offset). The archive is split into several shelves so many people can read in parallel (partitions). Each newspaper title — "Sports", "Business" — is a topic.

Readers don't take pages away. Each reader just keeps a bookmark saying "I've read up to page 42" (the committed offset). The sports app and the analytics team read the same pages independently, each with their own bookmark (different consumer groups). A new reader can even start from page 1 and read the whole history (replay). Old pages are thrown away after, say, 7 days (retention).

3.2 Topics, partitions and offsets

Key facts to remember:

  • Records are appended to the end of a partition and are immutable (you can't edit or delete one record).
  • Offsets are per partition: partition 0 and partition 1 both have an offset 0.
  • Order is guaranteed only inside one partition.
  • Reading does not delete. Records disappear only when retention expires.

3.3 Keys and ordering

The producer chooses the partition from the record's key: the same key always goes to the same partition (as long as the partition count doesn't change). So:

key = order-7
CREATED→ key = order-7
PAID→ key = order-7
SHIPPED⇒ all in partition 1, in this order ✔

If we used no key, the three events could land in different partitions, and a consumer might see "SHIPPED" before "PAID". Rule: choose as key the thing whose events must stay in order — usually the entity id (orderId, customerId, accountId).

⚠️ Hot partitionsIf one key is extremely common (e.g. key = country and 90% of orders are from India), one partition gets most of the traffic while the others are idle. Pick keys with many different values.

3.4 Consumer groups – sharing work and broadcasting

Consumers belong to a consumer group. Kafka's two rules:

  1. Inside one group, each partition is read by exactly one consumer. The group's consumers share the partitions → parallel work.
  2. Different groups are independent. Each group gets every record and keeps its own offsets → broadcast.
  • Partitions = the maximum parallelism of one group. 3 partitions + 5 consumers in one group → 2 consumers sit idle.
  • When a consumer joins or leaves, Kafka redistributes partitions — a rebalance.
  • A brand-new group with no saved offsets starts where auto-offset-reset says: earliest (from the beginning) or latest (only new records).

3.5 Brokers, replication and retention

In production a cluster has at least 3 brokers. Each partition has a leader (on one broker) and followers (copies on other brokers). With replication-factor=3, two brokers can fail and no data is lost. Producers with acks=all wait until the in-sync replicas have the record.

Kafka keeps records according to retention: retention.ms (time, default 7 days) or retention.bytes (size). A special mode, log compaction, keeps only the latest record per key — handy for "current state" topics.

Locally we run one broker in KRaft mode. Older tutorials also start a ZooKeeper container; that's no longer needed (and Kafka 4.0 removed ZooKeeper support completely).

💡 Rule of thumb"Do this job" → RabbitMQ. "This happened, anyone may care, now or later" → Kafka. Many companies use both.

3.7 Serialization – bytes on the wire

Kafka itself only stores bytes. Producers need a serializer (object → bytes) for the key and value; consumers need the matching deserializer (bytes → object). We use:

PartProducerConsumer
Key (orderId text)StringSerializerStringDeserializer
Value (OrderEvent)JsonSerializer (Spring Kafka, uses Jackson)ErrorHandlingDeserializer wrapping JsonDeserializer

JsonSerializer also adds a __TypeId__ header with the Java class name; JsonDeserializer uses it, but only for classes in trusted packages. Large companies often use Avro or Protobuf with a Schema Registry instead of JSON — mention-level knowledge is enough for now.

3.8 Error handling: retries and the dead-letter topic

Kafka can't "reject" a single record like RabbitMQ. A consumer reads records in order, so if record 5 keeps failing, it would block records 6, 7, 8... forever. Spring Kafka's DefaultErrorHandler solves this:

record fails→ retry (1 s) × 2→ still failing→ DeadLetterPublishingRecoverer
writes to orders.DLT→ commit offset, continue with next record
  • Retryable errors (network glitch, service temporarily down) are retried with a back-off.
  • Not retryable errors (invalid data) should go straight to the DLT: handler.addNotRetryableExceptions(IllegalArgumentException.class).
  • Poison pills — records that can't even be deserialized (not JSON) — are caught by ErrorHandlingDeserializer and also sent to the DLT instead of crashing the consumer in a loop.
  • The DLT record gets headers such as kafka_dlt-exception-message and kafka_dlt-original-offset.
ℹ️ Non-blocking retriesThe retries above block the partition for a few seconds. For long back-offs, Spring Kafka offers @RetryableTopic, which moves failed records to retry topics (orders-retry-0, ...) so the main topic keeps flowing. Good to know for later.

3.9 Delivery guarantees in simple words

  • Producer: acks=all + enable.idempotence=true = the broker has safely stored it and retries don't create duplicates.
  • Consumer: Spring commits offsets after your listener returns. If the app crashes in between, the record is processed again → at-least-once. Make consumers idempotent (e.g. remember eventIds).
  • Exactly-once is possible with Kafka transactions but is an advanced topic.

4.3 Creating topics with NewTopic beans

config/KafkaTopicConfig.java@Bean
public NewTopic ordersTopic(@Value("${app.kafka.topic}") String topic,
                            @Value("${app.kafka.partitions}") int partitions) {
    return TopicBuilder.name(topic)
            .partitions(partitions)                 // 3
            .replicas(1)                            // 1 broker locally (3 in production)
            .config(TopicConfig.RETENTION_MS_CONFIG, String.valueOf(7L * 24 * 60 * 60 * 1000))
            .build();
}

@Bean
public NewTopic ordersDeadLetterTopic(...) {
    return TopicBuilder.name(topic + ".DLT").partitions(partitions).replicas(1).build();
}

Spring Boot's KafkaAdmin creates these topics at startup if they don't exist. It can increase partitions but never decrease them.

4.4 The producer

order/OrderEventProducer.javapublic CompletableFuture<SendResult<String, OrderEvent>> publish(OrderEvent event) {
    return kafkaTemplate.send(topic, event.orderId(), event)     // topic, KEY, value
            .whenComplete((result, ex) -> {
                if (ex == null) {
                    var meta = result.getRecordMetadata();
                    log.info("SENT {} for order {} -> topic={} partition={} offset={}",
                            event.status(), event.orderId(), meta.topic(), meta.partition(), meta.offset());
                } else {
                    log.error("FAILED to send ...", ex);
                }
            });
}

send() is asynchronous: it returns a CompletableFuture right away (remember Topic 17). The callback tells us which partition and offset the record got. Using orderId as the key keeps each order's events in order.

4.5 The consumers

consumer/NotificationConsumer.java@KafkaListener(topics = "${app.kafka.topic}", groupId = "notification-service", concurrency = "3")
public void onOrderEvent(ConsumerRecord<String, OrderEvent> record) {
    OrderEvent event = record.value();
    log.info("NOTIFY  partition={} offset={} key={} status={} customer={}",
            record.partition(), record.offset(), record.key(), event.status(), event.customerName());

    if (event.amount() != null && event.amount().signum() < 0) {
        throw new IllegalArgumentException("Negative amount ...");   // not retryable -> DLT now
    }
    if ("fail".equalsIgnoreCase(event.customerName())) {
        throw new IllegalStateException("SMS gateway unavailable");  // retried, then DLT
    }
    String text = switch (event.status()) {
        case CREATED -> "Thanks " + event.customerName() + ", we received your order!";
        case PAID -> "Payment received for order " + event.orderId();
        case SHIPPED -> "Good news! Your order is on the way.";
        case CANCELLED -> "Your order was cancelled.";
    };
    log.info("NOTIFY  message to {}: {}", event.customerName(), text);
}
consumer/AnalyticsConsumer.java (listener part)@KafkaListener(topics = "${app.kafka.topic}", groupId = "analytics-service")
public void onOrderEvent(@Payload OrderEvent event,
                         @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                         @Header(KafkaHeaders.OFFSET) long offset) {
    long count = countsByStatus.computeIfAbsent(event.status().name(), k -> new AtomicLong()).incrementAndGet();
    log.info("ANALYTICS partition={} offset={} {} events so far: {}", partition, offset, event.status(), count);
}

Two ways to get metadata: take the whole ConsumerRecord, or take the value with @Payload and single headers with @Header. Because the groups differ, both consumers receive every event.

4.6 Error handling configuration

config/KafkaErrorHandlingConfig.java@Bean
public DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<String, Object> jsonTemplate,
                                             ProducerFactory<String, Object> producerFactory) {
    // poison pills only exist as raw bytes -> need a byte[] template
    KafkaTemplate<String, byte[]> bytesTemplate = new KafkaTemplate<>(new DefaultKafkaProducerFactory<>(
            producerFactory.getConfigurationProperties(), new StringSerializer(), new ByteArraySerializer()));

    Map<Class<?>, KafkaOperations<?, ?>> templates = new LinkedHashMap<>();
    templates.put(byte[].class, bytesTemplate);
    templates.put(Object.class, jsonTemplate);

    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(templates);
    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2L));
    handler.addNotRetryableExceptions(IllegalArgumentException.class);
    return handler;
}

Spring Boot automatically attaches a single CommonErrorHandler bean to all @KafkaListeners. FixedBackOff(1000L, 2L) = wait 1 second, retry at most 2 times (3 attempts in total). The DLT consumer overrides its value deserializer with properties = "value.deserializer=...StringDeserializer" so it can print anything, even broken records.

6. Common mistakes

⚠️ Mistake: "Connection to node -1 (localhost:9092) could not be established" Kafka isn't running or isn't ready yet; the app keeps logging warnings.
Fix: docker compose up -d, wait ~15 s, check docker compose logs kafka.
⚠️ Mistake: wrong advertised listener The first connection works but then the client tries to reach a hostname like kafka:9092 or a container id and fails.
Fix: KAFKA_ADVERTISED_LISTENERS must be an address your app can reach — localhost:9092 for an app on your PC; the service name (e.g. kafka:9092) for apps inside the same Docker network.
🚫 Mistake: no key when order matters Events of one order land on different partitions and are processed out of order (SHIPPED before PAID).
Fix: send with a key: kafkaTemplate.send(topic, orderId, event).
⚠️ Mistake: "The class '...' is not in the trusted packages" The JsonDeserializer refuses to create classes from unknown packages.
Fix: set spring.json.trusted.packages to your event package (avoid "*" in production).
🚫 Mistake: endless loop on a poison pill Without ErrorHandlingDeserializer, a non-JSON record throws during deserialization, before your code runs; the consumer fails, seeks back, and fails again forever.
Fix: wrap the deserializer with ErrorHandlingDeserializer and configure a DLT recoverer.
⚠️ Mistake: more consumers than partitions You set concurrency = "10" on a 3-partition topic and wonder why 7 threads do nothing.
Fix: plan partition counts for the parallelism you need (you can increase partitions later, but that changes which partition a key maps to).
⚠️ Mistake: expecting old records with auto-offset-reset=latest A new consumer group with latest starts at the end and doesn't see existing records.
Fix: use earliest when a new group should read the history. (It only matters when the group has no committed offset yet.)
⚠️ Mistake: same groupId for different services If notification and analytics used the same groupId, they would split the records — each event processed by only one of them.
Fix: one group per logical service (usually the spring.application.name).

7. Best practices

  • Name topics clearly: orders, payments.completed, or <domain>.<event>; DLTs as <topic>.DLT.
  • Choose keys deliberately (ordering + even distribution).
  • Treat events as contracts: include an eventId, a timestamp and a type; evolve schemas backwards-compatibly (consider Avro/Protobuf + Schema Registry for many teams).
  • Producer safety: acks=all, enable.idempotence=true (defaults in modern Kafka clients, but be explicit).
  • Idempotent consumers: duplicates are possible (at-least-once).
  • Always configure error handling: ErrorHandlingDeserializer, DefaultErrorHandler, a DLT, and non-retryable exceptions for bad data. Monitor the DLT.
  • Watch consumer lag (how far behind a group is) — it's the #1 Kafka health metric.
  • Production cluster: 3+ brokers, replication-factor=3, min.insync.replicas=2, security (TLS + SASL), or a managed service (Confluent Cloud, Amazon MSK, Aiven).
  • Transactional outbox when "save to DB" and "publish event" must both happen or both not happen.
  • Test with @EmbeddedKafka (spring-kafka-test) or Testcontainers.

8. Key takeaways

  • Kafka is a distributed, append-only log: records are kept until retention ends, not deleted when read.
  • A topic is split into partitions; each record has an offset in its partition.
  • Order is guaranteed only within a partition; the key decides the partition → same key, same order.
  • In a consumer group, each partition is read by one consumer (work sharing); different groups each get all records (broadcast).
  • Groups save committed offsets, so they can stop, resume and even replay.
  • Spring Kafka: KafkaTemplate.send(topic, key, value), @KafkaListener(topics, groupId), NewTopic beans, JSON (de)serializers.
  • DefaultErrorHandler + DeadLetterPublishingRecoverer = retries then <topic>.DLT.
  • RabbitMQ for tasks and smart routing; Kafka for event streams, history and high throughput.
  • Locally: one apache/kafka container in KRaft mode — no ZooKeeper.

    @KafkaListener(topics = "payments", groupId = "payment-service")
    public void onPayment(OrderEvent event) {
        if ("fail".equals(event.customerName())) {
            throw new IllegalStateException("bank timeout");
        }
        log.info("Payment processed for {}", event.orderId());
    }

    @DltHandler
    public void onDlt(OrderEvent event) {
        log.error("Payment permanently failed: {}", event.orderId());
    }
}

10. Interview questions

Q1. What are a topic, a partition and an offset?

A topic is a named stream of records. It is split into partitions, each an ordered, immutable, append-only log stored on brokers. An offset is the sequential position of a record within a partition; consumers use offsets to track progress.

Q2. How does Kafka guarantee ordering?

Only within a single partition. Records with the same key are sent to the same partition (default partitioner: hash of the key modulo partition count), so all events for one key are read in the order they were written. There is no global ordering across partitions. With idempotent producers, ordering is preserved even with retries.

Q3. What is a consumer group and how are partitions assigned?

A consumer group is a set of consumers with the same group.id that cooperatively consume a topic. Each partition is assigned to exactly one consumer in the group, so the number of partitions limits parallelism. Different groups consume independently and each receive all records. When membership changes, a rebalance reassigns partitions.

Q4. What are committed offsets and auto.offset.reset?

A committed offset is the position a consumer group has stored (in the internal __consumer_offsets topic) as processed. On restart, consumption resumes from it. auto.offset.reset applies only when there is no valid committed offset: earliest starts at the beginning, latest at the end. Spring Kafka commits after the listener returns (AckMode BATCH by default).

Q5. Kafka vs RabbitMQ — when would you use each?

RabbitMQ: a broker with queues and flexible routing (exchanges); messages are removed after acknowledgement; ideal for task distribution, request/reply and complex routing. Kafka: a distributed log with retention, replay, very high throughput and partition-based scaling; ideal for event streaming, event sourcing, analytics and data pipelines.

Q6. How do you handle failures in a Spring Kafka consumer?

Configure a DefaultErrorHandler with a BackOff for retries and a DeadLetterPublishingRecoverer to publish failed records to a dead-letter topic (<topic>.DLT). Mark exceptions that can't succeed on retry as not retryable. Use ErrorHandlingDeserializer for poison pills. For long delays without blocking the partition, use @RetryableTopic.

Q7. What delivery semantics does Kafka offer?

At-most-once (commit before processing), at-least-once (commit after processing — the usual default, may produce duplicates), and exactly-once within Kafka using idempotent producers plus transactions (read-process-write). In practice, at-least-once with idempotent consumers is most common.

Q8. What do acks=all and enable.idempotence do?

acks=all makes the producer wait until all in-sync replicas have the record, so it isn't lost if the leader crashes. enable.idempotence=true gives each producer a sequence number per partition so broker-side duplicates from retries are discarded, and ordering is kept.

Q9. What is KRaft and why does it matter?

KRaft (Kafka Raft) is Kafka's built-in consensus protocol for managing cluster metadata, replacing ZooKeeper. It simplifies deployment (one system instead of two), scales to more partitions and speeds up failover. ZooKeeper mode was removed in Kafka 4.0.

Q10. How many partitions should a topic have?

Enough for the peak consumer parallelism you need (partitions ≥ consumers in the largest group) and for throughput, but not excessively many (each partition costs broker resources). Increasing partitions later is possible but changes key-to-partition mapping, which can break per-key ordering for existing keys — so plan ahead.
