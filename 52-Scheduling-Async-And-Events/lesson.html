52. Scheduling, Async & Events

Run jobs on a timer, move slow work to background threads, and let parts of your app react to "something happened" without knowing each other.

1. Why this matters

So far, our code only ran when a request arrived: a user clicks, the controller runs, a response goes back. Real applications also need work that does not fit this "ask and wait" shape:

  • Work on a timer – "Every night at 2 AM, create the sales report." "Every 5 minutes, cancel unpaid orders older than 30 minutes." "Every Monday, email the newsletter." This is scheduling.
  • Slow work the user should not wait for – sending a welcome email takes 3 seconds because the mail server is slow. The user only wants to see "Registered!". Let another thread send the email. This is async (asynchronous) processing.
  • Many reactions to one thing – when a user registers, we want to send an email, write an audit log, give a coupon and update statistics. If UserService called all of them directly, it would depend on four other services and grow every time marketing has a new idea. Instead, it announces "a user registered", and whoever cares reacts. These are events.

All three are built into Spring – no extra libraries needed – and you will meet them in almost every enterprise codebase: cleanup jobs, report generation, notification sending, cache warming, retrying failed payments, and modules that talk through events.

2. Real-life analogy

🍽️ A restaurant
  • Scheduling = the wall clock and the duty roster. "Clean the kitchen every night at 11 PM." "Check the fridge temperature every 30 minutes." Nobody asks for it; the clock triggers it.
  • Async = the waiter and the kitchen. A waiter takes your order, hands the ticket to the kitchen, and immediately goes to the next table. He does not stand in the kitchen for 20 minutes waiting for your pasta. The kitchen (another "thread") cooks in the background. The kitchen staff is the thread pool – a fixed team of cooks; when all are busy, new tickets wait on the rail (the queue).
  • Events = the announcement bell. When a guest arrives, the host rings a bell: "New guest at table 5!" The waiter brings water, the busboy sets cutlery, the manager updates the guest count. The host does not tell each person what to do and does not even know who reacts. That is publish → listen.
  • Transactional events = "only after the bill is paid". The "thank you" SMS is sent only after the payment succeeded – never if the card was declined. That is AFTER_COMMIT.

3.2 Scheduling – step 1: @EnableScheduling

@Configuration
@EnableScheduling      // without it, @Scheduled methods are silently ignored
public class SchedulingConfig { }

Spring Boot then auto-configures a ThreadPoolTaskScheduler – the "clock" that calls your methods.

3.3 Step 2: @Scheduled methods

Put @Scheduled on a method of any Spring bean. Rules: the method returns void, has no parameters, and nobody calls it – the scheduler does.

@Component
public class ShopJobs {

    @Scheduled(fixedRate = 20000)                    // every 20 s, counted from each START
    public void heartbeat() { ... }

    @Scheduled(fixedDelay = 30000, initialDelay = 5000) // 30 s after each run FINISHES; first run 5 s after startup
    public void retryFailedEmails() { ... }

    @Scheduled(cron = "0 0 2 * * *")                 // every day at 02:00:00
    public void dailyReport() { ... }
}
AttributeMeaningGood for
fixedRateStart a new run every N ms, measured from the start of the previous run.Steady "tick": heartbeats, polling, metrics.
fixedDelayWait N ms after the previous run finished, then start again.Jobs whose duration varies; guarantees a rest between runs.
initialDelayWait N ms after startup before the first run.Let the app warm up first.
cronCalendar rule: "at 02:00 every day".Business times: nightly, weekly, month-end.
timeUnitUnit for the numbers (default MILLISECONDS).@Scheduled(fixedRate = 5, timeUnit = TimeUnit.MINUTES)
zoneTime zone for the cron expression.zone = "Asia/Kolkata"

3.5 The scheduler's thread pool

By default Spring Boot's scheduler has one single thread. If one job takes 10 minutes, every other job waits! Give it more threads:

spring.task.scheduling.pool.size=2
spring.task.scheduling.thread-name-prefix=sched-

3.6 Scheduling with several app instances

In production you often run 2–3 copies of your app. Each copy has its own scheduler, so the "nightly report" runs three times! Options:

  • Switch scheduling on in only one instance with a property (our app.scheduling.enabled + @ConditionalOnProperty).
  • Use a distributed lock library such as ShedLock – only the instance that gets the lock (stored in the database) runs the job.
  • For complex needs (persistent jobs, misfire handling, clustering) use Quartz (spring-boot-starter-quartz), or an external scheduler (Kubernetes CronJob).

3.7 Async – synchronous vs asynchronous

Synchronous = the caller waits until the work is done. Asynchronous = the caller hands the work to someone else and continues immediately.

Request thread→ save user (20 ms)→ send email (3000 ms) ⏳→ response after ~3 s 😞
Request thread→ save user (20 ms)→ response after ~20 ms 😀 ⤵ meanwhile async-1: send email (3000 ms)

3.8 @EnableAsync and @Async

@Configuration
@EnableAsync
public class AsyncConfig { ... }

@Service
public class ReportService {
    @Async                                   // runs on a pool thread, caller does not wait
    public void rebuildSearchIndex() { ... }
}

How it works: like caching and transactions, Spring wraps the bean in a proxy (topic 27). When you call an @Async method on the proxy, the proxy packs the call into a task, gives it to a thread pool (an executor), and returns immediately.

The same proxy rules apply as always:

  • The method must be public.
  • It must be called from another bean. this.rebuildSearchIndex() inside the same class runs synchronously (self-invocation).

3.9 Return types of @Async methods

Return typeWhat the caller getsExceptions go to…
voidNothing – "fire and forget".The AsyncUncaughtExceptionHandler (logs by default).
CompletableFuture<T>A "promise" of a T in the future. Can wait, combine, chain.The future completes exceptionally; join() rethrows.
Future<T>Old style; only get(). Prefer CompletableFuture.get() throws ExecutionException.
anything else, e.g. StringAlways null! The real value is lost.–

Returning a result:

@Async
public CompletableFuture<Integer> totalSalesToday() {
    // ... slow work ...
    return CompletableFuture.completedFuture(15_430);   // wrap the ready value
}

Inside the method you compute the value normally and wrap it with completedFuture. Spring hands the caller a different future that completes when the pool thread finishes.

3.10 Running work in parallel with CompletableFuture

Three independent 1-second queries take 3 seconds one after the other. Started together, they take about 1 second:

CompletableFuture<Integer> sales     = reportService.totalSalesToday();    // starts now, returns at once
CompletableFuture<Integer> customers = reportService.newCustomersToday();  // starts now
CompletableFuture<Integer> orders    = reportService.openOrders();         // starts now

CompletableFuture.allOf(sales, customers, orders).join();   // wait for ALL three

int total = sales.join();     // already done - returns immediately

Useful CompletableFuture methods (recap from topic 17):

MethodWhat it does
join()Wait and get the value (unchecked exception on failure).
allOf(a, b, c)A future that completes when all are done.
anyOf(a, b)Completes when the first one is done.
thenApply(fn)Transform the result: sales.thenApply(s -> s * 2).
thenCombine(other, fn)Combine two results: sales.thenCombine(orders, Integer::sum).
exceptionally(fn)Fallback value when it fails.
orTimeout(2, SECONDS)Fail if not done in time.

3.11 Your own thread pool: ThreadPoolTaskExecutor

Spring Boot auto-configures an executor called applicationTaskExecutor (8 core threads, unlimited queue). For real apps you usually define your own, with limits that match your workload:

config/AsyncConfig.java@Bean(name = "appTaskExecutor")
public ThreadPoolTaskExecutor appTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(3);
    executor.setMaxPoolSize(6);
    executor.setQueueCapacity(50);
    executor.setThreadNamePrefix("async-");
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(10);
    executor.initialize();
    return executor;
}

How a ThreadPoolTaskExecutor decides what to do with a new task – this surprises almost everyone:

  1. Fewer than core (3) threads busy? → use/create a core thread.
  2. All core threads busy? → put the task in the queue (up to 50 waiting tasks). No new thread yet!
  3. Queue full? → create extra threads up to max (6).
  4. Max threads busy AND queue full? → the task is rejected (TaskRejectedException) – unless you set a rejection policy such as CallerRunsPolicy.
new task→ core threads free?no → queue has space?no → below max threads?no → rejected

Which executor does @Async use? You can name it: @Async("appTaskExecutor"). Or make one the default by implementing AsyncConfigurer.getAsyncExecutor() – that is what our project does, so plain @Async uses appTaskExecutor.

3.12 Exceptions in void async methods

When a void @Async method throws, nobody is waiting for it, so there is nobody to catch the exception. Register a handler to at least log it:

@Override
public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
    return (exception, method, params) ->
            log.error("@Async method {}({}) failed: {}", method.getName(), Arrays.toString(params), exception.getMessage());
}

3.13 What does NOT travel to the async thread

Some things are stored "per thread" (in a ThreadLocal), so the new thread starts without them:

  • The transaction – an @Async method does not join the caller's transaction. It may even run before the caller's transaction commits and not see the new data! (Section 3.17 shows the fix.)
  • The logged-in user (Spring Security's SecurityContext).
  • MDC values such as a request id (topic 30).

Pass what you need as method parameters (ids, not entities). For MDC/security, a TaskDecorator on the executor can copy values across.

3.14 Events – why?

Without events, the registration service must know everyone who reacts:

public AppUser register(...) {
    AppUser user = repository.save(...);
    emailService.sendWelcome(user);      // UserService depends on EmailService
    auditService.log(user);              // ... and AuditService
    couponService.giveWelcomeCoupon(user); // ... and CouponService. Next month: CrmService? AnalyticsService?
    return user;
}

With events, it only announces the fact:

public AppUser register(...) {
    AppUser user = repository.save(...);
    eventPublisher.publishEvent(new UserRegisteredEvent(user.getId(), user.getName(), user.getEmail(), user.getRegisteredAt()));
    return user;
}

Each reaction lives in its own listener class. Adding a new reaction = adding a new class; UserService never changes. This is the classic Observer pattern (publisher/subscriber), built into the Spring container.

UserService
publishEvent()→ Spring
ApplicationEventMulticaster→ WelcomeEmailListener AuditLogListener RegistrationFailedListener

3.15 The three parts: event, publisher, listener

1. The event – any object. A record is perfect: small and immutable. Name it in the past tense.

public record UserRegisteredEvent(Long userId, String name, String email, LocalDateTime registeredAt) { }

(Before Spring 4.2, events had to extend ApplicationEvent. Not needed any more.)

2. The publisher – inject ApplicationEventPublisher and call publishEvent(event).

3. The listener – a method in any bean, annotated with @EventListener. The parameter type decides which events it receives.

@Component
public class AuditLogListener {
    @EventListener
    public void audit(UserRegisteredEvent event) {
        log.info("AUDIT: user {} registered", event.userId());
    }
}

3.16 @EventListener is synchronous!

A very important fact: by default, publishEvent() calls every @EventListener immediately, on the same thread, inside the same transaction. It is like a normal method call that you cannot see. Consequences:

  • publishEvent() returns only after all listeners finished. A slow listener makes the request slow.
  • If a listener throws, the exception comes out of publishEvent() and the publisher's transaction rolls back.

More options:

@EventListener
@Order(1)                                               // lower number runs first
public void audit(UserRegisteredEvent event) { ... }

@EventListener(condition = "#event.email().endsWith('@course.com')")   // SpEL filter
public void flagStaffAccount(UserRegisteredEvent event) { ... }

3.17 @TransactionalEventListener – wait for the commit

Problem: we publish the event inside the registration transaction. If we send the welcome email immediately and then the transaction rolls back (duplicate email, database error…), we emailed a user who does not exist! The fix:

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)   // AFTER_COMMIT is the default
public void sendWelcomeEmail(UserRegisteredEvent event) { ... }

Spring holds the event and delivers it to this listener only after the transaction has successfully committed.

PhaseRuns when…Typical use
BEFORE_COMMITjust before commit, still inside the transactionlast-minute validation / extra writes that must be in the same transaction
AFTER_COMMIT (default)the commit succeededemails, messages to other systems, cache eviction
AFTER_ROLLBACKthe transaction rolled backlogging / alerting about failures
AFTER_COMPLETIONafter commit or rollbackcleanup
⚠️ No transaction = no callIf the event is published when no transaction is active, a @TransactionalEventListener is simply not called. Use @TransactionalEventListener(fallbackExecution = true) if it should run anyway.
ℹ️ Careful with database writes in AFTER_COMMITThe original transaction is already committed. If the listener must write to the database, give it its own transaction: @Transactional(propagation = Propagation.REQUIRES_NEW) (Spring 6.1+ even enforces this for transactional listeners) – or make it @Async.

3.18 Async listeners: @Async + @TransactionalEventListener

Combine both and you get the perfect "welcome email":

@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void sendWelcomeEmail(UserRegisteredEvent event) { ... }
  • Only if the user was really saved (after commit).
  • Without making the user wait (on an async-N thread).
  • An exception in the email code cannot break the registration.

@Async also works on a plain @EventListener.

4.1 The registration flow, step by step

user/UserService.java@Transactional
public AppUser register(String name, String email) {
    if (repository.existsByEmail(email)) {
        throw new IllegalArgumentException("Email already registered: " + email);
    }
    AppUser saved = repository.save(new AppUser(name, email));
    log.info("Saved user {} - publishing UserRegisteredEvent", saved.getId());

    eventPublisher.publishEvent(
            new UserRegisteredEvent(saved.getId(), saved.getName(), saved.getEmail(), saved.getRegisteredAt()));

    if (email.contains("fail")) {                      // DEMO: roll back AFTER publishing
        throw new IllegalStateException("Simulated failure after publishing the event - rolling back");
    }
    log.info("register() finished - returning the response now (email is sent in the background)");
    return saved;
}

What happens for asha@example.com, in order:

  1. The request thread saves the user (inside the transaction).
  2. publishEvent immediately calls AuditLogListener.audit (synchronous, same thread).
  3. The WelcomeEmailListener is a transactional listener, so Spring only remembers it for now.
  4. register() returns → the transaction commits.
  5. After the commit, Spring calls sendWelcomeEmail. Because it is @Async, it is handed to async-1, and the HTTP response goes out immediately.
  6. 3 seconds later async-1 logs "Welcome email SENT".

For fail@example.com: steps 1–3 are the same, then the exception rolls back the transaction, so the AFTER_COMMIT listener is never called, and the AFTER_ROLLBACK listener logs a warning.

6. Common mistakes

⚠️ Mistake: forgetting @EnableScheduling / @EnableAsyncNo error – jobs never run and @Async methods run synchronously.
Fix: add the annotation to a @Configuration class. Check the thread name in the log.
⚠️ Mistake: calling an @Async method from the same class 
public void register(...) {
    ...
    this.sendEmail(user);   // runs SYNCHRONOUSLY - the proxy is bypassed
}
Fix: move the async method to another bean (e.g. an EmailService), or better, publish an event.
⚠️ Mistake: an @Async method returning String or ProductThe caller always receives null.
Fix: return CompletableFuture<String> and use CompletableFuture.completedFuture(value).
⚠️ Mistake: thinking "max pool size 6" means 6 parallel tasksWith a queue capacity of 50, extra threads are created only when 50 tasks are already waiting. Until then only the core threads work. We saw this while building the project: right after registering two users, two of the three core threads were busy sending emails, so the three dashboard tasks queued up behind one thread and took ~3000 ms instead of ~1000 ms.
Fix: size the core pool for normal load, or use a small queue; use separate executors for separate kinds of work (e.g. emailExecutor, reportExecutor).
⚠️ Mistake: a 5-field cron expression@Scheduled(cron = "0 2 * * *") fails at startup.
Fix: Spring cron has 6 fields (seconds first): "0 0 2 * * *".
⚠️ Mistake: one slow job blocks all other jobsThe default scheduler has 1 thread.
Fix: spring.task.scheduling.pool.size=2 (or more), and keep jobs short.
🛑 Mistake: sending the email in a plain @EventListener or @Async method inside the transaction The email goes out, then the transaction rolls back → the user gets "Welcome!" but has no account. Or the async thread reads the user before the commit and finds nothing.
Fix: @TransactionalEventListener(phase = AFTER_COMMIT) (+ @Async).
⚠️ Mistake: passing JPA entities in events to async listenersThe entity is detached in the new thread; touching a lazy relationship throws LazyInitializationException.
Fix: put ids and simple values into the event (a record), and reload in the listener if needed.
⚠️ Mistake: the same job runs 3× in productionThree app instances = three schedulers.
Fix: ShedLock, a property switch for one instance, or an external scheduler.

7. Best practices

  • Configure schedules in properties, not in code, so operations can change them per environment and switch jobs off.
  • Keep scheduled methods thin: the job calls a service method. The service can then also be tested and triggered manually (e.g. an admin endpoint).
  • Make jobs idempotent – running twice should not break anything ("cancel unpaid orders older than 30 min" is safe to repeat; "add 10 points to every user" is not).
  • Log the start, end and duration of every job, and catch exceptions inside – one failure should not stay invisible.
  • Always define your own bounded thread pool for @Async with a clear name prefix; use separate pools for very different kinds of work.
  • Prefer CompletableFuture over void when the caller cares about the result or errors.
  • Events: past-tense names, immutable records, ids not entities.
  • Use @TransactionalEventListener(AFTER_COMMIT) for anything that talks to the outside world (email, SMS, other services).
  • Remember: in-memory events and async tasks are lost if the app crashes. For must-not-lose work, use a message broker (topics 57–58) or the "outbox" pattern.
  • Graceful shutdown: setWaitForTasksToCompleteOnShutdown(true) and spring.task.scheduling.shutdown.await-termination=true let running work finish.

8. Key takeaways

  • @EnableScheduling + @Scheduled run methods on a timer: fixedRate (start-to-start), fixedDelay (end-to-start), cron (calendar, 6 fields).
  • The scheduler has one thread by default – raise spring.task.scheduling.pool.size.
  • @EnableAsync + @Async run methods on a thread pool; the caller continues immediately.
  • Async methods return void or CompletableFuture<T>; combine futures with allOf to run work in parallel.
  • Define a bounded ThreadPoolTaskExecutor; extra threads beyond core start only when the queue is full.
  • Like caching and transactions, @Async works through proxies: public methods, called from another bean.
  • Events decouple code: publish with ApplicationEventPublisher, react with @EventListener.
  • @EventListener is synchronous; @TransactionalEventListener waits for commit/rollback; add @Async to move it off the request thread.

10. Interview questions

Q1. What is the difference between fixedRate and fixedDelay?

fixedRate measures from the start of one run to the start of the next (steady rhythm). fixedDelay measures from the end of one run to the start of the next (a guaranteed rest). For jobs with varying duration, fixedDelay avoids back-to-back runs.

Q2. Explain the Spring cron format.

Six fields: second, minute, hour, day-of-month, month, day-of-week. * = every, , = list, - = range, / = step, L = last. Example: 0 0 2 * * * = 02:00 every day; 0 30 9 * * MON-FRI = 09:30 on weekdays. Unix crontab has 5 fields (no seconds). A zone attribute sets the time zone.

Q3. How does @Async work, and when does it NOT work?

@EnableAsync makes Spring create a proxy around beans with @Async methods. Calling such a method through the proxy submits it to a TaskExecutor and returns immediately. It does not work for self-invocation (this.method()), non-public methods, or objects not managed by Spring (new MyService()).

Q4. What can an @Async method return and how are exceptions handled?

void or CompletableFuture<T> (or Future). For void, exceptions go to the AsyncUncaughtExceptionHandler (configure via AsyncConfigurer). For a future, the future completes exceptionally and the caller sees the exception on join()/get() or handles it with exceptionally/handle.

Q5. Explain corePoolSize, maxPoolSize and queueCapacity of ThreadPoolTaskExecutor.

New tasks use core threads first; when all core threads are busy, tasks go to the queue; only when the queue is full are extra threads created up to max; when max threads are busy and the queue is full, tasks are rejected (or handled by a rejection policy like CallerRunsPolicy). With an unbounded queue, max size is never used.

Q6. Why use application events instead of direct method calls?

Loose coupling: the publisher does not know or depend on the reactions. New reactions are new listener classes (Open/Closed principle), modules stay independent, and listeners can be synchronous, asynchronous or transaction-bound without changing the publisher. Downsides: the flow is less obvious when reading code, and in-memory events are lost on crash.

Q7. Is @EventListener synchronous or asynchronous?

Synchronous by default: listeners run on the publisher's thread, inside its transaction, before publishEvent() returns. An exception in a listener propagates to the publisher. Add @Async to make it asynchronous (or configure an async multicaster).

Q8. What is @TransactionalEventListener and when would you use it?

A listener bound to the publisher's transaction. It runs in a chosen phase: AFTER_COMMIT (default), AFTER_ROLLBACK, AFTER_COMPLETION or BEFORE_COMMIT. Use it for side effects that must only happen if the data was really saved, like emails or messages to other systems. Without an active transaction it is not called unless fallbackExecution = true.

Q9. Your scheduled job runs three times in production. Why, and how do you fix it?

Each of the three application instances has its own scheduler. Fixes: a distributed lock (ShedLock), enabling scheduling on only one instance via a property/profile, moving the job to an external scheduler (Kubernetes CronJob), or Quartz in clustered mode. Also make the job idempotent.

Q10. What is lost when work moves to an @Async thread?

Thread-bound context: the current transaction, the Spring Security SecurityContext, MDC logging values and request attributes. Pass the needed data as parameters, use a TaskDecorator to copy MDC/security context, and never pass managed JPA entities to another thread.
