8. Polymorphism, Abstraction & Interfaces

Write code that works with "any kind of payment" or "any kind of shape" — and learn the single most important design idea behind Spring: program to an interface.

1. Why this matters

Imagine an online shop's checkout. Today it accepts credit cards. Next month: UPI. Next year: PayPal and a "buy now, pay later" app. Without polymorphism, the checkout code turns into a growing tower of if (type.equals("CARD")) ... else if (type.equals("UPI")) ..., and every new payment method means editing (and possibly breaking) the checkout.

With polymorphism and interfaces, the checkout says only: "give me something that can pay()". Any class that keeps that promise can be plugged in — without changing a single line of the checkout.

This is not just theory. Spring is built entirely on this idea:

  • Your services depend on interfaces (PaymentGateway, ProductRepository), and Spring injects the implementation (Topics 22–24).
  • Spring Data JPA (Topic 38): you write only an interface ProductRepository extends JpaRepository — Spring generates the class for you!
  • Spring Security, caching, transactions: all wrap your objects in "proxy" objects that implement the same interface (Topic 27).
  • In tests (Topics 21, 46), you replace real dependencies with fakes or mocks — possible only because code depends on interfaces.

If you understand this topic deeply, Spring will feel natural instead of magical.

2. Real-life analogy

🔌 The wall socket A wall socket is an interface: a standard shape and voltage. It doesn't care what you plug in — a phone charger, a laptop, a fan, a TV. Each device implements the plug standard in its own way inside. The socket works with devices that were invented after the socket was installed. That's polymorphism (one socket, many devices) and loose coupling (the wiring in your wall doesn't know your TV's brand).

Now imagine a fan whose wire is soldered directly into the wall. It works, but to replace it you need an electrician and a hammer. That's tight coupling — what happens when a class does new RazorpayGateway() inside itself.
🚗 Abstraction = driving a car You use the steering wheel, accelerator and brake. You don't need to know about fuel injection or ABS sensors. The car shows you what it can do and hides how. A petrol car and an electric car have the same pedals but totally different insides.

3. Concepts step by step

3.1 What is polymorphism?

Poly = many, morph = form. Polymorphism means "one name, many forms": the same method call can behave differently depending on the situation. Java has two kinds:

Compile-time polymorphismRuntime polymorphism
Also calledStatic polymorphism, early bindingDynamic polymorphism, late binding, dynamic method dispatch
Achieved byMethod overloadingMethod overriding + parent-type references
Who decides which method runs?The compiler, by the argument typesThe JVM, by the real object's class at runtime
Exampletotal(100, 2) vs total(99.5, 3)Notification n = new SmsNotification(); n.send()

3.2 Compile-time polymorphism (overloading)

You met overloading in Topic 4. Same method name, different parameter list — by number, type or order of parameters:

int    total(int unitPrice, int quantity)                    // 2 ints
double total(double unitPrice, int quantity)                 // different type
int    total(int unitPrice, int quantity, int discount)      // different number
String total(String product, int quantity)
String total(int quantity, String product)                   // different order
  • The compiler picks the best match by looking at the arguments. If no exact match, it tries widening (e.g. short → int).
  • Changing only the return type is not overloading → compile error "already defined".
  • You use it daily: System.out.println has versions for int, double, char, boolean, String, Object …

3.3 Runtime polymorphism (overriding + parent references)

The key rule: a variable of a parent type can hold an object of any child type.

Notification n1 = new EmailNotification("priya@shop.com");
Notification n2 = new SmsNotification("98480-12345");

n1.send("Your order has shipped");   // EMAIL to priya@shop.com | ...
n2.send("Your order has shipped");   // SMS to 98480-12345: ...

Both variables have the type Notification, but each send runs the version from the real object. The JVM looks at the object at runtime and "dispatches" the call to the right override — that's dynamic method dispatch.

💡 Remember this sentence "Reference type decides WHAT you can call (checked at compile time). Object type decides WHICH implementation runs (at runtime)."

Why is this so powerful? Because you can write code against the parent type once:

static void alertCustomer(Notification notification, String message) {
    notification.send(message);    // works for Email, SMS, Push ... and any future channel
}

Add a WhatsAppNotification class next month — alertCustomer works with it immediately, unchanged. This is called the Open/Closed Principle: code should be open for extension (new classes) but closed for modification (no edits to old code).

ℹ️ What is NOT polymorphic Only instance methods are dispatched at runtime. Fields and static methods are chosen by the variable type (remember field hiding in Topic 7). One more reason to keep fields private.

3.4 Upcasting and downcasting

Casting means treating an object as a different type in its family tree.

Employee (parent) ⇄ Manager (child)
UpcastingDowncasting
DirectionChild → parent typeParent → child type
SyntaxAutomatic: Employee e = manager;Explicit: Manager m = (Manager) e;
Safe?Always (a Manager IS-A Employee)Only if the object really is that child type — otherwise ClassCastException at runtime
Why do it?To treat many types uniformly (polymorphism)To use a child-only method like approveLeave()
Employee employee = new Manager("Anil", 8);   // upcast
// employee.approveLeave();                    // ❌ compile error: Employee has no approveLeave()
Manager m = (Manager) employee;                // downcast - OK, the object IS a Manager
m.approveLeave();                              // ✅

Employee intern = new Intern("Zoya", "Spring Boot");
Manager wrong = (Manager) intern;              // compiles, but 💥 ClassCastException at runtime

Note: casting never changes the object itself. It only changes how you look at it (which methods the compiler lets you call).

3.5 instanceof and pattern matching (Java 16+)

obj instanceof Type returns true if the object is that type (or a subtype). It returns false for null — it never crashes. Use it to check before downcasting.

// Old style (before Java 16): check, then cast on a separate line
if (e instanceof Manager) {
    Manager m = (Manager) e;
    System.out.println(m.getTeamSize());
}

// Java 16+ pattern matching: check + cast + new variable, in one step
if (e instanceof Manager m) {
    System.out.println(m.getTeamSize());       // m is already a Manager
}

// The pattern variable can be used in the same condition after &&
if (e instanceof Intern i && i.getTopic().contains("Spring")) { ... }
⚠️ instanceof chains are a design smell If you find yourself writing if (p instanceof Card) ... else if (p instanceof Upi) ... else if ... to decide behaviour, that behaviour should usually be an overridden method instead (p.pay()). Use instanceof sparingly — e.g. in equals() or when dealing with objects you don't control.
ℹ️ In newer Java Java 21 adds pattern matching in switch and record patterns. We stay on Java 17 in this course, where instanceof pattern matching is fully available.

3.6 Abstraction and abstract classes

Abstraction = expose what an object does, hide how. Java gives two tools: abstract classes and interfaces.

Look at the Shape idea: every shape has an area, but "a shape" in general has no formula. It makes no sense to create new Shape(). So we mark it abstract:

Example04_AbstractClasses.java (part)abstract class Shape {
    private final String name;              // fields: allowed

    protected Shape(String name) {          // constructor: allowed (called via super)
        this.name = name;
    }

    abstract double area();                 // abstract method: NO body, ends with ;
    abstract double perimeter();

    void printReport() {                    // concrete method: shared by all shapes
        System.out.printf("%-9s area = %7.2f%n", name, area());
    }
}

class Circle extends Shape {
    private final double radius;
    Circle(double radius) { super("Circle"); this.radius = radius; }

    @Override
    double area() { return Math.PI * radius * radius; }   // MUST implement

    @Override
    double perimeter() { return 2 * Math.PI * radius; }
}

Rules for abstract classes:

  • Declared with abstract class. Cannot be instantiated (new Shape(...) → compile error).
  • May contain abstract methods (no body) and normal methods, fields, constructors.
  • A concrete (non-abstract) child must implement every abstract method, otherwise it must be abstract too.
  • You can still have variables of the abstract type: Shape s = new Circle(7); — that's polymorphism.
  • If a class has even one abstract method, the class must be abstract.

Notice printReport(): a concrete method in the parent calls area(), which is abstract. At runtime the child's version is used. This "parent defines the steps, children fill in the details" idea is called the Template Method pattern — Spring's JdbcTemplate (Topic 37) is built this way.

3.7 Interfaces — pure contracts

An interface is a contract: a list of methods a class promises to provide. It says what, never how (except default methods, see below). A class signs the contract with implements.

interface Payment {
    boolean pay(double amount);       // automatically public abstract
    String methodName();
}

class UpiPayment implements Payment {
    @Override
    public boolean pay(double amount) { ... }    // must be public
    @Override
    public String methodName() { return "UPI"; }
}

Payment p = new UpiPayment("neha@okbank");       // interface type, concrete object
p.pay(1500);

What can go inside an interface?

MemberSinceNotesExample
Abstract methodsJava 1Implicitly public abstract; implementing class must provide themboolean pay(double amount);
ConstantsJava 1Every field is implicitly public static finaldouble MIN_AMOUNT = 1.0;
default methodsJava 8Have a body; implementations inherit it and may overridedefault double fee(double a) { return 0; }
static methodsJava 8Helpers called on the interface name; not inherited by classesPayment.isValidAmount(250)
private methodsJava 9Internal helpers for default/static methodsprivate String line()
Instance fields / constructors—Not allowed — interfaces have no state
ℹ️ Why were default methods added? To let Java's designers add new methods to old interfaces (like forEach on Iterable, stream() on Collection) without breaking millions of existing classes that implemented them.

💡 Rule of thumb Start with an interface. If several implementations end up sharing a lot of code or state, add an abstract class that implements the interface (Java's own List interface + AbstractList class do exactly this). You get the best of both.

3.9 Multiple interfaces

A class may extend one class but implement any number of interfaces. This is how Java offers multiple inheritance — of type and contracts — without the diamond problem of state.

class SmartPhone extends Gadget implements Camera, MusicPlayer, Phone { ... }

Camera camera = phone;          // the same object, seen as a Camera
MusicPlayer player = phone;     // ... or as a MusicPlayer

Default method conflict: if two interfaces provide the same default method, the compiler forces the class to override it. Inside, you can call a specific parent's version with InterfaceName.super.method():

@Override
public void powerOn() {
    Camera.super.powerOn();
    MusicPlayer.super.powerOn();
    System.out.println(name + " is ready");
}

Interfaces can also extend other interfaces (even several): interface Camera extends Device. And if a class and an interface both supply a method, the class wins.

3.10 Functional interfaces — a preview

An interface with exactly one abstract method is a functional interface. Mark it with @FunctionalInterface so the compiler checks the rule. Its special power: you can implement it with a short lambda expression instead of writing a whole class.

@FunctionalInterface
interface DiscountRule {
    double apply(double price);
}

// Full class (long way)
class FestivalDiscount implements DiscountRule {
    public double apply(double price) { return price * 0.8; }
}

// Lambda (short way):   parameter -> result
DiscountRule tenPercent = price -> price * 0.9;
DiscountRule flat100    = price -> price - 100;

tenPercent.apply(2000);    // 1800.0

A lambda is just "a tiny implementation of the one method". You can now pass behaviour as an argument: printFinalPrice(2000, p -> p > 1500 ? p - 300 : p). Java has many built-in functional interfaces (Runnable, Comparator, Predicate, Function …). All of that is Topic 13.

3.11 Programming to an interface — loose coupling (KEY for Spring)

Coupling = how strongly one class depends on another. Tight coupling means a class is glued to a specific concrete class; loose coupling means it depends only on a contract (interface).

❌ Tightly coupled

class TightCheckoutService {
    private final RazorpayGateway gateway = new RazorpayGateway();   // glued to Razorpay
    ...
}
  • Switch to Stripe? Edit this class.
  • Run a test without charging real money? Impossible — it always creates the real gateway.
  • Razorpay's constructor changes? This class breaks too.

✅ Loosely coupled

interface PaymentGateway {
    boolean charge(String orderId, double amount);
}

class CheckoutService {
    private final PaymentGateway gateway;          // depends on the INTERFACE

    CheckoutService(PaymentGateway gateway) {      // the implementation is GIVEN to us
        this.gateway = gateway;
    }
    ...
}

// Somebody else (main today, Spring tomorrow) decides which implementation to use:
new CheckoutService(new RazorpayGateway());
new CheckoutService(new StripeGateway());
new CheckoutService(new FakePaymentGateway(false));   // for tests

This pattern — depend on an interface, receive the implementation from outside — has a name: Dependency Injection (DI). The outside "assembler" that creates objects and plugs them together is, in a Spring app, the Spring container. In Topic 22 you will replace our hand-written main wiring with Spring doing it for you, and in Topic 24 you'll choose between multiple implementations with @Qualifier and @Primary.

💡 Declare variables with the interface type Write List<String> names = new ArrayList<>(); rather than ArrayList<String> names = .... The rest of your code then depends only on List, so switching to LinkedList later is a one-word change. Same idea, everyday scale.

4.5 Example05 — the Payment interface

Example05_Interfaces.javainterface Payment {
    double MIN_AMOUNT = 1.0;                       // constant

    boolean pay(double amount);                    // abstract
    String methodName();

    default void printReceipt(double amount) {     // default (uses a private helper)
        System.out.println(line() + "\nReceipt: Rs. " + amount + " paid via " + methodName() + "\n" + line());
    }

    default double fee(double amount) {
        return 0;
    }

    static boolean isValidAmount(double amount) {  // static
        return amount >= MIN_AMOUNT;
    }

    private String line() {                        // private (Java 9+)
        return "-".repeat(30);
    }
}

CreditCardPayment overrides fee (2%), UpiPayment keeps the default (free), PayPalPayment overrides both printReceipt and fee. Note the implementing methods are public — required because interface methods are public.

6. Common mistakes

❌ Mistake: downcasting without checking Manager m = (Manager) employee; crashes with ClassCastException if the object is an Intern.
Fix: if (employee instanceof Manager m) { ... } — or better, redesign so you don't need the cast (an overridden method).
⚠️ Mistake: calling a child-only method through a parent variable Employee e = new Manager(...); e.approveLeave(); → "cannot find symbol".
Fix: the variable type decides what you can call. Either declare it as Manager, or move the method to the parent/interface if all types should have it.
⚠️ Mistake: trying to instantiate an abstract class or interface new Shape("x") / new Payment() → "is abstract; cannot be instantiated".
Fix: create a concrete subclass/implementation: new Circle(7), new UpiPayment(...).
⚠️ Mistake: forgetting public when implementing an interface method boolean pay(double amount) { ... } in the class → "attempting to assign weaker access privileges; was public".
Fix: public boolean pay(double amount).
⚠️ Mistake: not implementing every abstract method "Square is not abstract and does not override abstract method area() in Shape".
Fix: implement all of them (VS Code: click the lightbulb → Add unimplemented methods), or mark the class abstract.
⚠️ Mistake: overloading only by return type int total(int, int) and long total(int, int) → "already defined".
Fix: change the parameter list or the method name.
⚠️ Mistake: long if/else instanceof chains They grow with every new type and are easy to forget to update.
Fix: put the varying behaviour in an overridden/implemented method and call it polymorphically.
⚠️ Mistake: new-ing dependencies inside a class private final RazorpayGateway gateway = new RazorpayGateway(); makes the class impossible to test or reconfigure.
Fix: depend on an interface and receive the implementation through the constructor.

7. Best practices

  • Program to an interface: declare fields, parameters and variables with the interface type (PaymentGateway, List, Map).
  • Inject dependencies through the constructor and store them in private final fields. This is exactly the style Spring recommends.
  • Prefer polymorphism over type checks. Replace if/else on types with overridden methods.
  • Keep interfaces small and focused ("Interface Segregation Principle"): Camera, MusicPlayer, Phone instead of one giant Device with 30 methods.
  • Use default methods sparingly — for convenient defaults, not to sneak state or big logic into interfaces.
  • Mark single-method interfaces with @FunctionalInterface so they can't accidentally gain a second abstract method.
  • Use abstract classes when related classes really share code/state; combine with an interface for the public contract.
  • Use instanceof pattern matching (Java 16+) instead of check-then-cast when you really need a type check.
  • Name implementations by what's special about them (StripeGateway, JpaProductRepository), not PaymentGatewayImpl — though you'll see ...Impl a lot in real projects.

8. Key takeaways

  • Polymorphism = one name, many forms. Overloading is compile-time; overriding + parent references is runtime.
  • Reference type decides what you can call; object type decides which version runs.
  • Upcasting is automatic and safe; downcasting needs a cast and an instanceof check (use if (x instanceof T t)).
  • Abstract classes can't be instantiated; they mix abstract methods (no body) with fields, constructors and concrete methods.
  • Interfaces are contracts: abstract, default, static, private methods and constants — no state.
  • A class extends one class but can implement many interfaces; conflicting defaults must be overridden (X.super.m()).
  • A functional interface has one abstract method and can be implemented with a lambda.
  • Program to an interface + constructor injection = loose coupling: easy to swap, extend and test. This is what Spring automates.

2. Abstract Employee pay. Create abstract class Worker with a name and abstract double monthlyPay(). Implement FullTimeWorker (fixed salary) and HourlyWorker (hours × rate). Put both in a Worker[] and print total payroll.

Hint / solution 
public class Practice02 {
    public static void main(String[] args) {
        Worker[] staff = { new FullTimeWorker("Asha", 50000), new HourlyWorker("Ben", 120, 300) };
        double total = 0;
        for (Worker w : staff) {
            System.out.println(w.getName() + ": " + w.monthlyPay());
            total += w.monthlyPay();
        }
        System.out.println("Total payroll: " + total);   // 86000.0
    }
}

abstract class Worker {
    private final String name;
    protected Worker(String name) { this.name = name; }
    String getName() { return name; }

10. Interview questions

Q1. What is polymorphism? What are its types in Java?

The ability of one name/interface to take many forms. Compile-time (static) polymorphism via method overloading, resolved by the compiler from argument types; runtime (dynamic) polymorphism via method overriding, where a parent-type reference calls the overridden method of the actual object, resolved by the JVM (dynamic dispatch).

Q2. What is dynamic method dispatch?

The mechanism by which a call to an overridden method through a superclass/interface reference is resolved at runtime based on the actual object type. E.g. Notification n = new SmsNotification(); n.send() runs SmsNotification.send().

Q3. What is the difference between upcasting and downcasting?

Upcasting converts a subclass reference to a superclass type — implicit and always safe. Downcasting converts a superclass reference to a subclass type — requires an explicit cast and throws ClassCastException at runtime if the object isn't actually an instance of that subclass; guard it with instanceof.

Q4. What is pattern matching for instanceof?

Java 16+ syntax if (obj instanceof Type t) that tests the type and, if true, binds a new variable t already cast to Type. It removes the separate cast line and the risk of casting to the wrong type. The variable is in scope only where the test is known to be true.

Q5. Abstract class vs interface — differences and when to use each?

An abstract class can have state (fields), constructors, any access modifiers and concrete methods, but a class can extend only one. An interface defines a contract (abstract methods plus default/static/private methods and constants), has no instance state or constructors, and a class can implement many. Use an interface for capabilities/contracts and dependencies between components; use an abstract class to share code and state among closely related classes. Often both together.

Q6. Can an abstract class have a constructor? Can it have no abstract methods?

Yes to both. The constructor is called by subclasses via super(...) to initialize shared fields. An abstract class with no abstract methods is legal — it simply prevents direct instantiation.

Q7. Why were default and static methods added to interfaces in Java 8? What about private methods?

Default methods let library designers evolve interfaces (e.g. add stream() to Collection) without breaking existing implementations; static methods let related helpers live on the interface. Java 9 added private methods so default/static methods can share helper code without exposing it.

Q8. What happens if a class implements two interfaces with the same default method?

Compilation fails unless the class overrides the method. Inside the override it can delegate to a specific one using InterfaceName.super.method(). If a superclass provides the method, the class's version wins over interface defaults.

Q9. What is a functional interface?

An interface with exactly one abstract method (it may also have default/static methods), optionally annotated @FunctionalInterface. It can be implemented with a lambda or method reference. Examples: Runnable, Comparator, Predicate, Function.

Q10. What does "program to an interface, not an implementation" mean and why does Spring rely on it?

Code should depend on abstract types (interfaces) rather than concrete classes, and receive concrete implementations from outside (e.g. via constructor). This gives loose coupling: implementations can be swapped (Razorpay → Stripe), extended, and replaced with fakes/mocks in tests without changing the dependent class. Spring's IoC container creates the implementations and injects them (dependency injection), and also wraps beans in proxies implementing the same interfaces for transactions, security, caching, etc.
