Follow one user request through many services: same trace id in every log line, a timeline in Zipkin, and all logs searchable in one place.

1. Why this matters

A customer complains: “My order at 10:42 took 9 seconds and then failed!”

In a monolith you open one log file and search for 10:42. In microservices that one click travelled through the gateway, order-service, payment-service, inventory-service and notification-service — five processes, maybe running as 3 copies each, on different machines, each with its own log. Thousands of other requests were logged at 10:42 too. Which lines belong to this customer? Which service was slow?

Without help, debugging is like finding five specific grains of sand on five beaches. Two tools fix it:

  • Distributed tracing — every request gets a unique trace id that travels with it to every service. Each service writes it into its logs and reports timing information (spans) to a tracing server like Zipkin.
  • Centralized logging — all services send their logs to one searchable place (ELK, Loki/Grafana, Splunk, Datadog, CloudWatch…). Search traceId=6ac86fd3… and you get the complete story across all services.
ℹ️ Where you will see this at work Every serious microservice company has a tracing UI (Zipkin, Jaeger, Grafana Tempo, Datadog APM, New Relic, AWS X-Ray) and a log platform. In incidents, the first question is usually “what's the trace id?”. Spring Boot 3 gives you all of this with two dependencies and three properties.

2. Real-life analogy

📦 The courier tracking number

You send a parcel from Delhi to Bangalore. The courier gives you one tracking number: DL7731.

  • The parcel is scanned at each step: picked up in Delhi, sorted at the hub, loaded on a flight, arrived in Bangalore, out for delivery.
  • Every scan is written with the same tracking number plus a time stamp.
  • On the website you type DL7731 and see the whole journey as a timeline — and that it sat 6 hours at the hub. That is where it was slow.

Mapping:

  • Tracking number = trace id (one per user request).
  • Each scan/step with start and end time = a span (with its own span id).
  • The label stuck on the box that every station reads = the HTTP header (traceparent) that carries the ids.
  • The tracking website = Zipkin.
  • Your own order number written on the box (“Birthday gift #42”) = a business correlation id (baggage).
  • A central office where all stations send their daily reports = centralized logging.

3. Concepts step by step

3.1 Observability: the three pillars

PillarAnswersExampleTooling
LogsWhat exactly happened?Payment PAY-d213 for order 1001 -> APPROVEDLogback → ELK / Loki
MetricsHow much / how often / how fast, overall?p99 latency 420 ms, 3 errors/minMicrometer → Prometheus → Grafana (topic 53)
TracesWhere did this one request go and where was time spent?order 120 ms → payment 610 ms → fraud-check 270 msMicrometer Tracing → Zipkin / Jaeger / Tempo

The magic happens when they are linked: a log line contains the trace id, so from a log you jump to the trace, and from a slow trace you jump to its logs.

3.2 Trace, span, trace id, span id

  • Span = one timed piece of work: “order-service handled POST /api/orders”, “RestClient called payment”, “fraud check”. It has a name, a start time, a duration, tags (key/values) and maybe an error.
  • Span id = 16 hex characters, unique per span (e.g. 767331487f79789a).
  • Parent span id = the span that caused this one. This links spans into a tree.
  • Trace = the whole tree of spans for one request.
  • Trace id = 32 hex characters, the same for every span in the tree (e.g. 6ac86fd3a00d09a8767331487f79789a).

Look at the timeline and you instantly see: most of the time is spent inside payment-service, and inside that, in the fraud check. Before the request reached payment-service there was also a gap — that's network + first-call warm-up.

3.3 How ids travel: context propagation

Inside one service the current trace is kept in a thread-local “context” (and copied into the logging MDC, topic 30). Between services it travels as an HTTP header. Spring Boot 3 uses the W3C Trace Context standard by default:

traceparent: 00-6ac86fd3a00d09a8767331487f79789a-9a1c5e0b7d2f4411-01
             │  │                                │                │
             │  trace id (32 hex)                parent span id   flags (01 = sampled)
             version
order-service
creates trace→ traceparent header → payment-service
reads header, continues trace→ traceparent → next service…

Older systems use B3 headers (X-B3-TraceId, X-B3-SpanId — from Zipkin). You can switch with management.tracing.propagation.type=b3 or support both: management.tracing.propagation.produce=w3c,b3.

3.4 The Spring Boot 3 tracing stack

Your code & Spring
(MVC, RestClient, Kafka…)→ Micrometer Observation
one API to measure→ Micrometer Tracing
spans, ids, MDC→ Bridge
Brave or OpenTelemetry→ Reporter / exporter→ Zipkin / Jaeger / Tempo
  • Micrometer Observation: Spring's instrumentation API. One Observation produces both a timer metric and a span.
  • Micrometer Tracing: a “facade” for tracers (like SLF4J is a facade for logging libraries).
  • Brave: the tracer library from the Zipkin project. Alternative: OpenTelemetry (micrometer-tracing-bridge-otel) — the vendor-neutral industry standard.
  • Reporter: zipkin-reporter-brave sends finished spans to Zipkin over HTTP in the background.
ℹ️ What about Spring Cloud Sleuth? In Spring Boot 2 tracing was done by Spring Cloud Sleuth. Sleuth does not work with Boot 3 — it was replaced by Micrometer Tracing. Old tutorials with spring-cloud-starter-sleuth are outdated.

3.6 Sampling — do we record every request?

Recording and storing every span of every request costs CPU, network and storage. So tracers sample: probability: 0.1 means 1 request in 10 is recorded (the decision is made once at the start and travels in the traceparent flags, so a trace is never “half recorded”).

  • Learning / local: 1.0.
  • Production: often 0.05–0.2, or smarter “tail-based” sampling in an OpenTelemetry collector (keep all slow/error traces).
  • Trace ids appear in logs even for unsampled requests — so log correlation always works.

3.7 Trace ids in every log line

When tracing is on, Spring Boot 3.2+ automatically puts traceId and spanId into the MDC and adds them to the console pattern. The default looks like [order-service,6ac86fd3…,767331487f79789a]. We extend the pattern with our correlation id:

logging:
  include-application-name: false      # the name is already inside our block
  pattern:
    correlation: "[${spring.application.name:},%X{traceId:-},%X{spanId:-},%X{correlation-id:-}] "

%X{traceId:-} means “the MDC value traceId, or empty if there is none” (e.g. during startup). Result (real output from this topic):

INFO 5976 --- [io-8081-exec-2] [order-service,6ac86fd3a00d09a8767331487f79789a,767331487f79789a,corr-d79f4144] c.course.tracing.order.OrderController : New order received: Pizza for 450.0
INFO 20628 --- [io-8082-exec-4] [payment-service,6ac86fd3a00d09a8767331487f79789a,5cce3a2304e50622,corr-d79f4144] c.c.tracing.payment.PaymentController : Payment request received for order 1001 amount 450.0

Two different processes, the same trace id. 🎉

3.8 Propagation across RestClient — the golden rule

🚨 Build HTTP clients from the Spring-provided builder Tracing headers are only added if the client is instrumented. Spring Boot instruments the injected RestClient.Builder, RestTemplateBuilder and WebClient.Builder. If you write RestClient.create() or new RestTemplate(), no header is sent and payment-service starts a new, unrelated trace.
PaymentClientConfig.java@Bean
public RestClient paymentRestClient(RestClient.Builder builder,          // injected => instrumented
                                    @Value("${payment-service.base-url}") String baseUrl) {
    return builder.baseUrl(baseUrl).build();
}
CommunicationTraced automatically?
Incoming Spring MVC / WebFlux requestsYes
RestClient / RestTemplate / WebClient from Boot's buildersYes
OpenFeign (topic 63)Yes, when io.github.openfeign:feign-micrometer is on the classpath (Spring Cloud OpenFeign wires it up)
Kafka / RabbitMQ (topics 57–58)Yes after enabling observation: spring.kafka.template.observation-enabled=true, spring.kafka.listener.observation-enabled=true (similar for RabbitMQ)
JDBC queriesNot by default (add the datasource-micrometer library if needed)
@Async / your own thread poolsOnly with a context-propagating task decorator (see mistakes)

3.9 Creating your own spans

Automatic spans cover HTTP in/out. To see inside a service, wrap interesting work in an Observation:

boolean suspicious = Observation.createNotStarted("payment.fraud-check", observationRegistry)
        .lowCardinalityKeyValue("payment.method", "card")      // tag, visible in Zipkin
        .observe(() -> fraudCheck(request));                  // the measured work

Three ways, from most to least recommended:

WayCodeNotes
Observation APIObservation.createNotStarted(...).observe(...)Span and metric. Tracer-independent.
@Observed annotation@Observed(name = "order.validate") on a bean methodNeeds spring-boot-starter-aop; same proxy rules as topic 27.
Tracer APItracer.nextSpan().name("x").start() … span.end()Low level; also gives tracer.currentSpan() to read ids.
⚠️ Low vs high cardinality tags Cardinality = how many different values a tag can have. payment.method=card|upi|wallet is low (few values) — fine for metrics. order.id=1001,1002,… is high (endless values) — use highCardinalityKeyValue so it goes only to the span, not to metrics (it would explode your metrics storage).

3.10 Baggage and correlation ids

Trace ids are random and technical. Sometimes you also want your own id travelling everywhere: a checkout id, a tenant id, a mobile session id. That is baggage — key/values that ride along with the trace.

management:
  tracing:
    baggage:
      remote-fields: correlation-id        # send/receive it as an HTTP header called "correlation-id"
      correlation:
        fields: correlation-id             # also copy it into the MDC (so logs can print it)

Our CorrelationIdFilter creates one if the caller did not send it, and returns it in the response header so the customer/support team can quote it. In the log lines above you saw corr-d79f4144 in both services.

⚠️ Baggage is sent with every downstream call Keep it small and never put secrets or personal data (emails, card numbers) in it — it may also reach third parties.

3.11 Zipkin

Zipkin is an open-source tracing server (from Twitter, 2012). It collects spans and shows them in a web UI. Easiest way to run it is Docker:

docker-compose.ymlservices:
  zipkin:
    image: openzipkin/zipkin:3
    container_name: course-zipkin
    ports:
      - "9411:9411"

In the UI (http://localhost:9411) you can: search traces by service, span name, tag or duration; open a trace and see the waterfall; click a span to see tags and errors; and open the Dependencies page that draws which service calls which. Alternatives: Jaeger, Grafana Tempo, and commercial APMs.

3.12 Centralized logging

Trace ids in logs only help if you can search all logs together. The common architecture:

Services
log to stdout / file (JSON)→ Shipper / agent

Elasticsearch / Loki→ UI
Kibana / Grafana

Structured (JSON) logs make this much easier: each line is a JSON object with fields (traceId, level, message…) instead of text the shipper must parse with regular expressions. Spring Boot 3.4+ supports it with one property:

logging:
  structured:
    format:
      console: ecs        # or "logstash" or "gelf" - JSON on the console
      file: ecs           # JSON in the log file

A line then looks like (shortened):

{"@timestamp":"2026-10-09T04:38:43.859Z","log":{"level":"INFO","logger":"c.course.tracing.order.OrderController"},
 "service":{"name":"order-service"},"message":"New order received: Pizza for 450.0",
 "traceId":"6ac86fd3a00d09a8767331487f79789a","spanId":"767331487f79789a","correlation-id":"corr-d79f4144"}
💡 In containers and Kubernetes The usual rule (12-factor app, topic 59) is: log to stdout, don't manage files yourself. The platform (Docker, Kubernetes) collects stdout and an agent ships it to the central store.

3.13 OpenTelemetry in one paragraph

OpenTelemetry (OTel) is the vendor-neutral industry standard for traces, metrics and logs. With Spring Boot you can swap Brave for OTel: micrometer-tracing-bridge-otel + opentelemetry-exporter-otlp and management.otlp.tracing.endpoint=http://localhost:4318/v1/traces. Your code (Observation API) stays the same — that is the benefit of the Micrometer facade. Many companies send OTLP to an OpenTelemetry Collector that forwards to Tempo, Jaeger or a commercial tool.

4.1 order-service controller

order-service/…/OrderController.java (core)@PostMapping
public OrderResponse placeOrder(@RequestBody OrderRequest request) {
    log.info("New order received: {} for {}", request.item(), request.amount());

    Observation.createNotStarted("order.validate", observationRegistry)   // custom child span
            .observe(() -> validate(request));

    long orderId = ids.incrementAndGet();
    log.info("Calling payment-service for order {}", orderId);
    PaymentResponse payment = paymentRestClient.post()                       // CLIENT span + headers
            .uri("/api/payments")
            .contentType(MediaType.APPLICATION_JSON)
            .body(new PaymentRequest(orderId, request.amount()))
            .retrieve()
            .body(PaymentResponse.class);

    return new OrderResponse(orderId, request.item(), request.amount(),
            payment.status(), payment.paymentId(), currentTraceId());
}

private String currentTraceId() {
    Span span = tracer.currentSpan();
    return span != null ? span.context().traceId() : "none";
}

We return the trace id in the response — handy for support: “please tell us the traceId shown in the error screen”.

4.2 The correlation id filter

order-service/…/CorrelationIdFilter.java (core)String existing = tracer.getBaggage(CORRELATION_ID) != null
        ? tracer.getBaggage(CORRELATION_ID).get()
        : null;

if (existing != null && !existing.isBlank()) {          // caller sent one: keep it
    response.setHeader(CORRELATION_ID, existing);
    chain.doFilter(request, response);
    return;
}

String newId = "corr-" + UUID.randomUUID().toString().substring(0, 8);
response.setHeader(CORRELATION_ID, newId);
try (BaggageInScope baggage = tracer.createBaggageInScope(CORRELATION_ID, newId)) {
    chain.doFilter(request, response);                  // everything inside sees the baggage
}

The filter runs inside Spring Boot's own tracing filter, so a span already exists. BaggageInScope is AutoCloseable; try-with-resources (topic 10) removes it when the request is done, so it never leaks to the next request on the same thread.

4.3 payment-service — zero tracing code needed for the basics

payment-service only has the two dependencies and the YAML. Because the incoming request carries traceparent and correlation-id headers, it continues the trace automatically. The only extra is the custom payment.fraud-check span shown in 3.9.

6. Common mistakes

⚠️ “Dropped 1 spans due to ConnectException” Zipkin is not running. Your app is fine — only the export failed.
Fix: docker compose up -d, or set management.tracing.enabled=false / remove the reporter if you only want ids in logs.
⚠️ “I see only some of my requests in Zipkin” Default sampling is 0.1 (10 %).
Fix: management.tracing.sampling.probability=1.0 while learning.
🚨 The trace breaks between services payment-service shows a different trace id. Cause: the client was created with RestClient.create(), new RestTemplate() or WebClient.create().
Fix: always inject and use Spring Boot's builder.
⚠️ Ids missing in logs from other threads Code in @Async methods, CompletableFuture.supplyAsync or your own executors logs [order-service,,]: the context is thread-local and did not move to the new thread.
Fix: decorate executors: executor.setTaskDecorator(new ContextPropagatingTaskDecorator()) (Spring 6.1+), or wrap with ContextSnapshotFactory.builder().build().captureAll().wrap(runnable).
⚠️ Old Sleuth dependency spring-cloud-starter-sleuth with Boot 3 → startup errors or simply no tracing.
Fix: remove it; use micrometer-tracing-bridge-brave (or -otel).
⚠️ Custom log pattern removes the ids Overriding logging.pattern.console completely without %X{traceId}.
Fix: prefer changing only logging.pattern.correlation, or include %correlation/%X{traceId} in your pattern.
🚨 Personal data in tags, baggage or logs Emails, card numbers or tokens in spans/baggage end up in Zipkin, log stores and even other companies' systems.
Fix: log ids, not personal data (topic 30). Mask where necessary.

7. Best practices

  • Always set spring.application.name — it is the service name everywhere.
  • Sample wisely in production (e.g. 10 %) but keep trace ids in all logs; consider tail-based sampling to keep all errors.
  • Return the trace id in error responses (e.g. a traceId field in your ProblemDetail, topic 35) so users can report it.
  • Log JSON to stdout in containers; let the platform ship logs.
  • Create custom spans only around meaningful work (external calls, heavy computations) — not every method.
  • Low-cardinality tags for metrics; high-cardinality values only on spans.
  • Propagate context through async code and messaging (enable observation for Kafka/RabbitMQ).
  • Standardize: W3C trace context, same logging format across all services, same field names.
  • Link the pillars: Grafana can jump from a Loki log line to the Tempo trace and to Prometheus metrics (exemplars).
  • Retention: keep traces days, not months; logs as long as your policy/legal requirements say.
  • Consider OpenTelemetry for vendor neutrality in new platforms.

8. Key takeaways

  • Observability = logs + metrics + traces, linked by trace ids.
  • A trace is a tree of spans; trace id (32 hex) is shared, span id (16 hex) is per span.
  • Boot 3: micrometer-tracing-bridge-brave + zipkin-reporter-brave + actuator; Sleuth is gone.
  • Ids travel in the W3C traceparent header; use Boot's injected client builders so they get added.
  • Logs get [app,traceId,spanId] automatically; customize with logging.pattern.correlation.
  • Custom spans with the Observation API (also produce metrics) or @Observed.
  • Baggage carries business correlation ids across services.
  • Zipkin (Docker, :9411) shows waterfalls and dependency graphs.
  • Centralized logging: ELK or Loki + Grafana; Boot 3.4+ structured JSON logs make shipping easy.

9. Practice exercises

Easy

Find the slow part. Run 5 orders, open Zipkin, sort by duration. Which span takes the most time in the slowest trace?

Hint / solution

Usually payment.fraud-check (100–300 ms random sleep). The very first request is often slower overall because of class loading / connection warm-up — a classic thing to notice in traces.

Easy

Sampling. Set management.tracing.sampling.probability: 0.0 in order-service only, send 3 orders. Are trace ids still in the logs? Do traces appear in Zipkin?

Hint / solution

Logs still have trace ids (ids are always created). Zipkin shows nothing new: the “not sampled” flag (-00 at the end of traceparent) travels to payment-service too, so it also does not report — the decision is made once, at the root.

Medium

Use @Observed. Move the validation into a new bean OrderValidator with a method annotated @Observed(name = "order.validate") and remove the manual Observation code.

Hint / solution
// pom.xml: add spring-boot-starter-aop
// application.yml: management.observations.annotations.enabled: true

@Component
public class OrderValidator {
    @Observed(name = "order.validate", contextualName = "validate-order")
    public void validate(OrderController.OrderRequest request) {
        if (request.item() == null || request.item().isBlank() || request.amount() <= 0) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "invalid order");
        }
    }
}
// OrderController: inject OrderValidator and call orderValidator.validate(request)
// (call it from ANOTHER bean - self-invocation would bypass the proxy)
Medium

Trace id in error responses. Add a @RestControllerAdvice to order-service that returns a ProblemDetail with a traceId property for every ResponseStatusException.

Hint / solution
@RestControllerAdvice
class ErrorHandler {
    private final Tracer tracer;
    ErrorHandler(Tracer tracer) { this.tracer = tracer; }

    @ExceptionHandler(ResponseStatusException.class)
    ProblemDetail handle(ResponseStatusException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(ex.getStatusCode(), ex.getReason());
        Span span = tracer.currentSpan();
        pd.setProperty("traceId", span != null ? span.context().traceId() : "none");
        return pd;
    }
}
Challenge

Third service. Add a notification-service (port 8083) that payment-service calls after an APPROVED payment. Confirm the trace now shows 3 services and the Zipkin dependency graph has two arrows.

10. Interview questions

Q1. What is distributed tracing and why do microservices need it?

It follows a single request across service boundaries by giving it a trace id that is propagated with every call, while each unit of work records a span with timing. It lets you see the full call path, find latency bottlenecks and errors, and correlate logs across services — impossible with isolated per-service logs.

Q2. Explain trace id, span id and parent span id.

Trace id identifies the whole request journey and is identical in all its spans. Span id identifies one operation. Parent span id points to the span that caused this one, forming a tree (the root span has no parent).

Q3. How is the trace context propagated between services?

Via headers. Spring Boot 3 uses W3C Trace Context (traceparent: version-traceId-parentSpanId-flags, optionally tracestate); B3 headers are an alternative. Instrumented clients inject the headers; instrumented servers extract them and continue the trace. For messaging, headers on messages are used.

Q4. What replaced Spring Cloud Sleuth in Spring Boot 3?

Micrometer Tracing (a tracer facade) on top of Micrometer Observation, with bridges for Brave or OpenTelemetry and reporters/exporters for Zipkin, OTLP, etc.

Q5. What is sampling and why is it used?

Recording only a fraction of traces to limit overhead and storage. Head-based sampling decides at the root (probability) and propagates the decision; tail-based sampling (in a collector) decides after seeing the whole trace, e.g. keep all errors and slow traces.

Q6. How do trace ids end up in log lines?

The tracer puts traceId and spanId into the SLF4J MDC whenever a span is in scope; Spring Boot's default log pattern (logging.pattern.correlation) prints them. Custom fields like baggage can be added to the MDC via correlation fields.

Q7. What is baggage? Give an example.

Key/value context propagated alongside the trace to all downstream services, e.g. a tenant id, checkout id or correlation id. It can be added to logs. It must be small and free of sensitive data because it is sent on every call.

Q8. Why might a trace break between two services?

The outgoing client was not instrumented (created manually instead of from Spring's builders), a proxy/gateway stripped headers, the two sides use different propagation formats (W3C vs B3), or context was lost on a thread switch in async code.

Q9. ELK vs Loki?

ELK (Elasticsearch, Logstash, Kibana) indexes full log content — powerful search, more resources. Loki indexes only labels and stores compressed chunks — cheaper, integrates with Grafana, Prometheus and Tempo. Both need a shipper (Filebeat/Fluent Bit vs Promtail/Alloy).

Q10. What is a correlation id and how is it different from a trace id?

A correlation id is any id used to correlate events of one business transaction across systems; it may be created by the client or business process (e.g. checkout id) and live longer than a single request (e.g. across async steps). A trace id is a technical id generated by the tracing system for one trace. Often the trace id is used as the correlation id; baggage lets you carry your own as well.
