1. Why this matters

Almost every program manages groups of things: products in a cart, students in a class, orders waiting in a kitchen, a phone book of name → number. In Topic 4 you used arrays, but arrays have big limits:

  • Fixed size — decide the size once; you can't add a 4th item to a 3-slot array.
  • No built-in operations — no "add", "remove", "contains", "remove duplicates", "look up by name". You write loops by hand every time.
  • One shape — just a numbered row. No "unique items only", no "key → value" lookups, no "first come, first served".

The Collections Framework (package java.util) is a set of interfaces and ready-made, well-tested, fast classes that solve all of this.

ℹ️ Where you'll see it at workEverywhere. A Spring REST endpoint returns List<ProductDto>, which becomes a JSON array. A JSON object maps to a Map<String, Object>. Spring Data's findAll() returns a List. A JPA @OneToMany relationship is a List or Set of child entities. Caches are maps. Choosing the wrong collection (or forgetting hashCode) causes real production bugs.

2. Real-life analogy

🏠 Think of things at home
  • List = a shopping list on paper. Items are in order, numbered 1, 2, 3… and you can write "Milk" twice.
  • Set = a bag of unique stickers. You can't have two identical stickers; if you try to add a copy, nothing happens.
  • Map = a phone book / dictionary. You look up a key (name) to get a value (number). Each name appears once.
  • Queue = the line at a ticket counter. First come, first served (FIFO).
  • Stack = a pile of plates. You take the one you put on top last (LIFO). Your browser's Back button works like this.
  • PriorityQueue = a hospital emergency room. The most serious patient is treated first, not the one who came first.

The <String> part — generics in one minute

List<String> reads "a List of String". The type in angle brackets tells Java what the collection may hold, so:

  • cart.add(42); → compile error (it's a list of Strings — type safety).
  • String first = cart.get(0); → no casting needed.
  • new ArrayList<>() — the empty <> is called the diamond; Java copies the type from the left side.

You'll learn to write your own generic classes in Topic 12. For now: always put the element type in the brackets.

💡 Primitives need wrappersList<int> is not allowed. Use List<Integer>, List<Double>, List<Boolean>. Java auto-converts int ↔ Integer (autoboxing / unboxing from Topic 2).

ArrayList vs LinkedList

Both are Lists with the same methods. The difference is what's inside:

ArrayList — an array inside
ABCD(spare)
Jumping to position 3 is instant. Inserting at the front means shifting every element right. When full, it creates a bigger array (×1.5) and copies.
LinkedList — a chain of nodes
A⇄B⇄C⇄D
Adding/removing at either end is instant (just re-link). But to reach position 3 it must walk node by node. Each node also stores 2 links (more memory).

ℹ️ What does O(1) / O(n) mean?"Big-O" describes how the work grows with the size n. O(1) = same time no matter how big (like opening a book at page 300 when you know the page). O(n) = time grows with size (like reading every page to find a word). O(log n) = in between, grows very slowly (like finding a word in a dictionary by halving).
💡 The practical answerUse ArrayList by default — it's the right choice 95% of the time thanks to fast reads and CPU-cache friendliness. If you need a queue or stack, use ArrayDeque, not LinkedList.

A Set refuses duplicates. add() returns false if the element is already there. "Duplicate" is decided by equals() (and hashCode() for hash-based sets — see 3.10).

A Map stores pairs. You find a value by its key, very fast. Keys are unique; putting an existing key replaces its value.

  • ArrayDeque — the go-to class for both queues (offer/poll) and stacks (push/pop/peek). Also offerFirst/offerLast/pollFirst/pollLast. Faster than LinkedList and the old Stack class. Doesn't allow null.
  • PriorityQueue — poll() always returns the smallest element (by natural order or a Comparator). Great for "most urgent first" or "cheapest first". Printing it does not show sorted order — only poll() does.
⚠️ Avoid java.util.Stack and VectorThey're legacy classes from Java 1.0, synchronized (slower) and with odd design. Use Deque<T> stack = new ArrayDeque<>(); and ArrayList instead.

3.7 Iterator and ConcurrentModificationException

An Iterator is a cursor that walks through a collection: hasNext() ("is there more?"), next() ("give me the next one"), remove() ("remove the one you just gave me"). Every for-each loop secretly uses one.

Iterator<String> it = products.iterator();
while (it.hasNext()) {
    String p = it.next();
    ...
}

Now the classic beginner bug:

for (String p : products) {
    if (p.startsWith("OUT:")) {
        products.remove(p);    // 💥 ConcurrentModificationException
    }
}

Why? The list keeps a counter of changes (modCount). The hidden iterator remembers the value when the loop started and checks it on every next(). You changed the list behind the iterator's back, so the counter no longer matches and the iterator stops immediately ("fail-fast") rather than give wrong results. The name is confusing: it has nothing to do with threads here.

Three correct ways:

// 1. Remove THROUGH the iterator
Iterator<String> iter = products.iterator();
while (iter.hasNext()) {
    if (iter.next().startsWith("OUT:")) {
        iter.remove();
    }
}

// 2. removeIf (Java 8+) — a tiny lambda: "remove p if p starts with OUT:" (lambdas: Topic 13)
products.removeIf(p -> p.startsWith("OUT:"));

// 3. Loop backwards by index
for (int i = products.size() - 1; i >= 0; i--) {
    if (products.get(i).startsWith("OUT:")) {
        products.remove(i);
    }
}
💡 In practiceUse removeIf — it's the shortest and clearest. Option 1 is what you'll see in older code.

Collections.sort(names) works for Strings and numbers because they already know how to compare themselves. For your own classes (like Employee) Java needs to be told how to order them. There are two ways:

Example07_ComparableVsComparator.javaclass Employee implements Comparable<Employee> {
    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.id, other.id);       // natural order: by id
    }
}

class NameComparator implements Comparator<Employee> {
    @Override
    public int compare(Employee a, Employee b) {
        return a.getName().compareTo(b.getName());       // alphabetical
    }
}

Collections.sort(staff);                 // uses compareTo → by id
staff.sort(new NameComparator());        // uses the comparator → by name

Descending order? Swap a and b, or call .reversed() on a comparator.

Sneak peek: the modern style

staff.sort(Comparator.comparing(Employee::getDepartment)
                     .thenComparing(Employee::getName));

Read it like English: "compare by department, then by name". Employee::getDepartment is a method reference — you'll learn exactly how it works in Topic 13. You'll see this style constantly in real code.

⚠️ Don't subtract to comparereturn this.id - other.id; can overflow for big or negative numbers and give the wrong sign. Use Integer.compare(a, b), Double.compare(a, b), or Comparator.comparing.

3.10 How HashMap works inside (simply)

How can map.get("Dosa") be instant even with a million entries? HashMap doesn't search one by one. It uses buckets:

  1. Ask the key for its hashCode() — an int "fingerprint". "Asha".hashCode() → 2050251.
  2. Turn that number into a bucket index (internal array of, initially, 16 buckets): roughly hash % 16 → bucket 4.
  3. Go directly to bucket 4. No searching through the other buckets.
  4. A bucket may hold several entries (a collision — "Ravi" also lands in bucket 4). Inside the bucket, use equals() to find the exact key.

Extra details (good for interviews):

  • Default capacity 16, load factor 0.75: when more than 12 entries exist, the table doubles and entries are redistributed ("rehashing").
  • Since Java 8, a bucket with many entries (8+) turns from a linked list into a balanced tree, so worst case is O(log n) instead of O(n).
  • HashSet is just a HashMap where your element is the key and the value is a dummy.

The equals/hashCode contract — the rule you must never break

❌ If two objects are equals(), they MUST have the same hashCode(). If you override equals but not hashCode, two "equal" keys get different (identity-based) hash codes → different buckets → map.get() looks in the wrong bucket and returns null, and a HashSet happily stores "duplicates". Example09 shows exactly this.
final class Isbn {
    private final String value;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Isbn)) return false;
        return value.equals(((Isbn) o).value);
    }

    @Override
    public int hashCode() {
        return Objects.hash(value);     // use the SAME fields as equals
    }
}
  • The opposite is NOT required: two different objects may share a hash code (collisions are normal).
  • Keys should be immutable. If you change a key's fields after put, its hash changes and the entry is "lost" in the old bucket.
  • VS Code can generate both methods: right-click → Source Action… → Generate hashCode() and equals(). Records (Topic 15) generate them automatically.

4.1 Example02 — the speed test

static long timeInsertFront(List<Integer> list, int n) {
    long start = System.nanoTime();
    for (int i = 0; i < n; i++) {
        list.add(0, i);                // insert at the FRONT
    }
    return (System.nanoTime() - start) / 1_000_000;   // nanoseconds → milliseconds
}

Notice the parameter type is List<Integer> — the same method times both an ArrayList and a LinkedList. That's programming to the interface. The results flip depending on the operation: LinkedList wins front-inserts, ArrayList wins index reads by a mile.

4.5 Example09 — seeing the buckets

static int bucketFor(int hash, int tableSize) {
    int spread = hash ^ (hash >>> 16);   // mix high bits into low bits (what HashMap does)
    return spread & (tableSize - 1);      // keep the low bits = index 0..15
}

You don't need to memorise the bit tricks — the idea is "hash → small bucket number". Then BrokenIsbn (equals only) fails to find its value and lets a duplicate into a Set, while Isbn (equals + hashCode) works perfectly.

6. Common mistakes

❌ Mistake: removing inside a for-each loop → ConcurrentModificationException.
Fix: removeIf, iterator.remove(), or a backwards index loop.
❌ Mistake: overriding equals without hashCode Objects "disappear" from HashMaps and HashSets contain duplicates.
Fix: always override both, using the same fields (let VS Code generate them, or use a record).
⚠️ Mistake: raw types List list = new ArrayList(); (no <String>) compiles with a warning, accepts anything, and crashes later with ClassCastException.
Fix: always write the type: List<String>. (More in Topic 12.)
⚠️ Mistake: list.remove(1) on a List<Integer> Removes index 1, not the value 1.
Fix: list.remove(Integer.valueOf(1)).
⚠️ Mistake: map.get(key) returning null and unboxing it int price = menu.get("Pizza"); → NullPointerException (null can't become an int).
Fix: getOrDefault("Pizza", 0) or check containsKey first.
⚠️ Mistake: trying to change List.of(...) or Arrays.asList(...) → UnsupportedOperationException.
Fix: wrap in new ArrayList<>(...) when you need a changeable list.
⚠️ Mistake: relying on HashMap/HashSet order Tests pass on your PC and fail elsewhere.
Fix: LinkedHashMap/TreeMap when order matters.
⚠️ Mistake: confusing Collection and Collections Collection = the interface. Collections = the utility class with static helpers.
⚠️ Mistake: using == to compare elements contains, indexOf, remove(obj) all use equals(). Your own classes need a proper equals for these to work as expected.

7. Best practices

  • Declare with interfaces: List<Order> orders = new ArrayList<>();; use interfaces in method parameters and return types.
  • Defaults: ArrayList, HashMap, HashSet, ArrayDeque. Switch only with a reason.
  • Always use generics; never raw types.
  • Return empty collections, not null: return List.of(); — callers can loop safely without null checks.
  • Prefer immutable collections for constants and for data you hand out (List.copyOf).
  • Use immutable keys (String, Integer, records, final classes) in maps and sets.
  • When you know roughly how many items you'll add, give a starting capacity: new ArrayList<>(10_000) — avoids repeated growing.
  • Use isEmpty() instead of size() == 0 — clearer.
  • Use entrySet() to loop over maps when you need keys and values.
  • Don't use legacy Vector, Hashtable, Stack in new code.
  • In Topic 14 you'll process collections with Streams (filter, map, groupingBy) — even more concise.

8. Key takeaways

  • Collections grow automatically and come with ready-made methods; they hold objects (use wrappers for primitives).
  • List = ordered + duplicates + index. Set = unique. Map = key → value. Queue/Deque = FIFO/LIFO/both ends.
  • Hash* = fastest, no order; Linked* = insertion order; Tree* = sorted.
  • ArrayList is the default list; ArrayDeque is the default queue and stack; PriorityQueue hands out the smallest first.
  • Don't remove inside for-each — use removeIf or Iterator.remove().
  • Comparable = one natural order inside the class; Comparator = any number of orders from outside.
  • List.of/Set.of/Map.of are immutable and reject null.
  • HashMap: hashCode picks the bucket, equals picks the entry. Override both together, and keep keys immutable.

4. Balanced brackets. Using an ArrayDeque as a stack, write isBalanced(String s) that returns true for "{[()]}" and false for "{[(])}" and "((". (A very common interview question!)

Hint / solution
import java.util.ArrayDeque;
import java.util.Deque;

public class Brackets {
    static boolean isBalanced(String s) {
        Deque<Character> stack = new ArrayDeque<>();
        for (char c : s.toCharArray()) {
            if (c == '(' || c == '[' || c == '{') {
                stack.push(c);
            } else if (c == ')' || c == ']' || c == '}') {
                if (stack.isEmpty()) return false;
                char open = stack.pop();
                if ((c == ')' && open != '(') || (c == ']' && open != '[') || (c == '}' && open != '{')) {
                    return false;
                }
            }
        }
        return stack.isEmpty();   // anything left open → not balanced
    }

    public static void main(String[] args) {
        System.out.println(isBalanced("{[()]}"));   // true
        System.out.println(isBalanced("{[(])}"));   // false
        System.out.println(isBalanced("(("));       // false
    }
}

10. Interview questions

Q1. What is the Collections Framework? Collection vs Collections?

A unified set of interfaces (List, Set, Queue, Map…), implementations (ArrayList, HashMap…) and algorithms for storing and processing groups of objects. Collection is the root interface for List/Set/Queue; Collections is a utility class with static methods (sort, reverse, unmodifiableList…).

Q2. ArrayList vs LinkedList?

ArrayList is backed by a resizable array: O(1) random access, O(n) inserts/removes in the middle/front because of shifting, compact memory. LinkedList is a doubly-linked list: O(1) add/remove at the ends, O(n) access by index, more memory per element. ArrayList is the default choice; for queues/stacks use ArrayDeque.

Q3. List vs Set vs Map?

List: ordered, allows duplicates, index-based. Set: no duplicates (by equals/hashCode or comparison). Map: key-value pairs with unique keys; it doesn't extend Collection.

Q4. HashSet vs LinkedHashSet vs TreeSet (and the same for maps)?

Hash*: O(1) operations, no ordering guarantee, allows one null. LinkedHash*: same speed plus predictable insertion order (maintains a linked list). Tree*: sorted by natural order or a Comparator, O(log n), no null keys, offers navigation methods (first, ceiling, headSet…).

Q5. How does HashMap work internally?

It keeps an array of buckets. put computes the key's hashCode, spreads it, and maps it to a bucket index. Entries with the same bucket form a linked list (converted to a red-black tree when a bucket has 8+ entries, Java 8+). get finds the bucket the same way and uses equals to locate the key. Default capacity 16, load factor 0.75; when the size exceeds capacity × load factor, the table doubles and entries are rehashed.

Q6. What is the equals/hashCode contract and what happens if you break it?

If a.equals(b) then a.hashCode() == b.hashCode() must hold (the reverse isn't required). If you override equals without hashCode, equal objects land in different buckets: HashMap lookups fail and HashSet allows logical duplicates.

Q7. What is ConcurrentModificationException and how do you avoid it?

Thrown by fail-fast iterators when a collection is structurally modified during iteration other than through the iterator itself (e.g. list.remove inside a for-each). Avoid it with Iterator.remove(), removeIf, iterating over a copy, or, for multi-threaded code, concurrent collections like CopyOnWriteArrayList / ConcurrentHashMap (whose iterators are fail-safe/weakly consistent).

Q8. Comparable vs Comparator?

Comparable (compareTo) defines the single natural ordering inside the class itself. Comparator (compare) defines external, alternative orderings and can be combined (thenComparing, reversed). Use Comparable for the obvious default, Comparator for everything else or for classes you can't modify.

Q9. What's the difference between List.of, Collections.unmodifiableList and Arrays.asList?

List.of: truly immutable, no nulls. unmodifiableList: a read-only view — changes to the underlying list are visible through it. Arrays.asList: fixed-size list backed by the array — set works, add/remove throw UnsupportedOperationException.

Q10. Which collection would you use for: a cache of user sessions by id, a leaderboard, an undo feature, a job queue?

Sessions by id: HashMap (or ConcurrentHashMap if multi-threaded). Leaderboard: TreeMap/TreeSet with a comparator, or sort a list. Undo: ArrayDeque as a stack. Job queue: ArrayDeque (FIFO) or PriorityQueue if jobs have priorities.
