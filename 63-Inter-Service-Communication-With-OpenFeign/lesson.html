1. Why this matters

In a microservice system, services talk to each other all day long. An order service must ask the product service for prices. A payment service must ask the user service for an address. A shipping service must tell the notification service to send an SMS.

In topic 59 you wrote these calls by hand with RestClient: build the URL, set the method, send, read the body, convert JSON, check the status code… For one call it is fine. But a real company service may call 10 other services with 50 different endpoints. All that “plumbing” code is boring, repeated and easy to get wrong.

OpenFeign removes the plumbing. You write a small Java interface that describes the remote API, and Spring generates the real HTTP code for you at startup. Your business code then simply calls productClient.getProductById(1L) — as if the product service were a local class.

ℹ️ Where you will see this at work Feign has been the most popular way to do service-to-service calls in Spring Cloud projects for almost 10 years. Banks, e-commerce sites and telecom companies running Spring Cloud almost always have @FeignClient interfaces in their code. Even if your new project uses @HttpExchange (the newer Spring way), you will meet Feign in existing code and in interviews.

2. Real-life analogy

📱 Speed dial on your phone To call your mum you do not type +91 98xxx xxxxx every time. You save her once as a contact called “Mum” and then just tap the name. The phone handles the number, the network, the ringing.

A @FeignClient is that contact card:
  • The contact name (“Mum”) = name = "product-service".
  • The phone number saved on the card = the url (or Eureka looks it up for you, like a phone book).
  • Each button on the card (Call, Message, Video) = each method in the interface (getProductById, reduceStock…).
  • “The number you are calling is not reachable” = an exception that your ErrorDecoder turns into a clear message.
  • “Hang up if nobody answers in 20 seconds” = the read timeout.
You think about whom you call and why — never about the wires.

3. Concepts step by step

3.1 The problem: hand-written HTTP calls

Here is how order-service would fetch a product with RestClient (topic 45). It works, but count the technical details you must remember each time:

ProductResponse product = restClient.get()
        .uri("http://localhost:8081/api/products/{id}", id)   // host, port, path
        .retrieve()
        .onStatus(status -> status.value() == 404,               // error handling
                  (req, res) -> { throw new ProductNotFoundException("..."); })
        .body(ProductResponse.class);                            // JSON -> Java

Now repeat this for getAllProducts, reduceStock, searchProducts… in every service. That is the pain Feign solves.

3.2 What is a declarative HTTP client?

Imperative = you tell the computer how to do something, step by step. Declarative = you only say what you want, and a framework works out the how.

With Feign you declare the remote API:

@FeignClient(name = "product-service", url = "http://localhost:8081")
public interface ProductClient {

    @GetMapping("/api/products/{id}")
    ProductResponse getProductById(@PathVariable("id") Long id);
}

That is the whole client. No class implements this interface — Spring creates a hidden object (a proxy, the same idea as AOP proxies in topic 27) that does the HTTP work whenever you call a method.

ℹ️ A little history (useful for interviews)
  • Feign was created at Netflix (around 2013) — like Eureka.
  • It moved to the community and was renamed OpenFeign (io.github.openfeign).
  • Spring Cloud OpenFeign is the Spring integration: it lets you use the familiar Spring MVC annotations (@GetMapping, @PathVariable…), Spring's JSON converters, Spring Cloud LoadBalancer and Spring Boot config.
  • Today the Spring team calls Spring Cloud OpenFeign “feature complete”: it is maintained and fully supported, but new features go into Spring's own @HttpExchange interfaces. Still very widely used.

            <type>pom</type>

Step 2 — switch Feign on with @EnableFeignClients on your main class. It tells Spring: “scan this package and its sub-packages for @FeignClient interfaces and create a bean for each one”.

public class OrderServiceApplication { ... }

Step 3 — write the interface with @FeignClient and inject it wherever you need it (constructor injection, as always).

3.6 Writing the interface methods

You use the same annotations as in a controller, but “from the other side”: in a controller they read the request, in a Feign client they build the request.

@FeignClient(name = "product-service", url = "${clients.product-service.url:}", path = "/api/products")
public interface ProductClient {

    @GetMapping                                   // GET /api/products
    List<ProductResponse> getAllProducts();

    @GetMapping("/{id}")                          // GET /api/products/7
    ProductResponse getProductById(@PathVariable("id") Long id);

    @GetMapping("/search")                        // GET /api/products/search?name=mouse&page=0
    List<ProductResponse> search(@RequestParam("name") String name,
                                 @RequestParam("page") int page);

    @PostMapping                                  // POST /api/products  with JSON body
    ProductResponse create(@RequestBody CreateProductRequest body);

    @GetMapping("/{id}")                          // send a header too
    ProductResponse getWithHeader(@PathVariable("id") Long id,
                                  @RequestHeader("X-Request-Id") String requestId);

    @GetMapping("/{id}")                          // need status code + headers? return ResponseEntity
    ResponseEntity<ProductResponse> getRaw(@PathVariable("id") Long id);
}
⚠️ Always write the name inside @PathVariable("id") and @RequestParam("name") In a controller Spring can often guess the name from the parameter. In a Feign interface it frequently cannot, and you get IllegalStateException: PathVariable annotation was empty on param 0 at startup. Writing the name is a 2-second habit that avoids it.

3.7 Feign + Eureka = client-side load balancing

Remember topic 60: services register in Eureka, and a @LoadBalanced client can call http://product-service/... by name. Feign does that automatically when the url attribute is empty:

In this topic's code the URL comes from a property, so the project runs without Eureka by default:

order-service/src/main/resources/application.yml (parts)clients:

The eureka client starter (already in the pom) brings Spring Cloud LoadBalancer with it. Default strategy: round robin (take turns).

3.8 Error handling — FeignException and the ErrorDecoder

When the remote service answers with a 4xx or 5xx status, Feign by default throws a FeignException sub-class: FeignException.NotFound (404), FeignException.BadRequest (400), FeignException.InternalServerError (500)… Your service code would then be full of catch (FeignException.NotFound e) blocks. Better: translate once, in an ErrorDecoder.

ProductClientErrorDecoder.java (short)public class ProductClientErrorDecoder implements ErrorDecoder {

    private final ErrorDecoder defaultDecoder = new ErrorDecoder.Default();

    @Override
    public Exception decode(String methodKey, Response response) {
        return switch (response.status()) {
            case 404 -> new ProductNotFoundException("Product not found in product-service");
            case 409 -> new OutOfStockException("Not enough stock in product-service");
            case 500, 502, 503, 504 -> new ProductServiceUnavailableException("...");
            default  -> defaultDecoder.decode(methodKey, response);   // let Feign handle the rest
        };
    }
}
ℹ️ Two very different kinds of failure
  • The server answered with an error (404, 500…) → the ErrorDecoder is called.
  • No answer at all (service not running = “connection refused”, or slower than the read timeout) → there is no response to decode. Feign throws feign.RetryableException. Handle it in your @RestControllerAdvice (we return 504 Gateway Timeout), or — much better — use a circuit breaker (topic 64).

3.9 Timeouts — never wait forever

A connect timeout limits how long we try to open the connection (“is anybody there?”). A read timeout limits how long we wait for the answer once connected.

spring:
  cloud:
    openfeign:
      client:
        config:
          default:                 # all Feign clients
            connect-timeout: 2000  # milliseconds
            read-timeout: 5000
          product-service:         # only this client (overrides default)
            connect-timeout: 1000
            read-timeout: 2000

Why so important? Each waiting call blocks one Tomcat thread. If product-service hangs and you wait 60 seconds per call, a few hundred users can use up all threads of order-service — now order-service is “down” too. That chain reaction is called a cascading failure (deep dive in topic 64).

3.11 RequestInterceptor — add something to every request

An interceptor runs before every request of a client. Typical uses: pass the user's JWT token along (topic 49), add an API key, add a correlation id (topic 65).

@Bean
public RequestInterceptor callerHeaderInterceptor() {
    return template -> template.header("X-Caller-Service", "order-service");
}

// Real-life example: forward the incoming JWT to the next service
@Bean
public RequestInterceptor bearerTokenForwarder() {
    return template -> {
        var attrs = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
        if (attrs != null) {
            String auth = attrs.getRequest().getHeader("Authorization");
            if (auth != null) template.header("Authorization", auth);
        }
    };
}

3.12 Configuration: YAML or Java, global or per client

🚨 The @Configuration trap The class you pass to @FeignClient(configuration = ...) should not have @Configuration (or must live outside the component-scan packages). If component scanning picks it up, its beans become global and silently apply to every Feign client — e.g. your product ErrorDecoder would also decode errors from the payment service.

If the same setting is in YAML and Java, YAML wins by default (spring.cloud.openfeign.client.default-to-properties=true).

3.13 Retries

Spring Cloud OpenFeign uses Retryer.NEVER_RETRY by default — a failed call is not repeated. You can add a bean new Retryer.Default(100, 1000, 3) (start 100 ms, max 1 s, 3 attempts), but most teams prefer Resilience4j's @Retry (next topic) because it combines nicely with a circuit breaker.

⚠️ Only retry safe operations Retrying GET is safe. Retrying POST /reduce-stock may reduce the stock twice if the first call actually succeeded but the answer got lost. That is why idempotency (topic 32/44) matters.

3.14 A preview: Feign with a fallback

With spring-cloud-starter-circuitbreaker-resilience4j on the classpath and spring.cloud.openfeign.circuitbreaker.enabled=true, Feign can call a fallback class when the remote call fails:

@FeignClient(name = "product-service", fallback = ProductClientFallback.class)
public interface ProductClient { ... }

@Component
class ProductClientFallback implements ProductClient {
    @Override
    public ProductResponse getProductById(Long id) {
        return new ProductResponse(id, "Unknown product", 0, 0);   // safe default
    }
    // ... other methods
}

Topic 64 explains circuit breakers properly — for now just know the door exists.

3.15 Feign vs RestClient vs @HttpExchange

Since Spring 6 you can also write a declarative interface without Spring Cloud, using @HttpExchange (you saw it in topic 45). The same product client looks like this:

@HttpExchange("/api/products")
public interface ProductHttpClient {
    @GetExchange("/{id}")
    ProductResponse getProductById(@PathVariable Long id);
}

@Bean
ProductHttpClient productHttpClient(RestClient.Builder builder) {
    RestClient restClient = builder.baseUrl("http://localhost:8081").build();
    return HttpServiceProxyFactory.builderFor(RestClientAdapter.create(restClient))
            .build()
            .createClient(ProductHttpClient.class);
}

4.1 The Feign client

order-service/src/main/java/com/course/feign/order/client/ProductClient.java@FeignClient(
        name = "product-service",
        url = "${clients.product-service.url:}",
        path = "/api/products",
        configuration = ProductClientConfig.class)
public interface ProductClient {

    @GetMapping
    List<ProductResponse> getAllProducts();

    @GetMapping("/{id}")
    ProductResponse getProductById(@PathVariable("id") Long id);

    @GetMapping("/{id}")
    ProductResponse getProductSlowly(@PathVariable("id") Long id, @RequestParam("delayMs") long delayMs);

    @PostMapping("/{id}/reduce-stock")
    ProductResponse reduceStock(@PathVariable("id") Long id, @RequestParam("quantity") int quantity);
}
  • url = "${clients.product-service.url:}" — the part after the colon is the default value; here it is empty. So if the property is missing or blank, Feign falls back to the load balancer.
  • path — saves us from writing /api/products four times.
  • getProductSlowly — the same endpoint with an extra query parameter. Two Java methods may map to the same URL; Feign does not care.
  • ProductResponse is order-service's own record. We do not import product-service's class — services stay independent and can be deployed separately.

4.3 The error decoder

Besides the switch you saw in 3.8, it reads the error body for the log. Note response.body() is a stream that can be read only once, and it may be null:

private String readBody(Response response) {
    if (response.body() == null) {
        return "";
    }
    try (Reader reader = response.body().asReader(StandardCharsets.UTF_8)) {
        return Util.toString(reader);
    } catch (IOException e) {
        return "<unreadable body>";
    }
}

4.4 The service — remote calls that look local

order-service/…/service/OrderService.java (core)public OrderResponse placeOrder(OrderRequest request) {
    // Remote call #1 (404 -> ProductNotFoundException thanks to the ErrorDecoder)
    ProductResponse product = productClient.getProductById(request.productId());

    if (product.stock() < request.quantity()) {
        throw new OutOfStockException("Only " + product.stock() + " left of '" + product.name() + "'");
    }

    // Remote call #2 (409 -> OutOfStockException)
    ProductResponse updated = productClient.reduceStock(product.id(), request.quantity());

    long orderId = idSequence.incrementAndGet();
    OrderResponse order = new OrderResponse(orderId, product.id(), product.name(),
            request.quantity(), product.price() * request.quantity(), updated.stock(), "CONFIRMED");
    orders.put(orderId, order);
    return order;
}
ℹ️ Why check stock twice? The local check gives a fast, friendly message. But between our check and our reduceStock call another customer could buy the last item — so product-service checks again (409). The owner of the data always has the final word. (Making the two calls one atomic action across services is the job of the Saga pattern.)

6. Common mistakes

⚠️ Mistake: forgetting @EnableFeignClients Error: No qualifying bean of type 'ProductClient' available.
Fix: add @EnableFeignClients to the main class, and keep the Feign interfaces in the same package or a sub-package (or use @EnableFeignClients(basePackages = "...")).
⚠️ Mistake: @PathVariable without a name Error at startup: PathVariable annotation was empty on param 0.
Fix: @PathVariable("id") Long id, @RequestParam("quantity") int quantity.
⚠️ Mistake: no url and no Eureka Error: Load balancer does not contain an instance for the service product-service.
Fix: either set url, or make sure Eureka is running and product-service is registered (check the dashboard on :8761).
⚠️ Mistake: “logger-level: full but I see nothing” Fix: also set logging.level.<your.client.Interface>=DEBUG.
🚨 Mistake: @Configuration on the per-client config class Its ErrorDecoder/interceptors suddenly apply to every Feign client — strange errors in unrelated calls.
Fix: remove @Configuration, reference it only via @FeignClient(configuration = ...).
⚠️ Mistake: version mismatch Writing a version on spring-cloud-starter-openfeign or using a Spring Cloud release that does not fit Spring Boot 3.5 → ClassNotFoundException/NoSuchMethodError at startup.
Fix: import the Spring Cloud BOM 2025.0.0 (made for Boot 3.5) and do not write versions on Spring Cloud starters.
⚠️ Mistake: sharing a “common-models” jar between services It feels like less typing, but now changing a class in product-service forces a release of order-service.
Fix: each service keeps its own small DTOs (ProductResponse). Only copy the fields you need.
⚠️ Mistake: treating a Feign call like a local call It looks like a normal method, so people call it inside loops (for each item → productClient.getProductById) — 100 items = 100 network calls.
Fix: add a batch endpoint (GET /api/products?ids=1,2,3) and call it once.

7. Best practices

  • Always set timeouts — per client, based on how fast that service normally is (e.g. 2–5 s, never “infinite”).
  • Translate errors with an ErrorDecoder and never leak FeignException details (internal URLs!) to your own clients.
  • Protect calls with a circuit breaker + fallback (topic 64). A slow dependency must not take you down.
  • Log BASIC in production, FULL only locally — bodies may contain personal data.
  • Pass security context along with a RequestInterceptor (JWT) or use service-to-service OAuth2 client credentials.
  • Keep the URL in configuration, never hard-coded; use Eureka/Kubernetes DNS names in real environments.
  • Retry only idempotent calls (GET, PUT with full replace) or use idempotency keys for POST.
  • Version your APIs (/api/v1/...) so a provider can change without breaking its consumers; consider contract tests (Spring Cloud Contract, Pact).
  • One Feign interface per remote service, named after it (ProductClient, PaymentClient), in a client package.
  • For new projects, also evaluate @HttpExchange — Spring's actively developed declarative client.
  • Prefer a production-grade HTTP client (add io.github.openfeign:feign-hc5 for Apache HttpClient 5 with connection pooling) for high traffic.

8. Key takeaways

  • OpenFeign = declarative HTTP client: write an interface, Spring generates the implementation (a proxy).
  • Setup: spring-cloud-starter-openfeign + Spring Cloud BOM + @EnableFeignClients + @FeignClient.
  • Use Spring MVC annotations in the interface; always name @PathVariable/@RequestParam.
  • Empty url → name resolved via Spring Cloud LoadBalancer + Eureka (round robin).
  • ErrorDecoder handles 4xx/5xx; RetryableException means no answer (down / timeout).
  • Set connect/read timeouts per client in YAML; logging needs logger-level and DEBUG.
  • RequestInterceptor adds headers (auth, correlation id) to every call.
  • Per-client config classes must not be picked up by component scanning.
  • Feign is feature complete; @HttpExchange is Spring's modern alternative.

10. Interview questions

Q1. What is OpenFeign and why would you use it?

A declarative HTTP client. You describe a remote REST API with a Java interface and annotations, and Spring Cloud OpenFeign generates a proxy implementation at runtime. It removes boilerplate (URL building, JSON conversion, error handling) and integrates with Spring MVC annotations, Spring Cloud LoadBalancer/Eureka, Spring Boot configuration and circuit breakers.

Q2. How does Feign create an implementation for an interface?

@EnableFeignClients registers a FeignClientFactoryBean for each @FeignClient interface. At startup it builds a JDK dynamic proxy. When a method is called, the proxy uses the Contract (SpringMvcContract) to read the annotations, builds a RequestTemplate, applies interceptors, encodes the body, sends it via the configured Client, then decodes the response or calls the ErrorDecoder.

Q3. How does Feign do load balancing?

If url is not set, the name is treated as a service id. Feign wraps its client in a load-balancing client that asks Spring Cloud LoadBalancer for an instance; the LoadBalancer gets the instance list from a discovery client (Eureka, Consul, Kubernetes) and picks one (round robin by default). This is client-side load balancing — no extra hop through a load-balancer server.

Q4. How do you handle errors from a Feign client?

Implement ErrorDecoder to map HTTP status codes to domain exceptions (404 → NotFound, 409 → Conflict, 5xx → Unavailable) and register it globally or per client. Connection failures and read timeouts produce RetryableException — handle them with a circuit breaker/fallback or an exception handler. Never expose raw Feign errors to your own API clients.

Q5. How do you configure timeouts in Spring Cloud OpenFeign?

With spring.cloud.openfeign.client.config.default.connect-timeout/read-timeout for all clients, or ...config.<clientName>.* for one client; or with a Request.Options bean in a configuration class. Connect timeout = time to establish the TCP connection; read timeout = time to wait for data.

Q6. What are the Feign logger levels and what is the gotcha?

NONE, BASIC, HEADERS, FULL. Feign logs at DEBUG level using the client interface's logger, so you must also set logging.level.<client-interface>=DEBUG, otherwise nothing appears.

Q7. Why should a Feign configuration class not be annotated with @Configuration?

Classes referenced in @FeignClient(configuration=...) are loaded into a child context for that client. If component scanning also picks them up (because of @Configuration in a scanned package), their beans land in the main context and become the default for all Feign clients.

Q8. Feign vs RestTemplate vs RestClient vs WebClient vs @HttpExchange?

RestTemplate: old blocking template API (maintenance mode). RestClient: modern fluent blocking client (Spring 6.1). WebClient: reactive, non-blocking. @HttpExchange: Spring's own declarative interfaces, running on RestClient or WebClient. Feign: Spring Cloud's declarative client with YAML config and built-in discovery integration, feature complete. For new code Spring recommends RestClient or @HttpExchange; Feign remains common in existing Spring Cloud systems.

Q9. Does Feign retry failed requests?

In Spring Cloud OpenFeign the default Retryer is NEVER_RETRY. You can register Retryer.Default, but retries are usually done with Resilience4j @Retry, and only for idempotent operations.

Q10. How do you pass the user's JWT from one service to the next with Feign?

Register a RequestInterceptor that reads the Authorization header of the current incoming request (via RequestContextHolder, or the SecurityContext) and adds it to the outgoing RequestTemplate. For calls not triggered by a user, use OAuth2 client-credentials tokens instead.
