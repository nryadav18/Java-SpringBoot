36. Thymeleaf — Server-Side Web Apps

Build a complete Todo web application where Spring Boot itself produces the HTML pages — with lists, links, forms, validation messages, a shared layout and CSS.

1. Why this matters

So far our apps returned JSON. Somebody else (a React app, a mobile app) had to turn that JSON into screens. But many real applications don't need a separate front-end at all:

  • Admin panels and back-office tools ("approve these 20 leave requests").
  • Internal company apps: HR forms, inventory screens, reports.
  • Simple public sites: a booking form, a blog, a "contact us" page.
  • Emails: Thymeleaf is also used to build nice HTML emails (topic 54).

For these, having the server produce finished HTML pages is simpler and faster to build: one project, one language (Java), no JavaScript build tools. Thymeleaf is the template engine recommended by Spring Boot and is used in many companies. Even if you mostly build REST APIs, you will meet Thymeleaf in admin screens and email templates — and this topic teaches the classic Spring MVC request cycle (model, view, forms, redirects) that every Spring developer should know.

2. Real-life analogy

📮 Mail merge for letters Imagine an office sending 500 letters. Someone writes one letter template: "Dear [name], your order [order no] ships on [date]." A machine then fills in the blanks for each customer and prints the finished letters.
  • The template = a Thymeleaf .html file with placeholders like th:text="${todo.title}".
  • The customer data = the Model your controller fills.
  • The machine = the Thymeleaf engine.
  • The printed letter = the final HTML the browser receives. The customer never sees the placeholders.
With a REST API + SPA, by contrast, the server sends only the data (the customer list) and the customer's own printer (JavaScript in the browser) builds the letter.

3. Concepts step by step

3.1 Server-side rendering (SSR) vs REST + SPA

Browser: GET /todos→ @Controller fills Model→ Thymeleaf merges template + Model→ Complete HTML page
Browser loads JS app once→ JS calls GET /api/todos→ @RestController returns JSON→ JS builds the HTML in the browser
Server-side rendering (Thymeleaf)REST API + SPA (React/Angular/Vue)
Who builds the HTML?The server, on every requestJavaScript in the browser
What travels over the networkWhole HTML pagesJSON data (after the first page load)
Projects / languagesOne project, Java + HTMLTwo projects, Java + JavaScript/TypeScript
FeelFull page reload on each click/submitSmooth, app-like, no reloads
SEO & first loadExcellent (HTML is ready immediately)Needs extra work (SSR frameworks)
Mobile apps can reuse it?No — HTML is for browsersYes — the same JSON API serves web and mobile
Best forAdmin panels, internal tools, forms, simple sites, emailsRich interactive apps, multiple clients, separate front-end teams
ℹ️ It's not either-or Many apps mix both: Thymeleaf pages with small bits of JavaScript, or libraries like htmx that update parts of a Thymeleaf page without a full reload. And one Spring Boot app can contain both @Controller (HTML) and @RestController (JSON) classes.

3.3 @Controller, view names and the Model

In REST topics we used @RestController: the return value is the response body (JSON). A plain @Controller is different: a returned String is a view name.

@Controller                                   // NOT @RestController
public class TodoController {

    @GetMapping("/todos")
    public String list(Model model) {
        model.addAttribute("todos", todoService.findAll("all"));  // put data in the "bag"
        model.addAttribute("openCount", todoService.countOpen());
        return "todos/list";                  // view name -> templates/todos/list.html
    }
}
GET /todos→ DispatcherServlet→ TodoController.list()
returns "todos/list" + Model→ ViewResolver
finds templates/todos/list.html→ Thymeleaf renders→ HTML response
  • Model is like a Map<String, Object> — a bag of named values. The template reads them with ${todos}, ${openCount}.
  • View name = path inside templates/ without .html.
  • Special prefix "redirect:/todos" tells the browser to go to another URL (more in 3.8).
⚠️ @RestController by mistake If you write @RestController and return "todos/list", the browser shows the literal text todos/list. Use @Controller for pages.

3.4 Thymeleaf basics: natural templates and expressions

A Thymeleaf template is a normal HTML file with extra th:* attributes. You declare the namespace once so editors don't complain:

<html lang="en" xmlns:th="http://www.thymeleaf.org">

Thymeleaf replaces the normal content with dynamic content. Because the file is still valid HTML, you can open it directly in a browser and see sample content — this is called a natural template:

<span th:text="${todo.title}">Buy milk</span>
<!-- in the browser file preview: "Buy milk";  when rendered by Spring: the real title -->
ExpressionNameMeaningExample
${...}VariableRead from the Model (dot = getter)${todo.title} → todo.getTitle()
*{...}SelectionProperty of the object chosen with th:object*{title}
@{...}Link URLBuilds URLs (adds context path, encodes params)@{/todos/{id}/edit(id=${todo.id})}
~{...}FragmentRefers to a reusable piece of a template~{fragments/layout :: navbar}
#{...}MessageText from messages.properties (i18n)#{app.title}
|...|Literal substitutionMix text and expressions easily|${openCount} open|

Helper objects start with #: #strings, #lists, #numbers, #temporals (for java.time), #fields (form errors), #ids.

3.5 th:text — showing values safely

<h1>My Todos <small th:text="|${openCount} open|">2 open</small></h1>
<small th:text="|Due ${#temporals.format(todo.dueDate, 'dd MMM yyyy')}|">Due 01 Jan 2030</small>

th:text escapes HTML: if a user types <script>alert(1)</script> as a title, it is shown as text, not executed. This protects you from XSS (cross-site scripting) attacks. th:utext ("unescaped text") does not escape — only use it for HTML you fully trust.

3.6 th:each — loops

<ul>
  <li th:each="todo, stat : ${todos}" th:classappend="${todo.done} ? 'done'">
    <span th:text="${stat.count} + '.'">1.</span>
    <span th:text="${todo.title}">Buy milk</span>
  </li>
</ul>

The <li> is repeated once per todo — like a Java for-each loop: for (Todo todo : todos). The optional second variable (stat) is the iteration status:

PropertyMeaning
stat.index / stat.countPosition starting at 0 / at 1
stat.sizeTotal number of items
stat.first / stat.lastIs this the first / last item?
stat.odd / stat.evenHandy for striped tables

th:classappend adds a CSS class when a condition is true (the done item gets class="todo done" and is crossed out by the CSS).

3.7 th:if / th:unless — conditions

<p th:if="${#lists.isEmpty(todos)}">Nothing here. Add your first todo 🎉</p>
<ul th:unless="${#lists.isEmpty(todos)}"> ... </ul>

<span class="badge overdue" th:if="${todo.overdue}">Overdue</span>   <!-- calls isOverdue() -->

If the condition is false, the whole element (and everything inside) is removed from the output. th:unless is simply "if not". There's also th:switch/th:case for several options.

💡 Truthiness th:if treats null, false, the number 0 and the strings "false", "off", "no" as false. An empty string is true! For optional text use th:unless="${#strings.isEmpty(todo.description)}".

3.8 th:href and @{...} — links

<a th:href="@{/todos/new}">+ New todo</a>                               <!-- /todos/new -->
<a th:href="@{/todos(filter='active')}">Active</a>                       <!-- /todos?filter=active -->
<a th:href="@{/todos/{id}/edit(id=${todo.id})}">Edit</a>                <!-- /todos/3/edit -->
<link rel="stylesheet" th:href="@{/css/app.css}">                         <!-- static CSS -->

Values in parentheses become either path variables (if the URL has a matching {id}) or query parameters. @{...} also adds the application's context path automatically (e.g. if the app is deployed under /shop), so never hard-code href="/todos".

3.9 Forms: th:object and th:field

A form needs a form-backing object — a Java object whose properties match the form fields. Ours is TodoForm (a class with a no-arg constructor, getters and setters, plus validation annotations).

@GetMapping("/todos/new")
public String newForm(Model model) {
    model.addAttribute("todoForm", new TodoForm());   // an empty object to fill the form
    return "todos/form";
}
templates/todos/form.html (simplified)<form th:action="@{/todos}" th:object="${todoForm}" method="post">
    <input type="text" th:field="*{title}">
    <textarea th:field="*{description}"></textarea>
    <select th:field="*{priority}">
        <option th:each="p : ${priorities}" th:value="${p}" th:text="${p.label}">Medium</option>
    </select>
    <input type="date" th:field="*{dueDate}">
    <button type="submit">Add todo</button>
</form>

th:field="*{title}" does three jobs at once. It renders:

<input type="text" id="title" name="title" value="(current value of todoForm.title)">
  • name="title" — so the browser sends title=... when submitting.
  • value="..." — so the field is pre-filled (important for edit forms and when re-showing a form after errors).
  • For <select> it marks the right option selected; for checkboxes it adds checked and a hidden _done field so "unchecked" is also detected.

When the user submits, Spring creates a TodoForm, calls setTitle(...), setPriority(...) etc. (this is called data binding) and passes it to your method:

@PostMapping("/todos")
public String create(@Valid @ModelAttribute("todoForm") TodoForm form, BindingResult bindingResult, ...) { ... }

Note: HTML forms send application/x-www-form-urlencoded data (title=Buy+milk&priority=HIGH), not JSON. So we use @ModelAttribute, not @RequestBody.

ℹ️ Dates and enums <input type="date"> sends 2026-12-31. @DateTimeFormat(iso = DateTimeFormat.ISO.DATE) on the LocalDate field tells Spring how to convert it (and how to display it again). Enums are converted automatically from their name ("HIGH" → Priority.HIGH).

3.10 Validation errors in forms

The same annotations from topic 34 work on TodoForm (@NotBlank, @Size, @FutureOrPresent…). The difference: instead of a 400 JSON response, we want to show the form again with red messages. The key is BindingResult:

@PostMapping("/todos")
public String create(@Valid @ModelAttribute("todoForm") TodoForm form,
                     BindingResult bindingResult,          // MUST be right after the @Valid parameter
                     Model model, RedirectAttributes redirectAttributes) {
    if (bindingResult.hasErrors()) {
        return "todos/form";        // show the same page; the form + errors are still in the model
    }
    todoService.create(form);
    redirectAttributes.addFlashAttribute("successMessage", "Todo was added.");
    return "redirect:/todos";
}
  • If a BindingResult parameter is present, Spring does not throw an exception on validation failure — it puts the errors into bindingResult and lets you decide.
  • It must come immediately after the validated object; otherwise Spring throws MethodArgumentNotValidException/BindException and you get an error page.

In the template, the #fields helper shows the errors:

<input type="text" th:field="*{title}" th:errorclass="invalid">
<p class="error" th:if="${#fields.hasErrors('title')}" th:errors="*{title}">Title is required</p>
  • th:errors="*{title}" prints the message(s) for that field (e.g. "Please enter a title").
  • th:errorclass="invalid" adds a CSS class only when the field has errors → red border.
  • ${#fields.hasGlobalErrors()} / ${#fields.globalErrors()} show errors not tied to one field.

Business rules that need data (e.g. "you already have a todo with this title") can be added manually:

if (todoService.titleExists(form.getTitle(), null)) {
    bindingResult.rejectValue("title", "duplicate", "You already have a todo with this title");
}

3.11 POST-Redirect-GET (PRG)

Problem: after submitting a form, if the server directly returns a page and the user presses F5 (refresh), the browser asks "Resubmit the form?" — and a second todo (or a second payment!) is created.

Solution: after a successful POST, don't render a page — redirect:

1. POST /todos
form data→ 2. Server saves,
answers 302 Location: /todos→ 3. Browser automatically
GET /todos→ 4. List page shown.
F5 only repeats the harmless GET

In Spring: return "redirect:/todos";

Flash attributes — messages that survive a redirect

A redirect is a brand-new request, so the Model is empty again. To show "Todo was added." on the list page, use a flash attribute: Spring stores it briefly in the HTTP session, puts it into the model of the next request, then deletes it.

redirectAttributes.addFlashAttribute("successMessage", "Todo 'Buy milk' was added.");  // survives one redirect
redirectAttributes.addAttribute("filter", "active");   // becomes a URL parameter: /todos?filter=active
💡 Rule Validation failed → render the form again (keep the user's input, show errors). Success → redirect.

And remember: anything that changes data (create, toggle, delete) must use a POST form, never a plain GET link — browsers, search engines and link previewers follow GET links freely. HTML forms only support GET and POST, so "delete" is POST /todos/{id}/delete here.

3.12 Layout fragments — write the header once

Every page needs the same <head>, navbar and footer. Copying them is a maintenance nightmare. Define them once as fragments:

templates/fragments/layout.html<head th:fragment="head(pageTitle)">                      <!-- fragment with a parameter -->
    <meta charset="UTF-8">
    <title th:text="${pageTitle} + ' · Todo App'">Todo App</title>
    <link rel="stylesheet" th:href="@{/css/app.css}">
</head>

<nav class="navbar" th:fragment="navbar">
    <a class="brand" th:href="@{/todos}">✅ Todo App</a>
    <a class="btn" th:href="@{/todos/new}">+ New todo</a>
</nav>

<div th:fragment="flash" th:if="${successMessage}" class="flash" th:text="${successMessage}">Saved!</div>

…and include them in each page:

<head th:replace="~{fragments/layout :: head('My Todos')}"></head>
<nav th:replace="~{fragments/layout :: navbar}"></nav>
<div th:replace="~{fragments/layout :: flash}"></div>
AttributeEffect
th:replaceReplaces the host tag completely with the fragment (most common)
th:insertKeeps the host tag and puts the fragment inside it
ℹ️ Layout Dialect For a "master page" where each page only fills a content area, many projects add the Thymeleaf Layout Dialect library (layout:decorate, layout:fragment). Plain fragments, as shown here, need no extra library and are enough for most apps.

3.13 Static resources and error pages

  • Anything in src/main/resources/static/ is served as-is: static/css/app.css → http://localhost:8080/css/app.css. Same for images and .js files. No controller needed.
  • When a browser request fails with 404, Spring Boot looks for templates/error/404.html (then error/4xx.html, then error.html) before showing the "Whitelabel Error Page". Our TodoNotFoundException has @ResponseStatus(NOT_FOUND), so /todos/99/edit shows our friendly page.

4.1 The controller

controller/TodoController.java (key parts)@Controller
public class TodoController {

    @ModelAttribute("priorities")             // runs before EVERY handler in this class
    public Priority[] priorities() {
        return Priority.values();             // the form's dropdown always has its options
    }

    @GetMapping("/todos")
    public String list(@RequestParam(defaultValue = "all") String filter, Model model) {
        model.addAttribute("todos", todoService.findAll(filter));
        model.addAttribute("filter", filter);
        model.addAttribute("openCount", todoService.countOpen());
        return "todos/list";
    }

    @GetMapping("/todos/{id}/edit")
    public String editForm(@PathVariable Long id, Model model) {
        model.addAttribute("todoForm", todoService.toForm(todoService.findById(id)));  // pre-filled
        model.addAttribute("editMode", true);
        return "todos/form";
    }

    @PostMapping("/todos/{id}/toggle")
    public String toggle(@PathVariable Long id, @RequestParam(defaultValue = "all") String filter,
                         RedirectAttributes redirectAttributes) {
        todoService.toggle(id);
        redirectAttributes.addAttribute("filter", filter);   // back to the same filter
        return "redirect:/todos";
    }
}

Notice how similar this is to a REST controller from topic 33: it calls the same kind of service. Only the output differs (view name + Model instead of a DTO).

    </div>

The condition ? a : b syntax works inside Thymeleaf expressions just like in Java. novalidate switches off the browser's own checks so you can see the server-side validation in action.

6. Common mistakes

⚠️ Mistake: @RestController instead of @Controller The page shows the text "todos/list".
Fix: Use @Controller for HTML views.
⚠️ Mistake: "Error resolving template [todos/lists]" The view name doesn't match a file, or the file is outside templates/.
Fix: View name = path below src/main/resources/templates/ without .html. Check spelling and folders.
⚠️ Mistake: BindingResult in the wrong position create(@Valid TodoForm form, Model model, BindingResult result) → validation errors cause a 400 error page instead of re-showing the form.
Fix: BindingResult must come directly after the validated parameter.
⚠️ Mistake: "Neither BindingResult nor plain target object for bean name 'todoForm' available" The template uses th:object="${todoForm}" but the controller didn't add a todoForm to the model.
Fix: model.addAttribute("todoForm", new TodoForm()) in the GET handler, and use the same name in @ModelAttribute("todoForm").
⚠️ Mistake: redirecting after a validation error return "redirect:/todos/new" loses the user's input and the error messages.
Fix: On errors, return the view name (render); redirect only on success.
⚠️ Mistake: forgetting the dropdown data when re-rendering The form works on GET but after an error the priority list is empty.
Fix: Use a @ModelAttribute method (like priorities()) so the data is added for every request.
🛑 Mistake: th:utext with user input Renders HTML unescaped — a title like <script>...</script> runs in other users' browsers (XSS).
Fix: Always th:text for user data.
⚠️ Mistake: deleting with a GET link <a href="/todos/3/delete"> — a browser prefetch or crawler can delete data.
Fix: Use a small POST form. (With Spring Security, POST forms also get a CSRF token automatically when you use th:action — topic 47.)
⚠️ Mistake: changes to templates don't appear Templates are cached or the old copy in target/classes is used.
Fix: spring.thymeleaf.cache=false in development, save the file (VS Code copies it), refresh. When in doubt, restart. Spring Boot DevTools can automate this.

7. Best practices

  • Thin controllers, logic in services — exactly as in REST apps (topic 33).
  • Use a dedicated form object (TodoForm) instead of binding directly to entities — same "mass assignment" reasons as DTOs.
  • Always PRG: render on errors, redirect on success, and show success with flash attributes.
  • GET never changes data; use POST forms for create/update/delete.
  • Use @{...} for every URL — never hard-code paths.
  • Keep templates dumb: complex logic belongs in Java (e.g. isOverdue() in the model) rather than long expressions in HTML.
  • Use fragments for repeated layout parts; consider the Layout Dialect for bigger apps.
  • Use th:text (escaped) by default — security first.
  • Keep caching on in production (spring.thymeleaf.cache=true is the default).
  • Put user-visible texts in messages.properties and use #{...} if you need multiple languages.
  • Add Spring Security (topics 47–48) before going live: login, CSRF protection for forms.

8. Key takeaways

  • Server-side rendering: the server sends finished HTML; great for admin tools, internal apps and simple sites. REST + SPA: server sends JSON; great for rich apps and multiple clients.
  • spring-boot-starter-thymeleaf; templates in templates/, static files in static/.
  • @Controller methods return a view name; data goes into the Model.
  • ${...} reads model data, *{...} reads the form object, @{...} builds URLs, ~{...} refers to fragments.
  • th:text (escaped), th:each (loops + status), th:if/th:unless, th:href, th:classappend.
  • Forms: th:object + th:field; on submit Spring binds fields to the form object (@ModelAttribute).
  • @Valid + BindingResult (right after it) lets you re-show the form with th:errors.
  • POST-Redirect-GET prevents double submits; flash attributes carry messages across the redirect.
  • Fragments (th:fragment + th:replace) keep layout in one place.

10. Interview questions

Q1. What is the difference between @Controller and @RestController?

@RestController = @Controller + @ResponseBody: return values are written directly into the response body (usually JSON). With @Controller, a returned String is interpreted as a logical view name that a ViewResolver (e.g. Thymeleaf) turns into HTML; you add @ResponseBody per method if you want raw data.

Q2. What is Thymeleaf and what are natural templates?

Thymeleaf is a server-side Java template engine integrated with Spring MVC. Templates are valid HTML files enriched with th:* attributes. "Natural templates" means the files can be opened directly in a browser and show static prototype content, while at runtime Thymeleaf replaces that content with real data.

Q3. What is the Model in Spring MVC?

A map-like container (Model, ModelMap, or ModelAndView) where the controller puts attributes for the view. The view (template) reads them by name, e.g. ${todos}. @ModelAttribute methods add attributes for every request handled by that controller.

Q4. Explain the POST-Redirect-GET pattern.

After a successful form POST, the server responds with a redirect (302/303) to a GET URL instead of rendering a page. The browser then loads that page with GET. Refreshing only repeats the harmless GET, preventing duplicate submissions. Messages are passed across the redirect with flash attributes (RedirectAttributes.addFlashAttribute), stored temporarily in the session.

Q5. How do you display validation errors in a Thymeleaf form?

Annotate the form object with constraints and the handler parameter with @Valid, followed immediately by a BindingResult. If bindingResult.hasErrors(), return the form view again. In the template use th:object/th:field, and th:errors="*{field}" with ${#fields.hasErrors('field')}; th:errorclass adds a CSS class to invalid inputs.

Q6. What is the difference between th:text and th:utext?

th:text HTML-escapes the value, so markup is shown as text — this prevents XSS. th:utext outputs raw, unescaped HTML; only use it for trusted content.

Q7. th:replace vs th:insert?

Both include a fragment. th:replace replaces the host element entirely with the fragment; th:insert keeps the host element and inserts the fragment as its body. (th:include is deprecated.)

Q8. When would you choose server-side rendering over a SPA?

For content- or form-centric applications like admin panels, internal tools, CRUD back-offices, simple public sites and emails: one codebase, fast development, good SEO and first-load performance, no separate front-end build. Choose an SPA with a REST API when you need rich interactivity, offline/app-like behaviour, multiple clients (web + mobile) or separate front-end teams.

Q9. Why can't we use @RequestBody for HTML form submissions?

HTML forms send application/x-www-form-urlencoded (or multipart) data, not JSON. Spring binds such request parameters to an object via data binding with @ModelAttribute (which is also the default for non-simple parameters). @RequestBody uses HttpMessageConverters for bodies like JSON.

Q10. Where do static files and templates go in Spring Boot?

Static files (CSS, JS, images) go to src/main/resources/static/ (also public/, resources/, META-INF/resources/) and are served at the root URL path. Thymeleaf templates go to src/main/resources/templates/ and are only accessible through controllers. Custom error pages go to templates/error/.
