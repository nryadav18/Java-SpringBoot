1. Why this matters

In Topic 9 you compiled a small project by hand: javac -d out src/com/shop/...java, then java -cp out .... Now imagine a real Spring Boot project:

  • It uses 100+ libraries (JAR files): Spring, Jackson, Hibernate, Tomcat, logging, database drivers...
  • Each library needs other libraries, in compatible versions.
  • You must compile, run hundreds of tests, and package everything into one deployable file.
  • Five developers and a CI server (Topic 68) must all build it exactly the same way.

Downloading JARs by hand and typing long javac -cp a.jar;b.jar;c.jar... commands is impossible at that size. A build tool automates all of it. Maven is the most widely used build tool in the Java world (Gradle is the other big one). Every project from Topic 21 to the capstone is a Maven project, and when you create a project on start.spring.io you get a pom.xml.

In job interviews and at work you'll constantly hear: "add the dependency", "run mvn clean install", "check the dependency tree", "the build is failing in the test phase". This lesson makes all of that clear.

2. Real-life analogy

🍰 A recipe card and a smart kitchen
  • pom.xml is a recipe card: the dish's name and version (GAV), the ingredients (dependencies), and the cooking steps (plugins).
  • Maven is a smart kitchen robot that reads the card and does everything: shops for ingredients, prepares, cooks, tastes, and packs the dish in a box.
  • Maven Central is the giant supermarket where every ingredient is sold, with an exact label (groupId, artifactId, version).
  • ~/.m2/repository is your home pantry. Once bought, an ingredient is kept there, so the next recipe that needs it doesn't go shopping again.
  • Transitive dependencies: you buy "cake mix", and it already contains flour and sugar — you didn't list them, but you get them.
  • The lifecycle is the fixed order of cooking: prepare → cook → taste (test) → pack (package) → put in the fridge (install). Asking for "pack" automatically does all the steps before it.
  • A parent POM is a family cookbook: shared rules ("always use these brands, in these quantities") that every recipe in the family inherits. The Spring Boot parent is exactly that.

3. Concepts step by step

3.1 What a build tool does

Maven's philosophy is "convention over configuration": if you put files in the standard places, Maven already knows what to do. You only configure the exceptions. (Spring Boot follows the same philosophy.)

3.2 The standard directory layout

my-project/
├── pom.xml                      ← the recipe (project description)
├── mvnw, mvnw.cmd, .mvn/        ← Maven Wrapper (optional, recommended)
├── src/
│   ├── main/
│   │   ├── java/                ← your application code (packages inside)
│   │   │   └── com/course/mavendemo/App.java
│   │   └── resources/           ← non-Java files that go on the classpath
│   │       └── app.properties       (Spring: application.properties, templates, static files)
│   └── test/
│       ├── java/                ← test code (same packages as main)
│       │   └── com/course/mavendemo/LabelFormatterTest.java
│       └── resources/           ← files only tests need
└── target/                      ← EVERYTHING Maven generates (safe to delete!)
    ├── classes/                     compiled main code + resources
    ├── test-classes/                compiled tests
    ├── surefire-reports/            test reports
    └── maven-demo-1.0.0.jar         the packaged JAR
💡 Rules of thumb Never put your own files in target/ — mvn clean deletes it. Never commit target/ to Git (add it to .gitignore). Package folders in src/main/java must match the package line, just like in Topic 9.

3.3 GAV coordinates — every artifact's address

Every Maven project and every library is identified by three values, called GAV:

ElementMeaningOur projectA library
groupIdWho makes it — usually a reversed domain namecom.courseorg.apache.commons
artifactIdThe project/library namemaven-democommons-lang3
versionWhich release1.0.03.17.0

Written in one line: org.apache.commons:commons-lang3:3.17.0. The JAR file name is artifactId-version.jar → commons-lang3-3.17.0.jar.

Versions: most libraries use semantic versioning MAJOR.MINOR.PATCH (major = breaking changes, minor = new features, patch = bug fixes). A version ending in -SNAPSHOT (e.g. 1.1.0-SNAPSHOT) means "work in progress, may change"; a version without it is a fixed release that never changes.

3.4 pom.xml element by element

pom.xml (skeleton)<project ...>
    <modelVersion>4.0.0</modelVersion>          <!-- POM format version, always 4.0.0 -->

    <parent>...</parent>                        <!-- optional: inherit settings (3.10) -->

    <groupId>com.course</groupId>               <!-- G -->
    <artifactId>maven-demo</artifactId>         <!-- A -->
    <version>1.0.0</version>                    <!-- V -->
    <packaging>jar</packaging>                  <!-- jar (default) | war | pom -->
    <name>...</name> <description>...</description>

    <properties>...</properties>               <!-- named values, used as ${name} -->
    <dependencyManagement>...</dependencyManagement>  <!-- version rules (3.10) -->
    <dependencies>...</dependencies>           <!-- the libraries you use -->

    <build>
        <resources>...</resources>             <!-- optional: resource settings -->
        <plugins>...</plugins>                 <!-- the tools that do the work -->
    </build>
</project>
ElementWhat it is for
modelVersionVersion of the POM format. Always 4.0.0.
parentInherit configuration from another POM (e.g. spring-boot-starter-parent).
groupId / artifactId / versionThis project's coordinates.
packagingWhat to produce: jar (normal, Spring Boot), war (old-style web app for an external Tomcat), pom (parent/aggregator project, no code).
propertiesKey/value settings. Some are read by plugins (maven.compiler.release, project.build.sourceEncoding); you can add your own (commons-lang3.version).
dependenciesLibraries this project needs, with optional scope.
dependencyManagementDeclares versions without adding the dependency — a rulebook (BOMs live here).
build/pluginsConfigure the plugins that compile, test, package, run...
modulesFor multi-module projects: list of sub-projects to build together.
repositoriesExtra places to download from (rarely needed — Central is the default).

3.5 Dependencies and scopes

Adding a library = adding its GAV in <dependencies>. Where do you find the GAV? On the library's website, or by searching central.sonatype.com / mvnrepository.com, which show a ready-to-copy snippet.

<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>3.17.0</version>
    <!-- no scope = compile -->
</dependency>

The scope says when a dependency is on the classpath:

ScopeCompile mainCompile/run testsRuntime / inside final appTypical example
compile (default)✅✅✅Spring, Jackson, commons-lang3
test❌✅❌JUnit, Mockito, AssertJ
runtime❌✅✅JDBC drivers (MySQL, H2) — code uses only java.sql interfaces
provided✅✅❌ (the server/JDK provides it)Servlet API for a WAR, Lombok
importOnly in <dependencyManagement> to import a BOM (3.10)Spring Cloud BOM

Scope test is a safety feature: if someone accidentally imports JUnit in src/main/java, the build fails instead of shipping test libraries to production.

3.6 Transitive dependencies

Libraries have their own dependencies (declared in their POMs). Maven downloads them automatically — these are transitive dependencies. You can see the whole tree:

mvn dependency:tree

[INFO] com.course:maven-demo:jar:1.0.0
[INFO] +- org.apache.commons:commons-lang3:jar:3.17.0:compile
[INFO] \- org.junit.jupiter:junit-jupiter:jar:5.11.4:test
[INFO]    +- org.junit.jupiter:junit-jupiter-api:jar:5.11.4:test
[INFO]    |  +- org.opentest4j:opentest4j:jar:1.3.0:test
[INFO]    |  +- org.junit.platform:junit-platform-commons:jar:1.11.4:test
[INFO]    |  \- org.apiguardian:apiguardian-api:jar:1.1.2:test
[INFO]    +- org.junit.jupiter:junit-jupiter-params:jar:5.11.4:test
[INFO]    \- org.junit.jupiter:junit-jupiter-engine:jar:5.11.4:test
[INFO]       \- org.junit.platform:junit-platform-engine:jar:1.11.4:test

We declared 2 dependencies; Maven resolved 9. A Spring Boot web project declares ~3 and gets ~40. When two paths bring different versions of the same library, Maven picks the one nearest to your project in the tree ("nearest wins"; if equal depth, the first declared). If that causes trouble, you can:

  • declare the version you want directly (direct dependencies are always nearest), or pin it in <dependencyManagement>;
  • remove an unwanted transitive dependency with <exclusions>:
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>                              <!-- e.g. use Jetty instead of Tomcat -->
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>

3.7 Repositories: local and remote

pom.xml needs commons-lang3:3.17.0→ In ~/.m2/repository? → use it→ else → Download from Maven Central→ Save in ~/.m2 for next time
  • Local repository: C:\Users\<you>\.m2\repository — a cache of everything you've ever downloaded, organised by GAV: .m2\repository\org\apache\commons\commons-lang3\3.17.0\commons-lang3-3.17.0.jar. Shared by all your projects.
  • Maven Central (https://repo.maven.apache.org/maven2): the default public remote repository with millions of artifacts.
  • Company repositories (Nexus, Artifactory, GitHub Packages): private servers for internal libraries; configured in ~/.m2/settings.xml.
ℹ️ Offline and broken downloads The first build needs internet; later builds work offline (mvn -o ...). If a download was interrupted, you may get strange "invalid LOC header" or "zip END header not found" errors — delete that library's folder in .m2\repository and build again.

3.8 The build lifecycle, phases and goals

Maven's default lifecycle is an ordered list of phases. When you run a phase, Maven runs every phase before it, in order:

validate→ compile→ test→ package→ verify→ install→ deploy
CommandWhat happensResult
mvn cleanSeparate "clean" lifecycle: deletes target/Fresh start
mvn compileCopy resources, compile src/main/javatarget/classes
mvn testcompile + compile tests + run tests (surefire)target/surefire-reports
mvn package... + build the JAR/WARtarget/maven-demo-1.0.0.jar
mvn verify... + integration tests/quality checks (used in CI)
mvn install... + copy the JAR into your local ~/.m2Other local projects can depend on it
mvn deploy... + upload to a remote repositoryShared with your team

You can combine them: mvn clean package = "delete old output, then build fresh". Skip tests (only when you really must): mvn package -DskipTests.

Plugins and goals. Phases are just names — the real work is done by plugins. Each plugin has goals (tasks), and goals are bound to phases:

PhasePlugin:goal bound to it (for jar packaging)
process-resourcesresources:resources
compilecompiler:compile
testsurefire:test
packagejar:jar (+ shade:shade in our pom)
installinstall:install

You can also run a goal directly, outside the lifecycle: mvn dependency:tree, mvn exec:java, mvn spring-boot:run (later!). Look at real build output — each --- line is one plugin goal running:

[INFO] --- compiler:3.13.0:compile (default-compile) @ maven-demo ---
[INFO] --- resources:3.3.1:testResources (default-testResources) @ maven-demo ---

3.9 Runnable JARs: thin vs fat

A normal mvn package produces a thin JAR: only your classes. Running it with java -jar fails because (1) the JAR doesn't say which class has main, and (2) the libraries (commons-lang3) are not inside.

Solutions:

  • exec-maven-plugin — run through Maven during development: mvn compile exec:java. Maven builds the classpath for you.
  • maven-shade-plugin — builds a fat JAR (also called uber JAR): your classes + all runtime dependencies unpacked into one file, with Main-Class in META-INF/MANIFEST.MF. Then java -jar target/maven-demo-1.0.0.jar works anywhere Java is installed.
  • spring-boot-maven-plugin — Spring Boot's own version: an executable JAR with dependencies nested inside (Topic 28). Same idea, smarter format.

3.10 Properties, parent POMs and BOMs (→ Spring Boot parent)

Properties are named values. Define once, use as ${name} anywhere in the POM (and in filtered resources):

<properties>
    <maven.compiler.release>17</maven.compiler.release>   <!-- read by the compiler plugin -->
    <commons-lang3.version>3.17.0</commons-lang3.version>  <!-- our own -->
</properties>
...
<version>${commons-lang3.version}</version>

Built-in ones include ${project.version}, ${project.artifactId}, ${java.version} (Spring Boot defines this one).

Parent POM. A POM can inherit from another with <parent> — it receives the parent's properties, plugin configuration and dependency versions. This is what every Spring Boot project does:

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.6</version>
</parent>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <!-- NO version! The parent knows the right one. -->
    </dependency>
</dependencies>

The Spring Boot parent gives you: tested-together versions of ~hundreds of libraries, UTF-8 encoding, Java version via <java.version>, sensible plugin settings, resource filtering for application.properties. That's why Spring Boot POMs are so short.

dependencyManagement and BOMs. <dependencyManagement> lists versions as rules without adding the dependencies. A BOM (Bill of Materials) is a special POM that contains only such a list — "these 50 libraries work together in these versions". You import a BOM with scope import:

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>2025.0.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

You will use exactly this for the microservices topics (59+). Unlike a parent (you can have only one), you can import many BOMs.

3.11 Resource filtering

Files in src/main/resources are copied to target/classes (so they end up on the classpath and inside the JAR). With <filtering>true</filtering>, Maven also replaces ${...} placeholders in them. Our app.properties contains app.version=${project.version}, which becomes app.version=1.0.0. Spring Boot's parent enables filtering with @...@ delimiters (because Spring itself uses ${...}).

3.12 The Maven Wrapper (mvnw)

Different Maven versions can behave differently. The Maven Wrapper pins a version per project. It consists of mvnw (Linux/macOS), mvnw.cmd (Windows) and .mvn/wrapper/maven-wrapper.properties. The first time you run mvnw, it downloads the exact Maven version written in the properties file (into ~/.m2/wrapper) and then uses it.

.\mvnw.cmd clean package       # Windows (PowerShell)
./mvnw clean package           # Linux / macOS / Git Bash

Benefits: nobody needs Maven installed, CI servers and teammates use the identical version. Projects from start.spring.io include the wrapper. You can add it to any project with mvn wrapper:wrapper — that's how this folder's wrapper was created.

3.13 Gradle in one minute

Gradle is the other popular build tool (default for Android). It uses the same Maven Central repository and the same GAV coordinates, but the build file is code (Groovy or Kotlin) instead of XML, and it's often faster thanks to caching:

build.gradle.kts (Gradle, for comparison only)dependencies {
    implementation("org.apache.commons:commons-lang3:3.17.0")
    testImplementation("org.junit.jupiter:junit-jupiter:5.11.4")
}

Concepts you learned here (dependencies, scopes ≈ configurations, repositories, wrapper) transfer directly. This course uses Maven everywhere.

LabelFormatter.java — using a library

src/main/java/com/course/mavendemo/LabelFormatter.javaimport org.apache.commons.lang3.StringUtils;   // comes from the downloaded JAR

public String toSlug(String productName) {
    if (StringUtils.isBlank(productName)) {       // null-safe: null, "", "   " -> true
        return "";
    }
    String lower = StringUtils.lowerCase(productName.strip());
    String lettersAndDigits = lower.replaceAll("[^a-z0-9]+", "-");
    return StringUtils.strip(lettersAndDigits, "-");
}

public String productCode(String productName, int id) {
    String prefix = StringUtils.upperCase(StringUtils.left(StringUtils.deleteWhitespace(productName), 3));
    return prefix + "-" + StringUtils.leftPad(String.valueOf(id), 5, '0');   // MOU-00042
}

Nothing special in the Java code: you just import the class. Maven made sure the JAR was on the classpath at compile time, test time and run time.

6. Common mistakes

⚠️ Mistake: "package org.apache.commons.lang3 does not exist" The dependency is missing, misspelled, or VS Code hasn't reloaded the POM.
Fix: check the GAV, run mvn compile in the terminal, then "Java: Reload Projects" in VS Code.
⚠️ Mistake: "no main manifest attribute, in target/xyz.jar" You ran java -jar on a thin JAR.
Fix: configure the shade plugin (or spring-boot-maven-plugin for Spring Boot) with the main class.
⚠️ Mistake: NoClassDefFoundError when running the JAR The JAR has a Main-Class but not the libraries.
Fix: build a fat JAR (shade) or run via mvn exec:java.
⚠️ Mistake: running mvn package twice without clean with the shade plugin The second run shades an already-shaded JAR and prints many "overlapping classes" warnings.
Fix: use mvn clean package.
⚠️ Mistake: using a test library in main code "package org.junit.jupiter.api does not exist" in src/main/java.
Fix: tests belong in src/test/java; test-scoped libraries are invisible to main code on purpose.
⚠️ Mistake: putting code in the wrong folder A .java file directly in src/ or in src/main/resources is ignored by the compiler.
Fix: follow the standard layout — src/main/java/<package folders>.
⚠️ Mistake: "invalid target release: 17" / "release version 17 not supported" Maven is running with an older JDK.
Fix: mvn -v shows which Java Maven uses; set JAVA_HOME to your JDK 17 (Topic 1).
🚫 Mistake: always building with -DskipTests It "saves time" until broken code reaches production.
Fix: keep tests fast and let them run; CI should always run them.

7. Best practices

  • Follow the standard layout — every Java developer and tool understands it.
  • Pin versions of dependencies and plugins (no LATEST, no version ranges) for repeatable builds. Use properties to keep them in one place.
  • Use the right scope: test for test libraries, runtime for JDBC drivers.
  • Prefer a parent or BOM (like Spring Boot's) to managing dozens of versions yourself — and don't override managed versions without a reason.
  • Check the dependency tree when something odd happens (two versions of a library, unexpected classes).
  • Commit the Maven Wrapper and use ./mvnw in CI.
  • Never commit target/; add it to .gitignore.
  • Use mvn clean verify (or package) before pushing — it's what CI will run (Topic 68).
  • Keep dependencies minimal and up to date: each library is code you ship and a possible security risk (tools like Dependabot help).

8. Key takeaways

  • Maven automates downloading libraries, compiling, testing and packaging, using pom.xml as the recipe.
  • Standard layout: src/main/java, src/main/resources, src/test/java; output in target/.
  • Every artifact has GAV coordinates: groupId:artifactId:version.
  • Scopes: compile (default), test, runtime, provided, import.
  • Transitive dependencies are resolved automatically; inspect with mvn dependency:tree.
  • Downloads are cached in ~/.m2/repository; the default remote is Maven Central.
  • Lifecycle: validate → compile → test → package → verify → install → deploy; running a phase runs all earlier ones. Plugins' goals do the actual work.
  • Fat JARs (shade / Spring Boot plugin) contain all dependencies and run with java -jar.
  • Parent POMs and BOMs manage versions — that's what spring-boot-starter-parent does for you.
  • The Maven Wrapper (mvnw) pins the Maven version for everyone.

Explore the lifecycle. Run mvn clean, then mvn compile, and look inside target/. Then run mvn test and open target/surefire-reports. Finally run mvn package. Write down which new folders/files appear after each command.

Hint / solution

After compile: target/classes (App.class, LabelFormatter.class, app.properties with 1.0.0). After test: also target/test-classes and target/surefire-reports (a .txt and an .xml report). After package: maven-demo-1.0.0.jar, original-maven-demo-1.0.0.jar, maven-archiver/.

Easy

Change the version. Change <version> to 1.1.0-SNAPSHOT, run mvn clean package and the JAR. What changes in the JAR's name and in the program's first output line? Why?

Hint / solution

The JAR becomes target/maven-demo-1.1.0-SNAPSHOT.jar and the program prints === Shop Label Printer v1.1.0-SNAPSHOT ===, because resource filtering replaced ${project.version} in app.properties.

Medium

Add a library. Add Jackson (com.fasterxml.jackson.core:jackson-databind:2.19.2) and print a product as JSON: create a record Product(String code, String name, double price) and use new ObjectMapper().writeValueAsString(product). Then look at mvn dependency:tree — which transitive dependencies did Jackson bring?

Hint / solution
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.19.2</version>
</dependency>
record Product(String code, String name, double price) { }

ObjectMapper mapper = new ObjectMapper();
String json = mapper.writeValueAsString(new Product("MOU-00042", "Mouse", 799.0));
System.out.println(json);   // {"code":"MOU-00042","name":"Mouse","price":799.0}

The tree shows jackson-annotations and jackson-core as transitive dependencies. (main must declare throws Exception or catch JsonProcessingException.) Spring Boot includes Jackson automatically — this is how it turns your objects into JSON (Topic 31).

Medium

Break the build on purpose. Change one expected value in LabelFormatterTest so the test fails. Run mvn package. What happens to the JAR? Read the failure message. Then try mvn package -DskipTests.

Hint / solution

mvn package stops in the test phase with BUILD FAILURE and an expected: <...> but was: <...> message; no new JAR is built. With -DskipTests the JAR is built anyway — which shows why skipping tests is dangerous. Fix the test afterwards!

Challenge

Multi-module project. Create a parent project shop-parent (packaging = pom) with two modules: shop-core (contains LabelFormatter) and shop-app (contains App and depends on shop-core). Build both with one mvn clean install from the parent folder.

Hint / solution
shop-parent/pom.xml<groupId>com.course</groupId>
<artifactId>shop-parent</artifactId>
<version>1.0.0</version>
<packaging>pom</packaging>
<modules>
    <module>shop-core</module>
    <module>shop-app</module>
</modules>
<properties><maven.compiler.release>17</maven.compiler.release></properties>
shop-app/pom.xml<parent>
    <groupId>com.course</groupId>
    <artifactId>shop-parent</artifactId>
    <version>1.0.0</version>
</parent>
<artifactId>shop-app</artifactId>
<dependencies>
    <dependency>
        <groupId>com.course</groupId>
        <artifactId>shop-core</artifactId>
        <version>${project.version}</version>
    </dependency>
</dependencies>

Maven works out the build order (core first, because app depends on it) — this is called the reactor. install also puts both JARs into your ~/.m2.

10. Interview questions

Q1. What is Maven and why do we use it?

Maven is a build automation and dependency management tool for Java. It uses a declarative pom.xml to download dependencies (including transitive ones) from repositories, compile, test, package and deploy the project with a standard lifecycle and directory layout, giving reproducible builds across machines and CI.

Q2. What are GAV coordinates?

groupId (organisation/namespace), artifactId (project name) and version. Together they uniquely identify an artifact in a repository, e.g. org.apache.commons:commons-lang3:3.17.0. Packaging and classifier can further qualify it.

Q3. Explain the Maven build lifecycle.

The default lifecycle is an ordered sequence of phases: validate, compile, test, package, verify, install, deploy (plus intermediate ones like process-resources). Executing a phase executes all previous phases. Plugin goals are bound to phases and do the work (compiler:compile, surefire:test, jar:jar...). There are also the separate clean and site lifecycles.

Q4. What is the difference between mvn package and mvn install?

package builds the artifact (e.g. JAR) into target/. install does everything package does plus verify, and then copies the artifact into the local repository (~/.m2) so other local projects can depend on it. deploy uploads it to a remote repository.

Q5. What dependency scopes exist?

compile (default; available everywhere and packaged), provided (needed to compile but supplied at runtime by the container/JDK), runtime (not needed to compile but needed to run, e.g. JDBC drivers), test (only for tests), system (deprecated, local path), and import (only in dependencyManagement to import a BOM).

Q6. What are transitive dependencies and how do you resolve version conflicts?

Dependencies of your dependencies, pulled in automatically. Conflicts are resolved by "nearest definition wins" (then first declaration). You can control them by declaring the dependency directly, pinning versions in dependencyManagement/a BOM, or using <exclusions>. Use mvn dependency:tree to diagnose.

Q7. dependencies vs dependencyManagement?

<dependencies> actually adds libraries to the project. <dependencyManagement> only declares versions (and scopes/exclusions) to be used if/when the dependency is added — in this POM or child POMs — so the version can be omitted. BOMs are imported into dependencyManagement.

Q8. What does spring-boot-starter-parent give you?

It's a parent POM that inherits from spring-boot-dependencies (a BOM with curated versions of hundreds of libraries), sets the Java version and UTF-8 encoding, configures resource filtering for application.properties/yml, and provides sensible plugin defaults (including spring-boot-maven-plugin configuration). So starters can be added without versions. Alternatively you can import the spring-boot-dependencies BOM if you need a different parent.

Q9. What is the Maven Wrapper?

Scripts (mvnw, mvnw.cmd) plus .mvn/wrapper/maven-wrapper.properties that download and use a specific Maven version for the project, so builds don't depend on a locally installed Maven and everyone (including CI) uses the same version.

Q10. Maven vs Gradle?

Both use the same repositories and coordinates. Maven uses declarative XML with a fixed lifecycle — very standardised and predictable. Gradle uses a Groovy/Kotlin DSL, is more flexible/programmable, and is often faster thanks to incremental builds and a build cache. Gradle is default for Android; both are fully supported by Spring Initializr.
