26. Spring Configuration, Profiles & Environment

Run the same code on your laptop and on the production server with different beans and settings — and discover the secret behind Spring Boot's auto-configuration.

  • How to write your own @Conditional — the mechanism that powers Spring Boot auto-configuration.

1. Why this matters

Real applications run in several environments:

  • dev — your laptop: an in-memory H2 database, files saved to a local folder, fake emails.
  • test / QA — a shared test server with test data.
  • prod — the real server: a MySQL database, files in cloud storage, real emails to real customers.

The code must be the same everywhere (you test what you ship!). Only the configuration changes. If you handle this with if (isProduction) scattered through the code, sooner or later someone sends test emails to real customers. Spring gives you clean tools: profiles choose beans, the Environment provides settings, and conditions switch features on or off.

And here's a bonus: when you add spring-boot-starter-web to a Spring Boot project, a web server "magically" appears. That magic is just hundreds of @Configuration classes guarded by @Conditional annotations — the exact thing you'll build by hand in this topic. After this lesson, Spring Boot auto-configuration (Topic 28) will feel obvious.

2. Real-life analogy

✈️ A pilot's checklists

An airline pilot flies the same aircraft (the same code) on different routes. Before take-off they pick the right checklist: "short domestic flight" or "long international flight". The checklist decides which equipment is loaded — that's a profile.

  • The flight plan board in the cockpit shows all current values: fuel, weather, altitude limits. Some values come from the control tower (system properties), some from the airport (environment variables), some from the airline's manual (property files). If two sources disagree, there's a fixed rule about who wins. That board is the Environment.
  • Some equipment is loaded only if a condition is true: "if the flight is over water, load life rafts". That's @Conditional.
  • The pilot's main manual says "see chapter: Engines" and "see chapter: Navigation" instead of putting everything in one huge chapter. That's @Import.

3. Concepts step by step

3.1 @Configuration in depth: full mode vs lite mode

Look at this configuration. The orderService() and paymentService() methods both call auditLog() directly:

proxydemo/FullConfig.java@Configuration
public class FullConfig {

    @Bean
    public AuditLog auditLog() {
        return new AuditLog();
    }

    @Bean
    public AuditedService orderService() {
        return new AuditedService("orderService", auditLog());     // a plain Java method call...
    }

    @Bean
    public AuditedService paymentService() {
        return new AuditedService("paymentService", auditLog());   // ...called a second time
    }
}

In normal Java, calling auditLog() twice runs new AuditLog() twice → two objects. But the output says:

FULL config class at runtime: FullConfig$$SpringCGLIB$$0
FULL: orderService uses AuditLog #1, paymentService uses AuditLog #1

Both services share AuditLog #1 — the singleton. How? At startup Spring generates a subclass of FullConfig using a library called CGLIB (that's the $$SpringCGLIB$$0 in the class name). The subclass overrides each @Bean method like this (simplified):

// generated by Spring at runtime (simplified idea)
class FullConfig$$SpringCGLIB$$0 extends FullConfig {
    @Override
    public AuditLog auditLog() {
        if (container already has a bean "auditLog") {
            return thatBean;                 // don't create a second one
        }
        return super.auditLog();             // first time: really create it
    }
}

This is full mode — the default for @Configuration (same as @Configuration(proxyBeanMethods = true)). It guarantees singleton semantics even for direct calls between @Bean methods.

With @Configuration(proxyBeanMethods = false) — lite mode — no subclass is created. Methods are plain Java again:

LITE config class at runtime: LiteConfig
LITE: container's AuditLog is #2, but orderService uses AuditLog #3, paymentService uses AuditLog #4
LITE: safePaymentService uses AuditLog #2  <- parameter injection is always safe

The services got extra AuditLogs that are not even beans. The fix in lite mode: ask for dependencies as method parameters, which are always resolved from the container:

proxydemo/LiteConfig.java@Bean
public AuditedService safePaymentService(AuditLog auditLog) {   // injected - the real singleton
    return new AuditedService("safePaymentService", auditLog);
}
Full mode (@Configuration)Lite mode (proxyBeanMethods = false)
CGLIB subclass created?YesNo
Direct call to another @Bean methodReturns the container's singleton ✅Creates a new object ⚠️
Startup costSlightly higherSlightly lower (Spring Boot's own auto-config classes use lite mode)
Class/methods may be final?No (a subclass must override them)Yes
Safe styleUse method parameters for dependencies — works correctly in both modes.
💡 Simple rule Always inject dependencies of a @Bean method as parameters. Then full vs lite never matters to you.

3.2 @Import — splitting configuration

One giant configuration class gets messy. Split it by topic and pull the pieces together with @Import:

config/AppConfig.java@Configuration
@Import({DevDataSourceConfig.class, ProdDataSourceConfig.class, StorageConfig.class, FeatureConfig.class})
@PropertySource("classpath:application.properties")
@PropertySource("classpath:application-${spring.profiles.active:dev}.properties")
@ComponentScan("com.course.configprofiles.service")
public class AppConfig { ... }
  • We start the container with only AppConfig; Spring follows the @Import and processes the four other classes too.
  • @Import is explicit — no package scanning needed. It's common for shared libraries: "import my company's SecurityConfig".
  • You can import @Configuration classes, plain @Component classes, or special "selector" classes that decide at runtime what to import (an ImportSelector). Spring Boot's @EnableAutoConfiguration is exactly such a selector — it imports a long list of auto-configuration classes.
  • Many @Enable... annotations work by importing configuration, e.g. @EnableAspectJAutoProxy (Topic 27), @EnableScheduling (Topic 52).

3.3 Profiles — different beans per environment

A profile is a named group of beans: dev, test, prod, cloud… A bean marked with @Profile is registered only if that profile is active. Beans without @Profile are always registered.

Class level — the whole configuration class belongs to a profile:

config/DevDataSourceConfig.java@Configuration
@Profile("dev")
public class DevDataSourceConfig {
    @Bean
    public DatabaseSettings databaseSettings(Environment env) { ... H2 ... }
}

@Configuration
@Profile("prod")
public class ProdDataSourceConfig {
    @Bean
    public DatabaseSettings databaseSettings(Environment env) { ... MySQL ... }
}

Method level — individual @Bean methods:

config/StorageConfig.java@Bean("storageService")
@Profile("dev")
public StorageService localStorage(@Value("${storage.root}") String root) {
    return new LocalDiskStorage(root);
}

@Bean("storageService")
@Profile("prod")
public StorageService cloudStorage(@Value("${storage.bucket}") String bucket) {
    return new CloudStorage(bucket);
}

@Bean
@Profile("!prod")                       // every profile EXCEPT prod
public String sampleDataLoader() { ... }

The rest of the app simply asks for a StorageService or DatabaseSettings and never knows which environment it's in. You can also put @Profile on a @Component class.

Profile expressionBean is active when…
@Profile("dev")dev is active
@Profile("!prod")prod is not active
@Profile({"dev", "test"}) or @Profile("dev | test")dev or test is active
@Profile("prod & cloud")both prod and cloud are active
@Profile("default")no profile at all was activated

3.4 Activating profiles

A profile does nothing until it's activated. Ways to activate (several can be active at once, comma-separated):

HowExampleTypical use
JVM system property-Dspring.profiles.active=prodStart scripts, our demo
OS environment variableSPRING_PROFILES_ACTIVE=prodServers, Docker, Kubernetes (Topics 66–69)
In code, before refresh()context.getEnvironment().setActiveProfiles("prod")Tests, demos
Spring Bootspring.profiles.active=dev in application.properties, or --spring.profiles.active=prod on the command lineTopic 29

If no profile is activated, Spring uses the default profiles — normally a profile literally called default. Our demo changes the default to dev, so a plain run behaves like a developer laptop:

App.javaAnnotationConfigApplicationContext context = new AnnotationConfigApplicationContext();  // empty, not started
context.getEnvironment().setDefaultProfiles("dev");    // used when nothing is activated
context.register(AppConfig.class);                     // add configuration
context.refresh();                                     // NOW start: read config, create beans
⚠️ Configure the Environment before refresh() The one-line form new AnnotationConfigApplicationContext(AppConfig.class) registers and refreshes immediately — too late to change profiles. Use the three-step form (create empty → configure → register + refresh). Spring Boot does all this for you.

3.5 The Environment

Environment (package org.springframework.core.env) is Spring's central object for two things: profiles and properties. You can inject it into any bean like a normal dependency:

service/EnvironmentReporter.java@Component
public class EnvironmentReporter {
    private final Environment env;

    public EnvironmentReporter(Environment env) { this.env = env; }

    public void report() {
        env.getActiveProfiles();                           // [prod]   or [] if none
        env.getDefaultProfiles();                          // [dev]
        env.acceptsProfiles(Profiles.of("prod"));          // true / false
        env.getProperty("app.greeting");                   // String or null
        env.getProperty("shop.max-items", Integer.class);  // converted to Integer
        env.getProperty("shop.currency", "INR");           // with a default
        env.getRequiredProperty("db.url");                 // throws IllegalStateException if missing
        env.containsProperty("PATH");                      // true - an OS environment variable
    }
}

Properties come from a list of property sources. Spring searches them in order and the first one that has the key wins:

1. systemProperties
-Dkey=value, java.version…→ 2. systemEnvironment
OS env vars: PATH…→ 3. application-dev.properties
later @PropertySource→ 4. application.properties
earlier @PropertySource

Consequences:

  • A -Dshop.name=MegaMart on the command line beats the value in any file. Great for a quick override.
  • An environment variable beats files too — that's how servers inject secrets without writing them in files. Spring even maps SHOP_NAME to shop.name (dots → underscores, upper case).
  • Between @PropertySource files, the later one wins. That's why features.loyalty.enabled=true in application-prod.properties overrides false from application.properties.
ℹ️ @Value vs Environment @Value("${key}") reads from the very same Environment. Use @Value (or Boot's @ConfigurationProperties) for normal injection; use Environment when you need dynamic keys, profile checks, or you're writing configuration/conditions.
💡 The profile-specific file trick @PropertySource("classpath:application-${spring.profiles.active:dev}.properties") — placeholders work in the file name! It's resolved from system properties/env vars, so -Dspring.profiles.active=prod loads application-prod.properties. Spring Boot does this automatically for application-{profile}.properties (Topic 29) — here you see how simple the idea is.

3.6 @Conditional — beans that exist only if a condition is true

@Profile is actually a special case of a more general feature: @Conditional. You write a class implementing Condition with one method, matches(), which returns true (register the bean) or false (skip it):

condition/OnClassPresentCondition.javapublic class OnClassPresentCondition implements Condition {

    @Override
    public boolean matches(ConditionContext context, AnnotatedTypeMetadata metadata) {
        return ClassUtils.isPresent("com.fasterxml.jackson.databind.ObjectMapper",
                                    context.getClassLoader());       // is Jackson on the classpath?
    }
}

// usage
@Bean
@Conditional(OnClassPresentCondition.class)
public String jsonExporter() { return "JsonExporter"; }

ConditionContext gives access to the Environment (properties/profiles), the bean registry (which beans exist already) and the class loader (which libraries are present). AnnotatedTypeMetadata lets you read the annotations on the method/class being checked.

Even nicer: wrap the condition in your own annotation using meta-annotations (Topic 18):

condition/ConditionalOnFeature.java@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
@Conditional(OnFeatureCondition.class)          // <-- the real work happens here
public @interface ConditionalOnFeature {
    String value();                             // feature name
}
condition/OnFeatureCondition.javapublic class OnFeatureCondition implements Condition {
    @Override
    public boolean matches(ConditionContext context, AnnotatedTypeMetadata metadata) {
        Map<String, Object> attributes =
                metadata.getAnnotationAttributes(ConditionalOnFeature.class.getName());
        String key = "features." + attributes.get("value") + ".enabled";
        return context.getEnvironment().getProperty(key, Boolean.class, false);
    }
}
config/FeatureConfig.java@Bean
@ConditionalOnFeature("recommendations")        // registered only if features.recommendations.enabled=true
public String recommendationService() { ... }

@Bean
@ConditionalOnFeature("loyalty")                // false in dev, true in prod
public String loyaltyService() { ... }
🔑 This is the secret behind Spring Boot auto-configuration Spring Boot ships with hundreds of configuration classes, each guarded by conditions like these — which Boot provides ready-made:
Spring Boot annotationRegisters the bean if…Our hand-made equivalent
@ConditionalOnClass(DataSource.class)a class is on the classpath (you added a library)OnClassPresentCondition
@ConditionalOnProperty("features.x.enabled")a property has a value@ConditionalOnFeature
@ConditionalOnMissingBeanyou did not define such a bean yourself(check the registry in ConditionContext)
@ConditionalOnWebApplicationit's a web app—
Example: "if H2 is on the classpath and you didn't define a DataSource yourself, create an in-memory H2 DataSource". That's why adding one dependency to your pom "magically" configures things — and why your own bean always wins over Boot's default.

3.7 SpEL — the Spring Expression Language

${...} only looks up a property. #{...} evaluates an expression — maths, method calls, conditions, other beans. It's called SpEL (Spring Expression Language).

service/PricingRules.java@Value("#{2 * 60 * 60}")                                  // arithmetic                 -> 7200
private int sessionTimeoutSeconds;

@Value("#{'${shop.name}'.toUpperCase()}")                 // property + String method   -> QUICKCART
private String shopNameUpper;

@Value("#{${shop.base-delivery-fee} * 1.18}")             // property + maths (18% tax) -> 59.0
private double deliveryFeeWithTax;

@Value("#{${shop.max-items} > 20 ? 'BULK' : 'NORMAL'}")   // ternary                    -> BULK
private String orderMode;

@Value("#{T(java.lang.Math).max(10, ${shop.max-items})}") // static method with T(...)  -> 25
private int effectiveLimit;

@Value("#{storageService.name()}")                        // method on ANOTHER BEAN     -> LocalDisk / Cloud
private String storageName;

@Value("#{systemProperties['java.version']}")             // built-in variable          -> 17.0.19
private String javaVersion;

@Value("#{ {100, 250, 499, 1200}.?[#this > 300] }")       // selection (filter)         -> [499, 1200]
private List<Integer> bigOrderAmounts;

Note the order when combining: ${...} placeholders are replaced first (text replacement), then the #{...} expression is evaluated. So #{${shop.base-delivery-fee} * 1.18} becomes #{50 * 1.18} → 59.0.

SpEL featureSyntax
Literals'text', 42, 3.14, true, null
Operators+ - * / %, == != < > (or eq ne lt gt), and or not, ?:
Methods & properties'abc'.length(), someBean.name
Bean referencestorageService (by bean name) or @storageService
Static typesT(java.time.LocalDate).now()
Safe navigationuser?.address?.city (no NullPointerException)
Elvis (default)name ?: 'Guest'
Collections{1,2,3}; selection .?[cond]; projection .![expr]

SpEL also works on its own, outside @Value:

App.javaExpressionParser parser = new SpelExpressionParser();
List<?> doubled = parser.parseExpression("{1499, 599, 8999}.![#this * 2]").getValue(List.class);
// -> [2998, 1198, 17998]
ℹ️ Where you'll meet SpEL later Security rules like @PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id") (Topic 48), cache keys like @Cacheable(key = "#id") (Topic 51), and @Scheduled(cron = "${jobs.cron}"). Keep expressions short — complex logic belongs in Java code.

4.3 When are conditions evaluated?

Look at the start of demo 2: the [condition] lines are printed before any bean is created. Conditions run while Spring is still reading configuration and collecting bean definitions (Topic 23, step 2). A skipped bean never even gets a recipe — containsBean("loyaltyService") is simply false.

6. Common mistakes

⚠️ Mistake: calling @Bean methods directly in lite mode With proxyBeanMethods = false (or @Bean methods in a @Component class), auditLog() creates a new object every time — silently.
Fix: take dependencies as @Bean method parameters.
⚠️ Mistake: making a full-mode @Configuration class or its @Bean methods final CGLIB can't subclass/override them; startup fails with a message about the class or method being final.
Fix: don't use final there, or use lite mode.
⚠️ Mistake: no profile active → "No qualifying bean of type DatabaseSettings" If every implementation is behind @Profile("dev")/@Profile("prod") and you forgot to activate one, no bean exists.
Fix: set a default profile, or make one implementation the fallback with @Profile("default") or @Profile("!prod").
⚠️ Mistake: setting profiles after the context started setActiveProfiles after refresh() has no effect on already-created beans.
Fix: create the context empty, configure the Environment, then register() + refresh().
⚠️ Mistake: unquoted -D arguments in PowerShell See the warning in "How to run". Always write "-Dkey=value" in PowerShell.
🛑 Mistake: production secrets in property files committed to Git db.password=SuperSecret123 in application-prod.properties ends up in your Git history forever.
Fix: read secrets from environment variables (they win over files) or a secrets manager. Topics 29 and 69 cover this.
⚠️ Mistake: business logic in SpEL strings Long #{...} expressions are not checked by the compiler, are hard to test and hard to debug.
Fix: keep SpEL tiny; put real logic in Java methods.

7. Best practices

  • Same code, different configuration: use profiles and properties, never if (env == "prod") in business code.
  • Keep the number of profiles small (dev, test, prod…). Prefer properties for small differences and profiles for different beans.
  • Make the safe choice the default: a forgotten profile should give you dev behaviour (fake emails), never prod behaviour.
  • Split configuration by concern (database, security, messaging) and combine with @Import or scanning.
  • Inject dependencies into @Bean methods as parameters — correct in full and lite mode.
  • Use feature flags (property + condition) to switch features on/off without redeploying code.
  • In Spring Boot, prefer the built-in @ConditionalOnProperty/@ConditionalOnClass/@ConditionalOnMissingBean over custom conditions.
  • Secrets come from environment variables or a vault — never from Git.

8. Key takeaways

  • @Configuration (full mode) creates a CGLIB subclass so inter-@Bean method calls return singletons; proxyBeanMethods = false (lite mode) skips that.
  • @Import combines configuration classes explicitly; @Enable... annotations and Boot's auto-configuration use it.
  • @Profile registers beans only when a profile is active; supports !, &, |.
  • Activate profiles with -Dspring.profiles.active, SPRING_PROFILES_ACTIVE, or setActiveProfiles before refresh; default profiles apply when none is active.
  • The Environment holds profiles and properties; property sources are searched in order: system properties → env vars → files (later @PropertySource wins).
  • A Condition decides whether a bean is registered; custom annotations meta-annotated with @Conditional make them reusable.
  • Spring Boot auto-configuration = configuration classes + conditions.
  • SpEL #{...} evaluates expressions; ${...} only looks up properties — and is resolved first.

Challenge

Write @ConditionalOnMissingBeanNamed. Create a condition annotation that registers a bean only if no bean with a given name has been registered yet. Use it on a fallback @Bean("storageService") that returns a LocalDiskStorage("C:/temp/fallback") and put it in a new configuration class imported last. Test it with a profile that matches neither dev nor prod (e.g. "-Dspring.profiles.active=demo") — remember application-demo.properties must exist.

Hint / solution 
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
@Conditional(OnMissingBeanNamedCondition.class)
public @interface ConditionalOnMissingBeanNamed {
    String value();
}

public class OnMissingBeanNamedCondition implements Condition {
    @Override
    public boolean matches(ConditionContext context, AnnotatedTypeMetadata metadata) {
        String name = (String) metadata
                .getAnnotationAttributes(ConditionalOnMissingBeanNamed.class.getName()).get("value");
        return !context.getRegistry().containsBeanDefinition(name);
    }
}

@Configuration
public class FallbackStorageConfig {
    @Bean("storageService")
    @ConditionalOnMissingBeanNamed("storageService")
    public StorageService fallbackStorage() {
        return new LocalDiskStorage("C:/temp/fallback");
    }
}
// AppConfig: @Import({..., FeatureConfig.class, FallbackStorageConfig.class})

With the demo profile, neither dev nor prod storage is registered, so the fallback appears. With dev or prod it's skipped. You'd also need a DatabaseSettings fallback for the demo profile to start fully. Spring Boot's real @ConditionalOnMissingBean is more careful about ordering (auto-configuration runs after your own config) — which is why your beans always win.

10. Interview questions

Q1. What is the difference between @Configuration and @Component when declaring @Bean methods?

In a @Configuration class (full mode) Spring creates a CGLIB subclass that intercepts @Bean method calls, so calling one @Bean method from another returns the container-managed singleton. In a @Component class (or @Configuration(proxyBeanMethods = false), "lite mode") the methods are called as plain Java, so direct calls create new instances. Injecting dependencies via method parameters works in both.

Q2. What does proxyBeanMethods = false do and why would you use it?

It disables the CGLIB proxy for the configuration class. Benefits: slightly faster startup, less memory, allows final classes, and works better with native images. Spring Boot's auto-configuration classes use it. The cost: inter-bean method calls are no longer intercepted.

Q3. What is @Import used for?

To include other configuration classes (or components, ImportSelectors, ImportBeanDefinitionRegistrars) explicitly, without component scanning. It's used to modularise configuration and underlies @Enable* annotations and Spring Boot's @EnableAutoConfiguration.

Q4. What are profiles and how do you activate them?

Profiles are named, logical groups of bean definitions (e.g. dev, test, prod). Beans annotated with @Profile are registered only if a matching profile is active. Activate with the spring.profiles.active property (system property, environment variable SPRING_PROFILES_ACTIVE, Boot properties or command-line argument) or programmatically via ConfigurableEnvironment.setActiveProfiles() before refresh. If none is active, the default profiles (normally default) apply.

Q5. What is the Spring Environment?

An abstraction (org.springframework.core.env.Environment) that models two aspects: profiles (active/default) and properties. Properties are resolved from an ordered list of PropertySources — JVM system properties, OS environment variables, @PropertySource files (and in Boot, many more). The first source containing a key wins.

Q6. How does @Conditional work? How does it relate to Spring Boot?

@Conditional(MyCondition.class) on a @Bean method or configuration class makes Spring call MyCondition.matches(ConditionContext, AnnotatedTypeMetadata) while loading bean definitions; the bean is registered only if it returns true. @Profile itself is implemented with a condition. Spring Boot auto-configuration consists of configuration classes guarded by conditions such as @ConditionalOnClass, @ConditionalOnProperty and @ConditionalOnMissingBean.

Q7. What's the difference between ${...} and #{...}?

${...} is a property placeholder resolved against the Environment. #{...} is a SpEL expression evaluated at runtime, supporting operators, method calls, bean references, static types (T()) and collection selection/projection. Placeholders inside an expression are resolved first.

Q8. If the same property exists in two @PropertySource files, which value wins?

The file declared/processed later wins (it's added with higher precedence). System properties and environment variables override both, because they come earlier in the property-source order.

Q9. How would you provide a bean only in non-production environments?

Annotate it with @Profile("!prod"), or guard it with a condition on a property (e.g. @ConditionalOnProperty in Boot, or a custom @Conditional).
