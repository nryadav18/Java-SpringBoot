1. Why this matters

Congratulations — you have finished Core Java! You can write classes, use interfaces, handle exceptions, work with collections, talk to a database with JDBC, build with Maven and test with JUnit. That is a lot.

Now imagine a real company application: an online shop. It has hundreds of classes — OrderService, PaymentService, ProductRepository, EmailSender, InvoiceGenerator, DiscountCalculator… Each class needs other classes to do its job. Somebody has to create all these objects, in the right order, and connect them together.

If every class creates its own helpers with new, the code becomes a big ball of glue:

  • Changing one class (say, Email → SMS) means editing many other classes.
  • Testing one class means you accidentally run all its helpers too (real emails, real database…).
  • Nobody can see which class needs what, because the new calls are hidden inside.

Spring is a framework that solves exactly this. It creates your objects, connects them, and manages them for you. That is why Spring (and Spring Boot, which is built on top of it) is the most used Java framework in companies: banks, e-commerce, telecom, insurance, government — almost every Java backend job description says "Spring Boot".

ℹ️ How this topic is different In this topic we will not rush into Spring. First we feel the pain, then we fix it ourselves in plain Java. Only then do we let Spring do it. When you understand why Spring exists, everything else in this course will make sense.

2. Real-life analogy

👨‍🍳 The chef and the kitchen manager

A chef in a big restaurant needs tomatoes, a knife and a stove to make a dish. Imagine if the chef had to grow the tomatoes, forge the knife and build the stove before cooking. Crazy! And if the restaurant switched from gas to an electric stove, the chef would have to learn to build a new stove.

In a real restaurant, the chef simply says: "To cook, I need tomatoes, a knife and a stove." A kitchen manager buys them, sets them up and hands them to the chef. The chef just cooks.

  • The chef = your class (e.g. OrderService).
  • Tomatoes, knife, stove = its dependencies (e.g. NotificationService).
  • "I need a stove" (any stove that works) = depending on an interface, not a brand.
  • Handing things to the chef = Dependency Injection.
  • The chef no longer controls shopping — the manager does = Inversion of Control.
  • The kitchen manager = the Spring container (ApplicationContext).

There is also a famous saying for IoC called the Hollywood Principle: "Don't call us, we'll call you." Actors don't phone the studio every day asking for work — the studio calls them when needed. Your classes don't go out and create things — the framework gives them what they need and calls them.

3. Concepts step by step

3.1 What is a "dependency"?

If class A uses class B to do its work, then B is a dependency of A. "A depends on B."

Example: an OrderService must tell the customer "your order is confirmed". It uses an EmailSender for that. So EmailSender is a dependency of OrderService.

OrderService— uses → EmailSender

Dependencies are normal and good — classes should work together. The question is only: who creates the dependency, and how tightly are they glued?

3.2 The problem: tight coupling

Here is the "beginner way" — the class creates its own helper with new:

step1/TightOrderService.javapublic class TightOrderService {

    // The class decides AND creates its own dependency. This "new" is the glue.
    private final EmailSender emailSender = new EmailSender();

    public void placeOrder(String customer, String item) {
        System.out.println("Order placed: " + item + " for " + customer);
        emailSender.sendEmail(customer, "Your order for " + item + " is confirmed!");
    }
}

It works. So what is wrong? Let's look at three real situations from work:

SituationWhat happens with tight coupling
🔁 The manager says: "Customers want SMS, not email."You must open and edit TightOrderService. If 20 classes do new EmailSender(), you edit 20 classes.
🧪 You want to unit-test placeOrder().Every test run sends a real email. You can't replace EmailSender with a fake one, because the class creates it itself.
🔍 A new team member reads the code.Looking at the constructor (there isn't even one!) you can't tell that this class needs an email sender. The dependency is hidden.

Tight coupling means: one class is glued to one specific concrete class. You can't change one without changing the other. The opposite, loose coupling, means classes know each other only through a small contract (an interface), so parts can be swapped freely — like plugging any charger into a standard wall socket.

3.3 Fix part 1 — depend on an interface

You learned this in Topic 8: "program to an interface". We describe what we need, not which class:

notification/NotificationService.javapublic interface NotificationService {
    void send(String recipient, String message);
    String channel();
}

Now we can have many implementations:

public class EmailNotificationService implements NotificationService { ... }
public class SmsNotificationService   implements NotificationService { ... }
// tomorrow: PushNotificationService, WhatsAppNotificationService ...

3.4 Fix part 2 — constructor injection

The class stops creating its helper. Instead, it asks for it in the constructor:

order/OrderService.javapublic class OrderService {

    private final NotificationService notificationService;   // an INTERFACE type

    // "Give me any NotificationService. I don't care which one."
    public OrderService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    public String placeOrder(String customer, String item) {
        String message = "Your order for " + item + " is confirmed!";
        notificationService.send(customer, message);
        return message;
    }
}

This is Dependency Injection (DI): the dependency is injected (handed in) from outside instead of being created inside. The word "inject" sounds medical, but it just means "pass in".

Look at what we gained:

  • OrderService no longer mentions Email or Sms anywhere. It only knows the interface.
  • Switching channels means passing a different object. OrderService.java never changes.
  • The constructor clearly shows what the class needs. Nothing is hidden.
  • In a test we can pass a fake that just records messages (we do exactly that in OrderServiceTest).

3.5 Fix part 3 — the "assembler" (and the birth of IoC)

But wait — somebody still has to call new SmsNotificationService() and new OrderService(...). Where does that happen now? We move it into one special place: an assembler.

step2/ManualAssembler.javapublic class ManualAssembler {

    public static OrderService buildOrderService(String channel) {
        NotificationService notifier;
        if ("sms".equalsIgnoreCase(channel)) {
            notifier = new SmsNotificationService();     // 1. decide + create the dependency
        } else {
            notifier = new EmailNotificationService();
        }
        return new OrderService(notifier);               // 2. create the class and WIRE it
    }
}

The assembler does three jobs:

  1. Decides which implementation to use (configuration).
  2. Creates the objects.
  3. Wires them together (injects dependencies).

Before, OrderService was in control of creating its helper. Now the assembler is in control. Control has been turned upside down — inverted. That is the meaning of Inversion of Control (IoC).

3.6 IoC and DI — the two big words

TermSimple meaningIn our code
Inversion of Control (IoC)A principle: your classes do not control the creation and wiring of their dependencies. Something outside (a framework) does. "Don't call us, we'll call you."ManualAssembler (by hand) or Spring's ApplicationContext (automatic) is in control.
Dependency Injection (DI)A technique to achieve IoC: dependencies are handed to an object (via constructor, setter or field) instead of the object creating them.new OrderService(notifier) — the notifier is injected through the constructor.
💡 Remember it like this IoC is the idea ("someone else is in charge of creating objects"). DI is the most common way to do it ("hand the objects in"). In interviews people often say "IoC/DI" together — that is fine.

3.7 Why not just keep the hand-written assembler?

For three classes, a manual assembler is perfect. But in a real application with 300 classes:

  • The assembler becomes thousands of lines of new calls, and the order matters (create B before A if A needs B).
  • You want most objects created once and shared (one OrderService for the whole app) — you would have to code caching yourself.
  • You want extra features: run code after an object is created, clean up on shutdown, read settings from a file, use different objects in test vs production, add logging or transactions around methods…

Writing all that yourself means writing a framework. Spring already is that framework — tested by millions of developers for 20+ years. In Topic 18 you even built a tiny one with reflection; Spring is the industrial-strength version of the same idea.

3.8 The Spring container and beans

Two words you will hear every day from now on:

  • Spring container (also called the IoC container or application context): the object that creates, wires, stores and manages your objects. In code it is an ApplicationContext. It is our "kitchen manager".
  • Bean: any object that is created and managed by the Spring container. A bean is just a normal Java object — the only special thing is that Spring made it and keeps it. If you create an object yourself with new, it is not a bean.
Your configuration
(@Configuration, @Bean)→ Spring container
(ApplicationContext)→ Ready-to-use beans
(wired objects)

You give Spring instructions (configuration metadata) — "these are the objects I want, this is how they connect". Spring reads them at startup and builds everything.

3.9 Your first Spring configuration: @Configuration + @Bean

Let's replace the manual assembler with Spring. We write a configuration class:

step3/AppConfig.javaimport org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration                      // "This class contains bean recipes."
public class AppConfig {

    @Bean                           // "Call me once and keep what I return as a bean."
    public NotificationService notificationService() {
        return new SmsNotificationService();
    }

    @Bean                           // Spring passes the NotificationService bean in for us!
    public OrderService orderService(NotificationService notificationService) {
        return new OrderService(notificationService);
    }
}

Read it slowly:

  • @Configuration — an annotation (you learned annotations in Topic 18) that marks this class as a "recipe book" for beans.
  • @Bean on a method — "Spring, call this method and register the returned object as a bean". The bean name is the method name: notificationService and orderService.
  • The method orderService(NotificationService notificationService) has a parameter. Spring looks in its container for a bean of type NotificationService, finds the SMS one and passes it in. That is Spring doing dependency injection.

It looks a lot like ManualAssembler — and that is on purpose. The difference: Spring decides when to call these methods, in which order, keeps one instance of each, and gives you lots of extra features for free.

3.10 Starting the container: ApplicationContext

App.java (step 3)try (AnnotationConfigApplicationContext context =
             new AnnotationConfigApplicationContext(AppConfig.class)) {

    OrderService orderService = context.getBean(OrderService.class);   // ask for a ready bean
    orderService.placeOrder("meera@example.com", "Laptop Stand");
}
  • AnnotationConfigApplicationContext is a kind of ApplicationContext that reads annotation-based configuration (our AppConfig class).
  • When you write new AnnotationConfigApplicationContext(AppConfig.class), Spring starts up: reads AppConfig, calls the @Bean methods in the right order, and stores the results.
  • context.getBean(OrderService.class) — "give me the bean of type OrderService". You get a fully wired object.
  • We use try-with-resources (Topic 10) because the context is Closeable: closing it shuts Spring down cleanly (it destroys beans and releases resources).
ℹ️ Beans are singletons by default Ask for the same bean twice and you get the same object: context.getBean(NotificationService.class) == context.getBean(NotificationService.class) is true. Spring creates one instance and shares it. This is efficient and is what you want for "service" objects. (Topic 25 shows other options.)
⚠️ In real apps you rarely call getBean() We call getBean here only because main() is the entry point and lives outside Spring. Inside your application, beans get their dependencies injected — they never go looking for them. In Spring Boot you will almost never write getBean.

For topics 22–27 we use plain Spring (without Spring Boot) so you see what is really happening. The project needs just one Spring library:

spring-context is the IoC container. Thanks to transitive dependencies (Topic 20) it automatically brings:

To run a main() method with Maven we add the exec-maven-plugin and tell it which class to run:

pom.xml (build)<plugin>
    <groupId>org.codehaus.mojo</groupId>
    <artifactId>exec-maven-plugin</artifactId>
    <version>3.5.0</version>

Now mvn -q compile exec:java means: "compile the code, then run App.main() with all the dependency jars on the classpath". (-q = quiet, so you only see your program's output.)

We also set <maven.compiler.parameters>true</maven.compiler.parameters>. It keeps parameter names (like notificationService) inside the compiled .class files. Spring 6.1+ uses these names in some situations, so it's good to always switch it on. (Spring Boot does it for you.)

4.1 App.java — the three steps

src/main/java/com/course/whyspring/App.javapublic static void main(String[] args) {

    System.out.println("=== STEP 1: Tight coupling (new inside the class) ===");
    TightOrderService tight = new TightOrderService();
    tight.placeOrder("asha@example.com", "Java Book");

    System.out.println("=== STEP 2: Plain Java DI (interface + constructor + assembler) ===");
    OrderService emailOrders = ManualAssembler.buildOrderService("email");
    emailOrders.placeOrder("ravi@example.com", "Headphones");
    OrderService smsOrders = ManualAssembler.buildOrderService("sms");
    smsOrders.placeOrder("+91-98765-43210", "Coffee Mug");

    System.out.println("=== STEP 3: Spring IoC container (@Configuration + @Bean) ===");
    try (AnnotationConfigApplicationContext context =
                 new AnnotationConfigApplicationContext(AppConfig.class)) {

        OrderService orderService = context.getBean(OrderService.class);
        orderService.placeOrder("meera@example.com", "Laptop Stand");

        for (String name : context.getBeanDefinitionNames()) {
            if (!name.startsWith("org.springframework")) {     // hide Spring's internal beans
                System.out.println("     - " + name);
            }
        }

        NotificationService first = context.getBean(NotificationService.class);
        NotificationService second = context.getBean(NotificationService.class);
        System.out.println("Same NotificationService object both times? " + (first == second));
    }
}

Line by line for the tricky parts:

  • Step 2 uses the same OrderService class twice with two different notifiers. The class never changed — only the assembler's choice.
  • getBeanDefinitionNames() lists all beans in the container. Spring also registers a few internal helper beans whose names start with org.springframework; we hide those. What remains: appConfig (yes — the configuration class itself is also a bean!), notificationService and orderService.
  • first == second compares references (Topic 6). true proves both calls returned the very same object — the singleton default.

4.2 OrderServiceTest.java — DI pays off in testing

src/test/java/com/course/whyspring/order/OrderServiceTest.javastatic class FakeNotificationService implements NotificationService {
    final List<String> sent = new ArrayList<>();

    @Override
    public void send(String recipient, String message) {
        sent.add(recipient + " -> " + message);       // remember instead of really sending
    }

    @Override
    public String channel() { return "FAKE"; }
}

@Test
void placeOrderSendsExactlyOneConfirmation() {
    FakeNotificationService fake = new FakeNotificationService();
    OrderService service = new OrderService(fake);     // inject the fake by hand

    service.placeOrder("test@example.com", "Pen");

    assertEquals(1, fake.sent.size());
    assertEquals("test@example.com -> Your order for Pen is confirmed!", fake.sent.get(0));
}

Notice: no Spring in the test. Because OrderService uses constructor injection, a plain new OrderService(fake) is enough. Try writing this test for TightOrderService — you can't stop it from "sending" a real email. This is one of the biggest practical benefits of DI.

6. Common mistakes

⚠️ Mistake: creating the object yourself and expecting Spring to wire it OrderService s = new OrderService(null); — this object is not a bean. Spring never sees it, never injects anything into it, and you get a NullPointerException later.
Fix: let Spring create it (@Bean) and obtain it from the container (or, later, have it injected).
⚠️ Mistake: forgetting @Bean or @Configuration A method without @Bean is just a method — Spring ignores it. Then getBean(OrderService.class) fails with NoSuchBeanDefinitionException: No qualifying bean of type 'com.course.whyspring.order.OrderService' available.
Fix: read the message — it tells you exactly which type is missing. Add the @Bean method for it.
⚠️ Mistake: two beans of the same type If AppConfig had both an Email and an SMS @Bean of type NotificationService, Spring would not know which one you mean: NoUniqueBeanDefinitionException: expected single matching bean but found 2. (Exercise 4 lets you see this.)
Fix: keep one, or tell Spring which one to prefer (@Primary / @Qualifier — Topic 24).
⚠️ Mistake: depending on the concrete class instead of the interface public OrderService(SmsNotificationService sms) brings back tight coupling — Spring cannot fix a bad design.
Fix: constructor parameters should use the interface type (NotificationService).
🛑 Mistake: wrong import VS Code may suggest another @Bean or @Configuration from a different library. The correct ones are org.springframework.context.annotation.Bean and org.springframework.context.annotation.Configuration.
⚠️ Mistake: running mvn exec:java without compile exec:java runs the already-compiled classes. If you edited code and skipped compile, you run the old version (or get ClassNotFoundException on a fresh folder).
Fix: always mvn -q compile exec:java.

7. Best practices

  • Depend on interfaces, not concrete classes, when there can be more than one implementation (payment, notification, storage…).
  • Use constructor injection and mark the fields final. The object is complete and valid right after construction (Topic 24 explains in depth).
  • Keep business classes free of Spring code where possible. Our OrderService has zero Spring imports, so it's easy to test and reuse.
  • Keep the "wiring" in one place (configuration classes), not scattered across the code.
  • Don't call getBean() all over your code (this is called the Service Locator anti-pattern). Let dependencies be injected. getBean is fine in main() and in small demos.
  • Close the context (try-with-resources) so Spring can clean up resources such as database connections.
  • Write unit tests with fakes or mocks — DI makes this easy, so take advantage of it.

8. Key takeaways

  • A dependency is an object another object needs to do its job.
  • new inside a class = tight coupling: hard to change, hard to test, hidden needs.
  • Fix it with an interface + constructor injection + one place that creates and wires objects.
  • IoC: something outside your classes controls object creation. DI: dependencies are handed in.
  • The Spring container (ApplicationContext) is a professional, automatic assembler.
  • A bean is an object created and managed by Spring. By default each bean is a singleton.
  • @Configuration marks a recipe class; @Bean methods produce beans; method parameters get injected.
  • Plain Spring needs only spring-context; we run it with mvn -q compile exec:java.
  • Spring Boot = Spring + auto-configuration + starters + embedded server. Same core ideas.

Add a new channel. Create PushNotificationService (prints [PUSH]) and use it in Spring. Did OrderService need any change?

Hint / solution 
package com.course.whyspring.notification;

public class PushNotificationService implements NotificationService {

Medium

A second dependency. Create an interface InvoiceGenerator with a method String generate(String item) and an implementation PdfInvoiceGenerator. Make OrderService need both a NotificationService and an InvoiceGenerator (constructor with two parameters). Update the manual assembler, AppConfig and the test.

Hint / solution 
public interface InvoiceGenerator { String generate(String item); }

public class PdfInvoiceGenerator implements InvoiceGenerator {
    public String generate(String item) { return "invoice-" + item + ".pdf"; }
}

public class OrderService {
    private final NotificationService notificationService;
    private final InvoiceGenerator invoiceGenerator;

    public OrderService(NotificationService notificationService, InvoiceGenerator invoiceGenerator) {
        this.notificationService = notificationService;
        this.invoiceGenerator = invoiceGenerator;
    }

    public String placeOrder(String customer, String item) {
        String invoice = invoiceGenerator.generate(item);
        String message = "Your order for " + item + " is confirmed! Invoice: " + invoice;
        notificationService.send(customer, message);
        return message;
    }
}

// AppConfig - Spring injects BOTH parameters for you
@Bean
public InvoiceGenerator invoiceGenerator() { return new PdfInvoiceGenerator(); }

10. Interview questions

Q1. What is Inversion of Control (IoC)?

IoC is a design principle where the control of creating and connecting objects is moved from the application code to an external party — a framework or container. Instead of a class creating its own dependencies with new, the container creates them and gives them to the class. It's also called the Hollywood Principle: "Don't call us, we'll call you."

Q2. What is Dependency Injection? How is it related to IoC?

DI is a technique where an object receives its dependencies from outside (through the constructor, a setter or a field) rather than creating them itself. DI is the most common way to implement IoC. IoC is the general principle; DI is a concrete pattern.

Q3. What problems does tight coupling cause?

(1) Changes ripple — swapping one implementation forces you to edit every class that creates it. (2) Testing is hard — you can't replace real dependencies with fakes or mocks. (3) Dependencies are hidden inside the class. (4) Reuse is hard, because the class drags its specific helpers along.

Q4. What is a Spring bean?

A bean is an object that is instantiated, assembled (wired) and managed by the Spring IoC container. Apart from that it is a normal Java object (a POJO). Objects you create yourself with new are not beans.

Q5. What is the Spring IoC container? Name its main interfaces.

It's the part of Spring that reads configuration, creates beans, injects dependencies and manages their lifecycle. The main interfaces are BeanFactory (basic) and ApplicationContext (a richer extension used in practice). A common implementation for Java-based config is AnnotationConfigApplicationContext. Topic 23 compares them.

Q6. What do @Configuration and @Bean do?

@Configuration marks a class as a source of bean definitions. @Bean on a method tells Spring to call that method and register the returned object as a bean; the bean name defaults to the method name. Parameters of a @Bean method are resolved from the container — that's how dependencies get injected.

Q7. What is the default scope of a Spring bean?

Singleton — one shared instance per container. Every getBean or injection receives the same object. Other scopes like prototype, request and session exist (Topic 25).

Q8. What is the difference between Spring and Spring Boot?

Spring Framework provides the core features (IoC/DI, AOP, MVC, transactions). Spring Boot is built on top of it and adds auto-configuration, starter dependencies, an embedded web server, production features (Actuator) and opinionated defaults so you can create a runnable app with almost no setup. Boot doesn't replace Spring — it configures Spring for you.

Q9. Why is constructor injection good for unit testing?

Because the test can simply call the constructor with fakes or mocks: new OrderService(fakeNotifier). No container or reflection is needed, and the compiler forces you to provide every required dependency.

Q10. What benefits does Spring give compared to a hand-written factory/assembler?

Automatic dependency resolution and creation order, singleton management, lifecycle callbacks, scopes, profiles and externalized configuration, AOP (transactions, security, logging around methods), events, easy integration with databases, web, messaging — and a huge, well-tested ecosystem.
