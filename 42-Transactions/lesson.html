1. Why this matters

A money transfer is two database changes: take 100 from Alice, give 100 to Bob. What if the server crashes, the network drops, or a bug throws an exception between the two steps? Alice has lost 100 and Bob never got it. The bank just "destroyed" money.

The same problem appears everywhere: placing an order (create order + reduce stock + charge payment), registering a user (user row + role row + welcome-email record)... Whenever several changes belong together, you need a transaction: all changes succeed together, or none of them is saved.

In Spring this is one annotation: @Transactional. It looks simple, but it has rules that surprise even experienced developers — this lesson's project proves each rule with a demo endpoint and a test. Transactions are one of the most-asked topics in Spring interviews.

2. Real-life analogy

🏦 The bank clerk's tray Imagine an old bank. A clerk handles your transfer on a tray: she writes "Alice −100" on a slip and puts it on the tray, then "Bob +100" on another slip. Nothing is in the official ledger yet.
• If both slips are fine, she commits: copies them into the ledger together.
• If something goes wrong (Alice has no money, the phone line to Bob's branch is dead), she rolls back: throws the whole tray in the bin. The ledger never shows half a transfer.
• Other clerks can't see the slips on her tray until she commits (isolation).
• Once in the ledger, it's written in ink — even a power cut can't erase it (durability).
@Transactional is the tray. Spring hands the clerk a new tray when your method starts, and decides "ledger or bin" when your method ends.

3.2 From JDBC to @Transactional

In topic 19 you managed transactions by hand:

connection.setAutoCommit(false);
try {
    withdraw(connection, "ACC-1001", amount);
    deposit(connection, "ACC-1002", amount);
    connection.commit();
} catch (Exception e) {
    connection.rollback();
    throw e;
}

In Spring you write only the business logic and add one annotation:

@Transactional
public void transfer(...) {
    from.withdraw(amount);
    to.deposit(amount);
}

Spring generates the begin/commit/rollback code around your method. This is called declarative transaction management (you declare what you want). There's also programmatic management with TransactionTemplate for rare special cases.

3.3 What happens behind the scenes: the proxy

Remember topic 27 (AOP)? Transactions are the most famous "cross-cutting concern". When Spring sees @Transactional on a bean, it doesn't give other beans the real object — it gives them a proxy that wraps it:

Controller→ TransferService PROXY
1. begin transaction→ real TransferService.transfer()→ PROXY
2. commit, or rollback on exception

In pseudo-code, the proxy does this:

// generated by Spring (simplified)
public TransferResponse transfer(TransferRequest r) {
    TransactionStatus tx = transactionManager.getTransaction(definition);   // begin
    try {
        TransferResponse result = realService.transfer(r);                  // your code
        transactionManager.commit(tx);
        return result;
    } catch (RuntimeException | Error e) {
        transactionManager.rollback(tx);                                     // default rule
        throw e;
    }
}

Spring Boot auto-configures the JpaTransactionManager. Inside one transaction, all your repository calls share the same database connection and the same persistence context — that's also why lazy loading and dirty checking work inside @Transactional methods (topics 38 and 40).

In our project the log level of JpaTransactionManager is DEBUG, so you can read what the proxy does:

Creating new transaction with name [...TransferService.transferThatFailsMidway]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT
Suspending current transaction, creating new transaction with name [...AuditService.logInNewTransaction]
Initiating transaction commit                     <- the REQUIRES_NEW audit row is committed
Resuming suspended transaction after completion of inner transaction
Participating in existing transaction             <- REQUIRED audit + repository calls join
Initiating transaction rollback                   <- the crash -> everything else is undone
Rolling back JPA transaction on EntityManager [SessionImpl(...)]

3.4 Where to put @Transactional

  • On service methods — the service layer is where a "unit of work" (one business action) lives. Not on controllers, and usually not on repositories (Spring Data repository methods are already transactional individually).
  • On the class = applies to every public method of the class. On a method = overrides the class setting for that method.
@Service
@Transactional(readOnly = true)          // default for all methods: read-only
public class ProductService {
    public List<Product> findAll() { ... }          // read-only transaction

    @Transactional                                   // overrides: read-write
    public Product create(...) { ... }
}
⚠️ Only public methods, only calls from outside With Spring's default proxy mode, @Transactional works on public methods (Spring 6 also supports protected/package-private for class-based proxies, but stay with public) and only when the call comes from another bean through the proxy. See self-invocation below. Use org.springframework.transaction.annotation.Transactional (it has more options than jakarta.transaction.Transactional).

3.5 Rollback rules — the big surprise

Thrown from the methodDefault behaviour
Unchecked exception (RuntimeException and subclasses)✅ Rollback
Error (e.g. OutOfMemoryError)✅ Rollback
Checked exception (Exception but not RuntimeException, e.g. IOException)❌ COMMIT — whatever was done before the exception is saved!
Exception caught inside the method and not re-thrown❌ COMMIT — the proxy never sees it

Why? This rule comes from old Java EE (EJB), where checked exceptions were seen as "expected business outcomes" that might still want a commit. Today it mostly surprises people. Our demo /api/demo/checked-exception loses 100 because of it.

Change the rules with attributes:

@Transactional(rollbackFor = FraudCheckException.class)        // roll back for this checked exception too
@Transactional(rollbackFor = Exception.class)                  // roll back for every exception
@Transactional(noRollbackFor = EmailNotSentException.class)    // don't roll back for this unchecked one
💡 Simple rule for your own code Make your business exceptions unchecked (extend RuntimeException) — like InsufficientFundsException. Then the default rollback works, and your method signatures stay clean. If you must deal with checked exceptions, add rollbackFor.
⚠️ "Transaction silently rolled back because it has been marked as rollback-only" If an inner REQUIRED method throws a RuntimeException, the shared transaction is marked "rollback-only". Even if the outer method catches the exception and continues normally, the commit at the end fails with UnexpectedRollbackException. Catching exceptions doesn't "repair" a transaction.

3.6 Propagation — what if a transaction is already running?

When a @Transactional method calls another @Transactional method (on another bean), should the second one join the first transaction or start its own? That's propagation.

PropagationTransaction already runningNo transaction runningTypical use
REQUIRED (default)join itstart a new one99% of service methods
REQUIRES_NEWpause it, start a new independent onestart a new oneAudit logs, "save this no matter what"
SUPPORTSjoin itrun withoutRead methods that don't care
MANDATORYjoin it❌ exception"Must be called inside a transaction"
NOT_SUPPORTEDpause it, run withoutrun withoutLong non-DB work, demos

NESTEDsavepoint inside itstart a new onePartial rollback (JDBC savepoints; limited JPA support)

Demo: REQUIRED vs REQUIRES_NEW

service/AuditService.java@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logInNewTransaction(String message) { repository.save(new AuditLog(message, "REQUIRES_NEW")); }

@Transactional(propagation = Propagation.REQUIRED)
public void logInCallerTransaction(String message) { repository.save(new AuditLog(message, "REQUIRED")); }

transferThatFailsMidway calls both, then crashes. Result of /api/demo/rollback:

"auditLogsAfter": ["REQUIRES_NEW | [REQUIRES_NEW] attempt 100.00 ACC-1001 -> ACC-1002"]

The REQUIRED row joined the transfer's transaction and was rolled back with it. The REQUIRES_NEW row had already been committed in its own transaction — so the bank keeps a record of the failed attempt. 🎯

⚠️ REQUIRES_NEW uses a second database connection While the inner transaction runs, the outer one still holds its connection. Under heavy load with many REQUIRES_NEW calls you can exhaust the connection pool. Use it deliberately, not by default.

3.7 Isolation levels — in simple words

Many users use the database at the same moment. Isolation decides how much one transaction may see of another's work-in-progress. Three classic problems:

ProblemWhat happens (bank example)
Dirty readReport reads Alice = 900 while the transfer is still running; then the transfer rolls back. The report showed money that never existed.
Non-repeatable readYou read Alice's balance twice in one transaction and get 1000, then 900, because someone committed a change in between.
Phantom readYou count "accounts with balance > 500" twice and get 2, then 3, because someone inserted a new account in between.
Isolation levelDirty readNon-repeatable readPhantom readSpeed
READ_UNCOMMITTEDpossiblepossiblepossiblefastest
READ_COMMITTEDpreventedpossiblepossiblefast — default of PostgreSQL, Oracle, SQL Server, H2
REPEATABLE_READpreventedpreventedpossible*medium — default of MySQL (InnoDB)
SERIALIZABLEpreventedpreventedpreventedslowest, may cause retries

*MySQL InnoDB also avoids most phantoms at REPEATABLE_READ. Isolation.DEFAULT (Spring's default) means "use the database's default". Set it per method only when you need it:

@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)
public BigDecimal totalMoneyInBank() { ... }

Higher isolation doesn't solve the "lost update" problem of two users editing the same row in separate requests — that's what locking (3.10, 3.11) is for.

3.8 readOnly = true

  • Tells Hibernate it doesn't need to keep snapshots for dirty checking and won't flush → less memory and CPU for big reads.
  • The JDBC connection is marked read-only; some databases and routing setups (read replicas) use that.
  • It is a hint, not a security feature — don't rely on it to block writes.

Common pattern: @Transactional(readOnly = true) on the class, @Transactional on write methods.

3.9 The self-invocation pitfall

public void transferViaSelfInvocation(String from, String to, BigDecimal amount) {
    this.transferThatFailsMidway(from, to, amount);   // @Transactional IGNORED!
}

@Transactional
public void transferThatFailsMidway(...) { ... }

this is the real object, not the proxy. The call never passes through the proxy, so no transaction starts. Our demo loses 100. (Interesting detail in the demo output: both audit rows survive — the REQUIRED one too — because there was no outer transaction to join, so it got its own and committed.)

Fixes:

  1. Put @Transactional on the public entry method that is called from outside (most common fix).
  2. Move the transactional method into another bean (like AuditService) and inject it.
  3. Use TransactionTemplate programmatically for that block.
  4. (Inject the bean into itself with @Lazy — works, but is a code smell.)

The same pitfall applies to @Async, @Cacheable and every other proxy-based annotation (topics 51, 52).

3.10 Optimistic locking with @Version

Two bank employees open Alice's account at the same time (two browser tabs). Both see balance 1000. Employee A adds 10 and saves (1010). Employee B adds 20 to her old copy and saves (1020). A's change is silently lost — the lost update problem.

Optimistic locking: "conflicts are rare, so don't lock anything — just detect them at save time".

@Version
private Long version;
update accounts set balance=?, version=1 where id=? and version=0   -- A: 1 row updated  ✅
update accounts set balance=?, version=1 where id=? and version=0   -- B: 0 rows updated ❌ -> exception

Hibernate throws OptimisticLockException; Spring wraps it as ObjectOptimisticLockingFailureException. Our handler returns 409 Conflict ("someone else changed it, please reload"). The client can reload and retry. Send the version to the client in DTOs and back with updates, so the check also works across HTTP requests.

3.11 Pessimistic locking with @Lock

Pessimistic locking: "conflicts are likely or very expensive, so lock the row first". The database row is locked until the transaction ends; others must wait.

repository/AccountRepository.java@Lock(LockModeType.PESSIMISTIC_WRITE)                          // SELECT ... FOR UPDATE
@Query("SELECT a FROM Account a WHERE a.accountNumber = :number")
Optional<Account> findForUpdate(@Param("number") String accountNumber);
Optimistic (@Version)Pessimistic (@Lock)
IdeaDetect conflicts at write timePrevent conflicts by locking at read time
Database locksNoneRow locks until commit
On conflictException → retry or ask userSecond transaction waits
Best forWeb apps, low contention, long "think time" (user editing a form)Short, hot operations: money transfers, stock decrement, seat booking
RisksMany retries under high contentionWaiting, timeouts, deadlocks
💡 Avoiding deadlocks Transfer A→B locks A then B; at the same moment transfer B→A locks B then A. Each waits for the other forever — a deadlock (topic 17). Our transfer() always locks the two accounts in alphabetical order, so this can't happen. Also keep locked transactions short, and consider a lock timeout hint (jakarta.persistence.lock.timeout).

3.12 Testing transactions

@DataJpaTest and @Transactional test classes wrap each test in a transaction that is rolled back at the end. That's great for isolation — but it means your service calls join the test's transaction, so you can't observe commits, rollbacks or REQUIRES_NEW. For transaction behaviour, use a non-transactional @SpringBootTest and reset the data yourself, as our TransactionBehaviourTest does.

4.1 The correct transfer

service/TransferService.java@Transactional
public TransferResponse transfer(TransferRequest request) {
    auditService.logInNewTransaction("Transfer requested: " + request.amount() + " from "
            + request.fromAccount() + " to " + request.toAccount());       // survives a rollback

    if (request.fromAccount().equals(request.toAccount())) {
        throw new IllegalArgumentException("Cannot transfer to the same account");
    }

    // lock both rows, always in the same (alphabetical) order -> no deadlocks
    boolean fromFirst = request.fromAccount().compareTo(request.toAccount()) < 0;
    Account first  = lock(fromFirst ? request.fromAccount() : request.toAccount());
    Account second = lock(fromFirst ? request.toAccount() : request.fromAccount());
    Account from = fromFirst ? first : second;
    Account to   = fromFirst ? second : first;

    from.withdraw(request.amount());     // InsufficientFundsException -> rollback
    to.deposit(request.amount());        // managed entities: dirty checking, no save() needed

    Transfer saved = transferRepository.save(new Transfer(request.fromAccount(), request.toAccount(), request.amount()));
    return TransferResponse.from(saved);
}   // normal return -> COMMIT

6. Common mistakes

🛑 Catching the exception inside the transactional method 
@Transactional
public void transfer(...) {
    try { from.withdraw(a); to.deposit(a); }
    catch (Exception e) { log.error("failed", e); }   // swallowed -> the proxy COMMITS the half-done work
}
Fix: let it propagate, or re-throw, or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().
⚠️ Expecting rollback for checked exceptions Fix: unchecked business exceptions, or rollbackFor = ....
⚠️ Self-invocation this.someTransactionalMethod() runs without a transaction.
Fix: annotate the public entry method or move the method to another bean.
⚠️ @Transactional on a private method / a class not managed by Spring Ignored silently (you created the object with new, or the method isn't public).
Fix: public method on a Spring bean, called through injection.
⚠️ Long transactions Calling a slow external API or sending an email inside a transaction keeps a DB connection (and maybe row locks) busy for seconds.
Fix: do slow, non-DB work before or after the transaction (or with events after commit — @TransactionalEventListener, topic 52).
⚠️ @Transactional in tests hiding real behaviour Your test passes because everything is rolled back at the end, but in production the commit fails (e.g. a constraint violation at flush time).
Fix: for important flows, also test without a test transaction, or call flush() in the test.
⚠️ Ignoring ObjectOptimisticLockingFailureException A 500 error for a normal concurrency situation.
Fix: map it to 409 Conflict (as here), or retry automatically for idempotent operations.

7. Best practices

  • Transactions belong in the service layer, around one business use case.
  • @Transactional(readOnly = true) on the class, @Transactional on write methods.
  • Unchecked business exceptions so rollback works by default; use rollbackFor when dealing with checked ones.
  • Keep transactions short: no HTTP calls, file uploads or emails inside.
  • Use REQUIRES_NEW sparingly — for audit/outbox-style records that must survive.
  • Add @Version to entities that users edit; return 409 on conflicts.
  • Pessimistic locks only for short, hot operations; lock in a consistent order; set timeouts.
  • Keep the default isolation unless you have a specific anomaly to prevent.
  • Turn on JpaTransactionManager DEBUG logs when in doubt — they tell you exactly what happens.
  • Remember: one database = local transaction. Across microservices (topic 59+) there is no shared transaction — patterns like Saga and the Outbox are used instead.

8. Key takeaways

  • A transaction makes several changes atomic: all committed or all rolled back (ACID).
  • @Transactional works through an AOP proxy that begins, commits or rolls back around your method.
  • Default rollback: RuntimeException and Error. Checked exceptions commit unless you set rollbackFor.
  • REQUIRED joins the current transaction; REQUIRES_NEW runs in its own and survives the caller's rollback.
  • Isolation levels trade safety (dirty / non-repeatable / phantom reads) for speed; use the DB default unless needed.
  • readOnly = true is a performance hint for reads.
  • Self-invocation (this.method()) bypasses the proxy → no transaction.
  • @Version = optimistic locking (detect conflicts); @Lock(PESSIMISTIC_WRITE) = SELECT ... FOR UPDATE (prevent conflicts).

            new TransferRequest("ACC-1001", "ACC-1002", new BigDecimal("600.00"))))
            .isInstanceOf(TransferLimitExceededException.class);
    assertThat(balance("ACC-1001")).isEqualByComparingTo("1000.00");   // withdrawal rolled back
    assertThat(accountService.auditLogs()).hasSize(1);                 // REQUIRES_NEW audit kept
}

In real code you would check the limit before changing anything — but it's good to see that even a late failure is safe inside a transaction.

4. Version over HTTP. Add PUT /api/accounts/{number}/owner with body { "ownerName": "...", "version": 0 }. If the version in the body doesn't match, return 409.

Hint / solution
public record RenameRequest(@NotBlank String ownerName, @NotNull Long version) { }

@Transactional
public AccountResponse rename(String number, RenameRequest req) {
    Account a = accountRepository.findByAccountNumber(number).orElseThrow(() -> new AccountNotFoundException(number));
    if (!a.getVersion().equals(req.version())) {
        throw new ObjectOptimisticLockingFailureException(Account.class, a.getId());   // -> 409
    }
    a.setOwnerName(req.ownerName());   // add this setter to Account
    return AccountResponse.from(accountRepository.saveAndFlush(a));
}

Hibernate checks @Version against the version it loaded, not the one the client saw; the explicit comparison makes the check work across HTTP requests.

5. Retry on conflict. Write a method that deposits money and retries up to 3 times when an optimistic locking failure happens. Why must the retry loop be outside the transactional method?

Hint / solution
// in another bean (or the controller/DemoService) - NOT transactional
public void depositWithRetry(String number, BigDecimal amount) {
    for (int attempt = 1; ; attempt++) {
        try {
            accountTxService.deposit(number, amount);         // @Transactional method on another bean
            return;
        } catch (ObjectOptimisticLockingFailureException e) {
            if (attempt == 3) throw e;
        }
    }
}

After a failure, the transaction (and its persistence context) is unusable — it's marked rollback-only and holds stale data. Each retry needs a fresh transaction that reloads the entity, so the loop must call the transactional method from outside. (Spring Retry's @Retryable does this declaratively.)

10. Interview questions

Q1. What does ACID mean?

Atomicity (all or nothing), Consistency (constraints/invariants hold before and after), Isolation (concurrent transactions don't interfere / see partial work, according to the isolation level), Durability (committed changes survive failures).

Q2. How does @Transactional work internally?

Spring creates an AOP proxy (JDK dynamic proxy or CGLIB) around the bean. The TransactionInterceptor asks the PlatformTransactionManager (e.g. JpaTransactionManager) to begin or join a transaction according to the attributes, invokes the target method, then commits, or rolls back if the exception matches the rollback rules. Resources (connection, EntityManager) are bound to the current thread.

Q3. Which exceptions cause a rollback by default?

Unchecked exceptions (RuntimeException and subclasses) and Errors. Checked exceptions do not — the transaction commits. Customize with rollbackFor / noRollbackFor.

Q4. Explain REQUIRED vs REQUIRES_NEW.

REQUIRED (default) joins an existing transaction or creates one if none exists; an inner failure marks the whole transaction rollback-only. REQUIRES_NEW suspends the current transaction and starts an independent one that commits or rolls back on its own — e.g. for audit logs that must persist even if the outer transaction fails. It needs a second connection.

Q5. Why doesn't @Transactional work when calling a method from the same class?

Self-invocation calls the method on this, the target object, bypassing the proxy where the transactional advice lives. Solutions: annotate the outer public method, move the method into another bean, use TransactionTemplate, or use AspectJ weaving mode.

Q6. What are the isolation levels and which problems do they prevent?

READ_UNCOMMITTED (allows dirty, non-repeatable and phantom reads), READ_COMMITTED (prevents dirty reads), REPEATABLE_READ (also prevents non-repeatable reads), SERIALIZABLE (prevents all three, lowest concurrency). Isolation.DEFAULT uses the database default (READ_COMMITTED for PostgreSQL/Oracle/SQL Server, REPEATABLE_READ for MySQL InnoDB).

Q7. What does readOnly = true do?

It's an optimization hint: Hibernate sets flush mode to manual and can skip dirty-checking snapshots; the JDBC connection may be set read-only, which some drivers/databases and routing data sources use. It's not a guarantee that no writes happen.

Q8. Optimistic vs pessimistic locking?

Optimistic: no locks; a @Version column is checked in the UPDATE's WHERE clause; a mismatch throws OptimisticLockException — good for low contention and long user think-time. Pessimistic: SELECT ... FOR UPDATE (@Lock(PESSIMISTIC_WRITE)) locks rows until commit so others wait — good for short, highly contended operations, but risks waiting and deadlocks.

Q9. What is UnexpectedRollbackException?

Thrown at commit time when the transaction was marked rollback-only (e.g. an inner REQUIRED method threw a RuntimeException) but the outer code caught the exception and tried to commit normally. Spring rolls back and reports it, so the caller isn't misled into thinking the work was saved.

Q10. Should @Transactional be on the controller, service or repository?

On the service layer, where business use cases are defined and multiple repository calls must be atomic. Controllers should stay thin and not hold transactions open during serialization; repositories are fine-grained and Spring Data already makes each method transactional.
