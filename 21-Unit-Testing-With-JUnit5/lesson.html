21. Unit Testing with JUnit 5

Write small automatic tests that prove your code works — today, tomorrow and after every change — using JUnit 5, Mockito and AssertJ.

🎯 What you will learn
  • Why automated tests matter, and the test pyramid (unit → integration → end-to-end).
  • JUnit 5 basics: @Test, assertions, @BeforeEach/@AfterEach, @BeforeAll/@AfterAll, @DisplayName, @Nested.
  • Testing exceptions with assertThrows; grouping checks with assertAll.
  • One test, many inputs: @ParameterizedTest with @ValueSource and @CsvSource.
  • The AAA pattern (Arrange–Act–Assert) and good test naming.
  • Mockito: mocking a repository dependency to test a service in isolation (@Mock, @InjectMocks, when, verify).
  • AssertJ's readable assertThat(...) style.
  • Running tests with Maven (mvn test, Surefire) and in VS Code.

1. Why this matters

Until now you checked your code by running main and reading the output with your eyes. That works for 10 lines. It does not work when:

  • the project has 500 classes and you change one method — which of the other 499 did you just break?
  • a teammate changes your code six months later and doesn't know what it was supposed to do;
  • a bug that was fixed last month quietly comes back (a "regression").

An automated test is a small piece of code that calls your code and checks the result automatically. You write it once and run it thousands of times — in one second, on every change, on every teammate's laptop, and on the CI server before every deployment (Topic 68).

  • Confidence to change code — refactor freely; tests tell you within seconds if something broke.
  • Living documentation — a test named withdrawWithAlert_sendsAlertWhenBalanceDropsBelow100 explains a business rule better than a comment.
  • Better design — code that's easy to test is usually loosely coupled (dependencies passed in as interfaces). That's exactly the design Spring encourages.
  • Job requirement — professional teams don't merge code without tests. Interviewers ask about JUnit and Mockito all the time.

2. Real-life analogy

🚗 Testing a car before it leaves the factory
  • A unit test is testing one part on a test bench: does this brake pad stop the wheel? Fast, cheap, and if it fails you know exactly which part is broken.
  • An integration test checks that parts work together: brake pedal + hydraulic line + brake pad.
  • An end-to-end test is a test drive of the whole car on a real road. Very realistic, but slow and expensive, and if it fails you don't know which part is guilty.
  • A mock is a crash-test dummy or a simulator: to test the airbag, you don't put a real person in the car — you use a dummy that behaves the way you need and records what happened to it. Mockito gives you dummies for your class's dependencies (like a fake database).
  • An assertion is the inspector's checklist line: "stopping distance must be less than 40 m". Pass or fail — no opinions.

3.2 Your first JUnit 5 test

JUnit is the standard testing framework for Java. Version 5 is also called JUnit Jupiter (the package is org.junit.jupiter). Add it with one Maven dependency in test scope:

<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.11.4</version>
    <scope>test</scope>
</dependency>

Tests live in src/test/java, in the same package as the class they test, in a class named <ClassName>Test:

src/test/java/com/course/unittesting/CalculatorTest.javaimport static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

class CalculatorTest {

    @Test                               // "this method is a test - JUnit, please run it"
    void addsTwoNumbers() {
        Calculator calculator = new Calculator();
        int result = calculator.add(2, 3);
        assertEquals(5, result);        // expected, actual
    }
}
  • @Test marks a test method. (Remember Topic 18? JUnit finds these methods with reflection and invokes them.)
  • Test methods return void and take no parameters (except parameterized tests).
  • In JUnit 5, test classes and methods don't need to be public.
  • If every assertion passes and no exception escapes → the test passes (green ✅). If an assertion fails → failure (red ❌) with a message like expected: <5> but was: <6>. If an unexpected exception is thrown → error.
  • import static ...Assertions.assertEquals lets you write assertEquals instead of Assertions.assertEquals.

3.3 The most-used assertions

AssertionPasses when
assertEquals(expected, actual)they are equal (equals())
assertEquals(0.3, actual, 0.0001)doubles are equal within a tolerance
assertNotEquals(a, b)they differ
assertTrue(cond) / assertFalse(cond)the condition is true / false
assertNull(x) / assertNotNull(x)x is / isn't null
assertSame(a, b)same object (==)
assertIterableEquals(list1, list2)same elements in the same order
assertThrows(Type.class, () -> code)the code throws that exception type (returns it)
assertDoesNotThrow(() -> code)no exception
assertAll(() -> ..., () -> ...)all grouped assertions pass (reports every failure, not just the first)
assertTimeout(Duration.ofSeconds(1), () -> code)code finishes in time
fail("message")never — fails on purpose

Every assertion accepts an optional last argument: a message shown on failure — assertEquals(0, result, "anything times zero must be zero").

⚠️ Expected first! assertEquals(expected, actual). If you swap them, the test still works, but a failure message will say "expected: <6> but was: <5>" — the opposite of the truth, which confuses everyone.

3.4 The AAA pattern and naming

Structure every test in three clear parts:

Arrange — prepare objects & inputs→ Act — call the ONE method under test→ Assert — check the result 
@Test
void depositAddsAmountToBalance() {
    // Arrange
    when(repository.findById("ACC-1")).thenReturn(Optional.of(account("ACC-1", "100")));
    when(repository.save(any(Account.class))).thenAnswer(inv -> inv.getArgument(0));

    // Act
    Account result = service.deposit("ACC-1", new BigDecimal("50"));

    // Assert
    assertThat(result.getBalance()).isEqualByComparingTo("150");
}

(Some teams say Given–When–Then — same idea.) Naming: a test name should say what behaviour is checked, e.g. divideByZeroThrows, withdraw_insufficientFunds_throwsAndSavesNothing, or use @DisplayName("dividing by zero throws IllegalArgumentException") for a human-readable sentence in reports.

3.5 Test lifecycle annotations

AnnotationRunsTypical use
@BeforeEachbefore every test methodCreate a fresh object under test
@AfterEachafter every test methodClean up (delete temp files, clear data)
@BeforeAll (static)once, before all tests of the classExpensive shared setup (start a server)
@AfterAll (static)once, after all testsShut that down
@DisplayName("...")—Readable name in reports/IDE
@Nested—Group tests in an inner class (e.g. per method)
@Disabled("reason")—Skip a test temporarily (shows as "skipped")
@Tag("slow")—Label tests to include/exclude groups

Order for one test: @BeforeAll (once) → [@BeforeEach → test → @AfterEach] for each test → @AfterAll (once).

ℹ️ A new object for every test JUnit creates a new instance of the test class for each test method. That's why @BeforeAll must be static, and why one test can't leak state into another through fields. Tests must be independent: they may run in any order.

3.6 Testing exceptions

@Test
void divideByZeroThrows() {
    IllegalArgumentException ex = assertThrows(
            IllegalArgumentException.class,
            () -> calculator.divide(10, 0));     // code inside a lambda

    assertEquals("Cannot divide by zero", ex.getMessage());
}

Why a lambda? If you wrote calculator.divide(10, 0) directly, the exception would be thrown before assertThrows could catch it. The lambda hands JUnit the code to run inside its own try/catch. assertThrows returns the exception so you can check its message.

3.7 Parameterized tests

Instead of copying a test five times with different numbers, write it once and feed it data:

@ParameterizedTest(name = "{0} is even")
@ValueSource(ints = {0, 2, 4, 100, -8})            // one argument per run
void evenNumbers(int number) {
    assertTrue(calculator.isEven(number));
}

@ParameterizedTest(name = "{0} + {1} = {2}")
@CsvSource({                                        // several arguments per run
        "1,   1,   2",
        "-5,  5,   0",
        "100, 250, 350"
})
void addsManyPairs(int a, int b, int expected) {
    assertEquals(expected, calculator.add(a, b));
}
SourceGives
@ValueSource(ints/strings/doubles = {...})one simple value per run
@CsvSource({"a, b, c", ...})several values per run (comma-separated)
@CsvFileSource(resources = "/data.csv")rows from a CSV file in src/test/resources
@EnumSource(OrderStatus.class)every enum constant
@MethodSource("provider")a static method returning a Stream of arguments (any objects)
@NullSource, @EmptySource, @NullAndEmptySourcenull / "" — great for validation tests

Each data row shows up as a separate test in the report; name = "{0} + {1} = {2}" makes the names readable.

3.8 Dependencies make testing hard → mocks

Calculator was easy: no dependencies. Real classes — especially Spring services — use other objects:

BankAccountService→ uses → AccountRepository (database)
BankAccountService→ uses → NotificationService (sends SMS)

A unit test of BankAccountService should test its logic only. We don't want a real database (slow, needs setup, data changes between runs) or real SMS messages. So we replace the dependencies with test doubles:

Test doubleWhat it is
DummyPassed in but never used
StubReturns pre-programmed answers ("findById("ACC-1") returns this account")
FakeA simple working implementation, e.g. an in-memory repository with a HashMap
MockPre-programmed answers and records calls so you can verify them ("was save() called once?")
SpyA real object that also records calls; you can override some methods

This only works because the service gets its dependencies from outside, through the constructor, typed as interfaces:

public BankAccountService(AccountRepository repository, NotificationService notificationService) {
    this.repository = repository;
    this.notificationService = notificationService;
}

If the service did new JdbcAccountRepository() inside, you could never swap in a fake. This is dependency injection — the core idea of Spring (Topic 22). Testability is one of its biggest benefits.

3.9 Mockito basics

Mockito is the most popular mocking library for Java. It creates mock objects of interfaces or classes at runtime.

@ExtendWith(MockitoExtension.class)        // enables the annotations below
class BankAccountServiceTest {

    @Mock AccountRepository repository;            // a fake repository
    @Mock NotificationService notificationService; // a fake notifier
    @InjectMocks BankAccountService service;       // real service, mocks passed to its constructor
    ...
}

Stubbing — tell the mock what to return:

when(repository.findById("ACC-1")).thenReturn(Optional.of(account));   // fixed answer
when(repository.findById("NOPE")).thenReturn(Optional.empty());
when(repository.save(any(Account.class))).thenAnswer(inv -> inv.getArgument(0)); // echo the argument
when(repository.findById("BOOM")).thenThrow(new RuntimeException("DB down"));    // simulate failure

An un-stubbed method of a mock returns a "empty" default: null for objects, 0, false, an empty Optional/List.

Verifying — check how the service used the mock:

verify(repository).save(any(Account.class));                        // called exactly once
verify(repository, times(2)).save(any(Account.class));              // exactly twice
verify(notificationService, never()).sendLowBalanceAlert(anyString(), anyString());
verifyNoInteractions(notificationService);                           // not touched at all

Argument matchers: any(), any(Account.class), anyString(), eq("ACC-1"). Rule: if you use a matcher for one argument, use matchers for all arguments of that call (eq(...) for exact values).

ArgumentCaptor — grab the actual argument to inspect it:

@Captor ArgumentCaptor<Account> accountCaptor;

verify(repository).save(accountCaptor.capture());
assertThat(accountCaptor.getValue().getId()).isEqualTo("ACC-1");
💡 Stubbing vs verifying — when to use which? Stub what the code under test needs to get (queries: findById). Verify what the code under test is supposed to do to the outside world (commands: save, sendAlert). Don't verify every call — that makes tests fragile.
ℹ️ Strict stubs With MockitoExtension, if you stub something the test never uses, Mockito fails with UnnecessaryStubbingException. Annoying at first, but it keeps tests clean: every line of setup must matter. That's why, in our tests, save(...) is only stubbed in tests that actually reach the save.

3.10 AssertJ — fluent assertions

AssertJ offers a single entry point assertThat(actual) followed by a chain of checks. Type a dot and your IDE shows every check that makes sense for that type:

assertThat(calculator.add(2, 3)).isEqualTo(5).isPositive().isLessThan(10);
assertThat("Hello, Spring Boot").startsWith("Hello").contains("Spring").hasSize(18);
assertThat(fruits).hasSize(3).contains("banana").doesNotContain("mango");
assertThat(students).extracting(Student::name).containsExactly("Asha", "Ben");
assertThat(balance).isEqualByComparingTo("150");     // BigDecimal: ignores scale (150 vs 150.00)

assertThatThrownBy(() -> calculator.divide(1, 0))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessage("Cannot divide by zero");
JUnit assertionsAssertJ
assertEquals(5, result)assertThat(result).isEqualTo(5)
assertTrue(list.contains("x")) → failure says only "expected true"assertThat(list).contains("x") → failure shows the whole list
Built into JUnitExtra library — but included in Spring Boot's spring-boot-starter-test

Both are fine; many Spring teams prefer AssertJ. Don't mix styles randomly inside one test.

3.11 How tests are run: Surefire and the IDE

  • Maven: mvn test runs the test phase; the Surefire plugin finds classes named *Test, Test*, *Tests, *TestCase and runs them through the JUnit Platform. Reports go to target/surefire-reports. A failing test makes the build fail — so mvn package never produces a JAR from broken code.
  • VS Code: the Extension Pack for Java includes the Test Runner for Java. Green ▶ icons appear next to test classes and methods, and the Testing panel (flask icon) shows a tree of all tests with ✅/❌.
ℹ️ Coverage Code coverage measures which lines your tests executed. Tools: JaCoCo (Maven plugin, Topic 46) and VS Code's "Run with Coverage". Aim for meaningful coverage of business logic, not a magic 100%: a test without good assertions "covers" lines but proves nothing.

BankAccountService.java — the class under test

src/main/java/com/course/unittesting/bank/BankAccountService.javapublic Account withdraw(String accountId, BigDecimal amount) {
    requirePositive(amount);
    Account account = findAccount(accountId);          // repository.findById(...) or AccountNotFoundException

    if (account.getBalance().compareTo(amount) < 0) {
        throw new InsufficientFundsException(accountId, account.getBalance(), amount);
    }

    account.setBalance(account.getBalance().subtract(amount));
    Account saved = repository.save(account);

    if (saved.getBalance().compareTo(LOW_BALANCE_LIMIT) < 0) {
        notificationService.sendLowBalanceAlert(accountId, "Your balance is low: " + saved.getBalance());
    }
    return saved;
}

This one method has four behaviours worth testing: invalid amount, account not found, insufficient funds (nothing saved, no alert), success without alert, success with alert. Good tests cover each path.

BankAccountServiceTest.java — Mockito in action

src/test/java/com/course/unittesting/bank/BankAccountServiceTest.java@ExtendWith(MockitoExtension.class)
class BankAccountServiceTest {

    @Mock private AccountRepository repository;
    @Mock private NotificationService notificationService;
    @InjectMocks private BankAccountService service;

    @Test
    @DisplayName("sends a low-balance alert when the balance drops below 100")
    void withdrawWithAlert() {
        // Arrange
        when(repository.findById("ACC-1")).thenReturn(Optional.of(account("ACC-1", "150")));
        when(repository.save(any(Account.class))).thenAnswer(inv -> inv.getArgument(0));

        // Act
        service.withdraw("ACC-1", new BigDecimal("80"));      // 150 - 80 = 70

        // Assert
        verify(notificationService, times(1))
                .sendLowBalanceAlert(eq("ACC-1"), eq("Your balance is low: 70"));
    }

    @Test
    @DisplayName("throws InsufficientFundsException and saves nothing when money is missing")
    void insufficientFunds() {
        when(repository.findById("ACC-1")).thenReturn(Optional.of(account("ACC-1", "50")));

        assertThatThrownBy(() -> service.withdraw("ACC-1", new BigDecimal("80")))
                .isInstanceOf(InsufficientFundsException.class)
                .hasMessageContaining("balance 50");

        verify(repository, never()).save(any());
        verifyNoInteractions(notificationService);
    }
}

Line by line for withdrawWithAlert:

  • @InjectMocks builds new BankAccountService(repository, notificationService) with the two mocks.
  • when(repository.findById("ACC-1")).thenReturn(...) — the fake DB "contains" an account with 150.
  • thenAnswer(inv -> inv.getArgument(0)) — save returns the same account it receives, like a real repository. Without this the mock would return null and the service would crash on saved.getBalance().
  • verify(...).sendLowBalanceAlert(eq("ACC-1"), eq("Your balance is low: 70")) — the important outcome: the customer was alerted with the right message. No real SMS was sent.

The @Nested classes (GetBalance, Deposit, Withdraw, Transfer) group tests by method, so the report reads like a specification.

6. Common mistakes

⚠️ Mistake: tests that are never run The class is named CalculatorCheck, or it's in src/main/java, or @Test is imported from org.junit.Test (JUnit 4).
Fix: name test classes *Test, put them in src/test/java, import org.junit.jupiter.api.Test.
⚠️ Mistake: "Tests run: 0" Usually a JUnit 4/5 mix-up or a very old Surefire version.
Fix: use junit-jupiter and Surefire 3.x as in this pom.xml.
⚠️ Mistake: tests that depend on each other Test B only passes if test A ran first (shared static data, shared DB rows).
Fix: each test arranges its own data; use @BeforeEach for fresh objects.
⚠️ Mistake: NullPointerException in a Mockito test Forgetting @ExtendWith(MockitoExtension.class) (mocks stay null), or not stubbing a method whose result is used (mocks return null by default).
Fix: add the extension; stub what the code needs (e.g. save).
⚠️ Mistake: "Invalid use of argument matchers" verify(mock).send("ACC-1", anyString()) mixes a raw value with a matcher.
Fix: all matchers: verify(mock).send(eq("ACC-1"), anyString()).
⚠️ Mistake: UnnecessaryStubbingException You stubbed something the test never used.
Fix: remove that stub (it was noise), or move it into the tests that need it.
⚠️ Mistake: comparing BigDecimal with assertEquals assertEquals(new BigDecimal("150"), new BigDecimal("150.00")) fails: equals also compares the scale.
Fix: assertThat(x).isEqualByComparingTo("150") or assertEquals(0, a.compareTo(b)).
🚫 Mistake: tests without assertions A test that calls code but asserts nothing passes even when the code is wrong.
Fix: every test must check an outcome (return value, exception, or a verified interaction).
⚠️ Mistake: mocking everything Mocking simple value objects (records, Account) or the class under test itself makes tests meaningless.
Fix: mock dependencies at boundaries (repositories, external services), use real objects for data.

7. Best practices

  • FIRST principles: tests should be Fast, Independent, Repeatable (same result every time, no network/clock surprises), Self-validating (pass/fail, no reading output), Timely (written with the code, not months later).
  • One behaviour per test, clear AAA structure, descriptive names or @DisplayName.
  • Test behaviour, not implementation: check results and important side effects, not every internal call.
  • Cover the edges: zero, negative, empty, null, maximum, "not found", "not enough money".
  • Design for testability: constructor injection + interfaces (exactly what Spring promotes).
  • Use parameterized tests instead of copy-pasted tests.
  • Keep tests clean — they are code too. Helper methods like account("ACC-1", "500") make them short and readable.
  • Run tests on every build (mvn verify in CI) and fix a red build immediately.
  • Write a failing test first when fixing a bug — it proves the bug and prevents it from returning. (Writing tests before code in general is called TDD, Test-Driven Development: red → green → refactor.)

8. Key takeaways

  • Automated tests give fast, repeatable proof that code works and protect against regressions.
  • Test pyramid: many unit tests, fewer integration tests, very few end-to-end tests.
  • JUnit 5: @Test + assertions (assertEquals(expected, actual), assertThrows, assertAll).
  • Lifecycle: @BeforeEach/@AfterEach per test, static @BeforeAll/@AfterAll per class; a new test instance per method.
  • @ParameterizedTest with @ValueSource/@CsvSource runs one test with many inputs.
  • Arrange–Act–Assert keeps tests readable.
  • Mockito replaces dependencies: @Mock, @InjectMocks, when(...).thenReturn(...), verify(...), never(), ArgumentCaptor.
  • Constructor injection + interfaces make classes testable — the same design Spring uses.
  • AssertJ's assertThat(...) gives fluent, readable assertions and great failure messages.
  • mvn test runs everything via Surefire; a failing test fails the build.

10. Interview questions

Q1. What is unit testing and why is it important?

Testing the smallest units of code (methods/classes) in isolation, automatically. It catches bugs early, prevents regressions, enables safe refactoring, documents expected behaviour, encourages loosely coupled design, and runs quickly in CI on every change.

Q2. Explain the test pyramid.

A guideline for the proportion of tests: a broad base of fast, cheap unit tests; a middle layer of integration tests that check components working together (DB, web layer); and a small top of slow, brittle end-to-end/UI tests. It balances confidence, speed and maintenance cost.

Q3. What are the main differences between JUnit 4 and JUnit 5?

JUnit 5 = Platform + Jupiter + Vintage (to run JUnit 4 tests). Package org.junit.jupiter.api; @BeforeEach/@AfterEach/@BeforeAll/@AfterAll replace @Before/@After/@BeforeClass/@AfterClass; @Disabled replaces @Ignore; extensions (@ExtendWith) replace runners and rules; built-in assertThrows, assertAll, @DisplayName, @Nested, parameterized tests; test classes/methods needn't be public; requires Java 8+.

Q4. What is the difference between @BeforeEach and @BeforeAll?

@BeforeEach runs before every test method (fresh setup per test). @BeforeAll runs once before all tests in the class and must be static (unless the class uses @TestInstance(Lifecycle.PER_CLASS)); it's for expensive shared setup.

Q5. How do you test that a method throws an exception?

With assertThrows(ExpectedException.class, () -> code()), which returns the exception so you can assert on its message. In AssertJ: assertThatThrownBy(() -> code()).isInstanceOf(...).hasMessage(...).

Q6. What is mocking? Why use Mockito?

Mocking replaces a real dependency with a controllable fake that returns programmed answers and records interactions. It isolates the unit under test from slow or unpredictable collaborators (databases, web services, email), allows simulating errors, and lets you verify interactions. Mockito provides a simple API: mock/@Mock, when().thenReturn(), verify(), argument matchers and captors.

Q7. What is the difference between @Mock and @InjectMocks?

@Mock creates a mock object for a dependency. @InjectMocks creates a real instance of the class under test and injects the mocks into it (via constructor, setters or fields). Both require the Mockito extension (@ExtendWith(MockitoExtension.class)) or MockitoAnnotations.openMocks(this).

Q8. Mock vs stub vs spy vs fake?

A stub returns canned answers; a mock also records calls so they can be verified; a fake is a lightweight working implementation (e.g. in-memory repository); a spy wraps a real object, calling real methods unless stubbed, while recording interactions.

Q9. What is a parameterized test?

A test method executed multiple times with different arguments supplied by a source (@ValueSource, @CsvSource, @MethodSource, @EnumSource...). It removes duplication and makes it easy to cover many cases, each reported separately.

Q10. How does dependency injection help testing?

When a class receives its dependencies (ideally as interfaces through its constructor) instead of creating them, tests can pass mocks or fakes. This isolates the unit, makes tests fast and deterministic, and is exactly the pattern Spring uses for beans.
