1. Why this matters

So far every bean was created once and shared. That's perfect for a ProductCatalog — but what about a ShoppingCart? If Spring shares one cart between all customers, Alice suddenly finds Bob's monitor in her cart. This exact kind of bug happens in real projects, and it can leak one customer's data to another.

You also often need to run code at a specific moment:

  • After a connection pool is configured → open the connections.
  • After a cache bean is created → pre-load popular products.
  • When the app shuts down → close connections, flush files, stop background threads.

Spring gives you clean "hooks" for all of these. And the BeanPostProcessor you'll meet today is how Spring itself implements @Transactional, @Async, @Cacheable and AOP — so understanding it explains a lot of Spring "magic".

2. Real-life analogy

🏨 A hotel
  • The hotel has one reception desk, shared by every guest. That's a singleton. Because everyone uses it, the receptionist must not scribble one guest's private notes on the shared counter (keep singletons stateless).
  • Every guest gets their own fresh towel. That's a prototype: a new object every time someone asks. The hotel hands it over and doesn't track it afterwards — the guest is responsible for it (Spring doesn't destroy prototypes).
  • A room-service tray exists for one order only → request scope. Your room key card is valid for your whole stay → session scope.

And a room has a lifecycle: built (constructor) → furnished (dependencies injected) → inspected and cleaned (@PostConstruct) → open for guests (ready) → closed for renovation: guests moved out, power off (@PreDestroy).

3. Concepts step by step

3.1 What is a scope?

A bean's scope answers one question: "When someone asks for this bean, does Spring give the same object, or a new one?" — and for how long that object lives.

ScopeHow many objectsLives untilTypical useAvailable in
singleton (default)One per containerContainer closesServices, repositories, controllers — 95% of beansAll apps
prototypeA new one on every request for the beanYou drop it (garbage collector)Stateful helpers: carts, builders, per-task objectsAll apps
requestOne per HTTP requestThe request endsRequest-specific data (request id, current user info)Web apps
sessionOne per HTTP session (one user's visit)The session expires / logoutShopping cart, user preferences in server-side web appsWeb apps
applicationOne per web application (ServletContext)App stopsRare — similar to singletonWeb apps
websocketOne per WebSocket sessionSocket closesChat-style appsWeb apps

You set the scope with @Scope on the class (or on a @Bean method):

@Component
@Scope("prototype")                                     // or ConfigurableBeanFactory.SCOPE_PROTOTYPE
public class ShoppingCart { ... }

@Bean
@Scope("prototype")
public ReportBuilder reportBuilder() { return new ReportBuilder(); }

3.2 Singleton — one shared object

Without @Scope, a bean is a singleton. Every getBean and every injection gives the same object. Our demo proves it with System.identityHashCode — a number based on the object's identity (two different objects almost always print different numbers):

ProductCatalog (singleton) hash codes: 1989680860 / 1989680860 -> same object? true
ShoppingCart (prototype) hash codes:   1369901573 / 1471324717 -> same object? false
ℹ️ Spring singleton ≠ the "Singleton pattern" The classic Singleton design pattern (Topic 9) means "one instance per JVM", enforced with a private constructor and a static getInstance(). A Spring singleton means "one instance per container". The class itself is normal — you could still call new ProductCatalog() yourself, and two separate containers would each have their own.
⚠️ Singletons are shared by all threads In a web app, 100 users are served by 100 threads at the same time (Topic 17) — all calling the same singleton OrderService. If that service stores private String currentCustomer; in a field, users overwrite each other's data: a race condition. Rule: singleton beans must be stateless — keep only dependencies (other beans) and constants in fields. Per-user data goes in method parameters, local variables, or a properly scoped bean.

3.3 Prototype — a fresh object each time

cart/ShoppingCart.java@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class ShoppingCart {
    private final List<String> items = new ArrayList<>();   // state! one cart per customer
    ...
}

Important facts about prototypes:

  • Spring creates a new one for every getBean call and every injection point.
  • Prototypes are created on demand, not at startup (no point creating one that nobody asked for).
  • Spring runs initialisation callbacks (@PostConstruct) for them, but then forgets them. @PreDestroy is never called for a prototype — if it holds resources, you must clean up yourself.

3.4 Request and session scopes (web apps)

These only exist in a web application (Spring MVC, from Topic 31). They're explained here so you know the full picture; our console demo can't use them.

  • Request scope — one bean per HTTP request. When a browser calls GET /orders, Spring creates the bean for that request; when the response is sent, it's thrown away. Example: a RequestContext holding a request id for logging.
  • Session scope — one bean per user session. A session starts when a user first visits and lasts (usually ~30 minutes of inactivity) until timeout or logout. Example: a cart in a classic server-rendered shop (Topic 36).
@Component
@RequestScope          // shortcut for @Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestContext {
    private final String requestId = UUID.randomUUID().toString();
    public String requestId() { return requestId; }
}

@Component
@SessionScope          // one per logged-in user session
public class UserPreferences {
    private String language = "en";
    ...
}
ℹ️ How can a singleton controller use a request-scoped bean? The controller is created once at startup — when there is no request yet! So Spring injects a scoped proxy: a stand-in object. Each time you call a method on it, the proxy finds the real bean for the current request/session and forwards the call. @RequestScope and @SessionScope set this up automatically (proxyMode = TARGET_CLASS).
💡 Modern REST APIs REST APIs (Topics 31+) are usually stateless: no server-side session; the client sends a token with every request (Topic 49). So session scope is common in server-rendered apps but rare in REST APIs.

3.5 The bean lifecycle

Every singleton bean goes through the same stages. Here is the complete order, exactly as our DatabaseConnectionPool prints it:

In words:

  1. Instantiate — Spring calls the constructor (constructor injection happens here).
  2. Populate properties — setter and field injection.
  3. Aware callbacks — if the bean implements BeanNameAware, ApplicationContextAware, etc., Spring tells it its name / the context. (Rarely needed.)
  4. BeanPostProcessor "before" — every BPP sees the bean.
  5. @PostConstruct method runs.
  6. afterPropertiesSet() runs (if the bean implements InitializingBean).
  7. Custom init method runs (if declared with @Bean(initMethod = "...")).
  8. BeanPostProcessor "after" — may wrap the bean in a proxy. The bean is now ready.
  9. On shutdown: @PreDestroy,
  10. destroy() (DisposableBean),
  11. custom destroy method.
💡 Memory trick "Annotation → Interface → Custom", both for init (5→6→7) and destroy (9→10→11).

3.6 Why not just use the constructor for setup?

Look at line 1 of our output: constructor -> url=jdbc:h2:mem:shop, poolSize=0 (not set yet!). Inside the constructor, setter/field-injected values are not there yet. @PostConstruct runs after all injection is finished — the safe place for setup that needs dependencies. It's also the right place for work that might fail (opening connections, loading files), because Spring reports such failures clearly as "init method failed".

(With pure constructor injection, all dependencies are available in the constructor — but @PostConstruct is still commonly used for "start-up work" so constructors stay simple.)

3.7 The three ways to hook into init and destroy

<dependency>
    <groupId>jakarta.annotation</groupId>
    <artifactId>jakarta.annotation-api</artifactId>
    <version>2.1.1</version>
</dependency>

3.8 Closing the container — when destroy callbacks run

Destroy callbacks run only when the container is closed:

  • context.close() — explicitly (our demo), or via try-with-resources.
  • context.registerShutdownHook() — asks the JVM to close the context automatically when the program exits (even on Ctrl+C).
  • Spring Boot registers that shutdown hook for you.

Singletons are destroyed in reverse order of creation: a bean is destroyed before the beans it depends on, so it can still use them during cleanup.

3.9 BeanPostProcessor — a hook for every bean

A BeanPostProcessor (BPP) is a special bean that Spring calls for every other bean it creates — once before initialisation and once after:

lifecycle/LoggingBeanPostProcessor.java@Component
public class LoggingBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        if (bean instanceof DatabaseConnectionPool) {
            System.out.println("4. BeanPostProcessor -> BEFORE init of '" + beanName + "'");
        }
        return bean;          // return the bean (unchanged)
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (bean instanceof DatabaseConnectionPool) {
            System.out.println("8. BeanPostProcessor -> AFTER init of '" + beanName + "'");
        }
        return bean;          // could return a WRAPPER (proxy) instead!
    }
}

The key detail: whatever you return goes into the container. A BPP can return a different object — usually a proxy that wraps the original bean and adds behaviour before/after each method call. That's exactly how Spring implements:

  • @Transactional (start/commit a database transaction around a method) — Topic 42
  • @Async (run a method in another thread) — Topic 52
  • @Cacheable (return a cached result) — Topic 51
  • AOP aspects (logging, timing) — Topic 27

Even @PostConstruct itself is handled by a built-in BPP (CommonAnnotationBeanPostProcessor), and @Autowired by AutowiredAnnotationBeanPostProcessor — some of the internal beans you saw in Topic 23's bean list.

⚠️ BPPs are special Spring creates BPPs before all normal beans. Keep them simple and avoid injecting normal beans into them (those beans would be created too early and miss post-processing). When you define one with @Bean, make the method static. You will rarely write your own BPP — but knowing they exist explains a lot.

3.10 @Lazy — create on first use

By default the ApplicationContext creates all singletons at startup (eager — Topic 23). @Lazy delays one bean until it's first requested:

report/SalesReportService.java@Service
@Lazy
public class SalesReportService {
    public SalesReportService() {
        System.out.println("[lazy] SalesReportService constructor runs NOW (first use)");
    }
}

In the output its constructor line appears in demo 4, long after "container READY". Good for heavy, rarely used beans — but errors in it are discovered late. Note: if an eager bean injects a @Lazy bean normally, the lazy bean gets created anyway (the eager one needs it!) unless the injection point is also @Lazy.

Spring Boot can make all beans lazy with spring.main.lazy-initialization=true (faster startup in development, but use with care).

3.11 The trap: prototype inside a singleton

Here's a bug many developers make once:

cart/BrokenCheckoutService.java@Service                                   // singleton - created ONCE
public class BrokenCheckoutService {
    private final ShoppingCart cart;       // prototype - but injected only ONCE

    public BrokenCheckoutService(ShoppingCart cart) {
        this.cart = cart;
    }

    public ShoppingCart cartFor(String customer) {
        return cart;                       // everybody gets the same cart!
    }
}

The singleton's constructor runs once, so it receives one cart — forever. The prototype scope only means "new object each time the container is asked", and the container is asked only once here. Output:

BROKEN: alice's cart #1 = [Keyboard, Monitor]   <- bob's Monitor is in alice's cart!

The fix: don't inject a cart — inject something that can ask the container again: an ObjectProvider.

cart/CheckoutService.java@Service
public class CheckoutService {
    private final ObjectProvider<ShoppingCart> cartProvider;
    private final Map<String, ShoppingCart> cartsByCustomer = new HashMap<>();

    public CheckoutService(ObjectProvider<ShoppingCart> cartProvider) {
        this.cartProvider = cartProvider;
    }

    public ShoppingCart cartFor(String customer) {
        return cartsByCustomer.computeIfAbsent(customer, c -> cartProvider.getObject());   // NEW cart
    }
}
FIXED:  alice's cart #4 = [Keyboard, Mouse]
FIXED:  bob's cart #5   = [Monitor]
FixHowComment
ObjectProvider<T>Inject the provider, call getObject() when you need a fresh bean✅ Recommended — simple and explicit
@Lookup methodAn (abstract) method annotated @Lookup; Spring overrides it to return a new bean🟡 Works, a bit "magic"
Scoped proxy@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)🟡 Every method call hits a new object — usually surprising for prototypes; this is the normal tool for request/session scope
jakarta.inject.Provider<T>Same idea as ObjectProvider, standard Jakarta APINeeds the jakarta.inject jar
⚠️ Our demo keeps carts in a HashMap inside a singleton That's fine for a single-threaded console demo. In a real multi-user app you would use session scope or store carts in a database/Redis — a plain HashMap in a singleton is shared state and not thread-safe (use ConcurrentHashMap at the very least — Topic 17).

    @PostConstruct public void postConstruct() { ... }                   // 5

}

Even though the object is created by our own new inside a @Bean method, it's still a Spring bean — so Spring runs setter injection (@Autowired setter), the Aware callback, BPPs and all the init/destroy hooks on it.

4.2 Why is "ShoppingCart #1" created at startup?

The very first line of the output is [cart] new ShoppingCart #1 created — before the pool! That's because the singleton BrokenCheckoutService is created at startup and its constructor needs a ShoppingCart. So the prototype is created at that moment — once. Cart #1 is the cart that Alice and Bob will wrongly share in demo 3.

6. Common mistakes

🛑 Mistake: storing per-user data in a singleton's fields private Customer currentCustomer; in an @Service. Under load, users see each other's data.
Fix: keep singletons stateless — pass data as method parameters; use request/session scope or a database for per-user state.
⚠️ Mistake: injecting a prototype directly into a singleton and expecting fresh objects You get one instance forever (our BrokenCheckoutService).
Fix: inject ObjectProvider<T> and call getObject() each time.
⚠️ Mistake: @PostConstruct is silently ignored In plain Spring without jakarta.annotation-api on the classpath, the annotation can't even be imported. With the old javax.annotation.PostConstruct import, Spring 6 ignores it.
Fix: use jakarta.annotation.PostConstruct and add the dependency (Spring Boot has it).
⚠️ Mistake: expecting @PreDestroy on a prototype It's never called — Spring doesn't track prototypes after handing them out.
Fix: clean up prototypes yourself (e.g. make them AutoCloseable and use try-with-resources).
⚠️ Mistake: destroy callbacks never run The program ends without closing the context, so @PreDestroy never fires and connections aren't closed.
Fix: context.close(), try-with-resources, or context.registerShutdownHook(). (Spring Boot does this for you.)
⚠️ Mistake: using injected setter values inside the constructor They aren't set yet (see poolSize=0 in step 1).
Fix: use constructor injection, or do the work in @PostConstruct.
⚠️ Mistake: a @PostConstruct method with parameters or that is static It must be a non-static method with no parameters (any visibility, usually void).

7. Best practices

  • Default to singleton and design beans to be stateless and thread-safe.
  • Use prototype only for genuinely stateful, short-lived helpers — and get them via ObjectProvider when the consumer is a singleton.
  • Use @PostConstruct/@PreDestroy for your own classes; @Bean(initMethod, destroyMethod) for library classes. Avoid the Spring interfaces in new code.
  • Keep init methods fast; slow start-up work (warming a big cache) can slow every deployment — consider doing it asynchronously or on first use.
  • Always release resources in destroy callbacks: connections, thread pools, file handles.
  • Use @Lazy sparingly; eager creation catches configuration errors at startup.
  • Write a custom BeanPostProcessor only when you are building framework-like features; prefer AOP (Topic 27) for cross-cutting behaviour.

8. Key takeaways

  • Scope = how many instances and how long they live. Default is singleton (one per container).
  • Prototype = a new instance every time the container is asked; Spring doesn't destroy it.
  • Request/session scopes exist in web apps and are injected via scoped proxies.
  • Singletons are shared across threads → keep them stateless.
  • Lifecycle: constructor → injection → Aware → BPP before → @PostConstruct → afterPropertiesSet → initMethod → BPP after → ready → @PreDestroy → destroy → destroyMethod.
  • A BeanPostProcessor sees every bean and can replace it with a proxy — the basis of AOP, @Transactional, @Async.
  • @Lazy delays creation until first use.
  • Prototype injected into a singleton is created only once — use ObjectProvider.

Spring generated a subclass at runtime (CGLIB) that implements newCart() as "ask the container for a ShoppingCart". That's how an abstract class can be a bean. ObjectProvider does the same thing more explicitly, which is why it's usually preferred.

10. Interview questions

Q1. What bean scopes does Spring support?

singleton (default, one per container) and prototype (new instance per request to the container) in any application; request, session, application and websocket in web-aware contexts. Custom scopes can also be registered.

Q2. Is a Spring singleton bean thread-safe?

No — Spring does nothing to make it thread-safe. One instance is shared by all threads, so it's thread-safe only if it's stateless or its shared state is immutable/properly synchronised. Best practice: keep singletons stateless.

Q3. How is a Spring singleton different from the GoF Singleton pattern?

GoF Singleton guarantees one instance per class loader/JVM via a private constructor and static accessor. A Spring singleton is one instance per container per bean definition; the class is ordinary and can have several bean definitions or be instantiated manually.

Q4. Describe the Spring bean lifecycle.

Instantiation → property population (DI) → Aware callbacks (BeanNameAware, ApplicationContextAware…) → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct → InitializingBean.afterPropertiesSet() → custom init method → postProcessAfterInitialization (may return a proxy) → bean in use → on close: @PreDestroy → DisposableBean.destroy() → custom destroy method.

Q5. Does Spring call destroy methods on prototype beans?

No. Spring creates, configures and initialises a prototype, then hands it over and no longer manages it. The client is responsible for cleanup.

Q6. What is a BeanPostProcessor? Give real examples.

An extension point called for every bean before and after initialisation; it can modify the bean or return a wrapper. Spring uses BPPs to process @Autowired (AutowiredAnnotationBeanPostProcessor), @PostConstruct/@PreDestroy (CommonAnnotationBeanPostProcessor), and to create AOP proxies for @Transactional, @Async, @Cacheable and aspects.

Q7. What's the difference between BeanPostProcessor and BeanFactoryPostProcessor?

A BeanFactoryPostProcessor runs earlier and works on bean definitions (recipes) before any bean is created — e.g. PropertySourcesPlaceholderConfigurer resolving ${...}. A BeanPostProcessor works on bean instances after they're created.

Q8. How do you inject a prototype bean into a singleton so you get a new instance each time?

Inject ObjectProvider<T> (or jakarta.inject.Provider<T>) and call getObject() each time; or use a @Lookup method; or use a scoped proxy (proxyMode = ScopedProxyMode.TARGET_CLASS). Direct injection gives only one instance, because injection happens once.

Q9. What does @Lazy do?

On a bean: create it on first request instead of at startup. On an injection point: inject a lazy-resolution proxy so the target is created on first method call (also used to break circular dependencies). Trade-off: faster startup vs. later discovery of errors.

Q10. @PostConstruct vs constructor — where should initialisation logic go?

The constructor should only assign dependencies. @PostConstruct runs after all injection (including setter/field injection) is complete, so it's the safe place for initialisation that needs dependencies or may fail (opening resources, validating configuration, warming caches).
